二、知识点详解

知识点 K7-1：ENV 与 ARG 指令

定义

  • ENV 指令：在 Dockerfile 中设置环境变量，该变量在构建阶段和容器运行时都生效，并且会持久化到镜像元数据中。
  • ARG 指令：在 Dockerfile 中定义构建时参数（build-time argument），该变量仅在构建阶段生效，不会出现在运行时的容器中。

原理

ENV 的语法与作用范围：

# 两种语法形式
ENV KEY=VALUE                          # 推荐形式（一次设置一个或多个）
ENV KEY VALUE                          # 老式形式（一次只能一个，已不推荐）

# 示例：设置 JAVA_HOME 与 APP_HOME
ENV JAVA_HOME=/usr/lib/jvm/java-17-openjdk \
    APP_HOME=/app \
    APP_PORT=8080

# 后续 RUN 指令可以使用该变量
RUN echo "Java home is $JAVA_HOME" > /etc/java_info
# 容器运行时也生效
CMD ["sh", "-c", "echo $APP_PORT"]

ARG 的语法与作用范围：

# 语法
ARG NAME=default_value                 # 定义构建时参数，可给默认值

# 示例：让镜像版本可参数化
ARG JAVA_VERSION=17
ARG APP_VERSION=1.0.0

FROM openjdk:${JAVA_VERSION}            # ARG 可以用在 FROM 之前（声明在 FROM 之前是全局 ARG）
ARG APP_VERSION                          # FROM 之后需重新声明才能在当前阶段使用
LABEL app.version=${APP_VERSION}
RUN echo "Building app version ${APP_VERSION}"

ENV vs ARG 核心对比：

对比项 ENV ARG
生效阶段 构建 + 运行时 仅构建阶段
是否进入镜像元数据 是（docker inspect 可见） 否
运行时是否可用 是（echo $VAR 可读） 否
是否能用 docker run -e 覆盖 是（运行时覆盖，不修改镜像） 否（运行时无法访问）
是否能用 docker build --build-arg 覆盖 是（构建时覆盖） 是（这是 ARG 的主要用法）
能否声明在 FROM 之前 否（FROM 之前用 ARG） 是（全局 ARG，用于 FROM 参数化）
典型用途 设置 JAVA_HOME、应用配置、PATH 参数化基础镜像版本、版本号、构建开关

问题 / 场景

问：什么时候用 ENV，什么时候用 ARG？

  • 用 ENV 设置"运行时也需要"的变量：JAVA_HOME、APP_PORT、SPRING_PROFILES_ACTIVE、PATH 追加等。
  • 用 ARG 设置"只在构建时需要"的变量：基础镜像版本（JAVA_VERSION）、构建版本号、是否启用调试构建等。
  • 简记：运行时还要用 → ENV；只在 build 时用 → ARG。

问：ARG 里有敏感信息怎么办？

  • ARG 的值会出现在 docker history 中，不要用 ARG 传递密码、token、私钥。敏感信息应在运行时通过 docker run -e、Secret 文件或 K8s Secret 注入。

问：ARG 和 ENV 能配合用吗？

  • 能，且很常见。先 ARG 接收构建参数，再 ENV 固化到运行时：
ARG APP_VERSION=1.0.0
ENV APP_VERSION=${APP_VERSION}          # 把构建参数变成运行时环境变量

完整示例

# 文件名：Dockerfile.env-arg-demo
FROM eclipse-temurin:17-jre

# ARG：构建时参数（默认值 1.0.0）
ARG APP_VERSION=1.0.0
ARG BUILD_TIME=$(date +%Y-%m-%d)

# ENV：运行时环境变量（持久化到镜像）
ENV APP_HOME=/app \
    APP_PORT=8080 \
    APP_VERSION=${APP_VERSION} \
    SPRING_PROFILES_ACTIVE=prod

WORKDIR ${APP_HOME}

# 把构建信息写入文件，运行时可读
RUN echo "App Version: ${APP_VERSION}, Built at: ${BUILD_TIME}" > /app/build-info.txt

# COPY 应用 jar（假设同目录有 app.jar）
COPY app.jar ${APP_HOME}/app.jar

EXPOSE ${APP_PORT}

CMD ["java", "-jar", "/app/app.jar"]

构建与运行：

# 1. 使用默认 ARG 构建
docker build -t env-arg-demo:default -f Dockerfile.env-arg-demo .

# 输出：
# => [internal] load build definition from Dockerfile.env-arg-demo
# => [1/4] FROM docker.io/library/eclipse-temurin:17-jre
# => [2/4] WORKDIR /app
# => [3/4] RUN echo "App Version: 1.0.0, Built at: 2026-07-22" > /app/build-info.txt
# => [4/4] COPY app.jar /app/app.jar
# => exporting to image
# => exporting layers
# => writing image sha256:abc123...
# => naming to docker.io/library/env-arg-demo:default

# 2. 使用 --build-arg 覆盖 APP_VERSION
docker build --build-arg APP_VERSION=2.0.0 -t env-arg-demo:v2 -f Dockerfile.env-arg-demo .

# 3. 运行容器，验证 ENV 在运行时可用
docker run --rm env-arg-demo:v2 sh -c 'echo "APP_HOME=$APP_HOME"; echo "APP_VERSION=$APP_VERSION"; cat /app/build-info.txt'
# 输出：
# APP_HOME=/app
# APP_VERSION=2.0.0
# App Version: 2.0.0, Built at: 2026-07-22

# 4. 运行时用 -e 覆盖 ENV（不修改镜像）
docker run --rm -e SPRING_PROFILES_ACTIVE=dev env-arg-demo:v2 sh -c 'echo "PROFILE=$SPRING_PROFILES_ACTIVE"'
# 输出：PROFILE=dev

# 5. 用 docker history 查看 ARG 是否泄露（不要传密码！）
docker history env-arg-demo:v2 --no-trunc | grep APP_VERSION
# 输出可见 ARG 值出现在历史中：
# ENV APP_VERSION=2.0.0

图示

Docker 构建与运行阶段变量作用范围：

   构建阶段 (docker build)              运行阶段 (docker run)
  ┌──────────────────────┐           ┌──────────────────────┐
  │  ARG  ✓ 生效          │           │  ARG  ✗ 不可见        │
  │  ENV  ✓ 生效          │   ───→   │  ENV  ✓ 生效          │
  │  --build-arg 可覆盖 ARG│           │  -e 可覆盖 ENV         │
  └──────────────────────┘           └──────────────────────┘
        │                                    │
        └─ ARG 不进入镜像元数据                └─ ENV 进入镜像元数据
            （但会出现在 docker history）         （docker inspect 可见）

最佳实践：
  - 敏感信息 → 不放 ARG/ENV，用运行时注入
  - 构建参数 → ARG
  - 运行时配置 → ENV

易错点

  1. ❌ 误认为 ARG 在容器运行时也能用。✅ ARG 仅在构建阶段生效，运行时容器内不可见。
  2. ❌ 在 FROM 之前用 ENV。✅ FROM 之前只能用 ARG（全局 ARG），ENV 必须在 FROM 之后的构建阶段中。
  3. ❌ 用 ARG 传递密码、token。✅ ARG 值会出现在 docker history，敏感信息应运行时注入。
  4. ❌ 把可以运行时覆盖的配置写死成 ARG。✅ 应写成 ENV，便于运行时 -e 覆盖。
  5. ❌ 在多阶段构建中期望 ARG 自动跨阶段。✅ ARG 默认只在当前阶段生效，跨阶段需在每个阶段重新声明（全局 ARG 除外）。

小结

ENV 设置环境变量并持久化到镜像（构建 + 运行时都可用，可被 -e 覆盖）；ARG 仅在构建阶段生效（可被 --build-arg 覆盖，不进入运行时）。简记："运行时还要用 → ENV；只在 build 时用 → ARG"。

知识点 K7-2：EXPOSE 与 VOLUME 指令

定义

  • EXPOSE 指令：声明容器在运行时监听的端口，是一种文档化/声明性指令，本身不会真正把端口映射到宿主机。
  • VOLUME 指令：声明容器中某个路径为数据卷，运行时容器会自动在该路径创建一个匿名数据卷（如果用户没有通过 -v 显式挂载），用于持久化数据。

原理

EXPOSE 的作用：

# 语法
EXPOSE <port> [<port>/<protocol>...]
# 示例
EXPOSE 8080
EXPOSE 80/tcp 443/tcp

EXPOSE 的作用是声明性的：

  1. 它告诉使用者（运维、开发）这个镜像运行起来会监听哪些端口，相当于"使用说明"。
  2. 它会在 docker inspect 中显示声明的端口。
  3. 在使用 -P（大写 P，自动映射）时，Docker 会自动把 EXPOSE 声明的端口映射到宿主机随机高位端口。
  4. 它不会自动把端口映射到宿主机——必须用 -p 或 -P 才能从宿主机访问。

VOLUME 的作用：

# 语法
VOLUME ["<path>"]                     # JSON 数组形式（推荐）
VOLUME <path>                          # 字符串形式
# 示例
VOLUME ["/var/lib/mysql", "/data/logs"]
VOLUME /data

VOLUME 的作用：

  1. 声明该路径为数据卷，容器运行时，如果用户没有用 -v 显式挂载，Docker 会自动在 /var/lib/docker/volumes/ 下创建一个匿名卷挂载到该路径。
  2. 该路径的数据不会随容器删除而消失（因为存在卷里）。
  3. 主要用于数据库数据、日志、上传文件等需要持久化的场景。

声明性指令 vs 实际操作：

指令 性质 是否自动生效 实际操作靠什么
EXPOSE 8080 声明性 否（不自动映射） docker run -p 8080:8080 或 -P
VOLUME /data 半声明+半自动 是（运行时自动挂匿名卷） docker run -v /host:/data 显式挂载更可控

问题 / 场景

问：EXPOSE 写了端口，为什么外面还是访问不了？

  • 因为 EXPOSE 只是"声明"，没有真正映射。要从宿主机访问容器端口，必须用 docker run -p 宿主端口:容器端口（小写 p，显式映射）或 -P（大写 P，自动映射所有 EXPOSE 端口到随机高位端口）。

问：VOLUME 写了路径，运行时还需要 -v 吗？

  • 不写也行：Docker 会自动挂一个匿名卷，数据能持久化，但卷名是随机的（一长串 hash），管理不便。
  • 推荐写 -v 具名卷名:路径 或 -v 宿主路径:路径，便于管理、备份、迁移。
  • 生产环境几乎都用显式 -v，不依赖 Docker 自动挂匿名卷。

问：为什么说 EXPOSE 和 VOLUME 是"声明性"指令？

  • 因为它们的主要作用是告知而不是操作。EXPOSE 告知"我会监听这个端口"，VOLUME 告知"这个路径需要持久化"。这样的"声明"让镜像更可读、更可复用，符合"镜像即文档"的工程规范。

完整示例

# 文件名：Dockerfile.expose-volume-demo
FROM mysql:8.0

# 声明端口
EXPOSE 3306

# 声明数据卷（MySQL 数据目录）
VOLUME ["/var/lib/mysql"]

# 设置环境变量（MySQL 必需）
ENV MYSQL_ROOT_PASSWORD=123456 \
    MYSQL_DATABASE=ctts

# 声明默认配置文件位置
EXPOSE 3306

构建与运行：

# 1. 构建
docker build -t mysql-ctts:demo -f Dockerfile.expose-volume-demo .
# 输出：
# => [internal] load build definition from Dockerfile.expose-volume-demo
# => [1/2] FROM docker.io/library/mysql:8.0
# => [2/2] DONE
# => exporting to image
# => naming to docker.io/library/mysql-ctts:demo

# 2. 用 -P 自动映射 EXPOSE 声明的端口
docker run -d --name mysql-auto -P mysql-ctts:demo
# 输出容器 ID：3a4b5c6d7e8f...

# 3. 查看自动映射的端口
docker port mysql-auto
# 输出：
# 3306/tcp -> 0.0.0.0:49153
# 3306/tcp -> :::49153
# 解读：容器 3306 → 宿主机 49153（随机高位端口）

# 4. 用 -p 显式映射
docker run -d --name mysql-explicit -p 13306:3306 mysql-ctts:demo

# 5. 用具名卷挂载（推荐，比匿名卷更可控）
docker volume create mysql-ctts-data
docker run -d --name mysql-named \
  -p 13307:3306 \
  -v mysql-ctts-data:/var/lib/mysql \
  mysql-ctts:demo
# 输出容器 ID：7f8e9d0c1b2a...

# 6. 查看挂载的卷
docker inspect mysql-named --format '{{json .Mounts}}' | python -m json.tool
# 输出：
# [
#     {
#         "Type": "volume",
#         "Name": "mysql-ctts-data",
#         "Source": "/var/lib/docker/volumes/mysql-ctts-data/_data",
#         "Destination": "/var/lib/mysql",
#         "Driver": "local",
#         "Mode": "z",
#         "RW": true
#     }
# ]

# 7. 即使不写 -v，VOLUME 指令也会让 Docker 自动挂匿名卷
docker run -d --name mysql-anon mysql-ctts:demo
docker inspect mysql-anon --format '{{json .Mounts}}' | python -m json.tool
# 输出：
# [
#     {
#         "Type": "volume",
#         "Name": "abc123def456...",       ← 匿名卷名（hash）
#         "Source": "/var/lib/docker/volumes/abc123def456.../_data",
#         "Destination": "/var/lib/mysql"
#     }
# ]

  •         直接挂宿主目录

易错点

  1. ❌ 误认为 EXPOSE 会自动映射端口。✅ EXPOSE 只是声明，要真映射必须用 -p 或 -P。
  2. ❌ 把 EXPOSE 写在 FROM 之前。✅ EXPOSE 必须在构建阶段（FROM 之后）。
  3. ❌ 误认为 VOLUME 写了就一定要用 -v。✅ 不写 -v Docker 也会自动挂匿名卷；但生产推荐显式 -v 具名卷便于管理。
  4. ❌ 在 Dockerfile 中用 VOLUME 挂载具体宿主路径。✅ Dockerfile 中 VOLUME 只能写容器内路径，宿主路径只能在 docker run -v 时指定。
  5. ❌ VOLUME 路径下的数据在构建阶段就期望被持久化。✅ VOLUME 仅在运行时生效，构建阶段（RUN）写入该路径的数据会被运行时挂载的卷覆盖。

小结

EXPOSE 与 VOLUME 都是声明性指令：EXPOSE 告诉使用者"我会监听这些端口"（需配合 -p/-P 真正映射）；VOLUME 告诉使用者"这个路径需要持久化"（不挂 -v 时 Docker 自动挂匿名卷，生产推荐显式挂具名卷）。声明性指令让镜像自带"使用说明"，提升可读性与规范性。

知识点 K7-3：CMD 指令

定义

CMD 指令：为容器指定默认启动命令。每个 Dockerfile 只能有一个 CMD（如果有多个，只有最后一个生效）。CMD 可以被 docker run 后面的参数覆盖。

原理

CMD 有三种形式：

# 1. exec 形式（推荐！JSON 数组）
CMD ["executable","param1","param2"]
# 示例：CMD ["java","-jar","/app/app.jar"]

# 2. shell 形式（命令字符串）
CMD command param1 param2
# 示例：CMD java -jar /app/app.jar

# 3. 作为 ENTRYPOINT 的默认参数（K7-4 详讲）
CMD ["param1","param2"]

exec 形式 vs shell 形式：

对比项 exec 形式 CMD ["java","-jar","app.jar"] shell 形式 CMD java -jar app.jar
实际执行 直接 exec 该命令（进程 PID=1） 通过 /bin/sh -c "java -jar app.jar" 执行
PID 1 是该命令本身 是 /bin/sh，命令是它的子进程
信号传递 能正确接收 SIGTERM（docker stop 优雅退出） sh 不转发信号给子进程，docker stop 会超时强杀
环境变量 不会自动展开（需用 shell 解析） 会通过 sh 自动展开 $VAR
推荐度 ✅ 推荐生产使用 ⚠️ 不推荐（除非要用 shell 特性）

CMD 被 docker run 参数覆盖：

# Dockerfile 中：
#   CMD ["java","-jar","/app/app.jar"]

# 正常运行（使用 CMD 默认命令）
docker run -it myapp
# 实际执行：java -jar /app/app.jar

# 用 docker run 参数覆盖 CMD
docker run -it myapp sh -c "echo hello"
# 实际执行：sh -c "echo hello"  ← CMD 被完全替换！

docker run -it myapp bash
# 实际执行：bash  ← CMD 被替换为 bash，进入交互式 shell

问题 / 场景

问：为什么 docker stop 我的容器要等 10 秒才停？

  • 大概率是因为你的 CMD 用了 shell 形式（CMD java -jar app.jar），实际进程是 /bin/sh，PID 1 是 sh，它不会把 SIGTERM 转发给 java 进程。docker stop 默认 10 秒超时后强杀（SIGKILL）。
  • 解决：用 exec 形式 CMD ["java","-jar","app.jar"]，java 进程成为 PID 1，能直接收到 SIGTERM 优雅退出。

问：CMD 和 RUN 有什么区别？

  • RUN 在构建阶段执行，每条 RUN 产生一个镜像层（如 RUN apt install -y curl）。
  • CMD 在运行阶段执行（容器启动时），不产生镜像层，只是指定容器默认启动命令。
  • 简记：RUN 是构建时做事，CMD 是运行时启动。

问：Dockerfile 里写多个 CMD 会怎样？

  • 只有最后一个 CMD 生效，前面的会被覆盖。Dockerfile 规范建议只写一个 CMD。

完整示例

WORKDIR /app

# 假设同目录有 app.jar
COPY app.jar /app/app.jar

ENV APP_PORT=8080

# exec 形式（推荐）
CMD ["java", "-jar", "/app/app.jar"]

易错点

  1. ❌ 用 shell 形式 CMD java -jar app.jar 导致信号传递问题。✅ 用 exec 形式 CMD ["java","-jar","app.jar"]。
  2. ❌ 在 exec 形式中使用 shell 特性（如 CMD ["java","-jar","$APP_HOME/app.jar"]）。✅ exec 形式不会展开 $VAR，要用 sh -c 包装：CMD ["sh","-c","java -jar $APP_HOME/app.jar"]。
  3. ❌ 写多个 CMD 期望都执行。✅ 只有最后一个 CMD 生效。
  4. ❌ 期望 CMD 在构建时执行。✅ CMD 在容器启动时执行，构建时不执行。
  5. ❌ 混淆 CMD 与 RUN。✅ RUN 构建时执行并产生层，CMD 运行时执行不产生层。

小结

CMD 指定容器默认启动命令，可被 docker run 参数覆盖。推荐用 exec 形式（CMD ["java","-jar","app.jar"]），让进程成为 PID 1，能正确接收 SIGTERM 信号优雅退出。每个 Dockerfile 只能有一个 CMD（多个时只有最后一个生效）。

知识点 K7-4：ENTRYPOINT 指令

定义

ENTRYPOINT 指令：为容器指定入口点程序。与 CMD 不同，ENTRYPOINT 不会被 docker run 后参数覆盖——docker run 后的参数会作为 ENTRYPOINT 的追加参数传入。这让 ENTRYPOINT 适合做"固定入口 + 可变参数"的镜像。

原理

ENTRYPOINT 同样有 exec 形式和 shell 形式：

# exec 形式（推荐）
ENTRYPOINT ["executable","param1","param2"]
# 示例：ENTRYPOINT ["java","-jar","/app/app.jar"]

# shell 形式（不推荐，同 CMD 的信号问题）
ENTRYPOINT command param1 param2

ENTRYPOINT 与 CMD 的核心对比：

对比项 CMD ENTRYPOINT
作用 默认启动命令 入口点程序
是否被 docker run 参数覆盖 是（完全替换） 否（参数作为 ENTRYPOINT 的追加参数）
是否能被 --entrypoint 覆盖 是（但少见） 是（docker run --entrypoint）
一个 Dockerfile 可有几个 多个时最后一个生效 多个时最后一个生效
典型用途 给默认参数、可被覆盖的命令 固定入口程序，参数化运行
是否可单独使用 是 是
是否推荐与对方组合 推荐与 ENTRYPOINT 组合 推荐与 CMD 组合

ENTRYPOINT + CMD 组合模式（生产推荐）：

# 入口点：固定执行 java -jar app.jar
ENTRYPOINT ["java","-jar","/app/app.jar"]

# 默认参数：--spring.profiles.active=prod
CMD ["--spring.profiles.active=prod"]

组合效果：

  • docker run myapp → 执行 java -jar /app/app.jar --spring.profiles.active=prod（用默认 CMD 参数）
  • docker run myapp --spring.profiles.active=dev → 执行 java -jar /app/app.jar --spring.profiles.active=dev（CMD 被 dev 覆盖，ENTRYPOINT 不变）
  • docker run myapp --debug → 执行 java -jar /app/app.jar --debug（参数追加到 ENTRYPOINT）

CMD 与 ENTRYPOINT 各种组合的行为：

组合 ENTRYPOINT CMD 实际执行 docker run 参数行为
只有 CMD 无 ["java","-jar","app.jar"] java -jar app.jar 替换 CMD
只有 ENTRYPOINT ["java","-jar","app.jar"] 无 java -jar app.jar 追加到 ENTRYPOINT 后
ENTRYPOINT + CMD ["java","-jar","app.jar"] ["--spring.profiles.active=prod"] java -jar app.jar --spring.profiles.active=prod 替换 CMD 部分，追加到 ENTRYPOINT
ENTRYPOINT shell + CMD exec java -jar app.jar（shell） ["--debug"]（exec） java -jar app.jar （CMD 被忽略！） shell 形式会忽略 CMD
都没有 无 无 报错（无启动命令） 启动失败

问题 / 场景

问：ENTRYPOINT 和 CMD 到底选哪个？

  • 如果你的镜像只是"启动一个固定命令"，两者都行，但用 CMD 更灵活——使用者可以 docker run myapp bash 临时进入 shell 调试。
  • 如果你的镜像是一个"可参数化工具"（如 myapp --port=8080、myapp --debug），用 ENTRYPOINT——保证入口固定，参数可变。
  • 生产推荐组合模式：ENTRYPOINT 固定可执行程序，CMD 给默认参数，既保入口又可覆盖。

问：为什么说 ENTRYPOINT 适合做"工具镜像"？

  • 例如做一个 curl 工具镜像：
FROM alpine:3.18
RUN apk add --no-cache curl
ENTRYPOINT ["curl"]
CMD ["--help"]
  • docker run curl-img → 执行 curl --help
  • docker run curl-img https://example.com → 执行 curl https://example.com
  • docker run curl-img -s -o /dev/null -w "%{http_code}" https://example.com → 执行带选项的 curl
  • 这就是 ENTRYPOINT 的"工具镜像"用法。

问：怎么覆盖 ENTRYPOINT？

  • 用 docker run --entrypoint 参数：
# 原 ENTRYPOINT 是 java -jar app.jar
docker run --entrypoint bash myapp
# 实际执行 bash（覆盖了 ENTRYPOINT）

知识点 K7-5：多阶段构建

定义

多阶段构建（Multi-stage Build） 是 Docker 17.05+ 引入的特性，允许在一个 Dockerfile 中使用多个 FROM 指令，每个 FROM 开启一个新阶段（stage），最终镜像只保留最后一个阶段的内容，前面阶段的产物可以通过 COPY --from=<阶段名> 拷贝过来，但前面阶段的镜像层、依赖、工具等都不会进入最终镜像。

原理

多阶段构建的语法：

# 第一阶段：构建阶段（命名 builder）
FROM maven:3.8-openjdk-17 AS builder
WORKDIR /build
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# 第二阶段：运行阶段（最终镜像）
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
# 从 builder 阶段拷贝构建产物
COPY --from=builder /build/target/*.jar /app/app.jar
EXPOSE 8080
CMD ["java","-jar","/app/app.jar"]

为什么多阶段能减小镜像体积：

图示 4：单阶段构建与多阶段构建对比
单阶段构建

构建工具被带进最终镜像

  • Maven、JDK、源码、target 旧产物都可能留在镜像里。
  • 运行时真正需要的只是 JRE + app.jar。
  • 示例体积约 645MB，攻击面也更大。
多阶段构建

只保留运行时产物

  • builder 阶段负责编译，最终会被丢弃。
  • runtime 阶段只拷贝 app.jar。
  • 示例体积约 110MB，镜像更小更干净。

多阶段构建的核心价值：

  1. 减小镜像体积：运行镜像只保留"运行所需"，构建工具、源码、中间产物全部丢弃。
  2. 安全性提升：镜像里没有编译器、调试工具，攻击面减小。
  3. 构建与运行解耦：构建阶段可以用重型镜像（含全部工具），运行阶段用精简镜像（只含运行时）。
  4. 单一 Dockerfile：不需要写多份 Dockerfile 或用 CI 脚本拼接，一个 Dockerfile 完成全流程。

问题 / 场景

问：以前没有多阶段构建是怎么做的？

  • 老办法 1：写两份 Dockerfile（Dockerfile.build + Dockerfile.run），用脚本串起来——构建镜像跑出 jar，再从构建容器里把 jar 拷出来，再用运行镜像打包。复杂、易错、脚本维护成本高。
  • 老办法 2：用"builder pattern"shell 脚本，手动 docker cp 拷贝产物。
  • 多阶段构建一个 Dockerfile 解决，是官方推荐方案。

问：多阶段构建中怎么命名阶段？

  • 用 FROM <image> AS <name> 命名：
FROM maven:3.8-openjdk-17 AS builder
FROM node:18 AS frontend
FROM eclipse-temurin:17-jre-alpine AS runtime
  • 用名字引用：COPY --from=builder /build/target/*.jar /app/app.jar
  • 也可以用阶段序号引用：COPY --from=0 /build/target/*.jar /app/app.jar（不推荐，可读性差）

问：能不能从前一个阶段拷贝文件到后一个阶段？反向呢？

  • 只能后拷前：后面的阶段可以用 COPY --from=<前面的阶段> 拷贝前面阶段的文件。
  • 不能前拷后：前面的阶段无法访问后面阶段的文件（执行顺序决定）。

  1. ❌ 在多阶段构建中期望前面阶段的镜像层进入最终镜像。✅ 最终镜像只保留最后一个 FROM 之后的阶段，前面阶段会被丢弃。
  2. ❌ COPY --from=builder 路径写错。✅ 路径是相对前面阶段的绝对路径，如 /build/target/*.jar。
  3. ❌ 不命名阶段，用序号 COPY --from=0。✅ 推荐 AS builder 命名，可读性好。
  4. ❌ 在运行阶段重复装编译工具。✅ 运行阶段应该精简，只装运行时（如 JRE）。
  5. ❌ 把源码 COPY 到运行阶段。✅ 运行阶段只需要 jar/war 等构建产物，不需要源码。
  6. ❌ 不利用层缓存（先 COPY src 再下依赖）。✅ 先 COPY pom.xml，再下依赖，最后 COPY src，让源码变化时依赖层命中缓存。

小结

多阶段构建用多个 FROM 把"构建"与"运行"分离：构建阶段用重型镜像（含编译器、源码），运行阶段只 COPY --from=builder 拿到产物，基于精简镜像运行。最终镜像只保留运行阶段，体积大幅减小（CTTS 后端从 680MB 优化到 180MB，减少 73%）。这是云原生镜像优化的核心手段，企业 CI/CD 的标配写法。

知识点 K7-6：镜像优化与 .dockerignore

定义

镜像优化：通过一系列手段让最终镜像更小、更安全、构建更快。核心策略包括：

  1. 选择精简基础镜像（alpine / slim / distroless）
  2. 合并 RUN 减少层数（每条 RUN 一层）
  3. 层缓存优化顺序（少变的放前面，多变的放后面）
  4. 清理构建垃圾（apt cache、临时文件）
  5. .dockerignore 排除无关文件（不进入构建上下文）

.dockerignore 文件：放在构建上下文根目录，作用类似 .gitignore，列出哪些文件不发送给 Docker 守护进程（不进入构建上下文）。

原理

1. 选择精简基础镜像：

基础镜像 大小 包含内容 适用场景
ubuntu:22.04 ~77MB 完整 Ubuntu 需要完整 Linux 环境
debian:bookworm-slim ~74MB 精简 Debian（无文档/man） 一般应用
alpine:3.18 ~7MB 极精简（musl libc） 极致优化（注意 musl 兼容性）
eclipse-temurin:17-jre-alpine ~85MB JRE17 + alpine Java 应用优化
eclipse-temurin:17-jre-jammy ~260MB JRE17 + Ubuntu Java 应用（兼容性好）
maven:3.8-openjdk-17 ~600MB Maven + JDK17 仅构建阶段用
gcr.io/distroless/java17 ~160MB 仅 JRE（无 shell） 极致安全（无 shell 难调试）

2. 合并 RUN 减少层数：

# ❌ 不推荐：多条 RUN，多个层
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git
RUN rm -rf /var/lib/apt/lists/*
# 结果：4 个层，且 apt cache 中间层仍占空间（层只追加不删除）

# ✅ 推荐：合并成一条 RUN，用 && 连接
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl git \
    && rm -rf /var/lib/apt/lists/*
# 结果：1 个层，apt cache 在同一层内清理

3. 层缓存优化顺序：

Docker 构建时按指令顺序逐层执行，某层失效则其后所有层都失效。所以应该把"少变的"放前面（如装依赖），"多变的"放后面（如拷贝源码）：

# ❌ 不推荐：源码放前面，源码一变后面全失效
COPY . /app
RUN mvn clean package         # 源码变就要重跑

# ✅ 推荐：依赖放前面，源码放后面
COPY pom.xml .
RUN mvn dependency:go-offline  # 缓存命中率高
COPY src ./src
RUN mvn clean package          # 只在源码变时重跑

4. .dockerignore 完整配置：

.dockerignore 文件放在构建上下文根目录（与 Dockerfile 同级），列出不发送给守护进程的文件：

5. .dockerignore 的价值：

价值 说明
减小构建上下文 不发送无关文件，加快 Sending build context 步骤
提升缓存命中率 避免无关文件变化导致 COPY 层缓存失效
防止敏感信息泄露 避免 .env、密钥、credentials 进入镜像
防止本地构建产物干扰 避免 target/、node_modules/ 覆盖镜像内文件

问题 / 场景

问：alpine 这么小，为什么不用 alpine 跑所有应用？

  • alpine 用 musl libc 而非 glibc，部分依赖 glibc 的应用（如某些原生库、Oracle JDK）在 alpine 上跑不起来或行为异常。
  • Java 应用要用专门的 alpine 版 JDK（如 eclipse-temurin:17-jre-alpine），不能用 openjdk:17（基于 glibc）。
  • 如果遇到兼容性问题，退回 slim 版（基于 glibc）。

问：为什么 "合并 RUN" 能减小镜像体积？即使我 rm 清理了？

  • Docker 镜像是只读层叠加。如果 RUN apt install 在一层装了 100MB，下一层 RUN rm -rf /var/lib/apt/lists/* 删了 50MB，最终镜像仍包含两层——装的那层是 100MB（只是看不到文件），删的那层是 0MB（删除操作）。所以装和删必须在同一层（用 && 连接），才能真正减小体积。

问：.dockerignore 和 .gitignore 有什么区别？

  • .gitignore：决定哪些文件不进入版本控制。
  • .dockerignore：决定哪些文件不进入构建上下文（不发送给 Docker 守护进程）。
  • 二者独立，一个文件可以 .gitignore 但不 .dockerignore，反之亦然。但生产中通常两个文件内容相似。

    && echo "Asia/Shanghai" > /etc/timezone \

    JAVA_OPTS="-Xms256m -Xmx512m"

易错点

  1. ❌ 选了 alpine 基础镜像但应用依赖 glibc 报错。✅ 用 slim 版（基于 glibc）或用对应 alpine 版本 JDK（如 eclipse-temurin:17-jre-alpine）。

四、拓展阅读（选学）

  1. distroless 镜像：Google 维护的极精简镜像（gcr.io/distroless/java17），只含运行时，无 shell、无包管理器，安全性极高。缺点是难调试（无 sh）。适合对安全要求极高的生产环境。
  2. BuildKit 与镜像优化：Docker 18.09+ 引入 BuildKit，支持 --mount=type=cache 把 Maven/npm 缓存挂载到构建阶段，跨构建共享缓存，大幅加速构建。
  3. 镜像扫描：用 Trivy、Grype 等工具扫描镜像漏洞，把扫描集成到 CI/CD，发现漏洞自动告警。
  4. OCI 镜像格式：现代镜像格式标准，支持新的特性（如 zstd 压缩、attestation），部分功能在 Docker 24+ 可用。
  5. 镜像瘦身工具：docker-slim 等工具能自动分析容器运行时实际用到的文件，反向生成极小镜像。适合调试期评估，生产慎用。
