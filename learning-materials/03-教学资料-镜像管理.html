二、知识点详解

知识点 K3-1：镜像概念与组成

定义

Docker 镜像（Image） 是一个只读的、分层的容器运行模板，包含了应用运行所需的全部内容——代码、运行时、系统库、依赖、配置文件、环境变量、元数据等。通过镜像可以启动一个或多个容器实例。

一句话理解：

镜像是容器的"图纸"，容器是按图纸造出来的"产品"。一份图纸可以造出多个产品。

原理

镜像包含什么（以 mysql:8.0 镜像为例）：

图示 1：mysql:8.0 镜像的组成结构
mysql:8.0
只读运行模板
应用层

MySQL Server

包含 mysqld 主程序、初始化脚本 entrypoint.sh 与默认配置文件 my.cnf。

运行时与依赖

让程序能跑起来

包含 MySQL 运行依赖库、shell 工具等基础运行环境。

基础系统层

Debian 11 最小化系统

提供 Linux 用户态文件系统，是上层程序和依赖的底座。

元数据

描述镜像如何启动

包含 CMD、EXPOSE 3306、ENV MYSQL_MAJOR=8.0、WORKDIR 等信息。

镜像不是单个可执行文件，而是“文件系统层 + 启动元数据”的组合；这些内容共同决定容器启动后看到什么、执行什么、暴露什么。

镜像的不可变（Immutable）特性：

  • 镜像一旦构建完成，其内容就不可修改。
  • 如果要"改"镜像，只能基于它构建一个新镜像（新 tag 或新 ID）。
  • 这就是为什么 Dockerfile 中每条指令生成一层、每层只读——只读保证不可变。
  • 不可变带来的好处：可复现、可回滚、可信任——同一个镜像 ID 在任何机器上运行的结果完全一致。

镜像 vs 容器（重要对比）：

维度 镜像（Image） 容器（Container）
状态 静态、只读 动态、可写
性质 模板 运行实例
存储 分层只读层 在镜像层上加一层可写层
关系 一份镜像 可启动多个容器实例
生命周期 长期存在（除非主动删除） 临时运行（停止/删除后可写层消失）
类比 面向对象的"类" 面向对象的"对象"

问题 / 场景

问：镜像和容器到底什么关系？

  • 镜像是只读模板，容器是镜像运行起来的实例。一个镜像可以同时启动多个容器，每个容器在镜像之上加一层可写层，互不干扰。就像"类"和"对象"——一个类可以 new 出多个对象。

问：为什么镜像要做成只读不可变的？

  • 保证可复现性：同一个镜像（同一个 IMAGE ID）在任何机器上运行结果一致，这是"环境一致性"的根基。
  • 保证可信任：镜像构建后内容不变，可以安全分发和审计。
  • 支持回滚：版本出问题时切回旧镜像即可，因为旧镜像内容没变。

问：镜像 ID（IMAGE ID）和镜像名:标签 是什么关系？

  • 镜像 ID 是镜像的唯一标识（SHA256 摘要的前若干位），全局唯一，不可重复。
  • 镜像名:标签（如 mysql:8.0）是人类可读的别名，可以重复（一个 ID 可以打多个 tag）。
  • 类比：ID 是身份证号（唯一），名:tag 是姓名+绰号（可重复、可改）。

问：镜像可以"修改"吗？

  • 不能直接修改。要改只能基于原镜像用 Dockerfile 构建新镜像，或用 docker commit 把容器的修改提交成新镜像（不推荐，第 6 次课详讲）。

完整示例

查看本地已有哪些镜像（先看现象，命令在 K3-2 详讲）：

docker images

预期输出（假设本地已有几个镜像）：

REPOSITORY    TAG       IMAGE ID       CREATED        SIZE
mysql         8.0       d1dc36f8e78f   2 weeks ago    521MB
nginx         latest    605c77e624dd   3 weeks ago    142MB
hello-world   latest    feb5d9fea6a5   6 months ago   13.3kB

各字段含义：

  • REPOSITORY：镜像仓库名（如 mysql、nginx）
  • TAG：镜像标签（如 8.0、latest）
  • IMAGE ID：镜像唯一 ID（SHA256 前 12 位）
  • CREATED：镜像创建时间（不是拉取时间）
  • SIZE：镜像"逻辑大小"（注意：不是实际磁盘占用，因为层可共享）

📌 REPOSITORY:TAG 是人类可读的别名，IMAGE ID 才是镜像的"身份证号"。

易错点

  1. ❌ 误认为"镜像可以像文件一样直接编辑"。✅ 镜像只读不可变，要改只能构建新镜像。
  2. ❌ 误认为"删除容器会删除镜像"。✅ 容器只是镜像的实例，删容器不影响镜像；反之删镜像要先删基于它的容器。
  3. ❌ 误认为"IMAGE ID 就是镜像名"。✅ IMAGE ID 是 SHA256 摘要前缀，全局唯一；镜像名:标签是别名，可重复可改。
  4. ❌ 误认为"SIZE 字段就是镜像实际占用磁盘"。✅ SIZE 是逻辑大小（所有层大小之和），实际占用可能因层共享而更小（K3-3 详讲）。

小结

镜像是只读、分层、不可变的容器运行模板，包含应用运行所需的全部内容。一个镜像可以启动多个容器实例。镜像通过 镜像名:标签 标识，也有唯一的 IMAGE ID。不可变特性保证了镜像的可复现、可回滚、可信任。

知识点 K3-2：镜像拉取与查看

定义

  • docker pull：从镜像仓库（默认 Docker Hub）拉取镜像到本地。
  • docker images / docker image ls：列出本地所有镜像。
  • 两条命令是镜像操作中最常用的入门命令。

原理

docker pull 完整用法：

docker pull [选项] 镜像名[:标签|@摘要]

常用形式：

命令 含义
docker pull mysql 拉取 mysql:latest（不写标签默认 latest）
docker pull mysql:8.0 拉取 mysql 镜像的 8.0 版本
docker pull mysql:8.0.35 拉取更精确的版本（推荐生产使用）
docker pull nginx:alpine 拉取基于 alpine 的 nginx 变体
docker pull openjdk:17-slim 拉取 openjdk 17 的精简版
docker pull registry.example.com/myimg:v1 从私有仓库拉取
docker pull mysql@sha256:abc123... 通过摘要拉取（最精确）
docker pull --platform linux/amd64 mysql:8.0 指定平台（跨架构时）

拉取流程：

  1. 客户端把 pull 请求通过 REST API 发给 dockerd。
  2. dockerd 联系镜像仓库（默认 Docker Hub），查询镜像 manifest。
  3. 逐层下载镜像的每一层（Layer），层有 SHA256 摘要校验。
  4. 本地已有的层不会重复下载（层缓存）。
  5. 下载完成后，组合成本地镜像。

docker images / docker image ls 完整用法：

docker images [选项] [镜像名[:标签]]
docker image ls [选项] [镜像名[:标签]]

常用形式：

命令 含义
docker images 列出所有本地镜像
docker image ls 同上（新语法，等价）
docker images mysql 列出仓库名为 mysql 的镜像
docker images mysql:8.0 列出 mysql:8.0（如有）
docker images -a 列出所有镜像（含中间层，一般不用）
docker images -q 只输出镜像 ID（常用于脚本批量删除）
docker images --digests 显示镜像摘要（SHA256）
docker images --format "{{.Repository}}:{{.Tag}} {{.Size}}" 自定义输出格式
docker images --filter "dangling=true" 只显示悬空镜像（K3-6 详讲）

输出字段详解：

字段 含义 示例
REPOSITORY 镜像仓库名 mysql、nginx、library/mysql（官方镜像带 library/ 前缀，可省略）
TAG 镜像标签 8.0、latest、alpine
IMAGE ID 镜像唯一 ID（SHA256 前 12 位） d1dc36f8e78f
CREATED 镜像构建时间（不是你拉取的时间） 2 weeks ago
SIZE 镜像逻辑大小（所有层大小之和） 521MB

问题 / 场景

问：docker pull mysql 不写标签拉的是什么版本？

  • 拉的是 mysql:latest。但 :latest 不一定是最新最稳定版，可能指向任意版本。生产环境必须指定明确版本号（如 mysql:8.0.35），避免不可复现问题（K3-5 详讲）。

问：为什么第二次拉同一个镜像很快？

  • 因为分层 + 层缓存。Docker 会校验每一层的 SHA256 摘要，本地已有的层不会重复下载，只下载缺失的层或更新的层。比如 mysql:8.0 和 mysql:8.0.35 共享很多层，第二次拉取只下载差异层。

问：CREATED 时间为什么不是我拉取的时间？

  • CREATED 是镜像构建者构建这个镜像的时间（即 Dockerfile 构建完成时间），不是你本地拉取的时间。所以你会看到 2 weeks ago、6 months ago 这种时间。

问：docker images 和 docker image ls 有什么区别？

  • 完全等价。docker images 是老语法，docker image ls 是 Docker 1.13+ 引入的新语法（更规范）。两者输出完全相同，用哪个都行。

问：怎么只列出镜像 ID？

  • docker images -q，常用于批量删除场景：docker rmi $(docker images -q)（慎用！）。

知识点 K3-3：镜像分层结构

定义

Docker 镜像采用分层结构（Layered Architecture）：一个镜像由多个**只读层（Layer）叠加而成，每条 Dockerfile 指令生成一层。多层通过联合文件系统（UnionFS）**叠加呈现为一个统一的文件系统视图。

  • 层（Layer）：镜像的一个增量修改集合，每层有 SHA256 摘要，可共享、可缓存。
  • 联合文件系统（UnionFS）：把多个只读层"叠加"成一个统一视图的文件系统技术，Docker 默认使用 OverlayFS（overlay2 驱动）。

原理

为什么镜像要分层？

考虑两个镜像 mysql:8.0 和 mysql:5.7：

  • 如果不分层：每个镜像是完整的 500MB 文件，两个镜像占 1000MB 磁盘。
  • 如果分层：两个镜像共享 Debian 基础层（约 80MB）、共享部分依赖层，实际占用可能只有 600MB。

分层带来的核心价值：

价值 说明
层共享 多个镜像共用同一基础层，节省磁盘和传输
层缓存 构建时未变化的层用缓存，加速构建；拉取时已有的层不重复下载
增量传输 push/pull 只传输差异层，大幅减少网络流量
可复用 一个基础镜像（如 openjdk:17）可被多个应用镜像复用

分层原理（UnionFS / OverlayFS）：

图示 3：OverlayFS 如何把镜像层与容器可写层合成统一视图
upperdir

容器可写层

容器运行时的新建、修改、删除都记录在这里。

lowerdir

镜像只读层

应用代码、依赖库、基础系统按层叠加，保持不可变。

OverlayFS

叠加合成

内核把可写层与多层只读层合并，形成一个统一文件系统视图。

merged

容器看到的完整目录

容器里看到 /usr、/etc、/var 等完整文件系统。

写时复制（CoW）：修改下层文件时，Docker 先把文件复制到 upperdir，再在可写层修改，从而保护镜像层不可变。

OverlayFS 三个核心概念（了解）：

  • lowerdir：只读的镜像层（可多层叠加）
  • upperdir：容器的可写层（运行时修改写这里）
  • merged：叠加后的统一视图（容器看到的）

修改文件时的"写时复制"（Copy-on-Write, CoW）：

  • 容器读取文件：从上往下找，找到第一个就返回。
  • 容器修改文件：先把文件从下层复制到可写层，再修改（这就是"写时复制"）。
  • 容器删除文件：在可写层创建一个 whiteout 文件，"遮盖"下层的同名文件。
  • 这样保证了下层只读层的不可变性。

为什么分层能共享？

图示 4：MySQL 不同版本镜像的层共享
mysql:8.0

共享底座 + 版本差异层

  • Layer C：MySQL 8 程序。
  • Layer B：MySQL 通用库。
  • Layer A：Debian 11 基础层。
mysql:5.7

共享底座 + 版本差异层

  • Layer D：MySQL 5.7 程序。
  • Layer B：MySQL 通用库。
  • Layer A：Debian 11 基础层。

相同摘要

Layer A、Layer B 内容完全一致，SHA256 摘要相同，只保存一份。

不同摘要

MySQL 程序版本不同，生成不同层，必须分别保存。

磁盘收益

两个镜像的实际占用小于 SIZE 逻辑相加，这就是层共享的价值。

问题 / 场景

问：怎么查看一个镜像有几层？每层做了什么？

  • 用 docker history 镜像名:标签，详见下方完整示例。

问：分层会不会影响性能？

  • 几乎不会。OverlayFS 是内核级实现，性能接近原生文件系统。读文件时最多查多层，但内核有缓存；写文件时第一次复制（CoW），后续直接写可写层。

问：为什么 Dockerfile 中指令顺序很重要？

  • 因为层缓存。如果某层变化（如 COPY 了新代码），后续所有层都会重新构建。所以要把"变化频率低的"放前面（如安装依赖），"变化频率高的"放后面（如 COPY 代码）。第 6~7 次课详讲。

问：所有层都可以共享吗？

  • 不是。只有 SHA256 摘要完全相同的层才能共享。如果两个镜像用了不同的基础系统（如 Debian vs Alpine），基础层不能共享。

  1. ❌ 误认为"镜像是一个整体大文件"。✅ 镜像由多个只读层叠加而成，通过 UnionFS 呈现统一视图。

小结

镜像采用分层结构，每条 Dockerfile 指令生成一层，多层通过 UnionFS（OverlayFS）叠加。分层带来三大价值：层共享（多个镜像共用基础层，省磁盘）、层缓存（构建/拉取时已有层不重复）、增量传输（push/pull 只传差异层）。docker history 查看镜像的构建层，docker image inspect 中的 RootFS.Layers 查看层摘要列表。

知识点 K3-5：镜像标签管理

定义

docker tag 命令用于给已有镜像打一个新的标签（重命名），不创建新镜像，只是给同一个镜像 ID 加一个别名。

原理

完整用法：

docker tag 源镜像[:标签] 目标镜像[:标签]

标签（Tag）的本质：

  • 标签是镜像的"别名"，格式 仓库名:标签。
  • 一个镜像 ID 可以有多个标签（一对多关系）。
  • docker tag 不创建新镜像，只是给同一个 ID 加别名。
  • 删除某个标签（docker rmi 镜像:标签）只是删别名，只要还有其他标签指向这个 ID，镜像本身不会被删。

:latest 陷阱：

:latest 的真相：
1. :latest 只是一个普通的标签名，没有任何"最新"语义
2. docker pull / docker run 不写标签时默认用 :latest
3. 镜像构建者可以随时把 :latest 指向任何版本（可能从 8.0 变成 8.1）
4. 所以"今天构建的 :latest"和"一个月后构建的 :latest"可能是完全不同的镜像

生产环境风险：
  FROM mysql:latest   ← 今天可能是 8.0.35，下个月可能是 8.1.0
  → 行为不一致 → 不可复现 → 上线事故

正确做法：
  FROM mysql:8.0.35   ← 永远是同一个版本，可复现

标签命名规范（生产环境推荐）：

场景 推荐命名 示例
版本号 镜像:主版本.次版本.修订 mysql:8.0.35
应用镜像 镜像:版本-构建号 ctts-backend:1.0.0-20240115
私有仓库 仓库地址/团队/应用:版本 harbor.company.com/dev/ctts-api:v1
Git 提交 镜像:git短哈希 ctts-api:a1b2c3d

问题 / 场景

问：为什么生产环境不能用 :latest？

  • 三个核心风险：
    1. 不可复现：今天和一个月后构建的镜像可能基于不同版本，行为不一致。
    2. 不可追溯：出问题时不知道用的是哪个具体版本，无法回滚。
    3. 不可审计：合规审计要求明确版本号，:latest 不满足。
  • 正确做法：用明确版本号（mysql:8.0.35）或 Git 提交哈希（ctts-api:a1b2c3d）。

问：一个镜像可以有多个标签吗？

  • 可以。比如 mysql:8.0 和 mysql:8.0.35 可能指向同一个镜像 ID。docker tag 就是给镜像加别名。

问：删除某个标签会删除镜像吗？

  • 不一定。如果该镜像还有其他标签，删一个标签只是删别名，镜像本身仍在。只有删除镜像的"最后一个标签"时，镜像才会被真正删除。

问：docker tag 会创建新镜像层吗？

  • 不会。docker tag 只是元数据操作，给同一个镜像 ID 加一个别名，不创建新层，不占额外磁盘。

知识点 K3-6：镜像删除与清理

定义

  • docker rmi / docker image rm：删除本地镜像（按标签或 ID）。
  • docker image prune：清理悬空镜像（dangling images）。
  • docker image prune -a：清理所有未被容器使用的镜像。

原理

docker rmi / docker image rm 完整用法：

docker rmi [选项] 镜像[:标签|ID] [镜像...]
docker image rm [选项] 镜像[:标签|ID] [镜像...]

常用形式：

命令 含义
docker rmi mysql:8.0 删除 mysql:8.0 标签
docker rmi d1dc36f8e78f 按 ID 删除镜像
docker rmi mysql:8.0 nginx:1.25 一次删多个
docker rmi -f mysql:8.0 强制删除（即使有容器依赖）
docker image rm mysql:8.0 新语法，等价于 docker rmi

删除规则：

  1. 如果镜像有对应容器存在（无论运行还是停止）：默认拒绝删除，提示先删容器。
  2. 强制删除 -f：先删除所有依赖此镜像的容器，再删镜像。慎用，可能误删运行中的容器。
  3. 如果镜像有多个标签：删一个标签只是 Untagged，镜像本身仍在；删最后一个标签才会 Deleted 各层。

docker image prune 清理悬空镜像：

docker image prune [选项]
命令 含义
docker image prune 清理悬空镜像（dangling，无标签的中间层）
docker image prune -a 清理所有未被任何容器使用的镜像（含已打标签的）
docker image prune -f 跳过确认提示，直接清理
docker image prune -a --filter "until=24h" 清理 24 小时前创建的未使用镜像
docker image prune -a --filter "label=deprecated" 按标签过滤清理

什么是悬空镜像（dangling image）？

悬空镜像 = 有层但无标签的镜像（REPOSITORY 显示 <none>，TAG 显示 <none>）

产生场景：
  1. 用相同标签重新构建镜像：旧镜像失去标签，变成 <none>:<none>
  2. 多阶段构建产生的中间层镜像
  3. 删除标签后剩下的无标签层

示例：
  docker build -t ctts-api:v1 .    # 构建镜像 ctts-api:v1
  # ... 修改代码 ...
  docker build -t ctts-api:v1 .    # 用相同标签再构建
  # 旧的 ctts-api:v1 镜像失去标签，变成 <none>:<none>，占磁盘但不被使用

docker image prune vs docker image prune -a：

命令 清理范围 风险
docker image prune 只清理悬空镜像（<none>:<none>） 低，悬空镜像肯定无用
docker image prune -a 清理所有未被容器使用的镜像 中，可能删掉你"打算用但还没用"的镜像

问题 / 场景

问：删镜像时报"image is being used by stopped container xxx"怎么办？

  • 有容器（即使已停止）依赖此镜像。两种处理：
    1. 先 docker rm 容器ID/名 删除依赖的容器，再 docker rmi 镜像。
    2. 用 docker rmi -f 镜像 强制删除（会先删容器再删镜像，慎用）。

问：docker rmi 镜像:标签 和 docker rmi 镜像ID 有区别吗？

  • 删除逻辑略有不同：
    • docker rmi 镜像:标签：如果该镜像有多个标签，只删这个标签（Untagged），不删层。
    • docker rmi 镜像ID：直接按 ID 删，会删除该 ID 的所有标签和层。
  • 生产环境删镜像优先用 ID，确保彻底删除。

问：docker image prune -a 会不会删掉正在运行容器使用的镜像？

  • 不会。-a 只删"未被任何容器使用的镜像"，正在运行容器使用的镜像不会被删。

问：删完镜像后磁盘没立刻释放？

  • Docker 有时会有延迟。可以：
    1. docker system prune 全面清理（含镜像、容器、网络、构建缓存）。
    2. 重启 Docker 服务：sudo systemctl restart docker。
    3. 极端情况下，Docker 的存储驱动可能需要手动清理残留。

问：怎么批量删除所有本地镜像？

  • docker rmi $(docker images -q) —— 删除所有镜像（如有容器依赖会报错）。
  • docker rmi -f $(docker images -q) —— 强制删除所有镜像（极其危险，慎用）。

四、拓展阅读（选学）

  1. OverlayFS 文件系统：Docker 默认使用的联合文件系统，是 Linux 内核 3.18+ 的特性。深入了解可读 OverlayFS 官方文档，理解 lowerdir/upperdir/merged 的工作原理。
  2. OCI 镜像规范：Open Container Initiative 定义了镜像格式标准（OCI Image Spec），Docker 镜像格式与之兼容。了解 OCI 有助于理解镜像的 manifest/config/layer 结构。
  3. 镜像摘要（Digest）：docker pull mysql@sha256:... 通过完整 SHA256 摘要拉取镜像，比标签更精确（标签会漂移，摘要永远不变）。生产环境推荐用摘要固定镜像版本。
  4. 多架构镜像（manifest list）：docker pull mysql:8.0 在 amd64 和 arm64 机器上拉到的是不同架构的镜像，背后是 manifest list 技术。docker manifest inspect mysql:8.0 可查看。
  5. 镜像签名与安全：Docker Content Trust（基于 Notary）可以对镜像签名，确保镜像来源可信。生产环境建议启用，防止拉取被篡改的镜像。

删除与清理

docker rmi、image prune、system df/prune 用于回收空间，但要先确认容器依赖。

一句话总结

镜像是只读、分层、不可变的容器模板。本节学会了用 docker pull 拉取、docker images 查看、docker history/inspect 分析、docker tag 打标签、docker rmi/prune 删除清理——这是后续 Dockerfile 构建（M3）和容器管理（第 4 次课）的基础。
