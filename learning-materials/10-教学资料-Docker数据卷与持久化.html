二、知识点详解

知识点 K10-1：数据持久化需求

定义

数据持久化（Data Persistence） 是指将容器运行时产生的数据保存到容器之外（宿主机或独立存储），使得容器删除、重建、迁移后数据仍然存在。

容器可写层（Container Writable Layer） 是 Docker 在只读镜像之上为每个容器添加的一层临时存储层，容器运行时的所有写入操作（新建文件、修改文件、删除文件）都写在这一层。

原理

Docker 镜像是只读的，容器在镜像之上加一层可写层（也叫 storage layer / ephemeral layer）：

图示 1：可写层（容器专属） ← 容器运行时写入的数据在这里
容器可写层

随容器生命周期变化

容器运行时写入的数据默认落在可写层；容器删除后，这些数据也随之消失。

Volume

独立于容器保存

数据写入 Docker 管理的数据卷，容器删除和重建后仍可重新挂载使用。

持久化的核心问题：不要把数据库数据放在容器可写层里。

可写层的问题：

问题 说明
容器删除数据丢失 docker rm 删除容器时，可写层随之删除，所有写入的数据全部消失
容器重建数据不延续 用同一个镜像重新 docker run 出来的容器是一个全新的可写层，与旧容器无关
可写层性能差 可写层使用联合文件系统（如 overlay2），写入性能低于直接写宿主磁盘
不便于共享与迁移 可写层绑定在容器上，其他容器无法直接访问，迁移容器时数据带不走
不便于备份 可写层数据藏在 Docker 内部目录，普通用户难以直接访问和备份

为什么不能把数据存容器里：

  1. 数据是核心资产：数据库的数据、应用的配置、用户上传的文件——这些都是核心资产，不能随容器生命周期消失。
  2. 容器是临时的：容器的设计哲学是" ephemeral（短寿命）"，随时可以删除、重建、水平扩展。如果数据绑在容器上，就违背了容器的设计哲学。
  3. 生产环境不可接受：生产环境的数据库容器升级、迁移、故障恢复时，如果数据丢了就是重大事故。
  4. 云原生原则：云原生架构的核心原则之一是"数据与计算分离"——计算（容器）是无状态的、可随意重建；数据是持久的、需要独立保障。

问题 / 场景

问：容器停止（stop）后数据会丢吗？

  • 不会。docker stop 只是暂停容器进程，可写层仍然保留。docker start 可以恢复运行，数据还在。只有 docker rm 删除容器，可写层才会消失。

问：我把容器提交成新镜像（docker commit）不就保留数据了吗？

  • 技术上可以，但这是反模式，不推荐：
    • docker commit 把可写层固化成镜像层，但数据会随镜像分发——你不想把数据库里的用户密码表分发到镜像仓库吧？
    • 镜像体积会越来越大，因为每次 commit 都叠加一层。
    • 数据无法独立备份、迁移、恢复。
    • 正确做法：数据用 Volume 持久化，镜像只包含应用代码和运行环境。

问：什么数据需要持久化？

  • 数据库数据（MySQL 的 /var/lib/mysql、PostgreSQL 的 /var/lib/postgresql/data）
  • 配置文件（需要保留的配置，如 Nginx 的 nginx.conf）
  • 用户上传文件（如图片、文档）
  • 应用日志（需要长期保留的日志）
  • 缓存数据（如 Redis 的持久化数据，看需求）

问：什么数据不需要持久化？

  • 应用代码本身（在镜像里）
  • 运行时依赖库（在镜像里）
  • 临时文件、临时缓存（如 /tmp）

完整示例

一个反例演示（说明问题，不要在生产环境这样做）：

# 1. 启动一个 MySQL 容器（没有挂载数据卷）
docker run -d --name bad-mysql -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0
# 输出示例：
# 1a2b3c4d5e6f7g8h9i0j...

# 2. 进入容器，写入数据
docker exec -it bad-mysql mysql -uroot -p123456 -e "CREATE DATABASE ctts; USE ctts; CREATE TABLE users(id INT, name VARCHAR(50)); INSERT INTO users VALUES (1, '张三'); SELECT * FROM users;"
# 输出示例：
# +------+--------+
# | id   | name   |
# +------+--------+
# |    1 | 张三   |
# +------+--------+

# 3. 删除容器
docker stop bad-mysql && docker rm bad-mysql
# 输出示例：
# bad-mysql

# 4. 用同样命令重新启动一个 MySQL 容器
docker run -d --name bad-mysql -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0

# 5. 查询数据——发现数据全没了！
docker exec -it bad-mysql mysql -uroot -p123456 -e "SHOW DATABASES;"
# 输出示例：
# +--------------------+
# | Database           |
# +--------------------+
# | information_schema |
# | mysql              |
# | performance_schema |
# | sys                |
# +--------------------+
# 注意：ctts 数据库不见了！张三那条记录也不见了！

📌 这就是没有持久化的后果——容器删除，数据全丢。生产环境这样部署就是事故。下面 K10-2~K10-6 就是解决方案。

没有持久化

MySQL 数据位于容器内部 /var/lib/mysql；执行 docker rm 后，可写层被删除，数据随容器消失。

使用数据卷

数据独立于容器

-v mysql_data:/var/lib/mysql 让数据写入宿主机卷；删除容器后卷仍保留，新容器挂载同一卷即可恢复数据。

易错点

  1. ❌ 误认为"容器停止后数据会丢"。✅ docker stop 只暂停进程，可写层保留；docker rm 才会删除可写层。
  2. ❌ 误认为"docker commit 是持久化数据的好方法"。✅ commit 会把数据固化进镜像，不便于独立管理、备份、迁移，是反模式。
  3. ❌ 误认为"只要不删容器数据就安全"。✅ 容器可能因为故障崩溃、被误删、被重建（如升级镜像），任何时候都可能丢，必须持久化。
  4. ❌ 误认为"所有数据都要持久化"。✅ 临时文件、缓存等不需要持久化，只持久化核心数据。

小结

容器的可写层是临时的，容器删除后数据丢失。生产环境必须把核心数据（数据库、配置、日志、用户文件）持久化到容器之外。数据持久化是数据安全的底线，也是云原生"数据与计算分离"原则的体现。

知识点 K10-2：数据卷 Volume

定义

数据卷（Volume） 是 Docker 提供的持久化机制，由 Docker 引擎管理，存储在宿主机上的特定目录（Linux 默认 /var/lib/docker/volumes/），独立于容器的生命周期。

Volume 是 Docker 官方推荐的持久化方式，特别适合生产环境。

原理

Volume 的工作机制：

图示 3：Docker Volume 在宿主机与容器中的映射
宿主机

/var/lib/docker/volumes/

  • mysql_data/_data/ 保存 MySQL 数据。
  • nginx_data/_data/ 保存 Nginx 数据。
  • Docker 引擎负责管理这些卷目录。
容器

/var/lib/mysql

容器看到的是业务路径，但实际读写会落到宿主机卷目录，而不是容器可写层。

-v mysql_data:/var/lib/mysql 的含义：把名为 mysql_data 的卷挂到容器内 /var/lib/mysql。

Volume 的关键特性：

  1. 由 Docker 管理：卷的创建、存储、删除都由 Docker 引擎管理，存储在固定目录。
  2. 独立于容器生命周期：容器删除，卷仍在；新容器挂载同一卷即可恢复数据。
  3. 可命名：可以创建命名卷（named volume，如 mysql_data），便于管理。
  4. 可共享：多个容器可以同时挂载同一个卷，实现数据共享。
  5. 跨平台兼容：在 Linux/Windows/Mac 上行为一致，Docker 处理了底层差异。
  6. 可备份迁移：卷数据在固定目录，可以用临时容器打包备份，或整体迁移。

Volume 的挂载方式：

Docker 提供两种挂载语法（效果等价，推荐 --mount 更清晰）：

# 方式一：-v / --volume（简短语法，老版本常用）
docker run -v mysql_data:/var/lib/mysql mysql:8.0

# 方式二：--mount（完整语法，官方推荐，更清晰）
docker run --mount type=volume,source=mysql_data,target=/var/lib/mysql mysql:8.0

两种语法对比：

对比项 -v / --volume --mount
语法 -v 卷名:容器路径[:ro] --mount type=volume,source=卷名,target=容器路径[,readonly]
可读性 简短但含义不直观 完整清晰，参数明确
历史版本 老版本（Docker 17.06 前）唯一选择 Docker 17.06+ 推荐
错误提示 字段写错时可能被静默忽略 字段写错会报错
推荐度 简单场景可用 生产推荐，更不易出错

Volume 的优势：

优势 说明
可移植性 卷由 Docker 管理，不依赖宿主机路径，迁移到别的机器也能用
易于备份恢复 卷数据在固定目录，可打包备份
易于管理 docker volume 系列命令统一管理
跨平台 Linux/Windows/Mac 行为一致
可共享 多容器挂载同一卷实现数据共享
驱动扩展 支持卷驱动（volume driver），可对接 NFS、云存储等远程存储
性能较好 直接写入宿主机目录，比可写层快

问题 / 场景

问：Volume 数据具体存在哪里？

  • Linux 默认存在 /var/lib/docker/volumes/<卷名>/_data/ 目录下。可以通过 docker volume inspect <卷名> 查看 Mountpoint 字段确认。
  • 不建议直接操作这个目录（应通过 Docker 命令管理），但了解位置有助于备份和排查问题。

问：创建容器时挂载一个不存在的卷名会怎样？

  • Docker 会自动创建这个卷（命名卷）。如果用 -v /var/lib/mysql（只写容器路径，不写卷名），Docker 会自动创建一个匿名卷（名字是一长串随机哈希），不便于管理，生产环境不推荐。

问：Volume 可以设置为只读吗？

  • 可以。加 :ro（-v 语法）或 readonly（--mount 语法）： 
    docker run -v config_data:/etc/app:ro myapp
docker run --mount type=volume,source=config_data,target=/etc/app,readonly myapp

完整示例

创建并使用一个 Volume 的完整流程：

# 1. 创建一个命名卷
docker volume create my_data
# 输出示例：
# my_data

# 2. 查看所有卷
docker volume ls
# 输出示例：
# DRIVER    VOLUME NAME
# local     my_data

# 3. 启动容器挂载卷（-v 语法）
docker run -d --name test-container -v my_data:/app/data alpine:3.18 tail -f /dev/null
# 输出示例：
# 2f3a4b5c6d7e8f9...

# 4. 进入容器写入数据
docker exec test-container sh -c "echo 'hello volume' > /app/data/test.txt"
docker exec test-container cat /app/data/test.txt
# 输出示例：
# hello volume

# 5. 删除容器
docker stop test-container && docker rm test-container
# 输出示例：
# test-container

# 6. 重新启动一个新容器挂载同一个卷
docker run -d --name test-container2 -v my_data:/app/data alpine:3.18 tail -f /dev/null

# 7. 验证数据还在
docker exec test-container2 cat /app/data/test.txt
# 输出示例：
# hello volume
# 数据持久化成功！

# 8. 用 --mount 语法（等价效果）
docker run -d --name test-container3 \
  --mount type=volume,source=my_data,target=/app/data \
  alpine:3.18 tail -f /dev/null
docker exec test-container3 cat /app/data/test.txt
# 输出示例：
# hello volume

# 9. 清理
docker stop test-container2 test-container3 && docker rm test-container2 test-container3
docker volume rm my_data

📌 这个示例完整演示了"创建卷→挂载→写入→删容器→重建容器→验证数据"的持久化流程，是本节课的核心操作模式。

易错点

  1. ❌ 误认为"Volume 数据存在容器里"。✅ Volume 数据存在宿主机的 /var/lib/docker/volumes/ 下，独立于容器。
  2. ❌ 误认为"删除容器时 Volume 会被自动删除"。✅ 删除容器不会删除 Volume，需要用 docker volume rm 显式删除。
  3. ❌ 混淆命名卷和匿名卷。✅ 命名卷有可读的名字（如 mysql_data），便于管理；匿名卷是随机哈希名，不便于管理，生产环境推荐命名卷。
  4. ❌ 挂载时路径写错。✅ -v 卷名:容器路径，卷名在前，容器路径在后，顺序不能反。

小结

数据卷（Volume）是 Docker 管理的持久化机制，存储在 /var/lib/docker/volumes/，独立于容器生命周期。它是 Docker 官方推荐的持久化方式，特别适合生产环境。使用 -v 卷名:容器路径 或 --mount type=volume,... 挂载。

知识点 K10-3：绑定挂载 Bind Mount

定义

绑定挂载（Bind Mount） 是将宿主机上的一个绝对路径直接映射到容器内的路径，容器对这个路径的读写实际上是在操作宿主机上的文件。

Bind Mount 依赖宿主机的目录结构，适合开发环境的热加载、配置文件挂载等场景。

原理

Bind Mount 的工作机制：

图示 5：/home/user/ctts/config/ ← 实际目录
  • 宿主机
  •     /home/user/ctts/config/ ← 实际目录
  •     application.yml
  •     logback.xml
  •   -v /home/user/ctts/config:/etc/app/config （绑定挂载）
  • 容器
  •     /etc/app/config/ ← 容器内路径
  •     （实际就是宿主机的 /home/user/.../）

Bind Mount 的关键特性：

  1. 依赖宿主机路径：必须指定宿主机的绝对路径，与宿主机强耦合。
  2. 直接映射：容器内对挂载路径的读写直接作用于宿主机文件，无中间层。
  3. 宿主机可任意操作：宿主机上可以直接编辑这些文件，容器内立即生效（适合热加载）。
  4. 路径不存在会自动创建：挂载时如果宿主机路径不存在，Docker 会自动创建（注意：可能以 root 权限创建，导致权限问题）。
  5. 不可移植：强依赖宿主机路径，换一台机器路径可能不存在。

Bind Mount 的挂载方式：

# 方式一：-v / --volume（简短语法）
docker run -v /home/user/ctts/config:/etc/app/config myapp

# 方式二：--mount（完整语法，官方推荐）
docker run --mount type=bind,source=/home/user/ctts/config,target=/etc/app/config myapp

注意：Bind Mount 的 source 必须是绝对路径，相对路径会被识别为卷名。

问题 / 场景

问：Bind Mount 和 Volume 到底有什么区别？

对比项 Volume（数据卷） Bind Mount（绑定挂载）
存储位置 Docker 管理，/var/lib/docker/volumes/ 宿主机任意路径，由用户指定
管理方式 docker volume 命令统一管理 宿主机文件系统直接管理
创建方式 显式 docker volume create 或挂载时自动创建 挂载时指定宿主路径，路径不存在则自动创建
可移植性 高（Docker 管理，不依赖宿主路径） 低（强依赖宿主机绝对路径）
适用场景 生产环境数据持久化（数据库、应用数据） 开发环境代码热加载、配置文件挂载
备份恢复 用临时容器打包卷目录 直接操作宿主机文件
安全性 较好（Docker 隔离） 较弱（暴露宿主路径，有风险）
跨平台 好（Docker 处理差异） 差（依赖宿主路径结构）
性能 较好 最好（直接宿主文件系统）
推荐场景 生产环境 开发/测试环境

问：什么时候用 Volume，什么时候用 Bind Mount？

场景 推荐 理由
生产环境 MySQL 数据持久化 Volume 可移植、可备份、Docker 管理
生产环境 Redis 数据持久化 Volume 同上
开发环境 Vue3 代码热加载 Bind Mount 宿主机改代码，容器内立即生效
开发环境 SpringBoot 配置热加载 Bind Mount 修改 application.yml 容器立即读到
团队共享配置文件 Bind Mount 配置文件在宿主机，便于版本管理
CI/CD 流水线构建产物输出 Bind Mount 把构建产物直接输出到宿主机工作区
生产环境应用日志 Volume 日志持久化，便于备份
容器间共享数据 Volume 可移植、可命名

一句话原则：

  • 生产环境：优先 Volume（可移植、安全、Docker 管理）。
  • 开发环境：用 Bind Mount（热加载、直接操作宿主文件）。
  • 不要在生产环境用 Bind Mount 暴露宿主路径——有安全风险，且可移植性差。

完整示例

Bind Mount 在开发环境的热加载示例：

# 1. 在宿主机准备一个目录和配置文件
mkdir -p /home/user/ctts-config
echo 'server.port=8080' > /home/user/ctts-config/application.properties
cat /home/user/ctts-config/application.properties
# 输出示例：
# server.port=8080

# 2. 启动容器，用 Bind Mount 挂载配置目录
docker run -d --name config-demo \
  -v /home/user/ctts-config:/etc/app/config \
  alpine:3.18 tail -f /dev/null

# 3. 容器内查看配置文件（与宿主机同步）
docker exec config-demo cat /etc/app/config/application.properties
# 输出示例：
# server.port=8080

# 4. 在宿主机修改配置文件
echo 'server.port=9090' > /home/user/ctts-config/application.properties

# 5. 容器内立即看到修改（热加载）
docker exec config-demo cat /etc/app/config/application.properties
# 输出示例：
# server.port=9090

# 6. 在容器内修改文件，宿主机也能看到（双向同步）
docker exec config-demo sh -c "echo 'spring.datasource.url=jdbc:mysql://db:3306/ctts' >> /etc/app/config/application.properties"
cat /home/user/ctts-config/application.properties
# 输出示例：
# server.port=9090
# spring.datasource.url=jdbc:mysql://db:3306/ctts

# 7. 用 --mount 语法（等价效果）
docker run -d --name config-demo2 \
  --mount type=bind,source=/home/user/ctts-config,target=/etc/app/config \
  alpine:3.18 tail -f /dev/null

# 8. 设置只读挂载（容器内不能修改，只能读）
docker run -d --name config-readonly \
  -v /home/user/ctts-config:/etc/app/config:ro \
  alpine:3.18 tail -f /dev/null
docker exec config-readonly sh -c "echo test > /etc/app/config/test.txt"
# 输出示例（报错）：
# sh: can't create /etc/app/config/test.txt: Read-only file system

# 9. 清理
docker stop config-demo config-demo2 config-readonly
docker rm config-demo config-demo2 config-readonly
rm -rf /home/user/ctts-config

📌 Bind Mount 的双向同步特性使其非常适合开发环境代码热加载——宿主机用 IDE 改代码，容器内立即生效，无需重启容器。

  • Bind Mount 双向同步：
  • 宿主机 容器
  • /home/user/ctts-config/ /etc/app/config/
  • application.properties ◀ ▶ application.properties
  • 修改任意一方，另一方立即同步

易错点

  1. ❌ 误用相对路径。✅ Bind Mount 的宿主路径必须是绝对路径，如 /home/user/...，写 ./config 会被识别为卷名。
  2. ❌ 误认为 Bind Mount 数据由 Docker 管理。✅ Bind Mount 数据就是宿主机文件，Docker 不参与管理，删除容器不影响宿主文件。
  3. ❌ 生产环境滥用 Bind Mount。✅ 生产环境优先用 Volume，Bind Mount 强耦合宿主路径，可移植性差且有安全风险。
  4. ❌ 路径顺序写反。✅ -v 宿主路径:容器路径，宿主在前，容器在后。
  5. ❌ 忽略权限问题。✅ 容器内通常以 root 运行，写入的文件在宿主机上可能是 root 所有，普通用户无法操作；需注意 UID/GID 对齐。

小结

绑定挂载（Bind Mount）将宿主机绝对路径直接映射到容器路径，实现双向同步。适合开发环境代码热加载、配置挂载等场景。生产环境优先用 Volume，Bind Mount 因强耦合宿主路径、可移植性差、有安全风险，不推荐在生产使用。

知识点 K10-4：数据卷管理命令

定义

Docker 提供 docker volume 系列命令管理数据卷的完整生命周期：创建、查看、检查、删除、清理。

原理

docker volume 命令体系：

命令 作用 语法
docker volume create 创建一个命名卷 docker volume create [卷名]
docker volume ls 列出所有卷 docker volume ls
docker volume inspect 查看卷详细信息 docker volume inspect <卷名>
docker volume rm 删除一个或多个卷 docker volume rm <卷名> [卷名...]
docker volume prune 清理所有未被使用的卷 docker volume prune

命名卷 vs 匿名卷：

类型 创建方式 命名 管理便利性 推荐度
命名卷 docker volume create mysql_data 或 -v mysql_data:/path 有可读名字 易于识别和管理 ★★★ 生产推荐
匿名卷 -v /path（只写容器路径，不写卷名） 随机哈希名（如 a1b2c3d4...） 难以识别，易遗留 ★ 不推荐

问题 / 场景

问：docker volume prune 会删除正在被容器使用的卷吗？

  • 不会。prune 只删除未被任何容器引用的卷。正在被容器使用的卷会被跳过，安全。

问：怎么知道一个卷被哪些容器使用？

  • 用 docker volume inspect <卷名> 看卷的详细信息，或用 docker ps -a --filter volume=<卷名> 查找使用该卷的容器。

问：删除卷时提示"volume is in use"怎么办？

  • 说明有容器正在使用这个卷。先 docker stop 并 docker rm 相关容器，再删除卷。可以用 docker ps -a --filter volume=<卷名> 找出使用该卷的容器。

知识点 K10-5：数据卷共享与备份

定义

数据卷共享 是指多个容器挂载同一个数据卷，实现容器间的数据共享。

--volumes-from 是 Docker 提供的共享卷挂载语法，可以让一个容器继承另一个容器的所有卷挂载配置。

数据卷备份 是指把卷里的数据打包导出到宿主机或其他存储，以便在数据丢失时恢复。

数据卷恢复 是指把备份的数据还原回卷中，使容器能重新访问这些数据。

原理

--volumes-from 共享卷的工作机制：

图示 8：volumes-from 共享卷关系
容器 A

数据提供者

挂载 shared_data:/app/data，定义卷使用方式。

shared_data

真正的数据位置

两个容器的 /app/data 都指向同一个 Docker 卷。

容器 B

数据消费者

通过 --volumes-from A 自动继承 A 的卷挂载配置。

注意：--volumes-from 共享的是卷挂载关系，不是复制数据；现代 Compose 更常直接声明同一个 named volume。

数据卷备份的原理：

图示 9：临时备份容器
  •     临时备份容器
  •     - 挂载要备份的卷：mysql_data -> /data
  •     - 挂载宿主备份目录：/backup -> /backup
  •     - 执行打包命令：tar cvf /backup/bak.tar /data
  •         mysql_data 宿主机
  •         (Docker 卷) /backup/
  •         原始数据 bak.tar 备份

为什么用临时容器备份？

  • Docker 卷数据存在 /var/lib/docker/volumes/ 下，普通用户可能没有权限直接访问。
  • 用一个临时容器挂载卷，容器内有权限访问卷数据，再通过 bind mount 把宿主机目录映射进来，就能把卷数据打包拷贝到宿主机。
  • 临时容器用完即删（--rm），不影响系统。

问题 / 场景

问：--volumes-from 和直接 -v 挂载同一个卷有什么区别？

  • 效果类似，但 --volumes-from 更方便：
    • -v 需要你知道卷名和挂载路径，手动写一遍。
    • --volumes-from 直接继承另一个容器的所有卷配置，不用关心具体卷名和路径。
    • 适合"我想用容器 A 的所有数据"的场景，如备份、辅助工具容器。

问：备份的 tar 包怎么恢复？

  • 用一个临时容器挂载目标卷和宿主机的备份目录，执行 tar xvf 解压： 
    docker run --rm -v mysql_data:/data -v /home/user/backup:/backup alpine \
  tar xvf /backup/mysql_data.tar -C /
    注意解压路径要与打包路径对应（打包时是 /data，解压时也要解到 /data）。

问：--volumes-from 能继承只读挂载吗？

  • 能。如果容器 A 用 :ro 只读挂载某个卷，--volumes-from 继承时也会是只读。可以在继承时覆盖：--volumes-from A:ro 让所有继承的卷都是只读。

完整示例

示例 1：--volumes-from 实现卷共享

# 1. 创建一个共享卷
docker volume create shared_data
# 输出示例：
# shared_data

# 2. 启动容器 A（数据提供者），挂载共享卷
docker run -d --name provider -v shared_data:/app/data alpine:3.18 tail -f /dev/null

# 3. 在容器 A 中写入数据
docker exec provider sh -c "echo 'data from provider' > /app/data/shared.txt"
docker exec provider cat /app/data/shared.txt
# 输出示例：
# data from provider

# 4. 启动容器 B，用 --volumes-from 继承 A 的卷挂载

# 5. 在容器 B 中读取 A 写入的数据
docker exec consumer cat /app/data/shared.txt
# 输出示例：
# data from provider
# 共享成功！

# 6. 在容器 B 中写入新数据，A 也能读到
docker exec consumer sh -c "echo 'data from consumer' >> /app/data/shared.txt"
docker exec provider cat /app/data/shared.txt
# 输出示例：
# data from provider
# data from consumer

# 7. 清理
docker stop provider consumer && docker rm provider consumer
docker volume rm shared_data

📌 "临时容器 + 卷挂载 + tar 打包/解压"是 Docker 数据卷备份恢复的经典模式，适用于任何卷的备份恢复，可迁移到生产环境定时备份脚本。

图示

图示 10：数据卷备份与恢复流程：
  • 数据卷备份与恢复流程：
  • 【备份】
  •           mysql_data ▶ 临时备份容器 ▶ 宿主机
  •           (原始卷) 挂载 tar cvf /backup/ 挂载 /backup/
  •         bak.tar /data bak.tar
  • 【恢复】
  •           mysql_data ◀ 临时恢复容器 ◀ 宿主机
  •           (空卷) 挂载 tar xvf /backup/ 挂载 /backup/
  •         bak.tar -C / bak.tar

易错点

  1. ❌ 备份时 tar 路径写错。✅ 备份时打包 /data（卷挂载路径），恢复时也要解压到 /data，路径要对应。
  2. ❌ 恢复时忘记 -C /。✅ tar xvf backup.tar -C / 表示解压到根目录，因为打包时用了 /data（绝对路径），解压时要从根开始还原。如果不加 -C /，会解压到当前目录，路径错乱。
  3. ❌ 误认为 --volumes-from 会复制数据。✅ --volumes-from 只是共享挂载配置，不会复制数据，多个容器指向同一个卷。
  4. ❌ 备份时容器还在写入。✅ 备份前最好停止业务容器，保证数据一致性（特别是数据库）。

小结

--volumes-from 让一个容器继承另一个容器的卷挂载，实现卷共享。数据卷备份用"临时容器 + 卷挂载 + tar 打包"模式，恢复用"临时容器 + 空卷挂载 + tar 解压"模式。这是 Docker 数据卷运维的经典模式，生产环境定时备份脚本通常基于此模式编写。

知识点 K10-6：MySQL 数据持久化实践

定义

MySQL 数据持久化配置 是指为 MySQL 容器挂载数据卷，把数据库数据目录 /var/lib/mysql 持久化到 Docker 卷中，确保容器删除、重建、升级后数据库数据不丢失。

这是 CTTS 项目数据库走向"生产可用"的关键配置。

原理

MySQL 容器的数据存储路径：

路径 内容 是否需要持久化
/var/lib/mysql 数据库数据文件（表、索引、日志等） 必需，核心数据
/etc/mysql/conf.d 自定义配置文件 推荐，便于配置保留
/var/log/mysql 日志文件（如已配置） 可选，看需求

持久化配置的关键参数：

docker run -d \
  --name ctts-mysql \
  -v mysql_data:/var/lib/mysql \         # 数据卷持久化数据目录
  -e MYSQL_ROOT_PASSWORD=123456 \        # root 密码
  -e MYSQL_DATABASE=ctts \               # 自动创建 ctts 数据库
  -e MYSQL_USER=ctts_user \              # 创建业务用户
  -e MYSQL_PASSWORD=ctts_pass \          # 业务用户密码
  -p 3306:3306 \                         # 端口映射
  mysql:8.0

验证持久化的标准流程：

  1. 创建卷并启动 MySQL 容器挂载卷
  2. 写入测试数据（建库建表插数据）
  3. 停止并删除容器
  4. 用同样命令重新启动容器挂载同一卷
  5. 查询数据，验证数据还在

问题 / 场景

问：为什么 MySQL 容器第二次启动时不执行初始化（建库建表）？

  • MySQL 官方镜像的初始化脚本（创建 MYSQL_DATABASE、MYSQL_USER 等）只在数据目录为空时执行。挂载已有数据的卷后，数据目录非空，初始化脚本跳过，直接加载已有数据。这就是持久化的体现。

问：升级 MySQL 版本（如 8.0 升 8.1）时数据会丢吗？

  • 如果用了持久化卷，不会丢。流程：
    1. 停止旧容器（docker stop）
    2. 删除旧容器（docker rm，卷保留）
    3. 用新镜像启动新容器，挂载同一卷（docker run -v mysql_data:/var/lib/mysql mysql:8.1）
    4. 数据自动加载
  • 注意：跨大版本升级（如 5.7 升 8.0）可能涉及数据格式兼容，需先备份数据，按 MySQL 官方升级流程操作。

问：CTTS 项目的 MySQL 需要持久化哪些东西？

  • 必需：/var/lib/mysql（数据库数据）
  • 推荐：/etc/mysql/conf.d（自定义配置，如字符集设置）
  • 可选：/var/log/mysql（日志，便于审计）

易错点

  1. ❌ 忘记挂载 /var/lib/mysql。✅ 这是 MySQL 数据目录，必须挂载卷持久化，否则容器删除数据全丢。
  2. ❌ 重建容器时担心 MYSQL_DATABASE 会覆盖已有数据库。✅ MySQL 初始化脚本只在数据目录为空时执行，挂载已有数据的卷会跳过初始化，直接加载已有数据。
  3. ❌ 跨大版本升级不备份。✅ 跨大版本升级（如 5.7→8.0）可能涉及数据格式不兼容，升级前必须备份数据。
  4. ❌ 升级时直接用新镜像覆盖旧容器但不挂载卷。✅ 升级时新容器必须挂载原卷，否则数据丢失。
  5. ❌ 混淆数据卷和配置挂载。✅ 数据用 Volume（持久化、可备份），配置可用 Bind Mount（便于编辑），各取所长。

小结

MySQL 容器持久化的核心是挂载 /var/lib/mysql 到数据卷。验证持久化的标准流程是"创建卷→启动容器→写入数据→删除容器→重建容器挂载同一卷→验证数据"。配置文件可用 Bind Mount 挂载便于编辑。这是 CTTS 项目数据库走向生产可用的关键配置，也是第 11 次课 Compose 编排的基础。

四、拓展阅读（选学）

  1. tmpfs 挂载：Docker 还有第三种挂载方式 tmpfs，数据存在宿主机内存中，容器停止即消失，适合敏感临时数据（如密钥）。详见 docs.docker.com/storage/tmpfs/。
  2. Volume Driver：Volume 支持驱动插件，可对接 NFS、AWS EFS、GCE Persistent Disk 等远程存储，实现跨主机共享。详见 docs.docker.com/storage/volumes/#use-a-volume-driver。
  3. 卷的只读挂载：用 :ro 或 readonly 让容器只读访问卷，提升安全性（如配置文件挂载为只读）。
  4. docker-compose 中的 volumes：第 11 次课会学到，Compose 文件中用顶层 volumes: 声明卷，服务中用 volumes: 挂载，语法更声明式。
  5. 生产环境备份策略：生产环境通常用 cron 定时任务 + 临时容器备份卷，结合异地存储（如对象存储 OSS/S3）实现 3-2-1 备份原则。
