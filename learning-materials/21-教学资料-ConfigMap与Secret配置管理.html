一、学习导读

1.1 上节课回顾

第20次课我们学习了K8s网络进阶：Pod网络（CNI、Flannel）、Service DNS（<svc>.<ns>.svc.cluster.local）、网络策略NetworkPolicy。这些解决了"Pod之间怎么通信"的问题。

1.2 本节课要解决的问题

  • CTTS后端SpringBoot的 application.yml 里写死了 spring.datasource.url=jdbc:mysql://mysql-svc:3306/ctts，换环境就要改代码重新打镜像。
  • 数据库密码 root123456 直接写在Deployment的env里，YAML提交到Git全班可见。
  • 想改个日志级别从INFO到DEBUG，要重新构建镜像、推送、滚动更新，慢且麻烦。

ConfigMap和Secret就是来解决这三件事的：把配置从镜像里搬出来、把密码从YAML里藏起来、让配置可以不重启Pod就更新。

1.3 学完本课你能做到

  • 用命令行和YAML两种方式创建ConfigMap和Secret。
  • 用env、envFrom、Volume三种方式把配置挂载到Pod。
  • 验证ConfigMap Volume挂载的热更新，理解env挂载不热更新。
  • 识别"密码明文存储"这类安全隐患并给出改造方案。
  • 排查"配置没生效""挂载文件为空""Secret编码错误"等常见报错。

1.4 学习建议

  • base64要亲手敲一遍：echo -n 'xxx' | base64，理解"编码"和"加密"的本质区别。
  • 一定要做热更新实验：kubectl edit configmap 后进Pod看文件变化，这是面试高频考点。
  • 对比着学：ConfigMap vs Secret、env vs Volume、热更新 vs 不热更新，三组对比记住核心差异。
  • 安全意识贯穿始终：看到明文密码就条件反射"这应该用Secret"。

二、知识点详解

K21-1 配置管理需求

定义

配置管理 是指将应用程序运行时所需的参数（数据库连接、日志级别、第三方API地址、密码、证书等）从镜像和代码中分离出来，以独立资源的形式管理。

Kubernetes提供两个核心资源对象：

  • ConfigMap：存储非敏感的配置数据（明文）。
  • Secret：存储敏感的配置数据（密码、Token、证书，base64编码）。

原理

传统应用把配置写在 application.yml、config.json 里，打进镜像。云原生应用遵循**十二要素应用（Twelve-Factor App）**第3条："配置存在环境中，不在代码里"。

图示 1：传统方式 云原生方式
  • 传统方式 云原生方式
  •         镜像 镜像 ← 同一镜像
  •         application application 跑多环境
  •         .yml .yml 模板
  •     (写死配置)
  •     换环境=重打镜像 启动时注入
  •     ConfigMap/Secret ← 配置独立
  •     (env/Volume挂载) 可改可换

问题：为什么需要ConfigMap/Secret？

痛点 不用ConfigMap/Secret 用ConfigMap/Secret
配置与镜像耦合 配置打进镜像，换环境=重打镜像 同一镜像+不同ConfigMap跑多环境
环境差异 dev/test/prod各打一个镜像 三个ConfigMap对应三环境
敏感信息暴露 密码写在YAML，Git可见 密码走Secret，base64编码
配置变更 改配置=改代码=重新构建发布 改ConfigMap即可（Volume可热更新）
配置复用 每个Pod重复写env 一份ConfigMap被多个Pod共享

一句话总结：ConfigMap/Secret让"镜像"和"配置"解耦，让"非敏感"和"敏感"信息分离。

完整示例（CTTS配置拆分前 vs 后）

拆分前（application.yml写死）：

spring:
  datasource:
    url: jdbc:mysql://mysql-svc:3306/ctts
    username: root
    password: root123456       # ← 明文！
    driver-class-name: com.mysql.cj.jdbc.Driver
logging:
  level:
    com.ctts: DEBUG            # ← dev用DEBUG，prod应该用INFO

拆分后：

  • ConfigMap ctts-db-config：url、username、driver、log-level
  • Secret ctts-db-secret：password
  • Pod通过env或Volume挂载，镜像里只剩 application.yml 模板（用 ${SPRING_DATASOURCE_URL} 占位）

图示

图示 2：ConfigMap (明文)
  • ConfigMap (明文)
  •     SPRING_DATASOURCE_URL = jdbc:mysql://...
  •     SPRING_DATASOURCE_USERNAME = root
  •     LOG_LEVEL = INFO
  •   env / Volume

  •     SpringBoot读环境变量/配置文件启动

  •     JWT_SECRET = bXlKd3RTZWNyZXQxMjM=

易错点

  • 误区：把密码也放进ConfigMap。✗ 密码必须用Secret。
  • 误区：以为ConfigMap能加密。✗ ConfigMap是明文，kubectl get configmap -o yaml 直接看到值。
  • 误区：把整个 application.yml 原样打进ConfigMap。✗ 应该拆成键值，或用 --from-file 挂载整个文件。

小结

配置管理的核心目标是"镜像与环境解耦"。非敏感配置用ConfigMap，敏感信息用Secret，这是云原生应用的基线实践。

K21-2 ConfigMap

定义

ConfigMap 是Kubernetes中用于存储非敏感配置数据的API对象，以键值对形式存在，数据明文存储在etcd中。

原理

ConfigMap本质是一个"键值对仓库"，Pod通过以下方式消费它：

  1. 环境变量：env（逐个引用）或 envFrom（批量注入）。
  2. Volume挂载：把ConfigMap的每个键变成文件，挂载到Pod目录。

ConfigMap本身不"做"任何事，只有被Pod引用时才生效。

创建方式一：命令行 kubectl create configmap

语法：

kubectl create configmap <name> [options]

三种数据来源：

参数 说明 示例
--from-literal=key=value 从字面量创建 --from-literal=LOG_LEVEL=INFO
--from-file=<path> 从文件创建（键=文件名，值=文件内容） --from-file=application.yml
--from-file=key=<path> 从文件创建并指定键名 --from-file=db-config=application.yml
--from-env-file=<path> 从env文件批量创建 --from-env-file=config.env

示例1：字面量创建CTTS数据库配置

kubectl create configmap ctts-db-config \
  --from-literal=SPRING_DATASOURCE_URL="jdbc:mysql://mysql-svc:3306/ctts" \
  --from-literal=SPRING_DATASOURCE_USERNAME="root" \
  --from-literal=SPRING_DATASOURCE_DRIVER="com.mysql.cj.jdbc.Driver" \
  --from-literal=LOG_LEVEL="INFO"

示例2：从文件创建（挂载整个application.yml）

# 假设本地有 application.yml
kubectl create configmap ctts-app-config --from-file=application.yml

示例3：从env文件批量创建

# config.env 内容：
# LOG_LEVEL=INFO
# APP_ENV=prod
# THREAD_POOL_SIZE=200
kubectl create configmap ctts-app-config --from-env-file=config.env

创建方式二：YAML定义

示例：CTTS数据库配置ConfigMap

apiVersion: v1
kind: ConfigMap
metadata:
  name: ctts-db-config
  namespace: default
  labels:
    app: ctts
data:
  SPRING_DATASOURCE_URL: "jdbc:mysql://mysql-svc:3306/ctts"
  SPRING_DATASOURCE_USERNAME: "root"
  SPRING_DATASOURCE_DRIVER: "com.mysql.cj.jdbc.Driver"
  LOG_LEVEL: "INFO"
  # 多行配置用 | 或 > 保留换行
  application.yml: |
    server:
      port: 8081
    spring:
      datasource:
        url: jdbc:mysql://mysql-svc:3306/ctts
        username: root
        driver-class-name: com.mysql.cj.jdbc.Driver
    logging:
      level:
        com.ctts: INFO

data vs stringData：

  • data：值必须是base64编码（ConfigMap一般直接写明文，因为是"非敏感"，但语法上data字段值是字符串）。
  • stringData：值是明文字符串，K8s自动处理。推荐用stringData写YAML，更直观不易错。
apiVersion: v1
kind: ConfigMap
metadata:
  name: ctts-db-config
data:
  LOG_LEVEL: "INFO"
# 等价写法（stringData更宽容，允许包含特殊字符）
# stringData:
#   LOG_LEVEL: "INFO"

验证与查看

# 查看所有ConfigMap
kubectl get configmap
kubectl get cm        # 简写

# 查看详情（含data）
kubectl describe configmap ctts-db-config

# 以YAML格式查看（看到完整data）
kubectl get configmap ctts-db-config -o yaml

输出示例：

apiVersion: v1
data:
  LOG_LEVEL: INFO
  SPRING_DATASOURCE_DRIVER: com.mysql.cj.jdbc.Driver
  SPRING_DATASOURCE_URL: jdbc:mysql://mysql-svc:3306/ctts
  SPRING_DATASOURCE_USERNAME: root
kind: ConfigMap
metadata:
  creationTimestamp: "2024-07-23T10:00:00Z"
  name: ctts-db-config
  namespace: default
  resourceVersion: "12345"

注意：data里的值是明文可见的，这就是ConfigMap不能存密码的原因。

易错点

  • 键名带特殊字符：ConfigMap键名必须符合DNS子域名规范，不能含空格、/、: 等。--from-file 的文件名若含特殊字符会报错。
  • 大配置超限：ConfigMap单个最大1MiB，超过需要拆分或用Volume挂载多个。
  • 误用data存二进制：data字段值是字符串，二进制数据应先base64编码或用Secret。
  • 命名空间隔离：ConfigMap属于某个namespace，Pod只能引用同namespace的ConfigMap。
  • 删除被引用的ConfigMap：不会影响已运行的Pod（环境变量已注入、文件已挂载），但Pod重启后会失败。

小结

ConfigMap用"键值对"+"明文"的方式管理非敏感配置，支持命令行和YAML两种创建方式，是配置外置化的第一步。

K21-3 Secret

定义

Secret 是Kubernetes中用于存储敏感数据（密码、Token、证书私钥）的API对象，数据以base64编码形式存储在etcd中。

原理：base64编码（非加密！）

关键认知：base64是编码，不是加密。

维度 base64编码 加密（如AES）
目的 让二进制数据可表示为文本 保护数据机密性
可逆性 任意人可解码 需要密钥才能解密
安全性 无 高
例子 echo -n 'root123456' | base64 → cm9vdDEyMzQ1Ng== 用AES加密需密钥
图示 4：明文: root123456
明文

root123456

echo -n 'root123456' | base64

编码

cm9vdDEyMzQ1Ng== ← Secret里存这个

echo 'cm9vdDEyMzQ1Ng==' | base64 -d

明文

root123456 ← 任何人都能解回来

Secret的意义：

  1. 避免在YAML/截图/终端里直接看到明文密码（防"肩窥"）。
  2. 支持挂载为环境变量或文件，应用读取时不感知编码过程（K8s自动解码）。
  3. 配合RBAC、etcd加密（encryption at rest）、审计日志实现更完整的安全体系。

真正让Secret安全的方式（进阶）：

  • 启用etcd静态加密（EncryptionConfiguration）。
  • 使用外部密钥管理（HashiCorp Vault、云厂商KMS、Sealed Secrets）。
  • 严格RBAC限制谁能 kubectl get secret。

Secret的三种类型

类型 type字段值 用途 典型键
Opaque Opaque 通用键值对（最常用） 自定义
docker-registry kubernetes.io/dockerconfigjson 私有镜像仓库认证 .dockerconfigjson
tls kubernetes.io/tls TLS证书和私钥 tls.crt、tls.key
service-account-token kubernetes.io/service-account-token SA令牌（自动创建） token、ca.crt

创建方式一：命令行 kubectl create secret

1. generic（Opaque类型）—— 最常用

kubectl create secret generic <name> \
  --from-literal=key=value \
  --from-file=key=path

示例：创建CTTS数据库密码Secret

kubectl create secret generic ctts-db-secret \
  --from-literal=MYSQL_ROOT_PASSWORD="Ctts@2024" \
  --from-literal=JWT_SECRET="myJwtSecretKey2024"

注意：命令行用 --from-literal 时直接写明文，K8s自动base64编码后存入。

2. docker-registry（私有仓库认证）

kubectl create secret docker-registry ctts-registry-secret \
  --docker-server=registry.cn-hangzhou.aliyuncs.com \
  --docker-username=admin \
  --docker-password='MyRegistry@2024' \
  --docker-email=admin@ctts.com

在Deployment中引用：

spec:
  template:
    spec:
      imagePullSecrets:
      - name: ctts-registry-secret
      containers:
      - image: registry.cn-hangzhou.aliyuncs.com/ctts/backend:v1

3. tls（TLS证书）

kubectl create secret tls ctts-tls-secret \
  --cert=cert.pem \
  --key=key.pem

（第19次课Ingress已演示过，这里回顾）

创建方式二：YAML定义

步骤1：手动base64编码

echo -n 'Ctts@2024' | base64
# 输出: Q3R0c0AyMDI0

echo -n 'myJwtSecretKey2024' | base64
# 输出: bXlKd3RTZWNyZXRLZXkyMDI0

注意 echo -n：必须加 -n 去掉换行符，否则编码结果会多一个字符。

步骤2：写YAML

apiVersion: v1
kind: Secret
metadata:
  name: ctts-db-secret
  namespace: default
  labels:
    app: ctts
type: Opaque
data:
  MYSQL_ROOT_PASSWORD: Q3R0c0AyMDI0
  JWT_SECRET: bXlKd3RTZWNyZXRLZXkyMDI0

用stringData简化（推荐，无需手动编码）：

apiVersion: v1
kind: Secret
metadata:
  name: ctts-db-secret
  namespace: default
type: Opaque
stringData:
  MYSQL_ROOT_PASSWORD: "Ctts@2024"
  JWT_SECRET: "myJwtSecretKey2024"

stringData 写明文，K8s自动编码后存入 data，且不显示在 kubectl get -o yaml 的stringData字段（只显示编码后的data）。

验证与查看

# 查看所有Secret
kubectl get secret
kubectl get secrets

# 查看详情（data字段显示base64编码值）
kubectl describe secret ctts-db-secret

# 以YAML查看（看到data的编码值）
kubectl get secret ctts-db-secret -o yaml

输出示例：

apiVersion: v1
data:
  MYSQL_ROOT_PASSWORD: Q3R0c0AyMDI0
  JWT_SECRET: bXlKd3RTZWNyZXRLZXkyMDI0
kind: Secret
metadata:
  name: ctts-db-secret
  namespace: default
type: Opaque

解码查看明文（演示用，生产慎用）：

kubectl get secret ctts-db-secret -o jsonpath='{.data.MYSQL_ROOT_PASSWORD}' | base64 -d
# 输出: Ctts@2024

图示：Secret创建与使用流程

图示 5：echo -n 'Ctts@2024' | base64 → Q3R0c0AyMDI0
1. 编码
echo -n 'Ctts@2024' | base64 → Q3R0c0AyMDI0
▼
2. 创建Secret
kubectl create secret generic ctts-db-secret
from-literal=MYSQL_ROOT_PASSWORD='Ctts@2024'

易错点

  • 忘记 echo -n：不加 -n 会把换行符也编码进去，导致密码多了 \n，应用连接数据库失败且极难排查。
  • 误以为Secret加密了：base64任何人可解码，要真正加密需启用etcd静态加密。
  • 把Secret提交到Git：YAML里的base64值等同于明文，应该用 --from-literal 或外部工具（Sealed Secrets、external-secrets）。
  • 超过1MiB限制：Secret单条最大1MiB，大证书或大文件需拆分。
  • type写错：Opaque是通用，dockerconfigjson必须用 kubectl create secret docker-registry 自动生成正确格式。
  • 命名冲突：Secret是namespace级资源，不同namespace可同名。

小结

Secret用base64编码存储敏感数据，支持generic/docker-registry/tls三种类型。核心要点：base64不是加密，Secret的价值在于"避免明文直视 + 配合RBAC/etcd加密构建安全体系"。

K21-4 挂载方式

定义

将ConfigMap/Secret的数据注入Pod的方式有两种：环境变量和Volume文件挂载。

原理对比

维度 环境变量（env/envFrom） Volume挂载（volumes）
形式 注入到容器环境变量 挂载为文件到目录
数量 env逐个、envFrom批量 整个ConfigMap/Secret
热更新 不支持（Pod启动时固化） 支持（kubelet周期同步）
适用 简单键值、启动参数 多文件、配置文件、需热更新
大小限制 单值不超过1MiB 同样受ConfigMap/Secret大小限制
应用感知 应用读环境变量 应用读文件，需自行感知变化

方式一：环境变量 env（逐个引用）

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ctts-backend
  template:
    metadata:
      labels:
        app: ctts-backend
    spec:
      containers:
      - name: ctts-backend
        image: ctts/backend:v1
        ports:
        - containerPort: 8081
        env:
        # 从ConfigMap引用单个键
        - name: SPRING_DATASOURCE_URL
          valueFrom:
            configMapKeyRef:
              name: ctts-db-config
              key: SPRING_DATASOURCE_URL
        - name: SPRING_DATASOURCE_USERNAME
          valueFrom:
            configMapKeyRef:
              name: ctts-db-config
              key: SPRING_DATASOURCE_USERNAME
        # 从Secret引用单个键
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: ctts-db-secret
              key: MYSQL_ROOT_PASSWORD

可选参数 optional：

- name: LOG_LEVEL
  valueFrom:
    configMapKeyRef:
      name: ctts-db-config
      key: LOG_LEVEL
      optional: true    # ConfigMap/键不存在时，Pod仍能启动（值为空）

方式二：环境变量 envFrom（批量注入）

把ConfigMap或Secret的所有键一次性注入为环境变量。

spec:
  template:
    spec:
      containers:
      - name: ctts-backend
        image: ctts/backend:v1
        envFrom:
        - configMapRef:
            name: ctts-db-config       # 注入所有键为环境变量
        - secretRef:
            name: ctts-db-secret       # 注入所有键为环境变量
        - configMapRef:
            name: ctts-app-config
            prefix: APP_               # 加前缀避免键名冲突

envFrom特点：

  • 一次性注入所有键，YAML简洁。
  • 支持 prefix 加前缀（如 APP_LOG_LEVEL）。
  • 键名不符合环境变量命名规范（含点号、横线）的会被自动转换或跳过（K8s 1.28+行为）。

方式三：Volume文件挂载

把ConfigMap/Secret的每个键变成一个文件，挂载到Pod指定目录。

apiVersion: apps/v1
kind: Deployment

  name: ctts-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ctts-backend

          readOnly: true

      - name: db-config-volume
        configMap:
          name: ctts-db-config             # 引用ConfigMap
      - name: db-secret-volume
        secret:
          secretName: ctts-db-secret       # 引用Secret

挂载后的效果：

  • SPRING_DATASOURCE_USERNAME

Volume挂载进阶：items（选择性挂载）

只挂载ConfigMap的部分键，并可重命名文件。

volumes:
- name: db-config-volume
  configMap:
    name: ctts-db-config
    items:
    - key: LOG_LEVEL
      path: log-level.txt         # 文件名改为log-level.txt
      mode: 0644
    - key: SPRING_DATASOURCE_URL
      path: db-url.txt

Volume挂载进阶：subPath（挂载单文件，不覆盖目录）

问题：Volume挂载会覆盖mountPath下的原有内容。如果镜像里 /app/application.yml 已经有文件，挂载ConfigMap后整个目录被覆盖。

解决：用 subPath 只挂载单个文件，不影响目录其他文件。

volumes:
- name: config-volume
  configMap:
    name: ctts-app-config
    items:
    - key: application.yml
      path: application.yml
---
containers:
- name: ctts-backend
  volumeMounts:
  - name: config-volume
    mountPath: /app/application.yml   # 挂载到具体文件路径
    subPath: application.yml          # 只挂载这一个文件

注意：使用subPath后，该文件不再支持热更新（因为subPath挂载是符号链接到具体版本，不会随ConfigMap更新而变化）。

易错点

  • env方式期望热更新：修改ConfigMap后env不变，学生常误以为"改了ConfigMap应用就能感知"。
  • Volume挂载覆盖目录：mountPath写到镜像已有目录会覆盖原有文件，需用subPath。
  • subPath与热更新冲突：用了subPath就不热更新，这是面试常考陷阱。
  • Secret Volume权限：默认文件权限0644，敏感信息建议设为0400（defaultMode: 0400）。
  • ConfigMap键名带点号：envFrom 会跳过含 . 的键，Volume挂载则正常（文件名带点号）。

小结

env适合简单键值且不需热更新，envFrom适合批量注入，Volume适合配置文件且支持热更新。subPath解决"挂载覆盖"问题但牺牲热更新。

K21-5 配置热更新

定义

配置热更新 指修改ConfigMap/Secret后，已运行的Pod能自动感知到新配置，无需重启。

原理：Volume挂载的自动更新机制

当ConfigMap以Volume方式挂载到Pod时：

  1. kubelet在节点上维护一份ConfigMap的副本（在 /var/lib/kubelet/pods/.../volumes/...）。
  2. kubelet周期性同步（默认约60-120秒）ConfigMap的最新版本到该目录。
  3. Pod内的挂载点（通过bind mount）自动反映新内容。
kubectl edit configmap         kubelet同步(~60-120s)      Pod内挂载点
     ctts-db-config                                            更新
          │                                                        │
          ▼                                                        ▼
   ┌─────────────┐         ┌─────────────────┐         ┌─────────────────┐
   │   etcd      │ ──同步─►│ 节点本地副本     │ ──bind──►│ /etc/ctts/config│
   │ ConfigMap   │         │ (kubelet维护)   │  mount  │ 文件内容变化    │
   │ v2          │         │ v2              │         │                 │
   └─────────────┘         └─────────────────┘         └─────────────────┘
                                                              │
                                                              ▼
                                                   应用是否感知？
                                                   ├─ 是 → 自动reload（需应用支持）
                                                   └─ 否 → 进程不感知，文件已变

env方式为什么不自动更新？

环境变量在Pod启动时由kubelet注入到容器进程的环境块中，之后不再变化。修改ConfigMap后：

  • 已运行Pod的环境变量不变。
  • 新建的Pod（如滚动更新）才会注入新值。

结论：env方式要生效新配置，必须重启Pod（kubectl rollout restart）。

应用如何感知Volume更新？

Volume挂载让文件变了，但应用进程是否重新读取配置，取决于应用自身：

  • SpringBoot：默认不感知，需集成 spring-cloud-context（refresh）或 spring-cloud-kubernetes。
  • Nginx：不感知，需 nginx -s reload 或外部reloader（如 stakater/reloader）。
  • Java应用：可监听文件变化（WatchService）或定期重新读取。
  • 配置中心客户端（Apollo/Nacos）：长轮询感知。

所以"热更新"分两层：

  1. K8s层：Volume挂载的文件自动更新（kubelet保证）。
  2. 应用层：应用是否重新加载配置（需应用自身支持）。

Secret为什么不建议热更新？

  • 凭证轮换需重启：数据库连接池在启动时建立，密码变了需要重建连接，热更新文件没有意义。
  • 安全考虑：Secret变更应有审计、应触发Pod滚动重启（确保新密码生效、旧密码失效）。
  • 实践：修改Secret后执行 kubectl rollout restart deployment <name>，让Pod按新Secret重建。

完整示例：ConfigMap热更新验证

1. 创建ConfigMap

kubectl create configmap ctts-log-config --from-literal=LOG_LEVEL=INFO

2. 用Volume挂载到Pod

apiVersion: v1
kind: Pod
metadata:
  name: config-test-pod
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sh", "-c", "while true; do cat /etc/config/LOG_LEVEL; sleep 10; done"]
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
  volumes:
  - name: config-volume
    configMap:
      name: ctts-log-config
kubectl apply -f config-test-pod.yaml
kubectl logs config-test-pod
# 输出: INFO INFO INFO ...

3. 修改ConfigMap

kubectl edit configmap ctts-log-config
# 把 LOG_LEVEL: INFO 改为 LOG_LEVEL: DEBUG

或用命令行：

kubectl patch configmap ctts-log-config -p '{"data":{"LOG_LEVEL":"DEBUG"}}'

4. 等待并观察Pod日志

# 等待60-120秒后
kubectl logs config-test-pod
# 输出: INFO INFO ... DEBUG DEBUG DEBUG ...  ← 自动变成DEBUG

5. 进入Pod直接查看文件

kubectl exec -it config-test-pod -- cat /etc/config/LOG_LEVEL
# 输出: DEBUG

6. 对比：env方式不热更新

apiVersion: v1
kind: Pod
metadata:
  name: env-test-pod
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo $LOG_LEVEL; sleep 10; done"]
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef:
          name: ctts-log-config
          key: LOG_LEVEL
kubectl apply -f env-test-pod.yaml
kubectl logs env-test-pod
# 输出: DEBUG DEBUG ...  (初始值)

kubectl patch configmap ctts-log-config -p '{"data":{"LOG_LEVEL":"ERROR"}}'
# 等待2分钟
kubectl logs env-test-pod
# 输出仍是: DEBUG DEBUG ...  ← 没变化！

结论：env方式不热更新，Volume方式热更新（kubelet同步周期内）。

图示 8：时间轴 ►

时间轴 ►

易错点

  • 以为env会热更新：最常见误区，修改ConfigMap后疑惑"为什么环境变量没变"。
  • subPath挂载不热更新：用subPath挂的单文件不会随ConfigMap更新。
  • 应用不感知：文件变了但应用没reload，配置没生效，需配合应用层机制。
  • Secret热更新期望：改了Secret但连接池没重建，密码"看起来变了其实没用上"。
  • 同步周期误以为是实时：默认60-120秒，不是立即生效。

小结

热更新只对Volume挂载生效（kubelet周期同步），env方式必须重启Pod。应用层需自行感知文件变化才能让新配置真正生效。Secret不建议依赖热更新，应配合滚动重启。

三、综合示例：CTTS配置完整改造

3.1 改造目标

将CTTS后端SpringBoot的数据库配置从镜像里搬出来：

  • 非敏感配置（URL、用户名、驱动、日志级别）→ ConfigMap
  • 敏感配置（数据库密码、JWT密钥）→ Secret
  • 通过envFrom批量注入到Pod

四、拓展阅读

4.1 Sealed Secrets（GitOps友好）

问题：Secret的YAML里是base64，等同于明文，不能提交到Git。 方案：Sealed Secrets用非对称加密，把Secret加密成 SealedSecret 资源，可安全提交Git。控制器在集群内解密还原为Secret。

# 安装kubeseal
kubeseal --format yaml < ctts-db-secret.yaml > ctts-db-sealed.yaml
# ctts-db-sealed.yaml 可以安全提交Git

4.2 External Secrets（对接外部密钥管理）

将AWS Secrets Manager、HashiCorp Vault、阿里云KMS等外部系统的密钥同步为K8s Secret。

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: ctts-db-secret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: ctts-db-secret    # 生成的K8s Secret名
  data:
  - secretKey: MYSQL_ROOT_PASSWORD
    remoteRef:
      key: ctts/db
      property: password

4.3 etcd静态加密

让Secret在etcd里真正加密（而非base64），需配置 EncryptionConfiguration：

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: <base64-encoded-32-byte-key>
  - identity: {}    # 兜底

4.4 配置中心对比（ConfigMap vs Apollo/Nacos）

维度 ConfigMap Apollo/Nacos
定位 K8s原生配置存储 分布式配置中心
热更新 Volume挂载（kubelet同步） 长轮询实时推送
多语言支持 通用（文件/环境变量） 需客户端SDK
多环境管理 多namespace/多ConfigMap 命名空间+环境+组
灰度发布 不支持 支持
适用规模 单集群、中小项目 多集群、大规模微服务

选型建议：K8s原生应用、配置量小用ConfigMap；微服务众多、需实时推送和灰度用Apollo/Nacos；两者也可结合（ConfigMap存启动配置，Apollo存运行时配置）。

4.5 十二要素应用（Twelve-Factor App）

第3条"配置"：配置应存在环境中，不在代码里。判断标准：代码库在不同环境间能否直接部署而不修改？如果代码库里没有任何环境特定信息（数据库地址、API地址、密码），就是符合十二要素的。

K8s的ConfigMap + Secret正是这一原则在云原生时代的标准实现。
