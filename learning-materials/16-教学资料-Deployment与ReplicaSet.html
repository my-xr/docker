二、知识点详解

知识点 K16-1：Deployment 概念与作用

定义

Deployment 是 Kubernetes 中最常用的工作负载控制器（Workload Controller），它通过管理 ReplicaSet 来间接管理 Pod，为应用提供自愈、扩缩容、滚动更新与回滚能力。

一句话理解：

Deployment 是 K8s 中管理无状态应用的工作负载控制器，它让你声明"我想要 3 个副本"，K8s 始终维持 3 个副本运行——挂了自动补、多了删、少了加、更新时渐进替换。

原理

裸 Pod 的三大痛点（为什么需要 Deployment）：

痛点 1：不自愈
  - 裸 Pod 所在节点宕机 → Pod 消失，无人重建
  - 裸 Pod 内容器崩溃 → restartPolicy 会重启容器，但 Pod 本身被删除后不会重建
  - 生产环境要求"挂了自动补"，裸 Pod 做不到

痛点 2：不能扩缩容
  - 裸 Pod 只有 1 个实例，无法应对流量高峰
  - 要扩容只能手动 kubectl run 再起几个，缺乏统一管理
  - 生产环境要求"按需扩缩容"，裸 Pod 做不到

痛点 3：不能滚动更新
  - 裸 Pod 更新镜像只能 delete + apply，服务中断
  - 没有"先启新再停旧"的滚动更新机制
  - 没有版本历史，无法回滚
  - 生产环境要求"不停机更新、可回滚"，裸 Pod 做不到

Deployment 解决三大痛点：

痛点 Deployment 如何解决
不自愈 Deployment 通过 ReplicaSet 持续监控 Pod 副本数，发现 Pod 少了就自动创建新的补齐
不能扩缩容 修改 replicas 字段或用 kubectl scale，Deployment 自动调整 Pod 数量
不能滚动更新 更新镜像版本后，Deployment 创建新 ReplicaSet，逐步替换旧 Pod，并保留历史版本可回滚

Deployment 的核心能力：

Deployment vs Pod 对比：

对比项 裸 Pod Deployment
自愈能力 无（Pod 删除后不重建） 有（自动补齐副本）
扩缩容 不支持 支持（replicas / kubectl scale）
滚动更新 不支持 支持（kubectl set image）
回滚 不支持 支持（kubectl rollout undo）

声明式管理 vs 命令式管理：

命令式（Imperative）：
  - 告诉 K8s "做什么动作"
  - 例：kubectl run nginx --image=nginx（创建一个 Pod）
  - 例：kubectl scale deployment xxx --replicas=5（扩容到 5）
  - 快速但不可复现

声明式（Declarative）：
  - 告诉 K8s "期望状态是什么"
  - 例：YAML 里写 replicas: 3，K8s 维持 3 个副本
  - 例：kubectl apply -f deployment.yaml（应用期望状态）
  - 可版本化、可复现、生产推荐

📌 Deployment 是声明式的：你描述"我要 3 个副本、镜像 v1"，K8s 始终维持这个状态。如果有人手动删了一个 Pod，Deployment 会自动创建新的补齐——这就是"声明式 + 自愈"的威力。

问题 / 场景

问：有了 Pod 为什么还要 Deployment？

  • 裸 Pod 是临时性的，无自愈、无扩缩容、无滚动更新能力。生产环境要求"挂了自动补、按需扩缩容、不停机更新可回滚"，这些都靠 Deployment 实现。所以生产环境几乎不用裸 Pod，都用 Deployment（或 StatefulSet/DaemonSet 等工作负载）。

问：Deployment 是 K8s 唯一的工作负载吗？

  • 不是。K8s 有多种工作负载控制器，Deployment 是最常用的，用于无状态应用（如 Web 服务、API 服务）。还有：
    • StatefulSet：有状态应用（如数据库，需要稳定网络标识和持久存储）
    • DaemonSet：每个节点跑一个（如日志收集、监控代理）
    • Job/CronJob：一次性/定时任务
  • 本课程重点掌握 Deployment，其他了解概念。

问：Deployment 怎么知道要管理哪些 Pod？

  • 通过 selector（标签选择器）。Deployment YAML 里 spec.selector.matchLabels 定义"我要管理带这些标签的 Pod"，spec.template.metadata.labels 定义"我创建的 Pod 带这些标签"。二者必须匹配，Deployment 才能找到并管理自己创建的 Pod。详见 K16-3。

问：声明式和命令式到底有什么区别？

  • 命令式告诉 K8s"做什么动作"（如 scale 到 5），声明式告诉 K8s"期望状态是什么"（如 YAML 写 replicas: 5，K8s 维持 5 个）。声明式的好处是可版本化（YAML 提交 Git）、可复现（同样 YAML 在任何集群都能创建同样状态）、自愈（实际状态偏离期望状态时自动纠正）。

完整示例

一个最小可用的 Deployment YAML（CTTS 后端，3 副本）：

# 文件名：ctts-backend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-backend
  namespace: ctts
  labels:
    app: ctts-backend
spec:
  replicas: 3                          # 期望副本数
  selector:
    matchLabels:
      app: ctts-backend                # 选择带 app=ctts-backend 标签的 Pod
  template:                            # Pod 模板
    metadata:
      labels:
        app: ctts-backend              # 创建的 Pod 带这个标签（必须与 selector 匹配）
    spec:
      containers:
      - name: backend
        image: ctts-backend:v1
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 8080

部署与查看：

# 应用 YAML 创建 Deployment
kubectl apply -f ctts-backend-deployment.yaml -n ctts
# 预期输出：
# deployment.apps/ctts-backend created

# 查看 Deployment
kubectl get deployments -n ctts
# 预期输出：
# NAME           READY   UP-TO-DATE   AVAILABLE   AGE
# ctts-backend   3/3     3            3           30s

# 查看 ReplicaSet
kubectl get replicasets -n ctts
# 预期输出：
# NAME                      DESIRED   CURRENT   READY   AGE
# ctts-backend-abc1234      3         3         3       30s

# 查看 Pod（3 个副本）
kubectl get pods -n ctts
# 预期输出：
# NAME                            READY   STATUS    RESTARTS   AGE
# ctts-backend-abc1234-xyz1       1/1     Running   0          30s
# ctts-backend-abc1234-xyz2       1/1     Running   0          30s
# ctts-backend-abc1234-xyz3       1/1     Running   0          30s

📌 这个最小示例展示了 Deployment 的核心：replicas=3（3 副本）+ selector（选择 Pod）+ template（Pod 模板）。详细字段见 K16-3。

易错点

  1. ❌ 误认为"Deployment = Pod"。✅ Deployment 是工作负载控制器，通过 ReplicaSet 管理 Pod，不是 Pod 本身。
  2. ❌ 误认为"生产环境可以直接用裸 Pod"。✅ 裸 Pod 无自愈、无扩缩容、无滚动更新，生产环境几乎不用裸 Pod，都用 Deployment 等工作负载。

小结

Deployment 是 K8s 中管理无状态应用的工作负载控制器，通过 ReplicaSet 管理 Pod，提供自愈、扩缩容、滚动更新、回滚、声明式管理五大能力。生产环境几乎不用裸 Pod，都用 Deployment。Deployment 是声明式的——你描述"期望状态"，K8s 维持这个状态。

知识点 K16-2：ReplicaSet 副本控制

定义

ReplicaSet 是 Kubernetes 中的副本控制器，它的核心职责是维持指定数量的 Pod 副本运行——少了就创建，多了就删除。ReplicaSet 通过标签选择器（selector）确定自己管理哪些 Pod。

Deployment 与 ReplicaSet 的关系：

Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod。 Deployment 是上层控制器，负责滚动更新与版本管理；ReplicaSet 是下层控制器，负责维持副本数。通常不直接使用 ReplicaSet，而是通过 Deployment 间接管理。

原理

三层管理关系：

图示 3：Deployment
  •     Deployment
  •     - 定义期望状态（replicas / template）
  •     - 管理多个 ReplicaSet 版本（用于滚动更新/回滚）
  •     - 不直接管 Pod
  •     ▼ 管理
  •         ReplicaSet (RS)
  •         - 持续监控 Pod 副本数
  •         - 少了就创建，多了就删除
  •         - 通过 selector 匹配 Pod
  •         - 不直接管 Pod 的运行（那是 kubelet 的事）
  •         ▼ 管理
  •           Pod1 Pod2 Pod3

ReplicaSet 如何维持副本数：

期望副本数 = 3（spec.replicas: 3）

场景 1：Pod-2 所在节点宕机
  - ReplicaSet 发现只有 2 个 Pod（Pod-1, Pod-3）
  - 立即创建 Pod-4 补齐
  - 恢复到 3 个 Pod（Pod-1, Pod-3, Pod-4）

场景 2：有人手动删了 Pod-1
  - ReplicaSet 发现只有 2 个 Pod
  - 立即创建 Pod-5 补齐
  - 恢复到 3 个 Pod（Pod-2, Pod-3, Pod-5）

场景 3：有人手动多起了一个同标签 Pod
  - ReplicaSet 发现有 4 个 Pod（多了 1 个）
  - 删除多余的 Pod（保留 3 个）

关键：ReplicaSet 通过 selector 匹配 Pod，只要标签匹配就纳入管理

为什么 Deployment 不直接管 Pod，而要多一层 ReplicaSet？

图示 4：答案：为了滚动更新与回滚

答案：为了滚动更新与回滚

Deployment 更新镜像版本时：

创建一个新的 ReplicaSet（RS-new，镜像 v2）

旧 ReplicaSet（RS-old，镜像 v1）保留，但副本数逐步减少

RS-new 副本数逐步增加

最终 RS-old 副本数=0（但保留 RS 对象，用于回滚）

RS-new 副本数=3（期望值）

这样 Deployment 保留了所有历史 ReplicaSet，可以随时回滚到任意版本。

如果 Deployment 直接管 Pod，就没有"版本"概念，无法回滚。

Deployment（管理多个 RS 版本）

RS-new (v2) 副本数=3 ← 当前版本

Pod1 (v2)

Pod2 (v2)

Pod3 (v2)

RS-old1 (v1) 副本数=0 ← 上一版本（可回滚）

(无 Pod，但 RS 对象保留)

RS-old2 (v0) 副本数=0 ← 更早版本（可回滚）

ReplicaSet 的 YAML 结构（了解，通常不直接写）：

apiVersion: apps/v1
kind: ReplicaSet                  # 资源类型
metadata:
  name: ctts-backend-rs
spec:
  replicas: 3                     # 期望副本数
  selector:                       # 标签选择器
    matchLabels:
      app: ctts-backend
  template:                       # Pod 模板（与 Deployment 一样）
    metadata:
      labels:
        app: ctts-backend
    spec:
      containers:
      - name: backend
        image: ctts-backend:v1

📌 实际工作中几乎不直接写 ReplicaSet YAML，而是写 Deployment YAML（Deployment 会自动创建和管理 ReplicaSet）。直接用 ReplicaSet 是 K8s 早期做法，现在已被 Deployment 取代。

问题 / 场景

问：为什么不直接用 ReplicaSet，还要套一层 Deployment？

  • ReplicaSet 只能维持副本数，不能滚动更新和回滚。Deployment 在 ReplicaSet 之上增加了版本管理能力——每次更新镜像都会创建新的 ReplicaSet，保留旧的 ReplicaSet（副本数=0）用于回滚。所以 Deployment 是 ReplicaSet 的"升级版"，实际工作中都用 Deployment。

问：ReplicaSet 是怎么"数"Pod 的？

  • 通过 selector 标签选择器。ReplicaSet 的 selector 定义"我要管理带这些标签的 Pod"，然后它持续查询集群中带这些标签的 Pod 数量，与期望副本数比较，少了就创建，多了就删除。所以标签匹配是 ReplicaSet 工作的基础。

问：手动删一个 Pod，ReplicaSet 会立即重建吗？

  • 会。ReplicaSet 通过控制器循环（control loop）持续监控，发现 Pod 数量少于期望值就立即创建新 Pod 补齐。这是 K8s"声明式 + 自愈"的核心体现。这也是为什么直接 kubectl delete pod 删不掉 Deployment 管理的 Pod——删了立即重建。

问：滚动更新时，旧 ReplicaSet 的 Pod 是立即删除吗？

  • 不是。滚动更新是渐进式的：先启动一定数量的新 Pod，再终止一定数量的旧 Pod，循环直到全部替换。这个过程由 maxSurge 和 maxUnavailable 参数控制速率（见 K16-4）。旧 ReplicaSet 不会被删除，只是副本数降到 0，保留用于回滚。

问题 / 场景

问：Deployment 的 apiVersion 为什么是 apps/v1 而不是 v1？

  • Deployment 属于 apps API 组（应用类资源），版本是 v1（稳定版）。Pod / Service / ConfigMap 属于核心 API 组，apiVersion 是 v1。不同资源 apiVersion 不同，记不住时可以用 kubectl api-resources 查询。

问：selector 和 template.labels 不匹配会怎样？

  • Deployment 会创建 Pod，但 ReplicaSet 找不到这些 Pod（因为标签不匹配），导致 READY 永远是 0/3，AVAILABLE 永远是 0。这是 Deployment YAML 最常见的错误。规则：template.labels 必须包含 selector.matchLabels 的所有键值对。

问：replicas 可以写小数吗？如 1.5？

  • 不可以。replicas 必须是正整数（如 1、3、5），不能是小数或负数。写 1.5 会报 YAML 校验错误。

问：revisionHistoryLimit 是什么？

  • 保留的历史 ReplicaSet 版本数，默认 10。每次滚动更新会创建新 ReplicaSet，旧的保留用于回滚。revisionHistoryLimit=10 表示最多保留 10 个旧版本，超过会清理最早的。设为 0 表示不保留历史（无法回滚，不推荐）。

问：Recreate 策略和 RollingUpdate 有什么区别？

  • RollingUpdate（默认）：先启新再停旧，服务不中断，适合生产。Recreate：先全删旧再建新，服务会中断一段时间，适合开发/测试或不能多版本共存的场景（如使用 ReadWriteOnce 存储的有状态应用，但那种场景应该用 StatefulSet）。

知识点 K16-4：滚动更新与回滚

定义

滚动更新（Rolling Update） 是 Deployment 的默认更新策略，在更新应用时逐步用新版本 Pod 替换旧版本 Pod，保证更新期间服务不中断。

回滚（Rollback） 是 Deployment 的版本回退能力，当新版本有问题时可以快速回到上一个稳定版本。

相关命令：

  • kubectl set image：触发滚动更新（更新镜像版本）
  • kubectl rollout status：查看滚动更新状态
  • kubectl rollout history：查看版本历史
  • kubectl rollout undo：回滚到上一版本（或指定版本）

原理

滚动更新的完整流程：

图示 8：Deployment 滚动更新时新旧 ReplicaSet 交替
  • 初始状态：Deployment 管理 RS-old（v1），3 个 Pod 都是 v1
  •     Deployment
  •     RS-old (v1) 副本数=3
  •       Pod1 (v1)
  •       Pod2 (v1)
  •       Pod3 (v1)
  •     RS-new (v2) 副本数=0（不存在）
  • 执行 kubectl set image deployment/xxx container=xxx:v2
  • Step 1：Deployment 创建 RS-new（v2），副本数=0
  •     Deployment
  •     RS-old (v1) 副本数=3
  •       Pod1 (v1)
  •       Pod2 (v1)
  •       Pod3 (v1)
  •     RS-new (v2) 副本数=0 ← 新 RS 创建
  • Step 2：RS-new 副本数+1（启动 Pod4 v2），RS-old 副本数-1（终止 Pod1）
  •     Deployment
  •     RS-old (v1) 副本数=2 ← 减 1
  •       Pod2 (v1)
  •       Pod3 (v1) ← Pod1 被终止
  •     RS-new (v2) 副本数=1 ← 加 1
  •     Pod4 (v2) ← 新 Pod 启动
  • Step 3：继续替换
  •     Deployment
  •     RS-old (v1) 副本数=1
  •       Pod3 (v1) ← Pod2 被终止
  •     RS-new (v2) 副本数=2
  •     Pod4 (v2)
  •     Pod5 (v2) ← 新 Pod 启动
  • Step 4：完成替换
  •     Deployment
  •     RS-old (v1) 副本数=0 ← 保留 RS（用于回滚）
  •     RS-new (v2) 副本数=3 ← 当前版本
  •     Pod4 (v2)
  •     Pod5 (v2)
  •     Pod6 (v2)
  • 关键：旧 RS 保留（副本数=0），用于回滚

RollingUpdate 策略参数详解：

图示 9：spec.strategy.rollingUpdate:

spec.strategy.rollingUpdate:

maxSurge

25% # 滚动更新时，最多超出期望副本数的比例

maxUnavailable

25% # 滚动更新时，最多低于期望副本数的比例

含义（以 replicas=3、maxSurge=25%、maxUnavailable=25% 为例）：

maxSurge=25%：

滚动更新期间，最多可以有 3 + 3*25% = 3.75 → 向上取整 = 4 个 Pod

即最多同时存在 4 个 Pod（3 期望 + 1 超出）

控制新 Pod 启动速率

maxUnavailable=25%：

滚动更新期间，最少必须有 3 - 3*25% = 2.25 → 向下取整 = 2 个 Pod

即最少保持 2 个 Pod 可用（3 期望 - 1 不足）

控制旧 Pod 终止速率

所以 3 副本默认滚动更新时：

最多 4 个 Pod（3+1）

最少 2 个 Pod（3-1）

即"先启 1 个新 Pod，再停 1 个旧 Pod"的节奏

参数可以是百分比（如 25%）或整数（如 1）：

maxSurge

1 # 最多超出 1 个

maxUnavailable

1 # 最多不足 1 个

maxSurge 与 maxUnavailable 的特殊组合：

参数组合 行为 适用场景
maxSurge=25%, maxUnavailable=25%（默认） 先启新再停旧，平滑 生产环境默认
maxSurge=0, maxUnavailable=1 先停旧再启新（不超出期望） 资源紧张，不能多出 Pod
maxSurge=1, maxUnavailable=0 先启新再停旧（不少于期望） 要求全程满副本，最安全
maxSurge=0, maxUnavailable=0 无法滚动更新（卡死） 错误配置，禁止使用

回滚原理：

图示 10：Deployment 保留历史 ReplicaSet（revisionHistoryLimit=10，默认保留 10 个）

每次滚动更新创建一个新 RS，版本号 +1：

revision 1

RS-1 (v1) ← 初始版本

revision 2

RS-2 (v2) ← 第一次更新

revision 3

RS-3 (v3) ← 第二次更新

...

回滚操作：

kubectl rollout undo deployment/xxx

→ 把当前 RS 副本数降到 0，把上一个 RS 副本数升到期望值

→ 相当于"反向滚动更新"

kubectl rollout undo deployment/xxx --to-revision=1

→ 回滚到指定版本（revision 1）

问题 / 场景

问：kubectl set image 后，旧 Pod 是立即被杀掉的吗？

  • 不是。滚动更新是渐进式的：先启动新 Pod，等新 Pod 就绪后，再终止旧 Pod。速率由 maxSurge 和 maxUnavailable 控制。默认 25%/25% 时，3 副本每次替换 1 个 Pod。

问：maxSurge 和 maxUnavailable 都设成 0 会怎样？

  • 会卡死，无法滚动更新。因为 maxSurge=0 表示不能多出 Pod（不能先启新），maxUnavailable=0 表示不能少于 Pod（不能先停旧），二者矛盾，K8s 无法执行任何操作。这是错误配置，禁止使用。

问：滚动更新期间服务会中断吗？

  • 默认不会（配合 Service 使用时）。因为滚动更新期间始终有旧 Pod 在服务（maxUnavailable 控制），新 Pod 就绪后才停旧 Pod。但要注意：如果应用启动很慢（如 SpringBoot 启动 30 秒），且 maxUnavailable 设太大，可能影响可用性。生产环境建议 maxUnavailable=0 或较小值。

问：回滚后，原来失败的版本（v2）还在历史里吗？

  • 在。回滚操作本身也是一次"滚动更新"，会创建新 revision（如 revision 4，镜像 v1）。原来的 revision 3（v2）仍在历史里，可以再次回滚到 v2。revisionHistoryLimit=10 表示最多保留 10 个 revision。

问：kubectl rollout undo 能回滚到任意版本吗？

  • 能。用 --to-revision=N 指定版本号。先用 kubectl rollout history 查看有哪些版本，再 kubectl rollout undo --to-revision=N 回滚到指定版本。

易错点

小结

滚动更新是 Deployment 的默认更新策略，逐步用新 Pod 替换旧 Pod，保证服务不中断。kubectl set image 触发更新，rollout status 查看状态，rollout history 查看历史，rollout undo 回滚。RollingUpdate 策略参数：maxSurge（最多超出期望副本数）控制新 Pod 启动速率，maxUnavailable（最多低于期望副本数）控制旧 Pod 终止速率。旧 ReplicaSet 保留用于回滚，revisionHistoryLimit 控制保留版本数。

标签（Labels）详解：

标签是键值对，附加到 K8s 资源上（如 Pod、Deployment、Service 等）

语法规则：
  - 键：前缀/名称，前缀可选（如 app、tier、version、app.kubernetes.io/name）
  - 值：字符串
  - 键和值都只能用字母、数字、-、_、.
  - 键前缀（如果有）是 DNS 子域名（如 kubernetes.io/、app.kubernetes.io/）

常见标签：

  tier: backend               # 层级（frontend/backend/database）

  - 标签：用于"选择"和"筛选"（selector 能用）
  - 注解：用于"附加元数据"（不能被 selector 选择）
  - 例：labels.app 用于 Service 选择 Pod
  - 例：annotations.kubernetes.io/... 用于记录构建信息、最后更新时间等

问题 / 场景

问：kubectl scale 和修改 YAML 哪种更好？

  • 生产环境推荐修改 YAML。原因：① 可版本化（YAML 提交 Git）；② 可复现（同样 YAML 在任何集群都能创建同样状态）；③ 团队协作友好（其他人能看到 YAML 里的 replicas）。kubectl scale 适合临时快速调整，但要记得同步更新 YAML 文件，否则下次 apply 又会改回去。

问：扩容和缩容哪个更快？

  • 扩容通常较慢（要启动新 Pod，等应用就绪），缩容较快（直接终止 Pod）。扩容时间主要取决于应用启动时间（如 SpringBoot 启动 30 秒）。缩容时间取决于优雅退出时间（默认 30 秒宽限期）。

问：缩容时 K8s 怎么决定终止哪些 Pod？

  • K8s 优先终止较新创建的 Pod（保持老 Pod 稳定性）。也可以通过 Pod 干扰预算（PodDisruptionBudget）控制终止策略。生产环境如果有状态依赖（如 Session），需要配合 Service 的 sessionAffinity 或应用层一致性。

问：matchLabels 和 matchExpressions 能混用吗？

  • 能。selector 下可以同时有 matchLabels 和 matchExpressions，二者是"AND"关系（都要满足）。但通常 matchLabels 足够，matchExpressions 用于复杂场景。

问：标签和命名空间有什么区别？

  • 命名空间是资源的"大分组"（如 dev/test/prod 环境隔离），标签是资源内部的"小标记"（如 app=backend、tier=db）。命名空间隔离是强制的（不同 ns 资源互不可见），标签筛选是可选的（用于选择和过滤）。

易错点

  1. ❌ 用 kubectl scale 扩容后忘记更新 YAML 文件。✅ 下次 apply 又会改回 YAML 里的 replicas 值，要保持 YAML 与实际一致。
  2. ❌ 误认为"缩容会随机终止 Pod"。✅ K8s 优先终止较新创建的 Pod，保持老 Pod 稳定性。
  3. ❌ 误认为"标签和命名空间是一回事"。✅ 命名空间是大分组（环境隔离），标签是小标记（资源筛选）。
  4. ❌ 误认为"kubectl label 修改标签不用 --overwrite"。✅ 修改已有标签必须加 --overwrite，否则报错。
  5. ❌ 删除标签语法写错。✅ 删除标签是 kubectl label pod xxx key-（键后加 -），不是 key=。
  6. ❌ selector.matchLabels 与 template.labels 不匹配导致 Deployment 找不到 Pod。✅ 必须匹配，详见 K16-3。

小结

扩缩容用 kubectl scale 或修改 YAML 的 replicas 字段，生产推荐修改 YAML（可版本化）。扩容是纯增加 Pod，缩容优先终止较新 Pod。标签是键值对，用于标识和筛选资源；选择器用于根据标签选择资源，有 matchLabels（精确匹配）和 matchExpressions（表达式匹配）两种写法。kubectl label 打标签，kubectl get -l 筛选资源。Deployment 的 selector 必须与 template.labels 匹配。

问题 / 场景

问：为什么要部署 3 副本而不是 1 副本？

  • 3 副本是高可用的最低要求。1 副本挂了服务就中断，3 副本挂 1 个还有 2 个可用。生产环境通常 3 副本起步，关键服务可能 5~10 副本。3 副本同时挂掉的概率远低于 1 副本挂掉的概率。

问：Deployment 部署后怎么从外部访问？

  • Deployment 本身不对外暴露，需要 Service（第 18 次课）。本节课用 kubectl port-forward 临时调试：kubectl port-forward deployment/ctts-backend 8080:8080 -n ctts，然后访问 http://localhost:8080。

问：3 个 Pod 都监听 8080 端口，会冲突吗？

  • 不会。每个 Pod 有独立的 IP，端口空间互相隔离。Pod1 的 8080 和 Pod2 的 8080 是不同的（不同 IP）。Service 会负载均衡到 3 个 Pod 的 8080。

问：如果节点资源不足，3 副本能全部调度吗？

  • 不一定。如果 Minikube 资源不足（如 2 核 2G），可能只能调度 2 个 Pod，第 3 个会 Pending。这时要减少 requests 或增加节点资源。本课程 Minikube 推荐 4 核 6G，足够 3 副本。

易错点

  1. ❌ imagePullPolicy 设成 Always 导致 ImagePullBackOff。✅ 本地构建的镜像用 Never 或 IfNotPresent。
  2. ❌ 第 15 次课的裸 Pod 和 Deployment 同名导致冲突。✅ 部署 Deployment 前先删除同名裸 Pod。
  3. ❌ resources.requests 设太大导致 3 副本调度失败。✅ requests 总和不要超过节点可用资源（Minikube 4 核 6G，3 副本每个 requests.cpu 不要超过 1 核）。
  4. ❌ 扩容后忘记同步 YAML 文件。✅ kubectl scale 后记得更新 YAML 里的 replicas，保持一致。
  5. ❌ 滚动更新时 v2 镜像没准备好就 set image。✅ 先 build 好 v2 镜像，再 set image，否则新 Pod 会 ImagePullBackOff。
  6. ❌ 删除 Pod 想要"停止服务"。✅ Deployment 管理的 Pod 删了立即重建，要停止服务需删除 Deployment。

四、拓展阅读（选学）

  1. HPA（HorizontalPodAutoscaler）自动扩缩容：

    • 根据 CPU/内存使用率或自定义指标自动调整副本数
    • 需要 metrics-server 提供 metrics
    • 例：CPU 超过 70% 自动扩容，低于 30% 自动缩容
    • 生产环境常用，弥补手动 kubectl scale 的不足

  2. Deployment 的 Pause/Resume：

    • kubectl rollout pause deployment/xxx：暂停滚动更新
    • kubectl rollout resume deployment/xxx：恢复滚动更新
    • 用于多次修改 YAML 后一次性触发更新，避免中间状态

  3. Progressive Delivery（渐进式交付）：

    • 金丝雀发布（Canary）：先小流量验证新版本，再逐步放大
    • 蓝绿部署（Blue-Green）：两套环境切换
    • A/B 测试：按用户特征分流
    • 工具：Argo Rollouts、Flagger 等（K8s 生态扩展）

  4. StatefulSet vs Deployment：

    • Deployment：无状态应用（如 Web 服务），Pod 可互换
    • StatefulSet：有状态应用（如数据库），Pod 有稳定网络标识和持久存储
    • CTTS 的 MySQL 应该用 StatefulSet（第 22 次课涉及存储时讲）

  5. PodDisruptionBudget（PDB）：

    • 保证自愿驱逐期间最少可用副本数
    • 例：minAvailable: 2 表示至少 2 个 Pod 可用
    • 防止维护操作（如 kubectl drain）导致服务不可用

  6. Deployment 排查工具：

    • kubectl rollout status：查看滚动更新状态
    • kubectl describe deployment：看 Events 和 Conditions
    • kubectl get events --sort-by=.metadata.creationTimestamp：看集群事件
    • kubectl get replicasets：看历史版本
