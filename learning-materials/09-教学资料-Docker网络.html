二、知识点详解

知识点 K9-1：Docker 网络模型概述

定义

Docker 网络子系统 是 Docker 引擎中负责容器网络管理的模块（早期称 libnetwork），它为每个容器提供独立的网络命名空间（network namespace），并通过不同的网络驱动（network driver） 决定容器如何与外部世界通信。

容器网络要解决的三大问题：

问题 说明 对应机制
隔离 每个容器要有自己独立的网络栈（网卡、IP、路由表、端口空间），不能互相干扰 network namespace
互通 同一台宿主机上的多个容器之间要能相互通信（前端调后端、后端连数据库） 网桥 / 自定义网络 + DNS
外部访问 容器内的服务要能被宿主机甚至宿主机外的用户访问 端口映射 -p / host 网络

原理

Docker 通过 Linux 内核的 network namespace 实现网络隔离：每个容器有自己独立的网卡、IP、路由表、iptables 规则，互不干扰。但光隔离还不够，还需要让容器之间能通信、让外部能访问容器——这就需要网络驱动来决定具体的连接方式。

Docker 内置的 5 种网络驱动（本课重点学前 3 种，macvlan/ipvlan 选学）：

驱动 说明 是否默认
bridge 默认驱动，容器通过虚拟网桥（docker0）通信 ✅ 默认
host 容器直接共享宿主机网络栈，无独立网络命名空间 否
none 容器只有 lo 回环接口，完全无网络 否
macvlan 给容器分配物理网络中的真实 MAC 地址，像独立主机一样接入物理网络 否（选学）
ipvlan 类似 macvlan 但不分配独立 MAC，支持 L2/L3 两种模式 否（选学） 
Docker 网络子系统三大职责：

┌─────────────────────────────────────────────┐
│              容器网络子系统                   │
├─────────────────────────────────────────────┤
│  1. 隔离：每容器独立 network namespace        │
│     （独立 IP、端口、路由表）                  │
├─────────────────────────────────────────────┤
│  2. 互通：通过网桥/自定义网络让容器相互通信    │
│     （同网络 + 容器名 DNS 解析）              │
├─────────────────────────────────────────────┤
│  3. 外部访问：通过 -p 端口映射或 host 网络让   │
│     宿主机/外部用户访问容器服务                │
└─────────────────────────────────────────────┘

问题 / 场景

问：容器之间默认能相互通信吗？

  • 同一个 bridge 网络（如默认 bridge 或同一个自定义 bridge）内的容器默认能相互通信（通过 IP）；但跨网络的容器默认隔离。这正是"按需互通"的体现。

问：为什么不用宿主机网络直接跑容器，而要搞这么多网络驱动？

  • 直接用宿主机网络（即 host 模式）虽然性能好，但失去隔离——容器端口会占用宿主机端口，多容器端口冲突、安全风险高。bridge 模式用虚拟网桥隔离，是隔离与互通的平衡点。

问：Docker 网络和 K8s 网络是什么关系？

  • Docker 网络解决单机多容器通信；K8s 网络解决跨节点多 Pod 通信（CNI 插件如 Calico、Flannel）。Docker 网络是基础，K8s 网络是上层扩展（第 20 次课详讲）。

易错点

  1. ❌ 误认为"容器之间默认不能通信"。✅ 同一个 bridge 网络内的容器默认能通过 IP 互通，跨网络才隔离。
  2. ❌ 误认为"Docker 网络只有 bridge/host/none 三种"。✅ 还有 macvlan、ipvlan、overlay（Swarm 集群用）等驱动，本课重点学前 3 种。
  3. ❌ 误认为"容器网络和宿主机网络是一回事"。✅ 每个容器有独立的 network namespace，是隔离的网络栈。

小结

Docker 网络子系统负责容器的隔离、互通和外部访问三大职责。Docker 默认提供 bridge、host、none 三种内置网络驱动，每种驱动解决不同场景的网络需求。理解网络驱动选型是后续容器编排（Compose/K8s）的基础。

知识点 K9-2：bridge 网络

定义

bridge 网络 是 Docker 的默认网络驱动。它在宿主机上创建一个虚拟网桥（默认名为 docker0），所有加入该网络的容器通过虚拟网卡（veth pair）连接到这个网桥，实现二层网络互通。

默认 bridge 是 Docker 安装后自动创建的、名为 bridge 的 bridge 网络（对应网桥设备 docker0）；自定义 bridge 是用户用 docker network create 创建的 bridge 网络（K9-4 详讲）。

原理

bridge 网络的核心原理涉及 Linux 的几个网络技术：

  1. 虚拟网桥 docker0：宿主机上的一个虚拟二层交换机，IP 默认 172.17.0.1/16。
  2. veth pair（虚拟以太网卡对）：每启动一个容器，Docker 在宿主机一端创建一个 veth 网卡插到 docker0，在容器一端创建对应的 eth0，两端通过内核连通。
  3. iptables NAT（地址伪装）：容器出向流量经过 iptables MASQUERADE 规则，源地址从容器 IP 改成宿主机 IP，让容器能访问外网。
  4. 端口映射 -p：外部访问宿主机端口时，iptables DNAT 规则把流量转发到容器端口，实现外部访问容器。
图示 1：bridge 网络原理（默认 bridge）：

  •     外部网络 ◀ iptables NAT

  •     外部访问容器：宿主机端口 → DNAT → 容器端口

默认 bridge 的关键特点：

特点 说明
自动加入 不指定 --network 时，容器默认加入默认 bridge
IP 互通 同 bridge 内容器可通过容器 IP 相互访问
无 DNS 解析 默认 bridge 没有 内置 DNS，容器之间不能用容器名互访（只能用 IP）
端口需映射 容器端口默认不对宿主机暴露，需要 -p 显式映射
隔离较弱 所有容器都在同一个 bridge，无法按业务分组隔离

问题 / 场景

问：为什么默认 bridge 不能用容器名互访？

  • 默认 bridge 是 Docker 早期保留的兼容性网络，没有 内置 DNS 服务。容器只能通过 IP 互访，但容器 IP 是动态分配的（重启可能变），用 IP 不可靠。这就是默认 bridge 的最大局限，自定义 bridge（K9-4）解决了这个问题。

问：怎么查看容器的 IP？

  • docker inspect <容器名> 中的 NetworkSettings.IPAddress 字段，或 docker network inspect bridge 看 Containers 字段。也可以进入容器内 ip addr 或 ifconfig 查看。

问：bridge 网络的容器能访问外网吗？

  • 能。容器出向流量经过 iptables MASQUERADE 规则做源地址转换（容器 IP → 宿主机 IP），所以容器能 ping 通外网、能 apt install、能 curl 公网服务。

完整示例

演示默认 bridge 下容器间只能 IP 互访：

# 1. 不指定 --network，容器默认加入默认 bridge
docker run -d --name c1 alpine sleep 3600
# 输出容器ID：a1b2c3d4e5f6...

docker run -d --name c2 alpine sleep 3600
# 输出容器ID：b2c3d4e5f6a1...

# 2. 查看默认 bridge 的容器与 IP
docker network inspect bridge --format '{{range .Containers}}{{.Name}}: {{.IPv4Address}}{{"\n"}}{{end}}'
# 输出示例：
# c1: 172.17.0.2/16
# c2: 172.17.0.3/16

# 3. 进入 c1，尝试用容器名 ping c2（失败）
docker exec -it c1 ping -c 2 c2
# 输出示例：
# ping: bad address 'c2'

# 4. 进入 c1，用 IP ping c2（成功）
docker exec -it c1 ping -c 2 172.17.0.3
# 输出示例：
# PING 172.17.0.3 (172.17.0.3): 56 data bytes
# 64 bytes from 172.17.0.3: seq=0 ttl=64 time=0.150 ms
# 64 bytes from 172.17.0.3: seq=1 ttl=64 time=0.180 ms
# --- 172.17.0.3 ping statistics ---
# 2 packets transmitted, 2 packets received, 0% packet loss

# 5. 清理
docker rm -f c1 c2

📌 上面步骤 3 失败、步骤 4 成功就是默认 bridge 的核心局限：只能 IP 互访，不能容器名互访。这正是 K9-4 自定义网络要解决的问题。

易错点

  1. ❌ 误认为"默认 bridge 也能用容器名互访"。✅ 默认 bridge 没有内置 DNS，只能用 IP。这是默认 bridge 与自定义 bridge 最大的区别。
  2. ❌ 误认为"bridge 网络的容器对外端口默认开放"。✅ 容器端口默认只在 bridge 内可达，外部访问必须 -p 映射到宿主机。
  3. ❌ 误认为"docker0 就是 Docker 网络"。✅ docker0 只是默认 bridge 对应的网桥设备，Docker 还有 host/none/自定义 bridge 等其他网络。
  4. ❌ 误认为"容器 IP 永远不变"。✅ 容器重启后 IP 可能变化，所以默认 bridge 用 IP 互访不可靠——这正是要自定义网络 + DNS 的原因。

小结

bridge 是 Docker 默认网络驱动，通过虚拟网桥 docker0 让同网络容器通过 IP 互通。默认 bridge 的最大局限是没有容器名 DNS 解析，只能用动态 IP 互访，不可靠。这个局限由自定义 bridge 网络（K9-4）解决。

知识点 K9-3：host 与 none 网络

定义

  • host 网络：容器直接共享宿主机的网络命名空间，没有独立的网卡、IP、端口空间——容器看到的网络就是宿主机看到的网络。容器内的端口就是宿主机上的端口。
  • none 网络：容器拥有独立的网络命名空间，但没有任何网络接口（除了 lo 本地回环），完全与外界网络隔离。

原理

host 网络原理：

图示 3：host 网络模式：

宿主机网络栈（eth0: 192.168.1.10）

容器不再拥有独立网络命名空间，而是直接共享宿主机网络栈；访问路径最短，但端口与隔离都交给宿主机承担。

容器 A

host 网络，直接使用宿主机 IP 与端口空间。

容器 B

host 网络，同样共享宿主机网络栈。

端口 80

谁先占用就是谁的。

端口 3306

重复绑定会直接冲突报错。

适用取舍

性能最好，无 NAT；代价是网络隔离弱，端口规划必须更严格。

none 网络原理：

图示 4：none 网络模式：

none 网络模式：

宿主机

容器 C

(none 网络)

只有 lo ← 仅本地回环 127.0.0.1

127.0.0.1 ← 无 eth0、无法 ping 通

宿主机或任何外部地址

特点

完全隔离，适合安全沙箱、离线计算、测试场景

三种网络驱动对比表：

对比项 bridge（默认/自定义） host none
网络隔离 独立网络命名空间 共享宿主机网络栈 独立网络命名空间
容器 IP 容器自己的 IP（172.x） 宿主机 IP 仅 lo（127.0.0.1）
端口冲突 不会（容器端口独立） 会（容器端口即宿主机端口） 不会（无网络）
外部访问 需要 -p 端口映射 直接访问（容器端口即宿主机端口） 无法访问
容器间通信 同 bridge 内可通过 IP/容器名 通过宿主机端口（localhost） 无法通信
性能 有 NAT 开销（略低） 无 NAT，性能最好 N/A
DNS 解析 自定义 bridge 有，默认 bridge 无 无（用 localhost） 无
典型场景 普通应用容器（Web、API、DB） 网络性能敏感、调试抓包 安全沙箱、离线计算

问题 / 场景

问：什么时候用 host 网络？

  • 仅在以下场景使用：①对网络性能极致敏感（如高频交易、海量小包）；②需要用 tcpdump 抓宿主机所有流量；③调试网络问题需要看宿主机视角。生产环境几乎不用 host，因为失去隔离、端口冲突风险高。

问：什么时候用 none 网络？

  • ①安全沙箱：分析不可信文件、运行可疑代码，完全断网防止外传；②离线计算：批处理、加密货币挖矿（不需要网络）；③测试：测试容器在无网络环境下的行为。

问：host 模式下 -p 端口映射还有意义吗？

  • 没意义。host 模式下容器端口已经是宿主机端口，-p 会被忽略并警告。例如 docker run --network host -p 80:80 nginx 会提示 WARNING: Published ports are discarded when using host network mode。

问：none 模式下容器还能干什么？

  • 容器内可以运行不依赖网络的任何任务：计算、文件处理、本地数据库读写（lo）、本地 socket 通信。只是无法访问网络，也无法被网络访问。

  1. ❌ 误认为"host 网络也有容器名 DNS"。✅ host 网络没有独立的网络命名空间，也没有 Docker DNS，容器之间只能用 localhost + 端口互访。

知识点 K9-4：自定义网络

定义

自定义网络 是用户通过 docker network create 命令创建的网络。最常用的是自定义 bridge 网络，它相对默认 bridge 有两大优势：容器名 DNS 解析 和 更好的网络隔离。

原理

自定义 bridge 网络相对默认 bridge 的两大优势：

优势 1：容器名 DNS 解析

Docker 在自定义 bridge 网络中内置了一个 DNS 服务（127.0.0.11），自动为该网络内的每个容器注册一条 <容器名> → 容器 IP 的 DNS 记录。容器之间可以直接用容器名互访，无需关心 IP 变化。

图示 6：自定义 bridge 内置 DNS 工作原理：
  • 自定义 bridge 内置 DNS 工作原理：
  •     自定义 bridge：ctts-net (172.20.0.0/16)
  •           ctts-mysql ctts-backend ctts-frontend
  •           172.20.0.2 172.20.0.3 172.20.0.4
  •         Docker 内嵌
  •         DNS 127.0.0.11
  •       ctts-mysql → 172.20.0.2
  •       ctts-backend → 172.20.0.3
  •       ctts-frontend → 172.20.0.4
  • 容器内 ping ctts-mysql → DNS 解析 → 172.20.0.2 → 通信成功

优势 2：更好的网络隔离

默认 bridge 下所有容器都在同一个网络，无法按业务分组隔离。自定义 bridge 可以按业务创建多个网络（如 ctts-net、monitor-net），不同网络的容器默认隔离，按需通过 docker network connect 互通。

问题 / 场景

问：为什么默认 bridge 没有 DNS，自定义 bridge 有？

  • 历史原因。默认 bridge 是 Docker 早期设计，为了向后兼容保留了"无 DNS"的行为；自定义 bridge 是后来新设计，引入了内嵌 DNS。Docker 官方明确推荐生产环境用自定义 bridge。

问：一个容器能不能加入多个自定义网络？

  • 能。一个容器默认接入一个网络，但可以通过 docker network connect <网络名> <容器名> 把容器追加接入到第二个、第三个网络。容器会有多个网卡（每个网络一张）。这就是跨网络通信的方式（K9-5 详讲）。

问：自定义网络能自定义子网和网关吗？

  • 能。docker network create --subnet 172.20.0.0/16 --gateway 172.20.0.1 mynet。不指定时 Docker 自动分配。

问：自定义网络的容器名冲突怎么办？

  • 容器名是全局唯一的，不能重复。但同一容器在不同网络中可以用不同别名（--network-alias），这是高级用法。

知识点 K9-5：容器间通信

定义

容器间通信 指同一台宿主机上多个容器之间的网络互访。Docker 提供两种主要的容器间通信方式：

  1. 同网络按容器名通信：同一自定义 bridge 网络内的容器，通过 Docker 内嵌 DNS 用容器名互访。
  2. 跨网络通信：通过 docker network connect 把容器追加接入到目标网络，实现跨网络互访。

原理

方式 1：同自定义网络按容器名通信

最常用的容器间通信方式。容器启动时用 --network <网络名> 加入同一自定义 bridge，即可用容器名互访。

图示 9：同自定义网络按容器名通信：
  • 同自定义网络按容器名通信：
  •     自定义 bridge：ctts-net
  •           ctts-frontend ctts-backend
  •           172.20.0.4 172.20.0.3
  •       curl http://ctts-backend:8080
  •       ▶
  •       DNS 127.0.0.11
  •       ctts-backend → 172.20.0.3
  • 关键：同一自定义 bridge + 容器名 → DNS 自动解析 → 通信

方式 2：跨网络通信（docker network connect）

当一个容器需要访问另一个网络的容器时，可以用 docker network connect <目标网络> <容器名> 把容器追加接入到目标网络。容器会获得目标网络中的一个 IP，并能按容器名访问该网络内的容器。

跨网络通信示例：

初始状态：
  ctts-net:        [ctts-frontend, ctts-backend]
  monitor-net:     [prometheus]

prometheus 想监控 ctts-backend：
  docker network connect ctts-net prometheus

连接后状态：
  ctts-net:        [ctts-frontend, ctts-backend, prometheus]  ← prometheus 接入
  monitor-net:     [prometheus]                                ← 仍在原网络

prometheus 现在可以：
  ping ctts-backend   ✓ (在 ctts-net 中按容器名)
  ping ctts-frontend  ✓ (在 ctts-net 中按容器名)

容器间通信的 3 种典型场景：

场景 通信方式 命令示例
同一自定义网络内 按容器名直接访问 curl http://ctts-backend:8080
跨网络 docker network connect 接入目标网络 docker network connect ctts-net prometheus
默认 bridge 内 只能按 IP 访问（不推荐） curl http://172.17.0.3:8080

问题 / 场景

问：--network 和 docker network connect 有什么区别？

  • --network 是 docker run 时的参数，指定容器初始加入的网络（一个容器只能有一个初始网络）；docker network connect 是容器启动后追加接入第二个、第三个网络的命令。一个容器可以有一个初始网络 + 多个追加网络。

问：容器启动时忘了指定 --network，怎么把它加入自定义网络？

  • 用 docker network connect <网络名> <容器名>。但容器此时已经在默认 bridge 中，再接入自定义网络后会有两个网卡，两个 IP。

问：跨网络访问容器名为什么不通？

  • Docker DNS 是按网络隔离的——每个自定义 bridge 网络有自己的 DNS 视图。容器 A 在 net1 中，无法解析 net2 中的容器名，必须把 A 接入 net2 才能按名访问 net2 中的容器。

问：容器名互访用的是哪个端口？

  • 容器内服务监听的端口。例如后端容器内 SpringBoot 监听 8080，前端就访问 http://ctts-backend:8080。同网络容器间通信不需要 -p 端口映射，-p 只是给宿主机外部用的。

完整示例

完整演示容器间通信的两种方式：

# === 方式 1：同自定义网络按容器名通信 ===

# 1. 创建自定义网络
docker network create ctts-net
# 3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a

# 2. 启动后端容器（用 nginx 模拟 API 服务）
docker run -d --name ctts-backend --network ctts-net nginx:alpine
# 输出容器ID：a1b2c3d4e5f6...

# 3. 启动前端容器（用 busybox 模拟前端，测试访问后端）
docker run -d --name ctts-frontend --network ctts-net busybox sleep 3600
# 输出容器ID：b2c3d4e5f6a1...

# 4. 前端容器用容器名访问后端（成功！）
docker exec -it ctts-frontend wget -qO- -S http://ctts-backend:80 2>&1 | head -5
# 输出示例：
#   HTTP/1.1 200 OK
#   Server: nginx/1.25.3
#   Date: Wed, 22 Jul 2026 10:00:00 GMT
#   Content-Type: text/html
#   ...

# 5. 查看后端容器 IP，验证 DNS 解析
docker exec -it ctts-frontend nslookup ctts-backend 2>/dev/null || \
docker exec -it ctts-frontend ping -c 1 ctts-backend
# 输出示例：
# PING ctts-backend (172.20.0.2): 56 data bytes
# 64 bytes from 172.20.0.2: seq=0 ttl=64 time=0.100 ms

# === 方式 2：跨网络通信（docker network connect）===

# 6. 创建第二个网络（监控网络）
docker network create monitor-net
# 4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b

# 7. 启动监控容器（在 monitor-net 中）
docker run -d --name prometheus --network monitor-net busybox sleep 3600
# 输出容器ID：c3d4e5f6a1b2...

# 8. 监控容器尝试访问 ctts-backend（失败，跨网络隔离）
docker exec -it prometheus ping -c 1 ctts-backend
# 输出示例：
# ping: bad address 'ctts-backend'

# 9. 把监控容器追加接入 ctts-net
docker network connect ctts-net prometheus

# 10. 监控容器再次访问 ctts-backend（成功！）
docker exec -it prometheus ping -c 1 ctts-backend
# 输出示例：
# PING ctts-backend (172.20.0.2): 56 data bytes
# 64 bytes from 172.20.0.2: seq=0 ttl=64 time=0.150 ms

# 11. 查看监控容器现在有几个网络接口
docker network inspect ctts-net --format '{{range .Containers}}{{.Name}} {{end}}'
# 输出示例：ctts-backend ctts-frontend prometheus
docker network inspect monitor-net --format '{{range .Containers}}{{.Name}} {{end}}'
# 输出示例：prometheus

# 12. 断开监控容器与 ctts-net 的连接
docker network disconnect ctts-net prometheus

# 13. 监控容器又无法访问 ctts-backend 了
docker exec -it prometheus ping -c 1 ctts-backend
# 输出示例：
# ping: bad address 'ctts-backend'

# 14. 清理
docker rm -f ctts-backend ctts-frontend prometheus
docker network rm ctts-net monitor-net

  2. ❌ 误认为"跨网络也能按容器名访问"。✅ 跨网络默认隔离，DNS 也隔离。必须 docker network connect 把容器接入目标网络才能按名访问。
  3. ❌ 误认为"docker network connect 会断开容器与原网络的连接"。✅ connect 是追加接入，不影响原网络连接。容器会同时存在于两个网络中。
  4. ❌ 误认为"容器名互访用的是宿主机端口"。✅ 用的是容器内服务监听的端口。如后端容器内 SpringBoot 监听 8080，前端访问 http://ctts-backend:8080，与宿主机端口无关。

小结

容器间通信有两种方式：①同一自定义 bridge 网络内通过容器名互访（推荐，Docker 内嵌 DNS 自动解析）；②跨网络通过 docker network connect 把容器追加接入目标网络。同网络通信不需要 -p 端口映射，-p 只用于宿主机外部访问。

知识点 K9-6：端口映射回顾与 CTTS 网络设计

定义

端口映射（-p / --publish）是 Docker 把宿主机端口流量转发到容器端口的机制，让宿主机外部能够访问容器内的服务。本节回顾端口映射原理，并将其与自定义网络结合，为 CTTS 三服务设计完整的网络通信方案。

CTTS 三服务网络方案：前端（Vue3+Nginx）+ 后端（SpringBoot）+ MySQL 三个容器接入同一自定义 bridge 网络 ctts-net，前端通过 -p 80:80 对外暴露，后端与 MySQL 仅在同网络内按容器名互访，不对宿主机暴露端口（最小暴露面原则）。

原理

端口映射原理回顾：

  • ▼ http://宿主机IP:80
  •     宿主机
  •     iptables DNAT 规则：
  •     宿主机:80 → 容器:80
  •         容器（bridge 网络）
  •         eth0: 172.20.0.4
  •         Nginx 监听 :80
  • 关键：外部访问宿主机:80 → DNAT 转发到容器:80

-p 的几种格式：

格式 含义 示例
-p 80:80 宿主机 80 → 容器 80（所有网卡） -p 80:80

-p 80 宿主机随机端口 → 容器 80 -p 80（不推荐生产）

设计原则：

三服务接入同一自定义 bridge：ctts-net（DNS 按容器名互访）

前端 -p 80:80 对外暴露（用户访问入口）

后端不 -p 暴露（仅前端通过 http://ctts-backend:8080 访问）

MySQL 不 -p 暴露（仅后端通过 mysql -h ctts-mysql 访问）

最小暴露面：只有前端 80 端口对宿主机外可见

为什么 MySQL 不对外暴露 3306？（网络安全思政点）

风险 说明
暴力破解 公网暴露的 MySQL 容易被扫描爆破 root 密码
漏洞利用 MySQL CVE 漏洞可能被远程利用
数据泄露 一旦数据库被攻破，全量用户数据泄露
横向移动 攻击者可能利用数据库权限读写文件，进一步渗透

正确做法：MySQL 仅在同网络内被后端按容器名访问，不对宿主机暴露端口。这是"默认隔离、按需放通"的网络安全原则。

问题 / 场景

问：后端需不需要 -p 8080:8080 对外暴露？

  • 看场景。①生产环境：不需要，前端通过容器名 http://ctts-backend:8080 访问即可，对外只暴露前端 80。②开发调试：可以临时 -p 8080:8080 方便开发者在浏览器直接调后端 API。建议生产关闭，调试时开启。

问：前端如何配置才能让浏览器访问到后端 API？

  • 浏览器加载前端页面后，前端发起的 API 请求是浏览器→宿主机的请求（不是前端容器→后端容器）。所以前端 Nginx 通常配置反向代理：/api/ 路径代理到 http://ctts-backend:8080，由 Nginx 容器转发到后端容器。这是容器化部署的常见模式。

问：如果后端和 MySQL 不在一个网络会怎样？

  • 后端连不上 MySQL（Name or service not known 或连接超时）。解决方案：①推荐——把后端和 MySQL 放同一个自定义 bridge；②备选——用 docker network connect 把后端接入 MySQL 所在网络。

问：端口映射 -p 80:80 和 host 网络 --network host 有什么区别？

  • -p 80:80 仍然在 bridge 网络，容器有独立网络命名空间，只是把宿主机 80 端口流量转发到容器 80；--network host 容器直接共享宿主机网络栈，容器内 Nginx 监听 80 就是宿主机 80，没有转发。生产推荐 -p，保留隔离。

易错点

  1. ❌ 误认为"三个容器要互通就必须用 -p 把端口都映射出来"。✅ 同网络容器间通过容器名 + 容器内端口直接访问，-p 只用于外部访问。把所有端口都 -p 暴露反而违反最小暴露面原则。
  2. ❌ 误认为"前端容器配置 API 地址用宿主机 IP"。✅ 前端容器内通过容器名访问后端（http://ctts-backend:8080）；浏览器加载页面后发起的请求才走宿主机 IP，这通常通过 Nginx 反向代理解决。
  3. ❌ 误认为"MySQL 容器必须 -p 3306:3306 才能让后端连"。✅ 后端容器和 MySQL 容器在同一自定义网络内，直接 mysql -h ctts-mysql 即可连，不需要 -p。
  4. ❌ 误认为"端口映射 -p 80:80 是把容器 80 映射到宿主机 80"。✅ 方向反了——-p 宿主机端口:容器端口，是把宿主机 80 流量转发到容器 80。

小结

CTTS 三服务网络方案的核心设计：①三个容器接入同一自定义 bridge 网络 ctts-net，通过容器名互访；②仅前端 -p 80:80 对外暴露；③MySQL 和后端不对宿主机暴露端口（最小暴露面原则）；④配置中用容器名（ctts-mysql、ctts-backend）而非 IP，避免 IP 变化导致连接失败。这套设计兼顾了通信便利性与网络安全。

四、拓展阅读（选学）

  1. macvlan 网络驱动：给容器分配物理网络中的真实 MAC 地址，让容器像独立物理主机一样接入局域网。适用于旧应用必须用真实 MAC 的场景。docker network create -d macvlan --subnet 192.168.1.0/24 --gateway 192.168.1.1 -o parent=eth0 mynet
  2. ipvlan 网络驱动：类似 macvlan 但不分配独立 MAC，支持 L2（ipvlan bridge）和 L3（ipvlan l3）两种模式。
  3. overlay 网络驱动：跨多台宿主机的容器通信（Docker Swarm 集群用）。K8s 跨节点 Pod 通信用 CNI 插件（Calico/Flannel）解决，原理类似但实现不同。
  4. Docker DNS 原理：Docker 在每个自定义 bridge 网络中启动一个内嵌 DNS 服务（127.0.0.11），自动注册容器名→IP 的记录。容器内的 /etc/resolv.conf 指向这个 DNS。
  5. 容器网络与 K8s 网络：Docker 网络是单机多容器通信；K8s 网络是跨节点多 Pod 通信（CNI 标准 + Calico/Flannel 等）。K8s 中每个 Pod 有独立 IP，Pod 间直接通信（无 NAT），这是 K8s 网络模型的核心（第 20 次课详讲）。
  6. NetworkPolicy（K8s）：K8s 中的网络隔离策略，类似云平台安全组，控制 Pod 间哪些流量允许、哪些拒绝。是 K8s 网络安全的核心机制。
