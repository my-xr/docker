一、学习导读

1. 为什么学这一课？

在前几节课中，你已经能将CTTS的Vue前端、SpringBoot后端、MySQL数据库部署到K8s，并能通过ConfigMap/Secret管理配置。但是——

问题来了：当你执行 kubectl delete pod mysql-xxx 后，重新拉起的MySQL容器里，昨天的用户数据全没了。

这就是Pod的临时性带来的数据丢失问题。容器内的文件系统是临时的，Pod一旦销毁，数据随之消失。对于数据库这类有状态应用，这是不可接受的。

2. 本课学什么？

本课学习K8s的持久化存储体系，掌握四层存储抽象：

抽象层 角色 类比
Volume Pod内最基础存储 U盘
PV (PersistentVolume) 集群级存储资源 机房机柜
PVC (PersistentVolumeClaim) 用户存储申请 租户申请工单
StorageClass 动态供给工厂 自动派工系统

3. 学完能做什么？

  • 为CTTS MySQL配置持久化存储，Pod销毁后数据依然存在。
  • 编写PV、PVC、StorageClass的YAML并部署。
  • 排查PV/PVC常见报错（Pending、Failed、无法绑定）。
  • 理解动态供给与静态供给的差异。

二、知识点详解

K22-1 存储需求与K8s存储体系总览

1.1 定义

持久化存储（Persistent Storage） 指在Pod生命周期之外仍能保留数据的存储机制。K8s通过一套分层抽象（Volume / PV / PVC / StorageClass）实现存储资源与Pod的解耦。

1.2 原理：为什么需要持久化？

Pod的容器文件系统基于容器的可写层（overlayfs），具有以下特性：

  • 临时性：Pod销毁，可写层数据丢失。
  • 不可迁移：同一Pod内多容器共享Volume，但Pod间不共享。
  • 节点绑定：Pod重新调度到其他节点，原节点数据无法跟随。

演示实验：体验数据丢失

# 文件名：demo-no-pv.yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo-no-pv
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sh", "-c", "echo 'hello' > /data/hello.txt && sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    emptyDir: {}   # 临时存储，Pod销毁即丢失
# 操作步骤
kubectl apply -f demo-no-pv.yaml
kubectl exec demo-no-pv -- cat /data/hello.txt   # 输出 hello
kubectl delete pod demo-no-pv
kubectl apply -f demo-no-pv.yaml                # 重新创建
kubectl exec demo-no-pv -- cat /data/hello.txt  # 报错：文件不存在

1.3 问题：临时存储带来的痛点

痛点 影响 后果
Pod销毁数据丢失 数据库重启数据清空 用户数据丢失
Pod迁移节点数据不跟随 重调度后无法访问原数据 服务异常
存储资源与Pod耦合 存储无法独立管理 运维复杂
多Pod共享数据难 同步读写困难 协作受阻

1.4 K8s存储体系总览

图示 2：结构与流程重绘
┌─────────────────────────────────────────────────────────────┐ │ K8s 存储体系四层抽象 │ ├─────────────────────────────────────────────────────────────┤ │ │ │ Pod ──► Volume (Pod级，最底层) │ │ │ │ │ ├── emptyDir 临时目录 │ │ ├── hostPath 节点目录 │ │ ├── configMap/secret 配置注入 │ │ ├── persistentVolumeClaim ──► PVC (用户申请) │ │ │ │ │ │ │ ▼ │ │ │ PV (集群资源, 静态) │ │ │ ▲ │ │ │ │ │ │ └── StorageClass ──动态创建──► PV (动态) │ │ │ └─────────────────────────────────────────────────────────────┘

四层关系：

  • Volume：Pod内最基础存储抽象，生命周期与Pod相同。
  • PV：集群级存储资源，由管理员创建（静态）或StorageClass自动创建（动态）。
  • PVC：用户对存储的申请，消耗PV资源。
  • StorageClass：动态供给工厂，按需自动创建PV。

1.5 易错点

  • ❌ 误认为 emptyDir 能持久化数据。✅ emptyDir生命周期与Pod相同，Pod销毁即丢失。
  • ❌ 误认为hostPath能跨节点。✅ hostPath绑定到具体节点，Pod重调度后数据不跟随。
  • ❌ 误认为PV和PVC是同一概念。✅ PV是资源，PVC是申请，二者通过绑定关联。

1.6 小结

持久化存储是K8s有状态应用的基础。K8s通过Volume→PV→PVC→StorageClass四层抽象，实现存储资源与Pod的解耦，让数据能脱离Pod生命周期而存在。

K22-2 PersistentVolume(PV)

2.1 定义

PersistentVolume（PV） 是K8s集群中的一块存储资源，由管理员创建，属于集群级资源（不属于任何命名空间意义上的"用户资源"，但PV本身是集群范围资源，PVC是命名空间级）。

注：PV是集群范围（cluster-scoped）资源，PVC是命名空间（namespaced）资源。

2.2 原理：PV的核心字段

字段 含义 示例值
capacity.storage 存储容量 5Gi
accessModes 访问模式 ReadWriteOnce / ReadOnlyMany / ReadWriteMany
persistentVolumeReclaimPolicy 回收策略 Retain / Delete / Recycle(已废弃)
storageClassName 关联的StorageClass nfs / standard
volumeMode 卷模式 Filesystem(默认) / Block
nodeAffinity 节点亲和性 限制PVC所在节点

访问模式说明：

  • ReadWriteOnce (RWO)：可被单节点读写（最常用）。
  • ReadOnlyMany (ROX)：可被多节点只读。
  • ReadWriteMany (RWX)：可被多节点读写（需NFS/CephFS等共享存储支持）。
  • ReadWriteOncePod：可被单Pod读写（K8s 1.22+）。

回收策略说明：

  • Retain：删除PVC后PV保留数据，状态变为Released，需管理员手动清理。
  • Delete：删除PVC后PV及底层存储自动删除（动态供给常用）。
  • Recycle：已废弃（K8s 1.11+），原行为是删除PV内数据后变为Available。

2.3 完整示例：PV YAML

示例1：hostPath类型PV（Minikube单节点适用）
# 文件名：pv-hostpath.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-hostpath-5gi
  labels:
    type: local
    app: ctts-mysql
spec:
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /data/ctts/mysql
    type: DirectoryOrCreate
示例2：NFS类型PV（生产环境多节点共享）
# 文件名：pv-nfs.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-10gi
  labels:
    type: nfs
    app: ctts-mysql
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteMany   # NFS支持多节点读写
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs
  nfs:
    server: 192.168.1.100
    path: /exports/ctts/mysql
    readOnly: false
示例3：CSI类型PV（云厂商存储）
# 文件名：pv-csi.yaml（以腾讯云CBS为例，了解即可）
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-cbs-50gi
spec:
  capacity:
    storage: 50Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Delete
  storageClassName: cbs
  csi:
    driver: com.tencent.cloud.csi.cbs
    volumeHandle: disk-xxxxxx
    fsType: ext4

2.4 PV生命周期

图示 3：结构与流程重绘
┌────────────┐ 创建PVC匹配 ┌──────────┐ 删除PVC ┌────────────┐ │ Available │ ─────────────► │ Bound │ ────────────► │ Released │ │ (可用) │ │ (已绑定) │ │ (已释放) │ └────────────┘ └──────────┘ └────────────┘ ▲ │ │ 手动回收（Retain策略） │ │ ▼ │ ┌──────────┐ └─────────────────────────────────────────────────────│ Failed │ │ (失败) │ └──────────┘

已由原 Markdown 字符图转换为网页图示，保留原有逻辑关系并优化阅读效果。

四态说明：

  • Available：PV已创建，尚未被PVC绑定，等待匹配。
  • Bound：PV已被PVC绑定，正在被使用。
  • Released：PVC被删除，PV保留数据，但不可立即被新PVC绑定（需清理claimRef）。
  • Failed：PV自动回收失败。

2.5 图示：PV字段结构

apiVersion: v1
kind: PersistentVolume
metadata:
  name: <PV名称>
  labels: <标签，用于selector匹配>
spec:
  capacity:
    storage: <容量>           ← 资源大小
  accessModes:                ← 访问模式列表
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain   ← 回收策略
  storageClassName: <SC名>   ← 关联StorageClass
  hostPath / nfs / csi:      ← 后端存储类型
    path: <路径>

2.6 易错点

  • ❌ hostPath的PV在多节点集群中不可用。✅ Pod可能调度到其他节点，应使用NFS或动态供给。
  • ❌ accessModes 写多个就一定支持。✅ 取决于后端存储类型，NFS才支持RWX。
  • ❌ Released状态的PV能直接被新PVC绑定。✅ 需清除 spec.claimRef 才能回到Available。
  • ❌ 容量单位 Gi 和 G 等价。✅ Gi 是2进制(1024Mi)，G 是10进制(1000M)，建议用 Gi。

2.7 小结

PV是集群级存储资源，通过capacity/accessModes/reclaimPolicy三个核心字段描述。生命周期四态：Available→Bound→Released→Failed。常用类型：hostPath（开发）、NFS（共享）、CSI（生产）。

K22-3 PersistentVolumeClaim(PVC)

3.1 定义

PersistentVolumeClaim（PVC） 是用户对存储资源的申请（声明），属于命名空间级资源。PVC描述"我要多大、什么访问模式的存储"，K8s自动匹配符合条件的PV并绑定。

3.2 原理：PVC与PV的绑定机制

绑定流程：

  1. 用户创建PVC，声明所需容量和访问模式。
  2. K8s控制循环寻找匹配的PV：
    • 容量匹配：PV容量 ≥ PVC申请容量。
    • 访问模式匹配：PV的accessModes包含PVC所需模式。
    • StorageClass匹配：PVC的storageClassName与PV一致。
    • selector匹配（可选）：PVC的labelSelector匹配PV的labels。
  3. 找到匹配PV后，PVC与PV绑定，状态变为Bound。
  4. 若无匹配PV，PVC保持Pending状态（动态供给时会自动创建PV）。

3.3 完整示例：PVC YAML

示例1：基础PVC
# 文件名：pvc-basic.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-mysql-5gi
  namespace: default
  labels:
    app: ctts-mysql
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 5Gi
示例2：带selector的PVC
# 文件名：pvc-selector.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-mysql-selector
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 5Gi
  selector:
    matchLabels:
      app: ctts-mysql
      type: local

3.6 易错点

  • ❌ PVC申请容量大于所有PV容量。✅ 会一直Pending，需先创建足够容量的PV。
  • ❌ PVC和PV的storageClassName不一致。✅ 必须一致才能绑定（除非都用空字符串）。
  • ❌ PVC和PV在不同命名空间能绑定。✅ PV是集群级，PVC是命名空间级，但绑定不受命名空间限制，PVC只能被同命名空间Pod使用。
  • ❌ selector匹配失败。✅ 检查PV的labels是否包含PVC selector所有键值对。

3.7 小结

PVC是用户的存储申请，通过accessModes/storageClassName/resources/selector匹配PV。无匹配PV时Pending，匹配成功后Bound。PVC是命名空间级资源，Pod只能使用同命名空间的PVC。

K22-4 StorageClass

4.1 定义

StorageClass 是K8s动态供给存储的模板，定义了"如何自动创建PV"。当用户创建PVC且指定StorageClass时，若没有匹配的静态PV，provisioner会按StorageClass模板自动创建PV并绑定。

4.2 原理：动态供给流程

图示 6：结构与流程重绘
用户创建PVC（指定StorageClass） │ ▼ K8s检查是否有匹配的静态PV │ ├── 有 ──► 直接绑定（静态供给） │ └── 无 ──► StorageClass的provisioner介入 │ ▼ provisioner调用后端存储API （如NFS、Ceph、云盘） │ ▼ 自动创建PV并绑定到PVC

已由原 Markdown 字符图转换为网页图示，保留原有逻辑关系并优化阅读效果。

4.3 StorageClass核心字段

字段 含义 示例
provisioner 存储供给器 k8s.io/minikube-hostpath、nfs-provisioner
reclaimPolicy 回收策略 Delete（默认）/ Retain
volumeBindingMode 绑定模式 Immediate（立即）/ WaitForFirstConsumer（等待首个消费者）
parameters 供给器参数 类型、性能等
allowVolumeExpansion 允许扩容 true / false

volumeBindingMode说明：

  • Immediate：PVC创建后立即绑定（可能选错节点）。
  • WaitForFirstConsumer：等到Pod调度后才绑定PV（适合拓扑约束场景，如云盘需与Pod同区域）。

4.4 完整示例：StorageClass YAML

示例1：Minikube默认StorageClass
# 文件名：sc-minikube.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # 设为默认
provisioner: k8s.io/minikube-hostpath
reclaimPolicy: Delete
volumeBindingMode: Immediate
allowVolumeExpansion: true
示例2：NFS StorageClass（需先部署nfs-subdir-external-provisioner）
# 文件名：sc-nfs.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-client
provisioner: nfs-storage   # 需提前部署nfs-subdir-external-provisioner
parameters:
  archiveOnDelete: "false"
reclaimPolicy: Delete
volumeBindingMode: Immediate
示例3：动态供给PVC（无需手动创建PV）
# 文件名：pvc-dynamic.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-dynamic-3gi
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard   # 指定StorageClass，自动创建PV
  resources:
    requests:
      storage: 3Gi

4.5 静态供给 vs 动态供给对比

维度 静态供给 动态供给
PV创建方式 管理员手动创建 StorageClass自动创建
适用场景 已有存储资源、hostPath、NFS固定路径 云盘、按需NFS、Ceph
灵活性 低，需预先规划 高，按需创建
运维成本 高 低
回收策略 多用Retain 多用Delete

4.7 易错点

  • ❌ Minikube未启用storage-provisioner插件。✅ minikube addons enable storage-provisioner。
  • ❌ NFS StorageClass未部署provisioner Pod。✅ 需先部署nfs-subdir-external-provisioner。
  • ❌ 默认StorageClass未设置。✅ 通过注解 storageclass.kubernetes.io/is-default-class: "true"。
  • ❌ WaitForFirstConsumer 模式下PVC一直Pending。✅ 需创建Pod后才会触发绑定。

4.8 小结

StorageClass实现动态供给，核心是provisioner字段。Minikube默认提供 k8s.io/minikube-hostpath provisioner。生产环境常用NFS/Ceph/CSI provisioner。volumeBindingMode: WaitForFirstConsumer 适合有拓扑约束的场景。

K22-5 在Pod中使用PVC

5.1 定义

在Pod中通过 volumes.persistentVolumeClaim 字段引用PVC，再通过 volumeMounts 挂载到容器内路径，实现数据持久化。

5.2 原理：Pod使用PVC的两步

5.3 完整示例：Pod挂载PVC

示例1：普通Pod使用PVC
# 文件名：pod-use-pvc.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-use-pvc
  namespace: default
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sh", "-c", "echo 'persistent data' > /data/test.txt && sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: pvc-mysql-5gi   # 引用前面创建的PVC
示例2：StatefulSet使用volumeClaimTemplates
# 文件名：sts-use-pvc.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
  namespace: default
spec:
  serviceName: web
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:           # StatefulSet专用：自动为每个Pod创建PVC
  - metadata:
      name: www
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 1Gi

volumeClaimTemplates说明：

  • StatefulSet为每个Pod副本自动创建独立PVC（如 www-web-0、www-web-1、www-web-2）。
  • Pod销毁后PVC保留，新Pod重新挂载同一PVC，实现数据持久化。
  • 适合有状态应用（如MySQL主从、ZooKeeper、Kafka）。

5.4 图示：Pod使用PVC的数据流

图示 9：结构与流程重绘
┌──────────────── Pod ─────────────────┐ │ ┌─────────── Container ──────────┐ │ │ │ /data ◄──── volumeMounts │ │ │ └────────────────┬───────────────┘ │ │ │ │ │ volumes: ▼ │ │ - pvc: pvc-mysql-5gi │ └───────────────────┬──────────────────┘ │ ▼ ┌───────────────┐ │ PVC │ │ (Bound) │ └───────┬───────┘ │ 绑定 ▼ ┌───────────────┐ │ PV │ │ hostPath/NFS │ └───────┬───────┘ │ ▼ ┌───────────────┐ │ /data/ctts/ │ ← 真实数据存储位置 │ mysql/ │ └───────────────┘

5.5 易错点

  • ❌ Pod的volumeMounts.name与volumes.name不一致。✅ 必须一致才能挂载成功。
  • ❌ PVC与Pod不在同一命名空间。✅ Pod只能引用同命名空间的PVC。
  • ❌ StatefulSet使用普通volumes而非volumeClaimTemplates。✅ StatefulSet必须用volumeClaimTemplates才能为每个Pod创建独立PVC。
  • ❌ Pod挂载路径与容器内已有目录冲突。✅ 挂载会覆盖原目录内容，建议挂载到空目录或子目录。

5.6 小结

Pod通过 volumes.persistentVolumeClaim.claimName 引用PVC，再通过 volumeMounts 挂载到容器。StatefulSet用 volumeClaimTemplates 自动为每个Pod创建独立PVC，适合有状态应用。

三、综合示例：CTTS MySQL数据持久化

3.1 场景描述

为CTTS项目的MySQL服务配置持久化存储，要求：

  • MySQL数据目录 /var/lib/mysql 持久化到宿主机。
  • Pod销毁重建后数据不丢失。
  • 使用hostPath（开发）或NFS（生产）两种方案。

3.2 方案一：hostPath静态供给（Minikube开发环境）

步骤1：创建PV

# 文件名：ctts-mysql-pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: ctts-mysql-pv
  labels:
    app: ctts
    component: mysql
spec:
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /data/ctts/mysql
    type: DirectoryOrCreate

步骤2：创建PVC

# 文件名：ctts-mysql-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ctts-mysql-pvc
  namespace: default
  labels:
    app: ctts
    component: mysql
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 5Gi
  selector:
    matchLabels:
      app: ctts
      component: mysql

步骤3：创建MySQL Deployment

# 文件名：ctts-mysql-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-mysql
  namespace: default
  labels:
    app: ctts
    component: mysql
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ctts
      component: mysql
  strategy:
    type: Recreate   # MySQL有状态，避免RollingUpdate导致双写
  template:
    metadata:
      labels:
        app: ctts
        component: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: ctts-mysql-secret
              key: root-password
        - name: MYSQL_DATABASE
          value: ctts
        - name: MYSQL_USER
          value: ctts
        - name: MYSQL_PASSWORD
          valueFrom:
            secretKeyRef:
              name: ctts-mysql-secret
              key: user-password
        ports:
        - containerPort: 3306
          name: mysql
        volumeMounts:
        - name: mysql-data
          mountPath: /var/lib/mysql   # MySQL数据目录
        - name: mysql-config
          mountPath: /etc/mysql/conf.d
        - name: mysql-init
          mountPath: /docker-entrypoint-initdb.d
        resources:
          requests:
            cpu: 200m
            memory: 512Mi
          limits:
            cpu: 1000m
            memory: 1Gi
      volumes:
      - name: mysql-data
        persistentVolumeClaim:
          claimName: ctts-mysql-pvc
      - name: mysql-config
        configMap:
          name: ctts-mysql-config
      - name: mysql-init
        configMap:
          name: ctts-mysql-init

步骤4：创建Secret和ConfigMap（前置依赖）

  name: ctts-mysql-init
  namespace: default

  init.sql: |

    USE ctts;
    CREATE TABLE IF NOT EXISTS users (
      id BIGINT PRIMARY KEY AUTO_INCREMENT,
      username VARCHAR(50) NOT NULL UNIQUE,

3.6 常见报错排查

报错1：PVC一直Pending

# 现象
kubectl get pvc
# NAME              STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
# ctts-mysql-pvc    Pending                                      manual         5m

# 排查步骤
kubectl describe pvc ctts-mysql-pvc
# 查看Events部分，常见原因：
# 1. 无匹配PV（容量不足、accessModes不匹配、storageClassName不一致）
# 2. selector标签不匹配
# 3. StorageClass的provisioner未部署

# 解决方案
kubectl get pv   # 检查是否有匹配PV
# - 若无PV：创建符合PVC要求的PV
# - 若PV存在但不匹配：检查storageClassName、accessModes、容量、selector

报错2：Pod挂载PVC失败

# 现象
kubectl get pod
# NAME           READY   STATUS              RESTARTS   AGE
# ctts-mysql-xx  0/1     ContainerCreating   0          2m

# 排查
kubectl describe pod ctts-mysql-xx
# 查看Events，常见原因：
# 1. PVC未Bound（Pending状态）
# 2. Pod与PVC不在同一命名空间
# 3. volumeMounts.name与volumes.name不一致

报错3：PV处于Released状态无法绑定新PVC

# 现象：PV状态Released，新PVC一直Pending
kubectl get pv ctts-mysql-pv
# NAME            CAPACITY   ...   STATUS     CLAIM
# ctts-mysql-pv   5Gi        ...   Released   default/ctts-mysql-pvc

# 原因：旧PVC删除后PV保留claimRef，需手动清除
# 解决：清除claimRef
kubectl patch pv ctts-mysql-pv -p '{"spec":{"claimRef": null}}'
# PV状态变为Available，可被新PVC绑定

报错4：MySQL启动失败——权限问题

# 现象：MySQL容器启动后立即CrashLoopBackOff
kubectl logs ctts-mysql-xx
# 报错：mysqld: Cannot change permissions of the file 'ibdata1'

# 原因：hostPath目录权限不符
# 解决：
minikube ssh -- sudo chmod -R 777 /data/ctts/mysql
# 或在PV中使用正确的SELinux标签
