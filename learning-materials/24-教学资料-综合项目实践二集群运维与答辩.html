一、故障排查指南（5大故障场景）

1.1 故障一：CrashLoopBackOff（Pod崩溃循环）

现象：

$ kubectl get pods
NAME                    READY   STATUS             RESTARTS   AGE
ctts-web-xxx-yyy        0/1     CrashLoopBackOff   5          3m

Pod反复重启，状态在Running与CrashLoopBackOff之间循环，RESTARTS计数持续增加。

常见原因：

  1. 容器启动命令错误（command/args配置不当）
  2. 应用启动失败（配置文件缺失、依赖服务未就绪、端口被占用）
  3. 容器内进程异常退出（应用代码异常、依赖缺失）
  4. 存活探针配置过严，应用未就绪即被杀死
  5. 资源限制过严（CPU/内存过低导致OOM后重启）

排查命令链：

# 步骤1：查看Pod详细事件
kubectl describe pod <pod-name> -n <namespace>

# 步骤2：查看当前容器日志
kubectl logs <pod-name> -n <namespace>

# 步骤3：查看上一次崩溃的日志（关键！）
kubectl logs <pod-name> -n <namespace> --previous

# 步骤4：查看Pod事件
kubectl get events -n <namespace> --sort-by='.lastTimestamp' | tail -20

# 步骤5：进入容器排查（如果Pod偶尔Running）
kubectl exec -it <pod-name> -n <namespace> -- /bin/sh

解决方案：

  • 启动命令错误：修正Deployment中的command/args
containers:
- name: ctts-web
  image: ctts-web:v1
  command: ["/app/server"]
  args: ["--config=/etc/ctts/config.yaml"]
  • 依赖服务未就绪：配置initContainer等待依赖
initContainers:
- name: wait-db
  image: busybox
  command: ['sh', '-c', 'until nslookup mysql-service; do sleep 2; done']
  • 存活探针过严：调大initialDelaySeconds、failureThreshold
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 60   # 应用启动慢时调大
  periodSeconds: 10
  failureThreshold: 6       # 允许失败次数调大

1.2 故障二：NotReady（节点不可达）

现象：

$ kubectl get nodes
NAME           STATUS                     ROLES    AGE   VERSION
k8s-master     Ready                      master   30d   v1.28.0
k8s-worker1    Ready                      <none>   30d   v1.28.0
k8s-worker2    NotReady                   <none>   30d   v1.28.0

节点状态显示NotReady，该节点上Pod可能被驱逐或无法调度。

常见原因：

  1. kubelet服务停止或崩溃
  2. 节点网络故障（与master失联）
  3. 节点资源耗尽（内存/CPU/磁盘满）
  4. 容器运行时（containerd/docker）异常
  5. 节点主机宕机或硬件故障

排查命令链：

# 步骤1：查看节点详情与条件
kubectl describe node <node-name>
# 关注 Conditions 部分：MemoryPressure/DiskPressure/PIDPressure/Ready

# 步骤2：查看节点上的Pod
kubectl get pods --all-namespaces --field-selector spec.nodeName=<node-name> -o wide

# 步骤3：SSH登录故障节点，检查kubelet
systemctl status kubelet
journalctl -u kubelet --since "10 minutes ago" | tail -50

# 步骤4：检查容器运行时
crictl ps    # 或 docker ps
systemctl status containerd   # 或 docker

# 步骤5：检查节点资源
free -h
df -h
top

解决方案：

  • kubelet停止：systemctl restart kubelet，并设置开机自启systemctl enable kubelet
  • 网络故障：检查节点与master的网络连通性ping <master-ip>、telnet <master-ip> 6443
  • 磁盘满：清理无用镜像与日志
crictl rmi --prune    # 清理未使用镜像
journalctl --vacuum-size=100M   # 清理日志
  • 容器运行时异常：systemctl restart containerd
  • 节点长期不恢复：kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data 后维护

1.3 故障三：Service无端点（服务不可达）

现象：

$ kubectl get svc ctts-web-service
NAME                 TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)    AGE
ctts-web-service     ClusterIP   10.96.50.100   <none>        80/TCP     5m

$ kubectl get endpoints ctts-web-service
NAME                 ENDPOINTS       AGE
ctts-web-service     <none>          5m

Service存在但ENDPOINTS为<none>，访问Service无响应或连接拒绝。

常见原因：

  1. Service的selector与Pod标签不匹配
  2. Pod未正常运行（未Ready）
  3. Service的targetPort与Pod容器端口不一致
  4. Pod的readinessProbe未通过
  5. 命名空间不一致（Service与Pod不在同一namespace）

排查命令链：

# 步骤1：查看Service详情，确认selector与targetPort
kubectl describe svc <service-name> -n <namespace>

# 步骤2：查看Endpoints（关键！）
kubectl get endpoints <service-name> -n <namespace>
kubectl describe endpoints <service-name> -n <namespace>

# 步骤3：查看Pod标签，与Service selector对比
kubectl get pods -n <namespace> --show-labels

# 步骤4：查看Pod是否Ready
kubectl get pods -n <namespace> -o wide

# 步骤5：查看Pod事件，确认readinessProbe是否通过
kubectl describe pod <pod-name> -n <namespace>

解决方案：

  • 标签不匹配：修正Service的selector或Pod的labels
# Service
spec:
  selector:
    app: ctts-web      # 必须与Pod标签完全一致
# Pod（Deployment模板）
spec:
  template:
    metadata:
      labels:
        app: ctts-web
  • targetPort不一致：修正Service的targetPort为容器实际监听端口
ports:
- port: 80
  targetPort: 8080     # 必须与containerPort一致
  • readinessProbe未通过：检查应用健康检查接口，或临时调整探针配置

1.4 故障四：ImagePullBackOff（镜像拉取失败）

现象：

$ kubectl get pods
NAME                    READY   STATUS              RESTARTS   AGE
ctts-web-xxx-yyy        0/1     ImagePullBackOff    0          2m

Pod状态为ImagePullBackOff或ErrImagePull。

常见原因：

  1. 镜像名称拼写错误（image: ctts-web:v1 写成 ctts_web:v1）
  2. 镜像不存在（tag错误、仓库无此镜像）
  3. 私有仓库未配置认证（imagePullSecrets缺失）
  4. 网络无法访问镜像仓库（防火墙/DNS问题）
  5. 镜像仓库限流（如Docker Hub速率限制）

排查命令链：

# 步骤1：查看Pod事件（关键！会显示拉取失败的详细原因）
kubectl describe pod <pod-name> -n <namespace>
# 关注 Events 部分：
# Failed to pull image "xxx": rpc error: code = Unknown desc = Error response from daemon: manifest unknown

# 步骤2：确认镜像名称与tag
kubectl get pod <pod-name> -n <namespace> -o jsonpath='{.spec.containers[*].image}'

# 步骤3：在节点上手动拉取测试
ssh <node-ip>
crictl pull <image-name>   # 或 docker pull <image-name>

# 步骤4：检查私有仓库认证
kubectl get secret -n <namespace>
kubectl describe pod <pod-name> -n <namespace> | grep -A5 imagePullSecrets

解决方案：

  • 镜像名错误：修正Deployment中的image字段
  • 私有仓库认证：创建imagePullSecrets
kubectl create secret docker-registry regcred \
  --docker-server=<registry> \
  --docker-username=<user> \
  --docker-password=<pass> \
  --docker-email=<email> \
  -n <namespace>
spec:
  template:
    spec:
      imagePullSecrets:
      - name: regcred
      containers:
      - name: ctts-web
        image: <registry>/ctts-web:v1
  • 网络问题：配置节点代理或使用国内镜像源
# containerd配置镜像加速
# /etc/containerd/config.toml 添加 registry_mirrors

1.5 故障五：OOMKilled（资源不足被杀）

现象：

$ kubectl describe pod <pod-name>
...
Last State: Terminated
  Reason: OOMKilled
  Exit Code: 137
  Started: ...
  Finished: ...

Pod被终止，退出码137，RESTARTS计数增加，状态可能为CrashLoopBackOff。

常见原因：

  1. resources.limits.memory设置过低，应用内存需求超过限制
  2. 应用内存泄漏
  3. Java应用JVM堆未根据容器限制调整（-Xmx设置过大）
  4. 节点内存压力，kubelet主动驱逐
  5. 未设置resources.requests导致调度到资源不足节点

排查命令链：

# 步骤1：查看Pod详情，确认OOMKilled
kubectl describe pod <pod-name> -n <namespace>
# 关注 Last State: Terminated, Reason: OOMKilled, Exit Code: 137

# 步骤2：查看资源限制
kubectl get pod <pod-name> -n <namespace> -o jsonpath='{.spec.containers[0].resources}'

# 步骤3：查看节点资源使用
kubectl describe node <node-name> | grep -A5 "Allocated resources"

# 步骤4：查看Pod历史资源使用（需metrics-server）
kubectl top pod <pod-name> -n <namespace>

# 步骤5：查看应用日志，确认内存使用情况
kubectl logs <pod-name> -n <namespace> --previous | grep -i "memory\|heap\|oom"

解决方案：

  • 调大内存限制：
resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"     # 从256Mi调大到512Mi
    cpu: "500m"
  • Java应用调整JVM参数（关键！）：
env:
- name: JAVA_OPTS
  value: "-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0"
# Java 8u191+ 和 Java 11+ 支持容器感知，自动按比例分配堆
  • 应用内存泄漏：排查应用代码，使用jmap/jstack分析堆dump
  • 设置合理的resources.requests避免调度到资源不足节点

二、运维操作手册

2.1 滚动更新（kubectl set image）

场景：将CTTS-web服务从v1版本更新到v2版本，零停机。

操作命令：

# 方式1：kubectl set image命令（推荐用于快速更新）
kubectl set image deployment/ctts-web ctts-web=ctts-web:v2 -n ctts-prod

# 方式2：kubectl apply更新YAML（推荐用于生产）
# 先修改 deployment.yaml 中 image: ctts-web:v2
kubectl apply -f deployment.yaml -n ctts-prod

查看更新进度：

# 查看滚动更新状态
kubectl rollout status deployment/ctts-web -n ctts-prod
# 输出：deployment "ctts-web" successfully rolled out

# 查看更新历史
kubectl rollout history deployment/ctts-web -n ctts-prod

# 查看某个版本的详情
kubectl rollout history deployment/ctts-web -n ctts-prod --revision=2

滚动更新原理：

  • Deployment默认策略：先创建新Pod，Ready后再删除旧Pod
  • maxSurge：超出期望副本数的最大比例（默认25%）
  • maxUnavailable：不可用副本的最大比例（默认25%）
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%

2.2 回滚（kubectl rollout undo）

场景：v2版本有bug，需回滚到v1版本。

操作命令：

# 回滚到上一版本
kubectl rollout undo deployment/ctts-web -n ctts-prod

# 回滚到指定版本
kubectl rollout undo deployment/ctts-web -n ctts-prod --to-revision=1

# 查看回滚状态
kubectl rollout status deployment/ctts-web -n ctts-prod

回滚注意事项：

  • 回滚同样采用滚动更新策略，零停机
  • 回滚后建议立即修复新版本问题，避免反复回滚
  • 生产环境回滚前先备份当前版本配置

2.3 扩缩容（kubectl scale + HPA）

2.3.1 手动扩缩容

# 扩容到5个副本
kubectl scale deployment ctts-web --replicas=5 -n ctts-prod

# 缩容到2个副本
kubectl scale deployment ctts-web --replicas=2 -n ctts-prod

# 查看扩缩容结果
kubectl get pods -n ctts-prod -l app=ctts-web

2.3.2 HPA自动扩缩容（Horizontal Pod Autoscaler）

HPA配置YAML：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ctts-web-hpa
  namespace: ctts-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ctts-web
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # CPU使用率超过70%扩容
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80   # 内存使用率超过80%扩容

HPA操作命令：

# 创建HPA
kubectl apply -f hpa.yaml

# 查看HPA状态
kubectl get hpa -n ctts-prod
# NAME            REFERENCE                 TARGETS   MINPODS   MAXPODS   REPLICAS
# ctts-web-hpa    Deployment/ctts-web       50%/70%   2         10        2

# 查看HPA详情
kubectl describe hpa ctts-web-hpa -n ctts-prod

# 压测触发自动扩容（需安装hey或ab）
hey -z 5m -c 50 http://<service-ip>/

HPA前置条件：

  • 集群必须安装metrics-server
  • Deployment必须配置resources.requests（HPA基于requests计算使用率）
# 安装metrics-server
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

2.4 日志查看与排障

2.4.1 kubectl logs 常用命令

# 查看当前日志
kubectl logs <pod-name> -n <namespace>

# 实时跟踪日志（类似tail -f）
kubectl logs -f <pod-name> -n <namespace>

# 查看上一个容器的日志（崩溃后排查关键）
kubectl logs <pod-name> -n <namespace> --previous

# 查看多容器Pod指定容器日志
kubectl logs <pod-name> -c <container-name> -n <namespace>

# 查看最近1小时日志
kubectl logs --since=1h <pod-name> -n <namespace>

# 查看最近100行日志
kubectl logs --tail=100 <pod-name> -n <namespace>

# 查看指定时间段日志
kubectl logs --since-time=2024-01-01T00:00:00Z <pod-name> -n <namespace>

2.4.2 kubectl describe 排障

# 查看Pod详情（排障第一命令）
kubectl describe pod <pod-name> -n <namespace>
# 关注：
# - Events部分：调度、拉取镜像、探针检查等事件
# - Containers部分：State、Last State、Restart Count
# - Conditions部分：PodReady、ContainersReady等

# 查看Node详情
kubectl describe node <node-name>
# 关注：Conditions、Allocated resources、系统信息

# 查看Service详情
kubectl describe svc <service-name> -n <namespace>
# 关注：Endpoints、Selector、Ports

2.4.3 kubectl exec 进入容器

# 进入容器交互
kubectl exec -it <pod-name> -n <namespace> -- /bin/sh
# 或
kubectl exec -it <pod-name> -n <namespace> -- /bin/bash

# 进入指定容器
kubectl exec -it <pod-name> -c <container-name> -n <namespace> -- /bin/sh

# 直接执行命令
kubectl exec <pod-name> -n <namespace> -- ls /app
kubectl exec <pod-name> -n <namespace> -- cat /etc/ctts/config.yaml

2.4.4 kubectl get 常用查询

# 查看所有资源
kubectl get all -n <namespace>

# 宽格式输出（显示IP、节点）
kubectl get pods -n <namespace> -o wide

# YAML格式输出
kubectl get pod <pod-name> -n <namespace> -o yaml

# JSON格式输出（配合jq查询）
kubectl get pod <pod-name> -n <namespace> -o json | jq '.spec.containers[0].image'

# 按标签查询
kubectl get pods -n <namespace> -l app=ctts-web

# 查看所有命名空间资源
kubectl get pods --all-namespaces

2.4.5 kubectl events 事件查看

# 查看命名空间事件（按时间排序）
kubectl get events -n <namespace> --sort-by='.lastTimestamp'

# 查看指定Pod事件
kubectl get events -n <namespace> --field-selector involvedObject.name=<pod-name>

# 查看警告事件
kubectl get events -n <namespace> --field-selector type=Warning

2.5 运维操作速查表

操作 命令 说明
滚动更新 kubectl set image deploy/<name> <container>=<image>:<tag> 快速更新镜像版本
查看更新状态 kubectl rollout status deploy/<name> 等待更新完成
查看更新历史 kubectl rollout history deploy/<name> 查看历史版本
回滚上一版本 kubectl rollout undo deploy/<name> 快速回滚

3.4 常见答辩问题（20个）

基础概念类

  1. 请解释Pod、Deployment、Service三者关系。

    • 答：Pod是最小调度单元，封装容器；Deployment管理Pod副本集，负责滚动更新与回滚；Service提供稳定访问入口，通过标签选择器关联Pod。

  2. ConfigMap和Secret有什么区别？如何使用？

    • 答：ConfigMap存非敏感配置（明文），Secret存敏感信息（Base64编码）。通过env或volume挂载使用。

  3. K8s的Service有哪几种类型？区别是什么？

    • 答：ClusterIP（集群内访问）、NodePort（节点端口暴露）、LoadBalancer（云负载均衡）、ExternalName（CNAME别名）。

  4. Ingress和Service的区别？为什么需要Ingress？

    • 答：Service是L4负载均衡，Ingress是L7（HTTP/HTTPS）负载均衡，支持域名路由与TLS终止，适合HTTP服务统一入口。

  5. 什么是Namespace？生产环境如何划分？

    • 答：Namespace是虚拟集群隔离。生产环境常按环境（dev/test/prod）或团队划分。

故障排查类

  1. CrashLoopBackOff如何排查？

    • 答：kubectl describe看事件 → kubectl logs --previous看崩溃前日志 → 定位根因（启动命令/配置/依赖）→ 修复。

  2. Pod状态OOMKilled是什么原因？如何解决？

    • 答：内存限制过低或应用内存泄漏。解决：调大resources.limits.memory、Java应用调整JVM参数、排查内存泄漏。

  3. Service没有端点（ENDPOINTS为none）可能的原因？

    • 答：selector与Pod标签不匹配、Pod未Ready、targetPort不一致、namespace不一致。

  4. 节点NotReady如何处理？

    • 答：kubectl describe node看Conditions → SSH登录检查kubelet/容器运行时/资源 → 重启服务或清理资源。

  5. ImagePullBackOff如何解决？

    • 答：检查镜像名拼写、确认镜像存在、配置私有仓库imagePullSecrets、检查网络连通性。

运维操作类

  1. 如何实现零停机滚动更新？

    • 答：Deployment默认滚动更新策略，maxSurge+maxUnavailable控制更新节奏，readinessProbe确保新Pod Ready后才删旧Pod。

  2. 如何回滚到上一个版本？

    • 答：kubectl rollout undo deployment/，可加--to-revision=N回滚到指定版本。

  3. HPA自动扩缩容的原理？需要什么前提？

    • 答：HPA基于CPU/内存使用率或自定义指标自动调整副本数。前提：安装metrics-server、Deployment配置resources.requests。

  4. 如何查看Pod崩溃前的日志？

    • 答：kubectl logs --previous，查看上一个容器的日志。

  5. 如何进入容器排查问题？

    • 答：kubectl exec -it -- /bin/sh，进入容器shell。

项目实践类

  1. CTTS项目为什么要拆分多服务部署？

    • 答：微服务架构、独立伸缩、独立部署、故障隔离、技术栈灵活。

  2. 你们的YAML清单如何组织？

    • 答：按服务分目录，每个服务含deployment.yaml+service.yaml+configmap.yaml，公共资源单独存放，使用Kustomize/Helm管理多环境。

  3. 如何保证配置与镜像解耦？

    • 答：使用ConfigMap/Secret管理配置，通过env或volume注入，镜像不包含环境相关配置。

  4. 项目部署过程中遇到的最大难点是什么？如何解决？

    • 答：（开放题，结合实际回答，如服务间依赖、配置管理、网络策略、存储持久化等）

  5. 如果让你优化这个项目，你会做哪些改进？

    • 答：增加监控告警（Prometheus+Grafana）、日志收集（EFK）、CI/CD流水线、Service Mesh、HPA自动伸缩、网络策略加固等。

6.5 课程核心知识点回顾表

模块 核心知识点 关键命令/技术
M1 容器基础 容器概念、Docker安装、镜像与容器 docker run/ps/images
M2 镜像管理 Dockerfile、多阶段构建、镜像仓库 docker build/push

M4 容器存储 数据卷、存储驱动、持久化 docker volume
M5 K8s基础 架构、Pod、Deployment、Service、ConfigMap kubectl get/apply
M6 K8s进阶 PV/PVC、StatefulSet、Job、Helm kubectl create/helm
M7 K8s高级 Ingress、RBAC、HPA、调度 kubectl autoscale
M8 综合实践 CTTS多服务部署、集群运维、项目答辩 综合运用
