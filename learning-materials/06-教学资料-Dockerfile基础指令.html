二、知识点详解

知识点 K6-1：Dockerfile 概念与作用

定义

Dockerfile 是一个文本文件，里面包含了一条条指令（instruction），每条指令描述镜像构建的一步。Docker 按 Dockerfile 中的指令顺序执行，最终生成一个镜像。

一句话概括：

Dockerfile 是镜像的源代码。

就像源代码描述了程序如何构建，Dockerfile 描述了镜像如何构建。它把"制作镜像"这件事从手工操作变成了代码化、可版本管理、可审计的工程过程。

原理

为什么用 Dockerfile 而非 docker commit？

docker commit 是把一个正在运行的容器"快照"成镜像。看起来很直接，但有三大致命问题：

问题 docker commit Dockerfile
可复现性 不可复现——没人知道你在这个容器里做了什么 完全可复现——任何人照着 Dockerfile 都能 build 出同样的镜像
版本管理 没法版本管理——镜像就是一个二进制 blob 可提交到 Git，每行修改都有 diff
审计与安全 没法审计——不知道装了什么、改了什么 可 Code Review，安全合规可检查

对比例子：

【docker commit 方式制作 CTTS 后端镜像】
1. docker run -it openjdk:17 bash
2. （在容器内）mkdir /app
3. （在容器内）exit
4. docker cp ctts-backend.jar <container_id>:/app/app.jar
5. docker commit <container_id> ctts-backend:v1
   → 得到一个镜像，但没人知道里面到底有什么
   → 三个月后别人接手，完全不知道这个镜像是怎么来的

【Dockerfile 方式制作 CTTS 后端镜像】
# 文件名：Dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY ctts-backend.jar /app/app.jar
CMD ["java", "-jar", "/app/app.jar"]

docker build -t ctts-backend:v1 .
   → 任何人看 Dockerfile 就知道镜像里有什么
   → 提交到 Git，每次修改都有记录
   → 同事可以 Code Review

Dockerfile 的基本结构：

# 这是注释（以 # 开头）
# 指令通常大写（虽然小写也能跑，但规范是大写）

FROM eclipse-temurin:17-jre          # 基础镜像（必须，且通常第一行）
WORKDIR /app                          # 设置工作目录
COPY ctts-backend.jar /app/app.jar    # 复制本地文件到镜像
RUN apt-get update && apt-get install -y curl   # 执行命令
USER appuser                          # 切换用户
CMD ["java", "-jar", "/app/app.jar"]  # 容器启动命令

Dockerfile 语法要点：

规则 说明
文件名 固定为 Dockerfile（无扩展名，首字母大写）
注释 # 开头
指令大小写 规范是大写（如 FROM、RUN），虽然小写也能执行
指令顺序 从上到下顺序执行
第一条指令 通常是 FROM（指定基础镜像）
指令参数 每条指令后跟参数，参数格式取决于指令

问题 / 场景

问：Dockerfile 的文件名必须是 Dockerfile 吗？

  • 默认是 Dockerfile（首字母大写，无扩展名）。如果用别的名字，构建时要加 -f 参数：docker build -f MyDockerfile -t myapp:v1 .。但工程上建议用默认名，便于团队协作。

问：Dockerfile 里能写中文注释吗？

  • 可以，但建议用英文注释，避免某些构建环境对中文编码处理不一致导致构建失败。注释以 # 开头。

问：docker commit 完全不能用吗？

  • 不是。docker commit 在"现场调试"场景有用——比如容器出问题了，临时 commit 一个镜像保留现场。但生产镜像绝不能用 commit 做，必须用 Dockerfile。

WORKDIR /app

# 复制一个脚本到镜像
COPY hello.sh /app/hello.sh

# 给脚本加执行权限
RUN chmod +x /app/hello.sh

# 容器启动时执行
CMD ["/app/hello.sh"]

易错点

  1. ❌ 文件名写成 dockerfile（小写 d）或 Dockerfile.txt（带扩展名）。✅ 默认文件名就是 Dockerfile，首字母大写、无扩展名。
  2. ❌ 误以为"能用 docker commit 就别写 Dockerfile"。✅ 生产镜像必须用 Dockerfile，commit 只用于临时调试。
  3. ❌ Dockerfile 里指令全小写（如 from、run）。✅ 规范是大写指令（FROM、RUN），便于区分指令和参数。
  4. ❌ 第一条指令不是 FROM。✅ Dockerfile 通常以 FROM 开头（除了 ARG、解析器指令等少数例外）。

小结

Dockerfile 是描述镜像构建过程的文本文件，是镜像的源代码。相比 docker commit，Dockerfile 具有可复现、可版本管理、可审计三大优势，是生产镜像构建的唯一规范方式。Dockerfile 由一条条指令组成，规范是指令大写、从上到下执行、以 FROM 开头。

知识点 K6-2：FROM 指令

定义

FROM 指令指定基础镜像（base image），是 Dockerfile 的"地基"。所有后续指令都在这个基础镜像之上叠加。FROM 通常是 Dockerfile 的第一条指令。

FROM <镜像名>:<标签>

原理

为什么要 FROM？

容器镜像采用分层结构。你的应用镜像不可能"从零开始"——它需要一个底层：要么是操作系统（如 ubuntu、alpine），要么是某个运行时（如 openjdk、python），要么是某个服务的官方镜像（如 mysql、nginx）。FROM 就是告诉 Docker："我这个镜像站在哪个巨人的肩膀上"。

图示 2：你的应用镜像（FROM 之上的层）

FROM

选择基础镜像，决定系统和运行时底座。

WORKDIR / COPY

建立工作目录，把应用文件放进镜像。

RUN

安装依赖或构建应用，每条 RUN 通常形成新层。

EXPOSE / CMD

声明端口和默认启动命令，决定容器运行方式。

Dockerfile 的本质是在基础镜像之上，一层层叠加你的应用运行所需内容。

FROM 的三种典型用法：

# 1. 用通用基础镜像（最常见）
FROM ubuntu:22.04
FROM alpine:3.18
FROM debian:bookworm-slim

# 2. 用语言运行时镜像（开发应用最常用）
FROM eclipse-temurin:17-jre     # Java 17 运行时
FROM python:3.11-slim            # Python 3.11
FROM node:20-alpine              # Node.js 20

# 3. 用 scratch（空镜像，极少数场景）
FROM scratch

官方镜像选择原则：

原则 说明 示例
用官方镜像 Docker Hub 上带 "Official Image" 标记的，经过安全审查 eclipse-temurin:17-jre 而不是随便某个 xxx/jdk17
固定版本 不用 :latest，指定明确版本号，保证可复现 alpine:3.18 而不是 alpine:latest
选 slim/alpine 变体 体积小、攻击面小 python:3.11-slim（~50MB）而不是 python:3.11（~350MB）
优先用运行时镜像 Java 应用用 eclipse-temurin:17-jre，而不是用 ubuntu 自己装 JDK 直接用现成的运行时镜像

关于 scratch：

scratch 是一个特殊的"空镜像"——它什么都不包含。用 FROM scratch 意味着你的镜像完全从零开始，里面只有你 COPY 进去的内容。常用于：

  • 静态编译的 Go 程序（不依赖任何库）
  • 极致追求镜像体积的场景
# Go 程序的 scratch 镜像示例
FROM scratch
COPY myapp /myapp
CMD ["/myapp"]

📌 大多数应用不需要用 scratch。用 scratch 意味着你必须自己处理所有依赖（glibc、动态库等），门槛较高。

问题 / 场景

问：为什么不用 :latest 标签？

  • :latest 是一个会变的指针——今天 alpine:latest 是 3.18，明天可能是 3.19。如果你的 Dockerfile 写 FROM alpine:latest，今天 build 和明天 build 出来的镜像可能不一样，破坏可复现性。生产环境必须指定明确版本。

问：eclipse-temurin 是什么？为什么不用 openjdk？

  • openjdk 是 Docker Hub 上的老牌 OpenJDK 镜像，但 Docker 官方已声明 openjdk 镜像不再更新（已被弃用）。eclipse-temurin 是 Adoptium 项目维护的 OpenJDK 镜像，是目前 Java 应用的事实标准。类似的还有 amazoncorretto、azul/zulu-openjdk 等。

问：alpine、slim、普通版有什么区别？

  • alpine：基于 Alpine Linux，体积最小（5MB 左右），但用 musl libc 而非 glibc，部分软件可能有兼容问题。
  • slim：基于 Debian，去掉了一些非必要文件，体积适中（50MB 左右），兼容性好。
  • 普通版：完整 Debian，体积最大（几百 MB），但最稳。
  • 选择原则：优先 slim，其次 alpine，最后普通版。如果 alpine 有兼容问题再退回 slim。

问：FROM 能用多个吗？

  • 可以，这叫"多阶段构建"，一条 Dockerfile 可以有多个 FROM，每个 FROM 开启一个构建阶段。这是第 7 次课的内容，本节不展开。

对比不同基础镜像的体积：

# 测试1：ubuntu 基础镜像

Java 应用基础镜像选择示例：

# CTTS 后端 Dockerfile - 选 eclipse-temurin:17-jre
# 为什么？
#   - eclipse-temurin 是官方维护的 OpenJDK 镜像（openjdk 已弃用）
#   - 17 是 LTS 版本，匹配 CTTS 项目用的 Java 17
#   - jre 变体只含运行时不含 JDK，体积更小（运行 jar 用 jre 就够）
#   - 没用 alpine 变体是因为某些 JNI 库在 alpine 上有兼容问题

FROM eclipse-temurin:17-jre
WORKDIR /app
COPY ctts-backend.jar /app/app.jar
CMD ["java", "-jar", "/app/app.jar"]

图示

图示 3：基础镜像选择决策图
先看应用运行时，再看体积、安全和兼容性

Java 应用

运行阶段优先 eclipse-temurin:17-jre；需要更小体积时评估 jre-alpine 兼容性。

Python / Node.js

Python 可选 python:3.11-slim，Node.js 可选 node:20-alpine 或 slim。

静态/单二进制

静态网站用 nginx:alpine；Go 静态二进制可用 scratch。

分层关系：你的应用层叠加在 FROM 指定的基础镜像之上；基础镜像越合理，最终镜像越小、越安全、越稳定。

易错点

  1. ❌ 用 FROM ubuntu:latest（不固定版本）。✅ 用 FROM ubuntu:22.04，固定版本保证可复现。
  2. ❌ Java 应用用 FROM ubuntu 然后自己 apt install openjdk。✅ 直接用 FROM eclipse-temurin:17-jre，省事且规范。
  3. ❌ 用 FROM openjdk:17（openjdk 已弃用）。✅ 用 FROM eclipse-temurin:17-jre。
  4. ❌ 一上来就用 FROM scratch。✅ 99% 的应用不需要 scratch，用现成基础镜像即可。
  5. ❌ 用不知名第三方镜像作为基础镜像。✅ 优先用 Docker Hub 官方镜像（带 "Official Image" 标记）。

小结

FROM 指定基础镜像，是 Dockerfile 的地基。选择原则：用官方镜像、固定版本、优先 slim/alpine 变体、优先用现成运行时镜像而非自己装。Java 应用首选 eclipse-temurin:17-jre，Python 首选 python:3.11-slim，静态网站用 nginx:alpine。绝不用 :latest 标签。

知识点 K6-3：RUN 指令

定义

RUN 指令在构建镜像时执行命令，通常用于安装软件包、创建目录、修改文件等。每条 RUN 指令都会在镜像中生成一个新的层（layer）。

# shell 形式（最常用）
RUN <命令>

# exec 形式（推荐用于需要精确控制时）
RUN ["可执行文件", "参数1", "参数2"]

原理

每条 RUN 生成一层：

Docker 镜像是分层的。Dockerfile 中每条 RUN、COPY、ADD 指令都会创建一个新的层。每层都是只读的，叠加在上一层之上。

# 反面教材：每条 RUN 一层，共 4 层
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y vim
RUN rm -rf /var/lib/apt/lists/*
生成 4 个层：
┌──────────────────────────┐
│ 层4: rm -rf /var/lib/apt │  ← 删除操作也占一层（虽然文件删了，但层在）
├──────────────────────────┤
│ 层3: install vim          │
├──────────────────────────┤
│ 层2: install curl         │
├──────────────────────────┤
│ 层1: apt-get update       │
└──────────────────────────┘

层缓存的影响：

Docker 构建时按指令顺序缓存。如果某条指令没变，Docker 会复用上次构建的层（缓存命中，秒过）。一旦某条指令变了，这条及之后的所有指令都会重新执行（缓存失效）。

# 假设这是 Dockerfile
FROM eclipse-temurin:17-jre          # 第1层 - 缓存
RUN apt-get update && apt-get install -y curl   # 第2层 - 缓存
WORKDIR /app                          # 第3层 - 缓存
COPY ctts-backend.jar /app/app.jar    # 第4层 - 这层每次 jar 变了就失效
CMD ["java", "-jar", "/app/app.jar"]  # 第5层
你改了 ctts-backend.jar 后重新 build：
FROM eclipse-temurin:17-jre          → CACHED (缓存命中)
RUN apt-get update && apt-get install -y curl   → CACHED (缓存命中)
WORKDIR /app                          → CACHED (缓存命中)
COPY ctts-backend.jar /app/app.jar    → 重新执行（jar 变了）
CMD ["java", "-jar", "/app/app.jar"]  → 重新执行

📌 这就是为什么 Dockerfile 里"不常变的指令放前面，常变的放后面"——让缓存尽量命中，加快构建。

合并 RUN 命令优化：

# ✅ 推荐：用 && 合并命令，只生成 1 层
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        curl \
        vim \
        ca-certificates \
    && rm -rf /var/lib/apt/lists/*

为什么合并？

  1. 减少层数（4 层 → 1 层），镜像更小。
  2. rm -rf /var/lib/apt/lists/* 在同一层执行，能真正减小体积（不会因为分层而保留中间状态）。

shell 形式 vs exec 形式：

# shell 形式：通过 /bin/sh -c 执行，支持变量替换、管道
RUN echo "Hello $NAME"          # $NAME 会被 shell 解析
RUN apt-get update | grep http  # 管道可用

# exec 形式：直接执行，不经过 shell，不支持变量替换
RUN ["echo", "Hello $NAME"]     # $NAME 不会被解析，原样输出
RUN ["/bin/bash", "-c", "echo Hello $NAME"]  # 显式调 shell 才能解析

何时用 exec 形式？

  • 需要精确控制时（避免 shell 干扰）
  • 命令中包含特殊字符（$、"）需要原样传递时
  • 大多数情况用 shell 形式即可

问题 / 场景

问：为什么 RUN apt-get update 和 RUN apt-get install 必须用 && 连起来？

  • 如果分开写：RUN apt-get update 单独一层，RUN apt-get install -y curl 单独一层。后者会用前者缓存中的包索引。但缓存可能过期，导致 install 时找不到包或版本错。用 && 连起来保证 update 和 install 在同一层执行，索引一定是最新的。

问：RUN 和 CMD 有什么区别？

  • RUN：在构建时执行，生成镜像层。通常用于装软件、配置环境。
  • CMD：在容器启动时执行，不生成层。指定容器默认启动命令。
  • 简单记忆：RUN 是"做镜像时跑一次"，CMD 是"启动容器时跑"。

问：RUN 写太多命令会不会让镜像很大？

  • 会。每条 RUN 一层，层越多镜像越大。所以要用 && 合并相关命令，并在同一层清理临时文件（如 apt 的 lists、wget 下载的压缩包）。

知识点 K6-4：COPY 与 ADD 指令

定义

COPY 和 ADD 都是把文件从构建上下文（通常是 Dockerfile 所在目录）复制到镜像中。功能相似但有差异。

COPY <源路径> <目标路径>
ADD <源路径> <目标路径>

原理

COPY 指令：

# 复制单个文件
COPY ctts-backend.jar /app/app.jar

# 复制整个目录
COPY target/ /app/target/

# 使用 WORKDIR 后的简写
WORKDIR /app
COPY ctts-backend.jar .          # . 表示当前工作目录 /app

COPY 的特点：

  • 只做一件事：把本地文件复制到镜像。
  • 行为可预测，没有"惊喜"。
  • 官方推荐优先使用 COPY。

ADD 指令：

ADD 在 COPY 基础上多了两个功能：

额外功能 示例 说明
自动解压 tar 包 ADD rootfs.tar.gz / 复制后自动解压 tar.gz/tar/tar.bz2 等
支持 URL ADD http://example.com/file.txt /app/ 从 URL 下载文件到镜像 
# ADD 额外功能1：自动解压 tar
ADD jdk-17_linux-x64.tar.gz /opt/

# ADD 额外功能2：从 URL 下载
ADD https://example.com/app.jar /app/app.jar

COPY vs ADD 选择建议：

场景 用什么 理由
复制本地文件到镜像 COPY 行为明确，可读性好
复制并解压 tar 包 ADD 或 COPY + RUN tar ADD 解压方便，但有人偏好显式 RUN tar 更清晰
从 URL 下载文件 RUN wget/curl + COPY ADD 的 URL 下载不可控（不能设 headers、不能校验），用 RUN wget 更好

官方建议：

Docker 官方文档明确建议："Although ADD and COPY are functionally similar, generally speaking, COPY is preferred."（虽然 ADD 和 COPY 功能相似，但通常推荐 COPY。）

为什么？因为 ADD 的"自动解压"和"URL 下载"功能容易让人意外：

  • 你以为 ADD file.tar.gz /app/ 是把 tar.gz 复制过去，结果是解压成了一堆文件。
  • 你以为 ADD http://... 跟 COPY 一样，结果它去网络下载了。

行为不可预测是工程大忌。所以：默认用 COPY，需要解压 tar 时再用 ADD。

问题 / 场景

问：COPY 的源路径是相对的还是绝对的？

  • 相对于构建上下文（build context，通常是 Dockerfile 所在目录）。不能写构建上下文之外的路径。
# 假设构建上下文是 ~/ctts/backend/
COPY ctts-backend.jar /app/         # ✅ 相对于 ~/ctts/backend/
COPY ../frontend/dist /app/         # ❌ 不能超出构建上下文

问：COPY 的目标路径是相对的还是绝对的？

  • 如果用了 WORKDIR，相对路径会基于 WORKDIR；没用 WORKDIR 则基于 /。建议用绝对路径或先设 WORKDIR。
WORKDIR /app
COPY ctts-backend.jar .             # . = /app（因为 WORKDIR）
COPY ctts-backend.jar /app/         # 等价写法（绝对路径）

问：COPY 一个目录时，是复制目录本身还是目录内容？

  • 看目标路径结尾有没有 /：
    • COPY mydir /app → 把 mydir 复制成 /app（如果 /app 不存在则 /app 就是 mydir 的内容；如果 /app 存在则 /app/mydir）
    • COPY mydir/ /app/ → 把 mydir 的内容复制到 /app 下
  • 工程上建议目标路径以 / 结尾，行为更可预测。

问：能不能用 COPY 把宿主机的任意文件复制到镜像？

  • 不能。COPY 只能从构建上下文复制。构建上下文是 docker build 命令最后的路径参数（通常是 .）。这是安全设计——防止 Dockerfile 读取宿主机敏感文件。

知识点 K6-5：WORKDIR 与 USER 指令

定义

  • WORKDIR：设置工作目录，后续指令（RUN、CMD、ENTRYPOINT、COPY、ADD）的相对路径都基于此目录。
  • USER：切换运行用户，后续指令以该用户身份执行，容器也以该用户启动。
WORKDIR /app
USER appuser

原理

WORKDIR 的工作机制：

# 没有 WORKDIR 时，所有相对路径基于 /
COPY app.jar app.jar          # 实际是 /app.jar

# 用 WORKDIR 后
WORKDIR /app
COPY app.jar app.jar          # 实际是 /app/app.jar
RUN pwd                       # 输出 /app

WORKDIR 可以多次设置：

WORKDIR /a
WORKDIR b
WORKDIR c
RUN pwd                       # 输出 /a/b/c（WORKDIR 支持相对路径，叠加）

WORKDIR 会自动创建目录：

如果 WORKDIR 指定的目录不存在，Docker 会自动创建（包括父目录）。

WORKDIR /a/b/c/d              # /a、/a/b、/a/b/c、/a/b/c/d 都会自动创建

USER 的工作机制：

# 默认情况下，容器以 root 用户运行（不安全！）
FROM alpine:3.18
RUN whoami                    # 输出 root
# 容器启动时也是 root

# 用 USER 切换用户
FROM alpine:3.18
RUN adduser -D appuser        # 创建用户
USER appuser
RUN whoami                    # 输出 appuser
# 容器启动时也是 appuser

为什么需要非 root 运行？

容器内的 root 虽然被 namespace 隔离，但仍然是"特权用户"。如果应用有漏洞被攻击，攻击者拿到容器内的 root，可能通过内核漏洞逃逸到宿主机 root。最小权限原则要求：应用能用普通用户跑就用普通用户跑。

图示 5：root 与非 root 运行容器的安全边界
以 root 运行

风险放大

  • 容器内进程拥有 root 身份。
  • 应用漏洞可能让攻击者拿到高权限。
  • 一旦叠加内核逃逸，宿主机风险会被放大。
以 appuser 运行

最小权限

  • 容器内应用只拥有普通用户权限。
  • 即使应用被攻破，影响范围也更有限。
  • 配合只读文件系统和能力裁剪更安全。

USER 的注意事项：

# USER 可以是用户名或 UID
USER appuser                  # 用户名
USER 1000                     # UID
USER 1000:1000                # UID:GID

# USER 切换后，后续指令都以该用户执行
USER appuser
RUN mkdir /app/logs           # 如果 appuser 对 / 没写权限会失败！
# → 通常先在 root 阶段创建好目录并 chown，再 USER 切换

# 正确做法
FROM alpine:3.18
RUN adduser -D -h /app appuser \
    && mkdir -p /app/logs \
    && chown -R appuser:appuser /app
USER appuser
WORKDIR /app
COPY app.jar .

问题 / 场景

问：为什么不直接用 RUN cd /app 切换目录？

  • RUN cd /app 只在那一条 RUN 执行时生效，下一条 RUN 又回到 /。因为每条 RUN 是独立的 shell。用 WORKDIR 设置后，所有后续指令都基于该目录。
# ❌ 反例：cd 不生效
RUN cd /app
RUN pwd                       # 输出 /，不是 /app！

# ✅ 正例：WORKDIR 持续生效
WORKDIR /app
RUN pwd                       # 输出 /app

问：USER 切换后还能切回 root 吗？

  • 能。USER root 可以切回。但工程上不建议在 Dockerfile 中频繁切换用户。

问：基础镜像里没有我要的用户怎么办？

  • 在 RUN 里创建。Debian/Ubuntu 用 useradd，Alpine 用 adduser。
# Alpine
RUN adduser -D -h /app appuser

# Debian/Ubuntu
RUN useradd -m -d /app appuser

图示 6：WORKDIR、RUN cd 与 USER 切换关系
WORKDIR 推荐

持续影响后续指令

  • WORKDIR /app
  • 后续 RUN pwd 仍在 /app。
  • COPY x . 会复制到 /app/x。
  • CMD ["./x"] 会在 /app 中查找。
RUN cd 不推荐

只在当前 RUN 生效

  • RUN cd /app && do_something
  • 下一条 RUN pwd 又回到默认目录。
  • 路径复制和启动命令更容易写复杂。

root 阶段

创建用户、目录并执行 chown。

USER appuser

切换到普通用户，后续 COPY/CMD 以低权限执行。

容器启动

应用以 appuser 身份运行，安全边界更清晰。

易错点

  1. ❌ 用 RUN cd /app 切换目录。✅ 用 WORKDIR /app，持续生效。
  2. ❌ 没设 WORKDIR，COPY 用绝对路径硬编码 /app/xxx。✅ 先 WORKDIR /app，COPY 用相对路径 .。
  3. ❌ 容器以 root 运行（默认）。✅ 创建非 root 用户，用 USER 切换，遵循最小权限原则。
  4. ❌ 切换 USER 后才创建目录或 chown，导致权限不足失败。✅ 在 root 阶段创建目录并 chown，再切换 USER。
  5. ❌ USER 写 USER appuser 但没创建该用户。✅ 先 RUN useradd/adduser 创建用户，再 USER 切换。

小结

WORKDIR 设置工作目录，后续指令的相对路径都基于此，比 RUN cd 更可靠。USER 切换运行用户，遵循最小权限原则，生产镜像应用非 root 用户运行。典型模式：root 阶段创建用户+目录+chown → USER 切换 → COPY/CMD 以非 root 执行。

知识点 K6-6：docker build 与构建上下文

定义

docker build 命令根据 Dockerfile 构建镜像。构建上下文（build context） 是构建时发送给 Docker 守护进程的文件集合，通常是 Dockerfile 所在目录的所有文件。

docker build -t <镜像名>:<标签> <构建上下文路径>

原理

docker build 命令详解：

docker build -t ctts-backend:v0.6 .
#             │                   │
#             │                   └── 构建上下文路径（. = 当前目录）
#             └── 镜像名:标签
参数 含义
-t name:tag 给构建的镜像命名并打标签，可重复使用 -t 打多个标签
.（最后一个参数） 构建上下文路径，. 表示当前目录
-f Dockerfile.xxx 指定 Dockerfile 路径（默认是上下文下的 Dockerfile）
--no-cache 不使用层缓存，强制全部重新构建
--build-arg KEY=VALUE 传递构建参数（配合 ARG 指令使用）

构建上下文是什么？

当执行 docker build 时，Docker 客户端会把构建上下文路径下的所有文件打包发送给 Docker 守护进程。这个"打包发送"的过程就是"发送构建上下文"。

图示 7：客户端 守护进程
  • 客户端 守护进程
  • 1.发送上下文
  •         docker ▶ dockerd
  •         CLI
  • 2.发送Dockerfile
  •   ▶
  •   3.按 Dockerfile 构建
  •   COPY/RUN/...
  •     镜像

关键点：构建上下文 = docker build 最后那个路径下的所有文件。不管 Dockerfile 里有没有 COPY 它们，都会被发送。

.dockerignore 的作用：

.dockerignore 是构建上下文路径下的一个文件，里面列出不要发送给守护进程的文件模式。作用：

  1. 减小构建上下文：跳过大文件、无关文件，加快构建。
  2. 避免泄漏：防止敏感文件（如 .git、 secrets、本地配置）进入镜像或被守护进程接收。
  3. 避免缓存失效：防止无关文件改动触发 COPY 层缓存失效。

docker build 的执行流程：

1. 读取 Dockerfile
2. 发送构建上下文给守护进程（看到 "sending build context to Docker daemon  XXMB"）
3. 按 Dockerfile 指令顺序执行：
   a. FROM：拉取/复用基础镜像
   b. 对每条指令（RUN/COPY/ADD 等）：
      - 检查是否有缓存（上一条指令没变 + 这条指令本身没变）
      - 缓存命中 → 复用上一次的层（CACHED）
      - 缓存未命中 → 执行指令，生成新层
4. 输出最终镜像 ID 和标签

问题 / 场景

问：为什么 docker build 要把整个上下文都发送给守护进程？为什么不只发送 Dockerfile 里 COPY 的文件？

  • Docker 守护进程不知道 Dockerfile 里 COPY 了哪些文件（解析在客户端做的话也复杂），最简单的策略就是"全发"。所以需要 .dockerignore 来排除大文件和敏感文件。

问：构建上下文能不能是当前目录之外的路径？

  • 能。docker build -t xxx /path/to/context。但通常约定上下文就是 Dockerfile 所在目录。

问：如果构建上下文里有 2GB 的日志文件，会怎么样？

  • 每次 docker build 都会把这 2GB 发送给守护进程，构建极慢。用 .dockerignore 排除 *.log 即可。

问：构建失败后，下次构建会从头开始吗？

  • 不会。Docker 会复用之前成功的层（缓存）。从第一个失败的指令重新开始执行。这就是层缓存的价值。

问：怎么强制完全重新构建？

  • 加 --no-cache 参数：docker build --no-cache -t xxx .

#   保证构建可复现
FROM eclipse-temurin:17-jre

# === K6-3 RUN：创建非 root 用户 ===
# 创建 appuser 用户和 /app 目录，并设置权限
# 用 && 合并命令，只生成 1 层
RUN useradd -m -d /app -u 1000 -s /usr/sbin/nologin appuser \
    && mkdir -p /app/config \
    && chown -R appuser:appuser /app

# === K6-5 WORKDIR：设置工作目录 ===
WORKDIR /app

# === K6-4 COPY：复制 jar 和配置文件 ===
# COPY（不用 ADD，因为没有 tar 解压需求）
COPY ctts-backend.jar /app/app.jar
COPY config/ /app/config/

# === K6-5 USER：切换到非 root 用户 ===
USER appuser

# === 容器启动命令（第 7 次课详讲 CMD/ENTRYPOINT）===
CMD ["java", "-jar", "/app/app.jar"]

四、拓展阅读（选学）

  1. BuildKit：Docker 18.09+ 引入的新构建引擎，比传统构建更快、支持并行构建、支持 --mount=type=cache 等高级特性。现在默认开启。深入了解可读 Docker 官方文档 "BuildKit" 章节。
  2. OCI 镜像规范：Open Container Initiative 定义的镜像格式标准，Docker 镜像遵循此标准。了解 OCI 有助于理解镜像分层、manifest、config 等结构。
  3. distroless 镜像：Google 维护的极简镜像，只含应用运行时（如 Java JRE）和最少系统库，不含 shell、包管理器等。比 alpine 更小更安全，但调试困难。适合极致优化场景。
  4. 镜像扫描：用 Trivy、Grype、Snyk 等工具扫描镜像中的漏洞（CVE）。生产镜像应定期扫描。
  5. Dockerfile 最佳实践：Docker 官方文档 "Best practices for writing Dockerfiles" 一节，涵盖指令顺序、缓存利用、安全性等。

五、本节小结与知识结构图

知识结构图（思维导图）

Dockerfile 基础指令
├── K6-1 Dockerfile 概念与作用
│   ├── 定义：描述镜像构建过程的文本文件
│   ├── 价值：可复现、可版本管理、可审计
│   ├── vs docker commit：commit 黑盒，Dockerfile 白盒
│   └── 基本结构：指令大写、从上到下、FROM 开头
├── K6-2 FROM 指令
│   ├── 作用：指定基础镜像
│   ├── 选择原则：官方、固定版本、slim/alpine、运行时镜像
│   ├── Java 首选：eclipse-temurin:17-jre
│   ├── scratch：空镜像，特殊场景
│   └── 禁忌：不用 :latest
├── K6-3 RUN 指令
│   ├── 作用：构建时执行命令
│   ├── 分层：每条 RUN 一层
│   ├── 优化：用 && 合并命令
│   ├── 缓存：按指令顺序缓存，前面的层变了后面全部失效
│   ├── shell vs exec 形式
│   └── 规范：apt update && install && rm 连在一起
├── K6-4 COPY 与 ADD
│   ├── COPY：只复制本地文件，行为明确（推荐）
│   ├── ADD 额外功能：解压 tar、URL 下载
│   ├── 选择建议：默认 COPY，需要解压 tar 才用 ADD
│   └── 注意：源路径必须在构建上下文内
├── K6-5 WORKDIR 与 USER
│   ├── WORKDIR：设置工作目录，持续生效（vs RUN cd 一次性）
│   ├── USER：切换运行用户
│   ├── 安全最佳实践：非 root 运行
│   └── 典型模式：root 创建用户+目录+chown → USER 切换
└── K6-6 docker build 与构建上下文
    ├── docker build -t name:tag .
    ├── 构建上下文：发送给守护进程的所有文件
    ├── .dockerignore：排除大文件和敏感文件
    ├── 层缓存：不常变的放前面，常变的放后面
    └── 常用参数：-t、-f、--no-cache、--build-arg

一句话总结

Dockerfile 是镜像的源代码——用 FROM 选基础镜像、RUN 执行命令（合并减层）、COPY 复制文件、WORKDIR 设工作目录、USER 切非 root 用户，最后 docker build -t name:tag . 构建出可复现、可版本管理、可审计的镜像。
