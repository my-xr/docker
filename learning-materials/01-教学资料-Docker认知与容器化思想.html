    二、知识点详解

    知识点 K1-1：为什么需要容器化

    定义

    容器化（Containerization） 是一种将应用程序及其所有依赖（运行时、库、配置、环境变量）打包到一起，形成一个标准化、可移植的运行单元（容器）的技术，使应用能在任何环境中一致地运行。

    原理

    软件交付中长期存在一个经典痛点——"在我电脑上能跑"（Works on my machine）：

    图示 1：环境不一致如何引发上线事故
    开发视角

    代码在我电脑上能跑

    本机依赖齐全，版本组合刚好匹配，问题被隐藏。

    运维视角

    服务器上跑不起来

    目标机器的系统、运行时、数据库或依赖版本发生偏差。

    开发环境WindowsJDK 17MySQL 8.0依赖 v1.2
    测试环境LinuxJDK 11MySQL 5.7依赖 v0.9
    生产环境LinuxJDK 17MySQL 8.0依赖 v1.3

    环境不一致

    基础软件和依赖版本漂移

    →

    行为不一致

    同一份代码表现不同

    →

    上线事故

    排障成本和交付风险上升

    传统解决方式与各自的问题：

    传统方式 做法 问题
    写部署文档 把环境要求写进文档，运维手动配 文档易过时、人为出错
    虚拟机镜像 做一个虚拟机快照分发 镜像太大（GB 级）、启动慢、资源浪费
    配置管理工具 Ansible/Puppet 自动化配置 仍是"在目标机上装环境"，环境本身不打包

    容器化的思路：不把环境装到目标机上，而是把"应用 + 它需要的全部依赖"打包成一个容器镜像，拿到任何机器上直接运行，环境完全一致。 

    传统交付：交付"代码 + 部署文档"，环境由目标机器提供（易不一致）
容器交付：交付"容器镜像（含应用+依赖）"，环境随镜像一起走（强一致）

    问题 / 场景

    问：容器化是不是只为了解决"在我电脑上能跑"这一个问题？

    • 不止。除了环境一致性，容器化还带来：
      • 快速启动：容器秒级启动（虚拟机分钟级），适合弹性扩容。
      • 资源利用率高：一台机器能跑成百上千个容器（虚拟机通常几十个）。
      • 标准化交付：镜像就是交付物，可版本化、可回滚。
      • 编排基础：为 Kubernetes 这类集群编排打下基础。

    问：不学容器化行不行？

    • 现代云原生应用几乎全部基于容器交付。DevOps、云运维、后端开发岗位都要求掌握容器技术。不学容器化，很难进入云原生技术栈。

    完整示例

    一个真实场景的对比（伪代码描述，说明问题即可，本节不执行）：

    【传统部署 CTTS 后端的痛苦流程】
1. 开发把 ctts-backend.jar 交给运维
2. 运维在服务器上：apt install openjdk-17、apt install mysql、配置环境变量
3. 运维发现服务器上是 JDK 11，升级怕影响别的应用
4. 运维装的 MySQL 版本和开发不一致，SQL 语法报错
5. 反复调试 3 天，终于能跑
6. 上线后发现测试环境和生产环境又不一致，再调 2 天

【容器化部署 CTTS 后端的流程】
1. 开发编写 Dockerfile，把 JDK17 + jar 一起打包成镜像
2. docker build -t ctts-backend:v1 .   →  生成一个镜像
3. docker push ctts-backend:v1           →  推送到镜像仓库
4. 运维：docker run ctts-backend:v1      →  直接运行，环境完全一致
5. 从交付到上线：10 分钟

    📌 这个对比体现了容器化的核心价值：环境随镜像走，一次构建到处运行。Docker 具体命令在第 2~4 次课学习。

    易错点

    1. ❌ 误认为"容器化 = 虚拟机"。✅ 容器和虚拟机是不同的隔离技术，详见 K1-3。
    2. ❌ 误认为"容器化只是为了部署方便"。✅ 它还带来标准化交付、弹性扩容、编排基础等。
    3. ❌ 误认为"容器化就不用管环境了"。✅ 容器只是把环境打包进镜像，镜像本身的构建仍需规范。

    小结

    容器化解决的核心问题是"环境一致性 + 标准化交付"。它把应用和依赖打包成镜像，做到"一次构建、到处运行"，是云原生技术的基础。

    知识点 K1-2：什么是 Docker 与容器化思想

    定义

    Docker 是一个开源的容器化平台，它让开发者能够将应用及其依赖打包成标准化的容器镜像，并在任何环境中快速、一致地运行。

    一句话概括 Docker 的核心思想：

    Build once, run anywhere（一次构建，到处运行）

    原理

    Docker 的核心思想是**"把应用和它的运行环境一起打包"**：

    图示 3：Docker 把应用和运行环境一起打包

    传统方式

    通常只交付应用代码，运行时、依赖库、配置由服务器另行准备。

    →
    Docker 镜像
    应用代码
    运行时：JRE / Python
    依赖库
    配置文件
    环境变量

    镜像

    静态、可分发、可复用

    →

    docker run

    从镜像启动运行实例

    →

    Docker 容器

    运行中的应用实例

    Docker 的诞生背景：

    • 2013 年由 dotCloud 公司（后改名 Docker Inc.）开源。
    • 基于 Linux 内核的 cgroups（资源限制）和 namespaces（隔离）技术。
    • 把容器技术"平民化"——以前容器技术门槛高，Docker 用简单的命令和镜像模型让容器易用。

    Docker 能做什么：

    1. 构建镜像：用 Dockerfile 把应用打包成镜像。
    2. 运行容器：用镜像启动容器实例。
    3. 分发镜像：通过镜像仓库（如 Docker Hub）分享镜像。
    4. 编排多服务：用 Docker Compose 编排多个容器（第 11 次课）。

    问题 / 场景

    问：Docker 和容器是什么关系？

    • 容器是一种技术概念（隔离的运行环境）。Docker 是实现容器技术的一个工具/平台。可以类比为："容器"是"汽车"这个概念，"Docker"是其中一款流行的"汽车品牌"。理论上还有别的容器工具（如 Podman、containerd），但 Docker 是最主流的。

    问：Docker 只能跑 Linux 应用吗？

    • Docker 容器原生基于 Linux 内核特性，所以容器主要运行 Linux 应用。Windows/Mac 上的 Docker Desktop 是通过一个轻量级 Linux 虚拟机来实现的。Windows 容器也存在，但应用场景少，本课程以 Linux 容器为主。

    问：Docker 是免费的吗？

    • Docker 引擎（社区版）开源免费。Docker Desktop 对个人和小企业免费，大企业商用需付费。容器运行时还有完全开源的替代品（如 containerd）。

    完整示例

    Docker 的典型工作流（命令本节只看流程，不要求记忆，后续课程详讲）： 

    # 1. 编写 Dockerfile（描述如何打包）

    易错点

    1. ❌ 误认为"Docker = 容器"。✅ Docker 是实现容器技术的工具，容器是技术概念。
    2. ❌ 误认为"Docker 就是虚拟机"。✅ 二者隔离机制不同，详见 K1-3。
    3. ❌ 误认为"Docker 只能跑 Web 应用"。✅ 任何 Linux 应用都能容器化（数据库、消息队列、命令行工具等）。

    小结

    Docker 是一个容器化平台，核心思想是"把应用和依赖一起打包成镜像，到处运行"。它是云原生技术的基础工具，本课程前 12 次课的核心内容。

    知识点 K1-3：容器 vs 虚拟机

    定义

    • 虚拟机（Virtual Machine, VM）：通过 Hypervisor 在物理机上虚拟出完整的计算机系统，每个虚拟机都运行一个完整的客户机操作系统（Guest OS）。
    • 容器（Container）：共享宿主机内核，通过 Linux 内核的 namespaces 和 cgroups 实现进程级隔离，不需要客户机操作系统。

    原理

    虚拟机架构：

    图示 4：虚拟机架构：每个 VM 携带完整 Guest OS
    VM 1
    AppBin / LibGuest OS
    VM 2
    AppBin / LibGuest OS
    VM 3
    AppBin / LibGuest OS
    Hypervisor：虚拟化层
    Host OS
    物理硬件
    隔离强，但每个 VM 都有一套完整操作系统，体积大、启动慢、资源开销高。

    容器架构：

    图示 5：容器架构：共享宿主机内核，只封装应用和依赖
    容器 1
    AppBin / Lib
    容器 2
    AppBin / Lib
    容器 3
    AppBin / Lib
    Docker 引擎：容器运行时
    Host OS 内核：所有容器共享
    物理硬件
    容器没有独立 Guest OS，使用进程级隔离，因此更轻、更快、更适合密集部署。

    核心区别对比：

    对比项 虚拟机 容器
    隔离机制 Hypervisor 虚拟硬件 namespaces + cgroups（内核级隔离）
    客户机 OS 每个 VM 一个完整 Guest OS 无 Guest OS，共享宿主内核
    启动速度 分钟级（要启动整个 OS） 秒级（启动进程）
    资源占用 重（GB 级，每个 VM 几个 G） 轻（MB 级，镜像通常几十~几百 MB）
    隔离强度 强（硬件级隔离） 较弱（进程级隔离，共享内核）
    单机密度 几个~几十个 VM 几十~几百~上千个容器
    典型用途 强隔离、异构 OS、基础设施 应用交付、微服务、弹性扩容

    问题 / 场景

    问：容器隔离没虚拟机强，是不是不安全？

    • 看场景。对于"多租户强隔离"（如公有云把不同客户的应用隔离），虚拟机更安全。对于"一个团队/一个公司内部的应用隔离"，容器的隔离强度足够，且更轻量。实际生产中常常虚拟机 + 容器并存：用虚拟机做基础设施隔离，在虚拟机里再跑容器。

    问：既然容器这么好，为什么还要虚拟机？

    • 容器共享内核，所以：
      • 不能在 Linux 宿主上跑 Windows 容器（需要 Windows 宿主），异构 OS 需要虚拟机。
      • 内核漏洞会影响所有容器，强安全场景需要虚拟机的硬件级隔离。
      • 一些传统应用（老旧系统）不适合容器化。

    问：容器和虚拟机会取代谁？

    • 不会互相取代，而是互补共存。云上典型架构：物理机 → 虚拟机（IaaS）→ 容器（应用层）→ K8s（编排）。

    完整示例

    判断一个场景该用容器还是虚拟机：

    场景                          推荐技术     理由
─────────────────────────────────────────────────────────────
个人电脑跑多个不同版本MySQL    容器        轻量、秒级启动、互不干扰
银行核心系统强隔离             虚拟机      硬件级隔离，安全性高
微服务快速弹性扩容             容器        启动快、密度高、适合K8s编排
教学实验环境秒级启动           容器        资源省、学生人手一套
跨OS运行（Linux上跑Windows）   虚拟机      容器不能跨内核
公有云多租户隔离               虚拟机+容器  虚拟机做租户隔离，容器做应用

    图示

    易错点

    1. ❌ 误认为"容器 = 轻量级虚拟机"。✅ 二者隔离机制根本不同：虚拟机虚拟硬件、跑完整 OS；容器共享内核、做进程隔离。
    2. ❌ 误认为"容器能完全取代虚拟机"。✅ 强隔离、异构 OS 场景仍需虚拟机，二者常并存。
    3. ❌ 误认为"容器不需要操作系统"。✅ 容器共享宿主机内核，仍依赖宿主 OS 内核，不是"无操作系统"。
    4. ❌ 误认为"容器隔离和虚拟机一样安全"。✅ 容器是进程级隔离，共享内核，隔离强度低于虚拟机的硬件级隔离。

    小结

    容器和虚拟机是两种不同的隔离技术：虚拟机硬件级隔离、跑完整 OS、重而安全；容器共享内核、进程级隔离、轻而快速。二者不是替代关系，生产中常常并存——虚拟机做基础设施，容器做应用交付。

    知识点 K1-4：Docker 引擎架构

    定义

    Docker 引擎（Docker Engine） 是一个 C/S（客户端/服务器）架构的应用，主要由三部分组成：

    1. Docker 守护进程（dockerd）：服务器端，管理镜像、容器、网络、存储。
    2. REST API：客户端与守护进程通信的接口。
    3. Docker 客户端（docker CLI）：命令行工具，用户通过它下发命令。

    容器管理

    run、stop、rm、logs

    网络管理

    创建网络、端口映射

    存储管理

    volume、bind mount

    三大组件详解：

    组件 作用 说明
    Docker Client（docker 命令） 用户交互入口 用户敲 docker xxx，客户端把命令通过 REST API 发给守护进程
    Docker Daemon（dockerd） 核心管理服务 后台常驻进程，负责构建/运行/分发镜像和容器，管理网络和存储
    REST API 通信接口 客户端与守护进程通过 Unix socket 或网络端口通信，接口是 RESTful 的

    更深的层次（了解）：

    docker CLI
    ↓
dockerd（守护进程）
    ↓
containerd（高级容器运行时，负责容器生命周期）
    ↓
runC（低级容器运行时，真正创建/运行容器，遵循OCI标准）

    📌 containerd 和 runC 是 Docker 捐献给 CNCF 的项目，现在是行业标准。Kubernetes 也能直接用 containerd 作为容器运行时。本课程了解即可，操作层面用 docker 命令。

    问题 / 场景

    问：为什么 Docker 要做成 C/S 架构？

    • 解耦：客户端和守护进程可以分开。可以远程管理——在本地敲 docker 命令，操作远端服务器的守护进程（通过 DOCKER_HOST 环境变量）。一个守护进程可以被多个客户端操作。

    问：dockerd 和 containerd 是什么关系？

    • dockerd 是 Docker 的守护进程，它内部调用 containerd 来管理容器生命周期，containerd 再调用 runC 来真正跑容器。简单理解：dockerd 是"管家"，containerd 是"执行者"，runC 是"工人"。

    问：不装 docker 命令行工具能用 Docker 吗？

    • 可以。dockerd 提供了 REST API，你可以直接用 curl 或程序调用 API 来管理容器。docker CLI 只是一个方便的客户端封装。

    完整示例

    一次 docker run 命令在架构中的流转（伪流程，说明原理）： 

    # 用户在终端敲：
docker run -d -p 8080:8080 ctts-backend:v1
    流转过程：
1. docker CLI 把 "run ctts-backend:v1" 通过 REST API 发给 dockerd
2. dockerd 收到命令：
   a. 检查本地有没有 ctts-backend:v1 镜像
   b. 没有则从仓库 pull 下来
   c. 有则在镜像基础上创建容器
3. dockerd 调用 containerd 启动容器
4. containerd 调用 runC 真正创建并运行容器进程
5. 容器跑起来，dockerd 返回容器 ID 给客户端
6. 客户端打印容器 ID：7f8a9b0c1d2e...

    📌 这个流转过程是理解所有 docker 命令的基础——所有命令都是"客户端 → API → 守护进程 → 执行"。后续命令课会反复用到这个模型。

    状态对象

    运行结果

    命令最终落到一个被隔离的容器进程。

    易错点

    1. ❌ 误认为"docker 命令直接操作容器"。✅ docker 命令是客户端，它通过 REST API 请求守护进程，由守护进程操作容器。
    2. ❌ 误认为"dockerd 就是容器"。✅ dockerd 是管理容器的守护进程（一个常驻后台服务），容器是被它管理的运行实例，二者不同。
    3. ❌ 误认为"容器运行时只有 Docker"。✅ 还有 containerd、CRI-O 等，K8s 支持多种容器运行时（CRI 标准）。

    小结

    Docker 引擎是 C/S 架构：docker CLI（客户端）→ REST API → dockerd（守护进程）→ containerd → runC。理解这个架构，就能理解所有 docker 命令的本质——"客户端发请求，守护进程执行"。

    知识点 K1-5：镜像、容器与仓库

    定义

    Docker 的三大核心概念，几乎所有操作都围绕它们展开：

    概念 定义 类比
    镜像（Image） 只读的模板，包含应用及运行所需的所有内容 面向对象中的"类" / 程序的"安装包"
    容器（Container） 镜像运行起来的实例，可读写 面向对象中的"对象" / 程序的"运行进程"
    仓库（Registry） 存放和分发镜像的地方 应用商店 / 代码托管平台（GitHub for images）

    原理

    三者的关系：

    图示 8：镜像、容器、仓库三者关系

    镜像 Image

    只读模板，可通过 docker run 启动为容器。

    →

    容器 Container

    镜像的运行实例，删除容器不影响镜像。

    本地镜像

    build 生成或 pull 下载

    ↔

    仓库 Registry

    存放镜像，供团队分发

    →

    多处运行

    不同机器，一致环境

    1. 镜像（Image）：

    • 只读的分层结构（Layer），每条 Dockerfile 指令生成一层。
    • 一个镜像可以在底层镜像之上叠加（如 FROM openjdk:17 + 你的应用层）。
    • 通过 镜像名:标签（tag） 标识，如 openjdk:17、mysql:8.0、ctts-backend:v1。
    • 镜像不可变（immutable），改了就生成新镜像（新 tag 或新 ID）。

    2. 容器（Container）：

    • 镜像运行起来就是容器，是一个活的进程。
    • 容器在镜像之上加一层"可写层"（writable layer），所有运行时修改写在这层。
    • 容器停止后可写层仍在（除非删除），可再次启动。
    • 一个镜像可以同时运行多个容器实例（互不干扰）。

    3. 仓库（Registry）：

    • 存放镜像的服务端，类似"镜像的 GitHub"。
    • Docker Hub（hub.docker.com）是 Docker 官方公共仓库，存放大量官方镜像（mysql、nginx、openjdk 等）。
    • 企业可搭建私有仓库（如 Harbor）存放内部镜像。
    • 通过 docker pull 拉取、docker push 推送。

    镜像的分层结构（重要，第 3 次课详讲）：

    图示 9：镜像分层结构与缓存价值
    从下到上叠加
    你的应用代码 + jar（Dockerfile COPY）
    应用依赖：Maven 下载（Dockerfile RUN）
    JDK 17 运行时（FROM openjdk:17）
    Debian 基础系统（基础镜像底层）

    共享

    多个镜像可复用相同基础层。

    缓存

    未变化的层无需重复构建。

    增量传输

    推送和拉取时只传变化层。

    问题 / 场景

    问：镜像和容器到底什么关系？

    • 镜像 = 模板（静态、只读）；容器 = 镜像运行出来的实例（动态、可写）。一个镜像可以跑出多个容器。类比：镜像是"类"，容器是"对象"；镜像是"安装包"，容器是"运行中的程序"。

    问：容器删了，镜像还在吗？

    • 在。容器只是镜像的一个运行实例，删容器不影响镜像。可以再用同一个镜像启动新容器。就像删了"对象"不影响"类"。

    问：为什么要有仓库？直接拷贝镜像文件不行吗？

    • 仓库提供版本管理、权限控制、分发加速。团队协作和 CI/CD 中，代码 push 到 Git，镜像 push 到仓库，部署时从仓库 pull——标准化流程。

    问：镜像名后面的 :v1、:latest 是什么？

    • 是标签（tag），用于标识镜像版本。openjdk:17 表示 openjdk 镜像的 17 版本。不写标签默认 :latest（最新版，但生产中不建议用 latest，因为不可控）。

    完整示例

    镜像/容器/仓库的完整操作流程（命令本节只看流程，第 2~5 次课详讲）： 

    # 1. 从仓库拉取镜像
docker pull mysql:8.0
# 输出示例：
# 8.0: Pulling from library/mysql
# 6ec7b7...: Pull complete
# ...
# Status: Downloaded newer image for mysql:8.0

# 2. 查看本地镜像
docker images
# REPOSITORY   TAG    IMAGE ID      CREATED        SIZE
# mysql        8.0    d1...         2 weeks ago    521MB

# 3. 用镜像运行容器（-d 后台，-p 端口映射，-e 环境变量）
docker run -d --name mydb -p 3306:3306 -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0
# 输出容器ID：a1b2c3d4...

# 4. 查看运行中的容器
docker ps
# CONTAINER ID  IMAGE       STATUS         NAMES
# a1b2c3d4      mysql:8.0   Up 3 seconds   mydb

# 5. 同一个镜像可以再启动一个容器（不同端口）
docker run -d --name mydb2 -p 3307:3306 -e MYSQL_ROOT_PASSWORD=123456 mysql:8.0
# 一个镜像 → 多个容器，互不干扰

# 6. 停止容器（镜像还在）
docker stop mydb
docker rm mydb   # 删除容器（镜像仍在）

# 7. 构建自己的镜像并推送到仓库
docker build -t myname/ctts-backend:v1 .
docker push myname/ctts-backend:v1   # 推送到 Docker Hub

    📌 这些命令是 Docker 的核心操作，第 2~5 次课会逐条详解。本节只需理解"镜像、容器、仓库"三者关系即可。

    图示 10：镜像从仓库到本地，再运行成多个容器

    关键：镜像是静态只读模板；容器是临时运行实例；仓库负责镜像分发。

    易错点

    1. ❌ 混淆镜像和容器。✅ 镜像是静态只读模板，容器是动态可写运行实例。
    2. ❌ 误认为"删了容器镜像就没了"。✅ 容器只是镜像的实例，删容器不影响镜像。
    3. ❌ 误认为"latest 标签就是最新的最稳定的"。✅ latest 只是默认标签名，可能指向任意版本，生产环境应指定明确版本号。
    4. ❌ 误认为"镜像必须从仓库下载"。✅ 镜像也可以本地用 Dockerfile build 出来，仓库只是分发手段。

    小结

    镜像、容器、仓库是 Docker 三大核心概念：镜像是只读模板，容器是镜像的运行实例，仓库用于存储和分发镜像。理解三者关系是理解所有 Docker 操作的基础。

    知识点 K1-6：云原生生态与课程项目导入

    定义

    云原生（Cloud Native） 是一种构建和运行应用程序的方法，利用云计算的弹性、分布式特性，通过容器、微服务、不可变基础设施、声明式 API 等技术，让应用更易于弹性伸缩、可靠运维。

    CNCF（Cloud Native Computing Foundation，云原生计算基金会） 是 Linux 基金会下的子基金会，托管 Kubernetes、containerd、Prometheus 等云原生核心项目，是云原生生态的 governing body。

    原理

    云原生技术栈全景：

    图示 11：云原生技术栈分层
    应用层：微服务 / Serverless / Service Mesh
    编排调度层：Kubernetes（核心）
    容器运行时层：Docker / containerd / runC
    基础设施层：物理机 / 虚拟机 / 公有云
    Docker 解决“装箱和运行”，Kubernetes 解决“集群调度和治理”，共同组成云原生落地链路。

    Docker 与 Kubernetes 的关系：

    维度 Docker Kubernetes
    定位 容器化平台（单机） 容器编排平台（集群）
    解决问题 怎么把应用打包成容器、怎么在单机运行 怎么管理成百上千个容器、怎么调度、怎么高可用
    关系 Docker 是基础（把应用容器化） K8s 建立在容器之上（编排管理容器）

    一句话理解：Docker 把应用装进"集装箱"，Kubernetes 是管理这些集装箱的"码头调度系统"。

    本课程定位：前 12 次课学 Docker（装箱），后 12 次课学 K8s（调度）。

    问题 / 场景

    问：为什么容器化还不够，还要 K8s？

    • 单机 Docker 能跑几十个容器，但生产环境是几十台机器、成千上万个容器。需要解决：哪个容器跑在哪台机器、某台机器挂了容器怎么迁移、流量怎么分发、怎么自动扩缩容。这些是 K8s 的工作。类比：Docker 是"造集装箱"，K8s 是"码头+物流调度系统"。

    问：云原生就是用容器和 K8s 吗？

    • 不完全是。云原生是一套方法论，容器和 K8s 是其核心技术，还包括：微服务、DevOps、CI/CD、不可变基础设施、声明式 API、Service Mesh 等。容器和 K8s 是云原生的基础底座。

    问：国产云原生技术有哪些？

    • 华为云 CCE、阿里云 ACK、腾讯云 TKE；开源项目有 KubeSphere（青云）、OpenAtom OpenHarmony 相关等。容器运行时 containerd 是 CNCF 毕业项目，被广泛采用。这正是"自主可控"的体现。
