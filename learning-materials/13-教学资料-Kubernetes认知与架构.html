这是《Docker 云容器与管理技术》的第 13 次课，是 K8s 部分（后 12 次课）的开篇认知课，也是课程前后半的转折点。前 12 次课你已经学会了用 Docker 把应用容器化、用 Compose 编排多服务；从本节课开始，我们要进入"集群编排"的世界——Kubernetes。

  • 我们的 CTTS 项目为什么要从 Docker 部署升级到 K8s 部署？

二、知识点详解

知识点 K13-1：什么是 Kubernetes

定义

Kubernetes（简称 K8s，因为 K 和 s 之间有 8 个字母）是一个开源的容器编排平台，用于自动化部署、扩展和管理容器化应用。它最初由 Google 基于内部 Borg 系统的设计经验开源，2014 年捐给 CNCF，现在是云原生生态的核心项目。

容器编排（Container Orchestration） 是指对集群中成百上千个容器进行自动化调度、扩缩容、故障恢复、滚动更新等管理工作的技术与系统。

一句话理解 K8s 的定位：

K8s 是云原生时代的"操作系统"，它把整个数据中心当成一台计算机来管理。

原理

为什么需要容器编排？

Docker 把应用装进了"集装箱"，但生产环境远不止一个集装箱：

图示 1：开发/测试环境（前 12 次课）：
开发/测试

一台机器 + Docker Compose

前 12 次课中，CTTS 用 mysql、backend、frontend 三到五个容器就能完成本地运行和联调。

  • 服务数量少
  • 部署目标单一
  • 手动启动和排查仍可接受
生产规模

多台机器 + 成百上千个容器

用户量增长后，问题从“能不能启动”变成“能不能自动调度、恢复和扩容”。

  • 容器该跑在哪台机器
  • 机器宕机后如何自愈
  • 流量突增时如何弹性扩容

调度

根据资源和规则选择合适节点。

自愈

机器或容器异常时自动重建。

弹性

根据负载扩缩副本数量。

滚动更新

升级过程中尽量不中断访问。

服务发现

服务之间用稳定入口互相访问。

声明式 API

用 YAML 描述期望状态，让平台持续维护。

这些问题 Docker Compose 解决不了，需要"容器编排系统"——K8s 就是事实标准。

Docker Compose 的四大局限性（K8s 要解决的核心问题）：

局限 说明 K8s 如何解决
① 单机局限 Compose 只能在单台机器上编排容器，跨机器无能为力 K8s 管理多节点集群，Pod 可调度到任意节点
② 无自愈 容器挂了 Compose 不会自动重启（除非加 restart 策略，且机器挂了完全没救） K8s 的控制器持续监控，Pod 挂了自动重建，节点挂了自动迁移
③ 无弹性 不能根据负载自动扩缩容，副本数写死在 yml 里 K8s 的 HPA（HorizontalPodAutoscaler）根据 CPU/内存自动扩缩容
④ 无滚动更新 更新镜像要手动停旧启新，会中断服务 K8s Deployment 支持滚动更新与回滚，零停机

问题 / 场景

问：有了 Docker Compose，为什么还要 K8s？

  • Compose 解决的是"单机上多个容器怎么一起启动"，K8s 解决的是"集群上成百上千个容器怎么调度、自愈、扩缩容、滚动更新"。二者不是替代，而是规模递进：开发/小规模用 Compose，生产/大规模用 K8s。

问：K8s 是 Google 的吗？

  • K8s 最初由 Google 开源（基于内部 Borg 系统经验），2014 年捐给 CNCF。现在是 CNCF 托管的开源项目，由社区共同维护，不属于任何一家公司。Google、微软、阿里、华为等都是核心贡献者。

问：K8s 只能编排 Docker 容器吗？

  • 不是。K8s 通过 CRI（Container Runtime Interface）标准支持多种容器运行时：containerd、CRI-O、Docker（已弃用 dockershim，但仍可通过 containerd 兼容）。K8s 编排的是"容器"，不是"Docker 容器"。

问：K8s 难学吗？

  • K8s 概念多、组件多、YAML 长，初学者确实有门槛。但它的核心思想是"声明式"——你描述"我想要 3 个后端副本"，K8s 帮你达到并维持这个状态。理解了声明式思维，后续就顺了。本课程后 12 次课会逐步带你掌握。

完整示例

CTTS 项目从 Docker 到 K8s 的演进对比（伪代码描述，说明问题即可，本节不执行）：

【第 11 次课成果：Docker Compose 部署 CTTS】
docker-compose.yml（单机）：
  services:
    mysql:    ...  ← 1 个 MySQL 容器
    backend:  ...  ← 1 个后端容器
    frontend: ...  ← 1 个前端容器
执行：docker compose up -d
结果：3 个容器跑在同一台机器上

问题：
- 机器挂了 → 全部服务不可用
- 后端扛不住 → 不能自动加副本
- 更新后端 → 要停服务再启
- 流量上来 → 一台机器扛不住

【第 13~24 次课目标：K8s 部署 CTTS】
K8s 集群（3 台机器）：
  - Master：管理节点
  - Node1、Node2：工作节点

K8s 资源清单（声明式 YAML）：
  - Deployment backend（replicas: 3）  ← 3 个后端副本，自动调度到不同节点
  - Deployment frontend（replicas: 2） ← 2 个前端副本
  - StatefulSet mysql（replicas: 1）+ PVC ← MySQL 持久化
  - Service × 3 + Ingress               ← 统一访问入口
  - ConfigMap + Secret                  ← 配置与密码分离

执行：kubectl apply -f ctts.yaml
结果：
- 3 个后端副本分布在 Node1、Node2，Node1 挂了自动迁移到 Node2
- 流量增加 → HPA 自动扩到 5 副本
- 更新后端 → 滚动更新，零停机
- 比单机 Compose 强太多

📌 这个对比体现了 K8s 的核心价值：从"单机手动编排"到"集群自动调度"。具体 K8s YAML 在第 15~23 次课逐步学习。

易错点

  1. ❌ 误认为"K8s = 升级版 Docker"。✅ K8s 不是 Docker 的升级，二者定位不同：Docker 是容器化平台（装箱），K8s 是容器编排平台（调度），K8s 建立在容器（如 containerd/Docker 产物）之上。
  2. ❌ 误认为"K8s 取代 Docker"。✅ K8s 不取代 Docker，K8s 编排的是"容器"，容器运行时可以是 containerd 或 Docker（产物）。K8s 取代的是"手动运维"。
  3. ❌ 误认为"Docker Compose 没用了"。✅ Compose 在本地开发、CI 测试、小规模部署仍然非常好用，K8s 适合生产大规模。二者并存。
  4. ❌ 误认为"K8s 只能编排 Docker 容器"。✅ K8s 通过 CRI 支持多种容器运行时（containerd、CRI-O 等），不只 Docker。

小结

Kubernetes（K8s）是开源的容器编排平台，解决"集群中成百上千容器的调度、自愈、弹性、滚动更新"问题。Docker Compose 在单机多容器场景够用，但生产环境需要 K8s 做集群编排。K8s 是云原生时代的"操作系统"，是后 12 次课的核心。

知识点 K13-2：K8s vs Docker Compose 对比

定义

Docker Compose 是 Docker 官方的单机多容器编排工具，通过 docker-compose.yml 描述服务、网络、存储，一键启动/停止一组容器。

Kubernetes 是跨机器的集群级容器编排平台，通过声明式 YAML 描述"期望状态"，由集群自动调度、维护。

原理

核心区别：

对比维度 Docker Compose Kubernetes
规模 单机（一台机器） 集群（多台机器，几十~几千节点）
编排方式 手动编排（写死服务定义） 自动调度（声明期望状态，集群自动分配）
调度 不调度，容器就在执行命令的机器上 scheduler 自动选择最合适的节点运行 Pod
自愈 restart 策略可重启容器，但机器挂了没救 控制器持续监控，Pod 挂了重建，节点挂了迁移
弹性扩缩容 不支持自动扩缩容（手动改 replicas 重启） HPA 根据 CPU/内存自动扩缩容
滚动更新 不支持原生滚动更新（需手动停旧启新） Deployment 原生支持滚动更新与回滚
服务发现 通过容器名 + 自定义网络 通过 Service + CoreDNS 自动发现
负载均衡 不提供（需自己加 Nginx） Service 内置负载均衡（kube-proxy）
配置管理 environment/env_file ConfigMap + Secret，支持热更新
存储管理 volumes（绑定挂载/数据卷） PV/PVC/StorageClass，集群级持久化
外部访问 ports 端口映射 Service NodePort/LoadBalancer + Ingress 七层路由
资源限制 deploy.resources（v2 支持但有限） resources requests/limits，调度依据
学习曲线 简单（一个 yml 文件） 陡峭（概念多、YAML 长、组件多）
适用场景 本地开发、CI 测试、小规模部署 生产环境、大规模、高可用

问题 / 场景

问：什么时候用 Docker Compose？什么时候用 K8s？

场景                              推荐        理由
────────────────────────────────────────────────────────────────────
本地开发联调（前端+后端+MySQL）    Compose    简单、启动快、单机够用
个人博客/小型网站部署             Compose    流量小、单机够用、运维简单
CI 流水线测试环境                 Compose    每次构建启动一组容器，快
企业级应用（用户上万）            K8s        多副本、自愈、弹性、滚动更新
金融/电商生产系统（高可用）       K8s        不能停机、需要故障自动迁移
微服务架构（几十个服务）          K8s        服务发现、负载均衡、统一管理
跨地域多机房部署                  K8s        多集群联邦、统一编排

判断原则：

  • 机器数 ≥ 2 且需要高可用 → K8s
  • 容器数 ≥ 10 且需要弹性 → K8s
  • 单机够用、追求简单 → Compose
  • 开发/测试环境 → Compose
  • 生产环境 → K8s

问：学 K8s 是不是要抛弃 Compose？

  • 不是。Compose 在本地开发、CI 测试场景仍然是首选。很多公司的工作流：开发用 Compose 联调，测试环境用 Compose 或 K8s，生产环境用 K8s。Compose 和 K8s 各有所长。

问：能不能从 Compose 平滑迁移到 K8s？

  • 可以。工具有 Kompose（kompose.io）能把 docker-compose.yml 转成 K8s YAML。但生产迁移不是简单转换，需要重新设计 Deployment/Service/ConfigMap 等。本课程第 23 次课会做 CTTS 的完整 K8s 部署。

完整示例

同一个 CTTS 后端服务，在 Compose 与 K8s 中的描述对比（本节只看差异，命令后续详讲）：

# Docker Compose 描述（单机，第 11 次课）
services:
  backend:
    image: ctts-backend:v1
    ports:
      - "8080:8080"
    depends_on:
      - mysql
    environment:
      - SPRING_DATASOURCE_URL=jdbc:mysql://mysql:3306/ctts
    restart: unless-stopped
# 局限：只有 1 个副本，机器挂了就没了，不能扩容，不能滚动更新

---
# K8s Deployment 描述（集群，第 16 次课详讲）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-backend
spec:
  replicas: 3                # 3 个副本，自动调度到不同节点
  selector:
    matchLabels:
      app: ctts-backend
  template:
    metadata:
      labels:
        app: ctts-backend
    spec:
      containers:
      - name: backend
        image: ctts-backend:v1
        ports:
        - containerPort: 8080
        env:
        - name: SPRING_DATASOURCE_URL
          value: jdbc:mysql://ctts-mysql:3306/ctts
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi
# 优势：3 副本高可用、自动调度、资源限制、滚动更新、自愈

📌 对比可见：K8s 的 YAML 更长，但表达力更强——声明"我要 3 个副本"，集群自动帮你维持。这就是声明式的力量。

图示

图示 3：Compose vs K8s 规模对比：
Docker Compose

单机编排

一台机器上启动 DB、Backend、Frontend，适合开发、教学和小规模验证。

  • 机器故障就是整体故障
  • 扩容更多依赖人工复制
  • 缺少跨节点调度和自愈
Kubernetes

集群编排

控制平面管理多个 Node，Pod 可被调度到不同机器上运行。

  • 多副本分散到多节点
  • 故障后自动补 Pod
  • 统一支持弹性、滚动更新和服务发现
Compose 管的是“这台机器上的几个容器”，K8s 管的是“整个集群中应该保持什么状态”。

易错点

  1. ❌ 误认为"K8s 是 Compose 的升级版，用法一样"。✅ 二者模型不同：Compose 是"启动这组容器"，K8s 是"维持这个期望状态"。声明式 vs 命令式。
  2. ❌ 误认为"小项目也必须用 K8s"。✅ 小项目用 Compose 足够，K8s 有运维成本，过度设计是问题。
  3. ❌ 误认为"Compose 完全没价值了"。✅ Compose 在本地开发、CI 测试场景仍是首选。
  4. ❌ 误认为"K8s 比 Compose 难就一定更好"。✅ 技术选型看场景，合适的才是最好的。

小结

Docker Compose 适合单机多容器编排（开发、测试、小规模部署），Kubernetes 适合集群级容器编排（生产、大规模、高可用）。二者不是替代关系，而是规模递进。选型原则：单机够用用 Compose，多机高可用用 K8s。

知识点 K13-3：K8s 整体架构

定义

Kubernetes 采用 Master-Node 架构（也叫控制平面-工作节点架构）：

  • Master（控制平面，Control Plane）：集群的"大脑"，负责管理集群状态、调度决策、故障检测。可以有多个 Master 做高可用（本课程以单 Master 为例）。
  • Node（工作节点，Worker Node）：集群的"手脚"，负责实际运行容器（Pod）。一个集群通常有多个 Node。

原理

K8s 集群整体架构图：

图示 4：Kubernetes 集群

用户入口

kubectl / YAML

提交期望状态。

→

API Server

所有操作的统一入口。

Control Plane

Master：决策大脑

API Server

认证、授权、准入、校验。

etcd

保存集群状态，是事实来源。

scheduler

决定 Pod 跑到哪个 Node。

controller-manager

持续调和期望状态和实际状态。

Worker Nodes

Node：业务执行

kubelet

管理本节点 Pod 生命周期。

kube-proxy

维护 Service 转发规则。

container-runtime

通过 containerd/runC 运行容器。

Pods

真正承载业务容器。

核心数据流（以 kubectl create deployment 为例）：

1. 用户：kubectl create -f deployment.yaml
2. kubectl → API Server：提交请求
3. API Server：把"期望状态（3 副本）"写入 etcd
4. controller-manager：监听到有新 Deployment，创建 ReplicaSet，再创建 Pod（但 Pod 还没分配节点）
5. scheduler：监听到有未调度的 Pod，根据资源/规则选择一个 Node，把 Pod 与 Node 的绑定信息写回 API Server → etcd
6. 目标 Node 上的 kubelet：监听到自己被分配了 Pod，调用 container-runtime 拉镜像、启容器
7. kubelet：持续上报 Pod 状态给 API Server → etcd
8. kube-proxy：为 Service 配置网络规则（iptables/ipvs），让流量能路由到 Pod

Master 与 Node 的关系：

维度 Master（控制平面） Node（工作节点）
角色 大脑（决策） 手脚（执行）
数量 通常 1 个（生产 3 个高可用） 几个~几千个
是否跑业务容器 一般不跑（ tainted） 跑业务 Pod
核心组件 API Server、etcd、scheduler、controller-manager kubelet、kube-proxy、container-runtime
故障影响 Master 挂了集群不能变更（但已运行的 Pod 仍工作） Node 挂了上面的 Pod 由控制器迁移

问题 / 场景

问：Master 挂了，集群就崩溃吗？

  • 不完全。Master 挂了，已运行的 Pod 仍在 Node 上跑，业务不中断。但不能做新操作（创建/删除/扩缩容）。生产环境用 3 个 Master 做高可用，单 Master 挂了另外两个接管。

问：一个 Node 上能跑多少 Pod？

  • 取决于 Node 的资源（CPU/内存）和 Pod 的资源请求。一台 4 核 8G 的 Node 通常能跑 10~30 个普通 Pod。K8s 调度器会根据资源自动分配。

问：Master 和 Node 必须是不同机器吗？

  • 学习环境（如 Minikube）单机版 Master 和 Node 在同一台机器。生产环境建议分离，Master 专门做管理，Node 专门跑业务。本课程第 14 次课用 Minikube 单机学习，生产用 kubeadm 多节点。

问：Master 上的组件必须都在一台机器吗？

  • 不必。生产环境可拆分：etcd 单独集群（3~5 节点）、API Server 多副本负载均衡。学习环境都跑一起即可。

知识点 K13-4：Master 控制平面组件

定义

Master（控制平面）包含四大核心组件：

组件 名称 一句话职责
kube-apiserver API Server 集群统一入口，所有组件与用户都通过它通信
etcd 键值存储 集群的"数据库"，保存集群所有状态数据
kube-scheduler 调度器 决定新 Pod 跑在哪个 Node 上
kube-controller-manager 控制器管理器 运行各种控制器，持续让"实际状态"趋近"期望状态"

原理

1. API Server（kube-apiserver）— 集群唯一入口

图示 6：所有操作都经过 API Server：

API Server 是集群唯一门面

kubectl

用户提交 apply、get、delete 等请求。

scheduler

监听未调度 Pod，写回绑定结果。

controller

观察资源变化，发起调和操作。

kubelet

接收本节点任务，上报 Pod 与 Node 状态。

API Server

RESTful API、认证、授权、准入、校验。

→

etcd

只有 API Server 直接读写 etcd，其他组件都间接访问。

2. etcd — 集群状态存储

etcd 是什么：
  - 分布式键值（KV）存储数据库
  - 使用 Raft 协议保证一致性
  - K8s 集群所有状态都存在这里：Pod/Service/Deployment/ConfigMap...

存什么：
  - 期望状态：用户通过 kubectl 提交的"我想要 3 个副本"
  - 实际状态：kubelet 上报的"现在 Node1 上有 2 个，Node2 上有 1 个"

特点：
  - 强一致性（Raft）
  - 生产环境部署 3 或 5 节点集群
  - K8s 的"真相之源"（source of truth）

3. scheduler（kube-scheduler）— 调度器

图示 7：scheduler 的职责：

发现未调度 Pod

监听 API Server，找到尚未指定 Node 的 Pod。

过滤可用节点

检查 CPU、内存、节点标签、污点与容忍等硬性条件。

评分选择节点

结合亲和性、资源余量和策略，为候选 Node 打分。

写回绑定结果

把 Pod → Node 的绑定写回 API Server，再由目标 kubelet 执行启动。

scheduler 只负责“决定跑哪”；真正拉镜像、启动容器的是目标 Node 上的 kubelet。

4. controller-manager（kube-controller-manager）— 控制器管理器

图示 8：controller-manager 是什么：

观察实际状态

例如当前只有 2 个 Pod、某个 Node 失联。

读取期望状态

例如 Deployment 声明 replicas: 3。

发现偏差

实际状态和期望状态不一致，就生成修复动作。

持续调和

创建、删除或更新资源，让集群回到期望状态。

Deployment Controller

管理 Deployment 与 ReplicaSet。

ReplicaSet Controller

维持 Pod 副本数。

Node Controller

监控节点健康。

Endpoint Controller

维护 Service 到 Pod 的映射。

controller-manager 的核心不是一次性执行命令，而是不断循环：观察、比较、修复、再观察。

问题 / 场景

问：为什么所有组件都通过 API Server 通信，不直接连？

  • 解耦 + 安全。所有操作经过 API Server，可以做认证授权审计。组件之间不直接连接，便于横向扩展（API Server 可多副本）。etcd 只对 API Server 开放，保护"真相之源"。

问：etcd 挂了会怎样？

  • etcd 是 K8s 的"真相之源"，挂了集群无法知道当前状态，无法做任何变更。但已运行的 Pod 仍工作（kubelet 还在 Node 上）。生产环境 etcd 部署 3/5 节点高可用。

问：scheduler 挂了会怎样？

  • 新 Pod 无法被调度（卡在 Pending），但已运行的 Pod 不受影响。多 Master 时 scheduler 多副本，靠 leader election 选主。

问：controller-manager 中的"调和循环"是什么意思？

  • 持续循环："我期望 3 副本，实际几个？少了就加，多了就删"。这种"观察-对比-操作"的循环叫 reconcile loop，是 K8s 声明式模型的核心。系统会持续逼近用户声明的期望状态。

完整示例

以部署 CTTS 后端 3 副本为例，四大组件的协作流程（伪流程，说明原理）：

用户操作：kubectl apply -f ctts-backend-deployment.yaml（replicas: 3）

协作流程：
1. API Server 收到请求
   - 认证：验证用户身份
   - 授权：检查用户能否创建 Deployment
   - 准入：校验 YAML 格式与策略
   - 通过 → 把 Deployment 对象写入 etcd

2. controller-manager 的 Deployment Controller 监听到新 Deployment
   - 创建一个 ReplicaSet（rs-abc123）
   - ReplicaSet Controller 监听到新 RS，期望 3 副本
   - 当前 0 个 → 创建 3 个 Pod 对象（Pod 还没分配 Node）
   - Pod 对象写入 etcd（状态：Pending）

3. scheduler 监听到有 3 个 Pending 的 Pod
   - 对每个 Pod 跑调度算法：
     Pod1 → 选 Node1（资源够、负载低）
     Pod2 → 选 Node2（资源够、与 Pod1 反亲和）
     Pod3 → 选 Node2（资源够）
   - 把绑定信息写回 API Server → etcd

4. Node1 的 kubelet 监听到自己被分了 Pod1
   - 调用 container-runtime 拉镜像、启容器
   - 上报状态：Pending → Running
   Node2 的 kubelet 同理处理 Pod2、Pod3

5. 持续监控（reconcile loop）
   - 如果 Node2 挂了，Node Controller 上报
   - ReplicaSet Controller 发现实际只剩 1 副本，期望 3
   - 再创建 2 个新 Pod，scheduler 重新调度到 Node1
   → 最终稳定在 3 副本

📌 这个流程体现了 K8s 的"声明式 + 控制循环"核心设计：你声明"3 副本"，K8s 持续维持这个状态。

易错点

  1. ❌ 误认为"scheduler 启动容器"。✅ scheduler 只"决定"Pod 跑在哪个 Node，真正启动容器的是该 Node 上的 kubelet。
  2. ❌ 误认为"etcd 是 MySQL 那种数据库"。✅ etcd 是分布式键值存储（KV），不是关系型数据库。
  3. ❌ 误认为"controller-manager 只有一个控制器"。✅ 它是多种控制器的集合（Deployment/ReplicaSet/Node/Endpoint 等）。
  4. ❌ 误认为"组件之间直接互相调用"。✅ 所有组件都只跟 API Server 通信，不直接互联。
  5. ❌ 误认为"API Server 直接启动 Pod"。✅ API Server 只负责接收请求和存状态，启动 Pod 由 kubelet 在 Node 上执行。

小结

Master 控制平面四大组件：API Server（唯一入口，认证授权）、etcd（键值存储，集群状态）、scheduler（调度 Pod 到 Node）、controller-manager（多种控制器，维持期望状态）。组件之间通过 API Server 通信，状态存在 etcd，scheduler 决策调度，controller 持续调和。

知识点 K13-5：Node 工作节点组件

定义

Node（工作节点）包含三大核心组件：

组件 名称 一句话职责
kubelet 节点代理 管理本节点上的 Pod 生命周期，与 API Server 通信
kube-proxy 网络代理 维护 Service 的网络规则，实现服务发现与负载均衡
container-runtime 容器运行时 真正运行容器的引擎（containerd/CRI-O/Docker）

原理

1. kubelet — 节点代理

图示 10：kubelet 是什么：

每个 Node 一个 kubelet：Master 在节点上的执行代表

监听任务

从 API Server 获取分配到本节点的 Pod。

调用运行时

通过 CRI 调用 containerd 拉镜像、启停容器。

健康检查

执行 livenessProbe、readinessProbe 等探针。

上报状态

持续向 API Server 汇报 Pod 与 Node 状态。

kubelet 是 K8s 和容器运行时之间的桥：它接收集群决策，并在本机把 Pod 真正跑起来。

2. kube-proxy — 网络代理

图示 11：kube-proxy 是什么：

每个 Node 上的 Service 网络代理

kube-proxy 监听 Service 与 Endpoints 的变化，并把“访问 Service VIP”这件事翻译成节点本地的转发规则。

监听变化

持续观察 Service 和 Endpoints。

写入规则

在 Node 上维护 iptables/ipvs。

完成转发

把 Service VIP 流量分发到后端 Pod。

访问 10.96.0.10:8080

Service ctts-backend 的虚拟入口。

→

kube-proxy 规则

在每个 Node 上生效，执行负载均衡。

→

Pod1 / Pod2 / Pod3

流量轮询到真实后端。

3. container-runtime — 容器运行时

图示 12：container-runtime 是什么：

kubelet

根据 PodSpec 发起创建、停止、探测等容器操作。

CRI

Container Runtime Interface，K8s 连接运行时的标准接口。

containerd

负责镜像拉取、容器生命周期管理，是当前常用运行时。

runC / 进程

最终创建 Linux 容器进程，让业务容器真正运行。

Docker 镜像仍可运行

Docker 构建出的镜像符合 OCI 标准，可由 containerd 拉取和运行。

Docker Engine 不再直连

K8s 1.24 起移除 dockershim，不再原生直连 Docker Engine。

问题 / 场景

问：kubelet 和 docker daemon 什么关系？

  • kubelet 不直接调 docker daemon，而是通过 CRI 调 container-runtime（可能是 containerd 或 CRI-O）。早期 K8s 通过 dockershim 支持 Docker Engine，1.24 起移除。但 Docker 构建的镜像（OCI 格式）仍能在 containerd 上跑。

问：kube-proxy 是不是负载均衡器？

  • 是一种"内核态负载均衡"。它通过 iptables/ipvs 规则在内核层做流量转发，比应用层 LB（如 Nginx）更高效。但只做四层（TCP/UDP），七层（HTTP 路由）需要 Ingress。

问：为什么 K8s 不再用 Docker Engine 了？

  • Docker Engine 不是为 K8s 设计的，多了一层 dockershim 适配，复杂且易出问题。containerd 是 Docker 捐给 CNCF 的运行时，更精简、专注。K8s 1.24 移除 dockershim，直接用 containerd。注意：镜像还是用 Docker build，只是 K8s 跑容器不再用 Docker Engine。

问：每个 Node 都要装这三个组件吗？

  • 是。每个 Node 都装 kubelet + kube-proxy + container-runtime，这样 Master 才能管理这个 Node 上的 Pod。

完整示例

以 CTTS 后端 Pod 部署到 Node1 为例，三大组件协作流程（伪流程）：

scheduler 决定把 ctts-backend Pod 调度到 Node1 →

Node1 上的协作：

1. kubelet 监听 API Server，发现 Node1 被分了新 Pod
   - 读取 Pod 规格：image=ctts-backend:v1, port=8080
   - 调用 container-runtime 的 CRI 接口：
     "拉取 ctts-backend:v1 镜像，启动容器"

2. container-runtime（containerd）执行：
   - 检查本地是否有 ctts-backend:v1
   - 没有则从仓库拉取
   - 调用 runC 创建容器进程
   - 容器跑起来

3. kubelet 持续监控：
   - 执行 livenessProbe（如 curl http://localhost:8080/health）
   - 执行 readinessProbe（如检查端口是否通）
   - 上报状态给 API Server：Pending → Running

4. kube-proxy 监听到 Service ctts-backend 关联了 Node1 上的 Pod
   - 在 Node1 上写 iptables 规则：
     访问 Service VIP:8080 → 可路由到本节点 Pod
   - 同样在其他 Node 上也写规则
   - 这样任何 Pod 访问 ctts-backend 都能命中

5. 持续运行：
   - kubelet 每隔几秒上报状态
   - Pod 挂了 → kubelet 重启（按 restartPolicy）
   - 节点资源不足 → kubelet 上报，scheduler 不再调度新 Pod 到这

易错点

  1. ❌ 误认为"kubelet 跑在 Master 上"。✅ kubelet 跑在每个 Node 上，是 Node 的代理。Master 上也可能跑 kubelet（用于静态 Pod 运行控制平面组件本身），但本课程理解为 Node 组件。
  2. ❌ 误认为"kube-proxy 做七层负载均衡"。✅ kube-proxy 做四层（TCP/UDP）负载均衡（iptables/ipvs），七层（HTTP 路由）由 Ingress 做。
  3. ❌ 误认为"K8s 1.24+ 不能用 Docker 镜像了"。✅ K8s 不再原生支持 Docker Engine（移除 dockershim），但 Docker 构建的镜像（OCI 格式）仍能在 containerd 上正常运行。
  4. ❌ 误认为"kubelet 直接调 docker daemon"。✅ kubelet 通过 CRI 调 container-runtime（通常是 containerd），不直接连 Docker。
  5. ❌ 误认为"Node 只跑业务 Pod，不跑 K8s 组件"。✅ Node 上跑 kubelet、kube-proxy、container-runtime，它们是 K8s 组件，不是业务 Pod。

小结

Node 工作节点三大组件：kubelet（节点代理，管 Pod 生命周期）、kube-proxy（网络代理，管 Service 流量规则）、container-runtime（容器运行时，真正跑容器，通常是 containerd）。每个 Node 都装这三个组件，由 Master 通过 API Server 统一管理。

知识点 K13-6：K8s 核心概念总览

定义

K8s 有很多资源对象（Resource Objects），本节做"概念总览"，每个概念用一句话简介，并标注后续哪次课详讲。本节不要求深入掌握，只要建立"K8s 有哪些核心资源"的全局认知。

原理

K8s 核心资源一览表：

资源 一句话概念 类比 详讲次课
Pod K8s 最小调度单元，包含一个或多个紧密协作的容器 一个"小盒子"装 1~N 个容器 第 15 次
Deployment 管理 Pod 副本，支持滚动更新与回滚 Pod 的"指挥官" 第 16 次
ReplicaSet 维持 Pod 副本数（Deployment 内部用） Pod 的"保镖" 第 16 次
Service 为一组 Pod 提供稳定访问入口（IP+DNS）+ 负载均衡 Pod 的"前台" 第 18 次
Ingress 七层路由（HTTP/HTTPS），把域名/路径映射到 Service 集群的"Nginx" 第 19 次
ConfigMap 存储非敏感配置（key-value），可挂载为环境变量或文件 配置文件 第 21 次
Secret 存储敏感信息（密码/密钥），base64 编码 加密保险箱 第 21 次
PV（PersistentVolume） 集群级持久化存储资源 集群的"硬盘" 第 22 次
PVC（PersistentVolumeClaim） 用户对存储的申请 "我要 10G 硬盘" 第 22 次
StorageClass 动态创建 PV 的模板 存储的"工厂" 第 22 次
Namespace 集群内的虚拟集群，资源隔离 集群的"房间" 贯穿
Label/Selector 资源标签与选择器，关联资源 资源的"标签贴纸" 第 16 次
StatefulSet 管理有状态应用（如 MySQL），Pod 有序、稳定 有状态 Pod 指挥官 拓展
DaemonSet 每个节点跑一个副本（如日志收集） 节点级 Pod 拓展
Job/CronJob 一次性/定时任务 K8s 的"crontab" 拓展
HPA 根据负载自动扩缩容 Pod 的"调速器" 拓展

问题 / 场景

问：为什么 K8s 这么多概念？

  • K8s 把"运维"工程化了——每种运维需求都对应一个资源对象：扩缩容 → Deployment，访问入口 → Service，配置 → ConfigMap，密码 → Secret，存储 → PV/PVC。看起来多，但每个职责清晰，组合起来能解决几乎所有运维场景。

问：Pod 和容器什么关系？为什么不是直接管容器？

  • K8s 不直接管容器，管的是 Pod。Pod 是"一个或多个紧密协作的容器组合"，共享网络与存储。这样设计是因为有些应用天然是"多容器协作"（如主容器 + sidecar 日志收集）。Pod 是最小调度单元。

问：CTTS 部署到 K8s 需要哪些资源？

  • 见下方综合示例，大约：3 个 Deployment/StatefulSet + 3 个 Service + 1 个 ConfigMap + 1 个 Secret + 1 个 PVC + 1 个 Ingress。后续 11 次课逐步学完。

易错点

  1. ❌ 误认为"K8s 直接管容器"。✅ K8s 管的是 Pod，Pod 是最小调度单元，容器在 Pod 内。
  2. ❌ 误认为"Deployment = Pod"。✅ Deployment 管理 Pod（通过 ReplicaSet），不是同一个东西。Deployment 是控制器，Pod 是被管理的实例。
  3. ❌ 误认为"Secret 是加密的"。✅ Secret 是 base64 编码（不是加密），生产环境需配合 RBAC 限制访问，或用外部密钥管理（如 Vault）。
  4. ❌ 误认为"PV 是 K8s 内置存储"。✅ PV 是对接外部存储（NFS/Ceph/云盘）的抽象，K8s 自己不存数据。

小结

K8s 核心资源：Pod（最小调度单元）、Deployment（副本管理与滚动更新）、Service（访问入口与负载均衡）、Ingress（七层路由）、ConfigMap/Secret（配置与密码）、PV/PVC/StorageClass（持久化存储）、Namespace（资源隔离）。本节只做总览，后续 11 次课会逐一详讲。

四、拓展阅读（选学）

  1. K8s 起源 — Borg 系统：K8s 的设计思想源于 Google 内部的 Borg 系统（2003 年开始），Google 用 Borg 管理内部成千上万的服务。2014 年 Google 开源 K8s，2015 年捐给 CNCF。想深入可读 Borg 论文《Large-scale cluster management at Google with Borg》。

  2. CRI / CNI / CSI 三大接口标准：

    • CRI（Container Runtime Interface）：容器运行时接口，让 K8s 支持 containerd/CRI-O 等多种运行时
    • CNI（Container Network Interface）：容器网络接口，让 K8s 支持 Calico/Flannel 等多种网络插件
    • CSI（Container Storage Interface）：容器存储接口，让 K8s 支持 NFS/Ceph/云盘等多种存储

  3. 声明式 API 与 Reconcile Loop：K8s 的核心设计是"声明式"——你描述期望状态，K8s 持续让实际状态趋近期望状态。每个控制器跑一个 reconcile loop（观察-对比-操作）。这种模式叫"水平触发"而非"边缘触发"，更健壮。

  4. 国产云原生平台：华为云 CCE、阿里云 ACK、腾讯云 TKE、青云 KubeSphere（开源 PaaS，国产化代表），都是基于 K8s 的自主可控平台。KubeSphere 特别适合学习，对 K8s 做了友好封装。

  5. Podman vs Docker：Red Hat 推出的 Podman 是 Docker 的替代品，无守护进程，更安全。但 K8s 生态以 containerd 为主流。了解即可。
