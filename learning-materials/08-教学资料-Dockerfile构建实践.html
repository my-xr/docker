二、知识点详解

知识点 K8-1：CTTS 后端 Dockerfile 编写

定义

CTTS 后端 Dockerfile 是描述如何把 CTTS 后端（SpringBoot 应用）打包成 Docker 镜像的脚本文件，采用多阶段构建：第一阶段用 Maven 镜像编译打包源码产出 jar，第二阶段用 JRE 镜像运行 jar，最终镜像只包含运行所需内容，体积小、安全。

原理

Java 应用容器化的核心矛盾：

图示 1：矛盾：构建时需要 Maven + JDK（几百 MB 工具链）
矛盾：构建时需要 Maven + JDK（几百 MB 工具链）
运行时只需要 JRE + jar（几十 MB）
如果用单阶段构建（FROM maven → COPY 源码 → RUN mvn package → CMD java -jar）：
最终镜像包含 Maven + JDK + 源码 + jar → 镜像 800MB+，含构建工具，不安全
用多阶段构建：
阶段1（builder）：FROM maven → COPY 源码 → RUN mvn package → 产出 jar
阶段2（runtime）：FROM jre → COPY --from=builder jar → CMD java -jar
最终镜像只含 JRE + jar → 镜像 200MB 左右

多阶段构建的关键指令 COPY --from=<阶段名>：从指定的构建阶段复制产物到当前阶段。

问题 / 场景

问：为什么要用 AS builder 给阶段命名？

  • 给构建阶段起名字（如 FROM maven:... AS builder），后面 COPY --from=builder 就能用名字引用，比用数字序号（COPY --from=0）更清晰、更易维护。

问：为什么不直接 COPY 本地构建好的 jar，而要在镜像里构建？

  • 两种方式都可以：
    • 本地构建后 COPY jar：Dockerfile 简单（FROM jre → COPY app.jar → CMD），但要求构建者本地有 Maven 环境，且构建过程不可复现。
    • 镜像内构建（多阶段）：Dockerfile 完整描述构建过程，任何人在任何机器上 docker build 都能得到一致的镜像，符合"镜像即交付物"的理念。生产推荐多阶段构建。

问：后端 jar 监听哪个端口？

  • SpringBoot 默认监听 8080。可在 application.yml 中用 server.port=8080 配置。容器化时通过 EXPOSE 8080 声明端口，运行时用 -p 8080:8080 映射。

2. 编写后端 Dockerfile

在 ctts-backend/Dockerfile 中写入：

# ============================================
# CTTS 后端多阶段构建 Dockerfile
# 阶段1：Maven 构建阶段（产出 jar）
# 阶段2：JRE 运行阶段（运行 jar）
# ============================================

# ---------- 阶段1：构建阶段 ----------
FROM maven:3.9-eclipse-temurin-17 AS builder

# 设置工作目录
WORKDIR /build

# 先单独 COPY pom.xml 并下载依赖（利用层缓存：源码变动时依赖层不重建）
COPY pom.xml .
RUN mvn dependency:go-offline -B

# COPY 源码
COPY src ./src

# 编译打包（跳过测试以加速构建）
RUN mvn clean package -DskipTests -B

# ---------- 阶段2：运行阶段 ----------
FROM eclipse-temurin:17-jre-alpine

# 设置工作目录
WORKDIR /app

# 从构建阶段复制 jar（注意 jar 名要与 pom.xml 中 artifactId-version 对应）
COPY --from=builder /build/target/ctts-backend-1.0.0.jar app.jar

# 声明端口（仅文档作用，运行时仍需 -p 映射）
EXPOSE 8080

# 启动命令
CMD ["java", "-jar", "app.jar"]

易错点

  1. ❌ COPY jar 路径写错：COPY --from=builder /build/target/ctts-backend-1.0.0.jar app.jar 中的 jar 文件名必须与 pom.xml 的 <artifactId>-<version>.jar 一致。✅ 可在构建后用 docker run --rm ctts-backend:v1 ls /app 验证。

  2. ❌ WORKDIR 与 COPY 路径不匹配：阶段1 WORKDIR 是 /build，则 COPY src ./src 复制到 /build/src；阶段2 WORKDIR 是 /app，则 COPY --from=builder /build/target/xxx.jar app.jar 复制到 /app/app.jar。

  3. ❌ 忘记 -DskipTests：不跳过测试会导致构建阶段跑测试，浪费时间且可能因测试环境不具备而失败。生产构建建议加 -DskipTests。

  4. ❌ 基础镜像选错：运行阶段用 eclipse-temurin:17（含完整 JDK，300MB+）而非 eclipse-temurin:17-jre-alpine（仅 JRE，约 170MB）。✅ 运行阶段只用 JRE，且 alpine 版本更小。

  5. ❌ 先 COPY 源码再下载依赖：把 COPY src 放在 RUN mvn dependency 之前，会导致每次源码变动都重新下载依赖。✅ 先 COPY pom.xml 下载依赖，再 COPY 源码，利用层缓存。

小结

CTTS 后端 Dockerfile 采用多阶段构建：阶段1 用 maven:3.9-eclipse-temurin-17 编译打包产出 jar，阶段2 用 eclipse-temurin:17-jre-alpine 运行 jar，最终镜像约 200MB。关键技巧是"先 COPY pom.xml 下载依赖，再 COPY 源码"以利用层缓存。

知识点 K8-2：CTTS 前端 Dockerfile 编写

定义

CTTS 前端 Dockerfile 是描述如何把 CTTS 前端（Vue3 应用）打包成 Docker 镜像的脚本文件，同样采用多阶段构建：第一阶段用 Node 镜像执行 npm install + npm run build 产出静态文件 dist，第二阶段用 Nginx 镜像托管 dist 中的静态资源。

原理

前端应用容器化的核心矛盾：

图示 4：矛盾：构建时需要 Node + npm + 源码 + node_modules（几百 MB ~ 1GB）
矛盾：构建时需要 Node + npm + 源码 + node_modules（几百 MB ~ 1GB）
运行时只需要 Nginx + 静态文件 dist（几十 MB）
单阶段构建（FROM node → npm install → npm run build → CMD nginx）：
最终镜像含 Node + node_modules + 源码 + dist → 1GB+，且含构建工具
多阶段构建：
阶段1（builder）：FROM node → npm install → npm run build → 产出 dist
阶段2（runtime）：FROM nginx → COPY --from=builder dist → html
最终镜像只含 Nginx + dist → 50MB 左右

Nginx 镜像的静态文件目录是 /usr/share/nginx/html，把 dist 内容 COPY 到这里即可。

问题 / 场景

问：为什么前端要用 Nginx 而不是 Node 运行？

  • Vue3 编译后的 dist 是纯静态文件（HTML/CSS/JS），不需要 Node 运行时。Nginx 是高性能静态文件服务器，体积小、并发强，是托管前端构建产物的标准选择。

问：npm install 用 npm ci 还是 npm install？

  • npm ci 更适合 CI/CD 和 Docker 构建：它严格按 package-lock.json 安装，速度更快、可复现性更强，且会先删除 node_modules。✅ Docker 构建中推荐 npm ci。前提是项目里有 package-lock.json。

问：构建产出的 dist 应该 COPY 到哪里？

  • Nginx 镜像默认静态目录是 /usr/share/nginx/html。COPY --from=builder /build/dist /usr/share/nginx/html 把 dist 内容放到这里，Nginx 启动后就能访问。

问：前端如何配置 Nginx 路由（history 模式 / API 代理）？

  • Vue Router 用 history 模式时，刷新页面会 404，需要 Nginx 配置 try_files $uri $uri/ /index.html。API 代理可以在 Nginx 中配置 proxy_pass 转发到后端容器。本节课先用最简配置，API 代理在 K8-4 联调时讲解。

2. 编写前端 Dockerfile

在 ctts-frontend/Dockerfile 中写入：

# ============================================
# CTTS 前端多阶段构建 Dockerfile
# 阶段1：Node 构建阶段（产出 dist 静态文件）
# 阶段2：Nginx 部署阶段（托管 dist）
# ============================================

# ---------- 阶段1：构建阶段 ----------
FROM node:20-alpine AS builder

WORKDIR /build

# 先 COPY package.json 和 lock 文件，再 npm ci（利用层缓存）
COPY package.json package-lock.json* ./
RUN npm ci

# COPY 源码
COPY . .

# 构建产出 dist 目录
RUN npm run build

# ---------- 阶段2：运行阶段 ----------
FROM nginx:alpine

# 从构建阶段复制 dist 到 Nginx 默认静态目录
COPY --from=builder /build/dist /usr/share/nginx/html

# 复制自定义 Nginx 配置（可选，用于 history 路由 + API 代理）
# COPY nginx.conf /etc/nginx/conf.d/default.conf

# 声明端口
EXPOSE 80

# Nginx 镜像默认 CMD 即 nginx -g 'daemon off;'，无需重复指定

3. （可选）Nginx 配置文件 nginx.conf

如果需要 history 路由支持或 API 代理，在 ctts-frontend/nginx.conf 中配置：

server {
    listen 80;
    server_name localhost;

    # 静态文件根目录
    root /usr/share/nginx/html;
    index index.html;

    # Vue Router history 模式支持
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 代理到后端容器（容器名 ctts-api，端口 8080）
    location /api/ {
        proxy_pass http://ctts-api:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

📌 启用此配置需取消 Dockerfile 中 COPY nginx.conf 那行的注释。

易错点

  1. ❌ COPY 上下文包含 node_modules：如果没有 .dockerignore，COPY . . 会把本地 node_modules 也拷进去，既慢又可能与容器内环境不兼容。✅ 必须配置 .dockerignore 排除 node_modules（见 K8-5）。

  2. npm ci 要求有 package-lock.json：如果项目没有 lock 文件，npm ci 会报错。此时可用 npm install 替代，或先在本地 npm install 生成 lock 文件。

  3. ❌ dist 路径写错：Vite 默认输出到 /build/dist，但有的项目配置 outDir 改成别的路径。✅ 可在构建阶段加 RUN ls -la /build/dist 调试确认。

  4. ❌ COPY 到 Nginx 目录路径错误：Nginx 默认静态目录是 /usr/share/nginx/html，不是 /var/www/html（那是 Apache）。✅ 记住 Nginx 用 /usr/share/nginx/html。

  5. ❌ 忘记 history 路由配置：Vue Router 用 history 模式时，刷新 /about 这样的路径会 404，因为 Nginx 找不到对应文件。✅ 需要 nginx.conf 配置 try_files $uri $uri/ /index.html。

小结

知识点 K8-3：镜像构建与标签管理

定义

镜像构建 是用 docker build 命令根据 Dockerfile 生成镜像的过程。标签管理 是用 docker tag 给镜像打标签（如版本号、仓库名），用于标识和分发镜像。

原理

docker build 命令的工作流程：

图示 7：读取 Dockerfile

读取 Dockerfile

把构建上下文（build context，即 PATH 或 URL 指定的目录）打包发给守护进程

按 Dockerfile 指令顺序，逐条执行：

a. 每条指令生成一个新层（layer）

b. 检查是否有可缓存的层（指令相同 + 上下文文件未变 → 复用缓存）

c. 执行指令（RUN/COPY 等）

所有指令执行完，组合成最终镜像

打上 -t 指定的标签

标签命名规范：

<仓库名>/<镜像名>:<标签>
└──────┬──────┘ └──┬──┘ └─┬─┘
       仓库名      镜像名  版本

示例：

  • ctts-backend:v1 —— 本地镜像，标签 v1
  • myname/ctts-backend:v1.0.0 —— Docker Hub 个人仓库
  • registry.example.com/ctts/backend:v1 —— 私有仓库

问题 / 场景

问：docker build -t ctts-backend:v1 . 末尾的 . 是什么？

  • . 是构建上下文（build context），即当前目录。Docker 会把这个目录下的所有文件发送给守护进程，Dockerfile 中的 COPY src ./src 等指令从上下文中复制文件。不是 Dockerfile 的位置（Dockerfile 默认从上下文根目录找）。

问：构建日志里 CACHED 是什么意思？

  • 表示该层命中了缓存，没有重新执行。例如 => [builder 3/5] COPY pom.xml . CACHED 表示 pom.xml 没变，复用上次构建的层。这是构建加速的关键。

问：如何强制不使用缓存？

  • 加 --no-cache 参数：docker build --no-cache -t ctts-backend:v1 .。用于排查缓存导致的构建问题，或确保完全重新构建。

问：一个镜像可以打多个标签吗？

  • 可以。docker tag ctts-backend:v1 ctts-backend:latest 给同一镜像再打一个 latest 标签。两个标签指向同一个 IMAGE ID。

定义

容器运行与验证 是把构建好的镜像用 docker run 启动成容器，并通过访问接口、查看日志等方式确认服务正常运行的过程。对于 CTTS 项目，需要分别运行后端容器和前端容器，并完成前后端联调验证。

原理

容器运行的核心要素：

   -d                  后台运行
   -p 宿主端口:容器端口  端口映射
   --name <名字>        给容器命名
   --network <网络>     加入指定网络（容器间通信）
   -e <键=值>           环境变量

容器间通信：

  • 默认情况下容器之间网络隔离，不能互相访问。
  • 要让前端容器（Nginx）通过 http://ctts-api:8080 访问后端容器，需要把两个容器加入同一个自定义网络（第 9 次课详讲）。
  • 本节课先用 --network 创建一个共享网络让前后端通信。

问题 / 场景

问：为什么前端容器调用后端要用容器名 ctts-api，不能用 localhost？

  • 每个容器有独立的 localhost，前端容器里的 localhost 是前端容器自己，不是后端容器。容器间通信要用容器名（在同一自定义网络中，Docker DNS 解析容器名为 IP）或宿主机 IP + 映射端口。

问：运行后 docker ps 看不到容器怎么办？

  • 容器可能启动失败立即退出了。用 docker ps -a（含已停止的）查看，再用 docker logs <容器名> 看错误日志。

问：如何验证后端服务正常？

  • 用 curl http://localhost:8080/actuator/health 访问健康检查接口，返回 {"status":"UP"} 即正常。
  • 或访问业务接口 curl http://localhost:8080/api/hello。

问：如何验证前端服务正常？

  • 浏览器访问 http://localhost，能看到页面。
  • 前端调后端 API 能返回数据（联调验证）。

  1. ❌ 端口被占用：docker run -p 80:80 时如果宿主机 80 端口被占用（如本机装了 Nginx/Apache），会报错 "bind: address already in use"。✅ 换端口如 -p 8081:80，或停掉占用端口的进程。

知识点 K8-5：构建优化实践

定义

构建优化 是通过层缓存、.dockerignore、多阶段构建、基础镜像选型等手段，加速构建过程、减小镜像体积、提升镜像安全性的工程实践。

原理

层缓存机制：

Docker 镜像是分层的，每条 Dockerfile 指令生成一层。构建时 Docker 会检查每层是否能复用缓存：

图示 10：判断缓存命中的规则：

判断缓存命中的规则：

指令本身没变（如 RUN mvn package 没改成 RUN mvn install）

对于 COPY/ADD：被复制的文件内容没变（按文件校验和判断）

上面的层都命中缓存

命中缓存 → 直接复用旧层（秒级）

未命中缓存 → 重新执行该层及后续所有层

所以：把变动少的层放前面，变动多的层放后面

.dockerignore 机制：

构建上下文中的文件会全部发给 dockerd。.dockerignore 类似 .gitignore，列出要排除的文件，让构建上下文更小、构建更快、避免敏感信息被打包。

.dockerignore 示例：
node_modules        # 前端依赖（容器内 npm ci 重新装）
target              # Maven 构建产物（容器内 mvn package 重新生成）
.git                # Git 仓库元数据
*.log               # 日志文件
.env                # 环境变量文件（可能含密码）
Dockerfile          # Dockerfile 本身不需要进镜像

镜像大小分析：

docker image ls                    # 查看镜像大小
docker image history <镜像名>       # 查看每层大小
docker images --format "table {{.Repository}}\t{{.Size}}"   # 格式化输出

问题 / 场景

问：为什么"先 COPY pom.xml 再 COPY src"能加速构建？

  • Maven 依赖下载耗时最久（几十秒~几分钟）。如果先 COPY pom.xml + RUN mvn dependency:go-offline，这层只依赖 pom.xml。修改源码时 pom.xml 没变，这层命中缓存，跳过依赖下载，只重新执行 COPY src + RUN mvn package。如果先 COPY src（包含 pom.xml），任何源码变动都会让后续层失效，依赖重新下载。

问：.dockerignore 该排除什么？

  • 构建产物（target、dist、build）、依赖目录（node_modules）、版本控制（.git）、IDE 配置（.idea、.vscode）、日志（*.log）、敏感文件（.env、密钥）。

问：如何对比优化前后镜像大小？

  • 构建一个单阶段镜像（如 ctts-backend:v1-single），再构建多阶段镜像（ctts-backend:v1），用 docker images 对比 SIZE。

问：alpine 镜像为什么小？

  • Alpine Linux 是基于 musl libc 和 BusyBox 的精简发行版，基础镜像只有 5MB。eclipse-temurin:17-jre-alpine 比 eclipse-temurin:17-jre（基于 Ubuntu）小很多。但 alpine 用 musl libc，少数依赖 glibc 的库可能不兼容，需测试。

易错点

  1. ❌ .dockerignore 排除了必要文件：如排除了 pom.xml 或 package.json，导致 COPY 失败。✅ .dockerignore 只排除构建产物和依赖目录，不要排除源码和配置文件。

  2. ❌ 缓存导致镜像含旧代码：极少数情况下 COPY 缓存判断失误。✅ 用 --no-cache 强制重新构建。

  3. ❌ alpine 不兼容：少数 Java 库依赖 glibc，在 alpine（musl libc）上运行报错。✅ 测试验证，如有兼容问题改用 eclipse-temurin:17-jre-jammy（基于 Ubuntu）。

  4. ❌ 优化过度影响可维护性：为减小几 MB 体积用过于奇技淫巧的 Dockerfile。✅ 优化要权衡体积与可读性，主流优化手段（多阶段、.dockerignore、alpine）足够。

  5. ❌ 不分析镜像层就优化：不知道哪层大就盲目优化。✅ 先用 docker image history 看每层大小，针对最大的层优化。

小结

构建优化三大手段：① .dockerignore 排除无用文件减小上下文；② 把变动少的层（如依赖下载）放前面利用缓存；③ 多阶段构建把构建工具链剔除出最终镜像。优化后镜像更小（820MB→198MB）、构建更快（120s→15s）、更安全。

定义

实践复盘 是对构建过程中遇到的问题进行汇总、分类、分析原因、给出解决方案的总结过程。本知识点梳理 CTTS 前后端镜像构建中的高频踩坑问题，培养学生"日志 → 定位 → 修复"的排查思维。

原理

构建问题排查的通用流程：

看日志：构建失败时 docker build 输出的最后一段就是错误信息

完整示例

问题 1：COPY 路径错误

现象：

=> ERROR: [builder 5/5] COPY srcc ./src
ERROR: failed to solve: COPY failed: stat /var/lib/docker/tmp/.../srcc: no such file or directory

排查：

# 查看构建上下文目录
ls ~/ctts-docker/ctts-backend/
# Dockerfile  pom.xml  src  target
# 没有 srcc 目录，只有 src

修复：把 Dockerfile 中 COPY srcc ./src 改回 COPY src ./src。

问题 2：Maven 依赖下载失败（网络问题）

现象：

=> ERROR: [builder 4/5] RUN mvn dependency:go-offline -B
------
 > [builder 4/5] RUN mvn dependency:go-offline -B:
...
Could not transfer artifact org.springframework.boot:spring-boot-starter-parent:pom:3.2.0 from central
...

排查：网络无法访问 Maven 中央仓库。

修复：在 pom.xml 或 Maven settings.xml 中配置阿里云镜像源：

<!-- 在 pom.xml 的 <project> 下添加 -->
<repositories>
    <repository>
        <id>aliyun</id>
        <url>https://maven.aliyun.com/repository/public</url>
    </repository>
</repositories>
<pluginRepositories>
    <pluginRepository>
        <id>aliyun</id>
        <url>https://maven.aliyun.com/repository/public</url>
    </pluginRepository>
</pluginRepositories>

或在 Dockerfile 中复制本地 settings.xml：

COPY settings.xml /root/.m2/settings.xml

问题 3：npm install 慢/失败

现象：

=> ERROR: [builder 4/6] RUN npm ci
------
npm ERR! network timeout

修复：在 Dockerfile 中配置 npm 镜像源：

RUN npm config set registry https://registry.npmmirror.com && npm ci

问题 4：容器启动立即退出

现象：

docker run -d --name ctts-api -p 8080:8080 ctts-backend:v1
docker ps  # 看不到
docker ps -a  # 看到 Exited (1) 5 seconds ago

排查：

docker logs ctts-api
# 假设输出：
# Error: Unable to access jarfile app.jar

修复：Dockerfile 中 COPY 的 jar 路径与 CMD 中引用的路径不一致。检查：

COPY --from=builder /build/target/ctts-backend-1.0.0.jar app.jar
CMD ["java", "-jar", "app.jar"]

两个 app.jar 要一致。

问题 5：端口被占用

现象：

docker run -d -p 80:80 --name ctts-web ctts-frontend:v1
# docker: Error response from daemon: driver failed programming external connectivity on endpoint ctts-web:
# Bind for 0.0.0.0:80 failed: port is already allocated.

排查：

# 看谁占用了 80
sudo netstat -tlnp | grep :80
# 或
sudo lsof -i :80

修复方案：

  • 方案1：换端口 docker run -p 8081:80 ...，访问 http://localhost:8081
  • 方案2：停掉占用 80 的进程（如本机 Nginx）sudo systemctl stop nginx

问题 6：前端调后端跨域（CORS）

现象：浏览器访问 http://localhost 能看到页面，但 Console 报：

Access to fetch at 'http://localhost:8080/api/hello' from origin 'http://localhost'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header...

原因：前端 http://localhost 调后端 http://localhost:8080，端口不同视为跨域。

修复方案：

  • 方案1（推荐）：Nginx 反向代理，前端调 /api/hello（同源），Nginx 转发到后端 
    location /api/ {
    proxy_pass http://ctts-api:8080;
}
    前端代码改成 fetch('/api/hello')（相对路径）
  • 方案2：后端加 CORS 头（SpringBoot 加 @CrossOrigin 注解或全局配置）

问题 7：前端调后端 DNS 失败

现象：前端容器日志报：

2026/07/22 10:30:00 [error] 12#12: *1 ctts-api could not be resolved (3: Host not found)

原因：前后端容器不在同一网络，Nginx 无法解析 ctts-api。

修复：把两个容器加入同一网络：

docker stop ctts-web ctts-api && docker rm ctts-web ctts-api
docker network create ctts-net
docker run -d --name ctts-api --network ctts-net -p 8080:8080 ctts-backend:v1
docker run -d --name ctts-web --network ctts-net -p 80:80 ctts-frontend:v1

问题 8：构建上下文过大导致构建慢

现象：构建日志显示 transferring context: 1.2GB，构建卡在这一步很久。

排查：构建目录里有大文件（如 node_modules、.git、target）。

修复：配置 .dockerignore（见 K8-5），排除：

node_modules
.git
target
dist

易错点

  1. ❌ 不看日志就猜原因：构建/运行失败后凭感觉改代码。✅ 先看 docker build 日志 / docker logs 输出，按错误信息定位。

  2. ❌ 改了 Dockerfile 不重新 build：改了 Dockerfile 但只 docker run，跑的还是旧镜像。✅ 每次改 Dockerfile 后先 docker build 再 docker run。

  3. ❌ 改了代码不重启容器：源码改了重新 build 镜像，但容器还在跑旧镜像。✅ docker stop + docker rm 旧容器，再用新镜像 docker run。

  4. ❌ 排查时一次改多个地方：同时改 Dockerfile + 源码 + 配置，问题变了不知道哪个修改生效。✅ 一次只改一处，逐步排查。

  5. ❌ 跨域问题以为是后端 bug：看到浏览器报 CORS 就去改后端代码，其实是前端没走代理。✅ 理解跨域是浏览器同源策略，用 Nginx 代理是最干净的方案。

小结

构建/运行问题排查的核心是"看日志 → 找 ERROR 行 → 看错误信息 → 定位 Dockerfile 行 → 修复 → 重建"。常见问题分四类：路径类（COPY 错）、网络类（依赖下载失败、DNS 失败、跨域）、端口类（被占用）、缓存类（旧代码）。养成"先看日志再动手"的习惯是 DevOps 工程师的基本素养。

四、拓展阅读（选学）

  1. BuildKit：Docker 18.09+ 引入的新构建引擎，默认启用（日志前缀 [+] 即 BuildKit）。支持并行构建多阶段、缓存挂载（--mount=type=cache）等高级特性。
  2. 多平台构建：docker buildx build --platform linux/amd64,linux/arm64 一次构建多架构镜像，用于在 x86 和 ARM（如 Apple M1、树莓派）上运行。
  3. 镜像扫描：docker scout 或 Trivy、Grype 等工具扫描镜像中的 CVE 漏洞，生产镜像应定期扫描。
  4. Distroless 镜像：Google 出的极简镜像，只有运行时和依赖，没有 shell、包管理器，更安全。gcr.io/distroless/java17 适合 Java 后端。
  5. Jib：Google 出的 Java 镜像构建工具，不用 Dockerfile 也能构建 Java 镜像，集成 Maven/Gradle 插件。适合 CI/CD 场景。

一句话总结

本节课通过多阶段构建把 CTTS 前后端分别打包成精简镜像（后端 200MB、前端 50MB），用 docker build 构建、docker run 运行、docker network 联通，最终在浏览器完成前后端联调。掌握"写 Dockerfile → build 镜像 → run 容器 → 验证联调 → 优化排查"的完整链路，是云原生工程师的核心基本功。
