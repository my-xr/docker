二、知识点详解

K20-1 K8s网络模型与CNI插件

1.1.1 定义

K8s网络模型是K8s集群中所有Pod、Node、Service之间通信规则的集合，由 CNI（Container Network Interface） 插件具体实现。它遵循三个核心原则：

  1. 每个Pod拥有独立IP：Pod是K8s最小网络单元，容器共享Pod的网络命名空间。
  2. Pod间无NAT直接通信：任意Pod可直接用对方PodIP访问，不需要地址转换。
  3. Node与Pod间无NAT通信：节点可直连本集群任意Pod。

1.1.2 原理

K8s不实现网络，只定义规范。具体由CNI插件完成：

图示 2：结构与流程重绘

主流CNI对比：

特性 Flannel Calico Cilium
模式 Overlay (VXLAN) Overlay(BGP)/Underlay eBPF
NetworkPolicy ❌ 不支持 ✅ 支持 ✅ 支持
性能 中 高 极高
复杂度 低 中 高
适用场景 小型/学习 中大型生产 大规模/高性能

1.1.3 常见问题

  • Q1：为什么K8s要求Pod间无NAT？ A：NAT会破坏端到端可达性，导致服务发现、日志追踪复杂化。扁平网络让每个Pod都是"一等公民"。

  • Q2：没有CNI插件会怎样？ A：Pod能创建但状态会停留在 ContainerCreating，因为kubelet无法完成网络配置。

1.1.4 完整示例（验证三原则）

# 文件：net-test.yaml

kind: Pod
metadata:
  name: pod-a
  namespace: default
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sleep", "3600"]
---
apiVersion: v1

  name: pod-b
  namespace: default
spec:
  containers:

    image: busybox:1.36

1.1.6 易错点

  • ❌ 误认为K8s自带网络实现，实际只是规范，必须装CNI。
  • ❌ 误以为PodIP会跨集群路由，PodIP仅集群内可达。
  • ❌ 选Flannel后又开启NetworkPolicy——Flannel不支持，需切Calico。

1.1.7 小结

K8s网络模型三原则：Pod独立IP、Pod间无NAT、Node与Pod无NAT。CNI插件负责实现，主流为Flannel（简单）、Calico（生产）、Cilium（高性能）。

1.2.4 dnsPolicy四种取值

取值 行为 适用场景
ClusterFirst（默认） 集群内域名走CoreDNS，其他转发上游 普通业务Pod
ClusterFirstWithHostNet 与ClusterFirst相同，但用于hostNetwork Pod 系统级Pod
Default 继承节点 /etc/resolv.conf 需要直接访问外部DNS的Pod
None 不做任何配置，必须自定义 dnsConfig 高级定制场景

示例YAML：

apiVersion: v1
kind: Pod
metadata:
  name: dns-demo
spec:
  dnsPolicy: ClusterFirst   # 默认值
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sleep", "3600"]

1.2.6 易错点

  • ❌ 跨命名空间访问忘记写命名空间段：curl http://user-service 在非ctts命名空间会失败。
  • ❌ 误用Pod域名格式 pod-ip-dashed.namespace.pod.cluster.local（仅Headless Service场景常用）。
  • ❌ dnsPolicy: None 后忘记自定义 dnsConfig，导致无法解析。

1.2.7 小结

CoreDNS以 service.namespace.svc.cluster.local 格式提供服务发现。默认 dnsPolicy: ClusterFirst 满足绝大多数场景。跨命名空间访问必须写全域名。

K20-3 NetworkPolicy网络策略

1.3.1 定义

NetworkPolicy是K8s中控制Pod间网络流量的资源对象，由CNI插件（如Calico、Cilium）实现，原生Flannel不支持。

1.3.2 核心语义（重点！）

  • 默认行为：没有NetworkPolicy选中Pod时，所有流量默认允许。
  • 隔离生效：一旦有NetworkPolicy选中Pod的ingress或egress方向，该方向变为默认拒绝，只允许策略中显式允许的流量。
  • 方向：
    • ingress：进入Pod的流量
    • egress：从Pod出去的流量

1.3.3 字段结构

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: <策略名>
  namespace: <命名空间>
spec:
  podSelector:           # 选择本命名空间中要隔离的Pod
    matchLabels:
      app: <app名>
  policyTypes:           # 指定生效方向：Ingress / Egress
  - Ingress
  - Egress
  ingress:               # 入站规则列表（OR关系）
  - from:
    - podSelector:       # 同命名空间Pod选择（AND语义）
        matchLabels:
          app: <允许的app>
    - namespaceSelector:  # 跨命名空间选择（AND语义）
        matchLabels:
          kubernetes.io/metadata.name: <允许的命名空间>
    ports:
    - protocol: TCP
      port: 8080
  egress:                # 出站规则列表（OR关系）
  - to:
    - podSelector:
        matchLabels:
          app: <目标app>
    ports:
    - protocol: TCP
      port: 5432

1.3.4 selector联合语义（难点！）

写法 语义
podSelector: {} 选中当前命名空间所有Pod
namespaceSelector: {} 选中所有命名空间的所有Pod
podSelector: {} + namespaceSelector: {} 同一from项 同时满足（AND）：所有命名空间的所有Pod
多个from项 OR：任一满足即可

1.3.5 完整示例：CTTS用户服务隔离策略

需求：

  • 仅允许 ctts-order 命名空间的 app=order Pod访问 ctts 命名空间的 app=user Pod的8080端口
  • app=user Pod仅允许出站到 app=postgres Pod的5432端口和CoreDNS
# 文件：ctts-networkpolicy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: user-service-policy
  namespace: ctts
spec:
  podSelector:
    matchLabels:
      app: user
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ctts-order
      podSelector:
        matchLabels:
          app: order
    ports:
    - protocol: TCP
      port: 8080
  egress:
  # 允许访问postgres
  - to:
    - podSelector:
        matchLabels:
          app: postgres
    ports:
    - protocol: TCP
      port: 5432
  # 允许访问kube-system的CoreDNS（DNS解析必需）
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53

应用与验证：

kubectl apply -f ctts-networkpolicy.yaml
kubectl get networkpolicy -n ctts
# NAME                  POD-SELECTOR   AGE
# user-service-policy   app=user       5s

# 验证：从ctts-order命名空间order Pod访问user → 成功
kubectl exec -n ctts-order deploy/order -- curl -s -o /dev/null -w "%{http_code}\n" \
  http://user-service.ctts.svc.cluster.local:8080/health
# 200

# 验证：从default命名空间busybox访问user → 失败（超时）
kubectl run probe --image=busybox:1.36 --rm -it --restart=Never -- \
  wget -T 3 -qO- http://user-service.ctts.svc.cluster.local:8080/health
# wget: download timed out   ← 隔离生效

1.3.7 易错点

  • ❌ 选错CNI：Flannel不生效，必须用Calico/Cilium。
  • ❌ namespaceSelector 用 name: 而非 kubernetes.io/metadata.name:（1.21+必须用后者）。
  • ❌ 开启egress策略后忘记放行DNS（UDP 53到kube-system），导致服务名解析失败。
  • ❌ 把 podSelector 与 namespaceSelector 写在不同from项以为是AND，实际是OR。

1.3.8 小结

NetworkPolicy实现"默认禁止+显式允许"的零信任模型。selector在同一from项内为AND，跨from项为OR。开启egress务必放行DNS。

K20-4 网络调试四件套

1.4.1 定义

nslookup、dig、ping、curl 是Pod内网络排查的四个核心命令，配合 kubectl exec 形成完整调试链路。

1.4.2 调试决策树

1.4.3 命令示例

# 进入调试Pod
kubectl exec -it dnsutil -- bash

# 1. nslookup：简单DNS查询
nslookup kubernetes.default
nslookup user-service.ctts.svc.cluster.local

# 2. dig：详细DNS查询（含TTL、权威解析）
dig +short user-service.ctts.svc.cluster.local
dig user-service.ctts.svc.cluster.local A
dig @10.96.0.10 user-service.ctts.svc.cluster.local   # 指定DNS服务器

# 3. ping：网络层连通性
ping -c 3 10.96.123.45
ping -c 3 user-service.ctts.svc.cluster.local

# 4. curl：应用层验证
curl -v http://user-service.ctts.svc.cluster.local:8080/health
curl -s -o /dev/null -w "HTTP:%{http_code} Time:%{time_total}s\n" \
  http://user-service.ctts.svc.cluster.local:8080/health

# 5. kubectl本身也可调试
kubectl get svc -A
kubectl describe svc user-service -n ctts
kubectl get endpoints user-service -n ctts   # 关键！检查后端Pod是否就绪
kubectl get networkpolicy -A

1.4.4 常见故障速查表

现象 可能原因 排查命令
nslookup 返回NXDOMAIN Service未创建或名字写错 kubectl get svc -n <ns>
nslookup OK但 curl 超时 NetworkPolicy拦截或Endpoint为空 kubectl get ep
curl 返回502/503 后端Pod未就绪 kubectl describe pod

跨命名空间失败 域名缺命名空间段 用完整FQDN

1.4.5 小结

网络调试四件套形成"应用层→网络层→DNS层"完整闭环。先 nslookup 再 ping 再 curl，逐层下钻。

1.5.2 Service Mesh（Istio）简介

定义：Service Mesh是处理服务间通信的基础设施层，典型实现为Istio、Linkerd。

核心能力：

  • 流量管理：细粒度路由（按比例灰度、A/B测试）
  • 安全：mTLS双向认证、授权策略
  • 可观测性：调用链追踪、指标采集

与K8s原生网络的关系：

  • K8s NetworkPolicy：L3/L4层、粗粒度、声明式
  • Istio AuthorizationPolicy：L7层、细粒度、按HTTP方法/路径

1.5.3 生产环境网络规划建议

  1. CNI选型：≤50节点用Flannel（仅学习）；50-1000节点用Calico；>1000节点或对延迟敏感用Cilium。
  2. 默认隔离：所有生产命名空间应配置"默认拒绝所有"的NetworkPolicy，再按需放行。
  3. DNS容量：CoreDNS建议 ≥2副本，开启 autopath 插件降低解析延迟。
  4. 可观测性：Calico开Calico Cloud，Cilium开Hubble，否则网络问题难定位。
  5. 多集群：跨集群通信用Submariner或Istio Multi-Cluster。

1.5.4 小结

生产网络选型需平衡性能、可观测性、运维成本。Service Mesh在K8s网络之上提供L7能力，是大规模微服务架构的演进方向。

三、综合示例：CTTS服务间DNS解析与NetworkPolicy

3.1 场景描述

CTTS项目需要：

  1. ctts 命名空间的 user-service 与 order-service 通过DNS互访
  2. 限制只有 ctts 命名空间的Pod能访问 user-service 的8080端口
  3. user-service 仅允许出站到PostgreSQL与CoreDNS

3.2 完整YAML（可直接apply）

# 文件：ctts-network-demo.yaml
---
# 1. 命名空间
apiVersion: v1
kind: Namespace
metadata:
  name: ctts
  labels:
    kubernetes.io/metadata.name: ctts
---
# 2. PostgreSQL（模拟）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
  namespace: ctts
spec:
  replicas: 1
  selector:
    matchLabels: {app: postgres}
  template:
    metadata:
      labels: {app: postgres}
    spec:
      containers:
      - name: postgres
        image: postgres:15-alpine
        env:
        - name: POSTGRES_PASSWORD
          value: "ctts123"
        ports:
        - containerPort: 5432
---
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: ctts
spec:
  selector: {app: postgres}
  ports:
  - port: 5432
    targetPort: 5432
---
# 3. user-service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
  namespace: ctts
spec:
  replicas: 2
  selector:
    matchLabels: {app: user}
  template:
    metadata:
      labels: {app: user}
    spec:
      containers:
      - name: user
        image: hashicorp/http-echo:1.0
        args: ["-listen=:8080", "-text=user-service-ok"]
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: user-service
  namespace: ctts
spec:
  selector: {app: user}
  ports:
  - port: 8080
    targetPort: 8080
---
# 4. order-service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: ctts
spec:
  replicas: 2
  selector:
    matchLabels: {app: order}
  template:
    metadata:
      labels: {app: order}
    spec:
      containers:
      - name: order
        image: hashicorp/http-echo:1.0
        args: ["-listen=:8080", "-text=order-service-ok"]
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
  namespace: ctts
spec:
  selector: {app: order}
  ports:
  - port: 8080
    targetPort: 8080
---
# 5. NetworkPolicy
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: user-service-policy
  namespace: ctts
spec:
  podSelector:
    matchLabels: {app: user}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:
        matchLabels: {app: order}
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels: {app: postgres}
    ports:
    - protocol: TCP
      port: 5432
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels: {k8s-app: kube-dns}
    ports:
    - protocol: UDP
      port: 53

# 2. 等待Pod就绪

# 3. 在order-service Pod内访问user-service（应成功）

七、思政要点：网络隔离是安全基础

7.1 国家政策背景

《网络安全法》第二十一条明确要求网络运营者采取"技术措施防范网络攻击和网络侵入"。《数据安全法》进一步要求对数据处理活动采取分类分级保护。K8s NetworkPolicy正是云原生时代落实这些法律要求的核心技术手段。

7.2 从"默认开放"到"零信任"

传统K8s网络默认所有Pod互通，这与"最小权限原则"相悖。2019年Capital One数据泄露事件中，攻击者正是利用了K8s集群内部过度宽松的网络策略横向移动，最终访问了S3存储桶。这一事件深刻警示我们：

"网络默认开放"是工程便利，"网络默认隔离"才是工程责任。

7.3 工程师的职业操守

作为未来的云原生工程师，我们应当：

  1. 在系统设计之初就把"网络隔离"作为非功能性需求纳入。
  2. 不为追求"先跑起来"而牺牲安全性，提交的YAML必须包含NetworkPolicy。
  3. 持续学习国家网络安全法规，将合规要求转化为技术实践。

网络隔离不是给业务"添堵"，而是给安全"兜底"。
