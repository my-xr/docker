一、学习导读

1.1 上节课回顾

第18次课我们学习了Service：ClusterIP（集群内访问）、NodePort（节点端口暴露）、LoadBalancer（云厂商LB）。它们都是**四层（TCP/UDP）**负载均衡，只认IP+端口，不认HTTP Host、Path、Header。

1.2 本节课要解决的问题

  • CTTS前端Service用NodePort暴露成 节点IP:30001，后端Service暴露成 节点IP:30002，用户要记两串数字端口，体验差。
  • 浏览器访问 http://节点IP:30001 时，前端Vue3调后端API写死成 http://节点IP:30002，跨端口CORS、跨环境改配置，运维痛苦。
  • 没有HTTPS，登录密码明文传输，不符合生产要求。

Ingress就是来解决这三件事的：统一入口（一个IP/域名）、域名+路径路由（不同后端Service）、TLS卸载（HTTPS在入口终止）。

1.3 学完本课你能做到

  • 安装并验证Nginx Ingress Controller。
  • 编写Ingress YAML，让 frontend.ctts.local 路由到前端、api.ctts.local 路由到后端。
  • 配置本机hosts，浏览器访问验证。
  • 生成自签证书、创建TLS Secret、为Ingress启用HTTPS。
  • 排查常见的404、503、路由不通等问题。

1.4 学习建议

  • 一定要动手：Ingress是"配置即代码"的典型，光看不写记不住YAML字段。
  • 善用 kubectl describe ingress：90%的路由问题都能从describe输出中看出来。
  • 看Controller日志：kubectl logs -n ingress-nginx <controller-pod> 是排查的高级手段。
  • 不要跳过hosts配置：很多同学Ingress写对了但浏览器访问404，原因就是没配hosts。

二、知识点详解

K19-1 Ingress概念

定义

Ingress 是Kubernetes中一种API对象，它管理对集群内Service的外部HTTP/HTTPS访问（七层），典型能力包括：

  • 基于域名的虚拟主机（virtual host）路由
  • 基于URL路径的路由
  • TLS/SSL终止（卸载）
  • 域名级负载均衡

原理

Ingress本身只是路由规则（一份YAML声明），真正执行转发的是 Ingress Controller（一个跑在集群里的Pod）。Controller监听Ingress资源变化，把规则翻译成自身配置（如Nginx配置文件），然后由自己接收外部流量并转发到对应Service。

图示 1：结构与流程重绘
外部用户 │ HTTP/HTTPS请求 (host: frontend.ctts.local) ▼ ┌─────────────────────────────┐ │ Ingress Controller (Pod) │ ← 一个独立的Pod，监听80/443 │ (Nginx Ingress Controller)│ └─────────────────────────────┘ │ 查询Ingress规则 │ 匹配 host + path ▼ ┌──────────────┐ ┌──────────────┐ │ ctts-frontend│ │ ctts-backend │ ← Service (ClusterIP) │ Service │ │ Service │ └──────────────┘ └──────────────┘ │ │ ▼ ▼ Pod Pod

问题：为什么需要Ingress？

痛点 不用Ingress 用Ingress
端口暴露 每个Service一个NodePort，端口散乱 一个80/443对外，内部路由
域名访问 只能用IP:Port 支持 frontend.ctts.local
HTTPS 每个Service都要装证书 入口统一TLS卸载
路由规则 无 按host/path灵活路由
资源占用 NodePort占用端口段、LB要钱 一个Controller即可

一句话总结：Service是"四层粗粒度暴露"，Ingress是"七层细粒度路由"。

完整示例（最小Ingress）

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: minimal-ingress
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80

图示：四层 vs 七层

图示 2：结构与流程重绘
四层（Service/NodePort）： 用户 → TCP:30001 → Service → Pod 只看IP+Port 七层（Ingress）： 用户 → HTTP host+path → Ingress → Service → Pod 看HTTP协议字段

易错点

  1. Ingress只支持HTTP/HTTPS，不支持TCP/UDP（如要四层七层混合，需Controller扩展，如Nginx Ingress的tcp-services ConfigMap）。
  2. Ingress本身不做负载均衡到Pod，它路由到Service，Service再负载到Pod。
  3. Ingress资源不创建Controller，需先有Controller运行。

小结

Ingress = 七层路由规则 + Controller执行。它解决了NodePort端口散、无域名、无HTTPS的问题。

K19-2 Ingress Controller

定义

Ingress Controller 是一个运行在K8s集群中的Pod，负责：

  1. 监听Ingress资源变化
  2. 将规则翻译为自身配置（Nginx配置、Traefik配置等）
  3. 接收外部HTTP/HTTPS流量并按规则转发

原理

K8s官方没有内置Controller，需自行选择实现：

Controller 特点
Nginx Ingress Controller 最主流、社区活跃、配置灵活、本课使用
Traefik Go实现、自动配置、云原生友好
HAProxy Ingress 高性能、企业级
Contour 基于Envoy、CNCF项目
Higress 阿里开源、国内生态友好、网关+MCP

关键认知：Ingress Controller本质是一个Pod + Service（LoadBalancer或NodePort）。它本身也需要被外部访问到。

问题：Minikube下如何安装？

Minikube提供了ingress addon，一键启用：

# 1. 启用ingress addon
minikube addons enable ingress

# 2. 验证addon状态
minikube addons list | grep ingress

# 3. 查看Controller Pod（在ingress-nginx命名空间）
kubectl get pods -n ingress-nginx

# 4. 查看Controller Service
kubectl get svc -n ingress-nginx

预期输出：

$ kubectl get pods -n ingress-nginx
NAME                                        READY   STATUS    RESTARTS   AGE
ingress-nginx-controller-5xxxx              1/1     Running   0          2m

完整示例：验证Controller工作

# 查看Controller的Deployment
kubectl get deploy -n ingress-nginx

# 查看Controller配置（实际就是Nginx配置）
kubectl exec -n ingress-nginx <controller-pod-name> -- cat /etc/nginx/nginx.conf | head -50

# 查看Controller Service，确认80/443端口
kubectl get svc -n ingress-nginx ingress-nginx-controller

易错点

  1. addon启用后Pod需1-2分钟才Running，别急着访问。
  2. Controller在 ingress-nginx 命名空间，不是default，查Pod要加 -n。
  3. ingressClassName 必须与Controller匹配，默认是 nginx，写错会路由不生效。
  4. Minikube的Controller Service默认是NodePort，外部访问用 minikube ip + NodePort，或 minikube tunnel 走LoadBalancer。

小结

Controller = Ingress规则的执行者。Minikube下用 minikube addons enable ingress 一键安装，Pod在 ingress-nginx 命名空间。

K19-3 Ingress资源YAML

定义

Ingress资源是K8s的一种API对象，apiVersion: networking.k8s.io/v1，kind: Ingress，用于声明HTTP/HTTPS路由规则。

原理：核心字段

apiVersion: networking.k8s.io/v1     # 必须是v1（旧的extensions/v1beta1已废弃）
kind: Ingress
metadata:
  name: <ingress名称>
  namespace: <命名空间>                # 默认default
  annotations:                        # 注解，针对Controller的扩展配置
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx             # 指定使用哪个Controller
  rules:                              # 路由规则列表
  - host: <域名>                       # 可省略，省略表示匹配所有host
    http:
      paths:
      - path: <URL路径>
        pathType: <Prefix|Exact>      # 路径匹配类型
        backend:
          service:
            name: <Service名称>
            port:
              number: <Service端口>    # 或 name: <端口名>
  defaultBackend:                     # 兜底后端（无规则匹配时）
    service:
      name: <Service名称>
      port:
        number: <端口>
  tls:                                # TLS配置
  - hosts:
    - <域名>
    secretName: <TLS Secret名称>

问题：pathType Prefix vs Exact 有什么区别？

pathType 含义 示例：path=/foo
Prefix 前缀匹配，匹配 /foo、/foo/、/foo/bar ✅ /foo、/foo/、/foo/baz
Exact 精确匹配，仅匹配 /foo 本身 ✅ /foo；❌ /foo/、/foo/baz
ImplementationSpecific 由Controller自定义解释 Nginx Ingress视同Prefix

注意：K8s 1.22+ 强制要求 pathType 字段，不能省略。

完整示例：CTTS前后端域名路由

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ctts-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: frontend.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80
  - host: api.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80

应用：

kubectl apply -f ctts-ingress.yaml
kubectl get ingress
kubectl describe ingress ctts-ingress

预期输出：

$ kubectl get ingress
NAME            CLASS   HOSTS                                  ADDRESS        PORTS   AGE
ctts-ingress    nginx   frontend.ctts.local,api.ctts.local     192.168.49.2   80      30s

图示：路径匹配流程

图示 4：结构与流程重绘
请求: GET http://frontend.ctts.local/user/list │ ▼ ┌─ Ingress Controller ────────────────────┐ │ 1. 解析Host: frontend.ctts.local │ │ 2. 查找该host的rules │ │ 3. 遍历paths，按最长前缀匹配 │ │ path=/ pathType=Prefix 匹配 ✓ │ │ 4. 转发到 ctts-frontend:80/user/list │ └─────────────────────────────────────────┘ │ ▼ ctts-frontend Service → Pod

易错点

  1. apiVersion必须 networking.k8s.io/v1，老的 extensions/v1beta1 在1.22+已删除。
  2. backend.service 是对象不是字符串，正确写法是 service.name 与 service.port.number。
  3. pathType不可省略，否则API拒绝。
  4. path要以 / 开头，如 /api 而非 api。
  5. ingressClassName必须匹配Controller，如Controller是nginx，className就写nginx。
  6. 多paths按最长前缀优先，但建议把更具体的path写在前面以增加可读性。

小结

Ingress YAML核心是 rules[].host.http.paths[].backend。pathType必填，Prefix最常用。

K19-4 域名虚拟主机与路径路由

定义

  • 域名虚拟主机路由：一个Ingress定义多个host，每个host路由到不同Service。即"多域名共享一个IP"。
  • 路径路由：一个host下定义多个path，不同path路由到不同Service。
  • defaultBackend：当没有任何rule匹配时（host和path都不匹配），转发到这里。

原理

Nginx Ingress Controller在内部生成Nginx配置：

  • 每个host对应一个 server { server_name xxx; } 块
  • 每个 path 对应一个 location /xxx { proxy_pass ...; } 块
  • defaultBackend 对应一个默认server

问题：多Ingress规则会冲突吗？

  • 同一host可以分散在多个Ingress资源中声明，Controller会合并成一个server块。
  • 但同名path重复声明可能产生冲突，建议同一host的路由集中在一个Ingress。

完整示例1：多域名虚拟主机

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: shop.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: shop-frontend
            port:
              number: 80
  - host: admin.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: admin-frontend
            port:
              number: 80
  - host: api.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80

完整示例2：单域名多路径

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: path-based-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
  - host: ctts.local
    http:
      paths:
      - path: /()(.*)
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80
      - path: /api(/|$)(.*)
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80

注：上面的rewrite-target: /$2 与 path中的正则捕获组配合，把 /api/xxx 重写为 /xxx 转发到后端。本课作为了解，初学者建议先用多host方案。

完整示例3：defaultBackend兜底

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-with-default
spec:
  ingressClassName: nginx
  defaultBackend:
    service:
      name: default-error-page
      port:
        number: 80
  rules:
  - host: frontend.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80

访问未定义的host或未匹配的path，会返回 default-error-page 服务的内容。

图示 5：结构与流程重绘
┌─── host=shop.ctts.local → shop-frontend 80/443 ────┼─── host=admin.ctts.local → admin-frontend ├─── host=api.ctts.local → ctts-backend └─── 其他host（未匹配） → defaultBackend

易错点

  1. 多Ingress同名host会合并，但同名path冲突：建议同一host的路由集中在同一Ingress。
  2. defaultBackend只在 spec 顶层，不是每个rule内。
  3. rewrite-target使用要谨慎：前端静态资源可能因路径重写找不到，调试时先去掉注解。
  4. 跨命名空间路由不支持：Ingress只能路由到同命名空间的Service。

小结

虚拟主机 = 多host多Service；路径路由 = 单host多path多Service；defaultBackend = 兜底。

K19-5 TLS/HTTPS配置

定义

Ingress支持TLS终止（TLS Termination）：用户与Controller之间用HTTPS加密，Controller与集群内Service之间用HTTP明文。证书以Secret形式存储。

原理

图示 6：结构与流程重绘
浏览器 ──HTTPS──> Ingress Controller ──HTTP──> Service ──HTTP──> Pod (TLS加密) (证书在此终止) (集群内可明文)

已由原 Markdown 字符图转换为网页图示，保留原有逻辑关系并优化阅读效果。

问题：证书从哪来？放哪？

  • 测试环境：用openssl生成自签证书。
  • 生产环境：从CA购买或用Let's Encrypt免费签发（结合cert-manager自动管理）。
  • 证书以 TLS类型Secret 存储在K8s中，Ingress通过 tls.secretName 引用。

完整示例：CTTS启用HTTPS

步骤1：生成自签证书（含两个域名）

# 生成私钥
openssl genrsa -out ctts.key 2048

# 生成证书签名请求（CSR），包含两个域名
cat > openssl.cnf <<EOF
[req]
distinguished_name = req_distinguished_name
req_extensions = v3_req
prompt = no
[req_distinguished_name]
CN = frontend.ctts.local
[v3_req]
subjectAltName = @alt_names
[alt_names]
DNS.1 = frontend.ctts.local
DNS.2 = api.ctts.local
EOF

openssl req -new -key ctts.key -out ctts.csr -config openssl.cnf

# 自签证书（有效期365天）
openssl x509 -req -in ctts.csr -signkey ctts.key -out ctts.crt -days 365 -extensions v3_req -extfile openssl.cnf

步骤2：创建TLS Secret

kubectl create secret tls ctts-tls-secret \
  --cert=ctts.crt \
  --key=ctts.key

# 验证
kubectl get secret ctts-tls-secret
kubectl describe secret ctts-tls-secret

步骤3：更新Ingress，启用TLS

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ctts-ingress-tls
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"   # HTTP自动跳转HTTPS
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - frontend.ctts.local
    - api.ctts.local
    secretName: ctts-tls-secret
  rules:
  - host: frontend.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80
  - host: api.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80

步骤4：应用并验证

kubectl apply -f ctts-ingress-tls.yaml

# 查看Ingress，PORTS应包含80, 443
kubectl get ingress

# curl测试HTTPS
curl -k https://frontend.ctts.local
curl -k https://api.ctts.local/actuator/health

# 验证HTTP自动跳转HTTPS
curl -I http://frontend.ctts.local
# 预期返回 301 Moved Permanently，Location: https://...

易错点

  1. 证书SAN必须包含所有域名：只有CN不行，现代浏览器只认SAN。
  2. Secret类型必须是 kubernetes.io/tls，用 kubectl create secret tls 创建的就是。
  3. tls.hosts要列出使用该证书的所有host，遗漏会导致证书不匹配。
  4. 自签证书浏览器会警告，需手动信任；生产用Let's Encrypt。
  5. ssl-redirect注解开启后，HTTP会自动301跳HTTPS。
  6. 不要把证书文件提交到Git，应放Secret或用cert-manager管理。

小结

TLS三步走：openssl生成证书 → kubectl create secret tls → Ingress的 tls 字段引用。

三、综合示例：CTTS完整Ingress部署流程

3.1 前置条件

  • Minikube已启动：minikube start
  • CTTS前后端已部署（Deployment + Service）
  • 假设Service清单如下：
    • ctts-frontend ClusterIP 80→Pod 8080（Vue3 nginx）
    • ctts-backend ClusterIP 80→Pod 8081（SpringBoot）

若还没有部署，可用以下快速示例：

kubectl create deployment ctts-frontend --image=nginx:alpine --port=8080
kubectl expose deployment ctts-frontend --port=80 --target-port=8080
kubectl create deployment ctts-backend --image=nginx:alpine --port=8081
kubectl expose deployment ctts-backend --port=80 --target-port=8081

3.2 完整流程

Step 1：启用Ingress addon

minikube addons enable ingress
kubectl get pods -n ingress-nginx -w
# 等待 ingress-nginx-controller 进入 Running

Step 2：编写 ctts-ingress.yaml

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ctts-ingress
  namespace: default
spec:
  ingressClassName: nginx
  rules:
  - host: frontend.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80
  - host: api.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80

Step 3：应用并查看

kubectl apply -f ctts-ingress.yaml
kubectl get ingress
kubectl describe ingress ctts-ingress

Step 4：配置本机hosts

# 获取Minikube IP
minikube ip
# 假设输出 192.168.49.2

# Windows: 以管理员身份编辑 C:\Windows\System32\drivers\etc\hosts
# Linux/Mac: 编辑 /etc/hosts
# 追加：
192.168.49.2 frontend.ctts.local
192.168.49.2 api.ctts.local

Step 5：浏览器访问验证

  • 打开 http://frontend.ctts.local → 看到Vue3首页
  • 打开 http://api.ctts.local → 看到后端响应
  • curl -H "Host: frontend.ctts.local" http://$(minikube ip) → 返回前端HTML

Step 6：生成自签证书并创建Secret

openssl genrsa -out ctts.key 2048

cat > openssl.cnf <<EOF
[req]
distinguished_name = req_distinguished_name
req_extensions = v3_req
prompt = no
[req_distinguished_name]
CN = frontend.ctts.local
[v3_req]
subjectAltName = @alt_names
[alt_names]
DNS.1 = frontend.ctts.local
DNS.2 = api.ctts.local
EOF

openssl req -new -key ctts.key -out ctts.csr -config openssl.cnf
openssl x509 -req -in ctts.csr -signkey ctts.key -out ctts.crt -days 365 \
  -extensions v3_req -extfile openssl.cnf

kubectl create secret tls ctts-tls-secret --cert=ctts.crt --key=ctts.key

Step 7：更新Ingress启用TLS

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ctts-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - frontend.ctts.local
    - api.ctts.local
    secretName: ctts-tls-secret
  rules:
  - host: frontend.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80
  - host: api.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80
kubectl apply -f ctts-ingress.yaml
kubectl get ingress
# PORTS 应为 80, 443

Step 8：HTTPS验证

curl -k https://frontend.ctts.local
curl -k https://api.ctts.local
curl -I http://frontend.ctts.local   # 应返回 301 跳转

浏览器访问 https://frontend.ctts.local，会有证书警告（自签证书），点击"继续访问"即可。

四、拓展阅读

4.1 Nginx Ingress Controller常用注解

注解 作用
nginx.ingress.kubernetes.io/rewrite-target: / 路径重写
nginx.ingress.kubernetes.io/ssl-redirect: "true" HTTP自动跳HTTPS
nginx.ingress.kubernetes.io/cors-allow-origin: "*" 启用CORS
nginx.ingress.kubernetes.io/limit-rps: "10" 限流（每秒请求数）
nginx.ingress.kubernetes.io/proxy-body-size: "10m" 上传文件大小限制
nginx.ingress.kubernetes.io/proxy-read-timeout: "3600" 读超时（秒）
nginx.ingress.kubernetes.io/canary: "true" 灰度发布标记
nginx.ingress.kubernetes.io/canary-weight: "20" 灰度流量比例

4.2 cert-manager自动证书管理

cert-manager是K8s的证书自动化控制器，可与Let's Encrypt对接，自动签发与续期：

  • 安装：kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.0/cert-manager.yaml
  • 配置Issuer（Let's Encrypt或自签）
  • 在Ingress加注解 cert-manager.io/issuer: letsencrypt-prod
  • 证书自动签发并续期

4.3 国产云原生网关：Higress

  • 阿里开源，基于Envoy，兼容Ingress API
  • 国内文档完善，对接Nacos、Sentinel等阿里生态友好
  • 适合国内企业落地，可作为课外了解

4.4 多Ingress Controller共存

  • 一个集群可安装多个Controller（如nginx + traefik）
  • 通过 ingressClassName 区分，每个Ingress指定使用哪个
  • 适合不同业务域走不同网关的场景

4.5 蓝绿与灰度发布

Nginx Ingress通过canary注解支持灰度：

metadata:
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"   # 20%流量到新版本

新建一个Ingress引用新版本Service即可，无需改动原Ingress。
