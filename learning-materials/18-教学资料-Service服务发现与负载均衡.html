二、知识点详解

知识点 K18-1：Service 概念与作用

定义

Service（服务） 是 Kubernetes 中一种将一组运行相同应用的 Pod 暴露为网络服务的抽象。它为这组 Pod 提供一个稳定的 IP 地址（ClusterIP）、一个稳定的 DNS 名和负载均衡能力，使得调用方无需关心后端 Pod 的具体 IP 与数量。

一句话概括 Service 的核心价值：

Pod 是短暂的，Service 是稳定的。Service 为短暂的 Pod 提供稳定的访问入口。

原理

为什么需要 Service？——Pod 有三个"不稳定"特征：

图示 1：Pod 的三个"不稳定"特征：

IP 不稳定

Pod 重建后 IP 可能变化，客户端不能依赖 Pod IP。

数量不稳定

Deployment 扩缩容会让 Pod 数量随时变化。

位置不稳定

Pod 可能被调度到不同 Node，访问路径不能绑定机器。

Service 的价值就是给一组变化的 Pod 提供稳定名字、稳定虚拟 IP 和负载均衡入口。

问题 / 场景

问：为什么不能直接用 Pod IP？

  • Pod IP 不固定，每次重建都变。如果后端配置里写死 MySQL Pod IP，Pod 一重建就连不上。Service 提供"稳定 IP + DNS 名"，调用方配置一次，永久有效。

问：Service 的 IP 能 ping 通吗？

  • 不能。Service 的 ClusterIP 是一个虚拟 IP（Virtual IP），不绑定任何网络接口，ping 它没有响应。但curl/TCP 请求可以访问——因为 K8s 通过 kube-proxy 在节点上配置了 iptables/IPVS 规则，把发往 ClusterIP 的流量 DNAT 转发到后端 Pod IP。这是 Service 的一个"反直觉"特性。

问：Service 和 Deployment 是什么关系？

  • 二者独立但常配合使用：Deployment 管理 Pod 副本（保证数量），Service 暴露这些 Pod 为网络服务（提供访问入口）。Service 通过 selector 关联 Pod，不直接关心 Pod 是哪个 Deployment 创建的。一个 Service 可以选多个 Deployment 的 Pod（只要标签匹配），一个 Deployment 的 Pod 也可以被多个 Service 选中。

问：没有 Deployment 能创建 Service 吗？

  • 能。Service 只关心"选哪些 Pod"，不关心 Pod 是谁创建的。你可以用 kubectl run 直接创建 Pod，再写 Service 选中它。但生产中通常 Deployment + Service 配合使用。

完整示例

通过命令直观感受 Service 的"稳定"：

易错点

  1. ❌ 误认为"Service 就是 Pod 的别名"。✅ Service 是独立的 K8s 资源，有自己的 IP、DNS 名、生命周期，通过 selector 关联 Pod。
  2. ❌ 误认为"Service IP 能 ping 通"。✅ ClusterIP 是虚拟 IP，ping 不通但 curl 能访问（kube-proxy 通过 iptables/IPVS 转发）。
  3. ❌ 误认为"删了 Pod Service 也要重建"。✅ Service 独立于 Pod，Pod 重建不影响 Service，Service 自动通过 Endpoints 感知新 Pod。
  4. ❌ 误认为"Service 必须配合 Deployment"。✅ Service 只要有 Pod 即可（任意方式创建的 Pod），但生产中通常 Deployment+Service 配合。

小结

Service 是 K8s 中将一组 Pod 暴露为网络服务的抽象，提供稳定 IP（ClusterIP）+ 稳定 DNS 名 + 负载均衡三大能力，解决"Pod IP 不固定、Pod 会重建、需要负载均衡"三个问题。Service 通过 selector 关联 Pod，通过 Endpoints 跟踪 Pod IP，Pod 变化对调用方透明。

知识点 K18-2：Service 类型详解

定义

K8s Service 有四种类型，从"仅集群内访问"到"对外暴露"再到"对接外部服务"，覆盖不同场景：

类型 访问范围 关键特征 典型场景
ClusterIP（默认） 集群内部 分配集群内虚拟 IP 内部服务间通信（后端访问数据库）
NodePort 集群外部（节点端口） 在每个节点开放一个端口（30000-32767） 临时对外调试、非云环境对外
LoadBalancer 集群外部（云负载均衡） 云厂商自动创建负载均衡器 云生产环境对外暴露服务
ExternalName 集群内部访问外部 通过 CNAME 映射到外部域名 集群内应用访问外部服务（如 RDS）

问题 / 场景

问：生产环境对外暴露 Web 服务，用 NodePort 还是 LoadBalancer？

  • 看环境。① 云厂商 K8s（ACK/ACK/TKE）用 LoadBalancer（自动创建云 LB，有公网 IP，端口任意）；② 本地/裸机 K8s 用 NodePort 或 Ingress（NodePort 端口范围受限 30000-32767，不优雅）；③ 生产环境最常用的是 Ingress（七层路由，基于域名/路径分发，下节课学），Ingress 底层通常基于 NodePort 或 LoadBalancer。

问：NodePort 的端口范围能改吗？

  • 能。默认 30000-32767，通过 kube-apiserver 的 --service-node-port-range 参数配置。但不建议改，保持默认便于运维。

问：ExternalName 和把外部数据库地址直接写在应用配置里有什么区别？

  • 解耦。用 ExternalName 后，应用配置里写的是 Service 名（my-db.ctts.svc.cluster.local），不关心外部地址。如果外部数据库换了地址，只需改 Service 的 externalName 字段，应用无需重新部署。这是"接口稳定、实现可变"的体现。

问：Minikube 创建 LoadBalancer 会怎样？

  • EXTERNAL-IP 一直显示 <pending>，因为 Minikube 没有云厂商的 LB 控制器。可以用 minikube tunnel 命令模拟（在另一个终端运行），但本质还是 NodePort。本课程主要在 Minikube 上实践，所以 LoadBalancer 仅了解原理。

完整示例

四种 Service 类型 YAML 对比：

# ============================================================
# 类型 1：ClusterIP（默认，最常用）
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: ctts-backend
  namespace: ctts
spec:
  type: ClusterIP                          # 默认，可省略
  selector:
    app: ctts-backend                      # 关联 app=ctts-backend 的 Pod
  ports:
  - port: 8080                             # Service 端口
    targetPort: 8080                       # Pod 端口（containerPort）
    protocol: TCP
    name: http

# ============================================================
# 类型 2：NodePort（对外暴露）
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: ctts-frontend-nodeport
  namespace: ctts
spec:
  type: NodePort                           # NodePort 类型
  selector:
    app: ctts-frontend
  ports:
  - port: 80                               # Service 端口（集群内访问）
    targetPort: 80                         # Pod 端口
    nodePort: 30080                        # 节点端口（外部访问，30000-32767）
    protocol: TCP
    name: http

# ============================================================
# 类型 3：LoadBalancer（云生产对外）
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: ctts-frontend-lb
  namespace: ctts
spec:
  type: LoadBalancer                       # LoadBalancer 类型
  selector:
    app: ctts-frontend
  ports:
  - port: 80                               # Service 端口
    targetPort: 80                         # Pod 端口
    protocol: TCP
    name: http
# 应用后云厂商自动创建 LB，分配 EXTERNAL-IP
# Minikube 上 EXTERNAL-IP 会一直 <pending>

# ============================================================
# 类型 4：ExternalName（对接外部服务）
# ============================================================
apiVersion: v1
kind: Service
metadata:
  name: external-db
  namespace: ctts
spec:
  type: ExternalName                       # ExternalName 类型
  externalName: rm-xxx.mysql.rds.aliyuncs.com
# 无 selector、无 ports、无 ClusterIP
# 集群内访问 external-db.ctts.svc.cluster.local
# → DNS CNAME → rm-xxx.mysql.rds.aliyuncs.com

把集群内服务名映射到外部 DNS 名称，不创建代理规则。

CTTS 内部服务优先 ClusterIP；真正对外访问通常交给 Ingress，而不是直接暴露每个 Service。

易错点

  1. ❌ 误认为"NodePort 没有 ClusterIP"。✅ NodePort 在 ClusterIP 基础上扩展，仍有 ClusterIP，集群内仍可通过 ClusterIP 访问。
  2. ❌ 误认为"Minikube 能用 LoadBalancer"。✅ Minikube 无云 LB 控制器，EXTERNAL-IP 一直 <pending>，可用 minikube tunnel 模拟但本质是 NodePort。
  3. ❌ 误认为"ExternalName 有 ClusterIP 和 Endpoints"。✅ ExternalName 无 ClusterIP、无 Endpoints，只是 DNS CNAME 映射。
  4. ❌ NodePort 的 nodePort 字段省略时认为不工作。✅ 省略时 K8s 自动分配 30000-32767 范围内端口。
  5. ❌ 把 NodePort 用于生产对外。✅ NodePort 端口范围受限（30000-32767）、暴露节点 IP 不优雅，生产对外通常用 Ingress 或 LoadBalancer。

小结

Service 四种类型覆盖不同访问场景：ClusterIP（默认，集群内部）、NodePort（节点端口对外）、LoadBalancer（云负载均衡对外）、ExternalName（CNAME 映射外部域名）。选型原则：内部通信用 ClusterIP；临时对外用 NodePort；云生产对外用 LoadBalancer；对接外部服务用 ExternalName。生产环境对外暴露 Web 服务通常用 Ingress（下节课学）。

知识点 K18-3：Service YAML 结构

定义

Service YAML 是声明式定义 Service 的 K8s 资源清单，包含 apiVersion、kind、metadata、spec 四个顶层字段。spec 中通过 type 指定类型、selector 关联 Pod、ports 定义端口映射。

原理

Service YAML 完整结构：

apiVersion: v1                       # Service 的 apiVersion 固定为 v1（注意不是 apps/v1）
kind: Service                        # 资源类型固定为 Service
metadata:
  name: <service-name>               # Service 名称（即 DNS 名的第一段）
  namespace: <ns>                    # 所属命名空间
  labels:                            # Service 自身的标签（可选）
    app: <app>
spec:
  type: <ClusterIP|NodePort|LoadBalancer|ExternalName>   # 类型，默认 ClusterIP
  selector:                          # 标签选择器，关联 Pod
    <key>: <value>                   # 必须与 Pod 的 labels 匹配
  ports:                             # 端口配置（可多个）
  - name: <port-name>                # 端口名（可选，多端口时建议命名）
    port: <service-port>             # Service 对外的端口（ClusterIP 上访问的端口）
    targetPort: <pod-port>           # Pod 的端口（containerPort，可省略则等于 port）
    nodePort: <node-port>            # 节点端口（仅 NodePort/LoadBalancer 类型，30000-32767）
    protocol: <TCP|UDP>              # 协议，默认 TCP
  sessionAffinity: <None|ClientIP>   # 会话亲和性（可选，默认 None 轮询）
  externalName: <external-domain>    # 仅 ExternalName 类型用
  externalIPs:                       # 外部 IP（可选，了解）
  - <ip>

问题 / 场景

问：targetPort 省略时会怎样？

  • 省略时 targetPort 默认等于 port。如 port: 8080（省略 targetPort）→ targetPort 也是 8080。如果 Pod 的 containerPort 与 Service port 不同，必须显式指定 targetPort。

问：targetPort 可以用端口名而不是数字吗？

  • 可以。Pod YAML 里 containerPort 可以命名（name: http），Service 的 targetPort 可以引用这个名（targetPort: http）。好处：Pod 端口变了不用改 Service YAML。本课了解即可。

问：一个 Service 可以暴露多个端口吗？

  • 可以。如一个 Service 同时暴露 80（HTTP）和 443（HTTPS）。多端口时每个端口必须命名（name: http / name: https）。示例：
spec:
  ports:
  - name: http
    port: 80
    targetPort: 8080
  - name: https
    port: 443
    targetPort: 8443

问：sessionAffinity 什么时候用？

  • 当应用需要"会话保持"时（如登录后必须连同一个 Pod），设 sessionAffinity: ClientIP，同一客户端 IP 的请求会固定打到同一 Pod（默认保持 10800 秒=3 小时）。但有副作用：Pod 挂了会话会断。一般推荐应用本身做会话共享（如 Redis Session），不依赖 Service 会话亲和。

知识点 K18-4：标签选择器与 Endpoints

定义

标签选择器（Label Selector） 是 Service 关联 Pod 的机制：Service 通过 spec.selector 声明要选择哪些标签的 Pod，K8s 自动把匹配的 Pod 加入 Service 的后端列表。

Endpoints（端点） 是 Service 的后端 Pod IP:端口列表，由 K8s EndpointsController 自动维护。Service 把流量转发到 Endpoints 里的 Pod。当 Pod 创建/删除/Ready 状态变化时，Endpoints 自动更新。

原理

selector → Endpoints → Pod 的关联机制：

图示 15：Service: ctts-backend
  •     Service: ctts-backend
  •     spec.selector: { app: ctts-backend }

  •   自动把匹配 selector 且 Ready 的 Pod 加入 Endpoints
  •     Endpoints: ctts-backend
  •     Addresses:
  •     - 10.244.1.10:8080 (Pod1, Ready)
  •     - 10.244.1.11:8080 (Pod2, Ready)
  •     - 10.244.1.12:8080 (Pod3, Ready)
  •   kube-proxy 在节点上配置 iptables/IPVS 规则
  •   把发往 ClusterIP 的流量 DNAT 到 Endpoints
  •     Pod1 (10.244.1.10) Pod2 (10.244.1.11) Pod3 (10.244.1.12)
  •     labels: app=ctts-backend

  • ① Service 创建时，EndpointsController 根据 selector 找到匹配的 Pod
  • ② 把 Ready 的 Pod IP:targetPort 加入 Endpoints
  • ③ Pod 变化时（新建/删除/NotReady），Endpoints 自动更新

  • ⑤ 流量通过 ClusterIP → iptables → Pod IP（负载均衡）

问题 / 场景

问：Endpoints 和 Service 是同一个资源吗？

  • 不是。Service 和 Endpoints 是两个独立的 K8s 资源。Service 定义"访问入口"（IP、DNS、端口、selector），Endpoints 定义"后端 Pod 列表"（IP:port）。K8s 自动根据 Service 的 selector 创建和维护 Endpoints。用 kubectl get endpoints 可以看到独立的 Endpoints 资源。

问：Pod 状态是 Running 但不在 Endpoints 里？

  • 可能原因：① readinessProbe 没通过（Pod Running 但 NotReady）；② selector 不匹配（Pod labels 与 Service selector 不一致）；③ Pod 在不同 namespace（Service 只选同 namespace 的 Pod）。排查：kubectl get endpoints <svc> -n <ns> 看是否有 IP，kubectl describe pod <pod> 看 readinessProbe 状态。

问：Endpoints 为空（No endpoints）怎么办？

  • 三步排查：① kubectl describe svc <svc> 看 Selector；② kubectl get pods -l <selector> --show-labels 确认有匹配的 Pod；③ kubectl get pods -l <selector> 确认 Pod 都是 Ready。常见根因：selector 写错、Pod 还没 Ready、Pod 在不同 namespace。

问：无选择器 Service 什么时候用？

  • 当你想通过 Service 的稳定 DNS 名访问集群外部的服务（IP 已知）时。例如：自建 MySQL 在 192.168.1.100，集群内应用想用 my-db.ctts.svc.cluster.local 访问，可以创建无选择器 Service + 手动 Endpoints 指向 192.168.1.100。比 ExternalName 更底层（L4 转发而非 DNS CNAME）。

易错点

  1. ❌ 误认为"Service 和 Endpoints 是同一个资源"。✅ 二者是独立的 K8s 资源，kubectl get endpoints 单独查看。

知识点 K18-5：DNS 服务发现

定义

DNS 服务发现 是 K8s 中 Pod 通过 Service 名自动解析到 Service ClusterIP 的机制。K8s 集群内置 CoreDNS 组件，为每个 Service 自动创建 DNS 记录，Pod 内直接用 Service 名（或完整 DNS 名）即可访问服务，无需查 IP。

原理

CoreDNS 工作机制：

图示 19：K8s 集群

集群内访问路径

Pod 不需要知道目标 Pod IP，只需要访问 Service 名称。

Frontend Pod

curl backend-service:8080

→

CoreDNS 解析并转发

→

Backend Pod

真实业务副本

Service DNS 名格式：

完整格式：
  <service-name>.<namespace>.svc.cluster.local

示例（ctts namespace 下的 mysql Service）：
  mysql.ctts.svc.cluster.local

解析层级：
  mysql                              ← 同 namespace 内可省略后缀
  mysql.ctts                         ← 同 namespace 内的简写
  mysql.ctts.svc                     ← 含 svc
  mysql.ctts.svc.cluster.local       ← 完整 FQDN（Fully Qualified Domain Name）

实际使用：
  同 namespace 访问：直接用 Service 名即可（mysql）
  跨 namespace 访问：用 <service-name>.<namespace>（mysql.ctts）
  完整访问：<service-name>.<namespace>.svc.cluster.local

Pod 的 DNS 配置：

# 查看任意 Pod 的 /etc/resolv.conf
kubectl exec -it deployment/ctts-backend -n ctts -- cat /etc/resolv.conf
# 预期输出：
# nameserver 10.96.0.10
# search ctts.svc.cluster.local svc.cluster.local cluster.local
# options ndots:5

# 解释：
# nameserver 10.96.0.10  → CoreDNS Service IP
# search ctts.svc.cluster.local svc.cluster.local cluster.local
#   → 解析时自动补全后缀（先 ctts.svc.cluster.local，再 svc.cluster.local...）
# options ndots:5
#   → 名字里有 5 个点以上才走完整 FQDN 解析，否则先走 search 补全

问题 / 场景

问：为什么 Pod 内直接用 Service 名（如 mysql）就能访问？

  • 因为 Pod 的 /etc/resolv.conf 配置了 search 后缀。当 Pod 查询 mysql 时，CoreDNS 自动补全为 mysql.ctts.svc.cluster.local（Pod 所在 namespace），找到对应 Service 记录。所以同 namespace 内直接用 Service 名最方便。

问：跨 namespace 访问 Service 怎么写？

  • 用 <service-name>.<namespace>。如 default namespace 的 Pod 访问 ctts namespace 的 mysql Service，写 mysql.ctts。CoreDNS 会补全为 mysql.ctts.svc.cluster.local。

问：CoreDNS 挂了会怎样？

  • 集群内所有用 DNS 名的访问会失败（如 mysql.ctts.svc.cluster.local 解析不了）。但用 ClusterIP 直接访问仍可（IP 转发不依赖 DNS）。CoreDNS 通常多副本部署保证高可用，生产环境监控 CoreDNS 状态是运维重点。

问：可以用 IP 而不用 DNS 名吗？

  • 可以但不推荐。直接用 ClusterIP 也能访问（iptables 转发不依赖 DNS），但 IP 不直观、不易维护、迁移环境会变。生产中一律用 DNS 名，DNS 名稳定可读。

问：Headless Service 是什么？

  • 普通服务（ClusterIP）DNS 解析返回 Service ClusterIP。Headless Service（clusterIP: None）DNS 解析直接返回后端 Pod IP 列表，不经过 Service IP 转发。适用场景：StatefulSet（如 MySQL 主从）、客户端需要知道所有 Pod IP 的场景。本课了解，第 22 次课 StatefulSet 会用到。

定义

CTTS 各 Service 创建 是为第 17 次课部署的三个 Deployment（MySQL / Backend / Frontend）分别编写标准 Service YAML 并应用到集群的实操。通过本知识点，你将打通 CTTS 服务间通信全链路：前端通过 ctts-backend Service 名访问后端，后端通过 mysql Service 名访问数据库。

MySQL

ClusterIP，仅后端在集群内访问。

Backend

ClusterIP，供前端或 Ingress 内部路由访问。

Frontend / Ingress

只有真正入口暴露给用户。

最小暴露原则：能不出集群就不出集群，能通过 Ingress 统一入口就不要散开多个外部端口。

问题 / 场景

问：为什么前端 Service 不直接用 NodePort 对外？

  • ① NodePort 端口范围受限（30000-32767），用户访问要带端口号（如 :30080），不友好；② 暴露节点 IP 不优雅（节点 IP 可能变化、多节点 IP 不一致）；③ 生产环境通常用 Ingress（七层路由、域名、HTTPS、路径分发），下节课学。本课前端用 ClusterIP + port-forward 调试。

问：mysql Service 名为什么叫 mysql 而不是 ctts-mysql？

  • 后端代码里连接数据库的 host 是 mysql（环境变量 DB_HOST=mysql.ctts.svc.cluster.local）。Service 名决定了 DNS 名第一段，叫 mysql 则 DNS 名是 mysql.ctts.svc.cluster.local，与后端环境变量匹配。如果叫 ctts-mysql 则 DNS 名是 ctts-mysql.ctts.svc.cluster.local，需要改后端环境变量。命名要与代码约定一致。

问：上节课用 kubectl expose 创建的 Service 怎么处理？

  • 上节课临时用 kubectl expose deployment ctts-mysql --name=mysql 创建了 mysql 和 ctts-backend 两个 Service。本课用 YAML 重新创建（标准做法）。可以先 kubectl delete svc mysql ctts-backend -n ctts 删除旧的，再 kubectl apply -f 创建新的。YAML 创建比 kubectl expose 更规范（可版本化、可复用）。

问：Service 创建后还需要做什么？

  • 验证三件事：① kubectl get svc 看 Service 创建成功；② kubectl get endpoints 看 Endpoints 有后端 Pod；③ 在 Pod 内 nslookup + curl 验证 DNS 解析和访问。

易错点

  1. ❌ Service 名与后端代码约定的 DNS 名不一致。✅ Service 名决定 DNS 名第一段，必须与后端环境变量（如 DB_HOST）匹配。本课 mysql Service 名是 mysql，后端 DB_HOST=mysql.ctts.svc.cluster.local。
  2. ❌ selector 与 Deployment 的 Pod labels 不匹配。✅ 三 Deployment 的 Pod labels 分别是 app=ctts-mysql / app=ctts-backend / app=ctts-frontend，Service selector 必须对应。
  3. ❌ 端口写错（如 mysql Service port 写 3306 但 targetPort 写 3307）。✅ targetPort 必须与 Pod 的 containerPort 一致（mysql:3306, backend:8080, frontend:80）。
  4. ❌ 忘记删除上节课 kubectl expose 创建的旧 Service。✅ 用 YAML 创建前先 kubectl delete svc 清理旧的，避免冲突。
  5. ❌ 把内部 Service（mysql / ctts-backend）暴露为 NodePort。✅ 内部服务一律 ClusterIP，对外仅暴露前端（且生产用 Ingress）。
  6. ❌ Service 创建后不验证 Endpoints。✅ 一定要 kubectl get endpoints 确认有后端 Pod，否则 Service 访问不通。

小结

CTTS 三 Service 创建：为 MySQL / Backend / Frontend 三 Deployment 分别创建 ClusterIP Service，selector 对应 Pod 标签（app=ctts-mysql / app=ctts-backend / app=ctts-frontend），端口对应 containerPort（3306 / 8080 / 80）。创建后用 kubectl get svc、kubectl get endpoints、kubectl exec nslookup、kubectl exec curl 四步验证。三个 Service 都用 ClusterIP（最小暴露原则），前端临时用 port-forward 或 NodePort 调试，生产用 Ingress（下节课）。完成后 CTTS 内部全链路通过 Service 名通信：Frontend → ctts-backend Service → Backend → mysql Service → MySQL。

===================================================

一、设计阶段（K18-1、K18-2、K18-6）

  ① 确定需要三个 Service：
     - mysql Service（后端访问数据库）
     - ctts-backend Service（前端访问后端）
     - ctts-frontend Service（外部访问前端）

  ② 确定类型：
     - mysql: ClusterIP（仅内部）

     kubectl delete svc mysql ctts-backend -n ctts

  ③ kubectl apply -f ctts-services.yaml -n ctts

  ① 内部访问：Pod 内通过 Service 名访问（K18-5）
  ② 临时外部访问：kubectl port-forward svc/ctts-frontend 8081:80
  ③ 节点端口访问（可选）：patch 为 NodePort，浏览器访问 minikube-ip:30080
  ④ 生产外部访问：Ingress（第 19 次课学）

四、拓展阅读（选学）

  1. kube-proxy 三种模式：userspace（旧，已废弃）/ iptables（默认）/ IPVS（高性能，生产推荐）。kube-proxy 监听 Service 和 Endpoints 变化，在节点上配置转发规则。IPVS 模式支持更多负载均衡算法（轮询/最少连接/源地址哈希等）。

  2. Headless Service：clusterIP: None 的 Service，DNS 解析直接返回 Pod IP 列表（不返回 ClusterIP）。适用场景：StatefulSet（如 MySQL 主从、Zookeeper）、客户端需要知道所有 Pod IP 的场景。第 22 次课 StatefulSet 会用到。

  3. Service Mesh（服务网格）：Istio/Linkerd 等 Service Mesh 在 Service 之上提供流量管理（熔断/重试/灰度/可观测）。本课了解，云原生进阶方向。

  4. EndpointSlices：K8s 1.21+ 用 EndpointSlice 替代 Endpoints（一个 Service 后端 Pod 很多时，Endpoints 单对象太大，EndpointSlice 分片更高效）。kubectl get endpointslice 查看。功能与 Endpoints 类似。

  5. Service 的 trafficDistribution 字段：K8s 1.21+ 引入，支持"就近路由"（PreferClose），让流量优先发给同节点/同区域的 Pod，减少跨节点流量。本课了解。

  6. 拓扑感知路由（Topology Aware Routing）：基于节点拓扑（区域/可用区）的流量路由，减少跨区流量费用。生产环境云厂商 K8s 常用。

为什么需要 Service

Pod IP、数量、位置都不稳定，需要稳定入口。

核心机制

selector 选中 Pod，Endpoints/EndpointSlice 维护真实后端。

Service 类型

ClusterIP、NodePort、LoadBalancer、ExternalName 对应不同访问范围。

CoreDNS 提供 service.namespace.svc.cluster.local 名称解析。

CTTS 实践

frontend、backend、mysql 都用 Service 建立稳定访问入口。

暴露原则

内部服务用 ClusterIP，对外入口留给 Ingress 或网关。

一句话总结

Service 为短暂的 Pod 提供稳定的访问入口（ClusterIP + DNS 名 + 负载均衡），通过 selector 关联 Pod、Endpoints 跟踪 Pod IP、CoreDNS 实现 DNS 解析，使 CTTS 三服务能通过 Service 名互相通信，解耦服务间依赖。
