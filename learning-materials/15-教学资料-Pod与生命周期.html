二、知识点详解

知识点 K15-1：Pod 概念

定义

Pod 是 Kubernetes 中能够创建和部署的最小单元，是 K8s 调度的最小单位。一个 Pod 可以包含一个或多个容器，这些容器共享网络和存储资源，作为一个整体被调度到同一个节点上运行。

一句话理解：

Pod 是 K8s 的"最小调度单元"——K8s 不直接管容器，而是把一个或多个容器打包成 Pod 来管理。

原理

为什么 K8s 需要引入 Pod，而不是直接管容器？

Docker 的管理方式：
  docker run -d --name backend ctts-backend:v1
  → 直接操作容器

K8s 的管理方式：
  kubectl apply -f pod.yaml
  → 创建 Pod（里面包含容器）
  → K8s 调度 Pod 到某个节点
  → 节点上的容器运行时启动 Pod 内的容器

引入 Pod 的三个核心原因：

原因 说明
① 容器组的管理需求 实际应用中，一个业务往往需要多个紧密协作的容器（如主容器 + 日志收集 sidecar），Pod 把它们作为一个整体调度和管理
② 共享网络与存储 Pod 内的容器共享同一个网络命名空间（IP、端口空间）和存储卷，容器间可通过 localhost 通信
③ 屏蔽容器运行时差异 K8s 通过 Pod 抽象屏蔽了 Docker/containerd/CRI-O 等不同运行时的差异，K8s 只管 Pod，不管底层容器

单容器 Pod vs 多容器 Pod：

模式 说明 应用场景
单容器 Pod Pod 内只有 1 个容器（最常见） 简单应用部署（如 CTTS 后端单独一个 Pod）
多容器 Pod Pod 内有多个紧密协作的容器 主容器 + sidecar（如日志收集、监控代理、配置代理）

📌 绝大多数 Pod 是单容器 Pod。多容器 Pod 用于"主容器 + 辅助容器"的紧密协作场景，辅助容器称为 sidecar。本课程重点掌握单容器 Pod，多容器 Pod 了解概念即可。

问题 / 场景

问：Pod 和容器到底是什么关系？

  • Pod 是 K8s 的最小调度单元，容器是 Pod 内的组成部分。K8s 不直接调度容器，而是调度 Pod。一个 Pod 可以含 1 个或多个容器。类比：Pod 是"集装箱"，容器是集装箱里的"货物"。

问：为什么 K8s 不直接管容器，非要多一层 Pod？

  • 三个原因：① 实际应用中多个容器需要紧密协作（如 backend + log-agent），Pod 把它们作为一个整体调度和管理；② Pod 内容器共享网络和存储，容器间通过 localhost 通信非常方便；③ Pod 抽象屏蔽了容器运行时差异，K8s 只管 Pod，不管底层是 Docker 还是 containerd。

问：Pod 内的容器能互相通信吗？

  • 能。Pod 内所有容器共享同一个网络命名空间，即同一个 IP 和端口空间。容器 A 访问容器 B，直接 localhost:<B的端口> 即可。这是 Pod 内多容器协作的基础。

问：Pod 是长期运行的吗？

  • Pod 是临时性的，不是持久的。Pod 会因为节点故障、资源不足、人为删除等原因消失。所以生产中不直接管理裸 Pod，而是用 Deployment/StatefulSet 等工作负载来管理 Pod（保证副本数，自动重建）。裸 Pod 主要用于学习、调试、一次性任务。第 16 次课学习 Deployment。

完整示例

单容器 Pod 与多容器 Pod 的对比示例（YAML 片段，完整 YAML 见 K15-2）：

# 单容器 Pod（CTTS 后端，最常见）
apiVersion: v1
kind: Pod
metadata:
  name: ctts-backend
spec:
  containers:
  - name: backend                # 只有 1 个容器
    image: ctts-backend:v1
    ports:
    - containerPort: 8080

---

# 多容器 Pod（主容器 + sidecar 日志收集）
apiVersion: v1
kind: Pod
metadata:
  name: ctts-backend-with-logs
spec:
  containers:
  - name: backend                # 主容器
    image: ctts-backend:v1
    ports:
    - containerPort: 8080
  - name: log-agent              # sidecar 容器（日志收集）
    image: busybox:1.36
    command: ["sh", "-c", "tail -f /var/log/app.log"]
    volumeMounts:
    - name: log-volume
      mountPath: /var/log
  volumes:
  - name: log-volume
    emptyDir: {}

易错点

  1. ❌ 误认为"K8s 直接操作容器"。✅ K8s 操作的是 Pod，Pod 是最小调度单元，容器是 Pod 内的组成部分。
  2. ❌ 误认为"一个 Pod 只能有一个容器"。✅ 一个 Pod 可以含多个容器（常见 sidecar 模式），但绝大多数 Pod 是单容器。
  3. ❌ 误认为"Pod 是持久的"。✅ Pod 是临时性的，会因节点故障、资源不足、人为删除等原因消失。生产中用 Deployment 管理 Pod。
  4. ❌ 误认为"Pod 内容器通过 IP 互相通信"。✅ Pod 内容器共享网络命名空间，通过 localhost 通信，不是通过 Pod IP。

小结

Pod 是 K8s 最小调度单元，K8s 不直接管容器而管 Pod。Pod 内容器共享网络（localhost 通信）和存储。一个 Pod 可含多个容器（sidecar 模式）。Pod 是临时性的，生产中用 Deployment 管理。

知识点 K15-2：Pod YAML 结构

定义

Pod YAML 是用 YAML 格式描述 Pod 的声明式配置文件，告诉 K8s"我要创建一个什么样的 Pod"。K8s 读取 YAML 后，会按 YAML 的描述创建并维持 Pod。

Pod YAML 的四要素：

要素 作用 必填
apiVersion API 版本（Pod 用 v1） 是
kind 资源类型（Pod） 是
metadata 元数据（name / labels / namespace 等） 是（name 必填）
spec 规格（定义 Pod 的内容，主要是 containers） 是

原理

Pod YAML 的完整结构：

apiVersion: v1                    # ① API 版本
kind: Pod                         # ② 资源类型
metadata:                         # ③ 元数据
  name: <pod-name>                #    Pod 名称（namespace 内唯一）
  namespace: <ns>                 #    所在 namespace（默认 default）
  labels:                         #    标签（键值对，用于选择）
    app: <label-value>
spec:                             # ④ 规格（核心）
  containers:                     #    容器列表（至少 1 个）
  - name: <container-name>        #    容器名称（Pod 内唯一）
    image: <image:tag>            #    镜像
    ports:                        #    容器端口
    - containerPort: <port>
    env:                          #    环境变量
    - name: <env-name>
      value: <env-value>
    resources:                    #    资源限制
      requests:
        cpu: <value>
        memory: <value>
      limits:
        cpu: <value>
        memory: <value>
    command: [<cmd>]              #    启动命令（覆盖镜像 ENTRYPOINT）
    args: [<arg1>, <arg2>]        #    启动参数（覆盖镜像 CMD）
    imagePullPolicy: <policy>     #    镜像拉取策略
  restartPolicy: <policy>         #    重启策略（Always/Never/OnFailure）

四要素详解：

① apiVersion: v1
   - Pod 属于 K8s 核心 API，版本是 v1（稳定版）
   - 注意：不同资源 apiVersion 不同（如 Deployment 是 apps/v1）

② kind: Pod
   - 资源类型，Pod 必须写 "Pod"（首字母大写）

③ metadata（元数据）
   - name：Pod 名称，namespace 内唯一，必填
   - namespace：所在 namespace，不填默认 default
   - labels：标签（键值对），用于 Service/Deployment 选择 Pod
   - annotations：注解（非标识性元数据，可选）

④ spec（规格）
   - containers：容器列表，至少 1 个
   - restartPolicy：重启策略（Always 默认 / Never / OnFailure）
   - volumes：存储卷（可选，多容器共享时用）
   - nodeSelector：节点选择器（可选，指定调度到哪些节点）

metadata 三要素对比：

字段 作用 示例 说明
name Pod 的唯一标识 ctts-backend namespace 内唯一，必填
namespace 所在 namespace ctts 资源隔离，不填默认 default
labels 标签键值对 app: ctts-backend 用于 Service/Deployment 选择 Pod

问题 / 场景

问：apiVersion 为什么是 v1？其他资源也是 v1 吗？

  • Pod 是 K8s 核心资源，apiVersion 是 v1（稳定版）。不同资源 apiVersion 不同：
    • Pod / Service / ConfigMap / Secret → v1
    • Deployment / ReplicaSet / DaemonSet → apps/v1
    • Ingress → networking.k8s.io/v1
    • Job / CronJob → batch/v1

问：name 和 labels 有什么区别？

  • name 是 Pod 的唯一标识，namespace 内不能重复。labels 是标签键值对，用于"选择"，可以被 Service/Deployment 通过 selector 选中。一个 name 只对应一个 Pod，但一个 label 可以对应多个 Pod（如 app: backend 可以匹配所有 backend Pod）。

问：YAML 里缩进错了会怎样？

  • YAML 严格要求缩进（空格，不能用 Tab），缩进错了 kubectl apply 会报错。建议用 2 空格缩进。可以用 kubectl apply -f pod.yaml --dry-run=client 先校验 YAML 语法。

问：spec 里除了 containers 还有什么字段？

  • spec 里核心是 containers（容器列表），还可以有：restartPolicy（重启策略）、volumes（存储卷）、nodeSelector（节点选择）、affinity（亲和性）、initContainers（初始化容器）等。本节课重点掌握 containers 和 restartPolicy，其他后续课程涉及。

完整示例

一份完整的 Pod YAML（含所有核心字段，后续 K15-3 详解每个字段）：

# 文件名：ctts-backend-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: ctts-backend
  namespace: ctts
  labels:
    app: ctts-backend
    tier: backend
spec:
  containers:
  - name: backend
    image: ctts-backend:v1
    imagePullPolicy: IfNotPresent
    ports:
    - containerPort: 8080
      name: http
    env:
    - name: SPRING_PROFILES_ACTIVE
      value: prod
    - name: DB_HOST
      value: mysql
    resources:
      requests:
        cpu: "500m"
        memory: "512Mi"
      limits:
        cpu: "1000m"
        memory: "1Gi"
    command: ["java", "-jar"]
    args: ["/app/app.jar", "--spring.profiles.active=$(SPRING_PROFILES_ACTIVE)"]
  restartPolicy: Always

易错点

  1. ❌ 忘写 apiVersion 或 kind。✅ 四要素缺一不可，kubectl apply 会报错。
  2. ❌ kind 写成小写 pod。✅ 必须首字母大写 Pod。
  3. ❌ metadata.name 和容器名混淆。✅ metadata.name 是 Pod 名，containers[].name 是容器名，二者不同。
  4. ❌ YAML 用 Tab 缩进。✅ YAML 严格用空格缩进（2 空格），不能用 Tab。
  5. ❌ labels 值不用引号导致解析错误。✅ 含特殊字符的值要加引号，如 version: "1.0"。

小结

Pod YAML 四要素：apiVersion（v1）、kind（Pod）、metadata（name/namespace/labels）、spec（containers 等）。metadata.name 是 Pod 唯一标识，labels 用于被 Service/Deployment 选择。spec.containers 是容器列表，至少 1 个。YAML 严格用空格缩进。

知识点 K15-3：容器定义详解

定义

Pod YAML 中 spec.containers[] 定义 Pod 内的容器，每个容器包含以下核心字段：

字段 作用 必填
name 容器名称（Pod 内唯一） 是
image 容器镜像（含仓库地址和标签） 是
ports 容器暴露的端口列表 否（但建议写）
env 环境变量列表 否
resources 资源限制（requests / limits） 否（但生产必填）
command 启动命令（覆盖镜像 ENTRYPOINT） 否
args 启动参数（覆盖镜像 CMD） 否
imagePullPolicy 镜像拉取策略 否（有默认值）

原理

各字段详解：

1. name（容器名）

  • Pod 内唯一，用于标识容器
  • 小写字母、数字、-，首尾须字母数字

2. image（镜像）

  • 格式：[仓库地址/]镜像名:标签
  • 例：ctts-backend:v1、mysql:8.0、registry.cn-hangzhou.aliyuncs.com/xxx/app:v1
  • 不写标签默认 :latest（生产环境不建议用 latest）

3. ports（端口）

  • 声明容器暴露的端口，供 Service 引用
  • containerPort：容器内端口
  • name：端口名（可选，便于 Service 引用）
  • 注意：ports 字段只是"声明"，不写也能访问；写了主要是文档性和被 Service 引用

4. env（环境变量）

  • 列表形式，每项含 name 和 value
  • 也可从 ConfigMap/Secret 引用（valueFrom，第 21 次课讲）
  • 用于向容器传递配置（如 SPRING_PROFILES_ACTIVE=prod）

5. resources（资源限制）— 重点

  • 分为 requests（请求）和 limits（上限）
resources:
  requests:          # 请求（保底）——影响调度
    cpu: "500m"      #    至少分配 0.5 核
    memory: "512Mi"  #    至少分配 512Mi
  limits:            # 上限（限制）——限制最大用量
    cpu: "1000m"     #    最多用 1 核
    memory: "1Gi"    #    最多用 1Gi

requests 和 limits 的区别（面试常考）：

对比项 requests limits
含义 请求量（保底） 上限量（限制）
作用 调度依据（kubelet 保证至少有这么多资源） 限制上限（超过会被限制或杀掉）
影响 影响 Pod 调度到哪个节点 影响 Pod 运行时最大资源用量
不设的后果 默认按 limits 算（若 limits 也没设则无保障） 无上限，可能挤占其他 Pod

📌 生产环境 requests 和 limits 都必须设置。只设 limits 不设 requests，Pod 调度时按 limits 算，可能调度失败；只设 requests 不设 limits，Pod 可能用爆节点资源。

CPU 和内存的单位：

  • CPU：m（millicore，毫核），1000m = 1 核。500m = 0.5 核
  • 内存：Mi（MiB）、Gi（GiB）、Ki、Ti。注意是二进制单位（1Mi=1024Ki）

6. command 和 args（启动命令）

  • command：覆盖镜像的 ENTRYPOINT
  • args：覆盖镜像的 CMD
  • 与 Dockerfile 的对应关系：
Dockerfile            K8s YAML            最终执行
ENTRYPOINT ["java"]   command: ["java"]   java -jar app.jar
CMD ["-jar","app.jar"] args: ["-jar","app.jar"]
  • 如果镜像有 ENTRYPOINT 和 CMD，K8s 里只写 command 会覆盖 ENTRYPOINT 但保留 CMD 作为 args；只写 args 会覆盖 CMD 但保留 ENTRYPOINT

7. imagePullPolicy（镜像拉取策略）— 重点

策略 含义 适用场景
Always 每次创建容器都从仓库拉取镜像 用 :latest 标签时（默认）
Never 从不拉取，只用本地镜像 本地构建的镜像（如 Minikube Docker daemon 构建）
IfNotPresent 本地没有才拉取 明确版本标签的镜像（默认，当镜像标签不是 latest）

默认规则（重要）：

  • 镜像标签是 :latest 或不写标签 → 默认 Always
  • 镜像标签是明确版本（如 :v1、:8.0）→ 默认 IfNotPresent

📌 第 14 次课用 Minikube Docker daemon 构建的 ctts-backend:v1 镜像，部署时必须设置 imagePullPolicy: Never 或 IfNotPresent，否则 K8s 会去仓库拉取（拉不到会报 ImagePullBackOff）。

问题 / 场景

问：resources.requests 和 limits 到底有什么区别？

  • requests 是"保底"——告诉调度器"这个 Pod 至少需要 0.5 核 CPU 和 512Mi 内存"，调度器据此选择合适的节点。limits 是"上限"——告诉容器运行时"这个容器最多只能用 1 核 CPU 和 1Gi 内存"，超过 CPU 会被限流，超过内存会被 OOM 杀掉。

问：CPU 单位 500m 是什么意思？

  • m 是 millicore（毫核），1000m = 1 核 CPU。所以 500m = 0.5 核，200m = 0.2 核。这表示该容器最少（或最多）能用 0.5 核（或 0.2 核）CPU。

问：内存单位 Mi 和 M 有什么区别？

  • Mi 是二进制单位（1 MiB = 1024 KiB = 1024×1024 字节），M 是十进制单位（1 MB = 1000 KB = 1000×1000 字节）。K8s 推荐用 Mi/Gi。常见值：256Mi、512Mi、1Gi、2Gi。

问：imagePullPolicy 设错了会怎样？

  • 如果镜像在仓库不存在（如本地构建的 ctts-backend:v1），但 imagePullPolicy 设成 Always，K8s 会去仓库拉取，拉不到就报 ImagePullBackOff，Pod 一直 Pending。解决：把 imagePullPolicy 改成 Never 或 IfNotPresent。

问：ports 字段不写会怎样？

  • ports 只是"声明"，不写也能通过 Pod IP 访问容器端口。但写了有好处：① 文档性，让人知道容器监听哪个端口；② 被 Service 引用时可以用端口名（如 http）而不是数字。

问：command 和 args 跟 Dockerfile 的 ENTRYPOINT/CMD 什么关系？

  • K8s 的 command 覆盖 Dockerfile 的 ENTRYPOINT，K8s 的 args 覆盖 Dockerfile 的 CMD。如果 K8s YAML 里只写 command 不写 args，会用镜像的 CMD 作为 args；如果只写 args 不写 command，会用镜像的 ENTRYPOINT 作为命令。两个都不写，用镜像默认的 ENTRYPOINT + CMD。

知识点 K15-4：Pod 生命周期与状态

定义

Pod 生命周期是指 Pod 从创建到终止的整个过程。Pod 在其生命周期中会经历不同的状态（Phase），K8s 通过这些状态描述 Pod 当前处于什么阶段。

Pod 的五种状态（Phase）：

状态 含义 说明
Pending 挂起 Pod 已被 K8s 接受，但还没全部就绪（正在调度、正在拉镜像、正在创建容器）
Running 运行中 Pod 已被调度到节点，所有容器已创建，至少一个正在运行
Succeeded 成功 Pod 内所有容器都正常退出（exit code 0），不会再重启
Failed 失败 Pod 内所有容器都已终止，至少一个异常退出（exit code 非 0）
Unknown 未知 无法获取 Pod 状态，通常是跟节点失联（节点宕机或网络不通）

原理

Pod 创建流程（Pending → Running）：

1. 用户提交：kubectl apply -f pod.yaml
   ↓
2. API Server 接收 YAML，写入 etcd（Pod 状态 = Pending）
   ↓
3. Scheduler 调度：根据 requests 资源、nodeSelector 等选择节点
   ↓
4. Kubelet（目标节点上）接管：
   a. 调用容器运行时拉取镜像（imagePullPolicy）
   b. 创建容器（按 image + command + args + env）
   c. 挂载存储卷
   d. 启动容器
   ↓
5. 容器启动后，Pod 状态 = Running

Pod 重启策略（restartPolicy）：

策略 含义 适用场景
Always 容器退出后总是重启 长期运行的服务（默认值，Pod 默认用这个）
OnFailure 容器异常退出（非 0）才重启 一次性任务（Job）
Never 容器退出后不重启 一次性任务、调试

📌 Pod 的 restartPolicy 默认是 Always，意味着容器崩溃会自动重启。这也是为什么 Pod 一直 Running 的原因。但反复崩溃会进入 CrashLoopBackOff 状态（退避重启）。

Pod 终止流程：

1. 用户执行 kubectl delete pod <name>
   ↓
2. API Server 把 Pod 标记为 Terminating
   ↓
3. Kubelet 向容器发送 SIGTERM 信号（默认宽限期 30 秒）
   ↓
4. 容器收到 SIGTERM，优雅退出（应用应该处理这个信号）
   ↓
5. 如果 30 秒后还没退出，发 SIGKILL 强制杀掉
   ↓
6. Pod 从 etcd 中删除

常见异常状态（排查重点）：

状态 含义 常见原因
Pending 一直挂起 资源不足无法调度、镜像拉不下来、调度约束不满足
ImagePullBackOff 拉镜像失败 镜像名错误、仓库不可达、认证失败、imagePullPolicy 设错
CrashLoopBackOff 反复崩溃重启 应用启动失败、配置错误、依赖服务不可达
OOMKilled 内存不足被杀 limits.memory 设太小，应用内存不够
Error 容器异常退出 应用本身报错（exit 非 0）

问题 / 场景

问：Pod 一直 Pending 怎么排查？

  • 用 kubectl describe pod <name> 看 Events 部分，常见原因：
    • 资源不足：FailedScheduling ... Insufficient cpu → 减小 requests 或加节点
    • 镜像拉不下来：Failed to pull image ... → 检查镜像名、仓库、imagePullPolicy
    • 调度约束不满足：nodeSelector 匹配不到节点

问：Pod 状态 CrashLoopBackOff 是什么意思？

  • 容器反复崩溃被重启。CrashLoopBackOff 是 K8s 的"退避重启"机制——容器崩溃后立即重启，再次崩溃则延长重启间隔（10s → 20s → 40s → ... 最多 5 分钟）。排查：kubectl logs <pod> 看应用日志，通常是应用启动失败（如连不上数据库、配置错误）。

问：Succeeded 状态的 Pod 还会重启吗？

  • 不会。Succeeded 表示所有容器正常退出（exit 0），restartPolicy=Always 也不会重启已 Succeeded 的 Pod。Succeeded 主要用于 Job 类一次性任务。长期服务 Pod 应该一直 Running，不应该 Succeeded（如果 Succeeded 说明容器跑完了任务退出，如 java -jar 跑完 main 方法返回）。

问：Pod 一直 Running 但服务访问不了，怎么办？

  • Pod Running 只表示容器在跑，不代表应用就绪。可能应用还在启动（如 SpringBoot 启动慢）。排查：
    • kubectl logs <pod> 看应用日志是否启动完成
    • kubectl exec -it <pod> -- curl localhost:8080/health 看应用是否响应
    • 配置 readinessProbe（就绪探针，第 16 次课讲）

问：restartPolicy=Always 和 OnFailure 有什么区别？

  • Always：容器无论正常退出（exit 0）还是异常退出（非 0）都重启。适用于长期服务（如 web 应用）。
  • OnFailure：只有异常退出才重启，正常退出不重启。适用于 Job（如批处理任务，跑完就算成功）。
  • Never：退出都不重启。

知识点 K15-5：kubectl 操作 Pod 命令

定义

kubectl 是 K8s 的命令行客户端（第 14 次课已安装配置），本知识点学习用 kubectl 操作 Pod 的核心命令：run / get / describe / logs / exec / delete / apply。

原理

kubectl 操作 Pod 的命令一览：

命令 作用 示例
kubectl run 命令式创建 Pod kubectl run nginx --image=nginx
kubectl get pods 查看 Pod 列表 kubectl get pods -A
kubectl describe pod 查看 Pod 详情 kubectl describe pod <name>
kubectl logs 查看 Pod 日志 kubectl logs <name> -f
kubectl exec 进入 Pod 容器 kubectl exec -it <name> -- bash
kubectl delete pod 删除 Pod kubectl delete pod <name>
kubectl apply -f 从 YAML 创建/更新 Pod kubectl apply -f pod.yaml

命令式 vs 声明式：

命令式（kubectl run）：
  - 直接敲命令创建 Pod
  - 快速、适合临时测试
  - 不可复现（没记录在文件里）
  - 不适合生产

声明式（kubectl apply -f）：
  - 写 YAML 文件，apply 创建/更新
  - 可版本化（YAML 文件可提交 Git）
  - 可复现（同样 YAML 在任何集群都能创建同样 Pod）
  - 生产推荐

问题 / 场景

问：kubectl run 和 kubectl apply -f 有什么区别？

  • kubectl run 是命令式，直接敲命令创建 Pod，快速但不可复现。kubectl apply -f 是声明式，通过 YAML 创建 Pod，可版本化、可复现。生产环境推荐 apply -f。学习时 run 适合快速测试。

问：kubectl get pods 默认看哪个 namespace？

  • 默认看 default namespace。要看其他 namespace 用 -n <namespace> 或 -A 看所有。如 kubectl get pods -n ctts 或 kubectl get pods -A。

问：kubectl logs 怎么看实时日志？

  • 加 -f 参数：kubectl logs <pod> -f，类似 tail -f。多容器 Pod 要指定容器：kubectl logs <pod> -c <container>。

问：kubectl exec 进入 Pod 后能做什么？

  • 进入容器后就像在容器里执行命令，可以查看文件、进程、网络、调试应用。如 kubectl exec -it <pod> -- bash 进入后可以 ls、ps、curl localhost:8080 等。

问：kubectl delete pod 后 Pod 立即消失吗？

  • 不是立即消失。K8s 会先发 SIGTERM 信号给容器，等宽限期（默认 30 秒）后才强制杀掉。如果用 kubectl delete pod <name> --grace-period=0 --force 则立即删除（不推荐，可能导致数据丢失）。

kubectl 操作 Pod 速查表：

命令 作用 常用选项
kubectl run <name> --image=<image> 创建 Pod -n <ns> 指定 namespace
kubectl get pods 查看 Pod 列表 -A 所有 ns，-o wide 详情，-n <ns>
kubectl describe pod <name> 查看 Pod 详情 -n <ns>
kubectl logs <name> 查看日志 -f 实时，--tail=N 最后 N 行，-c <容器>
kubectl exec -it <name> -- <cmd> 进入容器 -c <容器> 指定容器
kubectl delete pod <name> 删除 Pod --force --grace-period=0 强制
kubectl apply -f <file> 从 YAML 创建/更新 -n <ns>
kubectl delete -f <file> 用 YAML 删除 —

易错点

  1. ❌ 忘记加 -n <namespace>，结果看不到 Pod。✅ Pod 在哪个 namespace 就用 -n 指定，或用 -A 看所有。
  2. ❌ 用 kubectl get pod（单数）报错。✅ 资源类型可以用复数（pods）或单数（pod），也可以用简写（po），都合法。
  3. ❌ kubectl exec 忘记加 --。✅ 必须加 -- 分隔 kubectl 参数和容器内命令，如 kubectl exec -it <pod> -- bash。
  4. ❌ 删除 Pod 后立即用 kubectl apply 重建失败。✅ Pod 删除有宽限期（30 秒），等完全删除后再 apply，或用 --force 立即删除。
  5. ❌ 修改 YAML 中不可变字段后 apply 报错。✅ 某些字段（如 spec.containers.name、spec.restartPolicy）不可修改，需要 delete 后重新 apply。

小结

kubectl 操作 Pod 七大命令：run（命令式创建）、get（查看列表）、describe（查看详情）、logs（看日志）、exec（进入容器）、delete（删除）、apply -f（声明式创建/更新）。生产环境推荐用 apply -f（可版本化、可复现），run 仅用于快速测试。排查 Pod 问题用 describe 看 Events + logs 看应用日志。

知识点 K15-6：CTTS 后端 Pod 部署实践

定义

把前面学到的 Pod 概念、YAML 结构、容器定义、kubectl 命令综合运用，编写 CTTS 后端 Pod YAML 并部署到第 14 次课搭好的 Minikube 集群上，完成 CTTS 项目在 K8s 上的第一次部署。

原理

CTTS 后端 Pod 部署的完整流程：

1. 准备工作（第 14 次课已完成） - Minikube 集群运行中 - ctts namespace 已创建 - ctts-backend:v1 镜像已在 Minikube Docker daemon 2. 编写 Pod YAML - metadata: name=ctts-backend, namespace=ctts, labels - spec.containers: image=ctts-backend:v1, ports=8080, env, resources - imagePullPolicy: Never（本地镜像，不去仓库拉） 3. 部署 Pod - kubectl apply -f ctts-backend-pod.yaml -n ctts 4. 验证 Pod - kubectl get pods -n ctts（状态 Running） - kubectl describe pod（看详情） - kubectl logs（看应用启动日志） 5. 测试服务 - kubectl exec 进入容器 curl localhost:8080 - 或从集群内访问 Pod IP 6. 故障排查（模拟问题） - 镜像名错误 → ImagePullBackOff - 应用崩溃 → CrashLoopBackOff - 资源不足 → Pending

问题 / 场景

问：CTTS 后端 Pod 的 imagePullPolicy 应该设成什么？

  • 第 14 次课用 eval $(minikube docker-env) 构建的 ctts-backend:v1 镜像，只存在于 Minikube 节点的 Docker daemon 里，没有推送到仓库。所以必须设 imagePullPolicy: Never（或 IfNotPresent），不能用 Always，否则会去仓库拉导致 ImagePullBackOff。

问：CTTS 后端 Pod 需要配什么环境变量？

  • CTTS 后端是 SpringBoot 应用，通常需要：
    • SPRING_PROFILES_ACTIVE：激活的配置文件（如 prod）
    • DB_HOST / DB_PORT：数据库地址和端口（MySQL 还没部署，先用占位值）
    • DB_NAME / DB_USER / DB_PASSWORD：数据库连接信息
  • 注意：第 21 次课会把密码类敏感信息提取为 Secret，配置类信息提取为 ConfigMap。本节课先用 env 直接写。

问：CTTS 后端 Pod 需要多少资源？

  • SpringBoot 应用通常需要：requests 0.5~1 核 CPU + 512Mi~1Gi 内存，limits 1~2 核 + 1~2Gi 内存。本节课设 requests 500m CPU + 512Mi 内存，limits 1000m CPU + 1Gi 内存。

问：Pod 部署后怎么从外部访问？

  • 裸 Pod 只能从集群内访问（通过 Pod IP）。要从外部访问需要 Service（第 18 次课）或 Ingress（第 19 次课）或 kubectl port-forward（临时调试）。
  • 临时调试：kubectl port-forward pod/ctts-backend 8080:8080 -n ctts，然后浏览器访问 http://localhost:8080。

易错点

  1. ❌ imagePullPolicy 设成 Always 导致 ImagePullBackOff。✅ 本地构建的镜像用 Never 或 IfNotPresent。
  2. ❌ 忘记指定 namespace，Pod 创建到 default。✅ YAML 里写 namespace: ctts 或命令加 -n ctts。
  3. ❌ YAML 里 env 的 DB_PASSWORD 明文写密码。✅ 本节课先用 env（演示），第 21 次课改用 Secret。
  4. ❌ resources 设太大导致调度失败。✅ requests 不要超过节点可用资源（Minikube 4 核 6G，requests 总和别超过 3.5 核 5G）。
  5. ❌ Pod Running 就以为服务可用。✅ 用 kubectl logs 确认应用启动完成，用 kubectl exec curl 确认服务响应。

四、拓展阅读（选学）

  1. Pod 的更多字段：

    • initContainers：初始化容器，在主容器启动前运行（如等待依赖服务就绪）
    • volumes：存储卷（emptyDir/hostPath/configmap/secret 等）
    • nodeSelector / affinity：节点选择与亲和性
    • tolerations：污点容忍
    • livenessProbe / readinessProbe / startupProbe：探针（第 16 次课讲）
    • securityContext：安全上下文（用户、权限）

  2. Pod 的 QoS 等级：

    • Guaranteed：requests == limits（最高优先级，最后被驱逐）
    • Burstable：requests < limits（中等）
    • BestEffort：没设 requests/limits（最低，最先被驱逐）
    • 生产环境建议核心服务用 Guaranteed

  3. Pod 驱逐与抢占：

    • 节点资源不足时，kubelet 会按 QoS 等级驱逐 Pod
    • 调度器抢占时，按优先级驱逐低优先级 Pod
    • Pod 优先级（PriorityClass）用于关键服务保障

  4. Pod 安全：

    • securityContext.runAsNonRoot: true：禁止 root 运行
    • securityContext.readOnlyRootFilesystem: true：只读根文件系统
    • securityContext.capabilities：限制 Linux capabilities
    • 生产环境建议最小权限原则

  5. 多容器 Pod 设计模式：

    • Sidecar：主容器 + 辅助容器（如日志收集、监控代理）
    • Ambassador：主容器 + 代理容器（如数据库代理）
    • Adapter：主容器 + 适配器容器（如监控指标转换）

  6. Pod 故障排查工具：

    • kubectl describe pod：看 Events
    • kubectl logs：看应用日志
    • kubectl exec：进入容器调试
    • kubectl get events --sort-by=.metadata.creationTimestamp：看集群事件
    • kubectl debug：临时调试容器（K8s 1.18+）
