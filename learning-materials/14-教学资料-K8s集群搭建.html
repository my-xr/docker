二、知识点详解

知识点 K14-1：集群搭建方案概览

定义

K8s 集群搭建方案是指把一组机器（或虚拟机/容器）组织成 K8s 集群的方法与工具。常见方案有四种：

方案 定位 适用场景
Minikube 单机学习集群 本地学习、开发测试、教学演示
kubeadm 多节点生产集群 生产环境、自建机房、需要多节点高可用
Kind（Kubernetes in Docker） 容器化集群 CI 流水线、临时测试集群、轻量级多节点
云托管 K8s（EKS/GKE/ACK/TKE） 托管集群 公有云上一键开通、免运维控制平面

原理

不同方案的本质差异在于"集群跑在哪里"和"谁负责运维控制平面"：

图示 1：方案 集群跑在哪 控制平面谁管
方案 集群跑在哪 控制平面谁管
Minikube 本机一台虚拟机/容器内 Minikube 自动管（学习用）
kubeadm 多台真实机器/虚拟机 用户自己搭自己管（生产用）
Kind 本机多个 Docker 容器内 Kind 自动管（CI 用）
云托管 K8s 云厂商的虚拟资源 云厂商托管控制平面，用户只管 Node

四种方案对比：

节点数 1（单机） 多（1 master + N worker） 多（容器模拟） 多（云托管）

学习曲线 低 中高 中 低（但要花钱）

是否适合生产 ✗ ✓ ✗ ✓
是否适合学习 ✓ △（门槛高） △（CI 用得多） △（要花钱）
是否需要多机 ✗ ✓ ✗ ✓（云上）
国产替代 — — — 华为 CCE / 阿里 ACK / 腾讯 TKE

选型建议：

  • 学习/开发：Minikube（首选，简单快）或 Kind（多节点测试）
  • 生产/自建：kubeadm（标准方式，可控性强）
  • 公有云生产：云托管 K8s（华为 CCE / 阿里 ACK / 腾讯 TKE，免运维控制平面）
  • CI 流水线：Kind（秒级启停，资源省）

问题 / 场景

问：本课程为什么主用 Minikube？

  • Minikube 单机够用、安装简单、对硬件要求低（2 核 2G 即可），适合教学。每个学生都能在自己机器上搭一套。kubeadm 多节点需要至少 2 台机器，学生机房环境不便，所以 kubeadm 只讲解流程不要求实操。

问：Minikube 和 Docker Desktop 内置 K8s 有什么区别？

  • Docker Desktop 也内置了 K8s（在设置里启用即可），但功能较简化。Minikube 是 K8s 官方维护的学习工具，更贴近真实集群，addons 丰富（dashboard、metrics-server、ingress 等），适合学习。本课程推荐 Minikube。

问：kubeadm 是不是已经过时了？

  • 没有。kubeadm 是 K8s 官方推荐的多节点集群搭建工具，至今仍是生产环境自建集群的主流方式。云托管 K8s 的底层很多也是用 kubeadm 或类似工具搭建。学 kubeadm 是理解 K8s 集群原理的最佳路径。

问：国产云厂商的 K8s 服务算自主可控吗？

  • 算。华为云 CCE、阿里云 ACK、腾讯云 TKE 都是基于开源 K8s 做的自主托管服务，符合自主可控要求。青云 KubeSphere 是开源的国产 PaaS，更值得关注。

易错点

  1. ❌ 误认为"Minikube 可以用于生产"。✅ Minikube 是单机学习集群，无高可用、无多节点，不能用于生产。
  2. ❌ 误认为"kubeadm 已过时"。✅ kubeadm 是官方推荐的生产搭建工具，至今主流。
  3. ❌ 误认为"云托管 K8s 不用学 kubeadm"。✅ 云托管底层也是 K8s，理解 kubeadm 才能理解集群原理，排查问题更有底。
  4. ❌ 误认为"Kind 是生产方案"。✅ Kind 是用 Docker 容器模拟节点，适合 CI 测试，不适合生产。

小结

K8s 集群搭建四大方案：Minikube（学习）、kubeadm（生产自建）、Kind（CI 测试）、云托管（公有云生产）。本课程主用 Minikube 实操，kubeadm 讲解流程。选型原则：学习用 Minikube，生产用 kubeadm 或云托管。

知识点 K14-2：Minikube 安装与启动

定义

Minikube 是 K8s 官方维护的单机版 K8s 集群工具，在本机一台虚拟机或容器内启动一套完整的 K8s 集群（含 Master 和 Node），用于学习、开发、测试。

一句话理解：

Minikube = 一键在本机起一套 K8s 集群，学习用。

原理

Minikube 的工作方式：

图示 3：本机（Windows/macOS/Linux）
  • 本机（Windows/macOS/Linux）
  • Docker（或虚拟化层，如 VirtualBox/Hyper-V/KVM）
  •   Minikube 节点（一个 Docker 容器 或 一个虚拟机）
  •   完整的 K8s 集群（Master + Node 都在里面）
  •   API Server
  •   etcd
  •   scheduler
  •   controller-manager
  •   kubelet
  •   kube-proxy
  •   container-runtime（containerd/docker）
  • kubectl（命令行客户端，连接 Minikube 集群）

Minikube 的特点：

  • 单机：Master 和 Node 都在同一个虚拟机/容器里
  • 一键启动：minikube start 自动完成所有组件拉起
  • 跨平台：Windows / macOS / Linux 都支持
  • 驱动可选：docker（推荐）/ virtualbox / hyperv / kvm2 / none
  • addons 丰富：dashboard、metrics-server、ingress、storage-provisioner 等

问题 / 场景

问：Minikube 启动需要什么前提？

  • 必装：Docker（推荐驱动）或虚拟化软件（VirtualBox/Hyper-V/KVM）。
  • 硬件：至少 2 核 CPU、2G 内存、20G 磁盘。
  • 系统：Windows 10+ / macOS 10.14+ / Ubuntu 20.04+ 等。
  • 网络：能访问 K8s 镜像仓库（国内建议配镜像加速）。

问：Minikube 启动卡在拉镜像怎么办？

  • 国内网络拉 k8s.gcr.io 的镜像很慢，启动时加 --image-mirror-country=cn 用国内镜像源： 
    minikube start --image-mirror-country=cn
  • 也可指定具体镜像仓库： 
    minikube start --image-repository=registry.cn-hangzhou.aliyuncs.com/google_containers

问：Minikube 用 docker 驱动和 virtualbox 驱动有什么区别？

  • docker 驱动：Minikube 在一个 Docker 容器里跑 K8s，启动快、资源省（推荐）。
  • virtualbox 驱动：Minikube 在 VirtualBox 虚拟机里跑 K8s，更隔离但启动慢、占资源。
  • 本课程推荐 docker 驱动（前提是已装 Docker）。

知识点 K14-3：kubectl 安装与配置

定义

kubectl 是 K8s 的命令行客户端，用户通过它与 K8s 集群的 API Server 通信，管理集群上的资源（Pod、Deployment、Service 等）。

kubeconfig 是 kubectl 的配置文件（默认位于 ~/.kube/config），记录了"如何连接到哪个集群、用什么身份认证"。kubectl 启动时会读取这个文件来确定连接目标。

一句话理解：

kubectl 是方向盘，kubeconfig 是钥匙——没有 kubeconfig，kubectl 不知道连哪个集群。

原理

kubectl 工作原理：

图示 5：用户敲命令 kubectl 读取 kubeconfig
  • 用户敲命令 kubectl 读取 kubeconfig
  • kubectl get pods 读取 ▶ ~/.kube/config
  •     含：集群 API Server 地址
  •     用户认证信息（证书/token）
  •     当前上下文（context）
  • HTTPS 请求 ▶ K8s API Server
  • etcd 读取/写入
  • 返回结果给 kubectl
  • kubectl 格式化输出

# kubeconfig 三大核心部分
apiVersion: v1
kind: Config

# 1. clusters：要连接的集群列表
clusters:
- name: minikube
  cluster:
    server: https://192.168.49.2:8443     # API Server 地址
    certificate-authority: /home/user/.minikube/ca.crt   # CA 证书
    # 或 certificate-authority-data: <base64>

# 2. users：用户认证信息
users:
- name: minikube
  user:
    client-certificate: /home/user/.minikube/profiles/minikube/client.crt
    client-key: /home/user/.minikube/profiles/minikube/client.key
    # 或 client-certificate-data / client-key-data: <base64>

# 3. contexts：上下文（绑定 cluster + user + namespace）
contexts:
- name: minikube
  context:
    cluster: minikube      # 用哪个 cluster
    user: minikube         # 用哪个 user 身份
    namespace: default     # 默认 namespace

# 4. current-context：当前使用哪个 context
current-context: minikube

三要素关系：

  • cluster：连接哪个集群（API Server 地址 + CA 证书）
  • user：以什么身份（客户端证书 / token）
  • context：把 cluster 和 user 绑定起来 + 默认 namespace
  • current-context：当前用哪个 context

问题 / 场景

问：为什么 Minikube 启动后 kubectl 就能直接用？

  • Minikube 启动时会自动把集群连接信息写入 ~/.kube/config，并设置 current-context: minikube。所以装好 kubectl 后，无需手动配置即可连接 Minikube 集群。

问：有多个集群（Minikube + 公司 K8s）怎么切换？

  • 在 kubeconfig 里配置多个 context，用 kubectl config use-context <name> 切换。例如： 
    kubectl config use-context minikube       # 切到 Minikube
kubectl config use-context company-prod   # 切到公司生产集群
kubectl config get-contexts               # 列出所有 context

问：kubectl 报 "The connection to the server was refused" 怎么办？

  • 表示 kubectl 找不到 API Server 或 API Server 没起。检查：
    1. Minikube 是否在运行（minikube status）
    2. ~/.kube/config 是否存在且正确
    3. API Server 地址是否可达（curl -k https://<api-server>:8443）

问：kubectl 一定要装在集群节点上吗？

  • 不必。kubectl 可以装在任何能访问 API Server 的机器上（你的笔记本、跳板机等），通过 kubeconfig 远程连接集群。这是 C/S 架构的优势。

易错点

  1. ❌ 误认为"装了 kubectl 就能连集群"。✅ 还必须有正确的 kubeconfig（含 API Server 地址和认证信息）才能连。
  2. ❌ 误认为"kubectl 必须装在集群机器上"。✅ kubectl 是客户端，可装在任何能访问 API Server 的机器上。
  3. ❌ 手动改 kubeconfig 出错导致连不上。✅ 推荐用 kubectl config 命令管理，不要手改。
  4. ❌ Minikube 重启后 IP 变化导致 kubeconfig 失效。✅ Minikube 启动时会自动更新 kubeconfig，重新 minikube start 即可。
  5. ❌ 多个集群 kubeconfig 冲突。✅ 用 KUBECONFIG 环境变量或 kubectl config 命令管理多集群。

小结

kubectl 是 K8s 命令行客户端，通过 kubeconfig（~/.kube/config）连接 API Server。kubeconfig 含三要素：cluster（集群）、user（身份）、context（绑定 + namespace）。Minikube 启动时自动生成 kubeconfig。kubectl 可装在任何机器远程管理集群。

知识点 K14-4：kubeadm 多节点集群搭建

定义

kubeadm 是 K8s 官方提供的集群搭建工具，用于在多台机器上快速初始化 K8s 控制平面（master）并把工作节点（worker）加入集群，形成多节点生产级 K8s 集群。

一句话理解：

kubeadm = 生产级 K8s 集群的"安装向导"，先 init 一个 master，再用 join 把 worker 加进来。

kubeadm 工作流程：

阶段 1：所有节点做前置条件配置（关 swap、防火墙、SELinux，装容器运行时和 kubeadm/kubelet/kubectl）
   ↓
阶段 2：在 master 上执行 kubeadm init
   - 拉取控制平面组件镜像
   - 启动 etcd、API Server、scheduler、controller-manager
   - 生成 kubeconfig 文件
   - 生成 worker 加入命令（kubeadm join ... --token ... --hash ...）
   ↓
阶段 3：配置 kubectl（拷贝 kubeconfig 到 ~/.kube/config）
   ↓
阶段 4：在每台 worker 上执行 kubeadm join（用 master 生成的 token）
   - worker 节点上的 kubelet 启动
   - 向 master 注册自己
   - master 上的 kubelet 开始管理该节点
   ↓
阶段 5：安装网络插件（CNI，如 Calico/Flannel）
   ↓
阶段 6：验证集群（kubectl get nodes 全部 Ready）

问题 / 场景

问：为什么要关 swap？

  • K8s 设计上假设节点不使用 swap（为了资源调度可预测、性能稳定）。kubelet 默认启动时会检查，如果发现 swap 开启会拒绝启动。所以搭建前必须关 swap。

问：为什么关防火墙和 SELinux？

  • 学习/初次搭建时关防火墙和 SELinux 可以避免端口被拦截导致组件通信失败。生产环境建议保留防火墙但开放 K8s 所需端口（10250/6443/2379-2380 等）。SELinux 也建议设为 permissive 或 disabled 以减少坑。

问：kubeadm init 生成的 join 命令丢了怎么办？

  • 可以重新生成： 
    kubeadm token create --print-join-command
  • 输出新的 kubeadm join ... --token ... --discovery-token-ca-cert-hash ... 命令。

问：kubeadm init 卡在拉镜像怎么办？

  • 国内拉 k8s.gcr.io/registry.k8s.io 镜像很慢，解决方案： 
    # 方式1：指定阿里云镜像仓库
kubeadm init --image-repository=registry.cn-hangzhou.aliyuncs.com/google_containers --kubernetes-version=v1.28.0 --pod-network-cidr=10.244.0.0/16

# 方式2：先手动拉镜像并改 tag
# 略

问：kubeadm 集群需要多少台机器？

  • 最少 2 台：1 master + 1 worker。生产建议 3 master（高可用）+ N worker。本课程演示 1 master + 2 worker。

易错点

  1. ❌ 不关 swap 就执行 kubeadm init，kubelet 启动失败。✅ 必须先 swapoff -a 并注释 /etc/fstab 中的 swap 行。
  2. ❌ 忘记装 CNI 网络插件，导致节点一直 NotReady。✅ kubeadm init 后必须装 Calico/Flannel 等网络插件。
  3. ❌ join 命令丢了或 token 过期（24 小时）。✅ 在 master 上 kubeadm token create --print-join-command 重新生成。
  4. ❌ 在 master 上执行 join 命令。✅ join 在 worker 节点上执行，不是 master。
  5. ❌ 不配 hosts 解析，导致节点间无法用主机名通信。✅ 三台机器都要配 /etc/hosts。
  6. ❌ 国内拉镜像卡死。✅ 加 --image-repository=registry.cn-hangzhou.aliyuncs.com/google_containers。
  7. ❌ worker 上的 kubelet 没启动。✅ 检查 systemctl status kubelet，join 成功后会自动启动。

知识点 K14-5：集群验证与基本操作

定义

集群搭建完成后，需要通过一系列 kubectl 命令验证集群是否正常，并掌握基本的资源查看操作。本知识点学习集群验证与日常运维最常用的 kubectl 命令。

原理

kubectl 命令结构：

kubectl <操作> <资源类型> [资源名] [选项]

操作示例：
  get      查看资源列表
  describe 查看资源详情
  logs     查看 Pod 日志
  exec     进入 Pod
  apply    创建/更新资源（声明式）
  delete   删除资源
  create   创建资源（命令式）

资源类型示例：
  nodes / no         节点
  pods / po          Pod
  services / svc     Service
  deployments / deploy  Deployment
  namespaces / ns    Namespace
  configmaps / cm    ConfigMap
  secrets            Secret

集群验证清单：

验证项 命令 期望结果
节点状态 kubectl get nodes 所有节点 Ready
集群信息 kubectl cluster-info 控制平面、CoreDNS 运行
系统 Pod kubectl get pods -A kube-system 下 Pod 全 Running
节点详情 kubectl describe node <name> 资源、容量、Pod 数正常
Service kubectl get svc -A kubernetes、kube-dns 存在

问题 / 场景

问：节点状态是 NotReady 怎么排查？

  • 三步排查：
    1. kubectl describe node <name> 看 Conditions 部分，找异常（如 KubeletNotReady）
    2. kubectl get pods -n kube-system -o wide | grep <name> 看该节点上的系统 Pod 是否正常
    3. SSH 到该节点 systemctl status kubelet 看 kubelet 是否运行，journalctl -u kubelet 看日志

问：kubectl get pods -A 中的 -A 是什么意思？

  • -A 是 --all-namespaces 的简写，表示查看所有 namespace 下的 Pod。不加默认只看 default namespace。

问：kubectl get 输出里 READY 列的 1/1 是什么意思？

  • 表示该 Pod 里有 1 个容器，1 个就绪。如果是 2/2 表示 2 个容器都就绪。0/1 表示 1 个容器中 0 个就绪（可能正在启动或异常）。

问：describe 和 get 有什么区别？

  • get 输出资源列表概要（一行一个），describe 输出单个资源的详细信息（事件、配置、状态等）。排查问题用 describe。

知识点 K14-6：CTTS 项目集群准备

定义

为 CTTS 三服务（前端 + 后端 + MySQL）的 K8s 部署准备集群环境，包括集群资源规划、镜像准备与推送、命名空间规划等。这是从"集群搭建"过渡到"应用部署"的桥梁——第 15 次课开始就要把 CTTS 服务部署到本次准备的集群上。

原理

CTTS K8s 部署的资源规划：

图示 8：CTTS 三服务 → K8s 资源映射：

CTTS 三服务 → K8s 资源映射：

CTTS 服务 K8s 资源 副本数

Frontend (Vue3) → Deployment + Service 2 副本

Backend (Spring) → Deployment + Service 3 副本

MySQL → StatefulSet + Service 1 副本（有状态）

通用资源：

ConfigMap（应用配置）

Secret（MySQL 密码）

PVC（MySQL 数据持久化，10Gi）

Ingress（域名入口，ctts.com）

Namespace（ctts，资源隔离）

集群资源估算：

Frontend 2 副本 × (0.25 核 + 256Mi) = 0.5 核 + 512Mi

Backend 3 副本 × (0.5 核 + 512Mi) = 1.5 核 + 1.5Gi

MySQL 1 副本 × (0.5 核 + 1Gi) = 0.5 核 + 1Gi

系统 Pod（kube-system） ≈ 1 核 + 1Gi

总计

约 3.5 核 CPU + 4Gi 内存

→ Minikube 至少分配 4 核 6G（学习用）

→ kubeadm 至少 1 master(2C4G) + 2 worker(2C4G)（生产用）

镜像准备策略：

服务 镜像来源 镜像名建议 说明
MySQL 官方镜像 mysql:8.0 直接从 Docker Hub 拉
Frontend 第 8 次课自构建 ctts-frontend:v1 需推送到仓库
Backend 第 8 次课自构建 ctts-backend:v1 需推送到仓库

镜像仓库选型：

  • Docker Hub：公共仓库，适合学习。镜像名需带用户名前缀：yourname/ctts-backend:v1。
  • 阿里云 ACR：国内拉取快，免费个人版。
  • Harbor：私有仓库，企业自建，第 23 次课拓展。

问题 / 场景

问：为什么 MySQL 要用 StatefulSet 而不是 Deployment？

  • MySQL 是有状态应用（数据要持久化、需要稳定网络标识）。StatefulSet 提供：稳定的 Pod 名（mysql-0）、稳定的持久化存储（每个 Pod 独立 PVC）、有序启动。Deployment 适合无状态应用（前端、后端）。详见第 16、22 次课。

问：Minikube 单机能跑下 CTTS 三服务吗？

  • 能。Minikube 默认分配 2 核 2G 可能不够，启动时建议指定资源： 
    minikube start --cpus=4 --memory=6g --image-mirror-country=cn
  • 这样 Minikube 容器有 4 核 6G，足够跑 CTTS 全套学习。

问：自构建镜像怎么让 Minikube 集群能用？

  • 两种方式：
    1. 推送到镜像仓库（Docker Hub/ACR），集群从仓库拉取（生产做法）
    2. 用 Minikube 的 Docker daemon 直接构建（学习做法，避免推仓库）： 
      eval $(minikube docker-env)
docker build -t ctts-backend:v1 .
# 此时镜像直接在 Minikube 节点上，Pod 可直接用
      注意：部署时 YAML 要加 imagePullPolicy: Never，否则会去仓库拉。

问：CTTS 用什么 namespace？

  • 建议创建独立 namespace ctts，与默认 namespace 隔离： 
    kubectl create namespace ctts
kubectl get namespaces
  • 后续部署时 kubectl apply -f ctts.yaml -n ctts 或在 YAML 里指定 namespace: ctts。

易错点

  1. ❌ Minikube 默认 2 核 2G 跑不动 CTTS 全套。✅ 启动时指定 --cpus=4 --memory=6g。

四、拓展阅读（选学）

  1. Minikube 高级用法：

    • 多节点集群：minikube start --nodes=3（在一个机器上模拟 3 节点）
    • 自定义 K8s 版本：minikube start --kubernetes-version=v1.27.0
    • 指定 CNI：minikube start --cni=calico
    • 持久化数据目录：minikube start --keep-context=true

  2. Kind（Kubernetes in Docker）：

    • 用 Docker 容器模拟 K8s 节点，秒级启停
    • 适合 CI 流水线、临时测试集群
    • 安装：go install sigs.k8s.io/kind@latest
    • 启动：kind create cluster --name mycluster
    • 与 Minikube 相比：Kind 更轻量，但不适合长期学习

  3. kubeadm 高可用集群：

    • 生产环境用 3 个 master 节点 + 堆叠 etcd 或外部 etcd
    • 用 keepalived + haproxy 做 API Server 负载均衡
    • 参考：K8s 官方文档《高可用拓扑选项》

  4. CNI 插件对比：

    • Calico：性能好、支持网络策略（NetworkPolicy），生产首选
    • Flannel：简单、稳定，无网络策略功能
    • Cilium：基于 eBPF，性能更好，新趋势
    • Weave Net：易用但社区活跃度下降

  5. 国产云托管 K8s：

    • 华为云 CCE：企业级托管 K8s，自主可控
    • 阿里云 ACK：与开源 K8s 完全兼容，国内市场领先
    • 腾讯云 TKE：与腾讯生态深度集成
    • 青云 KubeSphere：开源 PaaS，国产化代表，对 K8s 做了友好封装

  6. kubectl 插件与工具：

    • kubectx / kubens：快速切换 context 和 namespace
    • k9s：终端 UI 工具，比 kubectl 更直观
    • stern：同时查看多个 Pod 日志
    • kubectl 插件管理器：krew
