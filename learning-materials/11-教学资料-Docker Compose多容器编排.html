二、知识点详解

知识点 K11-1：Docker Compose 概念与作用

定义

Docker Compose 是 Docker 官方提供的单机多容器编排工具，它通过一个 YAML 文件（docker-compose.yml）描述一组关联容器的配置（镜像、端口、网络、数据卷、环境变量、依赖关系等），然后用一条命令（docker compose up）把这些容器一起启动起来，用一条命令（docker compose down）一起停止并清理。

一句话概括 Compose 的核心思想：

用一份声明式 YAML 描述"我要什么"，用一条命令得到结果。

原理

单机多容器编排的痛点：

图示 1：手工启动 CTTS 三服务的痛点链路

创建网络

docker network create ctts-net

创建数据卷

docker volume create ctts-mysql-data

启动 MySQL

配置 root 密码、数据库名、数据卷和网络。

等待就绪

常用 sleep 硬等，时间不稳定。

启动 Backend

配置端口、数据库主机、密码和镜像版本。

启动 Frontend

配置端口和前端镜像，接入同一网络。

命令多，参数多，记不住。
启动顺序错，后端连不上数据库。
迁移给同事时需要重敲一遍。
命令不在 Git 中，难以版本化管理。

Compose 的解决思路：把上面这一坨命令，转化为一份结构化的 YAML 文件：

# docker-compose.yml（伪代码，完整版见 K11-6）
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: "123456"
    volumes:
      - ctts-mysql-data:/var/lib/mysql
  backend:
    image: ctts-backend:v1
    ports:
      - "8080:8080"
    depends_on:
      - mysql
  frontend:
    image: ctts-frontend:v1
    ports:
      - "80:80"
    depends_on:
      - backend

volumes:
  ctts-mysql-data:

启动只要一条命令：

docker compose up -d

Compose v2 vs v1：

对比项 Compose v1（已废弃） Compose v2（当前）
命令形式 docker-compose（连字符） docker compose（空格，作为 docker CLI 子命令）
实现语言 Python Go（与 Docker 引擎同语言，性能更好）
安装方式 独立二进制 docker-compose Docker Desktop / docker-compose-plugin 内置
配置文件 docker-compose.yml docker-compose.yml（兼容）
状态 2023 年 7 月已 EOL 当前维护版本

📌 本课程使用 Compose v2，命令一律写作 docker compose（空格）。若环境中仍可用 docker-compose（连字符）说明装了 v1，建议升级。

Compose 与 Docker / K8s 的关系：

工具 定位 解决问题
Docker 容器引擎（单机） 怎么把应用打包成容器、怎么在单机运行一个容器
Compose 单机多容器编排 怎么在一台机器上把多个容器按关系一起启动
Kubernetes 集群容器编排 怎么在多台机器上调度管理成百上千个容器，支持高可用、弹性、滚动更新

一句话理解：Docker 装箱，Compose 单机编排，K8s 集群编排。Compose 是 Docker 到 K8s 的过渡——它的 YAML 声明式思维是 K8s 资源清单的预演。

问题 / 场景

问：已经有了 docker run，为什么还要 Compose？

  • docker run 是单容器命令，多容器应用要敲很多条，参数易错、不可复现、无法入 Git。Compose 把多容器配置收敛为一份 YAML，一条命令启停，是工程化的必然选择。

问：Compose 能用在生产环境吗？

  • 单机小规模应用可以用 Compose 上生产（如小型内部系统、CI 环境）。但生产级高可用、多节点、弹性扩缩容场景必须用 K8s。Compose 的定位更偏向开发、测试、CI、单机部署。

问：Compose 和 Docker Swarm 是什么关系？

  • Docker Swarm 是 Docker 内置的集群模式（多机），Compose 文件可以用来在 Swarm 上部署服务（docker stack deploy）。但 Swarm 已基本被 K8s 取代，本课程不深入 Swarm。

完整示例

最小可运行的 Compose 示例（单服务，验证 Compose 是否可用）：

# 文件名：docker-compose.yml
# 放在任意空目录下，例如 ~/compose-demo/
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"

执行命令与预期输出：

# 1. 启动
docker compose up -d
# 预期输出：
# [+] Running 2/2
#  ✔ Network compose-demo_default  Created   0.0s
#  ✔ Container compose-demo-web-1  Started   0.0s

# 2. 查看状态
docker compose ps
# 预期输出：
# NAME                  IMAGE          COMMAND                   SERVICE   STATUS         PORTS
# compose-demo-web-1    nginx:alpine   "/docker-entrypoint.…"   web       Up 10 seconds  0.0.0.0:8080->80/tcp

# 3. 访问验证
curl http://localhost:8080
# 预期输出：nginx 默认欢迎页 HTML（<!DOCTYPE html> ... Welcome to nginx! ...）

# 4. 停止并清理
docker compose down
# 预期输出：
# [+] Running 2/2
#  ✔ Container compose-demo-web-1  Removed   0.0s
#  ✔ Network compose-demo_default  Removed   0.0s

📌 即使没有显式定义 networks，Compose 也会自动创建一个名为 <项目名>_default 的 bridge 网络，所有服务默认接入。项目名默认是所在目录名（这里是 compose-demo）。

Dockerfile

描述单个服务镜像如何构建。

Compose 不是替代 Dockerfile，而是在镜像之上编排多个容器的本地/测试运行形态。

易错点

  1. ❌ 误认为"Compose 是另一种容器引擎"。✅ Compose 不是引擎，它是 Docker CLI 的子命令，本质上还是调用 dockerd 管理容器。
  2. ❌ 误认为"Compose 能跨多台机器编排"。✅ Compose 只能在单机上编排，跨机要用 K8s 或 Swarm。
  3. ❌ 把 v1 命令 docker-compose（连字符）当成 v2。✅ v2 命令是 docker compose（空格），是 docker CLI 的子命令。
  4. ❌ 误认为"Compose 文件必须叫 docker-compose.yml"。✅ 默认名是这个，但可以用 -f 指定任意文件名。

小结

Docker Compose 是单机多容器编排工具，用一份 docker-compose.yml 描述多服务配置，一条命令启停。它解决了手工 docker run 易错、不可复现的痛点，是从 Docker 到 K8s 的过渡技术，也是声明式 YAML 思维的入门。

知识点 K11-2：docker-compose.yml 文件结构

定义

docker-compose.yml 是 Compose 的核心配置文件，采用 YAML 格式，描述一组关联容器的完整配置。它的顶层结构主要有四个一级键：

顶层键 作用 必需
version Compose 文件格式版本（如 "3.8"） v2 中已不再必需，可省略
services 定义一组服务（每个服务对应一个容器） ✅ 必需
networks 定义自定义网络（可选） 可选
volumes 定义具名数据卷（可选） 可选

📌 Compose v2 已经不再强制要求 version 字段。新版 Compose 会自动识别文件格式，建议直接省略 version，让 Compose 自动处理。

原理

顶层结构示意：

# docker-compose.yml 顶层结构
# version: "3.8"   # v2 可省略

services:           # 必需：定义所有服务
  服务名1:
    # 服务1的配置
  服务名2:
    # 服务2的配置

networks:           # 可选：定义自定义网络
  网络名:
    # 网络配置

volumes:            # 可选：定义具名数据卷
  卷名:
    # 卷配置

关键概念：项目名（project name）

Compose 会把当前目录下的所有服务归为一个"项目"，项目名默认是所在目录名（小写、特殊字符去除），也可以用 -p 显式指定。所有 Compose 创建的资源（容器、网络、卷）都会带上项目名前缀，便于区分。

# 在 ~/ctts/ 目录下执行 docker compose up
# 项目名默认为 ctts
# 创建的容器名形如：ctts-mysql-1、ctts-backend-1、ctts-frontend-1
# 创建的网络名形如：ctts_ctts-net
# 创建的卷名形如：ctts_mysql-data

services 下的"服务名"是什么？

  • 服务名是你自定义的，比如 mysql、backend、frontend。
  • 服务名在 Compose 项目内唯一，并且会被用作：
    • 容器在自定义网络中的主机名（即 DNS 名）——其他容器可以用服务名访问它。
    • Compose 命令中的服务标识——如 docker compose logs backend。
    • 默认容器名的一部分——<项目名>-<服务名>-<序号>，如 ctts-backend-1。

问题 / 场景

问：services 下的服务名能不能用大写或下划线？

  • 建议用小写字母 + 数字 + 连字符（-），不要用下划线或大写。因为服务名会作为容器的主机名，DNS 域名规范不建议下划线，且部分程序对主机名大小写敏感。

问：一份 docker-compose.yml 能定义多少个服务？

  • 理论上没有硬限制，但实际受单机资源（CPU、内存、端口）约束。一般 10~30 个服务以内比较合理，再多就该考虑 K8s 了。

问：networks 和 volumes 顶层段不写会怎样？

  • Compose 会自动创建一个 <项目名>_default 的 bridge 网络让所有服务互通；数据卷如果用字符串路径（绑定挂载）则不需要在 volumes 顶层段声明。但具名 volume（如 ctts-data:/var/lib/mysql）必须在 volumes 顶层段声明，否则报错。

完整示例

一个体现完整顶层结构的示例（带注释说明）：

# 文件名：docker-compose.yml
# 演示完整的顶层结构：services + networks + volumes

services:
  # 服务1：数据库
  db:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: "123456"
    volumes:
      - db-data:/var/lib/mysql        # 引用下方定义的具名卷
    networks:
      - app-net                        # 引用下方定义的自定义网络

  # 服务2：应用
  app:
    image: nginx:alpine
    ports:
      - "8080:80"
    networks:
      - app-net
    depends_on:
      - db

# 自定义网络定义
networks:
  app-net:
    driver: bridge                     # bridge 是默认驱动，可省略

# 具名数据卷定义
volumes:
  db-data:
    driver: local                      # local 是默认驱动，可省略

执行与预期输出：

# 启动
docker compose up -d
# 预期输出：
# [+] Running 4/4
#  ✔ Network compose-demo_app-net   Created   0.0s
#  ✔ Volume  compose-demo_db-data   Created   0.0s
#  ✔ Container compose-demo-db-1    Started   0.0s
#  ✔ Container compose-demo-app-1   Started   0.0s

# 查看网络
docker network ls | grep app-net
# 输出：compose-demo_app-net   bridge    ...

# 查看卷
docker volume ls | grep db-data
# 输出：compose-demo_db-data

# 查看容器
docker compose ps
# NAME                    IMAGE          SERVICE   STATUS         PORTS
# compose-demo-app-1      nginx:alpine   app       Up 10 seconds  0.0.0.0:8080->80/tcp
# compose-demo-db-1       mysql:8.0      db        Up 10 seconds  3306/tcp

# 清理
docker compose down
# 预期输出：
# [+] Running 4/4
#  ✔ Container compose-demo-app-1   Removed   0.0s
#  ✔ Container compose-demo-db-1    Removed   0.0s
#  ✔ Network compose-demo_app-net   Removed   0.0s
#  ✔ Volume  compose-demo_db-data   Removed   0.0s（注意：默认 down 不删卷）

📌 注意：docker compose down 默认不会删除具名卷，要加 -v 才删：docker compose down -v。这是为了保护数据。上面输出"Volume Removed"是演示预期，实际默认不删。

易错点

  1. ❌ 在 v2 中仍写 version: "2" 或 version: "3.8" 导致旧特性告警。✅ v2 中可省略 version 字段，Compose 自动处理。
  2. ❌ services 缩进错误（YAML 严格要求缩进，不能 Tab/空格混用）。✅ 统一用 2 个空格缩进，禁止 Tab。
  3. ❌ 服务名用大写或下划线（如 My_Service）。✅ 用小写字母 + 连字符，如 my-service。
  4. ❌ 引用了未在 networks 或 volumes 顶层段定义的网络/卷。✅ 顶层段必须先定义，services 才能引用。

小结

docker-compose.yml 顶层结构有四个一级键：version（v2 可省）、services（必需）、networks（可选）、volumes（可选）。services 下的服务名是 Compose 项目内的唯一标识，也用作容器主机名。YAML 严格依赖缩进，必须用空格而非 Tab。

知识点 K11-3：services 核心配置项

定义

services 下的每个服务都是一个容器的声明式配置。常用核心配置项如下：

配置项 作用 对应 docker run 参数
image 指定服务使用的镜像 docker run <镜像>
build 指定 Dockerfile 构建上下文，启动时自动构建镜像 docker build + docker run
container_name 指定容器名（覆盖默认的 <项目名>-<服务名>-N） --name
ports 端口映射（宿主机:容器） -p
volumes 挂载数据卷或绑定挂载 -v / --mount
environment 环境变量（字典或列表两种写法） -e
env_file 从文件加载环境变量 --env-file
networks 服务接入的网络 --network
depends_on 依赖的其他服务（控制启动顺序） 无（Compose 独有）
restart 重启策略 --restart
command 覆盖镜像默认启动命令 <命令> 末尾参数
working_dir 容器工作目录 -w
hostname 容器主机名 --hostname
healthcheck 健康检查 --health-cmd 等

原理

核心配置项详解：

1. image —— 指定镜像

services:
  mysql:
    image: mysql:8.0            # 镜像名:标签
  backend:
    image: ctts-backend:v1      # 本地构建或推送过的镜像

如果本地没有该镜像，docker compose up 会自动从仓库拉取（相当于 docker pull）。

2. build —— 构建镜像

services:
  backend:
    build:
      context: ./backend         # Dockerfile 所在目录
      dockerfile: Dockerfile     # 默认就是 Dockerfile，可省略
    image: ctts-backend:v1       # 构建后打的标签（可选）

image 与 build 二选一或组合使用：

  • 只写 image：用现成镜像。
  • 只写 build：每次 up 都重新构建（--build 时强制）。
  • 同时写：构建后打上指定标签，方便后续引用。

3. container_name —— 容器名

services:
  mysql:
    image: mysql:8.0
    container_name: ctts-mysql   # 固定容器名

不写时默认 <项目名>-<服务名>-<序号>（如 ctts-mysql-1）。生产中通常不固定，因为固定后无法用 --scale 扩缩容（多个容器会重名）。

4. ports —— 端口映射

services:
  backend:
    image: ctts-backend:v1
    ports:
      - "8080:8080"              # 宿主机端口:容器端口（字符串）
      - "443:8443"               # 可映射多个
      - "5000"                   # 只写容器端口，宿主机随机分配
      - target: 9090             # 长格式
        published: "9090"
        protocol: tcp

短格式 "宿主机:容器" 是最常用写法，必须用引号包起来，否则 YAML 会把 8080:8080 解析成时间字符串。

5. volumes —— 挂载卷

services:
  mysql:
    image: mysql:8.0
    volumes:
      - mysql-data:/var/lib/mysql       # 具名卷:容器路径
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql  # 绑定挂载:容器路径
      - /data/mysql:/var/lib/mysql      # 绝对路径:容器路径（也是绑定挂载）

三种形式：

  • 卷名:容器路径 —— 具名卷，需在 volumes 顶层段声明。
  • ./相对路径:容器路径 —— 绑定挂载，挂载宿主机目录。
  • /绝对路径:容器路径 —— 绑定挂载，绝对路径。

6. environment —— 环境变量

services:
  mysql:
    image: mysql:8.0
    environment:
      # 字典写法（推荐）
      MYSQL_ROOT_PASSWORD: "123456"
      MYSQL_DATABASE: ctts
      MYSQL_USER: ctts
      MYSQL_PASSWORD: "ctts123"

或列表写法：

    environment:
      - MYSQL_ROOT_PASSWORD=123456
      - MYSQL_DATABASE=ctts

字典写法更清晰，列表写法更接近 docker run -e。两种都行，但不要混用。

7. networks —— 接入网络

services:
  backend:
    image: ctts-backend:v1
    networks:
      - app-net                   # 引用顶层 networks 定义的网段

一个服务可以接入多个网络：

    networks:
      - app-net
      - db-net

8. depends_on —— 启动依赖

services:
  backend:
    image: ctts-backend:v1
    depends_on:
      - mysql                     # backend 会在 mysql 之后启动

⚠️ 重要限制：depends_on 只控制启动顺序，不控制就绪顺序。即 Compose 会先启动 mysql 容器再启动 backend 容器，但 mysql 进程启动 ≠ MySQL 服务能接受连接。MySQL 真正就绪通常需要再等几秒到几十秒。

生产环境的正确写法是配合健康检查：

services:
  mysql:
    image: mysql:8.0
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-p123456"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  backend:
    image: ctts-backend:v1
    depends_on:
      mysql:
        condition: service_healthy    # 等 mysql 健康检查通过才启动

9. restart —— 重启策略

services:
  backend:
    image: ctts-backend:v1
    restart: always                  # 总是重启

可选值：

  • no（默认）：不重启。
  • always：总是重启（容器退出就重启）。
  • on-failure：非零退出码才重启。
  • unless-stopped：除非手动 stop，否则总是重启（推荐生产使用）。

问题 / 场景

问：image 和 build 能同时写吗？

  • 可以。同时写时，build 构建 image 并打上 image 字段指定的标签。后续 up 时若本地已有该标签镜像则直接用，加 --build 才强制重新构建。

问：depends_on 写了就一定能保证依赖服务就绪吗？

  • ❌ 不能。depends_on 只控制"容器启动顺序"，不保证"服务就绪"。MySQL 启动后还要初始化数据库、加载权限表，可能需要 10~30 秒才能真正接受连接。要保证就绪必须配合 healthcheck + depends_on: condition: service_healthy。这是面试常考题。

问：ports 不写引号会怎样？

  • 8080:8080 在 YAML 中会被解析为时间字符串（60 进制），导致端口映射错误。必须用引号包起来："8080:8080"。

问：environment 字典写法里密码要不要加引号？

  • 纯数字字符串（如 123456）建议加引号，否则 YAML 会解析为整数；含特殊字符（@、#、:）的值必须加引号。密码建议统一加引号。

知识点 K11-4：networks 与 volumes 配置

定义

networks 和 volumes 是 docker-compose.yml 的两个可选顶层段，用于定义自定义网络和具名数据卷，供 services 下的服务引用。

  • networks 顶层段：定义 Compose 项目内的自定义网络。每个网络可以指定驱动（driver）等属性。
  • volumes 顶层段：定义 Compose 项目内的具名数据卷。每个卷可以指定驱动、外部标识等属性。

原理

networks 顶层段定义与引用：

services:
  backend:
    image: ctts-backend:v1
    networks:
      - ctts-net              # 引用：服务接入这个网络
      - db-net                # 可接入多个网络

  mysql:
    image: mysql:8.0
    networks:
      - db-net                # mysql 只在 db-net，与 backend 共享 db-net

networks:
  ctts-net:                   # 定义：自定义 bridge 网络
    driver: bridge            # 默认就是 bridge，可省略
  db-net:
    driver: bridge
    name: custom-db-net       # 可指定创建后的实际网络名（覆盖默认前缀）

引用规则：

  • 服务在 networks: 下写网络名，必须在顶层 networks: 段有定义（除非用 external: true 引用外部已存在的网络）。
  • 同一个网络内的服务可以通过服务名互相访问（DNS 解析）。
  • 跨网络的服务默认不能通信（网络隔离）。

volumes 顶层段定义与引用：

services:
  mysql:
    image: mysql:8.0
    volumes:
      - mysql-data:/var/lib/mysql        # 引用：具名卷
      - ./init:/docker-entrypoint-initdb.d  # 绑定挂载（无需顶层声明）

volumes:
  mysql-data:                            # 定义：具名卷
    driver: local                        # 默认就是 local，可省略

引用规则：

  • 具名卷（卷名:容器路径）必须在 volumes 顶层段声明。
  • 绑定挂载（./路径:容器路径 或 /绝对路径:容器路径）不需要在顶层段声明。
  • 具名卷默认在 docker compose down 时保留，加 -v 才删除。

外部网络与外部卷（external）：

networks:
  existing-net:
    external: true                # 引用 Docker 中已存在的网络（不创建新的）
    # 或指定实际名字：external: true + name: my-existing-net

volumes:
  existing-volume:
    external: true                # 引用已存在的卷

external: true 告诉 Compose："这个网络/卷已经存在，不要创建，直接用"。常用于多个 Compose 项目共享网络或卷的场景。

问题 / 场景

问：不定义 networks 顶层段会怎样？

  • Compose 会自动创建一个 <项目名>_default 的 bridge 网络，所有服务默认接入。简单场景下不定义也能用，但生产中建议显式定义自定义网络，便于隔离与命名。

问：为什么用具名卷而不是绑定挂载存 MySQL 数据？

  • 具名卷由 Docker 管理（在 /var/lib/docker/volumes/ 下），跨平台一致、性能好、权限正确，且不会被宿主机意外修改。绑定挂载更适合挂配置文件、初始化脚本等需要直接编辑的内容。

问：两个 Compose 项目要共享一个网络怎么办？

  • 在两个项目的 docker-compose.yml 里都定义这个网络为 external: true，然后先用 docker network create <名字> 创建好，再分别 up。

易错点

  1. ❌ 在 services 里引用了未在顶层段定义的具名卷。✅ 具名卷必须先在 volumes: 顶层段声明。

小结

知识点 K11-5：docker compose 常用命令

定义

docker compose 命令是 Docker CLI 的子命令（v2 形式：docker compose，空格），用于管理 Compose 项目内的所有服务。常用命令如下：

命令 作用 常用参数
docker compose up 启动所有服务 -d 后台 / --build 强制重新构建
docker compose down 停止并删除容器、网络 -v 同时删除卷
docker compose ps 查看服务状态 无
docker compose logs 查看日志 -f 跟随 / 服务名指定单个
docker compose exec 进入运行中的容器 服务名 + 命令
docker compose start 启动已停止的服务 无
docker compose stop 停止服务（不删除） 无
docker compose restart 重启服务 无
docker compose build 构建或重建镜像 --no-cache 不用缓存
docker compose pull 拉取服务镜像 无
docker compose config 校验并渲染配置 无
docker compose top 查看容器内进程 无

原理

docker compose up：核心启动命令

# 前台启动（日志直接输出到终端，Ctrl+C 停止）
docker compose up

# 后台启动（推荐）
docker compose up -d

# 启动时强制重新构建镜像
docker compose up -d --build

# 只启动部分服务
docker compose up -d backend mysql

# 启动时若依赖镜像不存在自动拉取（默认行为）
docker compose up -d

docker compose down：停止并清理

# 停止并删除容器、网络（保留卷）
docker compose down

# 同时删除卷（慎用！数据会丢）
docker compose down -v

# 同时删除镜像（慎用）
docker compose down --rmi all

# 同时删除匿名卷
docker compose down -v

docker compose ps：查看状态

# 查看所有服务状态
docker compose ps

# 只看某个服务
docker compose ps backend

# 显示所有容器（包括已停止的）
docker compose ps -a

docker compose logs：查看日志

# 查看所有服务日志
docker compose logs

# 跟随日志（实时）
docker compose logs -f

# 只看某个服务
docker compose logs -f backend

# 只看最近 100 行
docker compose logs --tail 100 backend

# 带时间戳
docker compose logs -t backend

docker compose exec：进入容器

# 进入 backend 容器的 sh
docker compose exec backend sh

# 在 backend 容器内执行命令（不进入交互）
docker compose exec backend env | grep MYSQL

# 指定用户
docker compose exec --user root mysql bash

docker compose start/stop/restart：生命周期

# 停止（不删除，下次 start 能恢复）
docker compose stop

# 启动已停止的
docker compose start

# 重启
docker compose restart backend

stop 与 down 的区别：

  • stop：只停止容器，不删除，配置和网络都保留，下次 start 直接恢复。
  • down：停止并删除容器和网络，卷保留，下次 up 重新创建容器。

-f 指定文件：

# 默认读 docker-compose.yml，可以用 -f 指定其他文件
docker compose -f docker-compose.prod.yml up -d

# 多文件合并（后面的覆盖前面的）
docker compose -f docker-compose.yml -f docker-compose.override.yml up -d

-p 指定项目名：

# 默认项目名是目录名，可以用 -p 指定
docker compose -p myapp up -d
# 创建的容器名形如：myapp-mysql-1、myapp-backend-1

--scale 扩缩容：

# 把 backend 扩展为 3 个实例
docker compose up -d --scale backend=3

# 注意：
# 1. 不能给固定 container_name 的服务用 --scale（会重名报错）
# 2. Compose 本身不做负载均衡，多实例需要外部反向代理
# 3. 端口映射会冲突（除非只映射容器端口不映射宿主机端口）

问题 / 场景

问：up 和 start 有什么区别？

  • up：根据 YAML 创建容器（如果不存在）、启动、连接网络。up 是"声明式对齐"——让真实状态向 YAML 描述的目标状态靠拢。
  • start：只启动已存在的停止状态的容器，不会创建新容器。修改了 YAML 后必须用 up 而不是 start。

问：down 之后卷还在吗？

  • 在。down 默认保留具名卷。要删卷必须加 -v：docker compose down -v。

问：修改了 docker-compose.yml 后怎么生效？

  • 直接再 docker compose up -d，Compose 会对比当前状态与 YAML，只重建有变化的服务。强制重建用 --force-recreate。

问：--scale backend=3 后访问哪个实例？

  • Compose 不做负载均衡，3 个实例都监听同一端口会冲突（除非只映射容器端口）。多实例负载均衡需要配合外部反向代理（如 Nginx），或直接用 K8s。本课程了解即可。

图示 7：Compose up、start、stop、down 的语义差异
up

声明式对齐

按 YAML 创建、启动，必要时重建服务，让真实状态向配置靠拢。

start

只启动已有容器

不会创建新容器，也不会根据 YAML 变化重建。

stop

停止但保留

停止容器，保留容器、网络和卷，便于后续 start。

down

停止并删除

易错点

  1. ❌ 修改 YAML 后用 start 期望生效。✅ 修改 YAML 后必须用 up -d，Compose 会重建有变化的服务。
  2. ❌ 以为 down 会删卷。✅ 默认不删卷，要 down -v 才删。
  3. ❌ 把 v2 的 docker compose（空格）写成 v1 的 docker-compose（连字符）。✅ v2 是 docker compose，作为 docker CLI 子命令。
  4. ❌ 给固定 container_name 的服务用 --scale。✅ 固定容器名会冲突，要扩缩容就不要固定名。

知识点 K11-6：CTTS 三服务 Compose 编排实战

定义

本知识点把前面 5 个知识点串联起来，编写一份完整的 CTTS 三服务 docker-compose.yml，包含：

  • MySQL 服务（数据库）
  • Backend 服务（SpringBoot 后端）
  • Frontend 服务（Vue3 前端 + Nginx 静态托管）

并设计正确的依赖顺序（depends_on）、自定义网络（ctts-net）、数据卷（mysql-data）与环境变量配置。

原理

CTTS 三服务架构回顾：

图示 8：Compose 三服务职责链路
frontend

Vue3 + Nginx :80

用户访问入口，提供静态资源，并通过反向代理把 API 请求转发给后端。

backend

Spring Boot :8080

承载业务逻辑和 REST API，连接 MySQL 读写业务数据。

mysql

MySQL :3306

负责持久化存储，使用 volume 保存数据，通常不直接面向外部用户。

依赖顺序设计：

服务 依赖 启动条件
mysql 无（最先启动） 数据库就绪（healthcheck 通过）
backend mysql mysql 健康检查通过（service_healthy）
frontend backend backend 启动即可（前端调用后端是运行时行为，不强依赖启动）

为什么 frontend 不强依赖 backend 就绪？

  • 前端是 Nginx 托管的静态资源，本身能独立启动。
  • 前端调后端是运行时调用（用户在浏览器点按钮时才发请求），不是启动时依赖。
  • 即使后端没启动，前端页面也能打开（只是请求会失败）。所以 frontend 的 depends_on 用默认的 service_started 即可。

网络设计：

图示 9：Compose 自定义网络 ctts-net
mysql

服务名 mysql

监听 3306，backend 使用 mysql:3306 连接数据库。

backend

服务名 backend

监听 8080，frontend 的 Nginx 反代配置可使用 backend:8080。

frontend

服务名 frontend

监听 80，是用户访问入口，通常映射 80:80。

同网络内

Compose 为服务加入 ctts-net 后，服务名就是 DNS 名，容器可互相解析。

对外暴露

开发调试可临时暴露 backend/mysql；生产环境优先只暴露 frontend，缩小攻击面。

数据卷设计：

图示 10：具名卷：mysql-data
  • 具名卷：mysql-data
  • 挂载到 mysql 容器的 /var/lib/mysql
  • MySQL 数据文件持久化
  • 绑定挂载：
  • ./init.sql → /docker-entrypoint-initdb.d/init.sql
  • MySQL 首次启动时执行初始化 SQL（建表、插数据）

问题 / 场景

问：为什么 backend 要等 MySQL 健康检查通过才启动？

  • SpringBoot 启动时会建立数据库连接池（如 HikariCP），如果连不上数据库会启动失败或反复重试。等 MySQL 真正就绪后再启动 backend，能避免启动期连接失败。

问：frontend 调 backend 用什么地址？

  • 容器内（同网络）用服务名 backend:8080。但浏览器是宿主机外的客户端，不能用服务名（DNS 解析不到）。常见做法是 frontend 的 Nginx 配反向代理，把 /api/ 路径转发到 backend:8080，浏览器访问 http://宿主机IP/ 即可。

问：MySQL 端口要不要对外暴露？

  • 开发调试时暴露 3306 方便用 Navicat 等工具连。生产环境不要暴露 3306，只让 backend 容器内部访问。本课为调试方便保留 3306 映射。

完整 CTTS 三服务 docker-compose.yml：

# 文件名：docker-compose.yml
# CTTS 三服务完整编排：MySQL + Backend + Frontend
# 假设目录结构：
#   ~/ctts/
#   ├── docker-compose.yml
#   ├── init.sql
#   ├── backend/
#   │   ├── Dockerfile
#   │   └── ctts-backend.jar
#   └── frontend/
#       ├── Dockerfile
#       ├── nginx.conf
#       └── dist/

services:
  # ───────── 1. MySQL 数据库 ─────────
  mysql:
    image: mysql:8.0
    container_name: ctts-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: "123456"
      MYSQL_DATABASE: ctts
      MYSQL_USER: ctts
      MYSQL_PASSWORD: "ctts123"
      TZ: Asia/Shanghai
    ports:
      - "3306:3306"
    volumes:
      - mysql-data:/var/lib/mysql
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    networks:
      - ctts-net
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-p123456"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  # ───────── 2. Backend 后端服务 ─────────
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    image: ctts-backend:v1
    container_name: ctts-backend
    restart: unless-stopped
    environment:
      MYSQL_HOST: mysql
      MYSQL_PORT: "3306"
      MYSQL_USER: ctts
      MYSQL_PASSWORD: "ctts123"
      MYSQL_DATABASE: ctts
      SPRING_PROFILES_ACTIVE: prod
    ports:
      - "8080:8080"
    networks:
      - ctts-net
    depends_on:
      mysql:
        condition: service_healthy

  # ───────── 3. Frontend 前端服务 ─────────
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    image: ctts-frontend:v1
    container_name: ctts-frontend
    restart: unless-stopped
    ports:
      - "80:80"
    networks:
      - ctts-net
    depends_on:
      - backend

  ctts-net:
    driver: bridge
    name: ctts-network

# ───────── 数据卷定义 ─────────

  mysql-data:
    driver: local

三、综合示例：从手工到编排——CTTS 部署方式对比

把前面所有知识点串起来，对比"手工部署"与"Compose 编排"两种方式部署 CTTS 三服务：

1. 手工部署（痛点回顾，K11-1）

  docker network create ctts-net
  docker volume create ctts-mysql-data
  docker run -d --name mysql --network ctts-net -e MYSQL_ROOT_PASSWORD=123456 ...
  sleep 30  # 等 MySQL 就绪
  docker run -d --name backend --network ctts-net -p 8080:8080 ...
  docker run -d --name frontend --network ctts-net -p 80:80 ...

  痛点：
  - 6+ 条命令，20+ 参数
  - 启动顺序靠人工记忆
  - 等待 MySQL 就绪靠 sleep，不可靠
  - 重启、迁移、交给同事都要重敲
  - 配置不在 Git 里，无法 Code Review

2. Compose 编排（K11-2 ~ K11-6）

  # docker-compose.yml（见 K11-6 完整版）
  services:
    mysql: ... + healthcheck
    backend: ... + depends_on: service_healthy
    frontend: ... + depends_on: backend
  networks:
    ctts-net: ...
  volumes:
    mysql-data: ...

  一条命令：
  docker compose up -d --build

  价值：
  - 一份 YAML 替代 6+ 条命令
  - depends_on + healthcheck 自动处理就绪
  - 可入 Git 版本管理
  - 一键启停、一键迁移
  - 配置可 Code Review

这个对比体现了 Compose 的核心价值：把"人的操作"转化为"机器可执行的描述"，让部署可重复、可审计、可版本化。

四、拓展阅读（选学）

  1. Compose 文件版本演进：从 v1（version: "2"）到 v3（version: "3.8"）再到 v2 插件时代的"无 version"写法，了解 Compose 规范（Compose Specification）的统一过程：https://github.com/compose-spec/compose-spec
  2. Compose 与 Swarm 的关系：docker stack deploy 可以用 Compose 文件在 Swarm 集群上部署服务，但部分指令（如 build）不被支持。Swarm 已逐步被 K8s 取代，了解即可。
  3. Compose Profile：用 profiles 字段按环境（dev/test/prod）选择性启动服务，类似 Spring Profile。例如 docker compose --profile prod up -d。
  4. Compose 与 K8s 的桥梁 —— Kompose：开源工具 kompose 能把 docker-compose.yml 转换为 K8s YAML 清单，是从 Compose 过渡到 K8s 的辅助工具（第 13 次课后可了解）。
  5. 生产环境的 Compose 替代品：单机小规模可用 Compose，生产环境推荐 K8s；CI 流水线中也常用 Compose 启动测试依赖（如 GitHub Actions 的 services 段就是 Compose 语法简化版）。

一句话总结

Docker Compose 用一份 docker-compose.yml 描述多服务，一条 docker compose up -d 启动、一条 docker compose down 清理，把"手工部署玄学"变成"声明式工程"，是从 Docker 走向 K8s 的关键过渡。
