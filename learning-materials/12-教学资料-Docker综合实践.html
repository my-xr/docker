知识点 K12-2：MySQL 服务容器化

定义

MySQL 服务容器化是指使用官方 mysql:8.0 镜像启动 MySQL 容器，并通过以下三种机制让容器化后的 MySQL 符合生产可用标准：

  1. 环境变量配置：通过 MYSQL_ROOT_PASSWORD、MYSQL_DATABASE 等环境变量配置 root 密码、初始数据库。
  2. init.sql 自动初始化：把 SQL 脚本挂载到 /docker-entrypoint-initdb.d/，MySQL 首次启动时自动执行建表与插数据。
  3. 数据卷持久化：用具名卷挂载 /var/lib/mysql，保证容器删除后数据不丢。

原理

MySQL 官方镜像的初始化机制：

图示 3：mysql:8.0 镜像启动流程：

mysql:8.0 镜像启动流程：

读取环境变量（MYSQL_ROOT_PASSWORD / MYSQL_DATABASE / MYSQL_USER / MYSQL_PASSWORD）

初始化数据目录 /var/lib/mysql（首次启动）

创建 root 用户，设置密码

如果指定了 MYSQL_DATABASE，创建该数据库

如果指定了 MYSQL_USER/MYSQL_PASSWORD，创建该用户并授权

扫描 /docker-entrypoint-initdb.d/ 目录，按文件名顺序执行 .sql/.sh 文件

启动 mysqld 服务，监听 3306

关键：第 6 步只在"首次启动"（数据目录为空）时执行！

如果数据卷已有数据，init.sql 不会再次执行。

环境变量说明：

环境变量 作用 必需
MYSQL_ROOT_PASSWORD root 用户密码 ✅ 必需（不设会启动失败）
MYSQL_DATABASE 首次启动时自动创建的数据库 可选
MYSQL_USER 首次启动时创建的普通用户 可选
MYSQL_PASSWORD 普通用户的密码 配合 MYSQL_USER 使用
MYSQL_ALLOW_EMPTY_PASSWORD 是否允许空密码（不推荐） 可选
TZ 时区 推荐 Asia/Shanghai

问题 / 场景

问：为什么 init.sql 只在首次启动时执行？

  • 因为 MySQL 容器启动脚本会检测 /var/lib/mysql 是否已有数据。如果有数据（说明已初始化过），就跳过 init.sql，避免覆盖现有数据。这也意味着：如果你想重新执行 init.sql，必须先 docker compose down -v 删除数据卷。

问：init.sql 可以放多个文件吗？

  • 可以。/docker-entrypoint-initdb.d/ 目录下可以放多个 .sql 或 .sh 文件，按文件名字母顺序执行。如 01-schema.sql、02-data.sql、03-index.sql。

问：生产环境能把 root 密码硬编码在 docker-compose.yml 里吗？

  • 不推荐。生产中敏感信息应该用 env_file 引用 .env 文件，或用 Docker Secret / K8s Secret 管理。本节课为教学方便直接写在 YAML 中，实际项目要避免。

问：MySQL 容器为什么要配 TZ 时区？

  • 默认 MySQL 容器时区是 UTC，与北京时间差 8 小时，会导致 CURRENT_TIMESTAMP 等时间字段不对。配 TZ: Asia/Shanghai 让容器时区与国内一致。

知识点 K12-3：后端服务 Dockerfile 与构建

定义

后端服务 Dockerfile 描述如何把 SpringBoot 应用打包成 Docker 镜像。本节采用多阶段构建（Multi-stage Build）：

  • 第一阶段（builder）：用 maven:3.9-eclipse-temurin-17 镜像，包含完整 Maven + JDK，负责把源码打包成 jar。
  • 第二阶段（runtime）：用 eclipse-temurin:17-jre 镜像，只含 JRE，负责运行 jar。

多阶段构建的核心价值是把"构建工具"与"运行时"分离，最终镜像只包含运行所必需的内容，体积大幅减小。

原理

为什么需要多阶段构建？

图示 6：【单阶段构建的问题】
【单阶段构建的问题】
FROM maven:3.9-eclipse-temurin-17
COPY . /app
WORKDIR /app
RUN mvn clean package -DskipTests
CMD ["java", "-jar", "target/ctts-backend.jar"]
问题：
最终镜像包含完整 Maven + JDK + 源码 + target 目录
镜像体积约 800MB+（实际运行只需要 JRE + jar）
攻击面大（包含构建工具、编译器等无关组件）
拉取/推送慢，浪费存储与带宽
【多阶段构建的解决思路】
阶段1（builder）：用 maven 镜像打包 → 产出 jar
阶段2（runtime）：用 jre 镜像 + 阶段1产出的 jar → 最终镜像
最终镜像只包含：JRE + jar，约 300MB

后端 Dockerfile 多阶段构建原理：

图示 7：阶段 1：builder（构建阶段）
阶段 1：builder（构建阶段）
基础镜像：maven:3.9-eclipse-temurin-17
包含：Maven 3.9 + JDK 17 + 编译工具
操作：
1. COPY pom.xml → 下载依赖（利用缓存）
2. COPY src/ → 编译源码
3. RUN mvn clean package -DskipTests
产出：target/ctts-backend-1.0.0.jar
COPY --from=builder 产物
▼
阶段 2：runtime（运行阶段）
基础镜像：eclipse-temurin:17-jre
包含：JRE 17（无 Maven、无编译器）
操作：
1. COPY --from=builder /app/target/*.jar
2. EXPOSE 8080
3. ENTRYPOINT java -jar app.jar
最终镜像体积：约 300MB

为什么先 COPY pom.xml 再 COPY src/？

  • Maven 构建分两步：①下载依赖（慢，但 pom.xml 不变就可缓存）②编译打包（快）。把这两步分开，pom.xml 不变时第一步走缓存，大幅加速重复构建。这是 Dockerfile 层缓存优化的经典模式。

后端连接 MySQL 的配置注入：

SpringBoot 的 application.yml 通过环境变量注入数据库配置：

spring:
  datasource:
    url: jdbc:mysql://${MYSQL_HOST:mysql}:${MYSQL_PORT:3306}/${MYSQL_DATABASE:ctts}
    username: ${MYSQL_USER:ctts}
    password: ${MYSQL_PASSWORD:ctts123}

Dockerfile 不写死配置，运行时由 docker-compose.yml 注入环境变量。
这样同一个镜像可以连不同的数据库（开发/测试/生产）。

问题 / 场景

问：为什么用 eclipse-temurin 而不是 openjdk？

  • openjdk 官方镜像已停止维护（OpenJDK 17 之后不再发布官方 Docker 镜像）。eclipse-temurin 是 Adoptium 项目维护的 OpenJDK 镜像，是当前推荐选择。其他可选：amazoncorretto、azul/zulu-openjdk。

问：多阶段构建真的能减小多少体积？

  • 实测对比：单阶段（maven 镜像）约 800MB，多阶段（jre 镜像）约 300MB，减小约 60%。生产环境中镜像体积直接影响拉取速度与存储成本。

问：为什么用 ENTRYPOINT 而不是 CMD？

  • ENTRYPOINT 让容器启动时固定执行 java -jar，不会被 docker run 后面的参数覆盖。CMD 可以被覆盖。对于"容器就是跑这个 jar"的场景，ENTRYPOINT 更合适。

问：为什么 -DskipTests 跳过测试？

  • 构建镜像时跑单元测试会拖慢构建速度，且测试失败会导致镜像构建失败。测试应该在 CI 流水线中单独跑，构建镜像时跳过。

知识点 K12-4：前端服务 Dockerfile 与构建

定义

前端服务 Dockerfile 描述如何把 Vue3 应用打包成 Docker 镜像。本节采用多阶段构建：

  • 第一阶段（builder）：用 node:20-alpine 镜像，包含 Node.js + npm，负责 npm run build 生成静态文件（dist/）。
  • 第二阶段（runtime）：用 nginx:alpine 镜像，把 dist/ 复制到 Nginx 静态目录，并配置 nginx.conf 实现：①静态资源托管 ②SPA 路由 fallback ③反向代理后端 API。

Nginx 反向代理是本知识点的核心——它解决了浏览器跨域问题，让前端与后端看起来"同源"。

原理

前端为什么要多阶段构建？

图示 9：【单阶段构建的问题】
【单阶段构建的问题】
FROM node:20-alpine
COPY . .
RUN npm install && npm run build
CMD ["npm", "run", "preview"]
问题：
最终镜像包含 Node.js + 源码 + node_modules + dist
镜像体积约 500MB+（实际运行只需要 Nginx + dist）
用 npm run preview 跑前端不适合生产（性能差、无 SPA fallback）
【多阶段构建】
阶段1（builder）：node 镜像 → npm run build → 产出 dist/
阶段2（runtime）：nginx 镜像 + dist/ → 最终镜像约 50MB

Nginx 反向代理解决跨域的原理：

SPA 路由 fallback 原理：

Vue3 用 Vue Router 时，路由可能是 /users、/courses/123 等前端路由。
但这些路由在 Nginx 上没有对应的静态文件，会 404。

解决：用 try_files 把所有找不到的路由都返回 index.html
      让 Vue Router 在前端处理路由。

location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
}

问题 / 场景

问：为什么不直接用 npm run preview 跑前端？

  • preview 是 Vite 提供的预览命令，不适合生产：①性能差（基于 Node.js）②无 SPA fallback ③无 gzip 压缩 ④无反向代理能力。生产必须用 Nginx 托管静态文件。

问：proxy_pass http://backend:8080/; 末尾的 / 重要吗？

  • 非常重要！末尾有 / 表示"替换 location 匹配的部分"：/api/users → /users（去掉了 /api）。末尾无 / 表示"保留完整路径"：/api/users → /api/users。根据后端接口设计选择。本节用 http://backend:8080/ 让后端接口去掉 /api 前缀。

问：为什么不把 dist 直接放到后端 SpringBoot 里？

  • 可以（SpringBoot 静态资源托管），但不推荐：①前后端耦合，每次前端改动都要重新打后端 ②Nginx 性能远优于 SpringBoot 静态资源 ③无法独立扩缩容。前后端分离 + Nginx 托管是主流方案。

问：构建阶段用 npm ci 还是 npm install？

  • 推荐用 npm ci：①基于 package-lock.json 安装，确保版本一致 ②删除现有 node_modules 后安装，更干净 ③速度比 npm install 快。前提是项目里有 package-lock.json。

        root /usr/share/nginx/html;
        index index.html;
        # SPA 路由 fallback：所有找不到的路由都返回 index.html
        try_files $uri $uri/ /index.html;
    }

    # ───────── 2. 反向代理后端 API ─────────
    # 浏览器访问 /api/users → Nginx 转发到 http://backend:8080/users
    # 注意 proxy_pass 末尾的 /，会去掉 /api 前缀
    location /api/ {
        proxy_pass http://backend:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时设置
        proxy_connect_timeout 30s;
        proxy_send_timeout 30s;
        proxy_read_timeout 30s;
    }

    # ───────── 3. 静态资源缓存（带 hash 的文件长期缓存）─────────
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|eot)$ {
        root /usr/share/nginx/html;
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 健康检查端点（供 docker healthcheck 使用）
    location = /healthz {
        access_log off;
        return 200 "ok\n";
    }
}

知识点 K12-5：docker-compose.yml 完整编排与一键部署

定义

本知识点把 K12-2~K12-4 的三个服务（MySQL + Backend + Frontend）用一份 docker-compose.yml 串联起来，加入自定义网络、具名数据卷、依赖顺序、健康检查，实现"一条命令一键部署完整应用"。

完整的 docker-compose.yml 是 Docker 部分所有知识的集大成者：它整合了镜像管理（image/build）、容器管理（ports/volumes/environment）、网络（networks）、存储（volumes）、Dockerfile（build）、Compose 编排（depends_on/healthcheck）等全部能力。

原理

为什么 backend 用 service_healthy，frontend 用 service_started？

服务 依赖条件 原因
backend → mysql service_healthy SpringBoot 启动时建数据库连接池，MySQL 未就绪会启动失败
frontend → backend service_started（默认） 前端是 Nginx 静态资源，能独立启动；调后端是运行时行为，不强依赖后端启动

问题 / 场景

问：为什么 mysql 端口要暴露 3306？

  • 开发调试时方便用 Navicat、DBeaver 等工具连数据库查看数据。生产环境应该删除 ports: - "3306:3306"，只让 backend 容器内部访问，提高安全性。

问：build 和 image 同时写是什么意思？

  • build: ./backend + image: ctts-backend:v1 表示：构建 ./backend 目录的 Dockerfile，构建后打标签 ctts-backend:v1。后续 up 时若本地已有该标签镜像则直接用，加 --build 才强制重建。

问：healthcheck 的 start_period: 30s 是什么意思？

  • start_period 是"启动宽限期"。在这段时间内健康检查失败不计入 retries。MySQL 启动初始化需要时间，30 秒宽限期避免误判。

问：restart: unless-stopped 和 always 有什么区别？

  • unless-stopped：除非手动 docker stop，否则总是重启；即使宿主机重启也会自启（除非之前手动停过）。always：总是重启，包括手动 stop 后也会重启（实际表现为 stop 后不会自启，但宿主机重启后会自启）。生产推荐 unless-stopped。

问题 / 场景

问题 1：后端启动失败，日志报 Communications link failure

现象：
  backend 容器启动后立即退出
  docker compose logs backend 显示：
    HikariPool-1 - Connection is not available
    Communications link failure
    java.net.ConnectException: Connection refused

原因分析：
  后端启动时连不上 MySQL。可能原因：
  ① depends_on 没用 service_healthy，MySQL 还没就绪
  ② MYSQL_HOST 环境变量写错（如写成 localhost 而非 mysql）
  ③ MySQL 密码错误
  ④ 网络配置错误（backend 不在 ctts-net 网络）

排查命令：
  # 1. 看 MySQL 是否 healthy
  docker compose ps mysql
  # 如果不是 (healthy)，先排查 MySQL 启动问题

  # 2. 看后端环境变量
  docker compose exec backend env | grep MYSQL
  # 确认 MYSQL_HOST=mysql（不是 localhost）

  # 3. 在 backend 容器内测试连 MySQL
  docker compose exec backend sh -c "ping -c 2 mysql"
  # 能 ping 通说明网络 OK

  # 4. 检查密码
  docker compose exec mysql mysql -uctts -pctts123 -e "SELECT 1;"
  # 能连上说明密码对

解决方案：
  方案1（最常见）：把 depends_on 改为
    depends_on:
      mysql:
        condition: service_healthy

  方案2：检查 MYSQL_HOST 环境变量，确保是 mysql（服务名）而非 localhost

问题 2：前端调用后端 API 返回 502 Bad Gateway

现象：
  浏览器访问 http://localhost/ 能看到前端页面
  但调用 http://localhost/api/users 返回 502 Bad Gateway

原因分析：
  Nginx 反代失败，无法连接到 backend:8080。可能原因：
  ① backend 容器没启动或已退出
  ② nginx.conf 里 proxy_pass 地址写错（如写成 localhost:8080）
  ③ backend 不在 ctts-net 网络

排查命令：
  # 1. 看 backend 状态
  docker compose ps backend
  # 如果不是 Up，先排查 backend 启动问题

  # 2. 看 Nginx 错误日志
  docker compose exec frontend cat /var/log/nginx/error.log
  # 可能显示：connect() failed (111: Connection refused)

  # 3. 在 frontend 容器内测试连 backend
  docker compose exec frontend wget -qO- http://backend:8080/api/users
  # 能访问说明网络 OK

  # 4. 检查 nginx.conf
  docker compose exec frontend cat /etc/nginx/conf.d/default.conf
  # 确认 proxy_pass http://backend:8080/;（带末尾 /）

解决方案：
  方案1：启动 backend 容器（docker compose up -d backend）
  方案2：修正 nginx.conf 的 proxy_pass 地址为 http://backend:8080/
  方案3：确保 backend 在 ctts-net 网络

问题 3：前端页面白屏，浏览器控制台报 CORS 错误

现象：
  浏览器访问 http://localhost/ 白屏
  F12 控制台显示：
    Access to XMLHttpRequest at 'http://localhost:8080/api/users' 
    from origin 'http://localhost' has been blocked by CORS policy

原因分析：
  前端代码直接调 http://localhost:8080/api/users（后端地址）
  浏览器认为 80 和 8080 是不同源，触发跨域限制

解决方案：
  方案1（推荐）：前端代码改成调 /api/users（相对路径）
    让 Nginx 反代处理，避免跨域
    axios.defaults.baseURL = '/api'

  方案2：后端配置 CORS（不推荐，复杂且降低安全性）
    @CrossOrigin(origins = "http://localhost")

  方案3：开发环境用 Vite 的 proxy 配置（仅开发，生产还是要 Nginx 反代）

问题 4：修改 init.sql 后重新启动，数据库数据没变化

现象：
  修改了 init.sql（如新增表或数据）
  docker compose down && docker compose up -d
  发现数据库还是原来的样子

原因分析：
  init.sql 只在 MySQL 首次启动时执行（/var/lib/mysql 为空时）
  docker compose down 不删卷，mysql-data 卷里已有数据
  再次 up 时 MySQL 检测到数据已存在，跳过 init.sql

解决方案：
  # 彻底清理（删卷）后重启
  docker compose down -v
  docker compose up -d
  # 现在 MySQL 会重新初始化，执行新的 init.sql

问题 5：docker compose up -d 报端口占用

现象：
  Error starting userland proxy: Bind for 0.0.0.0:80: unexpected permission error
  或
  Bind for 0.0.0.0:3306 failed: port is already allocated

原因分析：
  宿主机的 80/3306/8080 端口被其他进程占用

排查命令：
  # Linux/Mac
  sudo netstat -anp | grep -E ':(80|3306|8080) '
  sudo lsof -i :80

  # Windows（PowerShell）
  netstat -ano | findstr ":80 "

解决方案：
  方案1：停掉占用端口的进程
  方案2：改 docker-compose.yml 的端口映射
    ports:
      - "8081:80"        # 改用 8081 访问前端
      - "3307:3306"      # 改用 3307 连 MySQL
      - "8082:8080"      # 改用 8082 调后端 API

易错点

  1. ❌ 出问题就直接 docker compose down -v 删数据重试。✅ 先看日志定位问题，删卷是最后手段。
  2. ❌ 只看容器状态，不看日志。✅ docker compose logs <服务名> 是排障第一步。
  3. ❌ 改了 Dockerfile/compose 文件后不重建。✅ docker compose up -d --build 强制重建。
  4. ❌ 改了 init.sql 后期望自动生效。✅ init.sql 只首次执行，改后要 down -v 删卷。
  5. ❌ 浏览器跨域问题在后端配 CORS。✅ 优先用 Nginx 反代解决，前端调相对路径 /api/。

小结

部署验证要按清单逐项检查：MySQL 数据、后端 API、前端页面、前后端联调、SPA 路由、容器间通信、数据持久化。排障遵循"看状态 → 看日志 → 进容器"三步法。常见问题有：后端连不上数据库（depends_on 配置）、前端跨域（用 Nginx 反代解决）、502 Bad Gateway（backend 未启动或反代地址错）、init.sql 不生效（需删卷重试）、端口冲突（改映射端口）。
