二、知识点详解

知识点 K17-1：实践总览与 CTTS 三服务 Deployment 规划

定义

CTTS 三服务 Deployment 规划 是在编写 YAML 之前，对三个服务（MySQL + 后端 + 前端）的副本数、资源限制、标签、Namespace、部署顺序进行系统设计的过程。规划先行是云原生运维的基本素养——"先想清楚再写 YAML"，避免边写边改导致部署混乱。

问题 / 场景

问：为什么 MySQL 用 1 副本而不是 3 副本？

  • MySQL 是有状态应用，多副本会导致数据写入冲突（除非用主从复制，但那是 StatefulSet + 持久化存储的场景）。本课用 1 副本 Deployment 简化部署，生产环境 MySQL 必须用 StatefulSet + PV/PVC（第 22 次课学），保证数据持久化和有序扩缩容。

问：副本数越多越好吗？

  • 不是。副本数要根据流量和资源平衡。3 副本已满足高可用最低要求（挂 1 个还有 2 个），副本过多会浪费资源、增加数据库连接压力。生产环境通常配合 HPA（Horizontal Pod Autoscaler）根据 CPU/内存自动扩缩容。

问：资源限制 requests 和 limits 怎么设？

  • requests 是 Pod 调度依据（K8s 保证分配），limits 是硬上限（超过会被限制或杀掉）。经验值：
    • requests 设为 limits 的 50%~70%（留出 burst 空间）
    • 后端 Java 应用 requests 内存至少 256Mi（JVM 堆 + 元空间）
    • 前端 Nginx 静态资源 requests 内存 128Mi 足够
    • 数据库 requests 内存 512Mi 起（InnoDB 缓冲池）

问：为什么标签要分 app / tier / version 三层？

  • app 区分服务（核心标识），tier 区分层级（便于按层筛选，如查所有 backend），version 区分版本（滚动更新时区分 v1/v2 Pod）。这是 K8s 标签的最佳实践，便于后续 Service 选择、监控分组、灰度发布。

易错点

  1. ❌ MySQL 设 3 副本导致数据冲突。✅ MySQL 是有状态应用，多副本会数据冲突，本课用 1 副本 Deployment 简化，生产用 StatefulSet。
  2. ❌ 忘记规划部署顺序，三个 Deployment 同时 apply。✅ 应按 MySQL → 后端 → 前端 顺序部署，否则后端启动时连不上 MySQL 会 CrashLoopBackOff。
  3. ❌ 标签设计混乱（如三个服务都用 app=ctts）。✅ 每个服务用唯一 app 标签（ctts-mysql / ctts-backend / ctts-frontend），便于 Service 选择和筛选。
  4. ❌ 资源限制设置过小（如后端 memory limits 128Mi）。✅ Java 应用 JVM 堆 + 元空间至少需要 256Mi，设太小会 OOMKilled。
  5. ❌ 忘记创建 namespace 直接 apply。✅ YAML 里写了 namespace: ctts，但 namespace 不存在会报错，需先 kubectl create namespace ctts。

小结

实践总览与规划是 CTTS 三服务部署的"施工图"：副本数（MySQL 1 / 后端 3 / 前端 2）+ 资源限制（按负载分配）+ 标签设计（app/tier/version 三层）+ Namespace（ctts）+ 部署顺序（MySQL→后端→前端）。规划先行，YAML 才能写得清晰、部署才能顺利。

知识点 K17-2：MySQL Deployment 部署

定义

MySQL Deployment 部署 是编写 MySQL 的 Deployment YAML 并应用到集群的过程。MySQL 是 CTTS 的数据存储服务，部署时要特别注意：① root 密码通过环境变量配置；② 数据通过 emptyDir 卷临时持久化（本课简化，生产用 PV/PVC）；③ 资源限制要充足（InnoDB 缓冲池需要内存）。

原理

MySQL Deployment 的关键设计点：

图示 5：结构与流程重绘
1. 副本数：1 - MySQL 是有状态应用，多副本数据冲突 - 本课用 1 副本 Deployment 简化（生产用 StatefulSet） 2. 镜像：mysql:8.0 - 官方镜像，版本明确（不用 :latest） - 端口 3306 3. 环境变量： - MYSQL_ROOT_PASSWORD：root 用户密码（必须设置，否则启动失败） - MYSQL_DATABASE：自动创建的数据库（ctts） - MYSQL_USER / MYSQL_PASSWORD：业务用户（可选） 4. 数据持久化： - 本课用 emptyDir 卷（Pod 删除数据丢失，仅实践用） - 生产用 PersistentVolumeClaim（第 22 次课学） - 挂载路径：/var/lib/mysql（MySQL 数据目录） 5. 资源限制： - requests: cpu=500m, memory=512Mi（InnoDB 缓冲池） - limits: cpu=1000m, memory=1Gi - 内存太小会 OOM，CPU 太小会查询慢 6. 标签： - app=ctts-mysql, tier=database

MySQL 官方镜像的环境变量：

mysql:8.0 镜像支持的环境变量：
  MYSQL_ROOT_PASSWORD     # root 密码（必须，否则启动报错）
  MYSQL_DATABASE          # 启动时自动创建的数据库
  MYSQL_USER              # 业务用户名（可选）
  MYSQL_PASSWORD          # 业务用户密码（可选）
  MYSQL_ALLOW_EMPTY_PASSWORD  # 允许空密码（不推荐，仅测试）
  MYSQL_RANDOM_ROOT_PASSWORD  # 随机 root 密码（打印到日志）

本课使用：
  MYSQL_ROOT_PASSWORD=ctts123456
  MYSQL_DATABASE=ctts
  MYSQL_USER=ctts
  MYSQL_PASSWORD=ctts123456

emptyDir 卷 vs PVC 卷：

emptyDir（本课用）：
  - Pod 创建时生成，Pod 删除时数据丢失
  - 适合：临时数据、缓存、实践练习
  - 语法：volumes.emptyDir

PersistentVolumeClaim（生产用，第 22 次课学）：
  - 持久化存储，Pod 删除后数据保留
  - 适合：数据库、文件存储
  - 语法：volumes.persistentVolumeClaim

本课为简化用 emptyDir，但要知道生产环境必须用 PVC！

问题 / 场景

问：MySQL Deployment 不设 MYSQL_ROOT_PASSWORD 会怎样？

  • 容器启动会报错退出，Pod 状态变为 CrashLoopBackOff。MySQL 官方镜像要求必须设置 MYSQL_ROOT_PASSWORD（或 MYSQL_ALLOW_EMPTY_PASSWORD=yes，但不推荐）。这是 MySQL Deployment 最常见的启动失败原因。

问：为什么用 emptyDir 而不是直接用容器本地存储？

  • 容器本地存储（ writable layer）在容器重启后会丢失（容器重建）。emptyDir 是 Pod 级别的卷，Pod 内容器重启数据保留（只有 Pod 删除才丢失）。比容器本地存储稍好，但仍不是真正的持久化。生产环境必须用 PVC。

问：MySQL 资源限制设多少合适？

  • 取决于数据量。本课实践用 512Mi~1Gi 足够。生产环境：① InnoDB 缓冲池通常占内存 50%~70%；② 建议 requests memory 2Gi 起，limits 4Gi；③ CPU requests 1000m 起（数据库是 CPU 密集型）。

问：MySQL Pod 挂了数据怎么办？

  • 本课用 emptyDir，Pod 删除数据丢失。生产环境用 PVC，Pod 重建后数据自动挂载恢复。这就是为什么"生产环境 MySQL 必须用 StatefulSet + PVC"。

完整示例

MySQL Deployment YAML（完整可执行）：

# 文件名：ctts-mysql-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-mysql
  namespace: ctts
  labels:
    app: ctts-mysql
    tier: database
spec:
  replicas: 1                              # 1 副本（有状态应用，多副本冲突）
  selector:
    matchLabels:
      app: ctts-mysql
  template:
    metadata:
      labels:
        app: ctts-mysql
        tier: database
        version: v1
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        imagePullPolicy: IfNotPresent      # 本地有就不拉取
        ports:
        - containerPort: 3306
          name: mysql
          protocol: TCP
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "ctts123456"              # root 密码（必须设置）
        - name: MYSQL_DATABASE
          value: "ctts"                    # 自动创建数据库 ctts
        - name: MYSQL_USER
          value: "ctts"                    # 业务用户
        - name: MYSQL_PASSWORD
          value: "ctts123456"              # 业务用户密码
        resources:

易错点

  1. ❌ 忘记设置 MYSQL_ROOT_PASSWORD。✅ MySQL 官方镜像要求必须设置 root 密码，否则启动报错，Pod CrashLoopBackOff。
  2. ❌ 副本数设为 3。✅ MySQL 有状态，多副本数据冲突，本课用 1 副本，生产用 StatefulSet。
  3. ❌ 数据卷用 emptyDir 还以为是持久化。✅ emptyDir 在 Pod 删除时数据丢失，生产必须用 PVC（第 22 次课学）。
  4. ❌ 资源限制 memory 太小（如 128Mi）。✅ MySQL InnoDB 缓冲池至少 256Mi，设太小会 OOMKilled。
  5. ❌ readinessProbe 配置错误导致 Pod 一直不 Ready。✅ 探针命令要正确（mysqladmin ping 或 mysql -e "SELECT 1"），initialDelaySeconds 要给足（30 秒以上）。

小结

MySQL Deployment 部署的关键：1 副本（有状态简化）+ mysql:8.0 镜像 + 环境变量（MYSQL_ROOT_PASSWORD 必须设置）+ emptyDir 卷临时持久化（生产用 PVC）+ 资源限制（memory 512Mi/1Gi）+ 标签（app=ctts-mysql, tier=database）。部署后用 kubectl exec 进入 Pod 验证数据库创建成功。

知识点 K17-3：后端 Deployment 部署

定义

CTTS 后端 Deployment 部署 是编写 SpringBoot 后端的 Deployment YAML 并应用到集群的过程。后端是 CTTS 的核心 API 服务，部署要点：① 3 副本高可用；② 环境变量连接 MySQL（DB_HOST / DB_PORT / DB_NAME / DB_USER / DB_PASSWORD）；③ requests/limits 资源限制（Java 应用需充足内存）；④ imagePullPolicy: Never（本地镜像）。

原理

后端 Deployment 的关键设计点：

1. 副本数：3
   - 后端是无状态应用，3 副本高可用
   - 任意一个 Pod 挂了，还有 2 个可用
   - 滚动更新时 3 副本能保证服务不中断

2. 镜像：ctts-backend:v1
   - 第 8 次课构建的本地镜像
   - imagePullPolicy: Never（用本地镜像，不从仓库拉取）

3. 端口：8080
   - SpringBoot 默认端口

4. 环境变量（连接 MySQL）：
   - DB_HOST: mysql.ctts.svc.cluster.local
     （Service DNS 名，第 18 次课创建 mysql Service 后才能解析）
     （本课临时调试可用 Pod IP，或先创建 headless Service）
   - DB_PORT: 3306
   - DB_NAME: ctts
   - DB_USER: ctts
   - DB_PASSWORD: ctts123456
   - SPRING_PROFILES_ACTIVE: prod

5. 资源限制：
   - requests: cpu=250m, memory=256Mi
   - limits:   cpu=500m, memory=512Mi
   - Java 应用 JVM 堆至少 256Mi，设太小会 OOM

6. 标签：
   - app=ctts-backend, tier=backend, version=v1

imagePullPolicy 三种策略：

Always:        每次都从仓库拉取（生产用，确保最新）

问题 / 场景

问：为什么后端用 3 副本，MySQL 用 1 副本？

  • 后端是无状态应用（不存数据），多副本无冲突，3 副本高可用。MySQL 是有状态应用（存数据），多副本数据冲突，必须 1 副本（或用 StatefulSet 主从复制）。

问：后端启动时报"Connection refused mysql.ctts.svc.cluster.local:3306"怎么办？

  • 三个可能原因：① mysql Service 还没创建（用 kubectl get svc mysql -n ctts 检查）；② MySQL Pod 还没 Ready（用 kubectl get pod -l app=ctts-mysql 检查）；③ 后端启动比 MySQL 快（SpringBoot 启动 5 秒，MySQL 启动 30 秒）。解决：先确保 MySQL Ready，再部署后端，或加启动重试机制。

问：imagePullPolicy 用 Always 还是 Never？

  • 本课用 Never（本地镜像）。生产环境用 Always（从镜像仓库拉取，确保版本一致）。如果用 IfNotPresent，本地有就不拉取，但版本可能过期。本课的 ctts-backend:v1 是本地构建的，Docker Hub 上没有，所以必须用 Never。

问：Java 应用内存限制怎么设？

  • Java 应用 JVM 堆 + 元空间 + 线程栈至少 256Mi。建议：① requests memory 256Mi 起；② limits memory 512Mi 起；③ 用 -XX:MaxRAMPercentage=75.0 让 JVM 根据容器 limits 自动设置堆大小（Java 10+ 支持）。本课简化，直接设 requests/limits。

# 文件名：ctts-backend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-backend
  namespace: ctts
  labels:
    app: ctts-backend
    tier: backend
spec:
  replicas: 3                              # 3 副本高可用
  revisionHistoryLimit: 10                 # 保留 10 个历史版本（用于回滚）
  strategy:
    type: RollingUpdate                    # 滚动更新（默认）
    rollingUpdate:
      maxSurge: 25%                        # 滚动更新时最多超出 25%
      maxUnavailable: 25%                  # 滚动更新时最多不足 25%
  selector:
    matchLabels:
      app: ctts-backend
  template:
    metadata:
      labels:
        app: ctts-backend
        tier: backend
        version: v1
    spec:
      containers:
      - name: backend
        image: ctts-backend:v1
        imagePullPolicy: Never             # 本地镜像，不从仓库拉取
        ports:
        - containerPort: 8080
          name: http
          protocol: TCP
        env:
        - name: SPRING_PROFILES_ACTIVE
          value: "prod"
        - name: DB_HOST
          value: "mysql.ctts.svc.cluster.local"   # MySQL Service DNS 名
        - name: DB_PORT
          value: "3306"
        - name: DB_NAME
          value: "ctts"
        - name: DB_USER
          value: "ctts"
        - name: DB_PASSWORD
          value: "ctts123456"
        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
        readinessProbe:                    # 就绪探针（可选，本课了解）
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 30          # SpringBoot 启动慢，给 30 秒
          periodSeconds: 10
        livenessProbe:                     # 存活探针（可选，本课了解）
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 60
          periodSeconds: 10

后端启动流程：
  Pod 创建 → 拉取镜像（Never，用本地）→ 启动 SpringBoot
  → 读取环境变量 → 连接 MySQL Service → 健康检查通过
  → readinessProbe 通过 → Pod Ready
  耗时：约 30~60 秒（SpringBoot 启动 + 连接数据库）

易错点

  1. ❌ imagePullPolicy 设为 Always 或 IfNotPresent。✅ 本地构建的镜像必须用 Never，否则 K8s 尝试从 Docker Hub 拉取，拉不到报 ImagePullBackOff。
  2. ❌ 忘记创建 MySQL Service，后端连不上 MySQL。✅ 后端用 mysql.ctts.svc.cluster.local 连接，必须先 kubectl expose deployment ctts-mysql --name=mysql 创建 Service。
  3. ❌ 后端比 MySQL 先部署，导致后端启动时 MySQL 还没 Ready。✅ 按 MySQL→后端 顺序部署，等 MySQL Ready 再部署后端。
  4. ❌ memory limits 设太小（如 128Mi）。✅ Java 应用 JVM 堆至少 256Mi，设太小会 OOMKilled，Pod 状态显示 OOMKilled。
  5. ❌ readinessProbe initialDelaySeconds 太短（如 5 秒）。✅ SpringBoot 启动需 30 秒以上，探针延迟要 30 秒以上，否则 Pod 反复重启。

小结

后端 Deployment 部署的关键：3 副本（无状态高可用）+ ctts-backend:v1 镜像 + imagePullPolicy: Never（本地镜像）+ 环境变量连接 MySQL（DB_HOST 指向 Service DNS）+ requests/limits（memory 256Mi/512Mi）+ 标签（app=ctts-backend, tier=backend）。部署前先创建 MySQL Service，部署后用 kubectl logs 确认 SpringBoot 启动成功。

知识点 K17-4：前端 Deployment 部署

定义

CTTS 前端 Deployment 部署 是编写 Vue3 前端（Nginx 静态服务）的 Deployment YAML 并应用到集群的过程。前端是 CTTS 的用户界面，部署要点：① 2 副本（静态资源轻量，2 副本够用）；② Nginx 镜像托管 Vue3 构建产物；③ 资源限制小（静态资源占用低）；④ Nginx 反向代理到后端 Service。

原理

前端 Deployment 的关键设计点：

1. 副本数：2
   - 前端是静态资源服务，资源占用小
   - 2 副本够用（挂 1 个还有 1 个）
   - 不需要 3 副本（静态资源无状态，2 副本足够高可用）

2. 镜像：ctts-frontend:v1
   - 第 8 次课构建的镜像（Vue3 build 产物 + Nginx）
   - imagePullPolicy: Never（本地镜像）

3. 端口：80
   - Nginx 默认端口

4. 资源限制：
   - requests: cpu=100m, memory=128Mi
   - limits:   cpu=200m, memory=256Mi
   - 静态资源服务，资源占用小

5. 标签：
   - app=ctts-frontend, tier=frontend, version=v1

6. Nginx 反向代理（可选，本课简化）：
   - 前端通常配置 Nginx 反向代理 /api 到后端 Service
   - 本课简化，先部署静态资源，反向代理在第 19 次课 Ingress 详学

问题 / 场景

问：前端为什么用 2 副本而不是 3 副本？

  • 前端是静态资源服务，资源占用小（CPU 100m、内存 128Mi），2 副本已满足高可用（挂 1 个还有 1 个）。3 副本会浪费资源。副本数根据流量和资源平衡，不是越多越好。

问：前端 Nginx 怎么访问后端 API？

  • 两种方式：① Nginx 反向代理（推荐）：前端 Nginx 配置 location /api { proxy_pass http://ctts-backend.ctts.svc.cluster.local:8080; }，浏览器请求 /api/xxx 由 Nginx 转发到后端 Service；② CORS 跨域：前端直接请求后端 Service，需后端配置 CORS 允许跨域。生产推荐方式 ①（避免 CORS 问题，前端 Nginx 和后端同域）。

问：前端资源限制为什么这么小？

  • Nginx 托管静态资源，CPU 100m（0.1 核）足够处理几百 QPS，内存 128Mi 足够缓存静态文件。前端不像后端有业务逻辑和数据库连接，资源占用低。

问：前端 Pod 挂了会怎样？

  • 2 副本，挂 1 个还有 1 个，Service 会负载均衡到健康 Pod。如果 2 个都挂了，用户访问不到页面，但后端 API 仍可用（影响范围限于前端）。Deployment 会自动重建 Pod。

前端 Deployment YAML（完整可执行）：

# 文件名：ctts-frontend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-frontend
  namespace: ctts
  labels:
    app: ctts-frontend
    tier: frontend
spec:
  replicas: 2                              # 2 副本（静态资源轻量）
  revisionHistoryLimit: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  selector:
    matchLabels:
      app: ctts-frontend
  template:
    metadata:
      labels:
        app: ctts-frontend
        tier: frontend
        version: v1
    spec:
      containers:
      - name: frontend
        image: ctts-frontend:v1
        imagePullPolicy: Never             # 本地镜像
        ports:
        - containerPort: 80
          name: http
          protocol: TCP
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "200m"
            memory: "256Mi"
        readinessProbe:                    # 就绪探针
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5           # Nginx 启动快，5 秒足够
          periodSeconds: 5
        livenessProbe:                     # 存活探针
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 10
          periodSeconds: 10

问题 / 场景

问：滚动更新期间用户请求会打到 v1 还是 v2 Pod？

  • 都会。Service 负载均衡到所有 Ready 的 Pod，滚动更新期间 v1 和 v2 Pod 共存，请求会分到两种版本。如果 v1 和 v2 API 兼容，用户无感知；如果不兼容（如 v2 改了 API 路径），需要用 Blue-Green 或 Canary 发布（高级策略，本课了解）。

问：滚动更新卡住（一直 1 out of 3 updated）怎么办？

  • 可能原因：① v2 镜像构建有问题，Pod 启动失败（CrashLoopBackOff）；② readinessProbe 配置错误，Pod 起来了但探针不通过；③ 资源不足，新 Pod Pending。排查：kubectl get pods 看新 Pod 状态，kubectl describe pod 看 Events，kubectl logs 看应用日志。

问：回滚后 v2 版本还在历史里吗？

  • 在。回滚操作本身也是一次"滚动更新"（创建新 revision），原来的 v2 revision 仍在历史里，可以再次回滚到 v2。revisionHistoryLimit: 10 默认保留 10 个版本。

问：怎么暂停滚动更新？

  • kubectl rollout pause deployment/ctts-backend。暂停后可以修改多个字段（如镜像 + 环境变量）再一起触发更新。恢复用 kubectl rollout resume deployment/ctts-backend。本课了解，不深入。

易错点

  1. ❌ kubectl set image 容器名写错。✅ 容器名必须与 YAML 里 spec.template.spec.containers[].name 一致（本课是 backend），否则报错 container "xxx" not found。
  2. ❌ 忘记构建 v2 镜像就 set image。✅ 先 docker build -t ctts-backend:v2 .，再 set image，否则 Pod ImagePullBackOff（Never 策略下找不到本地镜像）。
  3. ❌ 滚动更新期间没观察过程。✅ 用 kubectl rollout status 或 kubectl get pods -w 观察，及时发现问题。
  4. ❌ 以为回滚只能回上一版。✅ 用 --to-revision=N 可以回滚到任意历史版本。
  5. ❌ 不加 --record 导致 history 没有 CHANGE-CAUSE。✅ 建议加 --record，便于追溯变更原因。

小结

滚动更新实战流程：① 构建 v2 镜像 → ② kubectl set image 触发更新 → ③ kubectl rollout status 观察 → ④ kubectl rollout history 查看版本 → ⑤ 必要时 kubectl rollout undo 回滚。3 副本 + maxSurge=25% + maxUnavailable=25% 保证更新期间最少 2 个 Pod 可用，服务不中断。旧 ReplicaSet 保留（副本=0）用于回滚，revisionHistoryLimit 控制保留版本数。

     spec:

     kubectl create secret docker-registry regcred \
       --docker-server=<registry> \
       --docker-username=<user> \
       --docker-password=<pass> \
       -n ctts
     # YAML 中引用：
     spec:
       imagePullSecrets:
       - name: regcred
  ③ 检查镜像名拼写

         memory: "128Mi"    # 从 256Mi 降到 128Mi

     minikube stop
     minikube start --cpus=4 --memory=6g
  ③ 查看节点资源：
     kubectl describe node minikube

易错点

  1. ❌ 遇到问题直接重新 apply 不排查。✅ 先 kubectl describe 和 kubectl logs 看根因，定位后再修复。
  2. ❌ 看 logs 时忘记加 Pod 名。✅ kubectl logs <pod-name>，或用 kubectl logs deployment/<name> 简化。
  3. ❌ CrashLoopBackOff 时只看 describe 不看 logs。✅ describe 看 K8s 层面事件，logs 看应用层报错，二者都要看。
  4. ❌ 修复后忘记重新 apply。✅ 修改 YAML 后必须 kubectl apply -f xxx.yaml 才生效。
  5. ❌ 排查时不知道用 -l 筛选。✅ 用 kubectl get pods -l app=xxx 筛选特定服务的 Pod，避免信息过载。

小结

K8s 部署问题排查四步法：① 看状态（kubectl get pods 的 STATUS 列）→ ② 看详情（kubectl describe pod 的 Events）→ ③ 看日志（kubectl logs）→ ④ 定根因（修复 YAML 重新 apply）。四大常见问题：CrashLoopBackOff（应用崩溃，看日志）、ImagePullBackOff（镜像拉取失败，检查镜像名和 imagePullPolicy）、Pending（资源不足，减少 requests 或加节点）、Deployment 0/3（selector 不匹配，修正 YAML）。90% 的部署问题都能用 describe + logs 定位。

四、拓展阅读（选学）

  1. StatefulSet vs Deployment：MySQL 等有状态应用生产环境用 StatefulSet，提供稳定网络标识、有序部署/扩缩容、持久存储。本课用 1 副本 Deployment 简化，第 22 次课学 PV/PVC 后再深入 StatefulSet。
  2. Horizontal Pod Autoscaler（HPA）：根据 CPU/内存自动扩缩容 Deployment 副本数。kubectl autoscale deployment ctts-backend --cpu-percent=70 --min=3 --max=10。
  3. PodDisruptionBudget（PDB）：限制自愿中断（如滚动更新、节点维护）时最多不可用 Pod 数，保证可用性。
  4. Blue-Green / Canary 发布：高级发布策略。Blue-Green 是同时部署两套环境，切换流量；Canary 是渐进放量（5%→20%→100%）。需配合 Service Mesh（如 Istio）实现。
  5. Init Container：在主容器启动前运行的容器，用于初始化任务（如等待 MySQL 就绪、下载配置）。本课未用，但生产常用。
