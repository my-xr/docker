一、选择题（共 40 题，每题 2 分）

1.1 单项选择题（30 题）

15-选择-001（★ 知识点：K15-1 Pod 概念） 关于 Pod，下列说法正确的是？

  • APod 是 K8s 中可以直接操作容器的最小单元
  • BPod 是 K8s 的最小调度单元，K8s 不直接管容器
  • C一个 Pod 只能包含一个容器
  • DPod 是持久的，创建后不会消失

答案：B 解析：Pod 是 K8s 最小调度单元，K8s 不直接操作容器而是操作 Pod。A 错，K8s 不直接操作容器；C 错，一个 Pod 可含多个容器（sidecar 模式）；D 错，Pod 是临时性的，会因各种原因消失。

15-选择-002（★ 知识点：K15-1 Pod 概念） K8s 为什么引入 Pod 而不直接管容器？

  • A因为 K8s 不支持容器技术
  • B因为 Pod 比容器更轻量
  • C因为实际应用中多个容器需要紧密协作，Pod 把它们作为整体调度管理，并共享网络和存储
  • D因为 Pod 启动比容器快

答案：C 解析：引入 Pod 的核心原因是：① 容器组的管理需求（多容器协作）；② 共享网络和存储；③ 屏蔽容器运行时差异。A、B、D 都不对。

15-选择-003（★ 知识点：K15-1 Pod 共享） Pod 内容器共享下列哪些资源？

  • APID 命名空间和 IPC 命名空间
  • B网络命名空间和存储卷
  • CCPU 和内存
  • D容器镜像

答案：B 解析：Pod 内容器共享同一个网络命名空间（同一 IP、端口空间，可通过 localhost 通信）和存储卷。A 不完全准确（默认共享网络和存储，PID/IPC 共享需显式配置）；C 错，资源是按容器隔离的；D 错，每个容器有自己的镜像。

15-选择-004（★ 知识点：K15-1 Pod 通信） Pod 内的两个容器 A 和 B，A 如何访问 B 监听的 8080 端口？

  • A通过 Pod IP 访问 pod-ip:8080
  • B通过 localhost:8080
  • C通过容器 B 的 IP 访问
  • D无法访问

答案：B 解析：Pod 内容器共享网络命名空间，可以通过 localhost 互相通信。A 也可行但不常用（Pod IP 主要用于 Pod 间通信）；C 错，容器没有独立 IP；D 错。

15-选择-005（★ 知识点：K15-2 YAML 四要素） Pod YAML 的四要素不包括下列哪一项？

  • AapiVersion
  • Bkind
  • Cmetadata
  • Dstatus

答案：D 解析：四要素是 apiVersion、kind、metadata、spec。status 是 K8s 自动维护的（实际状态），用户不写。

15-选择-006（★ 知识点：K15-2 apiVersion） Pod 资源的 apiVersion 是？

  • Aapps/v1
  • Bv1
  • Cbatch/v1
  • Dnetworking.k8s.io/v1

答案：B 解析：Pod 是 K8s 核心资源，apiVersion 是 v1。apps/v1 是 Deployment/ReplicaSet；batch/v1 是 Job/CronJob；networking.k8s.io/v1 是 Ingress。

15-选择-007（★ 知识点：K15-2 kind） Pod YAML 中 kind 字段的正确写法是？

  • Apod
  • BPOD
  • CPod
  • Dpods

答案：C 解析：kind 必须首字母大写，写作 Pod。小写 pod 或全大写 POD 都会报错。

15-选择-008（★ 知识点：K15-2 metadata） 关于 Pod YAML 的 metadata.name 字段，下列说法正确的是？

  • A是 Pod 的唯一标识，namespace 内不能重复
  • B是 Pod 的标签，可重复
  • C全集群唯一，跨 namespace 也不能重复
  • D可不填，K8s 自动生成

答案：A 解析：metadata.name 是 Pod 唯一标识，namespace 内唯一，必填。B 错，labels 才是标签；C 错，不同 namespace 可以有同名 Pod；D 错，name 必填。

15-选择-009（★ 知识点：K15-2 labels） Pod YAML 中 labels 的作用是？

  • A标识 Pod 唯一性
  • B用于 Service/Deployment 通过 selector 选择 Pod
  • C限制 Pod 的资源使用
  • D定义 Pod 的启动顺序

答案：B 解析：labels 是键值对，用于被 Service/Deployment 通过 label selector 选择。A 错，唯一性由 name 保证；C、D 都不对。

15-选择-010（★ 知识点：K15-3 image） Pod YAML 中 image 字段的格式是？

  • A镜像名:标签
  • B仓库地址:镜像名
  • C镜像ID
  • D镜像URL

答案：A 解析：image 格式是 [仓库地址/]镜像名:标签，如 ctts-backend:v1、mysql:8.0。不写标签默认 :latest。

15-选择-011（★ 知识点：K15-3 ports） Pod YAML 中 ports 字段的作用是？

  • A自动映射容器端口到宿主机
  • B声明容器暴露的端口，供 Service 引用和文档性
  • C限制容器只能监听该端口
  • D必填字段

答案：B 解析：ports 是声明性字段，不写也能通过 Pod IP 访问，写了便于 Service 引用和文档性。A 错，端口映射到宿主机由 Service/NodePort 处理；C 错，不限制容器监听；D 错，非必填。

15-选择-012（★ 知识点：K15-3 env） Pod YAML 中 env 字段的作用是？

  • A设置容器的环境变量
  • B设置容器的端口
  • C设置容器的资源限制
  • D设置容器的启动命令

答案：A 解析：env 用于设置容器环境变量，如 SPRING_PROFILES_ACTIVE=prod。B 是 ports；C 是 resources；D 是 command/args。

15-选择-013（★★ 知识点：K15-3 requests vs limits） 关于 resources.requests 和 limits 的区别，下列说法正确的是？

  • Arequests 是资源上限，limits 是资源保底
  • Brequests 是资源保底（影响调度），limits 是资源上限（限制运行时）
  • C两者作用相同，只是写法不同
  • D只设 requests 就够了，limits 可不设

答案：B 解析：requests 是保底（调度依据，至少这么多），limits 是上限（运行时限制，最多这么多）。A 说反了；C 错；D 错，生产环境两者都要设。

15-选择-014（★ 知识点：K15-3 CPU 单位） K8s 中 CPU 资源单位 500m 表示？

  • A500 个 CPU 核
  • B0.5 核 CPU
  • C500 MB 内存
  • D500 MHz 频率

答案：B 解析：m 是 millicore（毫核），1000m = 1 核，所以 500m = 0.5 核。

15-选择-015（★ 知识点：K15-3 内存单位） K8s 中内存资源 1Gi 等于？

  • A1000 MB
  • B1024 MB（即 1024×1024 KiB）
  • C1 GB
  • D100 MB

答案：B 解析：Gi 是 GiB（二进制单位），1 Gi = 1024 Mi = 1024×1024 KiB。M/Mi 区别：M 是十进制（1000），Mi 是二进制（1024）。K8s 推荐用 Mi/Gi。

15-选择-016（★★ 知识点：K15-3 imagePullPolicy） imagePullPolicy 的三种策略是？

  • AAlways / Never / IfNotPresent
  • BAlways / Sometimes / Never
  • CPull / Push / Cache
  • DAuto / Manual / Force

答案：A 解析：三种策略：Always（每次都拉）、Never（从不拉，用本地）、IfNotPresent（本地没有才拉）。

15-选择-017（★★ 知识点：K15-3 imagePullPolicy 默认） 当镜像标签是 :latest 时，imagePullPolicy 的默认值是？

  • ANever
  • BIfNotPresent
  • CAlways
  • D无默认值，必填

答案：C 解析：镜像标签是 :latest 或不写标签时，默认 Always；明确版本标签（如 :v1）时，默认 IfNotPresent。

15-选择-018（★★ 知识点：K15-3 imagePullPolicy 应用） 使用 Minikube Docker daemon 本地构建的 ctts-backend:v1 镜像，部署 Pod 时 imagePullPolicy 应设为？

  • AAlways
  • BNever
  • CIfNotPresent
  • D不设置

答案：B 解析：本地构建的镜像只存在于 Minikube 节点 Docker daemon，没推到仓库。设 Always 会去仓库拉导致 ImagePullBackOff。应设 Never（从不拉，只用本地）或 IfNotPresent（本地有就不拉）。Never 更明确。

15-选择-019（★★ 知识点：K15-3 command/args） K8s YAML 中的 command 字段覆盖镜像的哪个指令？

  • ACMD
  • BENTRYPOINT
  • CRUN
  • DEXPOSE

答案：B 解析：K8s 的 command 覆盖 Dockerfile 的 ENTRYPOINT；args 覆盖 Dockerfile 的 CMD。

15-选择-020（★ 知识点：K15-4 Pod 状态） Pod 的五种状态不包括下列哪一项？

  • APending
  • BRunning
  • CSucceeded
  • DStarting

答案：D 解析：五种状态是 Pending、Running、Succeeded、Failed、Unknown。Starting 不是 K8s Pod 状态。

15-选择-021（★ 知识点：K15-4 Pending 状态） Pod 状态为 Pending 表示？

  • APod 已被 K8s 接受，但还没全部就绪（正在调度、拉镜像、创建容器）
  • BPod 内所有容器都已正常运行
  • CPod 内所有容器都已正常退出
  • DPod 与节点失联

答案：A 解析：Pending 表示 Pod 已被接受但未就绪（调度中、拉镜像中、创建容器中）。B 是 Running；C 是 Succeeded；D 是 Unknown。

15-选择-022（★ 知识点：K15-4 Running 状态） Pod 状态为 Running 表示？

  • APod 内所有容器都已正常退出
  • BPod 已被调度到节点，所有容器已创建，至少一个正在运行
  • CPod 无法访问
  • DPod 正在被删除

答案：B 解析：Running 表示 Pod 已调度、容器已创建、至少一个在运行。A 是 Succeeded；C 是 Unknown；D 是 Terminating。

15-选择-023（★★ 知识点：K15-4 Succeeded 状态） Pod 状态为 Succeeded 表示？

  • APod 正在运行
  • BPod 内所有容器都正常退出（exit code 0），不会再重启
  • CPod 至少一个容器异常退出
  • DPod 调度成功

答案：B 解析：Succeeded 表示所有容器正常退出（exit 0），不再重启，主要用于 Job。C 是 Failed。

15-选择-024（★ 知识点：K15-4 restartPolicy） Pod 的 restartPolicy 默认值是？

  • AAlways
  • BOnFailure
  • CNever
  • DNever

答案：A 解析：Pod 的 restartPolicy 默认是 Always（容器退出后总是重启）。OnFailure 用于 Job，Never 用于一次性任务或调试。

15-选择-025（★★ 知识点：K15-4 CrashLoopBackOff） Pod 状态 CrashLoopBackOff 表示？

  • A镜像拉取失败
  • B容器反复崩溃重启，K8s 退避重启
  • CPod 资源不足
  • DPod 与节点失联

答案：B 解析：CrashLoopBackOff 表示容器反复崩溃被重启，K8s 按指数退避（10s/20s/40s...）尝试重启。A 是 ImagePullBackOff；C 是 Pending；D 是 Unknown。

15-选择-026（★ 知识点：K15-4 ImagePullBackOff） Pod 状态为 ImagePullBackOff，最可能的原因是？

  • A资源不足无法调度
  • B镜像名错误、仓库不可达或 imagePullPolicy 设错
  • C应用启动失败
  • D节点宕机

答案：B 解析：ImagePullBackOff 是拉取镜像失败，常见原因：镜像名错、仓库不可达、认证失败、imagePullPolicy 设错（本地镜像设了 Always）。A 是 Pending；C 是 CrashLoopBackOff；D 是 Unknown。

15-选择-027（★ 知识点：K15-5 kubectl 命令） 查看所有 namespace 的 Pod，命令是？

  • Akubectl get pods
  • Bkubectl get pods -A
  • Ckubectl get pods -n default
  • Dkubectl get pods --all

答案：B 解析：-A 是 --all-namespaces 简写，查看所有 namespace 的 Pod。A 只看 default；C 指定 default；D 不是合法选项。

15-选择-028（★ 知识点：K15-5 kubectl 命令） 查看 Pod 详情（含 Events），命令是？

  • Akubectl get pod
  • Bkubectl describe pod
  • Ckubectl logs
  • Dkubectl inspect pod

答案：B 解析：kubectl describe pod 显示 Pod 详细信息（含 Events、容器状态、环境变量等），是排查问题的必用命令。A 是列表概要；C 是日志；D 不是 kubectl 命令。

15-选择-029（★ 知识点：K15-5 kubectl logs） 查看 Pod 实时日志（类似 tail -f），命令是？

  • Akubectl logs -f
  • Bkubectl logs -r
  • Ckubectl logs --realtime
  • Dkubectl logs --follow

答案：A 解析：-f 参数表示 follow，实时输出新日志，类似 tail -f。D 也对（--follow 是 -f 的全写），但 A 更常用。本题选 A（最简写法）。

15-选择-030（★ 知识点：K15-5 kubectl exec） 进入 Pod 容器交互式 shell，命令是？

  • Akubectl exec bash
  • Bkubectl exec -it -- bash
  • Ckubectl ssh
  • Dkubectl attach

答案：B 解析：kubectl exec -it -- bash 进入交互式 shell。-it 表示交互式 + 分配 TTY；-- 分隔 kubectl 参数和容器命令。A 缺 -it 和 --；C、D 不是进入容器的命令。

15-选择-036（★★ 知识点：K15-4 Pod 状态） 下列属于 Pod 状态的有？（多选）

  • BRunning

15-选择-037（★★ 知识点：K15-4 restartPolicy） Pod 的 restartPolicy 可选值包括？（多选）

  • AAlways
  • BOnFailure
  • CNever
  • DUntilSucceeded E. OnSuccess

答案：A、B、C 解析：restartPolicy 三种：Always（总是重启，默认）、OnFailure（异常退出才重启）、Never（不重启）。D、E 不是合法值。

15-选择-038（★★ 知识点：K15-5 kubectl 命令） 下列 kubectl 命令用于操作 Pod 的有？（多选）

  • Ckubectl describe pod

15-选择-039（★★ 知识点：K15-4 故障状态） 下列属于 Pod 异常状态的有？（多选）

  • BCrashLoopBackOff
  • COOMKilled
  • DRunning E. ErrImagePull

答案：A、B、C、E 解析：A、B、C、E 都是异常状态。D 是正常状态。ImagePullBackOff/ErrImagePull 是拉镜像失败，CrashLoopBackOff 是反复崩溃，OOMKilled 是内存不足被杀。

15-选择-040（★★ 知识点：K15-5 创建方式） 关于 kubectl run 和 kubectl apply -f 的对比，下列说法正确的有？（多选）

答案：A、B、C、D 解析：A、B、C、D 都对。E 错，kubectl run 创建的 Pod 也可以用 kubectl delete 删除。

二、判断题（共 20 题，每题 1 分）

15-判断-001（★ 知识点：K15-1 Pod 概念） Pod 是 K8s 中能够创建和部署的最小单元，是 K8s 调度的最小单位。

答案：正确（✓） 解析：Pod 是 K8s 最小调度单元，K8s 不直接管容器而管 Pod。

15-判断-002（★ 知识点：K15-1 K8s 与容器） K8s 直接操作容器，不需要通过 Pod。

15-论述-002（★★ 知识点：K15-3 resources/imagePullPolicy，10 分） 请详细说明 resources.requests 和 limits 的区别，以及 imagePullPolicy 三种策略的含义和适用场景。

参考答案与评分标准（10 分，按要点给分）：

  1. requests 和 limits 的区别（5 分）：

    • requests（请求/保底）（2 分）：告诉调度器"这个 Pod 至少需要多少资源"，是调度依据。如 cpu: 500m 表示至少 0.5 核 CPU。kubelet 保证 Pod 至少有这么多资源。
    • limits（上限/限制）（2 分）：告诉容器运行时"这个容器最多能用多少资源"，是运行时限制。如 cpu: 1000m 表示最多用 1 核。超过 CPU 会被限流，超过内存会被 OOM 杀掉。
    • 生产环境建议（1 分）：requests 和 limits 都要设置。只设 limits 不设 requests，调度按 limits 算可能失败；只设 requests 不设 limits，Pod 可能用爆节点资源。

  2. imagePullPolicy 三种策略（5 分，每策略 1.5 分 + 默认规则 0.5 分）：

    • Always（1.5 分）：每次创建容器都从仓库拉取镜像。适用于用 :latest 标签的镜像（latest 标签默认 Always）。
    • Never（1.5 分）：从不拉取，只用本地镜像。适用于本地构建的镜像（如 Minikube Docker daemon 构建的镜像，未推到仓库）。
    • IfNotPresent（1.5 分）：本地没有才拉取。适用于明确版本标签的镜像（如 mysql:8.0），避免重复拉取已存在的镜像。
    • 默认规则（0.5 分）：镜像标签是 :latest 或不写标签时默认 Always；明确版本标签时默认 IfNotPresent。

评分要点：两部分独立给分；要点完整即可满分；意思对即可。

15-论述-003（★★ 知识点：K15-4 Pod 生命周期，10 分） 请描述 Pod 的五种状态及其含义，并画出（或描述）它们之间的流转关系。同时说明 restartPolicy 的三种取值及适用场景。

参考答案与评分标准（10 分，按要点给分）：

  1. Pod 的五种状态及含义（5 分，每状态 1 分）：

    • Pending：Pod 已被 K8s 接受，但还没全部就绪（正在调度、拉镜像、创建容器）
    • Running：Pod 已被调度到节点，所有容器已创建，至少一个正在运行
    • Succeeded：Pod 内所有容器都正常退出（exit code 0），不会再重启
    • Failed：Pod 内所有容器都已终止，至少一个异常退出（exit code 非 0）
    • Unknown：无法获取 Pod 状态，通常是跟节点失联（节点宕机或网络不通）

  2. 状态流转关系（2 分）：

    • 创建 → Pending → Running（容器创建成功）
    • Running → Succeeded（正常退出，exit 0）
    • Running → Failed（异常退出，exit 非 0）
    • Failed → Running（restartPolicy=Always/OnFailure 时重启）
    • 反复崩溃 → CrashLoopBackOff（退避重启）
    • 节点失联 → Unknown
    • 用户删除 → Terminating → 已删除

  3. restartPolicy 三种取值（3 分，每策略 1 分）：

    • Always：容器退出后总是重启（无论正常异常）。适用于长期运行的服务（默认值）。
    • OnFailure：容器异常退出（非 0）才重启。适用于一次性任务（Job）。
    • Never：容器退出后不重启。适用于一次性任务、调试。

评分要点：三部分独立给分；状态流转不必画图，描述清楚即可；restartPolicy 适用场景意思对即可。

参考答案与评分标准（8 分，按要点给分）：

  1. kubectl 操作 Pod 的七大命令（4 分，每命令 0.5 分 + 作用简述）：

    • kubectl run：命令式创建 Pod（快速测试用）
    • kubectl get pods：查看 Pod 列表（-A 看所有 namespace）

    • kubectl delete pod：删除 Pod
    • kubectl apply -f：从 YAML 创建/更新 Pod（声明式）

参考答案与评分标准（20 分）：

1. ImagePullBackOff 的原因分析（4 分）： YAML 中 imagePullPolicy: Always，但 ctts-backend:v1 是用 Minikube Docker daemon 本地构建的镜像，没有推送到镜像仓库。Always 策略会让 K8s 每次都去仓库拉取，但仓库里没有这个镜像，所以拉取失败，进入 ImagePullBackOff 状态。（4 分）

2. 修复方案（4 分）： 把 YAML 中的 imagePullPolicy: Always 改成 imagePullPolicy: Never（或 IfNotPresent）。（4 分）

  • Never：从不拉取，只用本地镜像（最明确）
  • IfNotPresent：本地没有才拉取（本地有就用本地）
  • 两者都给分，Always 不给分
