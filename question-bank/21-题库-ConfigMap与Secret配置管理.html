一、单项选择题（30题，每题2分，共60分）

21-单选-01 ★

Kubernetes 中用于存储非敏感配置数据的 API 对象是？ A. Secret B. ConfigMap C. PersistentVolume D. ServiceAccount

答案：B 解析： ConfigMap 用于存储非敏感的明文配置数据；Secret 用于存储敏感数据（密码、证书等）；PersistentVolume 是存储卷；ServiceAccount 是服务账号。

21-单选-02 ★

下列哪类信息应该存储在 Secret 中而不是 ConfigMap 中？ A. 日志级别 B. 数据库连接URL C. 数据库密码 D. 应用端口号

答案：C 解析： 数据库密码属于敏感信息，必须使用 Secret 存储；日志级别、连接URL、端口号属于非敏感配置，可用 ConfigMap。

21-单选-03 ★

ConfigMap 中存储的数据是哪种形式？ A. 加密存储 B. base64编码存储 C. 明文存储 D. 哈希存储

答案：C 解析： ConfigMap 的数据是明文存储的，kubectl get cm -o yaml 可直接看到原始值；只有 Secret 使用 base64 编码。这是 ConfigMap 不能存密码的根本原因。

21-单选-04 ★★

Secret 中存储的数据使用的编码方式是？ A. AES加密 B. MD5哈希 C. base64编码 D. RSA加密

答案：C 解析： Secret 使用 base64 编码，不是加密。base64 任何人都能解码，因此 Secret 本身并不"安全"，需要配合 etcd 静态加密、RBAC 等机制才能真正保护敏感数据。

21-单选-05 ★

创建 ConfigMap 时，使用 --from-literal 参数的作用是？ A. 从文件读取配置 B. 从字面量键值对创建配置 C. 从环境变量文件读取 D. 从目录批量读取

答案：B 解析： --from-literal=key=value 直接在命令行以字面量形式提供键值对；--from-file 从文件读取；--from-env-file 从 env 文件批量读取。

21-单选-06 ★★

下列命令能正确创建包含 LOG_LEVEL=INFO 的 ConfigMap 的是？ A. kubectl create configmap app-config --file=LOG_LEVEL=INFO B. kubectl create configmap app-config --from-literal=LOG_LEVEL=INFO C. kubectl create configmap app-config --set LOG_LEVEL=INFO D. kubectl create configmap app-config --env=LOG_LEVEL=INFO

答案：B 解析： 创建 ConfigMap 用字面量时必须用 --from-literal=key=value；A、C、D 都不是合法参数。

21-单选-07 ★★

使用 kubectl create secret generic db --from-literal=password=abc123 创建 Secret 后，存入 etcd 的 password 值是？ A. abc123 B. YWJjMTIz C. abc123 的 MD5 值 D. abc123 的 AES 加密值

答案：B 解析： 命令行用 --from-literal 时直接写明文，但 K8s 会自动进行 base64 编码后存入 etcd。echo -n 'abc123' | base64 的结果是 YWJjMTIz。

21-单选-08 ★★

Secret 的默认类型（type 字段）是？ A. Opaque B. dockerconfigjson C. kubernetes.io/tls D. kubernetes.io/service-account-token

答案：A 解析： Opaque 是 Secret 的默认通用类型，用于存储任意键值对；dockerconfigjson 用于私有仓库认证；tls 用于证书；service-account-token 用于 SA 令牌。

21-单选-09 ★

下列哪个 Secret 类型用于存储私有镜像仓库的认证信息？ A. Opaque B. kubernetes.io/dockerconfigjson C. kubernetes.io/tls D. kubernetes.io/basic-auth

答案：B 解析： kubernetes.io/dockerconfigjson 类型 Secret 专门存储 Docker 私有仓库认证信息，通过 kubectl create secret docker-registry 命令创建。

21-单选-10 ★★

在 Pod 中引用 Secret 的某个键作为环境变量，应使用哪个字段？ A. configMapKeyRef B. secretKeyRef C. valueFrom.secretRef D. envFrom.secret

答案：B 解析： 引用 Secret 单个键用 valueFrom.secretKeyRef；引用 ConfigMap 单个键用 valueFrom.configMapKeyRef；批量注入用 envFrom.secretRef 或 envFrom.configMapRef。

21-单选-11 ★★

下列命令能正确生成字符串 Ctts@2024 的 base64 编码的是？ A. echo 'Ctts@2024' | base64 B. echo -n 'Ctts@2024' | base64 C. base64 'Ctts@2024' D. echo 'Ctts@2024' | base64 -d

答案：B 解析： 必须用 echo -n 去掉换行符，否则编码结果会包含换行符导致密码错误；base64 -d 是解码而非编码；C 的语法不正确。

21-单选-12 ★★

ConfigMap 和 Secret 的单个资源大小限制是？ A. 1 KB B. 100 KB C. 1 MiB D. 10 MiB

答案：C 解析： K8s 规定单个 ConfigMap 或 Secret 的最大大小为 1 MiB，超过需拆分或使用其他方案（如外部配置中心）。

21-单选-13 ★★

关于 ConfigMap 和 Secret 的命名空间作用域，下列说法正确的是？ A. 两者都是集群级资源 B. 两者都是命名空间级资源，Pod 只能引用同命名空间的配置 C. ConfigMap 是集群级，Secret 是命名空间级 D. 两者都可以跨命名空间引用

答案：B 解析： ConfigMap 和 Secret 都是命名空间级（namespaced）资源，Pod 只能引用同一命名空间下的 ConfigMap/Secret，不能跨命名空间引用。

21-单选-14 ★★

将 ConfigMap 的所有键一次性注入为环境变量，应使用哪个字段？ A. env B. envFrom C. volumeMounts D. valueFrom

答案：B 解析： envFrom 用于批量注入 ConfigMap 或 Secret 的所有键为环境变量；env 是逐个引用；volumeMounts 是文件挂载；valueFrom 是单个值引用。

21-单选-15 ★★★

修改 ConfigMap 后，下列哪种挂载方式会让 Pod 内的配置自动更新？ A. env 方式 B. envFrom 方式 C. Volume 文件挂载方式 D. subPath 单文件挂载方式

答案：C 解析： 只有 Volume 文件挂载方式支持自动热更新（kubelet 周期同步，约60-120秒）；env/envFrom 在 Pod 启动时注入后不再变化；subPath 挂载的单文件不支持热更新。

21-单选-16 ★★★

关于 ConfigMap 热更新的同步周期，下列描述正确的是？ A. 立即生效 B. kubelet 周期同步，默认约 60-120 秒 C. 需要 Pod 重启才生效 D. 需要 Node 重启才生效

答案：B 解析： ConfigMap Volume 挂载的热更新由 kubelet 周期同步机制实现，默认约 60-120 秒生效，不是立即生效，也不需要重启 Pod 或 Node。

21-单选-17 ★★

下列关于 subPath 的描述，正确的是？ A. subPath 用于挂载多个 ConfigMap B. subPath 挂载的单文件支持热更新 C. subPath 用于挂载单个文件且不覆盖原目录内容 D. subPath 只能用于 Secret 挂载

答案：C 解析： subPath 用于挂载单个文件到指定路径，不影响目录其他文件（避免覆盖）；但使用 subPath 后该文件不支持热更新，这是重要陷阱。

21-单选-18 ★★

使用 envFrom 批量注入 ConfigMap 时，键名包含下列哪个字符会被跳过或转换？ A. 字母 B. 数字 C. 下划线 D. 点号（.）

答案：D 解析： 环境变量名规范不允许点号、横线等特殊字符，envFrom 会跳过或转换含这些字符的键名；含字母、数字、下划线的键名正常注入。

21-单选-19 ★★★

关于 Secret 的热更新，下列做法最合理的是？ A. 修改 Secret 后等待应用自动感知 B. 修改 Secret 后执行 kubectl rollout restart 让 Pod 按新凭证重建 C. Secret 不支持任何形式的热更新 D. 修改 Secret 后必须删除 Pod 重建

答案：B 解析： Secret 挂载的文件会像 ConfigMap 一样自动更新，但凭证（如数据库密码）通常在应用启动时建立连接，热更新文件没有意义。推荐做法是修改 Secret 后执行 kubectl rollout restart，让 Pod 按新凭证滚动重建。

21-单选-20 ★★

下列命令中，能查看 Secret 中某个键的明文值的是？ A. kubectl get secret <name> B. kubectl describe secret <name> C. kubectl get secret <name> -o jsonpath='{.data.key}' | base64 -d D. kubectl logs secret <name>

答案：C 解析： kubectl get secret 默认不显示 data；describe 只显示键名不显示值；-o jsonpath 提取 base64 值后用 base64 -d 解码可看到明文；logs 是查看 Pod 日志，不是 Secret。

21-单选-21 ★★

在 YAML 中定义 Secret 时，data 字段和 stringData 字段的区别是？ A. data 是明文，stringData 是加密 B. data 需要 base64 编码，stringData 写明文由 K8s 自动编码 C. data 用于 ConfigMap，stringData 用于 Secret D. 两者完全等价

答案：B 解析： data 字段的值必须是 base64 编码后的字符串；stringData 字段写明文字符串，K8s 自动编码后存入 data。stringData 更直观不易错，推荐使用。

21-单选-22 ★★

Deployment 中引用私有镜像仓库的 Secret，应使用哪个字段？ A. spec.template.spec.imagePullSecrets B. spec.template.spec.containers[].imageSecrets C. spec.imagePullSecrets D. spec.template.spec.volumes[].secret

答案：A 解析： 引用 docker-registry 类型 Secret 用于拉取私有镜像，字段是 spec.template.spec.imagePullSecrets，是一个列表，每项包含 name。

21-单选-23 ★★★

下列关于 base64 编码的说法，正确的是？ A. base64 是一种加密算法，不可逆 B. base64 编码后的数据任何人都能解码回明文 C. base64 比 AES 更安全 D. base64 编码会压缩数据

答案：B 解析： base64 是编码不是加密，是可逆的，任何人都能用 base64 -d 解码回明文；它不提供任何安全性，也不压缩数据（反而增大约33%）。

21-单选-24 ★★

下列哪个不是 ConfigMap 支持的创建数据来源？ A. --from-literal B. --from-file C. --from-env-file D. --from-encrypt

答案：D 解析： ConfigMap 支持 --from-literal（字面量）、--from-file（文件）、--from-env-file（env文件）；--from-encrypt 不是合法参数。

21-单选-25 ★★★

Pod 引用了不存在的 ConfigMap，且未设置 optional: true，会发生什么？ A. Pod 正常启动，配置为空 B. Pod 启动失败，状态为 CreateContainerConfigError C. Pod 启动失败，状态为 CrashLoopBackOff D. Pod 正常启动，使用默认值

答案：B 解析： 引用不存在的 ConfigMap 且未设置 optional: true 时，Pod 无法启动，状态为 CreateContainerConfigError；设置 optional: true 后即使 ConfigMap 不存在，Pod 也能启动（对应环境变量为空）。

21-单选-26 ★★

关于 ConfigMap 和 Secret 的关系，下列说法错误的是？ A. 两者都是命名空间级资源 B. 两者都支持 env 和 Volume 两种挂载方式 C. Secret 的数据比 ConfigMap 更安全因为使用了加密 D. 两者单个资源大小限制都是 1 MiB

答案：C 解析： Secret 使用的是 base64 编码而非加密，因此并不比 ConfigMap 更"安全"；要真正安全需要启用 etcd 静态加密、RBAC 或外部密钥管理。A、B、D 描述正确。

21-单选-27 ★★

kubectl create configmap app-config --from-file=application.yml 创建的 ConfigMap 中，键名是？ A. application B. application.yml C. app-config D. config

答案：B 解析： 使用 --from-file=<path> 时，默认以文件名（含扩展名）作为键名，文件内容作为值；若想自定义键名可用 --from-file=<key>=<path>。

21-单选-28 ★★★

下列哪种情况会导致 ConfigMap Volume 挂载的文件不热更新？ A. 使用 items 选择性挂载 B. 使用 subPath 挂载单个文件 C. 设置 readOnly: true D. ConfigMap 在另一个命名空间

答案：B 解析： 使用 subPath 挂载的单文件是符号链接到具体版本，不会随 ConfigMap 更新而变化，不支持热更新；items 选择性挂载仍支持热更新；readOnly: true 不影响热更新；跨命名空间无法引用。

21-单选-29 ★★★

十二要素应用（Twelve-Factor App）关于配置的原则是？ A. 配置存在代码中，方便版本管理 B. 配置存在环境中，不在代码里 C. 配置打进镜像，保证一致性 D. 配置写死在 YAML，避免外部依赖

答案：B 解析： 十二要素应用第3条"配置"明确指出：配置应存在环境中（环境变量），不在代码里。判断标准是代码库在不同环境间能否直接部署而不修改。K8s 的 ConfigMap + Secret 正是这一原则的实现。

21-单选-30 ★★★

关于 Secret 的安全加固，下列做法中效果最弱的是？ A. 启用 etcd 静态加密（EncryptionConfiguration） B. 严格 RBAC 限制 kubectl get secret 权限 C. 使用 base64 编码后存入 Secret D. 对接 HashiCorp Vault 等外部密钥管理

答案：C 解析： base64 编码是 Secret 的默认行为，不提供任何安全性（任何人可解码）；etcd 静态加密、RBAC、外部密钥管理都是有效的加固手段。C 是"看起来安全"的假象。

二、多项选择题（10题，每题2分，共20分）

21-多选-01 ★★

下列信息中，应该存储在 Secret 中的有？ A. 数据库密码 B. TLS 证书私钥 C. 第三方 API Token D. 日志级别 E. 镜像拉取仓库地址

答案：ABC 解析： 密码、证书私钥、API Token 都属于敏感信息，应用 Secret；日志级别是非敏感配置用 ConfigMap；镜像仓库地址是非敏感信息用 ConfigMap 或直接写镜像名。

21-多选-02 ★★

创建 ConfigMap 的合法方式有？ A. kubectl create configmap --from-literal B. kubectl create configmap --from-file C. kubectl create configmap --from-env-file D. kubectl apply -f configmap.yaml E. kubectl create configmap --from-encrypt

答案：ABCD 解析： A、B、C 是命令行的三种数据来源；D 是 YAML 方式；E 不是合法参数。

21-多选-03 ★★

Secret 的常见类型包括？ A. Opaque B. kubernetes.io/dockerconfigjson C. kubernetes.io/tls D. kubernetes.io/service-account-token E. kubernetes.io/configmap

答案：ABCD 解析： Secret 的类型有 Opaque（通用）、dockerconfigjson（私有仓库）、tls（证书）、service-account-token（SA令牌）等；configmap 不是 Secret 类型。

21-多选-04 ★★

将 ConfigMap 挂载到 Pod 的方式有？ A. env 逐个引用 B. envFrom 批量注入 C. Volume 文件挂载 D. subPath 单文件挂载 E. imagePullSecrets

答案：ABCD 解析： A、B、C、D 都是 ConfigMap 挂载方式；E 是用于引用 docker-registry Secret 拉取私有镜像，不是挂载配置。

21-多选-05 ★★★

关于 ConfigMap 热更新，下列说法正确的有？ A. Volume 挂载方式支持自动热更新 B. env 方式不支持热更新 C. envFrom 方式支持热更新 D. subPath 挂载方式不支持热更新 E. 热更新由 kubelet 周期同步实现

答案：ABDE 解析： A、B、D、E 正确；C 错误，envFrom 本质仍是环境变量方式，不支持热更新。只有 Volume 挂载（且不用 subPath）支持自动热更新。

21-多选-06 ★★

关于 base64 编码，下列说法正确的有？ A. base64 是编码不是加密 B. base64 编码后的数据任何人都能解码 C. echo -n 必须加 -n 去掉换行符 D. base64 让 Secret 真正安全 E. base64 会压缩数据

答案：ABC 解析： A、B、C 正确；D 错误，base64 不提供安全性；E 错误，base64 不压缩反而增大约33%。

21-多选-07 ★★★

下列哪些做法可以让 Secret 真正安全？ A. 启用 etcd 静态加密 B. 严格 RBAC 限制访问权限 C. 对接 HashiCorp Vault 外部密钥管理 D. 使用 Sealed Secrets 加密后提交 Git E. 把 Secret 的 base64 值写在代码注释里

答案：ABCD 解析： A、B、C、D 都是有效的安全加固手段；E 是严重错误，base64 等同明文，写在代码注释里等于泄露。

21-多选-08 ★★

21-判断-10 ★

单个 ConfigMap 的最大大小是 1 MiB。 答案：正确 解析： K8s 规定单个 ConfigMap 或 Secret 最大 1 MiB，超过需要拆分或使用外部配置中心。

21-判断-11 ★★

Secret 挂载为 Volume 时，Pod 内文件内容是 base64 编码值。 答案：错误 解析： Secret 挂载为 Volume 时，K8s 会自动将 base64 解码为明文写入文件，应用直接读取明文即可。

21-判断-12 ★★

ConfigMap 和 Secret 可以被同一命名空间内的多个 Pod 同时引用。 答案：正确 解析： ConfigMap 和 Secret 是共享资源，一个配置可以被多个 Pod 引用，实现配置复用。

21-论述-01 ★★（8分）

请论述 Kubernetes 中 ConfigMap 和 Secret 的区别，以及各自适用的场景。

评分标准（满分8分）：

  • 核心区别（3分）：ConfigMap 明文存储非敏感配置；Secret base64 编码存储敏感数据。
  • 数据形式（2分）：ConfigMap data 明文；Secret data base64 编码（非加密）、stringData 明文输入自动编码。
  • 适用场景（2分）：ConfigMap 用于 URL、端口、日志级别等；Secret 用于密码、Token、证书私钥。
  • 安全认知（1分）：base64 不是加密，Secret 需配合 etcd 加密、RBAC 才真正安全。

参考答案：

  1. 核心区别：ConfigMap 用于存储非敏感的明文配置数据，Secret 用于存储敏感数据（密码、Token、证书等）并以 base64 编码形式存储。
  2. 数据形式：ConfigMap 的 data 字段值是明文字符串，kubectl get cm -o yaml 直接可见；Secret 的 data 字段值是 base64 编码字符串，需解码才能看到明文。Secret 还支持 stringData 字段，可直接写明文由 K8s 自动编码。
  3. 适用场景：
    • ConfigMap：数据库 URL、用户名、端口号、日志级别、应用配置文件等非敏感信息。
    • Secret：数据库密码、JWT 密钥、API Token、TLS 证书私钥、私有仓库认证等敏感信息。
  4. 安全认知：base64 是编码不是加密，Secret 本身并不"安全"。要真正保护敏感数据需启用 etcd 静态加密、严格 RBAC、或对接 Vault 等外部密钥管理系统。

请完整说明在 Kubernetes 中将应用配置外置化的流程，包括 ConfigMap 创建、Secret 创建、Pod 挂载、验证热更新。

评分标准（满分10分）：

  • 配置分析（2分）：区分敏感与非敏感配置，确定 ConfigMap 和 Secret 的键值划分。
  • ConfigMap 创建（2分）：命令行或 YAML 方式创建，含 data/stringData 字段。
  • Secret 创建（2分）：命令行或 YAML 方式创建，base64 编码，指定 type。
  • Pod 挂载（2分）：env/envFrom/Volume 三种方式任选其一，YAML 字段正确。
  • 验证热更新（2分）：Volume 挂载方式修改 ConfigMap 后 Pod 内文件自动更新；env 方式不热更新需重启。

参考答案：

  1. 配置分析：以 SpringBoot 应用为例，将 application.yml 中的配置分为两类：非敏感（数据库 URL、用户名、驱动、日志级别）走 ConfigMap；敏感（数据库密码、JWT 密钥）走 Secret。

    kubectl create configmap app-config \

  --from-literal=DB_USER="root" \
  --from-literal=LOG_LEVEL="INFO"
    或 YAML 方式： 
    apiVersion: v1

  name: app-config

  DB_URL: "jdbc:mysql://mysql-svc:3306/app"

  LOG_LEVEL: "INFO"

    kubectl create secret generic app-secret \

    apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  DB_PASSWORD: "MyPwd@2024"
  JWT_SECRET: "MyJwtSecret"
  4. Pod 挂载（以 envFrom 为例）： 
    spec:
  template:
    spec:
      containers:
      - name: app
        image: app:v1
        envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: app-secret
  5. 验证热更新：
    • env/envFrom 方式：修改 ConfigMap 后 kubectl exec 查看环境变量不变，需 kubectl rollout restart 重启 Pod 才生效。

21-论述-03 ★★★（8分）

请论述 ConfigMap 配置热更新的机制，包括哪些挂载方式支持热更新、哪些不支持、应用如何感知配置变化。

评分标准（满分8分）：

  • 热更新机制（3分）：Volume 挂载由 kubelet 周期同步（约60-120秒）更新 Pod 内文件；env/envFrom 在 Pod 启动时注入后不变化。
  • 支持与不支持（2分）：Volume 挂载（不用 subPath）支持；env、envFrom、subPath 单文件挂载不支持。
  • 应用感知（2分）：K8s 层文件自动更新，但应用层需自行感知（inotify、定期重读、Spring Cloud refresh、配置中心客户端）。
  • Secret 热更新（1分）：Secret 不建议依赖热更新，凭证轮换应配合 kubectl rollout restart。

参考答案：

  1. 热更新机制：当 ConfigMap 以 Volume 方式挂载到 Pod 时，kubelet 在节点上维护一份 ConfigMap 副本，并周期性同步（默认约60-120秒）ConfigMap 的最新版本。Pod 内的挂载点通过 bind mount 自动反映新内容，无需重启 Pod。
  2. 支持与不支持：
    • 支持热更新：Volume 文件挂载（configMap 卷，不用 subPath）。
    • 不支持热更新：env 逐个引用、envFrom 批量注入（环境变量在 Pod 启动时固化）、subPath 单文件挂载（符号链接到具体版本）。
  3. 应用感知：K8s 层保证了文件内容自动更新，但应用进程是否重新加载配置取决于应用自身：
    • SpringBoot：默认不感知，需集成 spring-cloud-context（refresh）或 spring-cloud-kubernetes。
    • Nginx：不感知，需 nginx -s reload 或外部 reloader（如 stakater/reloader）。
    • Java 应用：可监听文件变化（WatchService）或定期重新读取。
    • 配置中心客户端（Apollo/Nacos）：长轮询感知。
  4. Secret 热更新：Secret 挂载的文件也会自动更新，但凭证（如数据库密码）通常在应用启动时建立连接，热更新文件没有意义。推荐做法是修改 Secret 后执行 kubectl rollout restart 让 Pod 按新凭证滚动重建。

21-论述-04 ★★（6分）

简述 Secret 的安全局限性以及如何让 Secret 真正安全。

评分标准（满分6分）：

  • 安全局限性（3分）：base64 是编码不是加密；kubectl get secret -o yaml 可见编码值；任何有 RBAC 权限的人可解码；默认 etcd 未加密存储。
  • 加固方案（3分）：① 启用 etcd 静态加密（EncryptionConfiguration）；② 严格 RBAC 限制 get/list/watch secret；③ 对接外部密钥管理（Vault、KMS、External Secrets）；④ 使用 Sealed Secrets 加密后提交 Git。

参考答案：

  1. Secret 的安全局限性：
    • base64 是编码不是加密，任何人都能用 base64 -d 解码回明文。
    • kubectl get secret -o yaml 能看到 base64 值，等同于明文可见。
    • 任何拥有 get/list/watch secret RBAC 权限的用户都能读取所有 Secret。
    • 默认情况下 etcd 中存储的 Secret 是 base64 编码而非加密，etcd 数据泄露即等于密码泄露。
    • 把 Secret 的 YAML 提交到 Git 等同于明文泄露。
  2. 让 Secret 真正安全的方案：
    • 启用 etcd 静态加密：配置 EncryptionConfiguration，让 Secret 在写入 etcd 前用 AES 等算法加密，即使 etcd 数据泄露也无法直接读取。
    • 严格 RBAC：限制 get/list/watch secret 权限，按命名空间、按角色分配最小权限。
    • 对接外部密钥管理：使用 HashiCorp Vault、阿里云 KMS、AWS Secrets Manager 等外部系统，通过 External Secrets Operator 同步为 K8s Secret，密钥不落 etcd。
    • 使用 Sealed Secrets：用非对称加密把 Secret 加密成 SealedSecret 资源，密文可安全提交 Git，集群内控制器自动解密还原，适合 GitOps。
    • 审计日志：开启 K8s 审计，记录所有 Secret 访问行为，便于追溯。

21-编程-02 ★★★（20分）

请设计一个 ConfigMap 热更新验证实验，要求： (1) 编写一个 ConfigMap YAML，包含 LOG_LEVEL=INFO 键 (2) 编写一个 Pod YAML，以 Volume 方式挂载该 ConfigMap 到 /etc/config，Pod 内循环打印文件内容 (3) 给出完整的验证步骤（创建→查看→修改ConfigMap→观察变化→对比env方式不热更新） (4) 编写一个对照 Pod YAML，用 env 方式挂载同样的 ConfigMap，用于对比验证

评分标准（满分20分）：

  • ConfigMap YAML（4分）：字段完整，键值正确。
  • Volume Pod YAML（6分）：
    • Volume 定义（configMap 引用）（2分）
    • volumeMounts（mountPath: /etc/config）（2分）
    • command 循环打印文件（2分）
  • 验证步骤（6分）：
    • 创建并查看初始内容（1分）
    • 修改 ConfigMap（kubectl edit/patch）（1分）
    • 等待并观察 Volume Pod 日志变化（2分）
    • 对比 env Pod 日志不变（1分）
    • 结论说明（1分）
  • env 对照 Pod YAML（4分）：env 字段正确引用 configMapKeyRef。

参考答案：

(1) ConfigMap YAML（cm-log.yaml）：

apiVersion: v1
kind: ConfigMap
metadata:
  name: log-config
data:
  LOG_LEVEL: "INFO"

(2) Volume Pod YAML（pod-volume.yaml）：

apiVersion: v1
kind: Pod
metadata:
  name: volume-pod
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo \"[$(date)] LOG_LEVEL=$(cat /etc/config/LOG_LEVEL)\"; sleep 10; done"]
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config-volume
    configMap:
      name: log-config

(3) 验证步骤：

# 步骤1：创建ConfigMap和Volume Pod
kubectl apply -f cm-log.yaml
kubectl apply -f pod-volume.yaml

# 步骤2：查看初始日志（应为INFO）
kubectl logs volume-pod
# 输出: [xxx] LOG_LEVEL=INFO

# 步骤3：修改ConfigMap
kubectl patch configmap log-config -p '{"data":{"LOG_LEVEL":"DEBUG"}}'
# 或 kubectl edit configmap log-config

# 步骤4：等待60-120秒后再次查看日志（应变为DEBUG）
kubectl logs volume-pod
# 输出: [xxx] LOG_LEVEL=INFO  (旧)
#       [xxx] LOG_LEVEL=DEBUG (新，热更新生效)

# 步骤5：直接进入Pod查看文件
kubectl exec -it volume-pod -- cat /etc/config/LOG_LEVEL
# 输出: DEBUG

# 步骤6：创建env对照Pod，观察不热更新
kubectl apply -f pod-env.yaml
kubectl logs env-pod
# 输出: LOG_LEVEL=DEBUG (初始值)

kubectl patch configmap log-config -p '{"data":{"LOG_LEVEL":"ERROR"}}'
# 等待2分钟
kubectl logs env-pod
# 输出仍是: LOG_LEVEL=DEBUG (env方式不热更新!)

# 步骤7：重启env Pod才生效
kubectl delete pod env-pod
kubectl apply -f pod-env.yaml
kubectl logs env-pod
# 输出: LOG_LEVEL=ERROR (重启后注入新值)

结论：Volume 挂载方式支持热更新（kubelet 周期同步，约60-120秒）；env 方式不支持热更新（环境变量在 Pod 启动时固化），需重启 Pod 才能生效。

(4) env 对照 Pod YAML（pod-env.yaml）：

apiVersion: v1
kind: Pod
metadata:
  name: env-pod
spec:
  containers:
  - name: busybox
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo \"LOG_LEVEL=$LOG_LEVEL\"; sleep 10; done"]
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef:
          name: log-config
          key: LOG_LEVEL
