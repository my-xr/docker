一、选择题（共 40 题，每题 2 分）

1.1 单项选择题（30 题）

13-选择-001（★ 知识点：K13-1 K8s 定义） Kubernetes（K8s）是一个开源的 ________ 平台。

  • A虚拟机管理
  • B容器编排
  • C数据库
  • D操作系统

答案：B 解析：K8s 是开源的容器编排平台，用于自动化部署、扩展和管理容器化应用。A 错，K8s 不管理虚拟机；C 错，K8s 不是数据库；D 错，K8s 不是操作系统（虽常被称为"云原生操作系统"，但这是比喻）。

13-选择-002（★ 知识点：K13-1 K8s 名称由来） Kubernetes 简称为 K8s，原因是？

  • A它有 8 个核心组件
  • BK 和 s 之间有 8 个字母
  • C它是第 8 代容器编排工具
  • D它支持最多 8 个节点

答案：B 解析：K8s 是 Kubernetes 的缩写，因为首字母 K 与末字母 s 之间有 8 个字母（ubernete），故称 K8s。与组件数、版本、节点数无关。

13-选择-003（★ 知识点：K13-1 容器编排概念） "容器编排"主要解决的问题是？

  • A如何把应用打包成容器镜像
  • B如何在集群中自动化调度、扩缩容、故障恢复容器
  • C如何编写 Dockerfile
  • D如何在单机上运行多个容器

答案：B 解析：容器编排解决集群中容器的自动化调度、扩缩容、故障恢复、滚动更新等问题。A 是 Docker 化（Dockerfile）；C 是镜像构建；D 是单机编排（Compose），不属于"编排"的核心范畴。

13-选择-004（★ 知识点：K13-1 K8s 起源） Kubernetes 最初是基于哪家公司的内部系统经验开源的？

  • AMicrosoft 的 Azure
  • BAmazon 的 AWS
  • CGoogle 的 Borg
  • D阿里巴巴的飞天

答案：C 解析：K8s 最初由 Google 基于内部 Borg 系统的设计经验开源，2014 年捐给 CNCF。Borg 是 Google 内部的集群管理系统。

13-选择-005（★ 知识点：K13-1 Compose 局限） 下列哪一项不属于 Docker Compose 的局限性？

  • A只能在单台机器上编排容器
  • B容器故障不能自动重启
  • C不能根据负载自动扩缩容
  • D不支持 YAML 描述服务

答案：D 解析：Compose 完全支持用 YAML（docker-compose.yml）描述服务，这是它的核心特性。A、B、C 都是 Compose 的真实局限（单机、无自愈、无弹性）。

13-选择-006（★ 知识点：K13-1 K8s 核心） K8s 的核心价值不包括下列哪一项？

  • A多机调度
  • B自动自愈
  • C弹性扩缩容
  • D取代 Docker 镜像构建

答案：D 解析：K8s 的核心价值是多机调度、自愈、弹性扩缩容、滚动更新。K8s 不取代 Docker 镜像构建，镜像构建仍然用 Docker（或其他工具）。A、B、C 都是 K8s 的真实价值。

13-选择-007（★ 知识点：K13-2 K8s vs Compose） 关于 Docker Compose 与 Kubernetes 的对比，下列说法正确的是？

  • ACompose 支持集群级编排，K8s 只支持单机
  • BCompose 是单机编排，K8s 是集群编排
  • C二者功能完全相同，只是厂商不同
  • DK8s 是 Compose 的升级版，用法一样

答案：B 解析：Compose 是单机多容器编排，K8s 是集群级容器编排。A 错，反了；C 错，二者模型不同；D 错，K8s 不是 Compose 升级版，模型不同（声明式 vs 命令式）。

13-选择-008（★ 知识点：K13-2 适用场景） 下列场景中，最适合使用 Kubernetes 而非 Docker Compose 的是？

  • A本地开发联调前后端
  • BCI 流水线测试环境
  • C企业级电商大促，需要多副本与故障自动迁移
  • D个人博客部署

答案：C 解析：企业级电商大促需要多副本、自愈、弹性扩缩容、高可用，是 K8s 的典型场景。A、B、D 都是单机够用，Compose 足够。

13-选择-009（★ 知识点：K13-2 K8s 优势） K8s 实现滚动更新与回滚的核心资源是？

  • APod
  • BDeployment
  • CConfigMap
  • DNamespace

答案：B 解析：Deployment 资源原生支持滚动更新（rolling update）与回滚（rollout undo），实现零停机升级。Pod 是最小调度单元，ConfigMap 是配置，Namespace 是隔离。

13-选择-010（★ 知识点：K13-3 K8s 架构） Kubernetes 采用的架构模式是？

  • A单体架构
  • BP2P 对等架构
  • CMaster-Node（控制平面-工作节点）架构
  • D主从复制架构

答案：C 解析：K8s 采用 Master-Node 架构（控制平面 Control Plane 与工作节点 Worker Node），Master 负责管理决策，Node 负责执行业务。其他选项都不对。

13-选择-011（★ 知识点：K13-3 Master 职责） 关于 K8s Master（控制平面），下列说法正确的是？

  • AMaster 负责运行业务容器
  • BMaster 是集群的"大脑"，负责管理与决策
  • CMaster 不需要任何组件
  • DMaster 必须部署在多台机器上

答案：B 解析：Master 是集群"大脑"，负责管理集群状态、调度决策、故障检测。A 错，业务容器跑在 Node 上；C 错，Master 有四大核心组件；D 错，学习环境可单 Master，生产才需多 Master 高可用。

13-选择-012（★ 知识点：K13-3 Node 职责） 关于 K8s Node（工作节点），下列说法正确的是？

  • ANode 负责集群管理决策
  • BNode 不需要安装任何 K8s 组件
  • CNode 负责实际运行业务 Pod
  • D一个集群只能有一个 Node

答案：C 解析：Node 是"手脚"，负责实际运行业务 Pod。A 错，那是 Master 的职责；B 错，Node 需装 kubelet/kube-proxy/container-runtime；D 错，一个集群通常有多个 Node。

13-选择-013（★ 知识点：K13-4 API Server） K8s 集群中，所有组件与用户访问的"统一入口"是？

  • Aetcd
  • Bkube-apiserver
  • Cscheduler
  • Dkubelet

答案：B 解析：API Server（kube-apiserver）是集群唯一入口，所有组件与用户都通过它通信，它是唯一能直接读写 etcd 的组件。其他组件都通过 API Server 间接操作 etcd。

13-选择-014（★ 知识点：K13-4 etcd） K8s 集群中，保存集群所有状态数据的组件是？

  • Aetcd
  • Bscheduler
  • Ccontroller-manager
  • Dkube-proxy

答案：A 解析：etcd 是分布式键值（KV）存储，保存集群所有状态数据（Pod/Service/Deployment 等），是 K8s 的"真相之源"。其他选项都不是存储组件。

13-选择-015（★ 知识点：K13-4 etcd 类型） etcd 是哪种类型的存储系统？

  • A关系型数据库
  • B文档数据库
  • C分布式键值（KV）存储
  • D文件系统

答案：C 解析：etcd 是分布式键值（KV）存储数据库，使用 Raft 协议保证一致性，不是关系型数据库（如 MySQL）也不是文档数据库（如 MongoDB）。

13-选择-016（★ 知识点：K13-4 scheduler） K8s 中，负责决定新 Pod 运行在哪个 Node 上的组件是？

  • AAPI Server
  • Betcd
  • Ckube-scheduler
  • Dkubelet

答案：C 解析：kube-scheduler（调度器）监听未调度的 Pod，根据资源、亲和性等规则选择最合适的 Node。注意：scheduler 只"决定"跑哪，真正启动容器的是目标 Node 上的 kubelet。

13-选择-017（★ 知识点：K13-4 controller-manager） K8s 中，运行多种控制器、持续让"实际状态"趋近"期望状态"的组件是？

  • AAPI Server
  • Bscheduler
  • Ckube-controller-manager
  • Dkube-proxy

答案：C 解析：controller-manager 是控制器的集合（Deployment/ReplicaSet/Node/Endpoint 等），每个控制器持续做"调和循环"（reconcile loop），让实际状态趋近期望状态。

13-选择-018（★ 知识点：K13-5 kubelet） 关于 kubelet，下列说法正确的是？

  • Akubelet 运行在 Master 上，负责调度
  • Bkubelet 是 Node 上的节点代理，管理 Pod 生命周期
  • Ckubelet 直接管理 etcd
  • Dkubelet 不与 API Server 通信

答案：B 解析：kubelet 跑在每个 Node 上的节点代理，管理本节点 Pod 生命周期，与 API Server 通信。A 错，kubelet 在 Node 上；C 错，只有 API Server 直接访问 etcd；D 错，kubelet 通过 API Server 上报状态。

13-选择-019（★ 知识点：K13-5 kube-proxy） kube-proxy 的主要职责是？

  • A调度 Pod 到 Node
  • B维护 Service 的网络规则，实现服务发现与负载均衡
  • C拉取镜像并启动容器
  • D保存集群状态

答案：B 解析：kube-proxy 维护 Service 的网络规则（iptables/ipvs），让访问 Service VIP 的流量路由到后端 Pod，实现服务发现与负载均衡。A 是 scheduler；C 是 container-runtime；D 是 etcd。

13-选择-020（★ 知识点：K13-5 容器运行时） K8s 通过哪个接口标准支持多种容器运行时（如 containerd、CRI-O）？

  • ACNI
  • BCRI
  • CCSI
  • DOCI

答案：B 解析：CRI（Container Runtime Interface）是容器运行时接口，让 K8s 支持 containerd、CRI-O 等多种运行时。CNI 是网络接口，CSI 是存储接口，OCI 是镜像/运行时标准（不是 K8s 接口）。

13-选择-021（★ 知识点：K13-5 K8s 1.24 变化） K8s 1.24 版本起移除了 ________，不再直接支持 Docker Engine 作为容器运行时。

  • ACRI
  • Bdockershim
  • Ccontainerd
  • DCNI

答案：B 解析：K8s 1.24 移除了 dockershim（用于适配 Docker Engine 的桥接层），不再原生支持 Docker Engine。但 Docker 构建的镜像（OCI 格式）仍能在 containerd 上运行。

13-选择-022（★ 知识点：K13-6 Pod 概念） K8s 中最小的调度单元是？

  • A容器
  • BPod
  • CDeployment
  • DNode

答案：B 解析：Pod 是 K8s 最小调度单元，包含一个或多个紧密协作的容器。K8s 不直接管容器，管的是 Pod。容器在 Pod 内。

13-选择-023（★ 知识点：K13-6 Deployment 概念） 关于 Deployment，下列说法正确的是？

  • ADeployment 直接运行容器
  • BDeployment 管理 Pod 副本，支持滚动更新与回滚
  • CDeployment 是 K8s 的存储资源
  • DDeployment 必须配合 Ingress 使用

答案：B 解析：Deployment 管理 Pod 副本（通过 ReplicaSet），支持滚动更新与回滚。A 错，Deployment 管的是 Pod，不直接运行容器；C 错，Deployment 是工作负载资源；D 错，Deployment 不必配 Ingress。

13-选择-024（★ 知识点：K13-6 Service 概念） K8s 中，为一组 Pod 提供稳定访问入口（IP+DNS）和负载均衡的资源是？

  • APod
  • BDeployment
  • CService
  • DConfigMap

答案：C 解析：Service 为一组 Pod 提供稳定的访问入口（ClusterIP/NodePort/LoadBalancer）和负载均衡。Pod 是最小调度单元，Deployment 管副本，ConfigMap 存配置。

13-选择-025（★ 知识点：K13-6 Ingress 概念） K8s 中，提供七层（HTTP/HTTPS）路由的资源是？

  • AService
  • BIngress
  • Ckube-proxy
  • DDeployment

答案：B 解析：Ingress 提供七层路由（基于域名/路径），把外部请求路由到 Service。Service 只做四层（TCP/UDP），kube-proxy 是 Node 上的网络代理组件，不是资源。

13-选择-026（★ 知识点：K13-6 ConfigMap/Secret） 关于 ConfigMap 和 Secret，下列说法正确的是？

  • AConfigMap 存敏感信息，Secret 存非敏感配置
  • BConfigMap 存非敏感配置，Secret 存敏感信息
  • C二者完全相同
  • DConfigMap 是加密的

答案：B 解析：ConfigMap 存储非敏感配置（key-value），Secret 存储敏感信息（密码/密钥，base64 编码）。注意：Secret 是 base64 编码（不是加密），生产需配合 RBAC 限制访问。

13-选择-027（★ 知识点：K13-6 PV/PVC） K8s 中，表示"用户对持久化存储的申请"的资源是？

  • APV
  • BPVC
  • CStorageClass
  • DPod

答案：B 解析：PVC（PersistentVolumeClaim）是用户对存储的申请（如"我要 10G 硬盘"）。PV（PersistentVolume）是集群级存储资源，StorageClass 是动态创建 PV 的模板。

13-选择-028（★ 知识点：K13-6 Namespace 概念） K8s 中，用于在集群内做资源隔离的虚拟集群概念是？

  • APod
  • BDeployment
  • CNamespace
  • DNode

答案：C 解析：Namespace 是集群内的虚拟集群，用于资源隔离（如 dev/test/prod 环境隔离）。不同 Namespace 的资源相互隔离。Pod、Deployment、Node 都不是隔离概念。

13-选择-029（★★ 知识点：K13-4 API Server 唯一性） K8s 集群中，能够直接读写 etcd 的组件是？

  • Akubelet
  • Bscheduler
  • Ckube-apiserver
  • Dcontroller-manager

答案：C 解析：只有 API Server 能直接读写 etcd，其他组件（scheduler、controller-manager、kubelet 等）都通过 API Server 间接操作 etcd。这是 K8s 的安全与解耦设计。

13-选择-030（★★ 知识点：K13-3 Master 故障） 当 K8s Master（控制平面）发生故障时，下列说法正确的是？

  • A所有业务 Pod 立即停止运行
  • B已运行的 Pod 仍可在 Node 上继续工作，但不能创建新资源
  • C集群完全崩溃，无法恢复
  • DNode 也会自动关机

答案：B 解析：Master 挂了，已运行的 Pod 仍由 Node 上的 kubelet 维持运行，业务不中断；但不能做新操作（创建/删除/扩缩容）。生产环境用多 Master 高可用避免单点故障。

1.2 多项选择题（10 题）

13-选择-031（★★ 知识点：K13-1 Compose 局限） Docker Compose 相比 Kubernetes 的局限性包括？（多选）

  • A只能在单台机器上编排容器
  • B容器故障后不能自动迁移到其他节点
  • C不支持根据负载自动扩缩容
  • D不支持原生滚动更新 E. 不能用 YAML 描述服务

答案：A、B、C、D 解析：A 单机局限、B 无自愈、C 无弹性、D 无滚动更新都是 Compose 的局限。E 错，Compose 完全支持 YAML（docker-compose.yml）。

13-选择-032（★★ 知识点：K13-1 容器编排职责） 下列属于"容器编排"系统职责的有？（多选）

  • A决定容器跑在哪个节点
  • B容器故障时自动重启或迁移
  • C根据负载自动扩缩容
  • D把应用打包成镜像 E. 滚动更新与回滚

答案：A、B、C、E 解析：容器编排负责调度（A）、自愈（B）、弹性（C）、滚动更新（E）。D 是 Dockerfile 的工作（容器化），不属于编排职责。

13-选择-033（★★ 知识点：K13-3 Master 组件） K8s Master（控制平面）的核心组件包括？（多选）

  • Akube-apiserver
  • Betcd
  • Ckube-scheduler
  • Dkube-controller-manager E. kubelet

答案：A、B、C、D 解析：Master 四大组件：API Server、etcd、scheduler、controller-manager。E 错，kubelet 跑在 Node 上，是 Node 组件。

13-选择-034（★★ 知识点：K13-5 Node 组件） K8s Node（工作节点）的核心组件包括？（多选）

  • Akubelet
  • Bkube-proxy
  • Ccontainer-runtime
  • Detcd E. scheduler

答案：A、B、C 解析：Node 三大组件：kubelet、kube-proxy、container-runtime。D、E 是 Master 组件，不在 Node 上。

13-选择-035（★★ 知识点：K13-2 K8s vs Compose） 与 Docker Compose 相比，Kubernetes 的优势包括？（多选）

  • A支持多节点集群调度
  • B容器故障自动自愈与迁移
  • C根据负载自动扩缩容
  • D原生支持滚动更新与回滚 E. 不需要学习 YAML

答案：A、B、C、D 解析：A 多机调度、B 自愈、C 弹性、D 滚动更新都是 K8s 的优势。E 错，K8s 大量使用 YAML（比 Compose 更复杂）。

13-选择-036（★★ 知识点：K13-2 适用场景） 下列场景中，适合使用 Kubernetes 的有？（多选）

  • A企业级应用生产部署（用户上万）
  • B微服务架构（几十个服务）
  • C跨地域多机房部署
  • D金融系统高可用部署 E. 个人本地开发联调

答案：A、B、C、D 解析：A、B、C、D 都需要集群调度、高可用、弹性扩缩容，适合 K8s。E 错，本地开发联调用 Compose 更简单。

13-选择-037（★★ 知识点：K13-4 controller-manager） 下列属于 kube-controller-manager 内置控制器的有？（多选）

  • ADeployment Controller
  • BReplicaSet Controller
  • CNode Controller
  • DEndpoint Controller E. CNI Controller

答案：A、B、C、D 解析：controller-manager 内置多种控制器：Deployment、ReplicaSet、Node、Endpoint 等。E 错，CNI 是网络插件接口，不是控制器。

13-选择-038（★★ 知识点：K13-5 容器运行时） 下列可以作为 K8s 容器运行时的有？（多选）

  • Acontainerd
  • BCRI-O
  • CVMware ESXi
  • DDocker（通过 containerd 兼容） E. KubeVirt

13-判断-001（★ 知识点：K13-1 K8s 定义） Kubernetes（K8s）是一个开源的容器编排平台，用于自动化部署、扩展和管理容器化应用。

答案：正确（✓） 解析：API Server 是唯一入口，所有组件（scheduler、controller-manager、kubelet 等）都通过 API Server 通信，这是 K8s 的解耦设计。

13-判断-007（★ 知识点：K13-4 etcd） etcd 是 K8s 的键值存储数据库，保存集群的所有状态数据。

13-判断-010（★ 知识点：K13-5 kube-proxy 职责） kube-proxy 维护 Service 的网络规则，实现服务发现与负载均衡。

答案：正确（✓） 解析：kube-proxy 跑在每个 Node 上，监听 Service 与 Endpoints 变化，配置 iptables/ipvs 规则，实现 Service 流量路由到后端 Pod。

13-判断-012（★ 知识点：K13-6 Pod 概念） Pod 是 K8s 最小的调度单元，包含一个或多个紧密协作的容器。

13-判断-016（★★ 知识点：K13-4 controller-manager 机制） controller-manager 中的控制器通过"调和循环"（reconcile loop）持续让实际状态趋近期望状态。

13-判断-018（★★ 知识点：K13-4 组件通信方式） K8s 各组件之间（如 scheduler 与 controller-manager）直接互相调用，效率更高。

答案：错误（✗） 解析：K8s 组件之间不直接调用，所有通信都经过 API Server。这是解耦设计，便于安全控制（认证授权）和横向扩展。

13-判断-019（★ 知识点：K13-2 Compose 价值） 学习 K8s 后应该完全抛弃 Docker Compose，所有场景都用 K8s。

答案：错误（✗） 解析：Compose 在本地开发、CI 测试、小规模部署场景仍是首选。K8s 运维成本高，过度设计是问题。技术选型要看场景。

13-判断-020（★ 知识点：K13-6 Ingress 职责） Ingress 是 K8s 的七层路由资源，基于域名和路径把请求转发到不同 Service。

13-论述-001（★★ 知识点：K13-1/K13-2 Compose 局限与 K8s 价值，10 分） 请阐述 Docker Compose 的四大局限性，并说明 Kubernetes 是如何分别解决这些问题的。

参考答案与评分标准（10 分，按要点给分）：

  1. 单机局限（2 分）：Compose 只能在单台机器上编排容器，不能跨机器调度。K8s 管理多节点集群，Pod 可由 scheduler 自动调度到任意合适的 Node，实现跨机部署。
  2. 无自愈（2 分）：Compose 的容器挂了不会自动迁移到其他节点（机器挂了完全没救）。K8s 的 controller-manager 持续监控 Pod 状态，Pod 挂了自动重建，Node 挂了自动迁移 Pod 到其他节点。
  3. 无弹性（2 分）：Compose 不能根据负载自动扩缩容，副本数写死在 yml 里。K8s 的 HPA（HorizontalPodAutoscaler）根据 CPU/内存等指标自动扩缩容。
  4. 无滚动更新（2 分）：Compose 更新镜像要手动停旧启新，会中断服务。K8s 的 Deployment 原生支持滚动更新（逐步替换 Pod）与回滚（rollout undo），实现零停机。
  5. 总结（2 分）：Compose 适合单机小规模场景（开发/测试），K8s 适合集群大规模生产场景，二者不是替代关系，而是规模递进。

评分要点：每个局限 2 分（说明局限 1 分 + K8s 解决方案 1 分）；总结 2 分；要点完整给满分。

    • etcd：分布式键值存储，保存集群所有状态（0.5 分）

13-论述-003（★★ 知识点：K13-2 K8s vs Compose，8 分） 请从规模、调度方式、自愈、弹性、滚动更新、服务发现六个维度，对比 Docker Compose 与 Kubernetes，并说明在什么情况下应该选择 K8s 而非 Compose。

    • 调度方式：Compose 不调度（写死在执行机器）；K8s 自动调度（scheduler 决策）
    • 自愈：Compose 仅 restart 重启容器，机器挂了没救；K8s 控制器自动重建 Pod，节点挂了自动迁移
    • 弹性：Compose 不支持自动扩缩容；K8s HPA 根据 CPU/内存自动扩缩容
    • 滚动更新：Compose 不支持（需手动停旧启新）；K8s Deployment 原生支持滚动更新与回滚

  2. 选型原则（2 分）：
    • 机器数 ≥ 2 且需要高可用 → K8s
    • 容器数 ≥ 10 且需要弹性 → K8s
    • 生产环境、大规模、微服务架构 → K8s
    • 本地开发、CI 测试、小规模部署 → Compose

评分要点：每个维度 1 分（要点对即可）；选型原则 2 分（答出 2 条以上给满分）。

13-论述-004（★★ 知识点：K13-6 核心概念与 CTTS 项目，8 分） 请简述 K8s 的核心资源（Pod、Deployment、Service、ConfigMap、Secret、PV/PVC、Ingress、Namespace）各自的概念，并说明在 CTTS 项目（前端 Vue3 + 后端 SpringBoot + MySQL）的 K8s 部署中，每个资源分别承担什么角色。

    • Deployment：管理 Pod 副本，支持滚动更新与回滚
    • Service：为一组 Pod 提供稳定访问入口（IP+DNS）和负载均衡
    • ConfigMap：存储非敏感配置（key-value），可挂载为环境变量或文件
    • Secret：存储敏感信息（密码/密钥），base64 编码

  2. CTTS 项目角色分配（4 分，每个 0.5 分）：
    • Pod：跑前端、后端、MySQL 的容器实例

    • Ingress：配置域名（如 ctts.com），把请求路由到前端 Service（/）和后端 Service（/api）
    • Namespace：可以按环境隔离（如 dev/test/prod），学习环境用 default 即可

13-编程-001（★★ 知识点：K13-2/K13-6 Compose vs K8s 资源对照，15 分） K8s 资源方案设计：CTTS 项目要从 Docker Compose 升级到 K8s 部署。已知 Compose 版的 docker-compose.yml 如下：

请设计 K8s 版本的资源方案（不要求写完整 YAML，只列资源清单），要求包含：

  1. 需要哪些 K8s 资源？每个资源的作用是什么？（8 分）

参考答案与评分标准（15 分）：

1. K8s 资源清单与作用（8 分）：

  • Deployment/ctts-frontend（或 StatefulSet）：管理前端 Pod 副本（2 副本），滚动更新（2 分）
  • Deployment/ctts-backend：管理后端 Pod 副本（3 副本），滚动更新（2 分）
  • StatefulSet/ctts-mysql：管理 MySQL Pod（有状态应用，1 副本），稳定网络标识（2 分）
  • Service/ctts-frontend（ClusterIP）：前端集群内访问入口（0.5 分）
  • Service/ctts-backend（ClusterIP）：后端集群内访问入口（0.5 分）

13-编程-002（★★★ 知识点：K13-3/K13-4/K13-5 综合应用，20 分） K8s 架构与命令流程综合题：某团队要将 CTTS 项目部署到 K8s 集群，集群拓扑如下：

集群：1 Master + 2 Node
Master: API Server + etcd + scheduler + controller-manager
Node1:  kubelet + kube-proxy + containerd
Node2:  kubelet + kube-proxy + containerd

团队成员小李在管理机执行了以下命令序列：

# 命令1
kubectl get nodes
# 命令2
kubectl apply -f ctts-backend-deployment.yaml   # replicas: 3
# 命令3
kubectl get pods -o wide
# 命令4
kubectl scale deployment ctts-backend --replicas=5
# 命令5
kubectl get pods

问题：

  1. 说明命令1~5每条命令的作用，并指出每条命令在 K8s 架构中是用户操作还是集群组件响应（10分）
  2. 命令2执行后，集群中哪些 Master 组件参与了处理？分别做了什么？（5分）
  3. 命令4执行后，集群如何从 3 副本扩容到 5 副本？涉及哪些组件？（5分）

参考答案与评分标准（20 分）：

1. 各命令作用与架构归属（10分，每条2分）：

  • 命令1 kubectl get nodes：列出集群所有 Node 及状态。用户操作（kubectl 发请求给 API Server），API Server 从 etcd 读数据返回。
  • 命令2 kubectl apply -f ctts-backend-deployment.yaml：提交 Deployment（3 副本）到集群。用户操作（kubectl 发请求给 API Server），API Server 写入 etcd，触发 controller-manager 与 scheduler 协作。
  • 命令3 kubectl get pods -o wide：列出所有 Pod 及详细信息（含所在 Node）。用户操作，API Server 从 etcd 读 Pod 状态返回。
  • 命令4 kubectl scale deployment ctts-backend --replicas=5：把 ctts-backend 副本数从 3 扩到 5。用户操作（kubectl 发请求给 API Server），API Server 更新 Deployment 的 replicas 字段，controller-manager 响应。
  • 命令5 kubectl get pods：列出所有 Pod。用户操作，API Server 返回当前 Pod 状态。 （每条命令：作用1分 + 归属1分）

2. 命令2执行后 Master 组件参与（5分）：

  • API Server：接收 kubectl 请求，认证授权，把 Deployment 对象写入 etcd（1.5分）
  • etcd：保存 Deployment 对象（期望 3 副本）及后续创建的 ReplicaSet、Pod 对象（1分）
  • controller-manager：Deployment Controller 监听到新 Deployment，创建 ReplicaSet；ReplicaSet Controller 创建 3 个 Pod 对象（但未调度）（1.5分）
  • scheduler：监听到 3 个未调度的 Pod，根据资源/规则选择 Node（如 Pod1→Node1, Pod2→Node2, Pod3→Node1），把绑定信息写回 API Server → etcd（1分） （注意：真正启动容器的是目标 Node 上的 kubelet，不属于 Master 组件）

3. 命令4 扩容流程（5分）：

  • kubectl 把 scale 请求发给 API Server（0.5分）
  • API Server 更新 Deployment 的 replicas 字段为 5，写入 etcd（1分）
  • controller-manager 的 Deployment Controller 监听到副本数变化，更新 ReplicaSet（0.5分）
  • ReplicaSet Controller 发现实际只有 3 个 Pod，期望 5 个，再创建 2 个新 Pod（1分）
  • scheduler 监听到 2 个未调度的 Pod，决策调度到哪个 Node（如 Node1、Node2），写回绑定信息（1分）
  • 目标 Node 的 kubelet 调用 container-runtime 启动新容器，上报状态（1分） （注意：kubelet 与 container-runtime 是 Node 组件，但扩容流程必须提到）

评分要点：各小题独立给分；流程顺序正确即可；专有名词理解正确即可；第3问必须提到 kubelet 才给最后1分。
