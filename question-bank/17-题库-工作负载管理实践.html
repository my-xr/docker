1.1 单项选择题（30 题）

17-选择-001（★ 知识点：K17-1 三服务规划） CTTS 三服务 Deployment 部署的推荐顺序是？

  • A前端 → 后端 → MySQL
  • B后端 → MySQL → 前端
  • CMySQL → 后端 → 前端
  • D任意顺序都可以

答案：C 解析：部署顺序由依赖关系决定。后端依赖 MySQL（要先连接数据库），前端依赖后端（Nginx 反向代理）。所以顺序是 MySQL → 后端 → 前端。若先部署后端，后端启动时连不上 MySQL 会 CrashLoopBackOff。

17-选择-002（★ 知识点：K17-1 副本数规划） CTTS 三服务中，MySQL Deployment 推荐的副本数是？

  • A1 副本
  • B2 副本
  • C3 副本
  • D5 副本

答案：A 解析：MySQL 是有状态应用，多副本会导致数据写入冲突。本课用 1 副本 Deployment 简化部署，生产环境用 StatefulSet + PV/PVC。后端 3 副本（无状态高可用），前端 2 副本（静态资源轻量）。

17-选择-003（★ 知识点：K17-1 副本数规划） CTTS 后端 Deployment 推荐的副本数是？

  • A1 副本
  • B2 副本
  • C3 副本
  • D5 副本

答案：C 解析：后端是核心 API 服务，无状态应用，3 副本是高可用的最低要求（挂 1 个还有 2 个）。前端 2 副本，MySQL 1 副本。

17-选择-004（★ 知识点：K17-2 MySQL 环境变量） MySQL Deployment 中，必须设置的环境变量是？

  • AMYSQL_USER
  • BMYSQL_DATABASE
  • CMYSQL_ROOT_PASSWORD
  • DMYSQL_PORT

答案：C 解析：MySQL 官方镜像要求必须设置 MYSQL_ROOT_PASSWORD（或 MYSQL_ALLOW_EMPTY_PASSWORD=yes 但不推荐），否则容器启动报错退出，Pod 进入 CrashLoopBackOff。MYSQL_DATABASE、MYSQL_USER 是可选的，MYSQL_PORT 不是 MySQL 镜像的环境变量。

17-选择-005（★ 知识点：K17-2 MySQL 数据卷） 本课 MySQL Deployment 用 emptyDir 做数据卷，关于 emptyDir 说法正确的是？

  • APod 删除后数据保留
  • BPod 删除后数据丢失
  • C数据持久化到宿主机磁盘
  • D需要先创建 PV 才能使用

答案：B 解析：emptyDir 是 Pod 级别的临时卷，Pod 删除时数据一起丢失。生产环境必须用 PVC（PersistentVolumeClaim）做持久化，emptyDir 仅用于实践练习或临时数据。

17-选择-006（★ 知识点：K17-3 imagePullPolicy） 本课 CTTS 后端 Deployment 的 imagePullPolicy 设为 Never，原因是？

  • A镜像在 Docker Hub 上不存在
  • B镜像是本地构建的，不想从仓库拉取
  • C节省网络带宽
  • D提高启动速度

答案：B 解析：ctts-backend:v1 是本地构建的镜像（在 Minikube Docker daemon 里），Docker Hub 上不存在。如果用 Always 或 IfNotPresent，K8s 会尝试从 Docker Hub 拉取，拉不到会报 ImagePullBackOff。设为 Never 表示只用本地镜像，不从仓库拉取。

17-选择-007（★ 知识点：K17-3 后端连接 MySQL） CTTS 后端 Deployment 中 DB_HOST 环境变量的推荐值是？

  • Alocalhost
  • B127.0.0.1
  • Cmysql.ctts.svc.cluster.local
  • DMySQL Pod 的 IP 地址

答案：C 解析：后端通过 Service DNS 名连接 MySQL，格式为 <service-name>.<namespace>.svc.cluster.local。本课 mysql Service 在 ctts namespace，所以是 mysql.ctts.svc.cluster.local。用 Pod IP 不可靠（Pod 重建 IP 变化），localhost/127.0.0.1 是本机回环，连不到 MySQL Pod。

17-选择-008（★ 知识点：K17-4 前端副本数） CTTS 前端 Deployment 推荐的副本数是？

  • A1 副本
  • B2 副本
  • C3 副本
  • D5 副本

答案：B 解析：前端是 Nginx 静态资源服务，资源占用小，2 副本已满足高可用（挂 1 个还有 1 个）。不需要 3 副本，避免浪费资源。后端 3 副本，MySQL 1 副本。

17-选择-009（★ 知识点：K17-4 前端镜像） CTTS 前端 Deployment 使用的镜像是？

  • Anginx:1.25
  • Bvue:3
  • Cctts-frontend:v1
  • Dnode:18

答案：C 解析：ctts-frontend:v1 是第 8 次课构建的镜像，包含 Nginx + Vue3 构建产物（dist）。nginx:1.25 是基础镜像，vue:3 和 node:18 不是前端运行镜像（node 是构建阶段用的）。

17-选择-010（★ 知识点：K17-5 滚动更新命令） 触发 Deployment 滚动更新的 kubectl 命令是？

  • Akubectl apply
  • Bkubectl set image
  • Ckubectl rollout
  • Dkubectl update

答案：B 解析：kubectl set image deployment/ = 触发滚动更新。kubectl apply 是应用 YAML（也可触发更新），kubectl rollout 是查看/管理更新状态（status/history/undo），kubectl update 不是有效命令。

17-选择-011（★ 知识点：K17-5 滚动更新观察） 查看滚动更新状态的 kubectl 命令是？

  • Akubectl rollout status deployment/
  • Bkubectl rollout history deployment/
  • Ckubectl rollout undo deployment/
  • Dkubectl get deployment

答案：A 解析：kubectl rollout status deployment/ 查看当前滚动更新状态（进行中/完成）。rollout history 查看版本历史，rollout undo 回滚，get deployment 查看 Deployment 概览（不显示更新过程）。

17-选择-012（★ 知识点：K17-5 回滚命令） 将 Deployment 回滚到上一版本的 kubectl 命令是？

  • Akubectl rollout undo deployment/
  • Bkubectl rollback deployment/
  • Ckubectl rollout back deployment/
  • Dkubectl undo deployment/

答案：A 解析：kubectl rollout undo deployment/ 回滚到上一版本。用 --to-revision=N 可回滚到指定版本。kubectl rollback 和 kubectl undo 不是有效命令。

17-选择-013（★ 知识点：K17-5 回滚指定版本） 将 Deployment 回滚到指定版本 revision 2 的命令是？

  • Akubectl rollout undo deployment/ --revision=2
  • Bkubectl rollout undo deployment/ --to-revision=2
  • Ckubectl rollout undo deployment/ --target=2
  • Dkubectl rollout undo deployment/ --version=2

答案：B 解析：kubectl rollout undo deployment/ --to-revision=2 回滚到指定 revision。--to-revision 是固定参数名，不是 --revision/--target/--version。

17-选择-014（★ 知识点：K17-5 版本历史） 查看 Deployment 版本历史的 kubectl 命令是？

  • Akubectl history deployment/
  • Bkubectl rollout history deployment/
  • Ckubectl get history deployment/
  • Dkubectl describe deployment/

答案：B 解析：kubectl rollout history deployment/ 查看版本历史（REVISION 和 CHANGE-CAUSE）。kubectl history 不是有效命令。kubectl describe 显示 Deployment 详情，不显示版本历史。

17-选择-015（★ 知识点：K17-6 CrashLoopBackOff） Pod 状态显示 CrashLoopBackOff，最可能的排查方法是？

  • A重启 Minikube
  • B删除 Deployment 重建
  • Ckubectl logs 查看 Pod 日志
  • Dkubectl scale 增加副本数

答案：C 解析：CrashLoopBackOff 表示容器反复崩溃重启，需用 kubectl logs 查看 Pod 日志定位应用层报错（如连不上数据库、代码 bug、配置错误）。重启 Minikube 或删除重建不解决根因，增加副本数只是掩盖问题。

17-选择-016（★ 知识点：K17-6 ImagePullBackOff） Pod 状态显示 ImagePullBackOff，最可能的根因是？

  • A应用代码有 bug
  • B内存不足
  • C镜像拉取失败（镜像名错或仓库不可达）
  • Dselector 不匹配

答案：C 解析：ImagePullBackOff 表示镜像拉取失败。常见原因：镜像名拼错、私有仓库未登录、网络问题、本地镜像但 imagePullPolicy 不是 Never。应用 bug 会导致 CrashLoopBackOff，内存不足会 OOMKilled，selector 不匹配会导致 Deployment READY 0/N。

17-选择-017（★ 知识点：K17-6 Pending） Pod 状态显示 Pending，最可能的根因是？

  • A应用启动失败
  • B镜像拉取失败
  • C节点资源不足，无法调度
  • D配置错误

答案：C 解析：Pending 表示 Pod 未被调度到任何节点。常见原因：节点 CPU/内存不足（requests 太大）、节点污点、nodeSelector 不匹配。用 kubectl describe pod 看 Events 部分的 FailedScheduling 信息。应用启动失败是 CrashLoopBackOff，镜像拉取失败是 ImagePullBackOff。

17-选择-018（★ 知识点：K17-6 Deployment 0/3） Deployment READY 显示 0/3 但 Pod 都在 Running，最可能的根因是？

  • A资源不足
  • Bselector.matchLabels 与 template.metadata.labels 不匹配
  • C镜像拉取失败
  • D副本数设错

答案：B 解析：Deployment READY 0/3 但 Pod Running，说明 Pod 起来了但 Deployment 不认识它们（selector 匹配不到）。根因是 selector.matchLabels 与 template.metadata.labels 不匹配。修正 YAML 让二者匹配即可。

17-选择-019（★ 知识点：K17-6 排查命令） K8s 部署问题排查的"四步法"顺序是？

  • A看状态 → 看详情 → 看日志 → 定根因
  • B看日志 → 看状态 → 看详情 → 定根因
  • C看详情 → 看日志 → 看状态 → 定根因
  • D定根因 → 看状态 → 看详情 → 看日志

答案：A 解析：四步法：① 看状态（kubectl get pods 的 STATUS 列）→ ② 看详情（kubectl describe pod 的 Events）→ ③ 看日志（kubectl logs）→ ④ 定根因（修复 YAML 重新 apply）。先从宏观状态入手，再逐步深入。

17-选择-020（★ 知识点：K17-2 MySQL 资源限制） MySQL Deployment 的 memory limits 建议至少设为？

  • A128Mi
  • B256Mi
  • C512Mi
  • D1Gi

答案：D 解析：MySQL 的 InnoDB 缓冲池需要较大内存，建议 limits 至少 1Gi。128Mi/256Mi 太小会 OOMKilled。本课实践配置 requests 512Mi / limits 1Gi，生产环境通常 2Gi~4Gi 起。

17-选择-021（★★ 知识点：K17-3 后端资源限制） CTTS 后端是 SpringBoot 应用，memory requests 建议至少设为？

  • A64Mi
  • B128Mi
  • C256Mi
  • D1Gi

答案：C 解析：Java 应用 JVM 堆 + 元空间 + 线程栈至少需要 256Mi。设太小会 OOMKilled（如 64Mi/128Mi 不够 JVM 启动）。本课配置 requests 256Mi / limits 512Mi，生产环境通常 512Mi~1Gi 起。

17-选择-022（★★ 知识点：K17-5 滚动更新原理） Deployment 滚动更新时，旧 ReplicaSet 的副本数如何变化？

  • A立即删除
  • B立即降到 0
  • C逐步降到 0（保留 RS 对象）
  • D保持不变

答案：C 解析：滚动更新是渐进式的，旧 RS 副本数逐步降到 0（不是立即删除或降到 0），新 RS 副本数逐步升到期望值。旧 RS 对象保留（副本数=0），用于回滚。revisionHistoryLimit 控制保留版本数（默认 10）。

17-选择-023（★★ 知识点：K17-5 服务不中断） 3 副本 Deployment 滚动更新，maxSurge=25%、maxUnavailable=25%，更新期间最少可用 Pod 数是？

  • A1
  • B2
  • C3
  • D4

答案：B 解析：maxUnavailable=25% 表示最多低于期望副本数 25%。3 * 25% = 0.75，向下取整 = 1，即最多少 1 个，最少保持 3 - 1 = 2 个 Pod 可用。maxSurge=25% 表示最多超出 25%，3 * 25% = 0.75，向上取整 = 1，最多 4 个 Pod。

17-选择-024（★★ 知识点：K17-5 --record 参数） kubectl set image 加 --record 参数的作用是？

  • A加快滚动更新速度
  • B把变更原因记录到 rollout history
  • C自动回滚失败更新
  • D强制立即替换所有 Pod

答案：B 解析：--record 把执行的 kubectl 命令记录到 rollout history 的 CHANGE-CAUSE 列，便于追溯版本变更原因。不影响更新速度、不自动回滚、不改变替换策略。

17-选择-025（★★ 知识点：K17-3 MySQL Service） 本课用 kubectl expose deployment ctts-mysql --name=mysql 创建 Service，其作用是？

  • A对外暴露 MySQL
  • B为后端提供 MySQL 的稳定 DNS 名
  • C增加 MySQL 副本数
  • D给 MySQL 打标签

答案：B 解析：kubectl expose 创建 ClusterIP Service，为 MySQL 提供稳定 DNS 名（mysql.ctts.svc.cluster.local），后端通过此 DNS 名连接 MySQL。Service 不增加副本数、不打标签、默认 ClusterIP 不对外暴露。

17-选择-026（★★ 知识点：K17-4 前端 Nginx） CTTS 前端 Nginx 容器中，Vue3 构建产物（dist）的存放路径是？

  • A/app/dist
  • B/var/www/html
  • C/usr/share/nginx/html
  • D/opt/nginx/html

答案：C 解析：Nginx 官方镜像默认静态资源路径是 /usr/share/nginx/html。Vue3 构建产物 dist 在 Dockerfile 中 COPY 到此目录。/var/www/html 是 Apache 的默认路径，/app/dist 和 /opt/nginx/html 不是标准路径。

17-选择-027（★★ 知识点：K17-1 标签设计） CTTS 三服务的标签设计中，区分服务身份的核心标签是？

  • Atier
  • Bversion
  • Capp
  • Denv

答案：C 解析：app 标签唯一标识服务（ctts-mysql / ctts-backend / ctts-frontend），是 Service 选择 Pod 的依据。tier 区分层级（database/backend/frontend），version 区分版本（v1/v2），env 标识环境（dev/prod）。

17-选择-028（★★ 知识点：K17-6 OOMKilled） Pod 状态显示 OOMKilled，最可能的根因是？

  • A镜像拉取失败
  • B容器内存使用超过 limits.memory
  • C应用代码 bug
  • D节点 CPU 不足

答案：B 解析：OOMKilled（Out Of Memory Killed）表示容器内存使用超过 limits.memory，被内核杀掉。解决：增大 limits.memory 或优化应用内存使用。镜像拉取失败是 ImagePullBackOff，代码 bug 通常 CrashLoopBackOff，CPU 不足不会直接 OOMKilled。

17-选择-029（★★ 知识点：K17-3 后端启动失败） 后端 Deployment 的 Pod 一直 CrashLoopBackOff，kubectl logs 显示 "Connection refused mysql.ctts.svc.cluster.local:3306"，最可能的根因是？

  • A后端镜像构建错误
  • BMySQL Service 未创建或 MySQL Pod 未 Ready
  • C后端资源不足
  • Dselector 不匹配

答案：B 解析：日志显示连不上 MySQL Service。可能原因：① mysql Service 未创建（kubectl get svc mysql 检查）；② MySQL Pod 未 Ready（kubectl get pod -l app=ctts-mysql 检查）；③ 后端比 MySQL 先部署。解决：确保 MySQL Ready 并创建 Service 后再部署后端。

17-选择-030（★★ 知识点：K17-5 回滚历史） 关于 kubectl rollout undo 回滚后，原版本是否还在历史中，说法正确的是？

  • A原版本被删除
  • B原版本仍在历史中，可再次回滚到该版本
  • C历史被清空
  • D只有最新版本保留

答案：B 解析：回滚操作本身也是一次"滚动更新"（创建新 revision），原版本 RS 仍在历史中，可以再次回滚到该版本。revisionHistoryLimit=10 默认保留 10 个 revision。所以回滚不会删除历史版本。

1.2 多项选择题（10 题）

17-选择-031（★★ 知识点：K17-1 三服务规划） CTTS 三服务 Deployment 部署时，关于副本数规划正确的有？（多选）

  • AMySQL 1 副本（有状态，多副本数据冲突）
  • B后端 3 副本（无状态，高可用最低要求）
  • C前端 2 副本（静态资源轻量，够用即可）
  • D所有服务都 3 副本 E. MySQL 3 副本（高可用）

答案：A、B、C 解析：MySQL 有状态多副本冲突，1 副本简化（生产用 StatefulSet）；后端无状态 3 副本高可用；前端静态资源轻量 2 副本够用。D 错，不是所有服务都 3 副本（MySQL 不能多副本）；E 错，MySQL 3 副本数据冲突。

17-选择-032（★★ 知识点：K17-2 MySQL YAML） MySQL Deployment YAML 中必须包含的字段有？（多选）

  • AMYSQL_ROOT_PASSWORD 环境变量
  • Bimage: mysql:8.0
  • CcontainerPort: 3306
  • Dreplicas: 3 E. env: MYSQL_DATABASE

答案：A、B、C 解析：MySQL 官方镜像必须设置 MYSQL_ROOT_PASSWORD（A），否则启动失败；image 用 mysql:8.0（B）；端口 3306（C）。D 错，MySQL 1 副本；E 错，MYSQL_DATABASE 可选（自动创建数据库，不设也能启动）。

17-选择-033（★★ 知识点：K17-3 后端环境变量） CTTS 后端 Deployment 连接 MySQL 需要的环境变量有？（多选）

  • ADB_HOST
  • BDB_PORT
  • CDB_NAME
  • DDB_USER E. DB_PASSWORD

答案：A、B、C、D、E 解析：后端连接 MySQL 需要完整连接信息：DB_HOST（Service DNS 名）、DB_PORT（3306）、DB_NAME（数据库名）、DB_USER（用户名）、DB_PASSWORD（密码）。SpringBoot 通过环境变量覆盖 application.yml 配置。

17-选择-034（★★ 知识点：K17-5 滚动更新命令） Deployment 滚动更新相关的 kubectl 命令有？（多选）

  • Akubectl set image
  • Bkubectl rollout status
  • Ckubectl rollout history
  • Dkubectl rollout undo E. kubectl scale

答案：A、B、C、D 解析：A 触发滚动更新，B 查看更新状态，C 查看版本历史，D 回滚。E 是扩缩容命令（kubectl scale），不属于滚动更新命令。

二、判断题（共 20 题，每题 1 分）

17-判断-001（★ 知识点：K17-1 部署顺序） CTTS 三服务 Deployment 部署顺序应该是 MySQL → 后端 → 前端。

答案：正确（✓） 解析：部署顺序由依赖关系决定。后端依赖 MySQL，前端依赖后端。若先部署后端，后端启动时连不上 MySQL 会 CrashLoopBackOff。

17-判断-002（★ 知识点：K17-1 MySQL 副本数） MySQL 是有状态应用，生产环境应该用 3 副本 Deployment 保证高可用。

答案：错误（✗） 解析：MySQL 有状态，多副本数据冲突。生产环境用 StatefulSet + PV/PVC（不是 Deployment 多副本）。本课用 1 副本 Deployment 简化实践。

17-判断-003（★ 知识点：K17-2 MySQL 环境变量） MySQL Deployment 可以不设置 MYSQL_ROOT_PASSWORD，镜像会用空密码启动。

答案：错误（✗） 解析：MySQL 官方镜像要求必须设置 MYSQL_ROOT_PASSWORD（或 MYSQL_ALLOW_EMPTY_PASSWORD=yes 但不推荐），否则启动报错，Pod CrashLoopBackOff。

17-判断-004（★ 知识点：K17-2 emptyDir） 本课 MySQL 用 emptyDir 做数据卷，Pod 删除后数据会丢失。

答案：正确（✓） 解析：emptyDir 是 Pod 级别临时卷，Pod 删除时数据一起丢失。生产环境必须用 PVC 持久化。

17-判断-005（★ 知识点：K17-3 imagePullPolicy） 本课 ctts-backend:v1 是本地构建的镜像，imagePullPolicy 应设为 Never。

答案：正确（✓） 解析：本地构建的镜像在 Minikube Docker daemon 里，Docker Hub 上不存在。设为 Never 表示只用本地镜像，不从仓库拉取，避免 ImagePullBackOff。

17-判断-006（★ 知识点：K17-3 后端连接 MySQL） CTTS 后端可以用 localhost 作为 DB_HOST 连接 MySQL。

答案：错误（✗） 解析：localhost/127.0.0.1 是本机回环，连不到 MySQL Pod（不同 Pod 不同 IP）。应该用 MySQL Service 的 DNS 名 mysql.ctts.svc.cluster.local。

17-判断-007（★ 知识点：K17-4 前端副本数） CTTS 前端是静态资源服务，2 副本已满足高可用要求。

答案：正确（✓） 解析：前端 Nginx 静态资源轻量，2 副本够用（挂 1 个还有 1 个）。不需要 3 副本，避免浪费资源。

17-判断-008（★ 知识点：K17-5 滚动更新命令） kubectl set image 是触发 Deployment 滚动更新的命令。

答案：正确（✓） 解析：kubectl set image deployment/ = 触发滚动更新。kubectl rollout status 观察，rollout undo 回滚。

17-判断-009（★ 知识点：K17-5 回滚） kubectl rollout undo 只能回滚到上一版本，不能回滚到更早版本。

答案：错误（✗） 解析：kubectl rollout undo 默认回滚到上一版本，但用 --to-revision=N 可以回滚到任意历史版本。先用 kubectl rollout history 查看版本号，再 --to-revision=N 指定。

17-判断-010（★ 知识点：K17-5 版本历史） Deployment 滚动更新后，旧 ReplicaSet 会被立即删除。

答案：错误（✗） 解析：旧 ReplicaSet 保留（副本数=0），用于回滚。revisionHistoryLimit=10 默认保留 10 个历史版本。立即删除旧 RS 会无法回滚。

17-判断-011（★ 知识点：K17-6 CrashLoopBackOff） Pod CrashLoopBackOff 时，应该优先用 kubectl logs 查看应用日志定位根因。

答案：正确（✓） 解析：CrashLoopBackOff 表示应用反复崩溃，kubectl logs 看应用层报错（如连不上数据库、代码 bug、配置错误）。kubectl describe 看 K8s 层面事件（Events），两者结合排查。

17-判断-012（★ 知识点：K17-6 ImagePullBackOff） Pod ImagePullBackOff 通常是因为镜像名错或镜像仓库不可达。

答案：正确（✓） 解析：ImagePullBackOff 表示镜像拉取失败。常见原因：镜像名拼错、私有仓库未登录、网络问题、本地镜像但 imagePullPolicy 不是 Never。用 kubectl describe 看 Events 部分的拉取错误信息。

17-判断-013（★ 知识点：K17-6 Pending） Pod Pending 通常是因为节点资源不足，无法调度。

答案：正确（✓） 解析：Pending 表示 Pod 未被调度。常见原因：节点 CPU/内存不足（requests 太大）、节点污点、nodeSelector 不匹配。用 kubectl describe pod 看 Events 部分的 FailedScheduling 信息。

17-判断-014（★ 知识点：K17-6 selector 不匹配） Deployment READY 0/3 但 Pod 都 Running，可能是 selector.matchLabels 与 template.metadata.labels 不匹配。

答案：正确（✓） 解析：Pod 起来了但 Deployment selector 匹配不到它们，导致 READY 0/3。修正 YAML 让 selector.matchLabels 与 template.metadata.labels 匹配即可。

17-判断-015（★ 知识点：K17-2 MySQL 资源限制） MySQL Deployment 的 memory limits 可以设为 128Mi，够用了。

答案：错误（✗） 解析：MySQL InnoDB 缓冲池需要较大内存，128Mi 太小会 OOMKilled。建议 limits 至少 1Gi，生产环境 2Gi~4Gi 起。

17-判断-016（★★ 知识点：K17-5 滚动更新不中断） 3 副本 Deployment 滚动更新，maxUnavailable=25%，更新期间最少 2 个 Pod 可用，服务不中断。

答案：正确（✓） 解析：maxUnavailable=25% 表示最多低于期望 25%，3 * 25% = 0.75，向下取整 = 1，最少保持 3 - 1 = 2 个 Pod 可用。配合 Service 负载均衡，服务不中断。

17-判断-017（★★ 知识点：K17-3 Service DNS 名） mysql.ctts.svc.cluster.local 是 K8s 集群内 MySQL Service 的 DNS 名格式。

答案：正确（✓） 解析：K8s Service DNS 名格式：..svc.cluster.local。mysql Service 在 ctts namespace，所以是 mysql.ctts.svc.cluster.local。集群内任意 Pod 都能解析此 DNS 名。

17-判断-018（★★ 知识点：K17-4 前端 Nginx） CTTS 前端 Nginx 可以配置反向代理，将 /api 请求转发到后端 Service。

答案：正确（✓） 解析：前端 Nginx 配置 location /api { proxy_pass http://ctts-backend.ctts.svc.cluster.local:8080; }，将 /api 请求反向代理到后端 Service。这样浏览器同域访问，避免 CORS 跨域问题。

17-判断-019（★★ 知识点：K17-5 --record） kubectl set image 加 --record 参数会把变更原因记录到 rollout history 的 CHANGE-CAUSE 列。

答案：正确（✓） 解析：--record 把执行的 kubectl 命令记录到 history 的 CHANGE-CAUSE 列，便于追溯版本变更原因。建议每次 set image 都加 --record。

17-判断-020（★★ 知识点：K17-6 OOMKilled） Pod OOMKilled 是因为容器内存使用超过 limits.memory 被内核杀掉。

答案：正确（✓） 解析：OOMKilled（Out Of Memory Killed）表示容器内存使用超过 limits.memory，被内核 OOM Killer 杀掉。解决：增大 limits.memory 或优化应用内存使用。kubectl describe pod 的 Last State Reason 显示 OOMKilled。
