一、选择题（共 40 题，每题 2 分）

1.1 单项选择题（30 题）

18-选择-001（★ 知识点：K18-1 Service 概念） K8s 中 Service 主要解决 Pod 的什么问题？

  • APod 资源不足
  • BPod IP 不固定、会重建、需要负载均衡
  • CPod 镜像拉取失败
  • DPod 配置文件管理

答案：B 解析：Pod IP 每次重建都变、Pod 会因滚动更新或崩溃而重建、多副本 Pod 需要负载均衡。Service 提供稳定 IP + DNS 名 + 负载均衡解决这三个问题。A、C、D 不是 Service 解决的问题。

18-选择-002（★ 知识点：K18-1 Service 作用） 关于 Service 提供的能力，下列说法不正确的是？

  • A稳定的 IP 地址（ClusterIP）
  • B稳定的 DNS 名
  • C镜像构建与分发
  • D负载均衡到后端 Pod

答案：C 解析：Service 提供稳定 IP（ClusterIP）、稳定 DNS 名、负载均衡三大能力。镜像构建与分发是 Docker/镜像仓库的职责，与 Service 无关。

18-选择-003（★ 知识点：K18-2 Service 类型） K8s Service 的默认类型是？

  • ANodePort
  • BLoadBalancer
  • CClusterIP
  • DExternalName

答案：C 解析：Service 默认类型是 ClusterIP，YAML 中 spec.type 省略时即为 ClusterIP，只能在集群内部访问。

18-选择-004（★ 知识点：K18-2 Service 类型） 以下哪种 Service 类型可以在集群外部通过节点 IP:端口访问？

  • AClusterIP
  • BNodePort
  • CExternalName
  • DHeadless

答案：B 解析：NodePort 在每个节点开放一个端口（默认 30000-32767），外部可通过节点 IP:nodePort 访问。ClusterIP 仅集群内；ExternalName 是 CNAME 映射；Headless 无 ClusterIP。

18-选择-005（★ 知识点：K18-2 Service 类型） 在云厂商 K8s 集群（如阿里云 ACK）上，对外暴露 Web 服务最合适的 Service 类型是？

  • AClusterIP
  • BNodePort
  • CLoadBalancer
  • DExternalName

答案：C 解析：云厂商 K8s 支持 LoadBalancer 类型，会自动创建云负载均衡器（如 SLB/ELB）并分配公网 IP，适合云生产环境对外暴露。NodePort 端口范围受限不优雅；ClusterIP 仅内部；ExternalName 是对接外部服务。

18-选择-006（★ 知识点：K18-3 YAML 结构） Service 的 apiVersion 是？

  • Aapps/v1
  • Bv1
  • Cextensions/v1beta1
  • Dnetworking.k8s.io/v1

答案：B 解析：Service 的 apiVersion 是 v1（与 Pod 一样）。apps/v1 是 Deployment；networking.k8s.io/v1 是 Ingress。这是 Service YAML 最易写错的字段。

18-选择-007（★ 知识点：K18-3 YAML 结构） Service YAML 中，spec.ports.targetPort 指的是？

  • AService 对外的端口
  • BPod 的端口（containerPort）
  • C节点端口
  • D集群外部端口

答案：B 解析：targetPort 是 Pod 的端口（与 containerPort 一致），流量最终到此端口。port 是 Service 端口（ClusterIP 上访问的端口）；nodePort 是节点端口（仅 NodePort/LoadBalancer 类型）。

18-选择-008（★ 知识点：K18-3 YAML 结构） NodePort 类型的 Service，nodePort 字段省略时会怎样？

  • AService 创建失败
  • BK8s 自动分配 30000-32767 范围内的端口
  • C使用 80 端口
  • D使用 443 端口

答案：B 解析：NodePort 类型省略 nodePort 字段时，K8s 自动从 30000-32767 范围内分配一个端口。生产中通常显式指定避免端口随机变化。

18-选择-009（★ 知识点：K18-4 Endpoints） Service 的 Endpoints 是什么？

  • AService 的 ClusterIP
  • BService 的 DNS 名
  • C后端 Pod 的 IP:端口列表
  • DService 的 nodePort

答案：C 解析：Endpoints 是 Service 关联的后端 Pod IP:端口列表，由 K8s EndpointsController 根据 Service 的 selector 自动维护。Service 把流量转发到 Endpoints 里的 Pod。

18-选择-010（★ 知识点：K18-4 Endpoints） 查看 Service 后端 Pod 列表的命令是？

  • Akubectl get pods
  • Bkubectl get svc
  • Ckubectl get endpoints
  • Dkubectl describe deployment

答案：C 解析：kubectl get endpoints（或简写 kubectl get ep）查看 Endpoints 资源，显示每个 Service 关联的后端 Pod IP:端口列表。kubectl get svc 只看 Service 基本信息；kubectl describe svc 也能看 Endpoints 但不直观。

18-选择-011（★ 知识点：K18-4 Endpoints） 关于 Endpoints，下列说法正确的是？

  • AEndpoints 需要手动维护
  • B只有 Ready 的 Pod 才会出现在 Endpoints 中
  • CPod 删除后仍会保留在 Endpoints 中
  • DEndpoints 与 Service 是同一资源

答案：B 解析：Endpoints 由 EndpointsController 自动维护（A 错）；只有 Ready 的 Pod 才在 Endpoints 中（NotReady 的会被移除）；Pod 删除后从 Endpoints 移除（C 错）；Endpoints 与 Service 是两个独立资源（D 错）。

18-选择-012（★ 知识点：K18-5 DNS 服务发现） K8s 集群中负责 DNS 服务发现的组件是？

  • Akube-proxy
  • Bkubelet
  • CCoreDNS
  • Detcd

答案：C 解析：CoreDNS 是 K8s 集群内置的 DNS 服务器（部署在 kube-system namespace），为每个 Service 自动创建 DNS 记录，实现服务发现。kube-proxy 负责流量转发；kubelet 管理 Pod 生命周期；etcd 是 K8s 数据存储。

18-选择-013（★ 知识点：K18-5 DNS 服务发现） ctts namespace 下的 mysql Service 的完整 DNS 名是？

  • Amysql.cluster.local
  • Bmysql.ctts.cluster.local
  • Cmysql.ctts.svc.cluster.local
  • Dmysql.svc.ctts.cluster.local

答案：C 解析：Service DNS 名格式为 <service-name>.<namespace>.svc.cluster.local。mysql Service 在 ctts namespace，完整 DNS 名为 mysql.ctts.svc.cluster.local。

18-选择-014（★ 知识点：K18-5 DNS 服务发现） 同 namespace 内，Pod 访问 Service 的最简写法是？

  • A完整 FQDN（service-name.namespace.svc.cluster.local）
  • Bservice-name.namespace
  • Cservice-name
  • DClusterIP

答案：C 解析：同 namespace 内直接用 Service 名（如 mysql）即可，CoreDNS 会通过 /etc/resolv.conf 的 search 后缀自动补全为完整 FQDN。跨 namespace 才需要 <service-name>.<namespace>。

18-选择-015（★ 知识点：K18-1 Service 价值） Pod 重建后 IP 变化，依赖该 Pod 的 Service 会怎样？

  • AService 失效，需要重建
  • BService 的 ClusterIP 变化
  • CService 的 DNS 名变化
  • DService 自动通过 Endpoints 感知新 Pod，无需任何操作

答案：D 解析：Service 独立于 Pod，Pod 重建后 EndpointsController 自动更新 Endpoints，把新 Pod IP 加入，Service 继续工作。Service 的 ClusterIP 和 DNS 名都不变。

18-选择-016（★★ 知识点：K18-2 Service 类型） 关于 ExternalName 类型 Service，下列说法正确的是？

  • A有 ClusterIP 和 Endpoints
  • B通过 DNS CNAME 映射到外部域名
  • C用于暴露集群内服务到外部
  • D必须配置 selector

答案：B 解析：ExternalName 类型通过 DNS CNAME 把 Service 名映射到外部域名，无 ClusterIP、无 Endpoints、无 selector。用于集群内应用通过 Service 名访问外部服务（如 RDS）。

18-选择-017（★★ 知识点：K18-3 selector） Service 的 selector 与 Pod labels 的关系是？

  • Aselector 的所有 key=value 必须在 Pod labels 中都存在
  • BPod labels 的所有 key=value 必须在 selector 中都存在
  • C二者必须完全相同
  • D无关联

答案：A 解析：selector 是 Pod labels 的"子集匹配"——selector 里的所有 key=value 都必须在 Pod labels 里存在，Pod labels 可以有额外的 label。即 selector 是"包含"关系，不是"相等"关系。

18-选择-018（★★ 知识点：K18-4 Endpoints 排查） Service 创建成功但访问不通，发现 Endpoints 为空（<none>），可能原因是？

  • Aselector 写错，没有匹配的 Pod
  • BPod 状态为 Running 但 readinessProbe 未通过
  • CPod 在不同 namespace
  • D以上都可能

答案：D 解析：Endpoints 为空的常见原因：① selector 写错匹配不到 Pod；② Pod NotReady（readinessProbe 没通过）；③ Pod 在不同 namespace（Service 只选同 namespace 的 Pod）。三种都可能。

18-选择-019（★★ 知识点：K18-5 DNS 服务发现） 跨 namespace 访问 Service，正确的写法是？

  • Aservice-name
  • Bservice-name.namespace
  • Cservice-name.svc
  • Dservice-name.cluster.local

答案：B 解析：跨 namespace 访问 Service 必须带 namespace 名，写法为 <service-name>.<namespace>，CoreDNS 会补全为完整 FQDN。同 namespace 才能省略 namespace。

18-选择-020（★★ 知识点：K18-2 Service 类型） 在 Minikube 上创建 LoadBalancer 类型的 Service，EXTERNAL-IP 会显示什么？

  • A立即分配公网 IP
  • B一直显示 <pending>
  • C显示 minikube IP
  • D报错无法创建

答案：B 解析：Minikube 没有云厂商的 LB 控制器，无法创建云负载均衡器，EXTERNAL-IP 会一直显示 <pending>。可以用 minikube tunnel 模拟，但本质还是 NodePort。云厂商 K8s（ACK/ACK/TKE）才能正常创建 LB。

18-选择-021（★ 知识点：K18-3 YAML 字段） Service YAML 中，spec.ports.port 指的是？

  • AService 端口（ClusterIP 上访问的端口）
  • BPod 端口（containerPort）
  • C节点端口
  • D外部端口

答案：A 解析：port 是 Service 端口，即 ClusterIP 上访问的端口（如 mysql.ctts.svc.cluster.local:3306 中的 3306）。targetPort 是 Pod 端口；nodePort 是节点端口。

18-选择-022（★★ 知识点：K18-4 无选择器 Service） 关于无选择器 Service（无 selector 的 Service），下列说法正确的是？

  • AK8s 会自动创建 Endpoints
  • B需要手动创建同名的 Endpoints 指向外部 IP
  • C不能有 ports 配置
  • D必须用 ExternalName 类型

答案：B 解析：无 selector 的 Service 不会自动创建 Endpoints，需要手动创建同名的 Endpoints 资源，在 subsets.addresses 里指定外部 IP。用于集群内通过 Service DNS 名访问外部 IP 服务。可以配置 ports；类型可以是 ClusterIP（不是必须 ExternalName）。

18-选择-023（★ 知识点：K18-2 NodePort 范围） NodePort 类型的 Service，nodePort 默认端口范围是？

  • A1-1023
  • B1024-65535
  • C30000-32767
  • D8000-9000

答案：C 解析：NodePort 默认端口范围是 30000-32767，由 kube-apiserver 的 --service-node-port-range 参数控制。范围可改但不建议，保持默认便于运维。

18-选择-024（★★ 知识点：K18-4 Endpoints 更新） 当 Deployment 扩容（如 3 副本 → 5 副本）时，关联 Service 的 Endpoints 会怎样？

  • A需要手动更新 Endpoints
  • BEndpointsController 自动加入新 Ready Pod 的 IP
  • CService 需要重建
  • DEndpoints 不变

答案：B 解析：EndpointsController 自动监听 Pod 变化，新 Pod Ready 后自动加入 Endpoints，删除的 Pod 自动移除。无需手动操作，Service 也无需重建。

18-选择-025（★ 知识点：K18-5 CoreDNS） CoreDNS 部署在哪个 namespace？

  • Adefault
  • Bkube-system
  • Ckube-public
  • Dctts

答案：B 解析：CoreDNS 部署在 kube-system namespace，Service 名为 kube-dns（IP 通常为 10.96.0.10）。所有 Pod 的 /etc/resolv.conf 自动指向 kube-dns Service IP。

18-选择-026（★★ 知识点：K18-3 多端口） 一个 Service 暴露多个端口（如 80 和 443）时，YAML 中 ports 字段的每个端口必须配置什么？

  • AnodePort
  • BtargetPort
  • Cname
  • Dprotocol

答案：C 解析：多端口 Service 必须为每个端口命名（name: http / name: https），否则 K8s 报错。单端口时 name 可省略。

18-选择-027（★★ 知识点：K18-2 类型对比） 以下哪种 Service 类型没有 ClusterIP？

  • AClusterIP
  • BNodePort
  • CLoadBalancer
  • DExternalName

答案：D 解析：ExternalName 类型无 ClusterIP、无 Endpoints，只是 DNS CNAME 映射。ClusterIP/NodePort/LoadBalancer 都有 ClusterIP（NodePort 和 LoadBalancer 在 ClusterIP 基础上扩展）。

18-选择-028（★★ 知识点：K18-4 Endpoints 与 Pod 状态） Pod 状态为 Running 但 readinessProbe 未通过，该 Pod 是否在 Service 的 Endpoints 中？

  • A在
  • B不在
  • C取决于 Pod 类型
  • D取决于 Service 类型

答案：B 解析：只有 Ready 的 Pod 才在 Endpoints 中。Pod Running 但 readinessProbe 未通过表示 Pod 还没就绪，EndpointsController 会将其标记为 NotReady 并从 Endpoints 中移除，Service 不会把流量发给它。这是就绪探针控制 Pod 是否收流量的机制。

18-选择-029（★★ 知识点：K18-6 CTTS Service） 在 CTTS 项目中，mysql Service 应该用什么类型？

  • ANodePort
  • BLoadBalancer
  • CClusterIP
  • DExternalName

答案：C 解析：mysql Service 仅后端 Pod 需要访问，不需要对外暴露，应使用 ClusterIP（最小暴露原则）。数据库对外暴露会增大攻击面。NodePort/LoadBalancer 用于对外；ExternalName 用于对接外部服务。

18-选择-030（★★ 知识点：K18-6 CTTS 通信） 在 CTTS 项目中，后端 Pod 连接 MySQL 应该使用的地址是？

  • AMySQL Pod 的 IP
  • Bmysql Service 的 ClusterIP
  • Cmysql.ctts.svc.cluster.local（DNS 名）
  • Dminikube 的 IP

答案：C 解析：生产环境一律用 Service DNS 名（mysql.ctts.svc.cluster.local），稳定可读，Pod IP 和 ClusterIP 都可能在环境迁移时变化。同 namespace 内可简写为 mysql。

1.2 多项选择题（10 题）

18-选择-031（★★ 知识点：K18-1 Service 作用） Service 提供的能力包括？（多选）

  • A稳定的 ClusterIP
  • B稳定的 DNS 名
  • C负载均衡到后端 Pod
  • DPod 副本数管理 E. 镜像构建

答案：A、B、C 解析：Service 提供稳定 ClusterIP（A）、稳定 DNS 名（B）、负载均衡（C）三大能力。D 是 Deployment 的职责；E 是 Docker 的职责。

18-选择-032（★★ 知识点：K18-2 Service 类型） 以下哪些 Service 类型有 ClusterIP？（多选）

  • AClusterIP
  • BNodePort
  • CLoadBalancer
  • DExternalName E. Headless（clusterIP: None）

答案：A、B、C 解析：ClusterIP/NodePort/LoadBalancer 都有 ClusterIP（NodePort 和 LoadBalancer 在 ClusterIP 基础上扩展）。ExternalName 无 ClusterIP（D 错）；Headless Service 显式设 clusterIP: None，也无 ClusterIP（E 错）。

18-选择-033（★★ 知识点：K18-3 YAML 结构） Service YAML 中 spec.ports 字段可以配置的子字段包括？（多选）

  • Aport
  • BtargetPort
  • CnodePort
  • DcontainerPort E. name

答案：A、B、C、E 解析：Service 的 ports 可配置 port（Service 端口）、targetPort（Pod 端口）、nodePort（节点端口，仅 NodePort/LoadBalancer）、name（端口名，多端口时必须）、protocol（协议）。D 错，containerPort 是 Pod YAML 的字段，不是 Service 的。

18-选择-034（★★ 知识点：K18-4 Endpoints） 关于 Endpoints，下列说法正确的有？（多选）

  • AEndpoints 是独立的 K8s 资源
  • BEndpointsController 自动维护 Endpoints
  • C只有 Ready 的 Pod 才在 Endpoints 中
  • DEndpoints 必须手动创建 E. Pod 变化时 Endpoints 自动更新

答案：A、B、C、E 解析：Endpoints 是独立资源（A）；由 EndpointsController 自动维护（B）；只有 Ready 的 Pod 才在 Endpoints（C）；Pod 变化时自动更新（E）。D 错，有 selector 的 Service 自动创建 Endpoints，只有无选择器 Service 才需手动创建。

18-选择-035（★★ 知识点：K18-5 DNS 服务发现） 关于 K8s DNS 服务发现，下列说法正确的有？（多选）

  • ACoreDNS 为每个 Service 自动创建 DNS 记录
  • BPod 内 /etc/resolv.conf 自动配置 nameserver 指向 CoreDNS
  • C同 namespace 内可以直接用 Service 名访问
  • D跨 namespace 必须带 namespace 名 E. Service DNS 名解析返回的是后端 Pod IP

答案：A、B、C、D 解析：CoreDNS 自动创建 DNS 记录（A）；Pod 的 resolv.conf 自动配置（B）；同 namespace 简写 Service 名（C）；跨 namespace 带 namespace 名（D）。E 错，普通 Service（ClusterIP）DNS 解析返回 Service ClusterIP，再由 kube-proxy 转发到 Pod；Headless Service 才直接返回 Pod IP。

18-选择-036（★★ 知识点：K18-2 类型选型） 下列场景中，适合用 ClusterIP 类型的有？（多选）

  • A后端 Pod 访问 MySQL 数据库
  • B前端 Pod 反向代理到后端 API
  • C开发测试时从外部浏览器访问前端
  • D云生产环境对外暴露 Web 服务 E. 集群内微服务间相互调用

答案：A、B、E 解析：A、B、E 都是集群内部通信，适合 ClusterIP。C 临时对外用 NodePort 或 port-forward；D 云生产对外用 LoadBalancer 或 Ingress。

18-选择-037（★★ 知识点：K18-3 selector） 关于 Service selector，下列说法正确的有？（多选）

  • Aselector 必须与 Pod labels 匹配才能关联 Pod
  • Bselector 是 Pod labels 的"子集匹配"
  • CPod labels 可以有 selector 之外的额外 label
  • D一个 Service 只能选一个 Deployment 的 Pod E. selector 写错会导致 Endpoints 为空

答案：A、B、C、E 解析：selector 必须匹配 Pod labels（A）；是子集匹配（selector 的所有 key=value 在 Pod labels 里）（B）；Pod labels 可以有额外 label（C）；selector 写错 Endpoints 为空（E）。D 错，一个 Service 可以选多个 Deployment 的 Pod，只要标签匹配。

18-选择-038（★★ 知识点：K18-4 Endpoints 排查） Service 创建成功但 Endpoints 为空，可能的原因有？（多选）

  • Aselector 与 Pod labels 不匹配
  • BPod 状态为 NotReady（readinessProbe 未通过）
  • CPod 在不同 namespace
  • DService 的 type 设置错误 E. 没有匹配的 Pod

答案：A、B、C、E 解析：A、B、C、E 都会导致 Endpoints 为空。D 错，type 设置不影响 Endpoints（type 只影响访问方式，不影响 selector 关联 Pod）。

18-选择-039（★★ 知识点：K18-6 CTTS Service） 在 CTTS 项目中，三个 Service 都用 ClusterIP 类型的原因包括？（多选）

二、判断题（共 20 题，每题 1 分）

18-判断-001（★ 知识点：K18-1 Service 概念） Service 的 ClusterIP 类型只能在集群内部访问，外部无法直接访问。

答案：正确（✓） 解析：ClusterIP 类型分配的虚拟 IP 只在集群内可路由，外部无法直接访问。对外暴露需用 NodePort/LoadBalancer/Ingress。

18-判断-002（★ 知识点：K18-1 Service 价值） Pod 重建后 IP 变化，依赖该 Pod 的 Service 也会失效需要重建。

答案：错误（✗） 解析：Service 独立于 Pod，Pod 重建后 EndpointsController 自动更新 Endpoints，把新 Pod IP 加入。Service 的 ClusterIP 和 DNS 名都不变，无需重建。

18-判断-003（★ 知识点：K18-3 selector） Service 通过 selector 关联 Pod，selector 必须与 Pod 的 labels 匹配。

答案：正确（✓） 解析：Service 的 selector 必须是 Pod labels 的子集（selector 的所有 key=value 在 Pod labels 里都存在），才能关联到 Pod。

18-判断-004（★ 知识点：K18-2 NodePort） NodePort 类型的 Service 会占用每个节点的一个端口（默认 30000-32767）对外暴露。

答案：正确（✓） 解析：NodePort 在每个节点上开放一个端口（nodePort，默认 30000-32767），外部可通过任意节点 IP:nodePort 访问。

18-判断-005（★ 知识点：K18-3 apiVersion） Service 的 apiVersion 是 apps/v1。

答案：错误（✗） 解析：Service 的 apiVersion 是 v1（与 Pod 一样），不是 apps/v1（那是 Deployment）。这是 Service YAML 最易写错的字段。

18-判断-006（★ 知识点：K18-5 DNS 服务发现） 同 namespace 内，Pod 可以直接用 Service 名访问 Service，无需写完整 DNS 名。

答案：正确（✓） 解析：CoreDNS 通过 Pod 的 /etc/resolv.conf 的 search 后缀自动补全。同 namespace 内写 mysql 即可，CoreDNS 自动补全为 mysql.ctts.svc.cluster.local。

18-判断-007（★ 知识点：K18-4 Endpoints） Endpoints 是 Service 的后端 Pod IP:端口列表，由 K8s 自动维护。

答案：正确（✓） 解析：Endpoints 由 EndpointsController 根据 Service 的 selector 自动维护，包含匹配且 Ready 的 Pod IP:targetPort。Pod 变化时自动更新。

18-判断-008（★★ 知识点：K18-2 LoadBalancer） Minikube 上创建 LoadBalancer 类型的 Service 会立即分配公网 IP。

答案：错误（✗） 解析：Minikube 没有云厂商 LB 控制器，无法创建云负载均衡器，EXTERNAL-IP 一直显示 <pending>。只有云厂商 K8s（ACK/ACK/TKE）才能正常创建 LB 并分配公网 IP。

18-判断-009（★ 知识点：K18-2 ExternalName） ExternalName 类型的 Service 有 ClusterIP 和 Endpoints。

答案：错误（✗） 解析：ExternalName 类型无 ClusterIP、无 Endpoints，只是 DNS CNAME 映射到外部域名。用于集群内应用通过 Service 名访问外部服务。

18-判断-010（★★ 知识点：K18-4 Endpoints 状态） Pod 状态为 Running 但 readinessProbe 未通过，该 Pod 仍在 Service 的 Endpoints 中。

答案：错误（✗） 解析：只有 Ready 的 Pod 才在 Endpoints 中。Pod Running 但 readinessProbe 未通过表示 NotReady，会从 Endpoints 中移除，Service 不会把流量发给它。

18-判断-011（★ 知识点：K18-5 CoreDNS） CoreDNS 是 K8s 集群内置的 DNS 服务器，部署在 kube-system namespace。

答案：正确（✓） 解析：CoreDNS 部署在 kube-system namespace，Service 名为 kube-dns（IP 通常为 10.96.0.10）。为每个 Service 自动创建 DNS 记录。

18-判断-012（★★ 知识点：K18-3 targetPort） Service 的 targetPort 必须等于 Pod 的 containerPort，否则流量到不了 Pod。

答案：正确（✓） 解析：targetPort 是流量最终到达的 Pod 端口，必须与 Pod 的 containerPort 一致。如果不一致，流量到不了 Pod 的应用进程。

18-判断-013（★ 知识点：K18-5 跨 namespace） 跨 namespace 访问 Service 必须带 namespace 名（如 mysql.ctts）。

答案：正确（✓） 解析：跨 namespace 访问必须用 <service-name>.<namespace>，CoreDNS 才能正确解析。同 namespace 才能省略 namespace 名。

18-判断-014（★★ 知识点：K18-4 无选择器 Service） 无 selector 的 Service 会自动创建 Endpoints。

答案：错误（✗） 解析：无 selector 的 Service 不会自动创建 Endpoints（因为没有 selector 就不知道选哪些 Pod）。需要手动创建同名的 Endpoints 资源，在 subsets.addresses 里指定外部 IP。

18-判断-015（★ 知识点：K18-2 类型层次） NodePort 类型在 ClusterIP 基础上扩展，仍然有 ClusterIP。

答案：正确（✓） 解析：NodePort 在 ClusterIP 基础上扩展节点端口，仍然有 ClusterIP，集群内仍可通过 ClusterIP 访问。LoadBalancer 同理。

18-判断-016（★★ 知识点：K18-1 ClusterIP 特性） Service 的 ClusterIP 是虚拟 IP，能 ping 通。

答案：错误（✗） 解析：ClusterIP 是虚拟 IP（Virtual IP），不绑定任何网络接口，ping（ICMP）没有响应。但 curl/TCP 请求可以访问，因为 kube-proxy 通过 iptables/IPVS 规则把发往 ClusterIP 的流量 DNAT 转发到后端 Pod。

18-判断-017（★★ 知识点：K18-3 多端口） 一个 Service 可以暴露多个端口（如 80 和 443），但每个端口必须命名。

答案：正确（✓） 解析：多端口 Service 必须为每个端口命名（name: http / name: https），否则 K8s 报错。单端口时 name 可省略。

18-判断-018（★ 知识点：K18-6 CTTS Service） 在 CTTS 项目中，mysql Service 应该用 ClusterIP 类型，不对外暴露。

答案：正确（✓） 解析：mysql Service 仅后端 Pod 需要访问，不需要对外暴露。用 ClusterIP 遵循"最小暴露原则"，避免增大攻击面。

18-判断-019（★★ 知识点：K18-4 Endpoints 命令） kubectl get endpoints 命令可以查看每个 Service 关联的后端 Pod IP:端口列表。

答案：正确（✓） 解析：kubectl get endpoints（或 kubectl get ep）查看 Endpoints 资源，显示每个 Service 关联的后端 Pod IP:端口列表，是排查 Service 问题的重要命令。

18-判断-020（★★ 知识点：K18-5 DNS 解析） 普通 Service（ClusterIP 类型）的 DNS 名解析返回的是后端 Pod IP 列表。

答案：错误（✗） 解析：普通 Service（ClusterIP）DNS 解析返回 Service 的 ClusterIP，再由 kube-proxy 转发到后端 Pod。Headless Service（clusterIP: None）才直接返回后端 Pod IP 列表。

四、论述题/简答题（共 4 题）

18-论述-001（★★ 知识点：K18-1 Service 概念，10 分） 请阐述 K8s 为什么需要 Service？从 Pod 的三个不稳定特征说明，并说明 Service 如何解决这些问题。

参考答案与评分标准（10 分，按要点给分）：

  1. Pod IP 不固定（2 分）：Pod 每次重建，IP 都由 CNI 插件重新分配（如 10.244.1.5 → 10.244.1.8）。如果调用方写死 Pod IP，Pod 重建后就连不上。Service 提供稳定的 ClusterIP，调用方只需记住 Service IP，不关心 Pod IP。
  2. Pod 会重建（2 分）：Deployment 滚动更新、Pod 崩溃自动重启、节点故障重新调度都会导致 Pod 生灭。调用方不能依赖"某个 Pod"。Service 独立于 Pod，通过 Endpoints 自动跟踪 Pod 变化，Pod 重建对调用方透明。
  3. 一组 Pod 需要负载均衡（2 分）：Deployment 3 副本，调用方请求来了应该分发给哪个 Pod？Service 提供负载均衡（默认轮询），把请求分发到所有 Ready 的后端 Pod，避免单点过载。
  4. Service 的三大能力（4 分）：
    • 稳定 IP（ClusterIP）：Service 创建时分配集群内固定 IP，生命周期内不变（1 分）
    • 稳定 DNS 名：CoreDNS 为 Service 自动创建 DNS 记录（service-name.namespace.svc.cluster.local），调用方用 DNS 名访问更友好（1.5 分）
    • 负载均衡：Service 通过 Endpoints 跟踪后端 Pod，kube-proxy 在节点上配置 iptables/IPVS 规则，把发往 ClusterIP 的流量负载均衡到后端 Pod（1.5 分）

评分要点：三个不稳定特征各 2 分；三大能力 4 分。要点完整给满分，只列项不解释每个给 1 分。

18-论述-002（★★ 知识点：K18-2 Service 类型，10 分） 请对比 Service 的四种类型（ClusterIP / NodePort / LoadBalancer / ExternalName），说明各自的访问范围、关键特征和适用场景。

参考答案与评分标准（10 分，按要点给分）：

  1. ClusterIP（2.5 分）：
    • 访问范围：集群内部（0.5 分）
    • 关键特征：分配集群内虚拟 IP（ClusterIP），只能在集群内访问（1 分）
    • 适用场景：内部服务间通信（如后端访问数据库、前端访问后端 API）（1 分）
  2. NodePort（2.5 分）：
    • 访问范围：集群外部（节点端口）（0.5 分）
    • 关键特征：在每个节点开放一个端口（nodePort，默认 30000-32767），外部可通过节点 IP:nodePort 访问；仍有 ClusterIP（1 分）
    • 适用场景：临时对外调试、非云环境对外暴露（1 分）
  3. LoadBalancer（2.5 分）：
    • 访问范围：集群外部（云负载均衡）（0.5 分）
    • 关键特征：在 NodePort 基础上，云厂商自动创建云负载均衡器（如 SLB/ELB）并分配公网 IP；仅在云厂商 K8s 生效（1 分）
    • 适用场景：云生产环境对外暴露服务（1 分）
  4. ExternalName（2.5 分）：
    • 访问范围：集群内部访问外部（0.5 分）
    • 关键特征：无 ClusterIP、无 Endpoints，通过 DNS CNAME 把 Service 名映射到外部域名（1 分）
    • 适用场景：集群内应用访问外部已有服务（如 RDS、外部 API）（1 分）

评分要点：四种类型各 2.5 分（访问范围 0.5 + 特征 1 + 场景 1）。要点完整给满分。

18-论述-003（★★ 知识点：K18-4 Endpoints，8 分） 请说明 Endpoints 是什么、如何自动维护、以及 Service 创建后 Endpoints 为空的排查方法。

参考答案与评分标准（8 分，按要点给分）：

  1. Endpoints 是什么（2 分）：Endpoints 是 Service 的后端 Pod IP:端口列表，是独立的 K8s 资源。Service 把流量转发到 Endpoints 里的 Pod。用 kubectl get endpoints 查看。
  2. 如何自动维护（3 分）：
    • EndpointsController 监听 Pod 变化（1 分）
    • Pod 新建并 Ready → 自动加入 Endpoints；Pod 删除或 NotReady → 自动移除（1 分）
    • 只有 Ready 的 Pod 才在 Endpoints 中（readinessProbe 未通过的 Pod 不在 Endpoints）（1 分）
  3. Endpoints 为空的排查方法（3 分）：
    • 第一步：kubectl describe svc <name> 查看 Selector（0.5 分）
    • 第二步：kubectl get pods -l <selector> 确认是否有匹配的 Pod（0.5 分）
    • 第三步：kubectl get pods -l <selector> 确认 Pod 是否 Ready（0.5 分）
    • 常见根因：① selector 写错匹配不到 Pod；② Pod NotReady（readinessProbe 未通过）；③ Pod 在不同 namespace（Service 只选同 namespace 的 Pod）（1.5 分）

评分要点：三部分各自独立给分；要点齐全即可满分。

  2. 三个 Service 的 selector 和端口应该怎么设计？

6. 解决方案：修改 Service 的 (f)________，让其与 Pod labels 匹配（app=ctts-api），或修改 Deployment 的 Pod labels 为 app=ctts-backend。

参考答案： (a) get (b) <none>（或 空 / none） (c) describe (d) app=ctts-backend (e) selector（或 Service selector） (f) selector

解析：kubectl get endpoints 查看 Endpoints；Endpoints 为空显示 <none>；kubectl describe svc 看 Selector；kubectl get pods -l <selector> 查找匹配 Pod；selector 与 Pod labels 不匹配是 Endpoints 为空的常见根因；修改 Service selector 或 Pod labels 让二者匹配。

18-编程-002（★★★ 知识点：K18-2、K18-3、K18-6 综合应用，20 分） Service 综合设计与排查：某团队在 Minikube 上部署 CTTS 项目，遇到以下问题。请回答：

团队部署情况：
- ctts namespace 下有三个 Deployment：
  - ctts-mysql（1 副本，containerPort 3306，Pod labels: app=ctts-mysql, tier=database）
  - ctts-backend（3 副本，containerPort 8080，Pod labels: app=ctts-backend, tier=backend）
  - ctts-frontend（2 副本，containerPort 80，Pod labels: app=ctts-frontend, tier=frontend）

团队创建了三个 Service：
  - mysql（ClusterIP, selector: app=ctts-mysql, port: 3306, targetPort: 3306）
  - ctts-backend（ClusterIP, selector: app=ctts-backend, port: 8080, targetPort: 8080）
  - ctts-frontend（ClusterIP, selector: app=ctts-frontend, port: 80, targetPort: 80）

问题：
1. 后端 Pod 通过 mysql.ctts.svc.cluster.local:3306 访问 MySQL，但连接失败。
   kubectl get endpoints mysql -n ctts 显示 ENDPOINTS: 10.244.1.5:3306（有 IP）。
   请列出至少 2 种可能的原因和排查方法。（6分）

2. 团队想从宿主机浏览器访问前端页面，试了 curl http://ctts-frontend.ctts.svc.cluster.local
   失败。请说明原因，并给出两种正确的访问方式。（6分）

3. 团队考虑把 ctts-frontend Service 改为 NodePort 类型对外暴露。
   请写出修改后的 YAML 关键部分（type、ports 部分），并说明这种方式的优缺点。（5分）

4. 团队最终决定保持 ctts-frontend 为 ClusterIP，理由是什么？（3分）

参考答案与评分标准（20 分）：

1. 后端连不上 MySQL 的可能原因与排查（6分，每种 3 分，答出 2 种即满分）：

  • 原因 1：MySQL Pod 启动慢，readinessProbe 未通过。虽然 Endpoints 有 IP，但可能 Pod 还在初始化。排查：kubectl get pod -l app=ctts-mysql -n ctts 看 READY 列是否 1/1；kubectl logs deployment/ctts-mysql -n ctts 看是否 "ready for connections"。
  • 原因 2：MySQL 用户权限或密码错误。后端环境变量 DB_USER/DB_PASSWORD 与 MySQL 配置不一致。排查：kubectl exec -it deployment/ctts-backend -n ctts -- env | grep DB_ 看环境变量；kubectl exec -it deployment/ctts-mysql -n ctts -- mysql -uroot -p -e "SELECT user,host FROM mysql.user" 看用户。
  • 原因 3：MySQL Pod 内 MySQL 服务未监听 3306 或监听地址不对。排查：kubectl exec -it deployment/ctts-mysql -n ctts -- netstat -tlnp | grep 3306 看监听端口。

2. 宿主机访问前端失败的原因与正确方式（6分）：

  • 原因（2分）：ctts-frontend.ctts.svc.cluster.local 是集群内部 DNS 名，宿主机不在集群内，无法解析（宿主机的 DNS 不是 CoreDNS）。且 ClusterIP 类型只能在集群内访问。
  • 正确方式 1（2分）：kubectl port-forward svc/ctts-frontend 8081:80 -n ctts，然后浏览器访问 http://localhost:8081。这是临时调试最简单的方式。
  • 正确方式 2（2分）：将 ctts-frontend Service 改为 NodePort 类型，然后浏览器访问 http://<minikube-ip>:<nodePort>（如 http://192.168.49.2:30080）。

3. 改为 NodePort 的 YAML 与优缺点（5分）：

  • YAML 关键部分（3分）：
spec:
  type: NodePort
  selector:
    app: ctts-frontend
  ports:
  - name: http
    port: 80
    targetPort: 80
    nodePort: 30080           # 节点端口，30000-32767
    protocol: TCP
  • 优点（1分）：配置简单，Minikube/本地环境直接可用，外部可访问。
  • 缺点（1分）：端口范围受限（30000-32767，用户要带端口号）；暴露节点 IP 不优雅（节点 IP 可能变化、多节点 IP 不一致）；不适合生产环境（生产用 Ingress 或 LoadBalancer）。

4. 保持 ClusterIP 的理由（3分）：

  • 最小暴露原则：内部服务不必要时不对外暴露，减小攻击面（1分）
  • 生产环境对外访问统一用 Ingress（七层路由、域名、HTTPS、路径分发），下节课学（1分）
  • ClusterIP 配置简单，临时调试用 port-forward 即可，不影响 Service 配置（1分）

评分要点：各小题独立给分；原因/方案合理即可，不要求与答案完全一致；YAML 关键字段（type、nodePort、port、targetPort）必须正确。
