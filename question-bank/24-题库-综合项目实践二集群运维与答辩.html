24-单选-01 ★ 题目：Docker容器的核心技术基础是？

  • A
    虚拟机技术
  • B
    Linux内核的命名空间（Namespace）和控制组（cgroups）
  • C
    Java虚拟机
  • D
    操作系统快照

答案：B 解析：Docker容器不是虚拟机，而是基于Linux内核的Namespace（实现资源隔离）和cgroups（实现资源限制）技术。Namespace提供PID、网络、挂载、UTS、IPC、用户等隔离，cgroups提供CPU、内存、IO等资源限制。

24-单选-02 ★ 题目：以下哪个命令用于查看本地所有Docker镜像？

  • A
    docker ps
  • B
    docker images
  • C
    docker list
  • D
    docker show

答案：B 解析：docker images（或docker image ls）用于列出本地所有镜像。docker ps查看运行中的容器，docker ps -a查看所有容器（含停止）。

24-单选-03 ★ 题目：Dockerfile中，哪个指令用于设置容器的工作目录？

  • A
    RUN
  • B
    CMD
  • C
    WORKDIR
  • D
    ENV

答案：C 解析：WORKDIR指令用于设置工作目录，后续的RUN、CMD、ENTRYPOINT、COPY、ADD等指令都会在该目录下执行。如果目录不存在会自动创建。

24-单选-04 ★★ 题目：以下Dockerfile指令中，哪个会使镜像层数增加？

  • A
    FROM
  • B
    WORKDIR
  • C
    RUN apt-get update && apt-get install -y nginx
  • D
    ENV

答案：C 解析：RUN、COPY、ADD指令会创建新的镜像层。WORKDIR、ENV、LABEL等指令只修改镜像的元数据，不会创建新层。合并多个RUN命令可减少层数。

24-单选-05 ★★ 题目：多阶段构建的主要优势是？

  • A
    加快构建速度
  • B
    减小最终镜像体积
  • C
    支持并行构建
  • D
    自动优化镜像层

答案：B 解析：多阶段构建通过FROM ... AS stage定义多个构建阶段，最终镜像只包含最后阶段的内容，编译工具和中间产物不会进入最终镜像，从而大幅减小镜像体积。

24-单选-07 ★★ 题目：以下哪个K8s资源对象是最小的调度单元？

  • A
    Deployment
  • B
    Service
  • C
    Pod
  • D

24-单选-09 ★★ 题目：Service类型为ClusterIP的Service，其访问范围是？

24-单选-10 ★ 题目：K8s中用于存储敏感信息（如密码、密钥）的资源对象是？

24-单选-12 ★★ 题目：Deployment滚动更新时，默认的maxSurge和maxUnavailable值是？

24-单选-22 ★★ 题目：PV和PVC的关系是？

24-单选-23 ★★ 题目：以下哪个探针用于判断容器是否处于正常运行状态（失败会重启）？

  • A
    readinessProbe
  • B
    livenessProbe
  • C
    startupProbe
  • D
    lifecycle

答案：B 解析：livenessProbe（存活探针）判断容器是否健康运行，失败会重启容器。readinessProbe（就绪探针）判断容器是否 ready 接收流量，失败会从Service端点移除但不重启。startupProbe（启动探针）判断容器是否启动完成。

24-单选-25 ★★ 题目：RBAC中，Role和ClusterRole的区别是？

24-单选-30 ★★★ 题目：以下哪种情况会导致Pod一直处于Pending状态？

  • A
    容器启动失败
  • B
    节点资源不足，无法调度
  • C
    镜像拉取失败
  • D
    应用抛出异常

答案：B 解析：Pending状态表示Pod尚未被调度到节点。常见原因：节点资源不足（CPU/内存不满足requests）、节点污点不匹配、节点选择器不匹配、亲和性约束无法满足。容器启动失败、镜像拉取失败是Pod已调度后的状态（ImagePullBackOff/CrashLoopBackOff）。

24-多选-01 ★ 题目：以下哪些是Docker的核心组件？（多选）

  • A
    Docker Daemon
  • B
    Docker Client
  • C
    Docker Registry
  • D
    Docker Hub
  • E
    Kubernetes

答案：ABCD 解析：Docker核心组件包括Docker Daemon（守护进程）、Docker Client（客户端）、Docker Registry（镜像仓库）。Docker Hub是公共镜像仓库的实例。Kubernetes是独立的容器编排系统，不属于Docker组件。

24-多选-02 ★★ 题目：以下哪些Dockerfile指令会创建新的镜像层？（多选）

  • A
    FROM
  • B
    RUN
  • C
    COPY
  • D
    ADD
  • E
    ENV
  • F
    WORKDIR

答案：BCD 解析：RUN、COPY、ADD会创建新的镜像层。FROM是基础镜像，ENV、WORKDIR、LABEL等只修改镜像元数据，不创建新层。合并RUN命令可减少层数。

24-多选-03 ★★ 题目：K8s中，以下哪些资源对象属于工作负载（Workload）？（多选）

  • A
    Pod
  • B
    Deployment
  • C
    Service
  • D
    StatefulSet
  • E
    DaemonSet
  • F
    ConfigMap

答案：ABDE 解析：工作负载资源包括Pod、Deployment、StatefulSet、DaemonSet、Job、CronJob、ReplicaSet等，用于管理应用的运行。Service属于网络资源，ConfigMap属于配置资源。

24-多选-04 ★★ 题目：以下哪些是K8s Service的类型？（多选）

  • A
    ClusterIP
  • B
    NodePort
  • C
    LoadBalancer
  • D
    ExternalName
  • E
    Ingress

答案：ABCD 解析：Service的四种类型：ClusterIP（集群内访问）、NodePort（节点端口暴露）、LoadBalancer（云负载均衡）、ExternalName（CNAME别名）。Ingress是独立的资源对象，不属于Service类型。

24-多选-05 ★★ 题目：Pod出现CrashLoopBackOff，可能的原因有哪些？（多选）

  • A
    容器启动命令错误
  • B
    应用配置错误导致启动失败
  • C
    依赖服务未就绪
  • D
    存活探针配置过严
  • E
    节点NotReady

三、判断题（20题）

24-判断-01 ★ 题目：Docker容器启动比虚拟机快，因为容器共享宿主机内核，不需要启动完整的操作系统。 A. 正确 B. 错误

答案：A 解析：Docker容器基于Linux内核的Namespace和cgroups实现隔离，共享宿主机内核，不需要像虚拟机那样启动完整的操作系统，因此启动速度可达毫秒级。

24-判断-02 ★ 题目：Dockerfile中可以有多个CMD指令，只有最后一个生效。 A. 正确 B. 错误

答案：A 解析：Dockerfile中只能有一个CMD指令，如果有多个，只有最后一个生效。CMD提供容器启动默认命令，可被docker run参数覆盖。同理ENTRYPOINT也只生效最后一个。

24-判断-03 ★★ 题目：Docker镜像的每一层都是只读的，容器运行时的修改会写入可写层。 A. 正确 B. 错误

答案：A 解析：Docker镜像采用分层存储，每层只读。容器启动时在镜像顶部添加一个可写层（容器层），所有修改写入可写层。删除容器后可写层丢失，这也是数据持久化需要Volume的原因。

24-判断-04 ★ 题目：K8s中一个Pod只能包含一个容器。 A. 正确 B. 错误

答案：B 解析：一个Pod可以包含一个或多个容器。多容器Pod常用于sidecar模式（如主容器+日志收集容器）、适配器模式、大使模式。但通常一个Pod只运行一个主容器。

24-判断-05 ★★ 题目：Deployment滚动更新时，默认策略是先删旧Pod再建新Pod。 A. 正确 B. 错误

答案：B 解析：Deployment默认RollingUpdate策略是先建新Pod（受maxSurge控制），新Pod Ready后再删旧Pod（受maxUnavailable控制），实现零停机。Recreate策略才是先删后建。

24-判断-06 ★★ 题目：kubectl rollout undo可以回滚到任意历史版本。 A. 正确 B. 错误

答案：A 解析：kubectl rollout undo deployment/<name> --to-revision=N可回滚到指定revision版本。默认revision保留10个（可通过revisionHistoryLimit调整）。

24-判断-07 ★★ 题目：HPA自动扩缩容不需要任何前置条件，开箱即用。 A. 正确 B. 错误

答案：B 解析：HPA基于CPU/内存使用率自动伸缩，前提是集群安装metrics-server提供指标数据，且Deployment配置了resources.requests（HPA基于requests计算使用率）。

24-判断-08 ★★ 题目：Secret中的数据是加密存储的，安全性等同于明文配置。 A. 正确 B. 错误

答案：B 解析：Secret的数据是Base64编码（不是加密），base64可逆解码。生产环境建议开启etcd加密静态Secret，或使用外部密钥管理（Vault、云KMS）。

24-判断-09 ★★ 题目：StatefulSet适合部署无状态应用，Deployment适合部署有状态应用。 A. 正确 B. 错误

答案：B 解析：反了。StatefulSet适合有状态应用（数据库等，提供稳定网络标识和存储）；Deployment适合无状态应用（Web服务、API服务等）。

24-判断-10 ★★ 题目：Ingress Controller需要单独安装，K8s集群默认不包含。 A. 正确 B. 错误

答案：A 解析：Ingress资源本身是K8s内置API，但Ingress Controller（如nginx-ingress、traefik）需要单独安装部署。没有Controller，Ingress规则不生效。

24-判断-11 ★★ 题目：Pod的readinessProbe失败会导致Pod被重启。 A. 正确 B. 错误

答案：B 解析：readinessProbe失败只会将Pod从Service的Endpoints中移除（不接收流量），不会重启Pod。livenessProbe失败才会重启Pod。

24-判断-12 ★★ 题目：kubectl scale命令可以立即改变Deployment的副本数。 A. 正确 B. 错误

答案：A 解析：kubectl scale deployment/<name> --replicas=N会立即修改Deployment的replicas字段，Controller会立即创建或删除Pod以达到目标副本数。

24-判断-13 ★★ 题目：所有K8s资源对象都可以通过kubectl apply创建和更新。 A. 正确 B. 错误

答案：A 解析：kubectl apply是声明式管理，支持所有K8s资源对象的创建和更新。apply会记录上次配置（last-applied-configuration注解），便于diff和精确管理。

24-判断-14 ★★ 题目：PVC和PV是手动绑定的，管理员需要为每个PVC手动创建PV。 A. 正确 B. 错误

答案：B 解析：PV和PVC可以手动绑定（静态供给），也可以通过StorageClass自动动态供给。动态供给时，PVC创建后StorageClass会自动创建PV并绑定。

24-判断-15 ★★ 题目：NetworkPolicy默认允许所有Pod间通信，需要显式配置才拒绝。 A. 正确 B. 错误

答案：A 解析：K8s默认网络模型是全开放（所有Pod可互通）。NetworkPolicy是白名单机制，只有配置了NetworkPolicy且匹配的流量才被允许，其余默认拒绝。

24-判断-16 ★★★ 题目：Docker Compose的volumes和K8s的PersistentVolume概念完全相同。 A. 正确 B. 错误

答案：B 解析：Docker Compose的volumes是简单的卷管理，K8s的PV/PVC是更完善的存储抽象体系，支持动态供给、StorageClass、回收策略、访问模式等。概念类似但实现和功能不同。

24-判断-18 ★★ 题目：Helm Chart可以用于多环境部署，通过values.yaml覆盖配置。 A. 正确 B. 错误

答案：A 解析：Helm通过values.yaml管理配置，helm install --values=prod.yaml或--set key=value覆盖默认配置，实现一份Chart多环境部署。

24-判断-20 ★★★ 题目：一个Pod的QoS（服务质量）等级为Guaranteed，意味着其requests和limits的CPU/内存必须完全相等。 A. 正确 B. 错误

24-论述-02 ★★★ 题目：请论述K8s Deployment滚动更新的原理，并说明如何实现零停机更新。

参考答案：

一、滚动更新原理

Deployment控制器通过ReplicaSet管理Pod副本。当更新Deployment的Pod模板（如镜像版本）时：

  1. 创建新ReplicaSet：Deployment创建一个新的ReplicaSet（版本+1）
  2. 扩容新RS：新RS的副本数从0开始增加，按maxSurge控制
  3. 缩容旧RS：旧RS的副本数减少，按maxUnavailable控制
  4. 交替进行：扩新RS与缩旧RS交替进行，直到旧RS副本数为0、新RS副本数为期望值
  5. 保留旧RS：旧RS保留（副本数为0），用于回滚

二、关键参数

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # 超出期望副本数的最大值，默认25%
      maxUnavailable: 25%  # 不可用副本的最大值，默认25%
  • maxSurge：控制新Pod的创建速度
  • maxUnavailable：控制旧Pod的删除速度
  • maxUnavailable=0 + maxSurge=1可实现严格零停机

三、零停机更新实现要素

  1. 滚动更新策略：默认RollingUpdate，先建新Pod再删旧Pod

  2. readinessProbe就绪探针：确保新Pod真正Ready后才接收流量

readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

  1. 合理的maxSurge和maxUnavailable：

    • 零停机要求maxUnavailable=0（不允许不可用）
    • maxSurge=1或25%（允许临时多出Pod）

  2. 优雅终止（graceful shutdown）：

    • preStop钩子：让应用处理完已有请求
    • terminationGracePeriodSeconds：给应用足够时间优雅退出
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 10 && nginx -s quit"]
terminationGracePeriodSeconds: 30
  1. Service端点自动更新：Pod Ready时加入Endpoints，Terminating时移除

四、完整流程

更新触发 → 创建新RS → 扩容新Pod(1) → 新Pod Ready → 加入Endpoints
→ 缩容旧Pod(1) → 旧Pod从Endpoints移除 → preStop钩子 → 优雅退出
→ 扩容新Pod(2) → ... → 旧RS副本数=0 → 更新完成

五、验证方法

kubectl rollout status deployment/<name>  # 查看更新状态
kubectl get rs                            # 查看新旧RS
kubectl get pods -l app=<name>            # 查看Pod

评分标准（满分10分）：

  • 滚动更新原理解释（3分）：ReplicaSet管理+扩缩交替
  • 关键参数说明（2分）：maxSurge+maxUnavailable
  • 零停机要素（4分）：readinessProbe+maxUnavailable=0+优雅终止+Service端点更新
  • 验证方法（1分）

24-论述-03 ★★★ 题目：CTTS项目部署到K8s后，某Pod出现CrashLoopBackOff状态。请详细描述排查思路和解决步骤。

参考答案：

一、现象识别

kubectl get pods -n ctts-prod
# NAME                    READY   STATUS             RESTARTS   AGE
# ctts-web-xxx-yyy        0/1     CrashLoopBackOff   5          3m

Pod状态为CrashLoopBackOff，RESTARTS持续增加，说明容器反复崩溃重启。

二、排查思路（四步法）

现象定位 → 事件查看 → 日志分析 → 根因定位 → 修复验证

三、详细排查步骤

步骤1：查看Pod详情与事件

kubectl describe pod ctts-web-xxx-yyy -n ctts-prod

关注：

  • Events部分：查看最近事件（拉取镜像、创建容器、探针检查等）
  • Containers.State：当前状态
  • Containers.Last State：上次崩溃状态（Exit Code、Reason）
  • Restart Count：重启次数

步骤2：查看当前容器日志

kubectl logs ctts-web-xxx-yyy -n ctts-prod

查看应用启动日志，是否有异常堆栈。

步骤3：查看崩溃前日志（关键！）

kubectl logs ctts-web-xxx-yyy -n ctts-prod --previous

查看上一个容器实例崩溃前的日志，这是定位根因的关键。

步骤4：查看Pod事件

kubectl get events -n ctts-prod --sort-by='.lastTimestamp' | tail -20

查看最近集群事件，辅助定位。

步骤5：必要时进入容器排查

kubectl exec -it ctts-web-xxx-yyy -n ctts-prod -- /bin/sh

进入容器检查配置文件、网络连通性、进程状态。

四、常见根因与解决方案

根因 判断依据 解决方案
启动命令错误 Exit Code 127/126，日志提示command not found 修正Deployment的command/args
配置文件缺失 日志提示config not found 检查ConfigMap挂载，修正volumeMounts
依赖服务未就绪 日志提示connection refused（数据库等） 添加initContainer等待依赖
应用代码异常 日志有Java/Python异常堆栈 修复应用代码，重新构建镜像
存活探针过严 Last State Reason: probe failed，但应用实际正常 调大initialDelaySeconds、failureThreshold
资源不足OOM Exit Code 137，Last State Reason: OOMKilled 调大resources.limits.memory

  • 名称：存活探针（livenessProbe）
  • 作用：判断容器是否正常运行。如果检查失败，kubelet会重启该容器。
  • 配置说明：
    • httpGet：HTTP健康检查，访问/health路径，端口8080
    • initialDelaySeconds: 30：容器启动30秒后开始检查（等应用启动完成）
    • periodSeconds: 10：每10秒检查一次

3. 探针检查失败的后果

  • livenessProbe失败：kubelet会重启容器（不是删除Pod，是重启容器）
  • 连续失败达到failureThreshold次后触发重启
  • Pod的RESTARTS计数增加
  • 如果反复崩溃，可能进入CrashLoopBackOff状态

4. QoS等级

  • QoS等级：Burstable
  • 原因：requests（cpu:250m, memory:256Mi）小于limits（cpu:500m, memory:512Mi），不满足Guaranteed（要求requests=limits）的条件，但设置了requests，所以是Burstable。
  • 补充：
    • Guaranteed：requests = limits（CPU和内存都相等）
    • Burstable：至少有一个resources设置了requests，且requests < limits
    • BestEffort：没有设置任何resources
