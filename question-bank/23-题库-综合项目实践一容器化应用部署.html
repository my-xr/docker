23-单选-01（★） 在 CTTS 项目部署中，以下哪个 K8s 资源对象用于隔离 MySQL、Backend、Frontend 资源？

  • A
    Deployment
  • B
    Namespace
  • C
    Node
  • D
    Service

答案：B 解析：Namespace 是 K8s 中用于资源隔离的逻辑分组机制。CTTS 项目将所有资源统一放在 ctts 命名空间下，避免与其他项目资源冲突。Deployment 管理 Pod 副本，Node 是工作节点，Service 提供网络访问入口。

23-单选-02（★） MySQL Secret 中存储密码时，value 必须经过哪种编码？

  • A
    URL 编码
  • B
    Hex 编码
  • C
    Base64 编码
  • D
    MD5 加密

答案：C 解析：K8s Secret 的 data 字段要求值必须是 base64 编码字符串（不是加密）。可通过 echo -n 'ctts_root_2024' | base64 生成。注意 base64 是可逆的编码，并非加密，生产环境建议启用 etcs 加密静态 Secret。

23-单选-03（★） 在 mysql.yaml 中，persistentVolumeReclaimPolicy: Retain 表示什么？

  • A
    PVC 删除后，PV 自动删除并释放存储
  • B
    PVC 删除后，PV 保留数据，需手动回收
  • C
    PVC 删除后，PV 数据自动清空
  • D
    PVC 删除后，PV 立即变为 Available 状态

答案：B 解析：Retain 策略下，当 PVC 被删除时，PV 仍然存在且数据保留，状态变为 Released，需要管理员手动回收（删除 PV 后数据才会被底层存储清理）。其他策略包括 Delete（自动删除）和 Recycle（已废弃）。MySQL 是有状态数据，建议使用 Retain 防止误删。

23-单选-04（★★） CTTS 项目中 Backend 的 initContainer wait-for-mysql 的核心作用是？

  • A
    初始化数据库表结构
  • B
    等待 MySQL Service 3306 端口可用后再启动 Backend
  • C
    拉取 MySQL 镜像
  • D
    创建 MySQL 用户

答案：B 解析：initContainer 在主容器启动前运行，且必须成功退出主容器才会启动。wait-for-mysql 通过 nc -z mysql-service 3306 轮询检测 MySQL 是否就绪，从而解决 Backend 启动时数据库尚未就绪导致连接失败的问题。数据库初始化由 MySQL 镜像自身的 MYSQL_DATABASE 机制完成。

23-单选-05（★★） Frontend 的 Nginx 配置中 try_files $uri $uri/ /index.html; 的作用是？

  • A
    防止 404，将所有未匹配的请求重定向到首页（支持 Vue Router history 模式）
  • B
    启用 gzip 压缩
  • C
    配置反向代理
  • D
    设置静态资源缓存

答案：A 解析：Vue Router 的 history 模式下，用户刷新 /about 这类前端路由时，浏览器会向服务器请求 /about，但服务器上并不存在该文件。try_files 让 Nginx 在找不到文件时回退到 index.html，由前端路由接管，避免 404。

23-单选-06（★） 以下哪个命令可以查看 ctts 命名空间下所有 Deployment、Service、Pod 的状态？

  • A
    kubectl get pods -A
  • B
    kubectl get all -n ctts
  • C
    kubectl describe ns ctts
  • D
    kubectl cluster-info

答案：B 解析：kubectl get all -n ctts 会列出指定命名空间下所有常见资源（Pod、Service、Deployment、ReplicaSet 等）。-A 是所有命名空间，describe ns 只看命名空间本身，cluster-info 看集群信息。

23-单选-07（★★） Ingress 资源中 ingressClassName: nginx 的含义是？

  • A
    指定使用 nginx 作为 Ingress Controller
  • B
    指定 Pod 使用 nginx 镜像
  • C
    指定 Service 类型为 nginx
  • D
    指定命名空间为 nginx

答案：A 解析：ingressClassName 指定该 Ingress 资源由哪个 IngressClass 关联的 Ingress Controller 处理。Minikube 启用 ingress addon 后会创建 nginx IngressClass，对应的 Ingress Controller 是 ingress-nginx-controller。

23-单选-08（★★） Backend Deployment 中 strategy.type: RollingUpdate 配合 maxUnavailable: 0 的效果是？

  • A
    一次性更新所有 Pod
  • B
    滚动升级过程中始终保持所有旧 Pod 可用，零停机
  • C
    不进行任何升级
  • D
    重建所有 Pod

答案：B 解析：RollingUpdate 策略下，maxUnavailable: 0 表示升级过程中不允许有任何旧 Pod 不可用，必须先启动新 Pod 就绪后再删除旧 Pod，实现零停机部署。maxSurge: 1 允许临时超出副本数 1 个。

23-单选-09（★） 以下哪个命令可以实时跟踪 Pod 的状态变化？

  • A
    kubectl get pods
  • B
    kubectl get pods -w
  • C
    kubectl describe pod
  • D
    kubectl logs -f

答案：B 解析：-w（watch）参数让 kubectl 持续监听资源变化并实时输出。-f 用于跟踪日志，describe 是一次性查看详细信息。

23-单选-10（★★） MySQL Deployment 中 strategy.type: Recreate 而非 RollingUpdate 的原因是？

  • A
    Recreate 性能更好
  • B
    MySQL 是有状态服务，多个副本同时挂载同一 PVC 会冲突，需先停旧再启新
  • C
    Recreate 升级更快
  • D
    RollingUpdate 不支持 MySQL 镜像

答案：B 解析：MySQL 使用 PVC 持久化数据，PVC 的 accessMode 通常是 ReadWriteOnce（RWO），只能被单个 Pod 挂载。若用 RollingUpdate，新旧 Pod 会同时尝试挂载 PVC 导致冲突。Recreate 先删除旧 Pod 释放 PVC，再创建新 Pod。

23-单选-11（★★） Backend 通过 Service DNS 访问 MySQL，正确的 Service DNS 格式是？

  • A
    mysql-service.ctts
  • B
    mysql-service.ctts.svc.cluster.local
  • C
    mysql-service.ctts.namespace.local
  • D
    mysql.ctts.svc

答案：B 解析：K8s Service DNS 标准格式为 <service-name>.<namespace>.svc.cluster.local。同命名空间内可简写为 <service-name>。CoreDNS 会自动解析。

23-单选-12（★） 以下哪个 K8s 资源对象适合存储数据库连接 URL、日志级别等非敏感配置？

  • A
    Secret
  • B
    ConfigMap
  • C
    PV
  • D
    Service

答案：B 解析：ConfigMap 专门用于存储非敏感的配置数据（键值对或文件）。敏感数据（密码、密钥、证书）应使用 Secret。CTTS 项目中 backend-config 是 ConfigMap（存 URL、端口），backend-secret 是 Secret（存密码、JWT）。

23-单选-13（★★） Backend Pod 出现 CrashLoopBackOff，以下哪条命令最有助于定位根因？

  • A
    kubectl get pods
  • B
    kubectl logs <pod-name> --previous
  • C
    kubectl delete pod <pod-name>
  • D
    kubectl scale deployment backend --replicas=0

答案：B 解析：--previous 参数查看上一次崩溃前的容器日志，能直接看到应用崩溃时的异常堆栈（如数据库连接失败、配置错误）。get pods 只看状态，delete/scale 是处理动作而非排查。

23-单选-14（★★） 在 mysql.yaml 中，MySQL 容器挂载 ConfigMap 的方式是？

  • A
    通过 envFrom 整体注入
  • B
    通过 volumeMounts 挂载为文件
  • C
    两者都有
  • D
    通过 image 内置

答案：C 解析：mysql.yaml 中 MySQL 同时使用两种方式：ConfigMap 中的 my.cnf 通过 volumeMounts 挂载到 /etc/mysql/conf.d/my.cnf；同时通过 envFrom.configMapRef 注入 ConfigMap 中的所有键作为环境变量（虽然 mysql-config 中只有 my.cnf 文件，但这是演示用法）。

23-单选-15（★） 以下哪个命令可以验证 Ingress 是否分配到外部 IP？

  • A
    kubectl get ingress -n ctts
  • B
    kubectl describe svc -n ctts
  • C
    kubectl get nodes
  • D
    kubectl cluster-info

答案：A 解析：kubectl get ingress 输出中的 ADDRESS 列即 Ingress Controller 分配的访问地址（在 Minikube 下为 Minikube IP）。若为空，说明 Ingress Controller 未就绪或 addon 未启用。

23-单选-16（★★） CTTS Frontend 镜像构建时，为何采用多阶段构建（multi-stage build）？

  • A
    减少最终镜像体积，只保留 Nginx 和 dist 静态文件
  • B
    加快构建速度
  • C
    避免使用 Node.js
  • D
    必须使用

答案：A 解析：多阶段构建第一阶段用 node:18 镜像编译 Vue3 项目生成 dist，第二阶段将 dist 复制到 nginx:alpine 镜像中。最终镜像不包含 node_modules、源码、构建工具，体积从 ~1GB 降到 ~50MB，更安全更轻量。

23-单选-17（★★） Backend 的 startupProbe 中 failureThreshold: 12 配合 periodSeconds: 10 的含义是？

  • A
    每 10s 探测一次，最多允许失败 12 次（即最多等 120s 启动）
  • B
    启动失败 12 次后立即重启
  • C
    每 12s 探测一次
  • D
    启动需要 12s

答案：A 解析：startupProbe 在容器启动阶段运行，periodSeconds: 10 表示每 10s 探测一次，failureThreshold: 12 表示最多允许连续失败 12 次（12×10=120s）。在启动探针成功前，livenessProbe 不会运行，避免 JVM 预热期被误杀。

23-单选-18（★） Minikube 中加载本地构建的镜像到集群内，需要执行哪条命令？

  • A
    minikube push
  • B
    eval $(minikube docker-env)
  • C
    minikube image load
  • D
    kubectl load image

答案：B 解析：eval $(minikube docker-env) 将当前 shell 的 docker 命令指向 Minikube 节点内的 Docker daemon，之后 docker build 构建的镜像会直接存在于 Minikube 节点中。配合 imagePullPolicy: IfNotPresent 即可使用本地镜像。退出用 eval $(minikube docker-env -u)。也可以用 minikube image load <name> 直接加载。

23-单选-19（★★） Ingress 注解 nginx.ingress.kubernetes.io/rewrite-target: / 的作用是？

  • A
    将所有请求重定向到根路径
  • B
    转发到后端时将路径重写为 /
  • C
    禁用 HTTPS
  • D
    启用 gzip

答案：B 解析：rewrite-target 注解控制 Nginx 转发请求到后端 Service 时的路径重写规则。例如请求 /api/users 转发时被改写为 /。CTTS 项目中 frontend 与 backend 都用根路径，因此设置为 /。

23-单选-20（★★） 以下哪个场景必须使用 Secret 而非 ConfigMap？

  • A
    数据库连接 URL
  • B
    日志级别
  • C
    数据库密码与 JWT 密钥
  • D
    应用端口

答案：C 解析：密码、密钥、证书等敏感信息应使用 Secret 存储，避免明文暴露在 ConfigMap 或镜像中。虽然 Secret 默认只是 base64 编码（非加密），但配合 RBAC 可以限制访问，且能通过 etcd 加密静态存储。URL、日志级别、端口属于非敏感配置。

23-单选-21（★★） Backend Pod 显示 1/1 Running 但 Service Endpoints 为空，可能原因是？

  • A
    Service selector 与 Pod labels 不匹配，或 readinessProbe 未通过
  • B
    Pod 没启动
  • C
    命名空间错误
  • D
    Service 类型错误

答案：A 解析：Service 通过 selector 选择 Pod 时，只有 readinessProbe 通过的 Pod 才会被加入 Endpoints。即使 Pod Running，若就绪探针失败，Endpoints 仍为空。需检查 selector 标签是否一致、探针路径是否正确。

23-单选-22（★） CTTS 项目部署顺序应该是？

  • A
    Frontend → Backend → MySQL → Ingress
  • B
    Ingress → Frontend → Backend → MySQL
  • C
    MySQL → Backend → Frontend → Ingress
  • D
    任意顺序

答案：C 解析：依赖关系决定部署顺序：MySQL 是数据源先启动；Backend 依赖 MySQL 通过 initContainer 等待；Frontend 依赖 Backend（Nginx 反向代理）；Ingress 依赖前后端 Service 存在。逆序部署会导致依赖服务不可达。

23-单选-23（★★） 以下哪个命令可以查看 MySQL Pod 内的实时日志？

答案：A 解析：kubectl logs 是查看日志的标准命令，-f（follow）实时跟踪，deployment/mysql 表示按 Deployment 选择 Pod。describe 用于查看资源详情，exec 是进入容器执行命令。

23-单选-24（★★） MySQL 的 livenessProbe 使用 mysqladmin ping 而非 HTTP 探针的原因是？

  • A
    MySQL 不支持 HTTP
  • B
    mysqladmin ping 是 MySQL 官方推荐的存活检测方式，准确反映数据库可用性
  • C
    HTTP 探针性能差
  • D
    集群不支持 HTTP 探针

答案：B 解析：MySQL 是数据库服务，不提供 HTTP 接口。mysqladmin ping 返回 mysqld 存活状态，比 TCP 探针更准确（TCP 端口可达不代表数据库可服务）。K8s exec 探针支持任意命令，适合非 HTTP 服务。

23-单选-25（★★） Frontend Service 的 type: ClusterIP 表示？

  • A
    Service 只能集群内部访问
  • B
    Service 暴露到集群外部
  • C
    Service 没有 IP
  • D
    Service 使用负载均衡

答案：A 解析：ClusterIP 是 Service 默认类型，分配集群内部 IP，只能在集群内访问。CTTS 中 frontend-service 是 ClusterIP，外部访问通过 Ingress 转发。其他类型：NodePort 暴露节点端口，LoadBalancer 云厂商负载均衡，ExternalName DNS 跳转。

23-单选-26（★★） Backend Pod 出现 OOMKilled 状态，应如何处理？

  • A
    调大 resources.limits.memory
  • B
    调小 resources.requests.cpu
  • C
    重启集群
  • D
    删除 Pod

答案：A 解析：OOMKilled 表示容器内存使用超过 limits.memory 被 K8s 杀死。需调大 limits.memory（如从 512Mi 调到 768Mi），或优化应用内存使用。kubectl describe pod 的 Last State 可看到 OOMKilled 原因与退出码 137。

23-单选-27（★★） 以下哪个命令可以进入 MySQL Pod 执行 SQL 命令？

  • A
    kubectl ssh mysql
  • B

  • C
    kubectl run mysql --rm -it
  • D
    kubectl attach mysql

答案：B 解析：kubectl exec -it 进入容器执行交互式命令。deployment/mysql 选择 Pod，-- 分隔 kubectl 参数与容器内命令。-it 分配 TTY 并交互。其他选项均为非标准命令。

23-单选-28（★★） Ingress 中 pathType: Prefix 与 pathType: Exact 的区别是？

  • A
    Prefix 前缀匹配，Exact 精确匹配
  • B
    Prefix 区分大小写，Exact 不区分
  • C
    Prefix 更快

三、判断题（20题）

23-判断-01（★） K8s 中 Secret 默认是加密存储的，可以直接在 YAML 中明文写密码。

答案：错误 解析：Secret 默认只是 base64 编码（非加密），etcd 中存储的仍是 base64 字符串。生产环境应启用 etcd 静态加密（EncryptionConfiguration）。YAML 中 data 字段值必须是 base64 编码字符串。

23-判断-02（★） ConfigMap 中的配置修改后，已运行的 Pod 会自动感知并重新加载配置。

答案：错误 解析：ConfigMap 修改后，通过 volumeMounts 挂载的文件会在一段时间后（约 1 分钟）自动更新到容器内，但通过 envFrom 注入的环境变量不会更新（环境变量在容器启动时固化）。要让环境变量生效，需执行 kubectl rollout restart 重启 Pod。

23-判断-03（★） PV 是集群级资源，不属于任何 Namespace；PVC 是命名空间级资源。

答案：正确 解析：PV 是集群全局资源（不属于任何 Namespace），PVC 是命名空间级资源。PVC 在自己的命名空间内引用 PV，K8s 通过 storageClassName 和 accessModes 自动匹配绑定。

23-判断-04（★★） MySQL Deployment 必须使用 strategy: Recreate，因为 PVC 是 ReadWriteOnce，不能被多个 Pod 同时挂载。

答案：正确 解析：ReadWriteOnce（RWO）模式的 PVC 只能被单个节点上的单个 Pod 挂载。若用 RollingUpdate，新旧 Pod 会同时存在并尝试挂载同一 PVC，导致冲突失败。Recreate 先删旧 Pod 释放 PVC，再启新 Pod。

23-判断-05（★） K8s Service 的 ClusterIP 默认是固定的，删除重建 Service 后 IP 不变。

答案：错误 解析：Service 的 ClusterIP 在创建时由 K8s 动态分配，删除重建后会得到新的 IP。因此应用间通信应通过 Service DNS 名称（如 mysql-service）而非 ClusterIP，DNS 名称是稳定的。

23-判断-06（★★） Backend 的 initContainer wait-for-mysql 失败后，主容器仍会启动。

答案：错误 解析：initContainer 必须按顺序成功完成后，主容器才会启动。若 initContainer 失败（退出码非 0），K8s 会重启 initContainer（受 restartPolicy 控制，默认 Always），主容器不会启动。

23-判断-07（★★） Ingress 只能路由 HTTP/HTTPS 流量，不支持 TCP/UDP。

答案：正确 解析：标准 Ingress 资源只支持七层 HTTP/HTTPS 路由。TCP/UDP 四层路由需要使用 Ingress Controller 的扩展配置（如 nginx-ingress 的 ConfigMap tcp-services）。CTTS 项目中 MySQL 仅集群内访问，不通过 Ingress 暴露。

23-判断-08（★） kubectl get all -n ctts 会显示 ctts 命名空间下的所有资源对象，包括 Secret 和 ConfigMap。

答案：错误 解析：kubectl get all 只显示常见工作负载资源（Pod、Service、Deployment、ReplicaSet、DaemonSet、StatefulSet 等），不包含 ConfigMap、Secret、PV、PVC、Ingress 等。需分别用 kubectl get cm、kubectl get secret、kubectl get ingress 查看。

23-判断-09（★★） CTTS 项目中 Frontend 的 Nginx 配置通过 ConfigMap 注入而非写入镜像，是为了方便修改反代地址而无需重新构建镜像。

答案：正确 解析：将 Nginx 配置抽离到 ConfigMap，修改 backend-service 地址或路径规则时只需更新 ConfigMap 并重启 Pod，无需重新构建前端镜像。这是"配置即基础设施"理念的体现，符合云原生十二要素应用的方法论。

23-判断-10（★） Minikube addons enable ingress 命令会安装 nginx ingress controller 到 kube-system 命名空间。

答案：错误 解析：Minikube ingress addon 默认将 ingress-nginx-controller 安装到 ingress-nginx 命名空间（不是 kube-system）。可用 kubectl get pod -n ingress-nginx 查看。

23-判断-11（★★） Pod 的 imagePullPolicy: Always 表示即使本地有同名镜像，也会从远程仓库拉取。

答案：正确 解析：Always 策略下，每次创建 Pod 都会尝试从远程仓库拉取镜像，即使节点本地已有同名 tag。对于本地构建的镜像（无远程仓库），应设置为 IfNotPresent 避免拉取失败。Latest tag 默认是 Always，其他 tag 默认是 IfNotPresent。

23-判断-12（★★） Backend Deployment 中 replicas: 2 表示始终运行 2 个 Pod 副本，K8s 会自动在节点故障时重建。

答案：正确 解析：Deployment 控制器持续监控 Pod 副本数，若实际副本数与期望不符（如节点故障、Pod 崩溃），会自动创建或删除 Pod 维持期望副本数。这是 K8s 自愈能力的体现。

23-判断-13（★） K8s 中不同命名空间的 Service 互相访问时，必须使用完整的 FQDN <svc>.<ns>.svc.cluster.local。

答案：正确 解析：同命名空间内可简写 Service 名称（如 mysql-service），但跨命名空间访问必须使用完整 FQDN（如 mysql-service.ctts.svc.cluster.local），否则 DNS 解析会找不到目标 Service。

23-判断-14（★★） PV 的 accessModes: ReadWriteOnce 表示该 PV 只能被一个 Pod 挂载。

答案：错误（部分正确，但不准确） 解析：ReadWriteOnce（RWO）表示该 PV 只能被单个节点以读写方式挂载，但同一节点上的多个 Pod 可以同时挂载。更准确的说法是"只能被一个节点挂载"。对于 MySQL 等单副本场景，效果等同于一 Pod 挂载。

23-判断-15（★★★） Backend 的 readinessProbe 和 livenessProbe 都配置 /actuator/health，所以它们的语义完全相同。

答案：错误 解析：虽然路径相同，但语义不同：readinessProbe 失败会将 Pod 从 Service Endpoints 移除（停止接收新流量，但 Pod 继续运行）；livenessProbe 失败会重启容器。SpringBoot Actuator 的 /actuator/health 在依赖组件异常时返回 503，能让 readiness 自动摘除故障 Pod。

23-判断-16（★） kubectl delete namespace ctts 会删除该命名空间下的所有资源。

答案：正确 解析：删除 Namespace 会级联删除其下所有资源（Pod、Service、Deployment、ConfigMap、Secret、PVC 等），但不会删除 PV（PV 是集群级资源）。这是快速清理项目所有资源的方式，但需谨慎使用。

23-判断-17（★★） CTTS 项目中 Frontend Nginx 通过 proxy_pass http://backend-service:8080 反向代理后端，依赖 K8s Service DNS 解析。

答案：正确 解析：Nginx 在容器内运行，通过 K8s CoreDNS 解析 backend-service 域名，获取 Service ClusterIP 并负载分发到后端 Pod。这是 K8s 集群内服务间通信的标准方式。

23-判断-18（★★） Pod 出现 ImagePullBackOff 后，删除该 Pod 让 K8s 重新创建即可解决所有问题。

答案：错误 解析：ImagePullBackOff 的根因是镜像拉取失败（镜像不存在、tag 错误、仓库认证失败、网络问题等）。若根因未解决，新创建的 Pod 仍会失败。需先排查根因（kubectl describe pod 看 Events）并修复后再删除 Pod 重建。

23-判断-19（★★★） CTTS 项目中若 MySQL Pod 崩溃重启，由于 PVC 持久化了 /var/lib/mysql，数据不会丢失。

答案：正确 解析：PVC 将 MySQL 数据目录持久化到 PV，Pod 崩溃或重建时数据保留。但需注意：若 MySQL 在写入过程中崩溃可能存在数据不一致风险（依赖 MySQL 的 binlog 与 InnoDB redo log 恢复）。生产环境建议使用 StatefulSet + StorageClass 提供更强保障。

23-判断-20（★★） K8s 中 Deployment 是声明式 API，用户声明期望状态，控制器持续调谐实际状态向期望状态收敛。

答案：正确 解析：K8s 核心设计是声明式 API + 控制器模式。用户在 Deployment YAML 中声明 replicas: 2 等期望状态，Deployment 控制器持续监控并调谐实际状态（如节点故障导致副本数减少时自动创建新 Pod）向期望状态收敛。这是 K8s 自愈与弹性的基础。

23-论述-01（★★★） 题目：请论述 CTTS 项目中 MySQL、Backend、Frontend 三个服务的部署顺序与依赖关系，并说明如何通过 K8s 机制保证依赖顺序。若颠倒顺序会出现什么问题？

参考答案：

1. 部署顺序与依赖关系

CTTS 项目部署顺序为：MySQL → Backend → Frontend → Ingress。依赖关系如下：

  • Backend 依赖 MySQL：SpringBoot 启动时需要建立数据库连接池（HikariPool），执行 JPA ddl-auto 建表。
  • Frontend 依赖 Backend：Nginx 反向代理 /api/ 到 backend-service，若 Backend 不可用，前端页面虽能加载但接口请求 502。
  • Ingress 依赖前后端 Service：Ingress 规则中 backend.service.name 必须指向已存在的 Service，否则 Ingress 规则无法生效。

2. K8s 保证依赖顺序的机制

CTTS 项目采用两层机制：

  • initContainer 等待依赖就绪：Backend Deployment 中配置 wait-for-mysql initContainer，通过 nc -z mysql-service 3306 轮询检测 MySQL Service 是否可达。initContainer 必须成功退出主容器才会启动，从而保证 Backend 启动时 MySQL 已就绪。

  • readinessProbe 控制流量接入：MySQL 配置 readinessProbe: SELECT 1，数据库可服务后才被加入 Service Endpoints；Backend 配置 readinessProbe: /actuator/health，应用就绪后才接收流量。这避免了"Pod Running 但服务未就绪"时被调用导致失败。

  • Service DNS 解析：Backend 通过 mysql-service DNS 名称访问 MySQL，无需关心 MySQL Pod IP 变化。即使 MySQL Pod 重建 IP 变化，DNS 仍指向新 Pod。

3. 颠倒顺序的后果

  • 若先部署 Backend 后部署 MySQL：Backend 的 initContainer 等待 MySQL Service 不存在（DNS 解析失败），会一直阻塞，Pod 卡在 Init:Error 或 Init:CrashLoopBackOff。即使最终 MySQL 启动，Backend 也可能因多次失败需手动重启。
  • 若先部署 Frontend 后部署 Backend：Frontend Nginx 启动时 proxy_pass 解析 backend-service 失败，Nginx 配置加载报错，容器无法启动。
  • 若先部署 Ingress：Ingress 规则引用的 Service 不存在，规则虽能创建但 ADDRESS 为空，无法路由。

4. 生产环境增强建议

  • 使用 StatefulSet 部署 MySQL（保证稳定网络标识与有序部署）。
  • 引入 Helm Chart 或 Kustomize 管理依赖关系。
  • 使用 Argo CD 等 GitOps 工具实现按序同步。

23-论述-02（★★★） 题目：CTTS 项目中 Backend Deployment 同时配置了 startupProbe、readinessProbe、livenessProbe 三种探针，路径都是 /actuator/health。请论述三种探针的区别、执行顺序，以及为什么 SpringBoot 应用需要 startupProbe。

参考答案：

1. 三种探针的区别

探针 作用 失败后果 适用场景
startupProbe 检测容器是否已成功启动 失败重启容器，启动成功后停止运行 慢启动应用（JVM、SpringBoot）
livenessProbe 检测容器是否存活 失败重启容器（kill + 重建） 检测死锁、僵死等不可恢复故障
readinessProbe 检测容器是否就绪接收流量 失败从 Service Endpoints 摘除，不重启 暂时性故障（如依赖不可用、缓存预热）

2. 执行顺序

容器启动
   ↓
startupProbe 周期运行（periodSeconds: 10, failureThreshold: 12，最多 120s）
   ↓ 成功
startupProbe 停止
   ↓
livenessProbe 与 readinessProbe 开始周期并行运行
   ├── livenessProbe 失败 → 重启容器
   └── readinessProbe 失败 → 摘除流量（不重启）

关键点：startupProbe 运行期间，livenessProbe 不运行，避免慢启动应用被误判为僵死而重启。

3. SpringBoot 需要 startupProbe 的原因

  • JVM 启动慢：SpringBoot 应用启动需要加载 Spring 容器、扫描 Bean、初始化数据源连接池、执行 JPA 建表等，通常需要 30-90s，大型应用可能 2-3 分钟。
  • 传统 livenessProbe 误杀问题：若只配置 livenessProbe 且 initialDelaySeconds: 30，应用启动若超过 30s，探针失败被重启，形成 CrashLoopBackOff 死循环。调大 initialDelaySeconds 又会延迟故障发现。
  • startupProbe 优势：在启动阶段宽容等待（最多 120s），启动成功后立即转入正常的 liveness 周期检测，既避免误杀又能及时发现启动失败。

4. 三探针协同设计原则

  • startupProbe：failureThreshold × periodSeconds ≥ 应用最大启动时间（SpringBoot 建议 ≥ 120s）。
  • livenessProbe：检测不可恢复故障，failureThreshold 较小（3 次），快速重启。
  • readinessProbe：检测暂时性故障，failureThreshold 可稍大，避免抖动导致流量频繁切换。
  • 路径选择：SpringBoot Actuator /actuator/health 返回 200 表示就绪，503 表示降级，配合 readiness 自动摘除故障实例。

23-论述-03（★★） 题目：CTTS 项目中 MySQL 数据通过 PV/PVC 持久化，请论述 PV 与 PVC 的关系、绑定机制、回收策略，以及为什么 MySQL 部署用 Recreate 而非 RollingUpdate 策略。

参考答案：

1. PV 与 PVC 的关系

  • PV（PersistentVolume）：集群级资源，由管理员预先创建或由 StorageClass 动态 provision，表示集群中的一块实际存储（如 hostPath、NFS、Ceph、云盘）。
  • PVC（PersistentVolumeClaim）：命名空间级资源，由用户声明对存储的需求（大小、访问模式、storageClassName），类似"存储的订单"。
  • 关系：PVC 是用户对 PV 的"消费声明"，K8s 控制器根据 PVC 的需求自动匹配合适的 PV 并绑定。

2. 绑定机制

K8s 通过以下维度匹配 PVC 与 PV：

  • storageClassName：PVC 与 PV 必须指定相同的 StorageClass（或都为空字符串表示默认）。
  • accessModes：PVC 要求的访问模式必须是 PV 支持的子集（如 PVC 要 RWO，PV 支持 RWO/RWX 都可匹配）。
  • capacity：PV 的容量必须 ≥ PVC 请求的容量。

CTTS 项目中：mysql-pv（5Gi, RWO, standard）匹配 mysql-pvc（请求 5Gi, RWO, standard）。

3. 回收策略

策略 行为 适用场景
Retain PVC 删除后，PV 保留数据变为 Released，需管理员手动回收 生产数据、有状态服务
Delete PVC 删除后，PV 与底层存储自动删除 动态 provision 的临时数据
Recycle（已废弃） 清空 PV 数据变为 Available 旧版本

CTTS MySQL 使用 Retain，保护数据安全。

4. MySQL 用 Recreate 的原因

  • PVC 是 ReadWriteOnce（RWO）：RWO 模式下，PVC 只能被单个节点挂载。
  • RollingUpdate 冲突：升级时新 Pod 创建时旧 Pod 还在，两者尝试同时挂载同一 PVC，新 Pod 挂载失败卡在 ContainerCreating。
  • Recreate 流程：先删除旧 Pod → PVC 释放 → 创建新 Pod → 挂载 PVC 成功。虽有短暂停机但数据安全。
  • 生产建议：MySQL 等有状态服务推荐使用 StatefulSet（内置有序部署、稳定网络标识、独立 PVC），而非 Deployment。

1. Ingress 与 Service 的区别

维度 Service Ingress
网络层级 四层（TCP/UDP） 七层（HTTP/HTTPS）
路由维度 端口转发 域名 + 路径

2. Ingress 工作原理

  • Ingress 资源：用户声明的路由规则（YAML），存储在 etcd，本身不处理流量。
  • Ingress Controller：运行中的 Pod（如 ingress-nginx-controller），监听 Ingress 资源变化，动态生成 Nginx 配置并 reload。
  • IngressClass：桥梁资源，关联 Ingress 与 Controller，ingressClassName: nginx 指定由 nginx Controller 处理。

   GET / HTTP/1.1

4. Ingress 的核心价值

  • 统一入口：所有外部流量通过单一入口（80/443），便于证书管理、日志监控、限流。
  • 域名路由：一个 IP 支持多个域名，按 Host 分发到不同 Service。
  • TLS 终结：证书配置在 Ingress，后端 Service 无需处理 HTTPS，简化应用。
  • 路径分发：同一域名下按路径分发（如 /api 到后端，/ 到前端）。

23-编程-02（★★★） 题目：请为 CTTS 项目编写完整的 ingress.yaml，要求：

  1. Ingress 名称：ctts-ingress，命名空间：ctts。
  2. 使用 nginx IngressClass。
  3. 配置两个域名路由规则：
    • frontend.ctts.local → frontend-service:80（路径 /，Prefix）
    • api.ctts.local → backend-service:8080（路径 /，Prefix）
  4. 添加注解：rewrite-target 为 /，proxy-body-size 为 50m，proxy-connect-timeout 为 30。
  5. （进阶）配置 TLS：使用 ctts-tls-secret 证书，启用 ssl-redirect，覆盖两个域名。

参考答案：

---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ctts-ingress
  namespace: ctts
  labels:
    app: ctts
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "30"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    # 进阶：TLS 重定向
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - frontend.ctts.local
        - api.ctts.local
      secretName: ctts-tls-secret
  rules:
    - host: frontend.ctts.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
    - host: api.ctts.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 8080

配套 TLS 证书生成命令（附加说明）：

# 生成自签名证书
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout tls.key -out tls.crt \
  -subj "/CN=*.ctts.local/O=CTTS"

# 创建 TLS Secret
kubectl create secret tls ctts-tls-secret \
  --namespace=ctts \
  --key=tls.key \
  --cert=tls.crt

# 验证
kubectl get secret ctts-tls-secret -n ctts
