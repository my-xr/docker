07-选择-001（★ 知识点：K7-1 ENV 与 ARG） 关于 ENV 和 ARG 指令，下列说法正确的是？

  • A两者在容器运行时都可用
  • BENV 仅在构建阶段生效，ARG 在构建和运行时都生效
  • CARG 仅在构建阶段生效，ENV 在构建和运行时都生效
  • D两者都不进入镜像元数据

答案：C 解析：ARG 仅在构建阶段生效，运行时容器内不可见；ENV 在构建和运行时都生效，并持久化到镜像元数据（docker inspect 可见）。A、B、D 均错误。

07-选择-002（★ 知识点：K7-1 ENV 指令） 在 Dockerfile 中使用 ENV JAVA_HOME=/usr/lib/jvm/java-17 后，下列说法正确的是？

  • A该变量仅在 RUN 指令中可用，CMD 中不可用
  • B该变量在构建阶段和容器运行时都可用
  • C该变量只能用 docker build --build-arg 覆盖
  • D该变量不会出现在 docker inspect 输出中

答案：B 解析：ENV 设置的环境变量在构建阶段和容器运行时都可用，并持久化到镜像元数据（docker inspect 可见）。A 错，CMD 中也可用；C 错，ENV 用 docker run -e 在运行时覆盖；D 错，ENV 进入镜像元数据。

07-选择-003（★★ 知识点：K7-1 ARG 指令） 关于 ARG 指令，下列说法错误的是？

  • AARG 定义的变量仅在构建阶段生效
  • BARG 可以用 docker build --build-arg 覆盖
  • CARG 的值会出现在 docker history 中
  • DARG 适合传递数据库密码等敏感信息

答案：D 解析：ARG 的值会出现在 docker history 中，不适合传敏感信息（密码、token、私钥等），敏感信息应在运行时通过 -e 或 Secret 注入。A、B、C 描述都正确。

07-选择-004（★★ 知识点：K7-1 ARG 全局） 在 Dockerfile 中，要让 FROM 指令使用一个可参数化的版本号，应该使用？

  • A在 FROM 之前用 ENV 定义变量
  • B在 FROM 之前用 ARG 定义变量（全局 ARG）
  • C在 FROM 之后用 ARG 定义变量
  • D直接写死版本号，无法参数化

答案：B 解析：FROM 之前只能用 ARG（称为全局 ARG），用于参数化基础镜像版本，如 ARG JAVA_VERSION=17 然后 FROM openjdk:${JAVA_VERSION}。A 错，ENV 不能在 FROM 之前；C 错，FROM 之后的 ARG 不能反向影响 FROM；D 错，可以用全局 ARG 参数化。

07-选择-005（★ 知识点：K7-2 EXPOSE 指令） 关于 EXPOSE 8080 指令，下列说法正确的是？

  • A它会自动把容器的 8080 端口映射到宿主机
  • B它只是声明端口，不自动映射，需用 -p 或 -P 真正映射
  • C它和 docker run -p 8080:8080 完全等价
  • D它只能声明一个端口

答案：B 解析：EXPOSE 是声明性指令，只声明容器会监听该端口，不会自动映射到宿主机。要用 -p 宿主端口:容器端口 显式映射，或 -P 自动映射所有 EXPOSE 声明的端口到随机高位端口。A、C 错；D 错，可一次声明多个端口如 EXPOSE 80 443。

07-选择-006（★★ 知识点：K7-2 VOLUME 指令） 关于 VOLUME ["/var/lib/mysql"] 指令，下列说法正确的是？

  • A它会自动把宿主机的 /var/lib/mysql 挂载到容器
  • B它会强制要求运行时用 -v 显式挂载，否则容器无法启动
  • C它声明该路径为数据卷，运行时不写 -v 时 Docker 会自动挂一个匿名卷
  • D它只能在 Dockerfile 中使用，不能在 docker run 中挂载该路径

答案：C 解析：VOLUME 声明该路径为数据卷，运行时若用户没写 -v，Docker 会自动在 /var/lib/docker/volumes/ 下创建匿名卷挂载到该路径。A 错，宿主路径由 -v 指定；B 错，不写 -v 也能启动（自动挂匿名卷）；D 错，docker run -v 仍然可用。

07-选择-007（★ 知识点：K7-3 CMD 指令） 关于 CMD 指令，下列说法正确的是？

  • A一个 Dockerfile 可以有多个 CMD，全部生效
  • BCMD 指定的命令在构建阶段执行
  • CCMD 可以被 docker run 后的参数覆盖
  • DCMD 必须用 exec 形式，不能用 shell 形式

答案：C 解析：CMD 是容器默认启动命令，可以被 docker run 后参数完全覆盖。A 错，多个 CMD 只有最后一个生效；B 错，CMD 在容器启动时执行，不在构建阶段；D 错，CMD 有 shell 和 exec 两种形式，推荐 exec 但不是必须。

07-选择-008（★★ 知识点：K7-3 CMD 形式） 下列 CMD 写法中，能正确接收 SIGTERM 信号（优雅退出）的是？

  • ACMD java -jar app.jar
  • BCMD "java -jar app.jar"
  • CCMD ["java", "-jar", "app.jar"]
  • DCMD [java, -jar, app.jar]

答案：C 解析：exec 形式 CMD ["java","-jar","app.jar"] 让 java 直接作为 PID 1 进程，能接收 SIGTERM 信号优雅退出。A 是 shell 形式，PID 1 是 /bin/sh，不转发信号；B 不是合法形式；D 不是合法 JSON（字符串没引号）。

07-选择-009（★ 知识点：K7-3 CMD 覆盖） 某 Dockerfile 中有 CMD ["java","-jar","app.jar"]，执行 docker run myapp bash 后，实际执行的命令是？

  • Ajava -jar app.jar bash
  • Bbash（CMD 被完全替换）
  • Cjava -jar app.jar（CMD 不被覆盖）
  • D报错，无法运行

答案：B 解析：CMD 可以被 docker run 后参数完全覆盖。docker run myapp bash 中的 bash 会替换掉 CMD，实际执行 bash。A 错（那是 ENTRYPOINT 的行为）；C 错（CMD 会被覆盖）；D 错（能正常运行 bash）。

07-选择-010（★ 知识点：K7-4 ENTRYPOINT 指令） 关于 ENTRYPOINT 指令，下列说法正确的是？

  • AENTRYPOINT 会被 docker run 后的参数完全覆盖
  • BENTRYPOINT 不会被 docker run 后的参数覆盖，参数会作为追加参数传入
  • CENTRYPOINT 不能与 CMD 同时使用
  • DENTRYPOINT 必须用 shell 形式

答案：B 解析：ENTRYPOINT 是入口点程序，docker run 后的参数会作为追加参数传入 ENTRYPOINT，不会覆盖它（除非用 --entrypoint 显式覆盖）。A 错；C 错，推荐与 CMD 组合使用；D 错，推荐 exec 形式。

07-选择-011（★★ 知识点：K7-4 组合模式） 某 Dockerfile 有：

ENTRYPOINT ["java","-jar","/app/app.jar"]
CMD ["--spring.profiles.active=prod"]

执行 docker run myapp --spring.profiles.active=dev 后，实际执行？

  • Ajava -jar /app/app.jar --spring.profiles.active=prod
  • Bjava -jar /app/app.jar --spring.profiles.active=dev
  • Cjava -jar /app/app.jar --spring.profiles.active=prod --spring.profiles.active=dev
  • D--spring.profiles.active=dev（ENTRYPOINT 被覆盖）

答案：B 解析：ENTRYPOINT 固定不变，CMD 部分被 docker run 参数替换。实际执行 java -jar /app/app.jar --spring.profiles.active=dev。A 是默认运行（不传参数）的情况；C 是误以为追加；D 是误以为 ENTRYPOINT 被覆盖。

07-选择-012（★★ 知识点：K7-4 覆盖 ENTRYPOINT） 要用 docker run 完全覆盖镜像的 ENTRYPOINT，应该使用哪个参数？

  • A--entrypoint
  • B-e
  • C--build-arg
  • D--cmd

答案：A 解析：docker run --entrypoint <新命令> 可以覆盖镜像的 ENTRYPOINT。B 是设置环境变量；C 是构建时参数；D 不存在该参数。

07-选择-013（★ 知识点：K7-5 多阶段构建） 关于多阶段构建，下列说法正确的是？

  • A每个 FROM 开启一个新阶段，最终镜像包含所有阶段
  • B最终镜像只保留最后一个阶段，前面阶段的镜像层不会进入最终镜像
  • C多阶段构建需要写多个 Dockerfile
  • D多阶段构建不能跨阶段拷贝文件

答案：B 解析：多阶段构建中，最终镜像只保留最后一个 FROM 之后的阶段，前面阶段通过 COPY --from=<阶段名> 拷贝产物，但其镜像层不进入最终镜像。A 错；C 错，一个 Dockerfile 完成全流程；D 错，COPY --from 可以跨阶段拷贝。

07-选择-014（★★ 知识点：K7-5 阶段命名） 在多阶段构建中，给阶段命名使用的语法是？

  • AFROM maven:3.8 AS builder
  • BFROM maven:3.8 NAME builder
  • CFROM maven:3.8 --name builder
  • DFROM maven:3.8 -> builder

答案：A 解析：使用 FROM <image> AS <name> 给阶段命名，然后用 COPY --from=<name> 引用。B、C、D 都不是合法语法。

07-选择-015（★★ 知识点：K7-5 跨阶段拷贝） 多阶段构建中，从名为 builder 的阶段拷贝 /build/target/app.jar 到当前阶段 /app/app.jar，正确的写法是？

  • ACOPY /build/target/app.jar /app/app.jar --from=builder
  • BCOPY --from=builder /build/target/app.jar /app/app.jar
  • CCOPY --stage=builder /build/target/app.jar /app/app.jar
  • DCOPY from=builder /build/target/app.jar /app/app.jar

答案：B 解析：跨阶段拷贝使用 COPY --from=<阶段名> <源路径> <目标路径>。A 选项 --from 应在前面；C、D 不是合法语法。

07-选择-016（★★ 知识点：K7-5 多阶段价值） 多阶段构建的核心价值不包括？

  • A减小镜像体积
  • B提升镜像安全性（攻击面减小）
  • C自动加速 Maven/npm 依赖下载
  • D把构建工具与运行环境解耦

答案：C 解析：多阶段构建的价值是减小体积、提升安全性、解耦构建与运行，但不会"自动加速依赖下载"（依赖下载速度由网络和镜像源决定，层缓存才能避免重复下载）。A、B、D 都是真实价值。

07-选择-017（★★ 知识点：K7-6 基础镜像） 下列基础镜像中，体积最小（最精简）的是？

  • Aubuntu:22.04
  • Bdebian:bookworm-slim
  • Calpine:3.18
  • Declipse-temurin:17-jre

答案：C 解析：alpine:3.18 约 7MB，是最精简的；debian-slim 约 74MB；ubuntu 约 77MB；eclipse-temurin:17-jre 约 260MB（含 JRE）。

07-选择-018（★★ 知识点：K7-6 alpine 注意事项） 关于 alpine 基础镜像，下列说法正确的是？

  • Aalpine 使用 glibc，与所有应用完全兼容
  • Balpine 使用 musl libc，部分依赖 glibc 的应用可能有兼容性问题
  • Calpine 不能用于 Java 应用
  • Dalpine 必须搭配 JDK 使用

答案：B 解析：alpine 使用 musl libc（非 glibc），部分依赖 glibc 的原生库可能有兼容性问题。Java 应用要用专门的 alpine 版本（如 eclipse-temurin:17-jre-alpine）。A 错；C 错，可以用专门 alpine 版 JDK；D 错，搭配 JRE 即可。

07-选择-019（★★ 知识点：K7-6 合并 RUN） 下列哪种写法能真正减小镜像体积（让 apt cache 不占空间）？

  • ARUN apt-get update 然后 RUN apt-get install -y curl 然后 RUN rm -rf /var/lib/apt/lists/*
  • BRUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
  • CRUN apt-get update 和 RUN apt-get install -y curl 和 RUN apt-get clean
  • D用 ENTRYPOINT 删除 apt cache

答案：B 解析：镜像层只追加不删除，装和删必须在同一层（用 && 连接）才能真正减小体积。A、C 是分多层，装的那层仍占空间；D 不合法（ENTRYPOINT 是运行时指令）。

07-选择-020（★★ 知识点：K7-6 层缓存顺序） 在 Java 项目 Dockerfile 中，为提升层缓存命中率，正确的 COPY 顺序是？

  • A先 COPY 源码，再 COPY pom.xml，最后 RUN mvn package
  • B先 COPY pom.xml，RUN 下载依赖，再 COPY 源码，最后 RUN 编译
  • C先 COPY 所有文件，再 RUN 一次完成下载和编译
  • D顺序不重要，Docker 会自动优化

答案：B 解析：层缓存按顺序生效，少变的放前。pom.xml 变化少，先 COPY 它并下载依赖（缓存稳定）；src 经常变，放后面，让源码变化时只重跑编译，不重下依赖。A、C 顺序导致源码变化时全部失效；D 错，顺序很重要。

07-选择-021（★ 知识点：K7-6 .dockerignore） .dockerignore 文件的作用是？

  • A决定哪些文件不进入版本控制
  • B决定哪些文件不进入构建上下文（不发送给 Docker 守护进程）
  • C决定哪些文件不进入镜像
  • D决定哪些文件被 COPY 指令忽略

答案：B 解析：.dockerignore 列出哪些文件不进入构建上下文（不发送给守护进程），影响的是构建上下文传输阶段。A 是 .gitignore 的作用；C、D 错，COPY 仍可手动指定要拷贝的文件，.dockerignore 影响的是上下文范围。

07-选择-022（★★ 知识点：K7-6 .dockerignore 价值） 下列哪一项不是 .dockerignore 的价值？

  • A减小构建上下文，加快构建
  • B防止敏感信息（如 .env、密钥）进入镜像
  • C提升层缓存命中率
  • D自动减小镜像体积（删除镜像内文件）

答案：D 解析：.dockerignore 影响的是"构建上下文"（发送给守护进程的文件集合），不直接减小已构建镜像的体积（COPY 仍按 Dockerfile 指令执行）。A、B、C 都是 .dockerignore 的真实价值；D 错，它减小的是上下文不是镜像。

07-选择-023（★★ 知识点：K7-1/K7-3 ENV 与 CMD 配合） 在 Dockerfile 中：

ENV APP_JAR=/app/app.jar
CMD ["java","-jar","$APP_JAR"]

执行后会怎样？

  • A容器启动时执行 java -jar /app/app.jar
  • B容器启动时执行 java -jar $APP_JAR（变量未展开，报错）
  • C容器启动时执行 java
  • D报错，CMD 不能用变量

答案：B 解析：CMD 的 exec 形式（JSON 数组）不会自动展开环境变量，$APP_JAR 会被当作字面字符串传给 java，导致 java 找不到 $APP_JAR 文件。要展开变量，需用 shell 形式或 ["sh","-c","java -jar $APP_JAR"]。

07-选择-024（★★ 知识点：K7-3 RUN vs CMD） 关于 RUN 和 CMD 的区别，下列说法正确的是？

  • A都是构建时执行
  • B都是运行时执行
  • CRUN 构建时执行并产生层，CMD 运行时执行不产生层
  • DRUN 运行时执行，CMD 构建时执行

答案：C 解析：RUN 在构建阶段执行，每条 RUN 产生一个镜像层；CMD 在容器启动时执行，不产生镜像层，只是指定默认启动命令。A、B、D 都错。

07-选择-025（★★ 知识点：K7-4 shell 形式 ENTRYPOINT） 某 Dockerfile 有 ENTRYPOINT java -jar app.jar（shell 形式）和 CMD ["--debug"]（exec 形式），实际执行？

  • Ajava -jar app.jar --debug
  • Bjava -jar app.jar（CMD 被忽略）
  • C--debug（ENTRYPOINT 被忽略）
  • D报错

答案：B 解析：ENTRYPOINT 用 shell 形式时，会以 /bin/sh -c "java -jar app.jar" 执行，CMD 会被忽略，不会被作为参数传入。这是 shell 形式 ENTRYPOINT 的一个陷阱。推荐用 exec 形式。

07-选择-026（★★★ 知识点：K7-5 多阶段综合） 某 Java 项目多阶段构建 Dockerfile：

FROM maven:3.8 AS builder
COPY src /build/src
COPY pom.xml /build/
RUN mvn package -DskipTests

FROM openjdk:17-slim
COPY --from=builder /build/target/app.jar /app/app.jar
CMD ["java","-jar","/app/app.jar"]

下列说法正确的是？

  • A最终镜像包含 Maven 和 JDK
  • B最终镜像只包含 OpenJDK 17 slim 和 app.jar
  • C最终镜像包含源码
  • D最终镜像大小约为 600MB+

答案：B 解析：多阶段构建最终镜像只保留最后一个 FROM 之后的阶段。最终镜像基于 openjdk:17-slim，只拷贝了 builder 阶段的 app.jar，不包含 Maven、JDK 完整版（openjdk:17-slim 只有 JRE/JDK 部分）、源码。A、C、D 错。

07-选择-027（★★ 知识点：K7-6 .dockerignore 内容） 下列哪一项不应该写入 .dockerignore？

  • A.git 目录
  • Btarget 目录（旧构建产物）
  • Cpom.xml（项目对象模型）
  • D.env（环境变量配置文件）

答案：C 解析：pom.xml 是 Maven 构建必需的文件，必须包含在构建上下文中。.git、target、.env 都应该排除（前两者无关，.env 含敏感信息）。

07-选择-028（★ 知识点：K7-2 EXPOSE 与 -P 配合） docker run -P（大写 P）的作用是？

  • A把容器的 80 端口映射到宿主机 80
  • B自动把 Dockerfile 中 EXPOSE 声明的端口映射到宿主机随机高位端口
  • C不做任何端口映射
  • D把宿主机 8080 映射到容器 8080

答案：B 解析：-P（大写）自动把 EXPOSE 声明的所有端口映射到宿主机随机高位端口（49152-65535）。-p（小写）才是显式映射指定端口，如 -p 8080:8080。

07-选择-029（★★★ 知识点：K7-5 阶段引用） 多阶段构建中，下列哪种方式可以引用前面的阶段？

  • ACOPY --stage=builder ...
  • BCOPY --from=builder ...（builder 是阶段名）

07-论述-001（★★ 知识点：K7-3/K7-4 CMD vs ENTRYPOINT，10 分） 请从作用、形式（shell/exec）、是否被覆盖、组合模式四个方面，对比 CMD 与 ENTRYPOINT 的区别，并说明生产镜像为什么推荐 ENTRYPOINT + CMD 组合模式。

参考答案与评分标准（10 分，按要点给分）：

  1. 作用（2 分）：

    • CMD：指定容器默认启动命令。
    • ENTRYPOINT：指定容器入口点程序。

  2. 形式（shell 与 exec）（2 分）：

    • 都有 shell 形式（CMD java -jar app.jar）和 exec 形式（CMD ["java","-jar","app.jar"]）。
    • exec 形式让进程成为 PID 1，能正确接收 SIGTERM 信号优雅退出，是生产推荐。
    • shell 形式通过 /bin/sh -c 执行，PID 1 是 sh，不转发信号给子进程。

  3. 是否被覆盖（2 分）：

    • CMD 可被 docker run 后参数完全覆盖。
    • ENTRYPOINT 不会被覆盖，docker run 后参数会作为追加参数传入 ENTRYPOINT。
    • 要覆盖 ENTRYPOINT 需用 --entrypoint 参数。

  4. 组合模式（2 分）：

    • ENTRYPOINT + CMD 组合：ENTRYPOINT 固定可执行程序，CMD 给默认参数。
    • docker run myapp 使用 CMD 默认参数；docker run myapp <新参数> 替换 CMD 部分，ENTRYPOINT 不变。
    • 例如 ENTRYPOINT ["java","-jar","app.jar"] + CMD ["--spring.profiles.active=prod"]，运行 docker run myapp --spring.profiles.active=dev 实际执行 java -jar app.jar --spring.profiles.active=dev。

07-论述-004（★★ 知识点：K7-1/K7-2 声明性指令与参数化，8 分） 请解释 ENV、ARG、EXPOSE、VOLUME 四个指令的"声明性"或"参数化"特征，并说明它们各自的典型用途。

参考答案与评分标准（8 分，按要点给分）：

  1. ENV（2 分）：

    • 特征：设置环境变量，在构建阶段和运行时都生效，持久化到镜像元数据。
    • 典型用途：设置 JAVA_HOME、APP_PORT、SPRING_PROFILES_ACTIVE、PATH 追加等运行时配置。
    • 可用 docker run -e 在运行时覆盖（不修改镜像）。

  2. ARG（2 分）：

    • 特征：定义构建时参数，仅在构建阶段生效，不进入运行时容器。
    • 典型用途：参数化基础镜像版本（如 ARG JAVA_VERSION=17 + FROM openjdk:${JAVA_VERSION}）、构建版本号、构建开关。
    • 可用 docker build --build-arg 覆盖。
    • 注意：不要用 ARG 传敏感信息（值会出现在 docker history）。

  3. EXPOSE（2 分）：

    • 特征：声明性指令，声明容器监听的端口，本身不自动映射。
    • 典型用途：声明应用端口（如 EXPOSE 8080），配合 -p 或 -P 真正映射；让镜像自带"使用说明"。
    • 在 docker inspect 中可见，便于使用者了解镜像的网络需求。

  4. VOLUME（2 分）：

    • 特征：声明数据卷路径，运行时不写 -v 时 Docker 自动挂匿名卷。
    • 典型用途：声明需要持久化的路径（如 MySQL 的 /var/lib/mysql、应用的 /app/logs），保证容器删除后数据不丢。
    • 生产推荐显式 -v 具名卷便于管理、备份、迁移。

评分要点：每个指令 2 分（特征 1 分 + 典型用途 1 分）；4 个都答对给满分；只列特征不举例每个扣 0.5 分。
