一、单项选择题（30题，每题2分）

22-单选-01 ★ 题目：K8s中，Pod销毁后容器内文件系统的数据会怎样？

  • A
    自动迁移到其他节点
  • B
    保留在原节点等待Pod重新调度
  • C
    随Pod销毁而丢失
  • D
    自动备份到etcd

答案：C 解析：Pod的容器文件系统基于容器的可写层（overlayfs），具有临时性，Pod销毁时可写层数据随之丢失。这是K8s引入持久化存储体系的根本原因。

22-单选-02 ★ 题目：下列哪个属于K8s集群级（cluster-scoped）资源？

  • A
    PVC
  • B
    PV
  • C
    ConfigMap
  • D
    Secret

答案：B 解析：PV是集群级资源，不属于任何命名空间；PVC、ConfigMap、Secret都是命名空间级资源。

22-单选-03 ★ 题目：PV的访问模式 ReadWriteOnce 表示什么？

  • A
    可被多节点读写
  • B
    可被单节点读写
  • C
    可被多节点只读
  • D
    可被单节点只读

答案：B 解析：ReadWriteOnce (RWO) 表示该PV可被单节点以读写方式挂载。ReadOnlyMany (ROX) 是多节点只读，ReadWriteMany (RWX) 是多节点读写。

22-单选-04 ★ 题目：下列哪种存储类型支持 ReadWriteMany 访问模式？

  • A
    hostPath
  • B
    NFS
  • C
    本地磁盘
  • D
    AWS EBS

答案：B 解析：NFS是网络文件系统，天然支持多节点同时读写。hostPath绑定单节点，AWS EBS等块存储通常只支持RWO。

22-单选-05 ★★ 题目：PV的回收策略中，删除PVC后PV会自动删除底层存储的是？

  • A
    Retain
  • B
    Recycle
  • C
    Delete
  • D
    Keep

答案：C 解析：Delete 策略下，PVC删除后PV及底层存储资源自动删除，常用于动态供给。Retain 保留数据，Recycle 已废弃。

22-单选-06 ★ 题目：PV生命周期的初始状态是？

  • A
    Bound
  • B
    Released
  • C
    Available
  • D
    Failed

答案：C 解析：PV创建后处于 Available 状态，等待PVC匹配。被PVC绑定后变为 Bound，PVC删除后变为 Released。

22-单选-07 ★★ 题目：PV处于 Released 状态后，如何使其重新被新PVC绑定？

  • A
    删除PV重建
  • B
    重启kube-controller-manager
  • C
    清除 spec.claimRef 字段
  • D
    修改PV的capacity

答案：C 解析：Released 状态的PV仍保留对旧PVC的引用（spec.claimRef），需通过 kubectl patch pv <name> -p '{"spec":{"claimRef":null}}' 清除引用后才会回到 Available。

22-单选-08 ★ 题目：PVC属于哪一级资源？

  • A
    集群级（cluster-scoped）
  • B
    命名空间级（namespaced）
  • C
    节点级（node-scoped）
  • D
    Pod级（pod-scoped）

答案：B 解析：PVC是命名空间级资源，Pod只能引用同命名空间的PVC。PV是集群级资源，可被任何命名空间的PVC绑定。

22-单选-09 ★★ 题目：PVC与PV绑定时不需要匹配的字段是？

  • A
    capacity
  • B
    accessModes
  • C
    storageClassName
  • D
    metadata.name

答案：D 解析：绑定匹配条件包括容量（PV≥PVC）、访问模式（PV包含PVC所需模式）、storageClassName（一致）、selector（可选）。名称不参与匹配。

22-单选-10 ★ 题目：StorageClass的核心字段是？

  • A
    capacity
  • B
    accessModes
  • C
    provisioner
  • D
    reclaimPolicy

答案：C 解析：provisioner 是StorageClass最核心字段，指定动态供给时调用的存储供给器（如 k8s.io/minikube-hostpath）。其他字段如reclaimPolicy、volumeBindingMode是辅助配置。

22-单选-11 ★★ 题目：Minikube默认的StorageClass provisioner是？

  • A
    kubernetes.io/nfs
  • B
    k8s.io/minikube-hostpath
  • C
    kubernetes.io/aws-ebs
  • D
    kubernetes.io/gce-pd

答案：B 解析：Minikube通过storage-provisioner插件提供 k8s.io/minikube-hostpath provisioner，在Minikube节点上创建hostPath类型的PV。

22-单选-12 ★★ 题目：StorageClass中 volumeBindingMode: WaitForFirstConsumer 的作用是？

  • A
    立即绑定PVC
  • B
    等到Pod调度后再绑定PVC
  • C
    等待管理员手动批准
  • D
    等待StorageClass配置完成

答案：B 解析：WaitForFirstConsumer 模式下，PVC创建后不会立即绑定PV，而是等到有Pod使用该PVC且Pod完成调度后才绑定，确保PV与Pod在同一拓扑域（如节点、区域）。

22-单选-13 ★ 题目：在Pod中引用PVC的字段是？

  • A
    volumes.persistentVolumeClaim.claimName
  • B
    volumes.hostPath.path
  • C
    volumes.emptyDir
  • D
    volumes.configMap.name

答案：A 解析：Pod通过 spec.volumes[].persistentVolumeClaim.claimName 引用PVC，再通过 containers[].volumeMounts 挂载到容器路径。

22-单选-14 ★★ 题目：StatefulSet中为每个Pod自动创建独立PVC的字段是？

  • A
    volumes
  • B
    volumeMounts
  • C
    volumeClaimTemplates
  • D
    persistentVolumeClaim

答案：C 解析：volumeClaimTemplates 是StatefulSet专用字段，会为每个Pod副本自动创建独立PVC（命名格式 <volumeClaimTemplate.name>-<statefulset.name>-<ordinal>），Pod销毁后PVC保留。

22-单选-15 ★★ 题目：下列哪种访问模式在K8s 1.22+引入，且只能被单个Pod读写？

  • A
    ReadWriteOnce
  • B
    ReadOnlyMany
  • C
    ReadWriteMany
  • D
    ReadWriteOncePod

答案：D 解析：ReadWriteOncePod (RWOP) 是K8s 1.22+引入的，比RWO更严格，限制只能被单个Pod（而非单节点多Pod）读写。

22-单选-16 ★ 题目：存储容量单位 Gi 表示什么？

  • A
    1000字节
  • B
    1024字节
  • C
    1000兆字节（10^9）
  • D
    1024兆字节（2^30）

答案：D 解析：Gi 是二进制单位（Gibibyte），表示2^30字节。G 是十进制单位（Gigabyte），表示10^9字节。K8s存储建议使用 Gi。

22-单选-17 ★★ 题目：MySQL Deployment建议使用的更新策略是？

  • A
    RollingUpdate
  • B
    Recreate
  • C
    Blue-Green
  • D
    Canary

答案：B 解析：MySQL是有状态应用，同时只能有一个实例写入数据。Recreate 策略先删除旧Pod再创建新Pod，避免双写冲突。RollingUpdate 可能导致新旧Pod同时挂载同一PVC引发数据损坏。

22-单选-18 ★★ 题目：下列哪个不是PVC一直Pending的可能原因？

  • A
    无匹配的PV
  • B
    storageClassName不匹配
  • C
    selector标签不匹配
  • D
    Pod未创建

答案：D 解析：PVC的绑定与Pod是否创建无关（除非使用WaitForFirstConsumer模式）。A/B/C都是常见Pending原因。

22-单选-19 ★ 题目：hostPath类型的PV主要适用于？

  • A
    生产环境多节点集群
  • B
    单节点开发环境（如Minikube）
  • C
    跨节点数据共享
  • D
    高可用数据库

答案：B 解析：hostPath绑定到具体节点，Pod重调度到其他节点后数据不跟随，仅适合单节点开发环境。生产环境应使用NFS/CSI等。

22-单选-20 ★★ 题目：将StorageClass设为默认的注解是？

  • A
    storageclass.kubernetes.io/is-default: "true"
  • B
    storageclass.kubernetes.io/is-default-class: "true"
  • C
    storageclass.beta.kubernetes.io/is-default-class: "true"
  • D
    storage.k8s.io/default-class: "true"

答案：B 解析：storageclass.kubernetes.io/is-default-class: "true" 是当前版本的注解（旧版 storageclass.beta.kubernetes.io/is-default-class 已废弃）。设为默认后，PVC不指定storageClassName时会自动使用。

22-单选-21 ★★★ 题目：关于PV和PVC的命名空间，下列说法正确的是？

  • A
    PV和PVC都必须在同一命名空间
  • B
    PV属于集群级，PVC属于命名空间级，但绑定不受命名空间限制
  • C
    PV属于命名空间级，PVC属于集群级
  • D
    PV和PVC都是集群级资源

答案：B 解析：PV是集群级资源（不属于任何命名空间），PVC是命名空间级资源。绑定时不看命名空间，但Pod只能引用同命名空间的PVC。

22-单选-22 ★★ 题目：下列哪种存储类型属于CSI？

  • A
    hostPath
  • B
    nfs
  • C
    awsElasticBlockStore
  • D
    腾讯云CBS通过csi.driver

答案：D 解析：CSI（Container Storage Interface）是K8s 1.13+推荐的标准存储接口，第三方存储厂商通过CSI插件接入。A/B/C是K8s内置存储类型（部分已废弃，推荐迁移到CSI）。

22-单选-23 ★★ 题目：StatefulSet使用volumeClaimTemplates创建的PVC命名规则是？

  • A
    <pvc-name>-<pod-name>
  • B
    <volumeClaimTemplate.name>-<statefulset.name>-<ordinal>
  • C
    <statefulset.name>-<volumeClaimTemplate.name>-<ordinal>

答案：B 解析：命名格式为 <volumeClaimTemplate.name>-<statefulset.name>-<ordinal>，如 www-web-0、www-web-1。Pod销毁后PVC保留，新Pod重新挂载同一PVC。

22-单选-24 ★ 题目：K8s中已废弃的PV回收策略是？

  • A
    Retain
  • B
    Delete
  • C
    Recycle
  • D
    Archive

答案：C 解析：Recycle 策略在K8s 1.11+废弃，原行为是删除PV内数据后变为Available。现在推荐使用动态供给+Delete或Retain手动管理。

22-单选-25 ★★ 题目：下列哪个命令可以查看PVC的绑定事件？

  • A
    kubectl get pvc
  • B
    kubectl describe pvc <name>
  • C
    kubectl logs pvc <name>
  • D
    kubectl exec pvc <name>

答案：B 解析：kubectl describe pvc <name> 输出中的Events部分会显示PVC的绑定过程和失败原因。kubectl get 只显示状态摘要。

22-单选-26 ★★ 题目：PV的 volumeMode 字段默认值是？

  • A
    Block
  • B
    Filesystem
  • C
    Raw
  • D
    Directory

答案：B 解析：volumeMode 默认为 Filesystem，PV会被格式化为文件系统后挂载。Block 模式提供原始块设备，适用于高性能数据库。

22-单选-27 ★★★ 题目：关于动态供给，下列说法错误的是？

  • A
    动态供给无需管理员预先创建PV
  • B
    动态供给由StorageClass的provisioner自动创建PV
  • C
    动态供给的PV默认reclaimPolicy为Retain
  • D
    动态供给适合云盘等按需存储

答案：C 解析：动态供给的PV默认reclaimPolicy为 Delete（与StorageClass配置一致），删除PVC后PV及底层存储自动删除。如需保留数据，应配置为 Retain。

22-单选-28 ★ 题目：Pod中volumeMounts的name字段必须与什么一致？

  • A
    Pod的name
  • B
    PVC的name
  • C
    volumes中的name
  • D
    PV的name

答案：C 解析：volumeMounts.name 必须与 volumes.name 一致，建立挂载点与卷的对应关系。PVC的name通过 volumes.persistentVolumeClaim.claimName 引用。

22-单选-29 ★★ 题目：NFS类型PV的 server 字段指定的是？

  • A
    NFS服务器的IP或主机名
  • B
    NFS服务器的端口号
  • C
    NFS挂载路径
  • D
    NFS版本号

答案：A 解析：server 字段指定NFS服务器的IP地址或主机名，path 字段指定NFS导出路径，readOnly 指定是否只读。

22-单选-30 ★★★ 题目：下列关于StatefulSet与Deployment在存储使用上的区别，正确的是？

  • A
    Deployment支持volumeClaimTemplates，StatefulSet不支持
  • B
    StatefulSet支持volumeClaimTemplates，每个Pod有独立PVC
  • C
    两者都支持volumeClaimTemplates
  • D
    StatefulSet只能使用静态PV

答案：B 解析：volumeClaimTemplates 是StatefulSet专用字段，为每个Pod副本自动创建独立PVC，适合有状态应用。Deployment不支持该字段，多个Pod共享同一PVC（可能引发数据冲突）。

二、多项选择题（10题，每题3分）

22-多选-01 ★ 题目：K8s存储体系的四层抽象包括？（多选）

  • A
    Volume
  • B
    PersistentVolume (PV)
  • C
    PersistentVolumeClaim (PVC)
  • D
    StorageClass
  • E
    Namespace

答案：ABCD 解析：K8s存储体系四层抽象是Volume、PV、PVC、StorageClass。Namespace是资源隔离机制，不属于存储抽象。

22-多选-02 ★★ 题目：PV的访问模式包括哪些？（多选）

  • A
    ReadWriteOnce
  • B
    ReadOnlyMany
  • C
    ReadWriteMany
  • D
    ReadWriteOncePod
  • E
    ReadWriteAll

答案：ABCD 解析：K8s支持四种访问模式：RWO、ROX、RWX、RWOP（K8s 1.22+）。ReadWriteAll 不是有效模式。

22-多选-03 ★★ 题目：PV的回收策略包括哪些？（多选）

  • A
    Retain
  • B
    Delete
  • C
    Recycle
  • D
    Archive
  • E
    Keep

答案：ABC 解析：PV回收策略有 Retain（保留）、Delete（删除）、Recycle（已废弃）。Archive 和 Keep 不是有效策略。

22-多选-04 ★★ 题目：PVC与PV绑定时的匹配条件包括？（多选）

  • A
    容量（PV容量≥PVC申请容量）
  • B
    访问模式（PV包含PVC所需模式）
  • C
    storageClassName一致
  • D
    selector标签匹配（如有）
  • E
    PV与PVC在同一命名空间

答案：ABCD 解析：A/B/C/D都是绑定匹配条件。PV是集群级资源，PVC是命名空间级资源，绑定不受命名空间限制，E错误。

22-多选-05 ★★ 题目：下列哪些存储类型支持 ReadWriteMany？（多选）

  • A
    NFS
  • B
    CephFS
  • C
    hostPath
  • D
    AWS EBS
  • E
    GlusterFS

答案：ABE 解析：NFS、CephFS、GlusterFS是共享文件系统，支持多节点读写。hostPath绑定单节点，AWS EBS等块存储通常只支持RWO。

22-多选-06 ★★★ 题目：StorageClass的核心字段包括？（多选）

  • A
    provisioner
  • B
    reclaimPolicy
  • C
    volumeBindingMode
  • D
    parameters
  • E
    allowVolumeExpansion

答案：ABCDE 解析：五个都是StorageClass的重要字段。provisioner 指定供给器，reclaimPolicy 回收策略，volumeBindingMode 绑定模式，parameters 供给器参数，allowVolumeExpansion 是否允许扩容。

三、判断题（20题，每题1分）

22-判断-01 ★ 题目：Pod销毁后，容器内文件系统的数据会自动迁移到其他节点。 答案：错误 解析：Pod容器文件系统基于可写层，Pod销毁时数据丢失，不会自动迁移。这是需要持久化存储的根本原因。

22-判断-02 ★ 题目：PV是命名空间级资源，PVC是集群级资源。 答案：错误 解析：相反。PV是集群级（cluster-scoped）资源，PVC是命名空间级（namespaced）资源。

22-判断-03 ★ 题目：emptyDir 类型的Volume可以实现数据持久化。 答案：错误 解析：emptyDir 生命周期与Pod相同，Pod销毁时数据丢失，不能实现持久化。持久化需使用PV/PVC。

22-判断-04 ★★ 题目：PV的 Retain 回收策略会在删除PVC后自动删除底层存储。 答案：错误 解析：Retain 策略下，删除PVC后PV保留数据，状态变为Released。自动删除底层存储的是 Delete 策略。

22-判断-05 ★★ 题目：NFS类型的PV支持 ReadWriteMany 访问模式。 答案：正确 解析：NFS是网络文件系统，天然支持多节点同时读写，可以使用RWX模式。

22-判断-06 ★ 题目：Pod可以引用任意命名空间的PVC。 答案：错误 解析：Pod只能引用同命名空间的PVC。PVC是命名空间级资源，跨命名空间引用不被允许。

22-判断-07 ★★ 题目：StatefulSet使用 volumeClaimTemplates 为每个Pod创建共享的PVC。 答案：错误 解析：volumeClaimTemplates 为每个Pod副本创建独立的PVC（命名带序号），不是共享的。每个Pod有自己独立的数据卷。

22-判断-08 ★ 题目：StorageClass可以实现PV的动态供给。 答案：正确 解析：StorageClass通过provisioner按需自动创建PV并绑定到PVC，实现动态供给。

22-判断-09 ★★ 题目：PV处于Released状态时，可以被新PVC直接绑定。 答案：错误 解析：Released状态的PV保留对旧PVC的claimRef引用，需手动清除 spec.claimRef 后才会回到Available，才能被新PVC绑定。

22-判断-10 ★ 题目：hostPath 类型的PV适合生产环境多节点集群。 答案：错误 解析：hostPath绑定到具体节点，Pod重调度到其他节点后数据不跟随，仅适合单节点开发环境（如Minikube）。生产应使用NFS/CSI。

22-判断-11 ★★ 题目：Minikube默认提供 k8s.io/minikube-hostpath provisioner。 答案：正确 解析：Minikube通过storage-provisioner插件提供该provisioner，支持StorageClass动态供给。

22-判断-12 ★★ 题目：volumeBindingMode: WaitForFirstConsumer 模式下，PVC创建后会立即绑定PV。 答案：错误 解析：WaitForFirstConsumer 模式下，PVC创建后不立即绑定，等到有Pod使用该PVC且Pod完成调度后才绑定，确保拓扑一致。

22-判断-13 ★ 题目：Pod的 volumeMounts.name 必须与 volumes.name 一致。 答案：正确 解析：二者必须一致，建立挂载点与卷的对应关系，否则挂载失败。

22-判断-14 ★★ 题目：MySQL Deployment建议使用 RollingUpdate 策略。 答案：错误 解析：MySQL是有状态应用，同时只能一个实例写入。应使用 Recreate 策略，避免新旧Pod同时挂载同一PVC引发数据损坏。

22-判断-15 ★★ 题目：动态供给的PV默认reclaimPolicy为 Delete。 答案：正确 解析：动态供给的PV继承StorageClass的reclaimPolicy，默认为 Delete，删除PVC后PV及底层存储自动删除。

22-判断-16 ★ 题目：Gi 和 G 在K8s中表示相同的容量。 答案：错误 解析：Gi 是二进制单位（2^30），G 是十进制单位（10^9）。建议使用 Gi 避免歧义。

22-判断-17 ★★★ 题目：CSI是K8s 1.13+推荐的标准存储接口。 答案：正确 解析：CSI（Container Storage Interface）是K8s推荐的存储接口标准，第三方存储厂商通过CSI插件接入，替代旧的in-tree存储插件。

22-判断-18 ★★ 题目：StatefulSet的Pod销毁后，对应的PVC会被自动删除。 答案：错误 解析：StatefulSet的Pod销毁后，volumeClaimTemplates 创建的PVC会保留，新Pod重新挂载同一PVC，实现数据持久化。需手动删除PVC才会释放存储。

22-判断-19 ★ 题目：PV和PVC通过selector标签进行必选匹配。 答案：错误 解析：selector是可选匹配条件，不是必选。只有PVC定义了selector时才进行标签匹配。

22-判断-20 ★★ 题目：StorageClass可以设为默认，使PVC不指定storageClassName时自动使用。 答案：正确 解析：通过注解 storageclass.kubernetes.io/is-default-class: "true" 设为默认，PVC不指定storageClassName时会自动使用该StorageClass。

五、论述简答题（4题，每题10分）

22-论述-01 ★★ 题目：简述K8s存储体系四层抽象（Volume/PV/PVC/StorageClass）的职责与关系。

评分标准（满分10分）：

  • 四层抽象各自职责（每层1.5分，共6分）
  • 层级关系说明（2分）
  • 类比或图示（1分）
  • 语言表述清晰（1分）

参考答案：

K8s存储体系通过四层抽象实现存储资源与Pod的解耦：

  1. Volume（卷）：Pod级最基础存储抽象，生命周期与Pod相同。包括emptyDir（临时）、hostPath（节点目录）、configMap/secret（配置注入）等类型。Volume是Pod内部概念，无法跨Pod共享。

  2. PersistentVolume (PV)：集群级存储资源，由管理员创建（静态）或StorageClass自动创建（动态）。PV描述"集群有什么存储"，包含capacity、accessModes、reclaimPolicy等字段，是存储资源的抽象。

  3. PersistentVolumeClaim (PVC)：命名空间级存储申请，用户创建。PVC描述"我要什么存储"，声明所需容量、访问模式、storageClassName。K8s自动匹配符合条件的PV并绑定。

  4. StorageClass：动态供给模板，描述"如何自动创建PV"。包含provisioner、reclaimPolicy、volumeBindingMode等字段。当PVC指定StorageClass且无匹配静态PV时，provisioner按模板自动创建PV。

关系：

  • Volume是Pod内基础抽象，可引用PVC。
  • PV是资源提供方，PVC是资源消费方，二者通过绑定关联。
  • StorageClass是PV的工厂，按需动态创建PV。
  • 类比：PV≈机房机柜，PVC≈租户申请工单，StorageClass≈自动派工系统。

22-论述-02 ★★★ 题目：详细描述PVC与PV的绑定机制，并说明PVC一直Pending的常见原因及排查方法。

评分标准（满分10分）：

  • 绑定机制流程（4分）
  • Pending常见原因（至少3个，3分）
  • 排查方法与命令（2分）
  • 表述清晰（1分）

参考答案：

绑定机制流程：

  1. 用户创建PVC，声明所需容量、访问模式、storageClassName、selector。
  2. K8s的PersistentVolumeController控制循环监听PVC创建事件。
  3. 遍历所有Available状态的PV，检查匹配条件：
    • 容量匹配：PV容量 ≥ PVC申请容量
    • 访问模式匹配：PV的accessModes包含PVC所需模式
    • storageClassName匹配：二者一致（或都为空）
    • selector匹配：PVC的labelSelector匹配PV的labels（如有）
  4. 找到匹配PV后，将PVC与PV绑定，二者状态变为Bound。
  5. 若无匹配PV且指定了StorageClass，触发动态供给创建PV。
  6. 若无匹配PV且无StorageClass，PVC保持Pending。

Pending常见原因：

  1. 无匹配容量的PV：集群中没有容量足够的PV。
  2. accessModes不匹配：如PVC需要RWO但PV只有RWX（部分场景下不匹配）。
  3. storageClassName不一致：PVC和PV的storageClassName必须一致。
  4. selector标签不匹配：PVC的selector与PV的labels不匹配。
  5. 动态供给provisioner未部署：如NFS StorageClass未部署nfs-provisioner。
  6. WaitForFirstConsumer模式未创建Pod：该模式下需Pod调度后才绑定。

排查方法：

# 1. 查看PVC状态和事件
kubectl describe pvc <name>
# 关注Events部分的提示信息

# 2. 查看可用PV
kubectl get pv
# 检查是否有Available状态且匹配的PV

# 3. 检查StorageClass
kubectl get sc
kubectl describe sc <name>
# 确认provisioner是否部署

# 4. 检查provisioner Pod
kubectl get pod -n kube-system | grep provisioner

22-论述-03 ★★ 题目：对比静态供给与动态供给的区别，并说明各自适用场景。

评分标准（满分10分）：

  • 静态供给定义与流程（3分）
  • 动态供给定义与流程（3分）
  • 区别对比（2分）
  • 适用场景（2分）

参考答案：

静态供给：

  • 定义：管理员手动创建PV，描述存储资源的详细信息（capacity、accessModes、后端存储类型）。
  • 流程：管理员创建PV → 用户创建PVC → K8s匹配并绑定。
  • 特点：PV预先存在，PVC只需匹配，不触发创建。

动态供给：

  • 定义：用户创建PVC指定StorageClass，无匹配静态PV时，provisioner按StorageClass模板自动创建PV。
  • 流程：管理员创建StorageClass → 用户创建PVC（指定SC）→ 无匹配静态PV → provisioner自动创建PV并绑定。
  • 特点：PV按需创建，无需预先规划。

区别对比：

维度 静态供给 动态供给
PV创建 管理员手动 provisioner自动
灵活性 低，需预先规划 高，按需创建
运维成本 高 低
回收策略 多用Retain 多用Delete
存储类型 hostPath、固定NFS路径 云盘、按需NFS、Ceph

适用场景：

  • 静态供给：已有存储资源（如自建NFS固定路径）、开发测试环境、需要精细控制PV配置。
  • 动态供给：云环境（AWS EBS、腾讯云CBS）、大规模生产、按需存储、多租户隔离。

22-论述-04 ★★★ 题目：结合CTTS项目，说明为MySQL配置持久化存储的完整方案，包括YAML设计要点、数据验证步骤和思政感悟。

评分标准（满分10分）：

  • 方案设计（PV/PVC/Deployment YAML要点）（4分）
  • 数据验证步骤（3分）
  • 思政感悟（数据安全）（2分）
  • 表述与完整性（1分）

参考答案：

方案设计：

CTTS MySQL持久化方案采用StatefulSet + volumeClaimTemplates（生产最佳实践）：

  1. PV/PVC设计：

    • 开发环境：hostPath静态供给，capacity 5Gi，RWO，Retain策略。
    • 生产环境：StorageClass动态供给，或NFS静态供给支持RWX。
    • selector标签匹配：app: ctts, component: mysql。

  2. Deployment/StatefulSet要点：

    • 策略：strategy.type: Recreate，避免新旧Pod同时挂载引发双写。
    • 数据目录：/var/lib/mysql 挂载到PVC。
    • 配置文件：通过ConfigMap挂载到 /etc/mysql/conf.d。
    • 密码：通过Secret注入，不硬编码。
    • 资源限制：requests 200m/512Mi，limits 1000m/1Gi。

  3. Service设计：

    • Headless Service（clusterIP: None），便于StatefulSet稳定网络标识。

YAML核心结构：

# StatefulSet + volumeClaimTemplates
spec:
  volumeClaimTemplates:
  - metadata: {name: mysql-data}
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources: {requests: {storage: 5Gi}}

数据验证步骤：

  1. 创建PV/PVC，验证状态Bound。
  2. 部署MySQL Pod，等待Ready。
  3. 写入测试数据：INSERT INTO users VALUES (...)。
  4. 验证宿主机数据：minikube ssh -- ls /data/ctts/mysql/。
  5. 删除Pod模拟故障：kubectl delete pod -l app=ctts,component=mysql。
  6. 等待新Pod重建，查询数据：SELECT * FROM users。
  7. 确认数据仍在——持久化成功。

思政感悟：

数据是用户信任的载体，持久化存储是数据保障的最后一道防线。作为工程师，在设计存储方案时必须贯彻"数据安全第一"原则：

  1. 责任意识：每一条用户数据背后都是真实用户的信任，数据丢失不仅造成业务损失，更损害用户信任。
  2. 预防胜于补救：通过Retain策略、定期备份、多副本等机制，将数据丢失风险降至最低。
  3. 敬畏生产：生产环境的存储配置需经过严格测试，遵循《数据安全法》要求，建立完善的数据安全制度。
  4. 终身学习：存储技术不断演进（CSI、快照、扩容），工程师需持续学习，跟上技术发展，才能更好地守护数据安全。

  ________④________:                  # 声明PVC模板的字段
  - metadata:
      name: ________⑤________        # 与volumeMounts.name一致
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 5Gi

评分标准（每空2分，共10分）：

答案：

  • ① ctts-mysql
  • ② mysql-data
  • ③ /var/lib/mysql
  • ④ volumeClaimTemplates
  • ⑤ mysql-data

解析：

  • ① StatefulSet必须关联Headless Service（serviceName字段）。
  • ②⑤ volumeMounts.name必须与volumeClaimTemplates.name一致，建立挂载关系。
  • ③ MySQL默认数据目录是 /var/lib/mysql。
  • ④ volumeClaimTemplates 是StatefulSet专用字段，为每个Pod自动创建独立PVC。

22-编程-02 ★★★ 题目：为CTTS项目编写StorageClass动态供给方案，要求：

  1. 定义StorageClass（provisioner为 k8s.io/minikube-hostpath，reclaimPolicy为Delete，设为默认）。
  2. 使用StatefulSet部署MySQL（1副本），通过 volumeClaimTemplates 自动创建PVC（5Gi，RWO，使用上述StorageClass）。
  3. 定义Headless Service。
  4. 编写数据验证的kubectl命令序列：部署→写入数据→删除Pod→验证数据持久化。

评分标准（满分15分）：

  • StorageClass YAML完整正确（含默认注解）（3分）
  • StatefulSet YAML含volumeClaimTemplates（4分）
  • Headless Service定义（2分）

  • 数据验证命令序列完整正确（4分）

参考答案：

# 文件名：ctts-mysql-dynamic.yaml
---
# StorageClass（设为默认）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: k8s.io/minikube-hostpath
reclaimPolicy: Delete
volumeBindingMode: Immediate
allowVolumeExpansion: true
---
# Headless Service
apiVersion: v1
kind: Service
metadata:
  name: ctts-mysql
  namespace: default
spec:
  selector:
    app: ctts
    component: mysql
  ports:
  - port: 3306
    targetPort: 3306
  clusterIP: None
---
# StatefulSet
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: ctts-mysql
  namespace: default
  labels:
    app: ctts
    component: mysql
spec:
  serviceName: ctts-mysql
  replicas: 1
  selector:
    matchLabels:
      app: ctts
      component: mysql
  template:
    metadata:
      labels:
        app: ctts
        component: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "Root@123456"
        - name: MYSQL_DATABASE
          value: ctts
        ports:
        - containerPort: 3306
        volumeMounts:
        - name: mysql-data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:
  - metadata:
      name: mysql-data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 5Gi

数据验证命令序列：

# 1. 部署
kubectl apply -f ctts-mysql-dynamic.yaml

# 2. 等待Pod就绪
kubectl wait pod -l app=ctts,component=mysql --for=condition=Ready --timeout=300s

# 3. 验证PVC和自动创建的PV
kubectl get pvc
kubectl get pv

# 4. 写入测试数据
POD_NAME=$(kubectl get pod -l app=ctts,component=mysql -o jsonpath='{.items[0].metadata.name}')
kubectl exec $POD_NAME -- mysql -uroot -pRoot@123456 -e "
USE ctts;
CREATE TABLE IF NOT EXISTS users (id INT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(50));
INSERT INTO users (name) VALUES ('test_user_1'), ('test_user_2');
SELECT * FROM users;
"

# 5. 删除Pod模拟故障（StatefulSet会自动重建）
kubectl delete pod -l app=ctts,component=mysql

# 6. 等待新Pod就绪
kubectl wait pod -l app=ctts,component=mysql --for=condition=Ready --timeout=300s

# 7. 验证数据持久化
POD_NAME=$(kubectl get pod -l app=ctts,component=mysql -o jsonpath='{.items[0].metadata.name}')
kubectl exec $POD_NAME -- mysql -uroot -pRoot@123456 -e "
USE ctts;
SELECT * FROM users;
"
