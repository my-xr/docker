一、单项选择题（30题，每题2分，共60分）

19-单选-01 ★ Ingress 在 Kubernetes 中主要提供的是哪一层的负载均衡与路由？

  • A
    二层（数据链路层）
  • B
    三层（网络层）
  • C
    四层（传输层）
  • D
    七层（应用层）

答案：D 解析： Ingress 是 Kubernetes 中的七层（应用层）路由资源对象，基于 HTTP/HTTPS 的域名（Host）和路径（Path）进行请求转发，区别于 Service 的四层（IP+端口）负载均衡。

19-单选-02 ★ 下列关于 Ingress 与 Service 的区别，描述正确的是？

  • A
    两者都工作在七层
  • B
    Service 只能做四层负载，Ingress 做七层路由
  • C
    Ingress 可以替代 Service 直接管理 Pod
  • D
    Service 无法与 Ingress 配合使用

答案：B 解析： Service 提供四层（IP:Port）负载均衡与服务发现，Ingress 在七层基于 HTTP Host/Path 进行路由；Ingress 通过 Service 间接将流量转发到 Pod，不能替代 Service。

19-单选-03 ★ 下列哪个是 Kubernetes 官方维护的 Ingress Controller 实现之一？

  • A
    Traefik
  • B
    HAProxy Ingress
  • C
    NGINX Ingress Controller
  • D
    Kong Ingress

答案：C 解析： NGINX Ingress Controller 是 Kubernetes 官方维护（kubernetes/ingress-nginx）的 Ingress 控制器实现之一；Traefik、HAProxy、Kong 均为第三方实现。

19-单选-04 ★★ 安装 NGINX Ingress Controller 时，通常通过哪个命令进行部署？

  • A
    kubectl apply -f https://k8s.io/ingress-nginx/deploy.yaml
  • B
    helm install ingress-nginx ingress-nginx/ingress-nginx
  • C
    docker run -d ingress-nginx
  • D
    kubeadm init ingress-nginx

答案：B 解析： 官方推荐使用 Helm 进行安装：helm install ingress-nginx ingress-nginx/ingress-nginx，也可使用 kubectl apply -f 部署官方 manifest，但 A 中的 URL 不是官方真实地址；C/D 不是 K8s 部署方式。

19-单选-05 ★ Ingress 资源定义中，spec.rules 字段的作用是？

  • A
    定义后端 Pod 的副本数
  • B
    定义七层路由规则（Host + Path + Backend）
  • C
    定义 TLS 证书
  • D
    定义命名空间隔离

答案：B 解析： spec.rules 是 Ingress 的核心字段，用于定义基于 Host（域名）和 Path（路径）的路由规则，每条规则指定一个后端 Service。

19-单选-06 ★ Ingress 资源 YAML 中，spec.rules[].http.paths[].backend 字段必须包含哪两个子字段（最简形式）？

  • A
    serviceName 和 servicePort
  • B
    name 和 port
  • C
    host 和 path
  • D
    kind 和 apiVersion

答案：B 解析： 自 networking.k8s.io/v1 起，backend.service 下使用 name（Service 名称）和 port（端口号或名称）两个字段。A 是已废弃的 extensions/v1beta1 写法。

19-单选-07 ★★ Kubernetes 1.19+ 中 Ingress 的稳定 API 版本是？

  • A
    extensions/v1beta1
  • B
    networking.k8s.io/v1beta1
  • C
    networking.k8s.io/v1
  • D
    apps/v1

答案：C 解析： networking.k8s.io/v1 是 Kubernetes 1.19 起的稳定版本，extensions/v1beta1 和 networking.k8s.io/v1beta1 已废弃。

19-单选-08 ★ Ingress 中 pathType 字段的可选值不包括下列哪一项？

  • A
    Prefix
  • B
    Exact
  • C
    ImplementationSpecific
  • D
    Regex

答案：D 解析： pathType 在 networking.k8s.io/v1 中只有三个合法值：Prefix（前缀匹配）、Exact（精确匹配）、ImplementationSpecific（由 Ingress Controller 决定）。没有 Regex。

19-单选-09 ★★ 若希望路径 /api 同时匹配 /api、/api/、/api/v1，应使用哪种 pathType？

  • A
    Exact
  • B
    Prefix
  • C
    ImplementationSpecific
  • D
    Regex

答案：B 解析： Prefix 按路径段前缀匹配，/api 会匹配 /api、/api/、/api/v1，但不会匹配 /apiabc。

19-单选-10 ★★ 若希望路径 /health 仅精确匹配 /health，不匹配 /health/x，应使用哪种 pathType？

  • A
    Exact
  • B
    Prefix
  • C
    ImplementationSpecific
  • D
    Regex

答案：A 解析： Exact 要求 URL 路径与 path 完全一致才转发，多一个字符都不匹配，适合健康检查等单一固定路径。

19-单选-11 ★ Ingress YAML 中 spec.tls[].hosts 字段的作用是？

  • A
    列出后端 Pod 的主机名
  • B
    列出该 TLS 配置所覆盖的域名列表
  • C
    列出 Node 节点
  • D
    列出 Ingress Controller 实例

答案：B 解析： spec.tls[].hosts 是字符串数组，列出该 TLS 证书所覆盖的域名（必须与 rules 中 host 对应），配合 secretName 使用。

19-单选-12 ★★ Ingress 中 TLS 证书存储在哪种 Kubernetes 资源中？

  • A
    ConfigMap
  • B
    Secret
  • C
    ServiceAccount
  • D
    PersistentVolume

答案：B 解析： TLS 证书和私钥以 kubernetes.io/tls 类型的 Secret 存储，Ingress 通过 spec.tls[].secretName 引用该 Secret 完成 HTTPS 配置。

19-单选-13 ★★ 创建 TLS Secret 时，证书文件和私钥文件对应的 key 名称分别是？

  • A
    cert 和 key
  • B
    tls.crt 和 tls.key
  • C
    public.crt 和 private.key
  • D
    certificate 和 privateKey

答案：B 解析： kubernetes.io/tls 类型 Secret 要求两个固定 key：tls.crt（证书）和 tls.key（私钥），可用 kubectl create secret tls --cert --key 自动生成。

19-单选-14 ★ 下列命令正确创建 TLS Secret 的是？

  • A
    kubectl create secret tls my-tls --cert=cert.pem --key=key.pem
  • B
    kubectl create configmap tls my-tls --cert=cert.pem --key=key.pem
  • C
    kubectl create secret generic my-tls --cert=cert.pem --key=key.pem
  • D
    kubectl create secret docker-registry my-tls --cert=cert.pem --key=key.pem

答案：A 解析： 使用 kubectl create secret tls <name> --cert=<cert> --key=<key> 创建 kubernetes.io/tls 类型 Secret；generic 是 Opaque 类型，docker-registry 是镜像仓库凭证。

19-单选-15 ★ Ingress 资源 YAML 顶层 kind 字段的值是？

  • A
    Ingress
  • B
    IngressController
  • C
    Gateway
  • D
    Route

答案：A 解析： Ingress 资源的 kind 字段固定为 Ingress，apiVersion: networking.k8s.io/v1。

19-单选-16 ★ 下列关于 Ingress 域名虚拟主机的描述，正确的是？

  • A
    一个 Ingress 只能配置一个 host
  • B
    多个 host 可在同一 Ingress 中通过 spec.rules 数组实现虚拟主机
  • C
    不同 host 必须使用不同的 Ingress Controller
  • D
    虚拟主机不能与 TLS 同时使用

答案：B 解析： Ingress 通过 spec.rules 数组定义多条规则，每条规则可以指定不同 host，实现基于域名的虚拟主机路由；不同 host 可共用同一个 Ingress Controller。

19-单选-17 ★★ 下列 Ingress YAML 片段中，能将 http://app.example.com/v1 转发到 Service app-svc:8080 的是？ A.

rules:
- host: app.example.com
  http:
    paths:
    - path: /v1
      pathType: Prefix
      backend:
        service:
          name: app-svc
          port:
            number: 8080

B.

rules:
- host: app-svc
  http:
    paths:
    - path: /v1
      backend: app.example.com:8080

C.

rules:
- host: app.example.com
  http:
    paths:
    - path: /v1
      pathType: Regex
      backend:
        name: app-svc
        port: 8080

D.

rules:
- host: app.example.com
  paths:
  - path: /v1
    backend:
      service: app-svc:8080

答案：A 解析： A 符合 networking.k8s.io/v1 规范，pathType=Prefix、backend.service.name + port.number 结构正确。B 缺少 pathType 且 backend 结构错误；C pathType=Regex 不存在；D 缺少 http 字段且 backend 结构错误。

19-单选-18 ★ Ingress 默认后端（defaultBackend）的作用是？

  • A
    处理所有请求
  • B
    处理不匹配任何 rule 的请求
  • C
    提供 HTTPS 证书
  • D
    管理命名空间

答案：B 解析： defaultBackend（默认后端）用于处理未匹配任何 host/path 规则的请求，通常返回 404。

19-单选-19 ★★ Ingress Controller 的核心职责是？

  • A
    直接运行业务 Pod
  • B
    监听 Ingress 资源变化并生成对应反向代理配置（如 nginx.conf）
  • C
    替代 kube-scheduler
  • D
    管理 etcd 数据

答案：B 解析： Ingress Controller 持续监听 Ingress、Service、Endpoints 等资源变化，将路由规则转换为底层代理（如 NGINX）的配置并 reload，从而实现七层路由。

19-单选-20 ★ NGINX Ingress Controller 默认监听的端口是？

  • A
    80 和 443
  • B
    8080 和 8443
  • C
    30000 和 30001
  • D
    53 和 22

答案：A 解析： NGINX Ingress Controller 默认对外暴露 80（HTTP）和 443（HTTPS）端口，通过 Service 类型为 LoadBalancer 或 hostNetwork 方式接入外部流量。

19-单选-21 ★★ Ingress 资源 YAML 中 ingressClassName 字段的作用是？

  • A
    指定 Ingress 使用的 Controller
  • B
    指定 Service 类型
  • C
    指定命名空间
  • D
    指定 TLS 版本

答案：A 解析： spec.ingressClassName 用于指定该 Ingress 由哪个 IngressClass（即哪个 Ingress Controller）处理，一个集群可存在多个 Controller。

19-单选-22 ★ IngressClass 资源的作用是？

  • A
    定义 Ingress 的命名空间
  • B
    描述一个 Ingress Controller 实例及其控制器
  • C
    定义后端 Pod
  • D
    定义证书

答案：B 解析： IngressClass 是集群级资源，描述一个 Ingress Controller 实例（包括其 controller 名称、参数等），Ingress 通过 ingressClassName 关联到某个 IngressClass。

19-单选-23 ★★ 当同一 Ingress 中存在多条 path 规则时，匹配优先级通常是？

  • A
    后定义的优先
  • B
    最长前缀匹配优先
  • C
    随机匹配
  • D
    全部转发到 defaultBackend

答案：B 解析： NGINX Ingress Controller 一般采用最长前缀匹配优先的策略，/api/v1 比 /api 更具体，会优先匹配。

19-单选-24 ★ 下列哪种 Service 类型最常用于暴露 NGINX Ingress Controller 给外部用户？

  • A
    ClusterIP
  • B
    NodePort
  • C
    LoadBalancer（云厂商环境下）
  • D
    Headless

答案：C 解析： 在云厂商环境下，通常使用 type: LoadBalancer 自动分配一个外部 IP 暴露 Ingress Controller；本地/裸机环境常用 NodePort 或 hostNetwork。

19-单选-25 ★★ 关于 Ingress 与 TLS 的关系，下列描述错误的是？

  • A
    一份证书可覆盖多个域名（SAN 证书）
  • B
    TLS 配置需通过 Secret 引用证书
  • C
    启用 TLS 后 HTTP 默认会自动重定向到 HTTPS（NGINX Ingress 默认行为）
  • D
    一个 Ingress 只能引用一个 Secret

答案：D 解析： spec.tls 是数组，可以指定多组 TLS 配置，每组引用一个 Secret，覆盖不同域名，因此 D 错误。

19-单选-26 ★ Ingress YAML 中 spec.rules[].host 字段缺省时表示？

  • A
    仅匹配 localhost
  • B
    匹配所有未指定 host 的请求
  • C
    等同于 defaultBackend
  • D
    报错

答案：B 解析： 当 host 字段缺省时，该规则匹配所有未明确指定 host 的请求（即通过 IP 访问或 Host 头为空的情况）。

19-单选-27 ★★ 使用自签名证书测试 HTTPS 时，客户端应？

  • A
    直接信任
  • B
    将 CA 证书加入信任或使用 -k 跳过验证
  • C
    删除证书
  • D
    重新申请 Let's Encrypt 证书

答案：B 解析： 自签名证书不在系统信任链中，客户端需要将 CA 加入信任链，或在测试环境使用 curl -k 跳过证书校验。

19-单选-28 ★★ 关于 NGINX Ingress 的 nginx.ingress.kubernetes.io/rewrite-target 注解，描述正确的是？

  • A
    修改响应状态码
  • B
    重写请求路径后再转发到后端
  • C
    修改 Host 头
  • D
    设置超时时间

答案：B 解析： rewrite-target 注解用于在转发请求到后端 Service 前重写 URL 路径，例如将 /api/(.*) 重写为 /$1。

19-单选-29 ★ 下列哪个命令可以查看 Ingress 资源状态？

  • A
    kubectl get ingress
  • B
    kubectl describe svc
  • C
    kubectl logs ingress
  • D
    kubectl exec ingress

答案：A 解析： 使用 kubectl get ingress（简写 kubectl get ing）列出 Ingress 资源，可通过 -o wide 查看 ADDRESS 和 PORTS。

19-单选-30 ★★ 若访问 Ingress 配置的域名返回 502/503，最不可能的原因是？

  • A
    后端 Service 没有 endpoints
  • B
    后端 Pod 健康检查失败
  • C
    域名未配置 DNS 解析
  • D
    Ingress Controller 副本数过多

答案：D 解析： 502/503 通常因后端不可用（A/B）或路由错误；C 会导致域名无法解析而非 502。Ingress Controller 副本数与 502/503 无直接因果，D 最不可能。

二、多项选择题（10题，每题2分，共20分）

19-多选-01 ★ 下列属于 Ingress Controller 实现的有？（多选）

  • A
    NGINX Ingress Controller
  • B
    Traefik
  • C
    HAProxy Ingress
  • D
    kube-proxy

答案：ABC 解析： A/B/C 都是常见的 Ingress Controller 实现；kube-proxy 是四层代理组件，不是 Ingress Controller。

19-多选-02 ★★ Ingress 资源 YAML 中，一条 rule 可以包含的字段有？（多选）

  • A
    host
  • B
    http.paths
  • C
    tls
  • D
    defaultBackend

答案：AB 解析： 一条 rule 包含 host 和 http.paths；tls 和 defaultBackend 属于 spec 顶层字段，不在 rule 内。

19-多选-03 ★★ 下列关于 pathType 的描述，正确的有？（多选）

  • A
    Prefix 按路径段前缀匹配
  • B
    Exact 要求完全一致
  • C
    ImplementationSpecific 由 Controller 决定语义
  • D
    Regex 是合法的 pathType

答案：ABC 解析： A/B/C 描述正确；D 错误，pathType 没有 Regex，正则需求需通过 ImplementationSpecific + 注解实现。

19-多选-04 ★★ 在 Ingress 中配置 HTTPS 需要？（多选）

  • A
    创建 kubernetes.io/tls 类型 Secret
  • B
    在 spec.tls 中指定 hosts 和 secretName
  • C
    配置 ServiceAccount
  • D
    安装并运行 Ingress Controller

答案：ABD 解析： HTTPS 需要 TLS Secret（A）、Ingress 引用（B）和 Controller 实现（D）；与 ServiceAccount 无关。

19-多选-05 ★ Ingress 的典型应用场景包括？（多选）

  • A
    基于域名的虚拟主机
  • B
    基于路径的路由分发
  • C
    HTTPS 终结（TLS Termination）
  • D
    跨集群数据库主从同步

答案：ABC 解析： A/B/C 都是 Ingress 典型场景；D 与 Ingress 无关。

19-多选-06 ★★ 下列关于 Ingress 与 Service 关系的描述，正确的有？（多选）

三、判断题（20题，每题1分，共20分）

19-判断-01 ★ Ingress 是 Kubernetes 内置的七层路由资源对象。

答案：正确 解析： Ingress 是 Kubernetes 的标准 API 资源（networking.k8s.io/v1），提供基于 HTTP/HTTPS 的七层路由能力。

19-判断-02 ★ Service 可以完全替代 Ingress 实现基于域名的路由。

答案：错误 解析： Service 是四层（IP:Port）负载均衡，无法基于 HTTP 域名/路径路由，需要 Ingress 才能实现七层路由。

19-判断-03 ★ Ingress Controller 是 Kubernetes 控制平面核心组件，集群启动时自动运行。

答案：错误 解析： Ingress Controller 不是 K8s 控制平面核心组件，需要用户根据需要自行安装部署（如 NGINX Ingress Controller）。

19-判断-04 ★★ networking.k8s.io/v1 是 Ingress 的稳定 API 版本。

答案：正确 解析： 自 K8s 1.19 起，networking.k8s.io/v1 成为 Ingress 的稳定版本（GA），1.22 起完全移除 extensions/v1beta1。

19-判断-05 ★ Ingress 必须配置 host 字段才能工作。

答案：错误 解析： host 字段可省略，省略时该规则匹配所有未指定 host 的请求。

19-判断-06 ★★ pathType: Exact 要求请求路径与配置路径完全一致。

答案：正确 解析： Exact 模式下，URL 路径必须与 path 完全相等才匹配转发，多一个字符都不行。

19-判断-07 ★ Ingress 可以直接将流量转发到 Pod，无需经过 Service。

答案：错误 解析： Ingress 的 backend 必须指向 Service，由 Service 再转发到 Pod，不能直接指向 Pod。

19-判断-08 ★★ TLS Secret 中证书和私钥的 key 名称分别为 tls.crt 和 tls.key。

答案：正确 解析： kubernetes.io/tls 类型 Secret 固定使用 tls.crt 和 tls.key 两个 key。

19-判断-09 ★ 一个 Ingress 资源只能定义一条路由规则。

答案：错误 解析： spec.rules 是数组，可定义多条规则，支持多 host 虚拟主机和多 path 路径路由。

19-判断-10 ★★ ingressClassName 用于指定处理该 Ingress 的 Controller。

答案：正确 解析： 通过 spec.ingressClassName 关联到某个 IngressClass，从而指定由哪个 Controller 实例处理。

19-判断-11 ★ ConfigMap 也可以存储 TLS 证书用于 Ingress。

答案：错误 解析： ConfigMap 不支持敏感数据，TLS 证书必须存储在 kubernetes.io/tls 类型的 Secret 中。

19-判断-12 ★★ Ingress 与 Service 必须在同一个命名空间。

答案：正确 解析： Ingress 引用 Service 时只能引用同命名空间的 Service，跨命名空间引用不被支持。

19-判断-13 ★★ pathType: Prefix 配置 path 为 / 时可以匹配所有路径。

答案：正确 解析： / 是最短前缀，所有路径都以 / 开头，因此可作为通配规则匹配所有请求。

19-判断-14 ★ Ingress Controller 一旦安装，集群所有 Ingress 资源都会被它处理。

答案：错误 解析： 只有 Ingress 通过 ingressClassName（或 Controller 设为默认）显式关联的 Ingress 才会被该 Controller 处理。

19-判断-15 ★★ NGINX Ingress Controller 默认会将 HTTP 请求重定向到 HTTPS（当配置了 TLS 时）。

答案：正确 解析： NGINX Ingress Controller 在 Ingress 配置了 TLS 后，默认启用 ssl-redirect: true，将 80 端口请求 301 重定向到 443。

19-判断-16 ★★ 多 host 虚拟主机需要在同一 Ingress 资源中定义才能生效。

答案：错误 解析： 不同 host 可以拆分到不同 Ingress 资源中定义，只要 Ingress Controller 处理即可，虚拟主机机制不要求合并。

19-判断-17 ★ Ingress 适用于 TCP/UDP 协议的负载均衡。

答案：错误 解析： Ingress 仅支持 HTTP/HTTPS（七层），TCP/UDP 需通过 Service（NodePort/LoadBalancer）或 Ingress Controller 的扩展配置实现。

19-判断-18 ★★ kubectl create secret tls 命令需要同时提供 --cert 和 --key 参数。

答案：正确 解析： 创建 TLS Secret 必须同时提供证书文件（--cert）和私钥文件（--key），缺一不可。

19-判断-19 ★★ defaultBackend 用于处理未匹配任何规则的请求。

答案：正确 解析： spec.defaultBackend 指定默认后端，处理未匹配任何 host/path 规则的请求，通常返回 404。

19-判断-20 ★★★ Ingress 配置 rewrite-target 注解后，原 path 不会被传到后端 Service。

答案：正确 解析： rewrite-target 会按规则重写 URL 后再转发，后端收到的是重写后的路径，原始 path 不直接透传。

19-论述-01 ★★（8分） 请论述 Ingress 与 Service 在 Kubernetes 中的区别与联系，并说明各自适用的场景。

评分标准（满分8分）：

  • 概念区别（3分）：Service 是四层（IP:Port）负载均衡与服务发现，提供稳定访问入口；Ingress 是七层（HTTP/HTTPS）路由资源，基于 Host/Path 转发。
  • 联系（3分）：Ingress 不能脱离 Service 独立工作，其 backend 必须指向 Service，由 Service 转发到 Pod；Ingress 是 Service 之上的七层路由层。
  • 适用场景（2分）：Service 适合 TCP/UDP 四层暴露、内部服务发现；Ingress 适合按域名/路径对外统一暴露多个 HTTP 服务、TLS 终结、虚拟主机等场景。

参考答案：

  1. 区别：
    • Service（ClusterIP/NodePort/LoadBalancer）工作在四层，基于 IP+端口转发，不感知 HTTP 协议内容。
    • Ingress 工作在七层，能基于 HTTP 的 Host 头和 URL Path 做精细化路由。
  2. 联系：
    • Ingress 的 backend.service 引用一个 Service，Ingress 将流量交给 Service，Service 再负载到 Pod。
    • Ingress 是 Service 之上的"七层路由层"，二者协同工作。
  3. 场景：
    • Service：内部服务互访、数据库等非 HTTP 协议暴露。
    • Ingress：对外统一域名入口、按路径拆分微服务、HTTPS 证书集中管理、灰度发布等。

19-论述-03 ★★★（8分） 请论述 Ingress 中 pathType 三种取值的含义、匹配规则及典型使用场景，并举例说明。

评分标准（满分8分）：

  • 三种取值含义（3分）：Prefix 前缀匹配、Exact 精确匹配、ImplementationSpecific 由 Controller 决定。
  • 匹配规则（3分）：Prefix 按路径段前缀（如 /api 匹配 /api、/api/、/api/v1，不匹配 /apiabc）；Exact 完全相等；ImplementationSpecific 由 Controller 自定义（NGINX 默认按 Prefix，可结合注解支持正则）。
  • 场景与示例（2分）：Prefix 适合业务前缀路由；Exact 适合健康检查端点；ImplementationSpecific 适合特殊匹配需求。

参考答案：

  1. Prefix（前缀匹配）：按 / 分段的前缀匹配，path: /api 能匹配 /api、/api/、/api/v1，但不匹配 /apixyz。是最常用的路由模式，适合微服务按业务前缀拆分。
  2. Exact（精确匹配）：要求 URL 路径与 path 完全一致，path: /health 仅匹配 /health，不匹配 /health/db。适合健康检查、心跳接口等单一固定路径。
  3. ImplementationSpecific（实现特定）：语义由 Ingress Controller 自定义。在 NGINX Ingress 中默认按 Prefix 处理，若使用 nginx.ingress.kubernetes.io/use-regex: "true" 注解，则可支持正则表达式匹配，适合复杂 URL 模式（如 /api/v[0-9]+/users）。

19-论述-04 ★★（6分） 简述 Ingress 配置 HTTPS 的完整流程，并说明证书与 Secret 的关系。

评分标准（满分6分）：

  • 流程（4分）：① 准备证书与私钥文件；② 用 kubectl create secret tls 创建 kubernetes.io/tls 类型 Secret；③ 在 Ingress 的 spec.tls 中引用该 Secret，并指定 hosts；④ 部署 Ingress，Controller 自动加载证书并监听 443。
  • 证书与 Secret 关系（2分）：证书+私钥以 tls.crt/tls.key 形式存于 Secret，Ingress 通过 secretName 引用，实现证书与 Ingress 解耦。

参考答案：

  1. 准备证书 cert.pem 和私钥 key.pem（可来自自签名、商业 CA 或 Let's Encrypt）。
  2. 创建 Secret： 
    kubectl create secret tls app-tls --cert=cert.pem --key=key.pem
    Secret 类型自动为 kubernetes.io/tls，包含 tls.crt 和 tls.key 两个 key。
  3. 在 Ingress 中引用： 
    spec:
  tls:
  - hosts:
    - app.example.com
    secretName: app-tls
  rules:
  - host: app.example.com
    http: {...}
  4. 部署后 Controller 加载证书并监听 443，默认将 80 端口请求 301 重定向到 443。
  5. 证书与 Secret 的关系：Secret 是 K8s 中存储敏感数据的资源对象，TLS Secret 专门存储证书和私钥；Ingress 通过 secretName 引用 Secret，实现证书生命周期与 Ingress 解耦，更新证书只需更新 Secret 即可。

19-编程-02 ★★★（20分） 请编写一个完整的 Ingress YAML，实现多域名虚拟主机 + TLS + 路径重写，需求如下：

  1. Ingress 名称：multi-app-ingress，命名空间：prod；
  2. 使用 NGINX Ingress Controller；
  3. 同时配置两个域名：
    • app.example.com：路径 /api/v1/* → Service app-v1-svc:8000，并在转发前将路径重写为 /*（去掉 /api/v1 前缀）；
    • admin.example.com：路径 / → Service admin-svc:80（Prefix）；
  4. 两个域名均启用 HTTPS：
    • app.example.com 使用 Secret app-tls；
    • admin.example.com 使用 Secret admin-tls；
  5. 为 app.example.com 启用金丝雀发布（10% 流量），金丝雀后端 Service 为 app-v1-canary-svc:8000（提示：使用 canary 注解 + 单独的 Ingress 资源），请同时给出主 Ingress 和金丝雀 Ingress 两份 YAML。

评分标准（满分20分）：

  • 主 Ingress 基本结构（apiVersion/kind/metadata.name/namespace）（2分）
  • ingressClassName: nginx（1分）
  • 两组 TLS 配置正确（4分，每组2分）
  • app.example.com 规则正确：path=/api/v1、pathType=Prefix、backend app-v1-svc:8000（3分）
  • admin.example.com 规则正确：path=/、Prefix、backend admin-svc:80（2分）
  • rewrite-target 注解 + use-regex 注解（或 capture 组）正确（3分）
  • 金丝雀 Ingress 独立定义，包含 canary 注解（3分）
  • canary-weight: "10"、canary-by-weight（2分）

参考答案：

主 Ingress：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-app-ingress
  namespace: prod
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: "/$2"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - app.example.com
    secretName: app-tls
  - hosts:
    - admin.example.com
    secretName: admin-tls
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api/v1(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: app-v1-svc
            port:
              number: 8000
  - host: admin.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: admin-svc
            port:
              number: 80

金丝雀 Ingress：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-app-ingress-canary
  namespace: prod
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: "/$2"
spec:
  ingressClassName: nginx
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api/v1(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: app-v1-canary-svc
            port:
              number: 8000

说明： 金丝雀 Ingress 通过 canary: "true" 注解标记为副本，canary-weight: "10" 表示 10% 流量进入金丝雀后端，主 Ingress 与金丝雀 Ingress 的 host/path 必须完全一致才能形成金丝雀关系。
