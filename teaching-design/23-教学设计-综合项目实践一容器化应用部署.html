课程：Docker云容器与管理技术 ｜ 课次：第 23 次课 ｜ 文档：教学设计

课程名称：Docker云容器与管理技术 模块归属：M8 综合项目实践模块 课时：2学时（90分钟） 课型：实践课（任务驱动型） 贯穿项目：CTTS（云原生交通违章管理系统）

一、教学目标

1. 知识目标

  • K1：系统梳理 Pod、Deployment、Service、Ingress、ConfigMap、Secret、PV、PVC 等 K8s 核心资源对象在真实项目中的协作关系与编排顺序。
  • K2：掌握多服务（前端 + 后端 + 数据库）应用在 K8s 集群中的部署架构、服务发现机制与数据流走向。
  • K3：理解 K8s 声明式编排思想在复杂业务场景中的应用，明确"配置即基础设施"的云原生理念。

2. 能力目标

  • A1：能够独立编写 CTTS 项目的全部 K8s 资源清单 YAML 文件（MySQL、Backend、Frontend、Ingress 共 12+ 个资源对象）。
  • A2：能够使用 kubectl 命令在 Minikube 集群中完成部署、扩缩容、服务暴露与全链路验证。
  • A3：能够运用 kubectl describe、kubectl logs、kubectl get events 等命令进行 Pod Pending、CrashLoopBackOff、ImagePullBackOff 等典型故障的定位与排查。
  • A4：能够通过 Ingress 实现基于域名的路由分发，并通过 curl 与浏览器完成端到端联调验证。

3. 素质目标（课程思政）

  • S1（系统思维）：从单容器到多服务集群的完整链路认知，培养学生"全局视角、分层解耦"的工程系统思维。
  • S2（工匠精神）：在 YAML 编写与调试中培养严谨细致、精益求精的工程师素养，体会"配置即代码"的工程规范。
  • S3（协作意识）：理解 DevOps 文化中开发与运维协同的核心理念，形成"一次定义、处处运行"的标准化交付意识。
  • S4（自主攻坚）：通过真实故障排查场景锻炼学生独立分析问题、查阅文档、复用经验的自学能力与抗压能力。

二、教学重点与难点

教学重点

  1. CTTS 三服务（MySQL/Backend/Frontend）K8s 资源清单的完整编写规范与字段语义。
  2. ConfigMap 与 Secret 在数据库配置、应用配置、镜像敏感信息注入中的实际用法。
  3. PV/PVC 与 MySQL Stateful 数据持久化的绑定流程。
  4. Ingress 域名路由规则与前后端联调验证方法。

教学难点

  1. 服务间依赖顺序：MySQL → Backend → Frontend 的启动次序与就绪探测配合。
  2. 配置注入闭环：ConfigMap/Secret 如何通过环境变量与 Volume 挂载两种方式进入容器，并与 SpringBoot 应用配置衔接。
  3. Ingress 与 Minikube addon：minikube ingress addon 的启用、Ingress Controller 工作机制与本地 hosts 解析。
  4. 故障链路定位：从 Pod 状态异常到根因（资源不足/配置错误/镜像拉取失败/探针失败）的快速定位方法论。

三、学情分析

  • 前置基础：学生已系统学习 M1-M7 模块，掌握 Docker 镜像构建、K8s 核心资源对象（Pod/Deployment/Service/Ingress/ConfigMap/Secret/PV/PVC）的单点用法，具备基本的 YAML 阅读与 kubectl 操作能力。
  • 薄弱环节：缺少多资源对象综合编排的实战经验，对"配置注入链路""服务依赖""故障排查链路"缺乏整体认知；YAML 字段易拼写错误、缩进不规范。
  • 学习偏好：实践课学生参与度高，偏好"边做边学"；但对失败场景的容忍度低，需教师及时给出排查路径而非直接给答案。
  • 差异化需求：约 20% 学生 YAML 编写速度较快，可挑战 Ingress TLS、滚动升级等进阶任务；约 30% 学生需逐步引导，重点保证基础部署成功。

五、教学环境与资源

七、实践任务书

任务总览

将 CTTS 项目（前端 Vue3 + Nginx、后端 SpringBoot、数据库 MySQL）完整部署到 Minikube K8s 集群，并通过 Ingress 域名路由实现外部访问。

子任务与验收标准

编号 子任务 验收标准 分值
T1 MySQL 部署 Pod Running；PVC 已绑定；kubectl exec 进入容器能查询到 ctts 数据库与初始表 20
T2 Backend 部署 Pod Running；/actuator/health 返回 {"status":"UP"}；日志显示"数据库连接成功" 25
T3 Frontend 部署 Pod Running；curl <frontend-svc> 返回 index.html 内容；静态资源 200 20
T4 Ingress 配置 curl -H "Host: frontend.ctts.local" $(minikube ip) 返回前端页面；curl -H "Host: api.ctts.local" $(minikube ip)/api/xxx 返回后端接口数据 20
T5 故障排查 完成 ≥3 个典型故障的定位与修复，填写排查表 10
T6（选做） 进阶挑战 Ingress TLS 配置成功；或实现 Backend 滚动升级；或实现 Pod 水平扩缩容 加 10 分

提交物

  1. 全套 YAML 文件（mysql.yaml、backend.yaml、frontend.yaml、ingress.yaml、namespace.yaml）。
  2. 部署验证截图（kubectl get all、curl 测试、浏览器访问）。
  3. 故障排查表（≥3 个案例）。
  4. 简要实践报告（500字以内，含遇到的问题与解决思路）。

八、课堂互动设计

互动一：知识点快闪回顾（导入环节，3分钟）

教师抛出 6 个关键词（Pod、Deployment、Service、ConfigMap、Secret、PV/PVC），学生轮流用一句话说出"它在 CTTS 项目中扮演什么角色"。 目的：激活前置知识，建立"对象-场景"映射。

互动二：故障排查研讨（75-85分钟）

采用"问题漂流"模式：

  1. 每位学生在便签上写下自己遇到的 1 个部署问题与解决思路。
  2. 便签在小组内漂流，其他成员补充或验证。
  3. 每组推选 1 个典型问题全班分享。
  4. 教师点评并归入"常见问题排查表"。

目的：把个体试错转化为集体经验沉淀。

互动三：链路图绘制（总结环节）

请 1-2 名学生上台在白板绘制 CTTS 在 K8s 中的完整请求链路图（用户 → Ingress → Service → Pod → 数据库），其他学生补充修正。 目的：检验"从容器到集群"链路认知的达成度。

十一、课后作业与拓展

必做作业

  1. 完成第23次课题库.md 中 ≥40 道题目，正确率 ≥80%。
  2. 提交实践报告（500字以内）+ 全套 YAML + 验证截图。

选做拓展

  1. Ingress TLS：为 frontend.ctts.local 与 api.ctts.local 配置 HTTPS（自签名证书）。
  2. 滚动升级：修改 Backend 镜像版本，观察 K8s 滚动升级过程，验证零停机。
  3. 水平扩缩容：将 Backend 扩展到 3 个副本，通过 kubectl get pods -w 观察负载分发。
  4. HPA 自动扩缩容：部署 metrics-server，配置 HPA 基于 CPU 自动扩缩容。

预习任务

  • 预习第24次课：Helm 包管理基础（Chart 结构、模板渲染、Repository）。
  • 思考：将 CTTS 全套 YAML 用 Helm Chart 重构后，能带来哪些收益？

十二、教学反思（课后填写）

实施情况

改进方向

  • YAML 模板是否需要进一步脚手架化（提供 stub 让学生填空）？
  • 故障注入环节是否覆盖了核心场景？是否需要增加 NetworkPolicy、ResourceLimit 场景？
  • 思政融入是否自然？是否需要更多一线工程案例？

学生反馈

  • 课堂反馈问卷结果（1-5 分）：任务难度 ___ / 实践收获 ___ / 资料完整度 ___ / 思政融入 ___。
  • 学生建议摘要：__________________________。

设计说明：本设计以"真实项目 + 任务驱动 + 故障注入 + 复盘研讨"为核心特色，强调学生动手实践与问题解决能力培养，思政元素自然融入工程实践场景，避免说教化。90分钟时间分配紧凑但留有弹性，教师可根据学生进度灵活调整演示与实践比例（建议 3:7）。
