二、教学目标

知识目标

  1. 理解 Pod 的概念——Pod 是 K8s 最小调度单元，明确"为什么需要 Pod 而非直接管容器"。
  2. 掌握 Pod 内容器共享网络和存储的机制，理解一个 Pod 可含多个容器（主容器 + 辅助容器）。
  3. 掌握 Pod YAML 的四要素结构（apiVersion / kind / metadata / spec）。
  4. 掌握容器定义核心字段：image / ports / env / resources（requests/limits）/ command / args / imagePullPolicy。
  5. 理解 Pod 生命周期与五种状态（Pending / Running / Succeeded / Failed / Unknown）。
  6. 掌握 Pod 创建流程、重启策略（restartPolicy）与终止流程。
  7. 熟练使用 kubectl 操作 Pod 的命令：run / get / describe / logs / exec / delete / apply -f。

能力目标

  1. 能够用自己的语言准确描述"什么是 Pod""为什么 K8s 用 Pod 而非直接管容器"。
  2. 能够独立编写一份完整的 Pod YAML（含 metadata、spec.containers、resources、ports、env）。
  3. 能够使用 kubectl run 快速创建 Pod，使用 kubectl apply -f 从 YAML 创建 Pod。
  4. 能够使用 kubectl get / describe / logs / exec / delete 完整管理 Pod 生命周期。
  5. 能够根据 Pod 状态（Pending / Failed / CrashLoopBackOff）初步排查问题。
  6. 能够编写 CTTS 后端 Pod YAML 并部署到集群，验证运行与日志。

素质目标（课程思政）

  1. 培养"精细管理"意识——K8s 中每个资源都是声明式定义，YAML 即"意图的代码化"。
  2. 培养"工程规范"意识——YAML 字段规范、资源限制必填，是生产可运维的基础。
  3. 建立"声明式思维"——从"命令式操作"转向"声明式定义"，是云原生核心思维转变。

五、课堂互动设计

互动 1：课前 5 分钟讨论（开场导入）

项目 内容
互动问题 "第 14 次课我们搭好了 K8s 集群。现在要把 CTTS 后端跑在 K8s 上，为什么不直接像 Docker 那样 docker run 一个容器，而要先引入 Pod 这个概念？K8s 多此一举吗？"
组织方式 自由发言，教师板书关键词，不评判对错
预期学生输出 提到"容器需要管理""多个容器一起跑""网络要打通""K8s 不能直接操作容器"等关键词
教师点评要点 肯定合理直觉，引出 K8s 的设计哲学——K8s 不直接管容器，而是管 Pod（容器组），Pod 是最小调度单元。引出 K15-1。

互动 2：代码阅读——分析 Pod YAML 各字段（讲解 K15-2、K15-3 后）

项目 内容
互动任务 教师投影一份完整的 CTTS 后端 Pod YAML（含 apiVersion/kind/metadata/spec/containers，含 resources/ports/env/imagePullPolicy），学生分组（4~5 人）阅读并回答：① 四要素各是什么？② metadata 里 name/labels/namespace 各起什么作用？③ spec.containers 里 image/ports/env/resources 分别定义什么？④ resources 里 requests 和 limits 有什么区别？⑤ imagePullPolicy 三种策略分别什么时候用？
组织方式 小组讨论 5 分钟 → 每组派代表回答 1 个问题（抽签决定）→ 教师逐题点评
预期学生输出 能识别四要素；能区分 name 是唯一标识、labels 是标签选择、namespace 是隔离空间；能说出 image 是镜像、ports 是端口、env 是环境变量、resources 是资源限制；能大致说出 requests 是保底、limits 是上限；imagePullPolicy 可能说不全
教师点评要点 重点纠正 resources.requests 和 limits 的理解（requests 影响调度、limits 限制上限）；imagePullPolicy 三种策略的适用场景（Always 用于 latest 标签、Never 用于本地镜像、IfNotPresent 是默认）；强调 YAML 是声明式定义——"你写的是什么，K8s 就给你维持什么"

互动 3：Pod 状态流转画图（讲解 K15-4 后）

项目 内容
互动任务 请学生在纸上画出 Pod 的五种状态（Pending / Running / Succeeded / Failed / Unknown）及其流转关系，并标出每种状态发生的时机
组织方式 个人独立完成 3 分钟 → 同桌互查 1 分钟 → 教师投影标准状态图讲解
预期学生输出 能画出 Pending → Running 的主流转；能标出 Running → Succeeded（正常结束）和 Running → Failed（异常退出）；Unknown 可能画错或漏掉
教师点评要点 纠正常见错误（如把 Unknown 当成正常状态——Unknown 是与节点失联时的异常状态）；强调 Succeeded 主要用于 Job 类 Pod（一次性任务），长期运行的服务 Pod 通常是 Running 或 Failed；引出 restartPolicy 决定 Failed 后是否重启

互动 4：kubectl 命令实操演示（讲解 K15-5 后）

项目 内容
互动任务 教师现场演示 kubectl 操作 Pod 的完整流程：kubectl run 快速创建 → kubectl get pods 查看 → kubectl describe pod 看详情 → kubectl logs 看日志 → kubectl exec 进入容器 → kubectl delete pod 删除 → kubectl apply -f 从 YAML 创建。学生同步在自己的 Minikube 上操作
组织方式 教师演示一个命令 → 学生跟做 → 教师巡视 → 下一个命令
预期学生输出 学生能跟做成功；部分学生可能出现"Pod Pending""ImagePullOff""CrashLoopBackOff"等问题
教师点评要点 现场排查学生遇到的问题，演示用 kubectl describe 和 logs 定位根因；强调"Pod 出问题先 describe 看 Events、再 logs 看应用日志"的排查套路

六、课程思政融入点

项目 内容
融入点 精细管理——每个资源都是声明式定义
技术关联 K8s 采用声明式 API：用户写 YAML 描述"期望状态"，K8s 控制器负责让实际状态趋近期望状态。这与传统"命令式"（敲一条命令做一件事）有本质区别。Pod YAML 里的每个字段（image/ports/env/resources）都是对资源的精细定义，resources.requests/limits 体现了对资源的精细管控
引导问题 "为什么 K8s 要用 YAML 声明式定义，而不是像 Docker 那样用命令式操作？声明式带来什么好处？"
预期价值目标 培养学生的"精细管理"意识和"声明式思维"——在云原生时代，运维从"敲命令"转向"写定义"，每个资源都要被精确描述。这种思维迁移到任何工程领域都是"规范化、可复现、可审计"的基础

思政自然融入，不空喊口号。通过"声明式 vs 命令式"的对比让学生体会云原生运维的思维转变。

七、课堂练习或随堂测验

随堂练习（5 分钟，讲解结束前进行）

判断题（口头快速作答）：

  1. Pod 是 K8s 中可以直接操作容器的最小单元，K8s 不直接管容器。（✓）
  2. 一个 Pod 只能包含一个容器。（✗）
  3. Pod YAML 中的 resources.requests 表示资源上限，resources.limits 表示资源保底。（✗）
  4. imagePullPolicy: Always 表示每次创建容器都去仓库拉取镜像。（✓）
  5. Pod 状态为 CrashLoopBackOff 表示容器反复崩溃重启。（✓）

详细题目与解析见 题库.md。此处仅作课堂快速互动，不计分。

八、课后任务

  1. 阅读：通读同文件夹 教学资料.md，重点理解 Pod 概念、Pod YAML 四要素、容器定义字段、Pod 生命周期与状态、kubectl 命令。
  2. 动手实践：在自己的 Minikube 集群上完成教学资料中的所有 kubectl 命令示例（run/get/describe/logs/exec/delete/apply），记录每条命令的输出。
  3. 编写 YAML：独立编写一份 CTTS 后端 Pod YAML（要求含 apiVersion/kind/metadata/spec/containers，含 image/ports/env/resources/imagePullPolicy），下次课抽查。
  4. 排查练习：故意把 CTTS 后端 Pod 的 image 改成不存在的镜像名，观察 Pod 状态（应为 ImagePullBackOff），用 kubectl describe 和 logs 排查并记录排查过程。
  5. 思考：对比 kubectl run 和 kubectl apply -f 两种创建 Pod 的方式，各有什么优缺点？生产环境推荐哪种？为什么？
  6. 拓展阅读：访问 K8s 官方文档（kubernetes.io/zh-cn/docs/concepts/workloads/pods/）了解 Pod 的更多内容（选做）。
