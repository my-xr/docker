二、教学目标

知识目标

  1. 理解 Docker Compose 的概念与作用，明确"单机多容器编排"痛点与 Compose 的解决思路。
  2. 掌握 docker-compose.yml 文件的顶层结构（version / services / networks / volumes）。
  3. 掌握 services 下的核心配置项（image / build / ports / volumes / depends_on / environment / networks / restart / container_name）。
  4. 掌握自定义 networks 与 volumes 的定义方式以及服务如何引用它们。
  5. 掌握 docker compose 常用命令（up -d / down / logs / ps / exec / start / stop / restart / -f / --scale）。
  6. 能编写 CTTS 三服务（MySQL + Backend + Frontend）完整的 Compose 编排文件，理清服务依赖顺序。

能力目标

  1. 能够把"手动启动多个容器 + 配网络 + 挂数据卷"的繁琐流程，转化为一个 docker-compose.yml 一键启动。
  2. 能够根据项目架构图（前端→后端→数据库）正确设计 depends_on 依赖顺序。
  3. 能够使用 docker compose up -d、docker compose logs -f、docker compose down 等命令完成多容器应用的部署、排查与回收。
  4. 能够通过 docker compose ps、docker compose exec 等命令检查与调试多服务编排结果。

素质目标（课程思政）

  1. 建立"工程化"意识——编排让部署可重复、可版本化、可回滚，告别"手工部署玄学"。
  2. 培养"声明式思维"——用一份 YAML 描述"我要什么"，而非"我怎么做"，为 K8s 声明式 API 打底。
  3. 强化"系统思维"——多服务部署不是单点累加，而是依赖、网络、存储的整体协同。

四、项目任务或案例任务

贯穿项目阶段 4：Compose 编排三服务

本次课任务：

  1. 教师演示"手工启动 CTTS 三服务"的痛苦流程（连敲 3 条 docker run + 配网络 + 挂数据卷，每次重启都要重来）。
  2. 引出 Compose 的价值：把多服务部署写成一份 YAML，一条 docker compose up -d 完成。
  3. 学生跟随教师一步步编写 CTTS 三服务 docker-compose.yml：MySQL 服务 → Backend 服务 → Frontend 服务。
  4. 课堂最后完成"接口设计讨论——服务依赖顺序"，理清 depends_on 的设计依据。

项目背景回顾：

  • 项目名称：多服务容器化部署项目
  • 项目架构：CTTS 前端（Vue3）+ CTTS 后端（SpringBoot）+ MySQL 三服务
  • 本课阶段：把第 8 次课构建出的前后端镜像 + 官方 MySQL 镜像，编排成一套可一键启动的多服务应用
  • 与第 12 次课衔接：本课写出编排文件并完成理论验证，第 12 次课进入综合实践，端到端打通部署

📌 本节课重点是编写 docker-compose.yml 文件并理解 Compose 命令；实操落地在第 12 次课综合实践。

五、课堂互动设计

互动 1：开场痛点复盘（课前 5 分钟）

项目 内容
互动问题 "上节课我们用 docker run 手动启动了 MySQL 容器。如果让你把 CTTS 三个服务（MySQL + 后端 + 前端）用 docker run 启动起来，你会怎么写？请估算需要敲多少条命令、配置多少参数？"
组织方式 自由发言，教师板书学生提到的命令和参数
预期学生输出 3 条 docker run（mysql / backend / frontend）；还要 docker network create；后端要 -e MYSQL_HOST=mysql；前端要 -p 80:80；启动顺序错了后端会连不上数据库；每次重启都要重新敲一遍
教师点评要点 肯定学生的痛点感知——"3 条命令 + 网络配置 + 启动顺序 + 环境变量"组合起来极易出错，且不可复现。引出"如果用一份文件描述全部，一条命令启动"就是 Compose 的核心价值，引出 K11-1

互动 2：服务依赖顺序讨论（核心互动，讲解 K11-6 时）

项目 内容
互动问题 "CTTS 三个服务的启动顺序应该怎么排？为什么？如果用 depends_on 控制顺序，能保证后端连数据库时 MySQL 一定就绪了吗？"
组织方式 小组讨论 5 分钟（4~5 人/组）→ 每组派代表发言 1 分钟 → 教师板书各组方案
预期学生输出 顺序：MySQL → Backend → Frontend；理由：后端依赖数据库、前端依赖后端 API；depends_on 能控制启动顺序但不保证就绪；可能提出"健康检查 + depends_on condition"
教师点评要点 强调三点：① 启动顺序 ≠ 就绪顺序，MySQL 进程启动了不代表已经能接受连接；② 生产环境应配合 healthcheck + depends_on: condition: service_healthy；③ 前端依赖后端是"调用依赖"而非"启动依赖"，可选 depends_on。引出工程化思维：编排不是"启动就行"，还要"就绪才用"

互动 3：YAML 找错（讲解 K11-3 后）

项目 内容
互动任务 投影一段有 3 处错误的 docker-compose.yml（如：services 缩进错、ports 写成单边、depends_on 引用了不存在的服务），学生找出并改正
组织方式 个人独立完成 3 分钟 → 同桌互查 1 分钟 → 教师投影正解
预期学生输出 找出缩进错误（YAML 严格要求缩进）；找出 ports 应为列表格式 "8080:8080"；找出 depends_on 引用的服务名应与 services 下定义的一致
教师点评要点 强调 YAML 的两个"坑"：① 缩进必须一致（不能 Tab/空格混用）；② 列表与字典格式区分。引出工程规范意识——YAML 是声明式配置，写错一个字符就启动不了

互动 4：命令对照（讲解 K11-5 后）

项目 内容
互动任务 给出 5 个 docker compose 子命令（up -d / down / logs / ps / exec），让学生说出对应的"手工 docker 命令"等价操作
组织方式 全班抢答，每题 30 秒
预期学生输出 up -d ≈ 批量 docker run；down ≈ 批量 docker stop && docker rm + 删网络；logs ≈ 批量 docker logs -f；ps ≈ 批量 docker ps；exec ≈ docker exec -it
教师点评要点 强调 Compose 的本质是"按服务名批量管理一组关联容器"，并不是新引擎，而是 Docker CLI 的子命令。引出 v2 关键变化：docker compose（空格）替代了 v1 的 docker-compose（连字符）

六、课程思政融入点

项目 内容
融入点 工程化——编排让部署可重复
技术关联 Compose 把"散落的命令 + 参数"收敛为一份 docker-compose.yml，可入 Git 版本管理、可 Code Review、可一键复现。这正是工程化交付的核心：把"人的操作"转化为"机器可执行的描述"。声明式 YAML 思维也是 K8s 资源清单的预演
引导问题 "如果团队里只有某一位老员工知道怎么手动启动 CTTS 三服务（依赖顺序、端口、环境变量都记在他脑子里），这个团队有什么风险？把部署写成 docker-compose.yml 入库后，解决了哪些问题？"
预期价值目标 树立工程规范意识——部署应可描述、可复现、可审计；培养"文档化 / 代码化"的协作思维，避免"老员工离职带走部署知识"的工程风险

思政自然融入，不空喊口号。通过"手工部署 vs 编排部署"的对比，让学生体会工程化的真实价值。

七、课堂练习或随堂测验

随堂练习（5 分钟，讲解结束前进行）

判断题（口头快速作答）：

  1. docker-compose.yml 中的 version 字段在 Compose v2 中已不再必需。（✓）
  2. depends_on 既能控制启动顺序，也能保证依赖服务"就绪"。（✗）
  3. docker compose down 会停止并删除容器，同时默认删除网络。（✓）
  4. docker compose up -d 启动时，若镜像本地不存在会自动尝试拉取。（✓）

详细题目与解析见 题库.md。此处仅作课堂快速互动，不计分。

八、课后任务

  1. 阅读：通读同文件夹 教学资料.md，重点理解 docker-compose.yml 顶层结构、services 配置项、depends_on 的局限。
  2. 手写：在本地新建一个 docker-compose.yml，把课堂讲的 CTTS 三服务编排文件完整敲一遍（不要复制粘贴），保存为下次综合实践的基线文件。
  3. 思考：用 200 字回答"为什么 depends_on 不能保证 MySQL 真正就绪？生产环境应该怎么补？"，下次课抽查。
  4. 拓展练习：尝试用 docker compose --scale backend=3 把后端服务扩展为 3 个实例，观察 docker compose ps 输出，思考负载如何分担（提示：Compose 本身不做负载均衡，需要配合外部反向代理）。
  5. 拓展阅读：访问 https://docs.docker.com/compose/compose-file/ 浏览 Compose File 完整参考（选做，为第 12 次课综合实践打底）。
  6. 项目准备：每组完善《CTTS Compose 编排方案》（1 页），列出三服务的镜像名、端口、环境变量、依赖关系，下次综合实践课带过来。
