二、教学目标

2.1 知识目标

  • K21-1：理解配置管理需求，能阐述"配置与镜像解耦、环境差异、敏感信息保护"三大动机，说明为什么不能把配置写死在镜像或YAML里。
  • K21-2：掌握ConfigMap概念与创建方式（kubectl create configmap --from-literal/--from-file、YAML定义），明确ConfigMap数据是明文存储。
  • K21-3：掌握Secret概念与创建方式（base64编码、kubectl create secret generic/docker-registry/tls、YAML定义），区分Opaque/dockerconfigjson/tls三种类型。
  • K21-4：掌握两种挂载方式（环境变量env/envFrom、Volume文件挂载volumes/items），理解subPath的作用与局限。
  • K21-5：掌握ConfigMap Volume挂载的自动热更新机制，理解env方式不自动更新、Secret不建议热更新的原因。

2.2 能力目标

  • 能独立为CTTS项目将MySQL数据库配置提取为ConfigMap、将密码提取为Secret，并挂载到SpringBoot Pod。
  • 能根据场景选择合适的挂载方式：环境变量（简单键值）vs Volume文件挂载（多文件/配置热更新）。
  • 能使用 kubectl get/describe/edit configmap/secret 完成配置的查看、修改、热更新验证。
  • 能识别并修复"密码明文写在YAML"这类常见安全隐患。

2.3 素质目标

  • 工程素养：建立"配置与代码分离、镜像与环境无关"的云原生十二要素应用意识。
  • 安全意识：养成"敏感信息一律走Secret、绝不入库/入镜像/入YAML明文"的红线意识。
  • 严谨态度：base64是编码不是加密，理解技术细节背后的安全边界，避免"看起来安全"的假象。
  • 运维思维：从"改配置要不要重启"这一具体问题，体会配置热更新对业务连续性的价值。

四、项目任务

4.1 任务名称

CTTS配置外置化——数据库配置ConfigMap + 密码Secret

4.2 任务背景

CTTS后端SpringBoot连接MySQL，目前数据库地址、端口、库名、密码全部硬编码在 application.yml 中，被打进镜像。带来的问题：

  • 切换环境（dev用本地MySQL、test用Minikube里的MySQL、prod用RDS）必须改代码重新构建镜像。
  • 密码 root123456 写在YAML里，git提交后全班可见，存在安全风险。
  • 改密码要重新打镜像，运维成本高。

本次课通过ConfigMap + Secret解决这三个问题。

4.3 任务产出

  1. ctts-db-configmap.yaml（数据库URL、驱动、用户名等非敏感配置）
  2. ctts-db-secret.yaml（数据库密码）
  3. ctts-backend-deployment.yaml（同时挂载ConfigMap和Secret到Pod）
  4. 验证记录：kubectl get configmap/secret、kubectl exec 进入Pod打印环境变量、kubectl edit configmap 触发热更新观察Pod内文件变化

4.4 任务流程

分析application.yml → 区分敏感/非敏感配置 → 创建ConfigMap（非敏感）
→ 创建Secret（密码）→ 修改Deployment挂载配置 → 应用YAML
→ 进入Pod验证环境变量/挂载文件 → 修改ConfigMap验证热更新 → 排查报错

五、课堂互动

5.1 互动一：代码找错——密码明文存储反例（核心互动，约10分钟）

问题：教师展示如下"有问题的"Deployment YAML，请学生找出其中至少3处配置管理方面的隐患。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ctts-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ctts-backend
  template:
    metadata:
      labels:
        app: ctts-backend
    spec:
      containers:
      - name: ctts-backend
        image: ctts/backend:v1
        env:
        - name: SPRING_DATASOURCE_URL
          value: "jdbc:mysql://mysql-svc:3306/ctts?useSSL=false"
        - name: SPRING_DATASOURCE_USERNAME
          value: "root"
        - name: SPRING_DATASOURCE_PASSWORD
          value: "root123456"          # ← 隐患1：密码明文
        - name: REDIS_PASSWORD
          value: "redis@2024"            # ← 隐患2：密码明文
        - name: JWT_SECRET
          value: "myJwtSecret123"        # ← 隐患3：密码明文
        - name: LOG_LEVEL
          value: "DEBUG"                 # ← 隐患4：环境差异配置硬编码

提问清单：

  1. 上述YAML中有几处敏感信息明文存储？分别是什么？
  2. 如果把这份YAML提交到Git仓库，会带来哪些风险？
  3. LOG_LEVEL=DEBUG 在生产环境是否合适？如何实现dev/prod差异化？
  4. 如果要修改密码，按当前写法需要执行哪些操作？改造后呢？
  5. 请给出改造方案：哪些配置用ConfigMap？哪些用Secret？

组织方式：

  • 4人一组讨论3分钟，每组在便签上列出"隐患清单 + 改造建议"。
  • 教师随机抽3组回答，每组至少陈述1个隐患和1个改造点。
  • 其他组可补充或质疑（例如"JWT_SECRET算不算敏感信息"的讨论）。

学生输出：

  • 1份隐患清单（至少3条）。
  • 1份改造方案（ConfigMap键 + Secret键的划分）。

教师点评要点：

  • 强调"密码、Token、证书私钥、API Key"四类信息一律走Secret，是配置管理的红线。
  • 提醒base64不是加密，Secret只是"避免明文直视"，真正加密要靠静态加密（etcd encryption at rest）或外部密钥管理（Vault、KMS）。
  • LOG_LEVEL 这类环境差异配置应走ConfigMap，dev用DEBUG、prod用INFO，用不同ConfigMap或不同namespace区分。
  • 改造后修改密码只需 kubectl apply 更新Secret + 滚动重启，无需重新打镜像。

5.2 互动二：方案选择小辩论（约5分钟）

问题：CTTS数据库配置要挂载到Pod，A组主张用环境变量（env）、B组主张用Volume文件挂载。请两组各用1分钟陈述优劣，重点回答"哪种方式支持热更新"。

教师点评：

  • env：简单直观、适合少量键值、不支持热更新（Pod启动时注入，修改ConfigMap后已运行的Pod环境变量不变）。
  • Volume挂载：适合多文件/大配置、支持热更新（kubelet周期同步，Pod内文件自动变化）、应用需自行感知文件变化（如SpringBoot的refresh或inotify）。
  • 生产建议：需要热更新的走Volume，敏感且不应轮换的走env。

六、课程思政

6.1 主题

安全意识——敏感信息必须用Secret

6.2 融入方式

  • 导入阶段：以"某互联网公司因数据库密码写在前端代码，被程序员上传GitHub导致全网泄露"的真实案例切入，引出"配置安全是工程红线"。
  • 讲解阶段：强调三类信息（密码、证书私钥、API Token）必须走Secret，是DevSecOps的基本要求。结合《网络安全法》《数据安全法》《个人信息保护法》三法，说明企业在敏感信息保护上的法律责任。
  • 对比阶段：ConfigMap明文 vs Secret编码，让学生直观看到"明文存储=裸奔"，培养"默认安全"的思维。
  • 延伸阶段：介绍国家密码管理局推动的商用密码应用、国密算法（SM2/SM3/SM4）在云原生场景的落地，引导学生关注自主可控的安全技术。

6.3 思政小结

密码泄露是低级错误但后果严重——一次GitHub的误提交可能让企业损失数千万。Secret不只是技术工具，更是工程伦理的体现：开发者为用户数据负责，为雇主资产负责，为社会网络安全负责。掌握Secret的正确使用，是每一位云原生工程师的职业底线。

七、课堂练习

练习1（基础，5分钟）

写出一条 kubectl 命令，用字面量方式创建ConfigMap ctts-app-config，包含 LOG_LEVEL=INFO 和 APP_ENV=prod 两个键。

参考答案：

kubectl create configmap ctts-app-config \
  --from-literal=LOG_LEVEL=INFO \
  --from-literal=APP_ENV=prod

练习2（进阶，5分钟）

已知MySQL密码是 Ctts@2024，请用YAML方式定义一个Opaque类型的Secret ctts-db-secret，包含键 MYSQL_PASSWORD。给出base64编码过程和完整YAML。

参考答案：

# 编码
echo -n 'Ctts@2024' | base64
# 输出: Q3R0c0AyMDI0
apiVersion: v1
kind: Secret
metadata:
  name: ctts-db-secret
  namespace: default
type: Opaque
data:
  MYSQL_PASSWORD: Q3R0c0AyMDI0

练习3（拓展，3分钟，口头回答）

kubectl create secret generic db --from-literal=password=abc123 与在YAML里写 data.password: Base64(abc123) 两种方式，最终存到etcd里的内容是否一致？为什么推荐前者？

参考答案：

  • 最终结果一致，都是base64编码后存入etcd。
  • 推荐前者因为：① 命令行自动编码，避免手动 echo | base64 出错；② 命令行不会把明文写进YAML文件、不会进入Git历史；③ 更适合CI/CD脚本化。

八、课后任务

任务1（必做）：完成CTTS配置外置化并提交截图

  1. 将CTTS后端 application.yml 中的数据库配置（url、username）提取为ConfigMap ctts-db-config。
  2. 将密码提取为Secret ctts-db-secret（base64编码）。
  3. 修改 ctts-backend-deployment.yaml，用env方式挂载ConfigMap和Secret。
  4. 部署后 kubectl exec 进入Pod，执行 env | grep MYSQL 验证。
  5. 截图：kubectl get configmap、kubectl get secret、kubectl exec ... env 输出。

任务2（必做）：验证ConfigMap热更新

  1. 将数据库配置改为Volume文件挂载方式（挂载到 /etc/config/application.yml）。
  2. 部署后进入Pod查看挂载文件内容。
  3. 执行 kubectl edit configmap ctts-db-config，修改某个键值。
  4. 等待约1-2分钟，再次进入Pod查看文件是否变化（验证热更新）。
  5. 对比：用env方式挂载的键，修改ConfigMap后Pod内环境变量是否变化？（验证env不热更新）
  6. 提交：操作记录 + 对比结论（不少于200字）。

任务3（选做）：Secret类型探索

为CTTS创建一个 docker-registry 类型的Secret ctts-registry-secret，用于拉取私有镜像仓库的镜像。然后在Deployment的 spec.template.spec.imagePullSecrets 中引用。提交YAML和验证截图。

任务4（选做，面向岗位）：调研密钥管理方案

对比K8s原生Secret、HashiCorp Vault、阿里云KMS Secrets Manager、Sealed Secrets四种方案的差异，整理为表格（维度：加密强度、轮换能力、运维成本、与K8s集成度、是否开源）。写一段不少于300字的选型建议。
