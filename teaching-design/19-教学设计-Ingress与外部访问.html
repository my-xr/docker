二、教学目标

2.1 知识目标

  • K19-1：理解Ingress概念，能阐述七层HTTP/HTTPS路由的工作原理，对比Service四层负载的区别。
  • K19-2：掌握Ingress Controller的本质（独立Pod），熟悉Nginx Ingress Controller在Minikube下的安装方式。
  • K19-3：掌握Ingress资源YAML结构（apiVersion、kind、rules/host/path/backend、pathType）。
  • K19-4：理解域名虚拟主机与路径路由的两种模式，掌握defaultBackend兜底机制。
  • K19-5：掌握TLS/HTTPS配置方法，能创建TLS Secret并接入Ingress。

2.2 能力目标

  • 能独立为CTTS项目编写Ingress YAML，实现 frontend.ctts.local 路由到前端Service、api.ctts.local 路由到后端Service。
  • 能安装Nginx Ingress Controller、配置本机hosts、生成自签证书并完成HTTPS访问验证。
  • 能根据 kubectl get ingress、kubectl describe ingress、Controller Pod日志排查路由异常。
  • 能区分Prefix与Exact两种pathType的差异，并合理选用。

2.3 素质目标

  • 工程素养：建立"统一入口、单一对外"的架构审美，避免端口乱放、入口分散。
  • 用户体验意识：从使用者视角思考访问路径的设计，让"复杂后端"对用户透明。
  • 安全意识：理解HTTPS/TLS对生产环境的基础性意义，养成"明文HTTP不出网"的习惯。
  • 协作精神：Ingress涉及开发、运维、前端多方协作，培养接口契约意识。

四、项目任务

4.1 任务名称

CTTS项目Ingress统一入口配置

4.2 任务背景

CTTS项目已通过Deployment+Service部署到Minikube，目前前端Service（ctts-frontend：ClusterIP 80→8080）与后端Service（ctts-backend：ClusterIP 80→8081）仅集群内可访问。若使用NodePort对外，会出现端口难以记忆、无域名、无HTTPS等问题。本次课通过Ingress实现：

  • http://frontend.ctts.local → 前端Vue3页面
  • http://api.ctts.local/ → 后端SpringBoot REST API
  • 后续支持HTTPS：https://frontend.ctts.local、https://api.ctts.local

4.3 任务产出

  1. ctts-ingress.yaml（含两条host规则）
  2. ctts-tls-secret.yaml（或命令行创建的TLS Secret）
  3. ctts-ingress-tls.yaml（启用HTTPS的Ingress）
  4. 验证记录：kubectl get ingress 截图、浏览器访问截图、curl -H "Host: frontend.ctts.local" http://<minikube ip> 输出

4.4 任务流程

启用ingress addon → 确认Controller Pod运行 → 编写Ingress YAML
→ 应用YAML → 配置本机hosts → 浏览器/curl验证 → 生成自签证书
→ 创建TLS Secret → 更新Ingress TLS字段 → HTTPS验证

五、课堂互动

5.1 互动一：代码阅读——分析Ingress路由规则（核心互动，约10分钟）

问题：教师展示如下Ingress YAML，请学生口头回答5个问题。

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ctts-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: frontend.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-frontend
            port:
              number: 80
  - host: api.ctts.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: ctts-backend
            port:
              number: 80

提问清单：

  1. 该Ingress定义了几条路由规则？分别指向哪些Service？
  2. pathType: Prefix 表示什么？如果改为 Exact，访问 /user/login 还能命中吗？
  3. nginx.ingress.kubernetes.io/rewrite-target: / 这个注解的作用是什么？不加会怎样？
  4. 如果用户访问 http://frontend.ctts.local/abc/def，会被转发到哪个Service的哪个路径？
  5. 若用户访问的Host既不是 frontend.ctts.local 也不是 api.ctts.local（例如直接用IP访问），会发生什么？如何改善？

组织方式：

  • 4人一组讨论3分钟，每组指定一名发言人。
  • 教师随机抽3组回答，每组至少回答1题。
  • 其他组可补充或质疑。

学生输出：

  • 5个问题的口头答案。
  • 1份小组讨论纪要（课后提交至学习通）。

教师点评要点：

  • 第1题强调"host数=规则数=2"，每条规则内部paths可以是多条。
  • 第2题澄清Prefix是前缀匹配（含子路径），Exact是精确匹配（仅/本身）。
  • 第3题说明rewrite-target与前后端路径前缀差异的关系，提醒"非必要不重写"。
  • 第4题引导学生追踪 /abc/def 的命中流程：host匹配 → path前缀匹配 → 转发到 ctts-frontend:80/abc/def。
  • 第5题引出 defaultBackend，并联系K19-4。

5.2 互动二：方案对比小辩论（约5分钟）

问题：CTTS项目要对外发布，A组主张NodePort、B组主张LoadBalancer、C组主张Ingress。请三组各用1分钟陈述优劣。

教师点评：NodePort端口难记、LoadBalancer在本地Minikube需 minikube tunnel、Ingress统一入口且支持域名/TLS，是生产标准做法。

六、课程思政

6.1 主题

用户体验——统一入口让访问更简单

6.2 融入方式

  • 导入阶段：以"打开淘宝、访问GitHub"为例，用户只需输入一个域名，背后是成百上千个微服务。这背后正是Ingress这类七层网关在做"复杂后端、简单入口"的工作。
  • 讲解阶段：强调"统一入口"不仅是技术选择，更是产品哲学——把复杂留给自己，把简单留给用户。
  • 对比阶段：NodePort方式让用户记忆 IP:30001、IP:30002，是"以开发者为中心"的设计；Ingress用域名，是"以用户为中心"的设计。
  • 总结阶段：引申至软件工程的"接口契约"——好的接口对调用方友好、对提供方解耦。从CTTS的小入口，看大系统的统一治理。

6.3 思政小结

统一入口体现的是"用户至上"的工程伦理，是开发者为使用者负责的具体表现。在云原生时代，谁掌握了入口，谁就掌握了治理权——这也是国家推进自主云原生网关（如Higress、APISIX）的战略意义所在。

七、课堂练习

练习1（基础，5分钟）

写出一条Ingress规则：将 blog.ctts.local/blog 路径前缀路由到 blog-service:8080，pathType使用Prefix。

参考答案：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: blog-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: blog.ctts.local
    http:
      paths:
      - path: /blog
        pathType: Prefix
        backend:
          service:
            name: blog-service
            port:
              number: 8080

练习2（进阶，5分钟）

已有Ingress ctts-ingress，现要求在不删除原有规则的前提下，新增一条路径 /api/v2 路由到 ctts-backend-v2:80。简述操作步骤。

参考答案：

  • 使用 kubectl edit ingress ctts-ingress 或 kubectl apply 更新YAML，在 api.ctts.local 的paths下新增一条path：/api/v2，backend指向 ctts-backend-v2:80。
  • 注意路径匹配顺序：更具体的 /api/v2 应写在更宽泛的 / 之前（Nginx Ingress Controller会按最长前缀优先匹配）。

八、课后任务

任务1（必做）：完成CTTS Ingress配置并提交截图

  1. 启用Minikube ingress addon。
  2. 编写并应用 ctts-ingress.yaml，实现 frontend.ctts.local→前端、api.ctts.local→后端。
  3. 配置本机hosts文件，浏览器访问验证。
  4. 截图：kubectl get ingress、kubectl get pods -n ingress-nginx、浏览器访问 frontend.ctts.local 与 api.ctts.local/actuator/health 的页面。

任务2（必做）：为CTTS配置HTTPS

  1. 使用openssl生成自签证书（涵盖 frontend.ctts.local 与 api.ctts.local）。
  2. 创建TLS Secret。
  3. 更新Ingress的tls字段。
  4. 验证 https://frontend.ctts.local 可访问（浏览器可能警告证书不受信任，需手动接受）。

任务3（选做）：路径路由探索

为CTTS新增 ctts.local/admin 路由到 ctts-admin-service:80，探索rewrite-target注解对前端静态资源路径的影响，写一段不少于200字的总结。

任务4（选做，面向岗位）：调研云厂商Ingress Controller

对比阿里云SLB Ingress、腾讯云TKE Ingress、Nginx Ingress、Traefik、Higress的差异，整理为表格（维度：协议支持、性能、生态、成本、国内适配）。
