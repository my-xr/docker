二、教学目标

知识目标

  1. 理解 Service 的概念与作用——为什么需要 Service（Pod IP 不固定、Pod 会重建、负载均衡需求）。
  2. 掌握 Service 的四种类型：ClusterIP、NodePort、LoadBalancer、ExternalName，并能根据场景选择合适类型。
  3. 掌握 Service YAML 结构（apiVersion/kind/spec.type/selector/ports），理解 selector 如何关联 Pod。
  4. 理解 Endpoints 概念，掌握 kubectl get endpoints 查看后端 Pod 列表。
  5. 理解 DNS 服务发现机制（CoreDNS、service-name.namespace.svc.cluster.local 格式）。
  6. 掌握无选择器 Service 的应用场景与配置方式。

能力目标

  1. 能够编写 Service YAML（含 selector 关联 Pod、ports 配置）并部署到集群。
  2. 能够使用 kubectl get svc、kubectl describe svc、kubectl get endpoints 查询和排查 Service。
  3. 能够为 CTTS 三 Deployment（MySQL / Backend / Frontend）创建 ClusterIP Service，并验证服务发现与负载均衡。
  4. 能够通过 Service DNS 名实现服务间通信（后端通过 mysql Service 名访问数据库，前端通过 backend Service 名访问后端 API）。
  5. 能够根据访问需求选择合适的 Service 类型（ClusterIP 内部通信、NodePort 对外暴露）。

素质目标（课程思政）

  1. 培养"服务化思维"——微服务间通过 Service 通信，而非硬编码 IP，理解解耦的工程价值。
  2. 建立"稳定接口"意识——Service 提供稳定 IP 与 DNS 名，后端 Pod 可任意变更，体现"接口稳定、实现可变"的工程思想。
  3. 强化"系统协作"视角——从单 Pod 视角跃迁到服务间协作视角，理解云原生应用的组合艺术。

三、主要知识点纲要

详细讲解内容见同文件夹 教学资料.md，此处为纲要。

编号 知识点 要点
K18-1 Service 概念与作用 Pod IP 不固定；Pod 会重建；负载均衡需求；Service 提供稳定 IP + DNS 名 + 负载均衡
K18-2 Service 类型详解 ClusterIP（默认，集群内部）、NodePort（节点端口对外）、LoadBalancer（云负载均衡）、ExternalName（外部名称映射）；四种类型对比表
K18-3 Service YAML 结构 apiVersion: v1, kind: Service, spec.type/selector/ports；selector 关联 Pod 标签；ports.port/targetPort/nodePort
K18-4 标签选择器与 Endpoints selector 匹配 Pod 标签；Endpoints 端点列表概念；kubectl get endpoints 查看后端 Pod；无选择器 Service
K18-5 DNS 服务发现 CoreDNS 组件；Service DNS 名格式：service-name.namespace.svc.cluster.local；服务间通过 Service 名通信；跨命名空间访问
K18-6 CTTS 各 Service 创建 为三 Deployment 创建 ClusterIP Service；验证服务发现与负载均衡；后端通过 mysql Service 名访问数据库；前端通过 backend Service 名访问后端 API

四、项目任务或案例任务

贯穿项目任务：为 CTTS 各 Deployment 创建 Service

本次课任务：

  1. 教师演示：为 CTTS MySQL Deployment 创建 ClusterIP Service（mysql），验证后端可通过 mysql.ctts.svc.cluster.local 连接数据库。
  2. 学生实操：为 CTTS Backend Deployment 创建 ClusterIP Service（ctts-backend），验证前端 Nginx 可通过 ctts-backend.ctts.svc.cluster.local 反向代理到后端。
  3. 学生实操：为 CTTS Frontend Deployment 创建 ClusterIP Service（ctts-frontend），并用 kubectl port-forward 临时验证前端访问。
  4. 进阶任务：将前端 Service 改为 NodePort 类型，从集群外部通过节点端口访问前端页面。
  5. 验证：用 kubectl get endpoints 查看各 Service 的后端 Pod 列表，验证 Endpoints 与 Pod 标签的关联。

项目背景衔接（详见 教学资料.md 综合示例）：

  • 第 17 次课已部署 CTTS 三 Deployment（MySQL 1 副本 + Backend 3 副本 + Frontend 2 副本）。
  • 第 17 次课用 kubectl expose 临时创建了 mysql 和 ctts-backend 两个 Service（仅暴露端口，未深入讲解）。
  • 本节课系统学习 Service 理论，并为三 Deployment 编写标准 Service YAML，统一管理。
  • 本节课完成后，CTTS 集群内部服务间通信全链路打通：Frontend → ctts-backend Service → Backend Pods → mysql Service → MySQL Pod。

📌 本节课是 M7 模块（Service 与网络）的开篇课，重点建立 Service 概念体系。Ingress（第 19 次课）和 NetworkPolicy（第 20 次课）是后续延伸。

五、课堂互动设计

互动 1：课前 5 分钟回顾与问题导入（开场）

项目 内容
互动问题 "上节课我们部署了 CTTS 三个 Deployment。请问：后端 Pod 连接 MySQL 时，DB_HOST 写的是 mysql.ctts.svc.cluster.local——这个域名是怎么来的？如果 MySQL Pod 重建后 IP 变了，后端还能连上吗？"
组织方式 自由发言，教师板书关键词
预期学生输出 提到"Service""DNS""上节课用 kubectl expose 创建过""IP 变了应该还能连，因为有 Service"等关键词；部分学生可能答不上来
教师点评要点 肯定学生的回忆，引出"Service 是 K8s 中解决'Pod IP 不稳定'的核心机制"，本节课系统学习。强调"Service 提供稳定 IP + DNS 名 + 负载均衡"三大能力

互动 2：四种 Service 类型辨析（讲解 K18-2 后）

项目 内容
互动问题 给出 4 个场景：① 后端访问数据库；② 开发测试时临时从外部访问前端页面；③ 生产环境对外暴露 Web 服务（云厂商环境）；④ 集群内应用访问外部已有数据库（如 RDS）。判断各场景适合用哪种 Service 类型
组织方式 小组讨论 3 分钟 → 每组派代表发言 1 分钟 → 教师投影对比表讲解
预期学生输出 能区分：① ClusterIP（内部通信）；② NodePort（临时对外）；③ LoadBalancer（云生产对外）；④ ExternalName（外部名称映射）。部分场景可能有分歧（如②③都可能选 NodePort）
教师点评要点 强调"选择 Service 类型要看访问场景"：内部通信用 ClusterIP（最常见，默认）；临时对外调试用 NodePort（暴露节点端口）；云生产对外用 LoadBalancer（云厂商提供 ELB/SLB）；对接外部服务用 ExternalName（CNAME 映射）。生产环境对外访问通常用 Ingress（下节课学），NodePort/LoadBalancer 是底层机制

互动 3：Service YAML 找错（讲解 K18-3 后）

项目 内容
互动任务 教师给出一含错误的 Service YAML（selector 与 Pod 标签不匹配 / ports.targetPort 写错 / apiVersion 写错），学生 3 分钟内找出错误并修正
组织方式 个人独立完成 3 分钟 → 同桌互查 1 分钟 → 教师投影标准答案讲解
预期学生输出 能找出 selector 不匹配、targetPort 与 containerPort 不一致等常见错误
教师点评要点 强调"selector 必须与 Pod 模板的 labels 匹配""targetPort 必须与 containerPort 一致""apiVersion: v1（注意不是 apps/v1）"。这是 Service 部署最常见的踩坑点

互动 4：小组讨论——何时用 ClusterIP，何时用 NodePort（核心互动）

项目 内容
互动问题 "在 CTTS 项目中，三个 Service（mysql / ctts-backend / ctts-frontend）应该分别用哪种类型？为什么？如果让你对外发布 CTTS 前端，你会选 NodePort 还是其他方式？"
组织方式 4~5 人一组讨论 8 分钟 → 每组派代表发言 2 分钟 → 教师汇总点评
预期学生输出 mysql：ClusterIP（仅后端访问，不需要对外）；ctts-backend：ClusterIP（仅前端访问，不需要对外）；ctts-frontend：ClusterIP（默认）+ Ingress（生产对外）或 NodePort（临时调试）。讨论中可能产生分歧：部分学生认为前端应该直接用 NodePort 对外
教师点评要点 ① 内部服务（数据库、后端 API）一律 ClusterIP，避免不必要的对外暴露（安全原则）；② 前端对外通常用 Ingress（七层路由，下节课学），NodePort 仅用于临时调试或非云环境；③ 生产环境几乎不用 NodePort 直接对外（端口范围受限 30000-32767、暴露节点 IP 不优雅）；④ 体现"最小暴露原则"——只暴露必须暴露的服务

六、课程思政融入点

项目 内容
融入点 服务化思维——微服务间通过 Service 通信
技术关联 Service 提供稳定 IP + DNS 名，使微服务间解耦：调用方只需知道 Service 名，不需关心后端 Pod IP 与数量。这是"微服务架构"能在 K8s 上落地的核心基础
引导问题 "如果让你设计一个电商系统，订单服务要调用商品服务，你会让订单服务直接记商品服务的 Pod IP 吗？为什么？Service 这种'稳定接口 + 后端可变'的设计思想，在哪些领域也有体现？"
预期价值目标 建立"服务化思维"：接口稳定、实现可变；解耦是复杂系统协作的基础。引申到"标准接口""契约精神"——服务间通过标准协议通信，是工程协作的素养

思政自然融入：从技术层面的"Service 解耦"延伸到工程协作层面的"接口契约"，再到团队协作的"稳定承诺"。

七、课堂练习或随堂测验

随堂练习（5 分钟，讲解结束前进行）

判断题（口头快速作答）：

  1. Service 的 ClusterIP 类型只能在集群内部访问，外部无法直接访问。（✓）
  2. Service 通过 selector 关联 Pod，selector 必须与 Pod 的 labels 完全匹配。（✓）
  3. NodePort 类型的 Service 会占用节点的一个端口（默认 30000-32767）对外暴露。（✓）
  4. Pod 重建后 IP 变化，依赖该 Pod 的 Service 也会失效需要重建。（✗）

详细题目与解析见 题库.md。此处仅作课堂快速互动，不计分。

八、课后任务

  1. 阅读：通读同文件夹 教学资料.md，重点理解 Service 四种类型对比、Service YAML 结构、Endpoints、DNS 服务发现。
  2. 思考：用 200 字描述"为什么 K8s 需要 Service"，下次课抽查。
  3. 实操：在 Minikube 集群中为 CTTS 三 Deployment 编写标准 Service YAML（mysql / ctts-backend / ctts-frontend 均为 ClusterIP），apply 后用 kubectl get svc、kubectl get endpoints、kubectl exec ... nslookup 验证。
  4. 进阶实操：将 ctts-frontend Service 改为 NodePort 类型，从宿主机浏览器通过 minikube ip:节点端口 访问前端页面。
  5. 画图：手绘 CTTS 三 Service 与三 Deployment 的关联图，标出 selector、ClusterIP、Pod IP、DNS 名，下次课带到课堂。
  6. 思考题：为什么 Service 的 ClusterIP 是"虚拟 IP"（Virtual IP），无法被 ping 通但可以被 curl 访问？（为第 20 次课 K8s 网络进阶做铺垫）
