二、教学目标

知识目标

  1. 理解 Docker 网络子系统的定位，明确"为什么容器需要网络"以及容器网络要解决的核心问题（隔离、互通、外部访问）。
  2. 掌握 Docker 三种内置网络驱动 bridge、host、none 的原理、特点与适用场景。
  3. 理解默认 bridge 网络（docker0 网桥）的工作原理及其局限（无容器名 DNS 解析）。
  4. 掌握自定义网络（custom bridge）的创建方法及其相对默认 bridge 的两大优势：容器名 DNS 解析、更好的网络隔离。
  5. 掌握容器间通信的实现方式：通过容器名互访、docker network connect 跨网络通信、--network 指定网络运行容器。
  6. 巩固 -p 端口映射原理，能够为 CTTS 前后端 + MySQL 三服务设计完整的网络通信方案。

能力目标

  1. 能够使用 docker network ls / inspect / create / connect / disconnect 命令管理 Docker 网络。
  2. 能够根据应用场景选择合适的网络驱动（bridge / host / none）。
  3. 能够创建自定义 bridge 网络并通过容器名实现容器间 DNS 互访。
  4. 能够为 CTTS 三服务（前端 Nginx + 后端 SpringBoot + MySQL）设计并实现容器网络通信方案。
  5. 能够使用 docker network inspect 排查容器网络连通性问题。

素质目标（课程思政）

  1. 树立"网络安全"意识——容器网络隔离是纵深防御的第一道防线，理解"默认隔离、按需放通"的工程原则。
  2. 培养"最小暴露面"思维——对外只暴露必要端口（如前端 80），数据库容器不应直接对宿主机暴露端口。
  3. 建立"系统思维"——从前端到后端到数据库的整条调用链上，网络配置环环相扣。

三、主要知识点纲要

详细讲解内容见同文件夹 教学资料.md，此处为纲要。

编号 知识点 要点
K9-1 Docker 网络模型概述 为什么需要容器网络；容器网络解决的三大问题（隔离、互通、外部访问）；Docker 网络子系统与 libnetwork
K9-2 bridge 网络 默认网络驱动；docker0 网桥；bridge 网络原理（veth pair + iptables NAT）；默认 bridge 的局限（无 DNS、隔离弱）
K9-3 host 与 none 网络 host 共享宿主网络栈（无隔离、性能高、端口冲突）；none 无网络（完全隔离、安全沙箱）；适用场景与限制
K9-4 自定义网络 docker network create；自定义 bridge 的两大优势（容器名 DNS 解析、更好隔离）；自定义网络与默认 bridge 的对比
K9-5 容器间通信 通过容器名互访（DNS）；docker network connect 把容器接入第二个网络；--network 指定网络运行容器；跨网络通信原理
K9-6 端口映射回顾与 CTTS 网络设计 -p 端口映射原理回顾（宿主机端口→容器端口）；CTTS 前端/后端/MySQL 三服务网络通信方案设计；安全暴露原则

四、项目任务或案例任务

贯穿项目阶段任务：CTTS 三服务网络通信方案设计

本次课任务：

  1. 教师演示在默认 bridge 网络下，两个容器只能通过 IP 互访，无法通过容器名互访（痛点引入）。
  2. 教师演示创建自定义 bridge 网络 ctts-net，将两个容器加入该网络后，可通过容器名直接互访（方案验证）。
  3. 学生分组（每组 4~5 人），讨论并为 CTTS 三服务设计网络通信方案：
    • MySQL 容器：是否需要对外暴露端口？应接入哪个网络？
    • 后端容器：如何通过容器名访问 MySQL？是否需要对外暴露端口？
    • 前端容器：如何对外暴露？如何通过容器名访问后端 API？
  4. 每组用 5 分钟画一张 CTTS 三服务网络拓扑图，标出网络名、容器名、端口映射、容器间调用关系。
  5. 教师投影标准方案并点评，引出"默认隔离、按需放通"的安全设计原则。

项目背景对接（详见 教学资料.md 综合示例）：

  • 项目名称：多服务容器化部署项目（CTTS）
  • 三服务：CTTS-Frontend（Vue3+Nginx）+ CTTS-Backend（SpringBoot）+ MySQL 8.0
  • 本次课聚焦：三服务在同一台宿主机上的容器网络通信方案设计（为第 11 次课 Compose 编排做铺垫）

📌 本节课聚焦网络设计与命令演示，不敲 Dockerfile（第 6~8 次课已学）。三服务完整编排将在第 11 次课 Compose 完成。

五、课堂互动设计

互动 1：痛点引入（讲解 K9-2 后）

项目 内容
互动问题 "在默认 bridge 网络下，容器 A 想通过容器名访问容器 B，结果报错 Name or service not known。为什么？怎么办？"
组织方式 教师现场演示报错（已备好两个容器） → 学生观察 → 自由发言
预期学生输出 提到"默认 bridge 没有DNS""只能用 IP 访问""IP 会变不好记""要自己写 /etc/hosts"等
教师点评要点 肯定观察，引出默认 bridge 的两大局限：无容器名 DNS 解析、隔离弱；引出 K9-4 自定义网络

互动 2：三人网络对比辨析（讲解 K9-3 后）

项目 内容
互动问题 给出 4 个场景（①生产数据库容器需要完全隔离做安全沙箱、②调试网络抓包工具需要看宿主机所有流量、③Web 前端服务对用户暴露 80 端口、④后端 API 容器需要被前端按名访问），判断分别该用 host / none / bridge / 自定义 bridge 哪种网络
组织方式 全班举手投票，少数派陈述理由
预期学生输出 能区分"完全隔离用 none""抓宿主流量用 host""普通服务用 bridge""需要按名访问用自定义 bridge"；个别学生可能混淆 host 和 bridge
教师点评要点 强调"按需选型"——多数场景用自定义 bridge；host 仅在调试或对网络性能极致敏感时用；none 仅用于完全隔离场景

互动 3：两人一组讲解 Docker 网络通信流程（讲解 K9-5 后）

项目 内容
互动任务 两人一组，A 同学讲解"前端容器如何通过容器名访问后端容器 API"，B 同学讲解"后端容器如何通过容器名访问 MySQL"，互相提问，教师抽查 2~3 组上台讲解
组织方式 小组配对 5 分钟讨论 → 互相讲解 3 分钟 → 教师随机抽查 2~3 组上台（每组 2 分钟）
预期学生输出 A：前端容器 curl http://ctts-backend:8080/api/xxx 能通，因为同在 ctts-net 自定义 bridge 网络，Docker 内嵌 DNS 解析容器名 → 容器 IP。B：后端容器 mysql -h ctts-mysql -u root -p 能通，同理 DNS 解析。能画出"前端→后端→MySQL"调用链与网络归属
教师点评要点 重点纠正三类错误：①误认为容器名互访需要写 /etc/hosts（自定义 bridge 内置 DNS）；②误认为跨网络也能按容器名访问（必须同网络或 docker network connect）；③误认为 host 网络也能按容器名访问（host 模式无 DNS）。强调"同自定义网络 + 容器名"是容器间通信的推荐模式

互动 4：CTTS 网络方案设计（讲解 K9-6 时）

项目 内容
互动任务 分组为 CTTS 三服务设计网络通信方案：画出网络拓扑图，标出 ① 使用哪种网络驱动 ② 三个容器分别接入哪些网络 ③ 哪些端口需要对外映射 ④ 容器间如何互访
组织方式 小组讨论 8 分钟 → 每组派代表在白板画图 2 分钟 → 教师投影标准方案对比讲解
预期学生输出 能给出"自定义 bridge 网络 ctts-net，三容器都接入；前端 -p 80:80 对外暴露；后端 -p 8080:8080 暴露（或仅对前端通过容器名访问不暴露）；MySQL 不对外暴露端口，仅同网络内按容器名访问"的设计
教师点评要点 强调"最小暴露面"——MySQL 不应对外暴露端口；后端可以选择只对前端通过容器名访问而不对宿主机暴露；只有前端必须对外暴露 80。引出网络安全思政点

六、课程思政融入点

项目 内容
融入点 网络安全——容器网络隔离是纵深防御的第一道防线
技术关联 Docker 默认对每个容器分配独立网络命名空间（network namespace），容器之间默认隔离；通过自定义网络按需放通通信；通过 none 网络实现完全隔离的安全沙箱；通过"最小暴露面"原则（MySQL 不对外暴露端口）降低攻击面
引导问题 "如果把 MySQL 容器的 3306 端口直接 -p 3306:3306 暴露到宿主机公网，会有什么风险？为什么生产环境应该让 MySQL 只在同网络内被后端按名访问？"
预期价值目标 树立"默认隔离、按需放通"的网络安全意识；理解"最小暴露面"原则；把网络安全从"运维事后补救"前移到"架构设计阶段就考虑"

思政自然融入，不空喊口号。通过"MySQL 不该对公网暴露 3306"这一具体设计决策，让学生体会"网络安全是设计出来的，不是补丁打出来的"。

七、课堂练习或随堂测验

随堂练习（5 分钟，讲解结束前进行）

判断题（口头快速作答）：

  1. 默认 bridge 网络支持通过容器名互访。（✗）
  2. 自定义 bridge 网络支持通过容器名互访，因为 Docker 内嵌了 DNS 服务。（✓）
  3. host 网络模式下容器与宿主机共享网络栈，容器端口即宿主机端口。（✓）
  4. none 网络模式下容器没有任何网络接口，无法进行任何网络通信。（✗，有 lo 回环接口）

详细题目与解析见 题库.md。此处仅作课堂快速互动，不计分。

八、课后任务

  1. 阅读：通读同文件夹 教学资料.md，重点理解 bridge/host/none 三种网络的对比、自定义网络的两大优势、容器间通信的两种方式。
  2. 命令实操：在实验环境中按 教学资料.md 中的命令序列操作一遍：①查看默认网络 ②运行两个容器到默认 bridge，验证只能 IP 互访 ③创建自定义网络 ctts-net ④运行两个容器到 ctts-net，验证容器名互访 ⑤用 docker network connect 把容器接入第二个网络。
  3. 画图：手绘 CTTS 三服务网络拓扑图（含网络名、容器名、端口映射、调用关系），下次课带到课堂。
  4. 思考：用 200 字回答"为什么生产环境不建议把 MySQL 容器的 3306 端口直接映射到宿主机公网？"，下次课抽查。
  5. 项目准备：每组按 CTTS 三服务网络设计方案，提前准备好三个容器的启动命令序列（下次课数据卷课会用到）。
  6. 拓展阅读：访问 Docker 官方文档 docs.docker.com/network/ 了解 macvlan、ipvlan 等高级网络驱动（选做）。
